# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Учебник по **алгоритмическим шаблонам для собеседований** (на русском), собранный как
mdBook, с тремя слоями обучения:

1. **Книга** (`src/*.md`) — теория 27 паттернов: когда применять, алгоритм, сложность, код на Go.
2. **Интерактив** (`assets/*.js` + `*.css`) — встроенные в HTML визуализации, квиз-тренажёр
   распознавания паттернов и трекер прогресса.
3. **Go-тренажёр** (`exercises/`) — рабочий Go-модуль с заготовками функций и тестами:
   читатель пишет реализацию сам и проверяет её тестами.

Книгу читают локально (`mdbook serve`); CI только проверяет, публикации нет. Репозиторий: `github.com/fazletdinov/algorithms-book`.

## Команды

### Книга (запускать из корня репозитория)
```bash
mdbook serve        # dev-сервер с авто-пересборкой на http://localhost:3000
mdbook build        # компиляция src/ -> book/
```
mdBook читает из `src/`, пишет в `book/`. `book/` — генерируемый вывод, не редактировать вручную.

### Go-тренажёр (запускать из `exercises/`)
```bash
cd exercises
go test ./slidingwindow/                  # прогнать ТЕСТЫ ПОЛЬЗОВАТЕЛЬСКОЙ заготовки (красные, пока не реализовано)
go test -tags solution ./slidingwindow/   # прогнать те же тесты на ЭТАЛОННОМ решении (должны быть зелёные)
go test -tags solution -count=1 ./...      # все эталоны разом — это то, что проверяет CI
go vet  -tags solution ./...               # линт эталонов — тоже в CI
```
Запуск одного пакета — указать его путь (`./trie/`); один тест — `-run TestName`.

### Запуск под пределом памяти и времени (запускать из корня)
```bash
scripts/safe-run.sh go -C exercises test -tags solution -count=1 ./cmd/runner/   # предел по умолчанию: 2G и 120 с
SAFE_MEM=4G SAFE_SECS=600 scripts/safe-run.sh node scripts/keys-check.js          # пределы — переменными
```
`scripts/safe-run.sh <команда>` запускает её в отдельной cgroup-области
(`systemd-run --user --scope`, `MemoryMax` = `SAFE_MEM`, своп выключен) под `timeout`
(`SAFE_SECS`). Код 137 — упёрлась в память, 124 — в срок; область после упора в память
остаётся `failed`, поэтому скрипт сам делает `reset-failed`. Через неё идёт всё, что исполняет
непроверенный код — решение читателя, мутант, новый тест runner'а, jsdom-смоук: 2026-10-06
решение «BFS без `visited`» за ~25 с заняло 28 ГБ и уронило редактор. Нужен systemd с
пользовательским сеансом; в CI обёртка не используется.

### Postgres-лаборатория (запускать из корня)
```bash
make pg-lab        # поднять базу главы «Postgres: EXPLAIN как pprof» и налить данные
make pg-psql       # psql внутрь контейнера
make pg-lab-down   # погасить и стереть данные (volume)
```
Определение — `pglab/` (`docker-compose.yml` + `init.sql`). В CI НЕ участвует: это
упражнение читателя, а не проверяемый артефакт. Порт наружу — **25432**, намеренно ниже
эфемерного диапазона Linux (32768–60999): прежний 55432 лежал внутри него и случайно
оказывался занят чужим исходящим соединением («bind: address already in use» при пустом
списке слушающих). `pglab/n_plus_one.sh [N] [повторов]` — замер N+1 против пачки для главы
«Когда алгоритм не нужен»: время из `\timing` самого psql, по TCP внутри контейнера (то есть
лучший случай для N+1 — без сетевой задержки).

### Redis-лаборатория (запускать из корня)
```bash
make redis-lab        # настоящий Redis к главе «Капстоун: мини-Redis», ждёт PONG до 60 с
make redis-cli        # redis-cli внутри контейнера
make redis-lab-down   # погасить и стереть (volume)
redislab/measure.sh wire|ttl|active|all   # замеры главы: провод, TTL, активное удаление
```
Определение — `redislab/docker-compose.yml`: образ `redis:7.4-alpine` (замеры главы сняты с
Redis 7.4.11; точную версию печатает первая строка `measure.sh`), контейнер `algo-redislab`, без
снапшотов и AOF. Порт наружу — **26379** и только на `127.0.0.1` (ниже эфемерного диапазона, как
у `pglab/`): команда `DEBUG` включена (нужна для `DEBUG SET-ACTIVE-EXPIRE`) в режиме `local` —
её принимают только соединения изнутри контейнера (`docker exec`), клиент через опубликованный
порт получает отказ. `measure.sh` берёт сценарии из `scripts/fixtures/redis-golden.json` (вторая
копия разошлась бы с эталоном), печатает каждый запрос и сырой ответ (`od -c`), каждый раздел
начинает с `FLUSHALL`, а `DEBUG SET-ACTIVE-EXPIRE 1` возвращает через `trap`. В CI НЕ участвует,
как и `pglab/`. Docker Desktop завис — `DOCKER_CONTEXT=default make redis-lab` (переменную docker
читает сам, `measure.sh` тоже). Паузы в `ttl` — настоящие: шаг ровно на границе срока может от
прогона к прогону дать разный ответ — это свойство замера.

### In-book runner — «решай прямо в книге» (запускать из `exercises/`)
```bash
cd exercises
go run ./cmd/runner          # локальный helper-сервер на http://localhost:8080
```
Книга обращается сюда по fetch: виджет `<div class="algo-runner" data-pkg="X">` отдаёт
заготовку пакета как стартовый код, принимает код читателя и прогоняет НАСТОЯЩИЙ `go test`
(копирует модуль во временную папку, подменяет заготовку, `GOWORK=off`), возвращая
pass/fail. Эталон — только по «Сдаюсь» после первого прогона тестов упражнения, отдельной панелью; код читателя не меняется. Виджеты с
`data-race="true"` (concurrency-пакеты) гоняются с `-race` и подсвечивают гонки данных.
`/api/run` принимает необязательный `tests` — список имён, и тогда гоняет только их
(`go test -run '^(A|B)$'`; имена валидируются `^Test[A-Za-z0-9_]*$`, не больше 32 — список
уходит в регэксп; сборка аргументов — `testArgs`, покрыта `cmd/runner/main_test.go`, включая
мутацию «без якорей»). Это нужно мок-интервью: `panic("TODO")` в ЛЮБОЙ функции пакета роняет
весь тестовый бинарник, и тест нужной функции может не запуститься вовсе — проверено вживую:
в `dp` без фильтра первым падает `TestClimbStairs`, а `TestCoinChange` не стартует. Ответ
несёт `filtered: true`, и `runner.js` по нему НЕ пишет `algoPkgSolved` — одна зелёная
функция не делает пакет решённым. Атрибуты виджета: `data-tests` (JSON-массив),
`data-func` (упражнение задано снаружи, списка нет), `data-draft="mock|mixed|review"` (свой черновик
`algoRunnerCode:<draft>:<pkg>`; `data-fresh="true"` ≡ `mock`), `data-hints="off"` (без подсказок и эталона).
Без них — список всех `funcs` + «весь пакет»; единица прогона: свои `tests` → функция, иначе `groupTests`
типа, иначе пакет; по умолчанию первое без отметки в `algoFnSolved` (`{"<pkg>.<имя>": ts}`, пишется только по `ok`;
отметка значит «решал где-то», поэтому в своём черновике `data-draft` соседи из `needs` считаются нерешёнными)
с отмеченными `needs`; код — `plain`, черновик не трогается; подсказки и эталон — кнопками. Разбор заготовок — пакет `cmd/internal/stubdoc` (общий для runner'а и `cmd/problembank`):
`/api/stub` отдаёт `code` (всегда; недописанная заготовка на диске — 200 с `warning`), `plain` (без подсказок),
`funcs` (упражнения: `tests`, `needs` — соседи, нужные тестам и эталону, включая `Тип.Метод`, `group`/`groupTests`,
`hint`, `recipe`) и `notes` (убранное из `plain`); `/api/solution?pkg=&func=` — эталон одной функции с методами её
вспомогательного типа. Абзацы «Шаблон:»/«Также решается:»/«Признак:» дают поля банка `c`/`a`/`g`,
«Ожидаемая сложность» — `x`, `needs` — `n`; проверки — `stubdoc/*_test.go`, `cmd/runner/stub_test.go`. После каждого прогона виджет шлёт
событие `algo-runner:result` с `{pkg, ok, filtered, passed, failed, noTests, stage, fn, unit, draft, hints, gaveUp}` — так mixed.js узнаёт
о зелёных тестах, не завязываясь на разметку редактора; ещё `algo-runner:giveup {pkg, fn}` и `algo-runner:state {pkg, up}`.
**Пределы прогона** (`cmd/runner/run.go`: `runLimits`, `defaultLimits`) — зависшее решение
раньше давало немое «✗ есть падения», а тестовый бинарник оставался сиротой. Срок теста —
20 с (45 с с `-race`) — уходит в `go test -timeout`: бинарник сам падает с
`panic: test timed out after 20s`, и `parseTestOutput` по этой строке называет тест. События
`fail` у зависшего теста НЕТ (оно только у пакета) — он просто не завершён, так его и находит
`markUnfinished`. Запасной срок на всё — срок теста + 25 с (сборка на холодном кэше): по нему,
как и по уходу клиента (`r.Context()`), убивается ГРУППА процессов (`groupCommand` в
`proc_unix.go`: `Setpgid`, `SIGKILL` группе, `WaitDelay` 2 с — `SIGKILL` одному `go` оставлял
бинарник жить, а `Wait` — висеть на унаследованной им трубе; вне unix `proc_other.go` убивает
только саму команду). У своей группы есть цена: Ctrl+C в терминале и `kill 0` из `make serve`
шлют сигнал группе runner'а и до прогона НЕ доходят (измерено: `go test` и бинарник переживали
сигнал). Поэтому `main` ловит SIGINT/SIGTERM (`signal.NotifyContext`) и гасит контекст, который
`serve` отдаёт запросам как базовый (`http.Server.BaseContext`): отмена доходит до `r.Context()`
и убивает группу тем же путём, что уход клиента, затем `Shutdown` со сроком `shutdownGrace` = 5 с
(больше `WaitDelay`). Мутант «`Shutdown` без `BaseContext`» ловит
`TestServeStopKillsRunningTests`. Сырой вывод копит `cappedBuffer` — не больше 4 МиБ (`maxRunOutput`),
остальное отбрасывается, но запись «принимается»: ошибка записи убила бы процесс и подменила
картину. На потолке прогон останавливается сразу (`cappedBuffer.onFull` гасит контекст — та же
смерть группы, что по сроку): `go test -json` копит вывод теста у себя в памяти без потолка, и
`prlimit` этого роста не видит; поэтому тест потолка печатает ограниченно и засыпает, а не печатает
без конца. Потолок считает сырой поток событий, а не саму печать читателя. Окружение `go` — только
через `goEnv`: `GOTMPDIR` стоит внутри временной копии модуля, иначе убитый `SIGKILL` `go` оставляет
`go-build…` в системном `/tmp`.
Один прогон за раз: окно `server.slot` ёмкости 1 общее для `/api/run` и `/api/trace`,
второй запрос ждёт очереди (состояние — в `server`, не в глобальных переменных). Ответ
`/api/run` несёт `stage`, `timeout`, `truncated`, `noTests`, `reason` — готовую фразу («тест TestX не
уложился в 20s — похоже на бесконечный цикл») — и `killed: "timeout"` у записей `tests[]`. Текст ошибки компиляции с Go 1.24 идёт в `go test -json` не
сырыми строками, а событиями `build-output` (с `ImportPath` вместо `Package`): `parseTestOutput`
складывает их в `output` — без этого читатель видел «Ошибка компиляции» и одну строку
`FAIL … [build failed]`, без `undefined: …`. Случаи табличных тестов — подтесты (`t.Run`, так
написаны тесты 42 пакетов из 72), и сообщение упавшего случая `go test -json` приписывает подтесту
`TestX/случай`: `parseTestOutput` вливает вывод подтестов в `tests[].output` их теста в порядке
событий, опуская случаи, прошедшие молча; счёт, имена `tests[]` и фильтр `tests` — по-прежнему по
тестам верхнего уровня (`TestParseSubtestOutput`, `TestHandleRunShowsFailedCaseMessage`). У `/api/trace` те же группа и потолок (на потолке
запуск тоже останавливается сразу), срок сборки харнесса 20 с (`runLimits.BuildTimeout`), срок
запуска 5 с, переполненная трасса отвечает `timeout` с причиной «трасса не поместилась». Поле `build` в
его ответе идёт БЕЗ `omitempty`: `trace-viz.js` узнаёт ошибку сборки по `resp.build === false`
(после `unsupported`, до `timeout` — поэтому остановленная трасса несёт `build: true`), а
опущенное поле давало «Не удалось построить трассу» без вывода компилятора. Виджет ставит
`reason` первой строкой (⏱ — срок, 💾 — предел памяти, ✂ — обрезанный вывод, △ — ни один тест не
запустился, ✗ — любая другая причина: прогон не запустился вовсе, тестовый бинарник упал сам, не запустились
запрошенные тесты), зависший тест метит ⏱ вместо ✗, а остановку без
единого события тестов не выдаёт за «Ошибку компиляции». Вид отдан наружу —
`window.ALGO_RUNNER_VIEW = { result, status, limits }` — и проверяется без сервера готовыми
ответами, как и ветки `AlgoTraceViz` (ошибка сборки, срок, предел памяти, «не запустилась»,
неподдерживаемая форма): `scripts/runner-render-check.js` (в CI). Go-тесты (`run_test.go`,
`run_unix_test.go`, `mem_test.go`, `mem_unix_test.go`) гоняют
НАСТОЯЩИЙ `go test` на крошечных модулях во временном каталоге: зависание и ошибка компиляции
через обработчик, «бинарник не пережил отмену» и «не пережил остановку сервера», потолок вывода,
очередь в обоих обработчиках, форма ответа трассы. Поток событий при таймауте и при ошибке
компиляции сверен на Go 1.24.0 (в CI — ветка 1.24) и 1.26.5 — одинаков; тесты `cmd/runner`
зелёные на обеих (`GOTOOLCHAIN=go1.24.0 scripts/safe-run.sh go -C exercises test …`).
**Причины и `ok`** — у них один владелец, `verdict` (`run.go`, чистая функция; таблица —
`TestVerdict`; исключение — причину срока теста, `panic: test timed out`, пишет `parseTestOutput`, а `verdict` её
оставляет, если нет упора в память): он смотрит на конец прогона (`runEnd`), фильтр `tests` и поток — было ли хоть одно
событие, запущен ли бинарник (`start` у пакета без `build-fail`), кончился ли пакет итогом `pass`.
Отсюда `stage`: `launch` — ни одного события и ошибка `Run` («прогон не запустился: <первая строка
вывода>»), `build` — до бинарника дело не дошло, `tests` — он запущен (`build` истинно ровно тогда).
Упор в память или запасной срок на стадии `build` — причина про сборку (`starvedBuild`,
`slowBuildHint`), а не про код читателя; бинарник, упавший сам (паника при инициализации, выход с
ошибкой после тестов), — своя причина, а не «Ошибка компиляции» и не зелёный прогон. `ok` истинно,
только если пакет кончился `pass`, ничего не упало и не остановлено и запустились ВСЕ имена из
фильтра: совпало ни одного — `noTests: true`, часть — `ok: false` и «не запустились запрошенные
тесты: …». Ему верит машинная оценка карточек. Трасса: срок сборки — `build: true, timeout: true`,
отмена — `build: true` без `timeout`; харнесс первой строкой печатает `__TRACE_START__`, без неё
ненулевой выход — «трасса не запустилась: …», если в выводе нет паники рантайма (та — сбой в коде
читателя). Итогу области systemd, которая ещё `active`, верить нельзя: `scopeOOMKilled` ждёт до
300 мс. Замеры — в док-комментариях этих функций и их тестов.
**Предел памяти** (`cmd/runner/mem.go`: `memLimiter`, `detectMemLimiter`) — срок теста от
бесконечного роста не спасает: 2026-10-06 решение «BFS без `visited`» за ~25 с заняло 28 ГБ и
уронило редактор. Способ выбирается один раз при старте, от точного к грубому. (1) `cgroup` —
весь `go test` (и сборка) уходит в область `systemd-run --user --scope -p MemoryMax=N
-p MemorySwapMax=0`: ядро считает настоящую память всего дерева; своп выключен, иначе лишнее
уходило бы в подкачку и машина вставала раньше предела. Успешный запуск `systemd-run` ничего не
доказывает (без делегированного контроллера памяти область создаётся, а предел не действует),
поэтому `cgroupWorks` заводит пробную область на 64 МиБ и читает ИЗНУТРИ её `memory.max`.
(2) `rlimit` — `go test -exec 'prlimit --as=N --'`: предел АДРЕСОВ, и только тестовому бинарнику
(компилятору и компоновщику адреса не режем); не меньше 1 ГиБ, с `-race` — `max(2N, 4 ГиБ)`.
(3) `none` — ни того, ни другого (macOS, Windows): лог пишет «ВНИМАНИЕ», виджет — «⚠ без предела
памяти». Флаг `-mem-mb` — МиБ на прогон, по умолчанию 2048, `0` выключает предел. Упор узнаёт
`hitLimit`: у области — `systemctl --user show <unit>.scope -p ActiveState -p Result` = `oom-kill`
(systemd гасит `go` раньше, чем тот напечатает причину; итогу области, которая ещё `active`, верить
нельзя — см. `scopeOOMKilled` выше), у остальных — строки в выводе: `runtime: out of memory`,
`too many address space collisions for -race mode`, `ThreadSanitizer failed to allocate`,
`signal: killed` (так `go test` пишет о бинарнике, убитом ядром: docker `--memory`, OOM-killer).
`cleanupUnit` после прогона снимает область (`kill` → `stop` → `reset-failed`: область с
`oom-kill` иначе остаётся `failed` до конца сеанса). Ответ `/api/run`: `memLimit: true`,
`killed: "memory"` у незавершённых тестов, `reason` — «TestX: упёрлось в предел памяти 2 ГиБ —
похоже на бесконечный рост (например, обход без visited)»; ветка памяти стоит раньше срока
(`timeout` при ней ложен), `ok` ложен. Незавершённых тестов нет (ядро убило бинарник после
последнего) — вместо имени «прогон»; своего предела нет — «предел памяти машины». `/api/trace` —
то же для бинарника харнесса (`memLimiter.binary`; сборка харнесса идёт без предела): `memLimit`
+ `reason`, `build: true`. `/api/health` отдаёт `limits: { memory: "cgroup"|"rlimit"|"none",
memoryBytes, memoryText, testTimeout: "20s", raceTimeout: "45s" }`; виджет спрашивает его один
раз на страницу и ставит в шапку плашку «предел 2 ГиБ · 20 с» (`limitsBadge`; у виджета с
`data-race` срок берётся из `raceTimeout`, `rlimit` — «предел адресов …», `none` —
предупреждение, старый сервер без `limits` — плашки нет). Шапка виджета переносится
(`flex-wrap`): с плашкой она на телефоне не помещается в строку, и без переноса все плашки
сжимались в столбики по слову («🏁 / - / race») — смотрелось в Chrome на собранной книге, 390px
и 925px, тема navy, ответы сервера подставные. Заодно закрыта немая ветка: команда
(`go` или ограничитель перед ним) не запустилась вовсе — это `reason` «прогон не запустился: …» /
«трасса не запустилась: …», а не «Ошибка компиляции / (нет вывода)» и не «Паника» с пустым текстом
(признак теперь шире — «ни одного события и ошибка `Run`», см. «Причины и `ok`»).
Замеры (2026-10-06, Go 1.26.5,
systemd 255; пожиратель кусками по 16 МиБ, сам останавливается на 600–900 МиБ): (а) область
`MemoryMax=400M` — сборка и компоновка крошечного теста проходят, на ~370 МиБ ядро убивает
бинарник, systemd гасит область: `go` получает SIGTERM (код 143), вывод обрывается на `=== RUN`,
`Result` сразу `oom-kill`; (б) внутри пробной области `memory.max` = `67108864`; (в) `prlimit
--as` 768 МиБ — первое же выделение 16 МиБ падает (`runtime: out of memory: cannot allocate
16777216-byte block`), 1 ГиБ — то же при ≈300 МБ в куче (293–326 от прогона к прогону; у
бинарника трассы — 360); (г) `-race`: 2 ГиБ адресов — `fatal error: too many address space
collisions for -race mode` на первом выделении, 4 ГиБ — падение между 560 и 600 МиБ (той же
строкой либо `ThreadSanitizer failed to allocate …`). Отсюда нижние границы 1 и 4 ГиБ: 768 МиБ и
2 ГиБ — пороги запуска пустого бинарника, а не рабочие значения. На живом сервере под пределом
2 ГиБ эталоны `bits` и `wordcount` (с `-race`) зелёные. Тесты (`mem_unix_test.go`) гоняют
пожирателя под каждым способом, для прогона и для трассы, плюс контроль с обеих сторон: без
предела маленький дорастает, под каждым пределом (включая `rlimit` с `-race`) маленький проходит.
Пожиратель ограничен САМ — 900 МиБ: `systemd-run --user --scope`, вызванный изнутри
`scripts/safe-run.sh`, создаёт СОСЕДНЮЮ область, и внешний предел на неё не действует — сломанный
предел обязан давать красный тест, а не упавшую машину. Нет пользовательского systemd (раннер CI)

результат, и набор сам его не отличит: сломанная проба cgroup отправила бы все cgroup-тесты в

случай (28 ГБ), остался бы непроверенным. Поэтому `needCgroup` при `RUNNER_REQUIRE_CGROUP=1`

`RUNNER_REQUIRE_CGROUP=1 scripts/safe-run.sh go -C exercises test -tags solution -count=1 ./cmd/runner/`
(из корня; в CI переменная не задана). Мутант «проба `cgroupWorks` всегда возвращает `false`»
(2026-10-07): с переменной красные `TestDetectMemLimiterOrder/cgroup`, `TestMemLimitCgroupStopsEater`,
`TestMemLimitSparesSmallRun/cgroup`, `TestTraceMemLimitCgroupStopsEater`,
`TestTraceMemLimitSparesSmallRun/cgroup`, без неё — `ok` с пятью `SKIP`.
Мутанты: `MemoryMax` → `MemoryHigh` в `scopeArgs` — красные `TestMemLimiterCommand` /

## Архитектура Go-тренажёра (ключевой паттерн)

Каждый пакет шаблона состоит из **трёх файлов** с одинаковыми именами функций,
но взаимоисключающей компиляцией через build-теги:

- `<pkg>.go` — заготовки с `panic("TODO: ...")`, тег `//go:build !solution`
- `<pkg>_solution.go` — эталонная реализация, тег `//go:build solution`
- `<pkg>_test.go` — табличные тесты **без** build-тега (общая спецификация для обоих вариантов)

Без флага `-tags solution` компилируется заготовка (тесты падают), с флагом — эталон
(тесты проходят). Один и тот же тест-файл служит спецификацией обеих версий, поэтому
**сигнатуры функций в заготовке и эталоне должны совпадать дословно**, иначе сломается
компиляция теста. При добавлении/правке функции меняй заготовку, эталон и тест согласованно.

Чтобы добавить шаблон: создай папку `mypattern/` с этими тремя файлами по образцу
любого существующего пакета (см. `exercises/README.md`). Модуль — Go 1.24,
`module github.com/fazletdinov/algorithms-book/exercises`. Файл случайных тестов, если он нужен,
называется `<pkg>_zrand_test.go`: `go test` исполняет тесты в порядке файлов, и буква `z`
ставит его после табличного — на нетронутой заготовке первым падает тест первой функции, а не
случайный тест чужой (имя проверяет `scripts/check-registries.js`).

## Архитектура интерактива

Визуализации, квиз и трекер прогресса — это vanilla-JS/SVG без зависимостей и сборщика.
Файлы из `assets/` подключаются в HTML через `additional-css`/`additional-js` в `book.toml`,
поэтому **новый JS/CSS работает только после `mdbook build`/`serve`**, а не в сыром Markdown.

Встраивание в главы — через `<div>` с data-атрибутами:
- `<div class="algo-viz" data-viz="ТИП" data-array="..." data-k="..."></div>` — визуализация
  (`algo-viz.js`; типы: `sliding-window-fixed`, `two-pointers-sum`, `binary-search`,
  `cyclic-sort`, `dp-coins`, `tree-bfs`/`tree-dfs`, `graph-bfs` и др.)
- `<div class="algo-fig" data-fig="tree" data-tree="…" data-caption="…"></div>` — СТАТИЧЕСКИЙ рисунок
  вместо ASCII-схемы (`renderFig` в `algo-viz.js`, стили `.algo-fig*` в конце `algo-viz.css`): тот же
  `treeFigure`, что у виджетов, без шагов и управления. Формат `data-tree` — в комментарии над
  `parseFigTree` (скобки, `метка|подпись`, `*` — ★ конец слова, `!` — выделен, `@N` — сноска,
  `^` — поддерево-заглушка, `;` — следующее дерево со стрелкой, `data-titles`/`data-notes`/
  `data-row`; `_` — пустое место, держит сторону единственного ребёнка двоичного дерева
  (`2(_,5)` — 5 правый; родитель встаёт над пустым местом, ребёнок отстоит на целую колонку); `|` внутри `[…]` — часть метки, узел B-дерева `[2 | 4]`; `data-forest` —
  деревья через `;` рядом без стрелок, элемент ровно в одном дереве: лес union-find; `<`/`>` в
  атрибуте — `&lt;`/`&gt;`, иначе тег рвётся у регэкспов проверок). Ширина колонки — по самой широкой
  метке, измеренной при отрисовке (`figLabelPx`: зонд-узел с теми же классами даёт шрифт, поля и
  `scale` выделенного узла, текст меряет canvas; работает и в свёрнутом `<details>`) плюс 14px, но не
  меньше пола 11px на символ + 30 (шрифт может догрузиться позже; в jsdom canvas нет — только пол).
  Путь замера проверен ТОЛЬКО в браузере (у jsdom нет canvas и вёрстки): `fig-check` видит лишь пол,
  поэтому правка `figLabelPx` требует ручной сверки в Chrome (шаг колонки и зазор между листьями).
  **Служебные знаки и буквальные.** Везде (дерево, ряд, список, указатели, отрезки) куски делятся
  по `,`/`;` вне `[…]`: метка `[0,3]`, ячейка `[1,2]`, узел `[c,d]` — один кусок; непарная скобка —
  ошибка. Суффиксы `!`, `*`, `~`, `@N`, префикс `^`, пустое место `_` и `∅` служебны, буквальный знак
  — через `\` (`n\!`, `a\*`, `\@1`, `\_`, `\∅`, `\,`; список — `FIG_ESC` в `algo-viz.js`, экранировать
  другой знак — ошибка). Повтор суффикса (`a!!`, ячейка `x!!`) и второй `^` — видимая ошибка: так
  забытый `\` не съедается молча. `!` красит по-разному: в дереве — синий «текущий» узел
  (`algo-tp__tnode--current`), в ряду — зелёная заливка (`algo-tp__big--found`), в списке — зелёный
  узел (`algo-tp__llnode--found`).
  Ещё три вида тем же `renderFig` (`FIG_KINDS`): **`data-fig="array"`** — ряд или таблица на CSS-сетке
  (колонка на позицию, равной ширины) из классов неонового ряда (`algo-nn__cell`, `algo-nn__idx`,
  плашки `algo-nn__tagtx`): `data-array` (ряды `;`, `_` — пусто, `!` — выделено, `@a-b` — ячейка
  посчитана по ячейкам a…b первого ряда), `data-rows`, `data-index` (`1`, `none`), `data-index-label`,
  `data-ptrs`/`data-ptrs-top` (`имя@позиция`), `data-ranges` (`подпись@a-b`, уровни без наложений),
  `data-bars` (столбики); наведение: указатель/отрезок — свои ячейки, ячейка — свои плашки, отрезки,
  подпись ряда, номер и ячейки `@a-b`. Плашки и подписи отрезков не раздвигают колонки, а свисают;
  поля сетки при раскладке — по самому длинному свесу. **`data-array` у дерева** + `data-link="index"`
  (подпись узла `[c]`) или `"label"` (метка `c`) — ряд под деревом, наведение на узел зажигает его
  ячейку и наоборот (куча, `parent[]` union-find). **`data-fig="list"`** — узлы и стрелки списков
  виджетов (`algo-tp__llnode`): `data-list` (списки `;`; пусто или `∅` — пустой список, узел «∅» — `\∅`), `data-rows`, `data-ptrs`
  (`имя@i`, `имя@список:i`), `data-end` (по умолчанию `nil`); наведение на узел — путь до него от
  головы. **`data-fig="graph"`** — неориентированный граф через `graphVizFactory` виджетов:
  `data-nodes`, `data-edges`, `data-adj` (список смежности в порядке главы); наведение — вершина,
  рёбра, соседи, строка adj. Токены `--tp-*` объявлены на `.algo-tp, .algo-fig`. Узкая рамка: последовательность
  деревьев встаёт столбцом (`@container algo-fig`), широкое ужимается до 0.75 и дальше
  прокручивается в своём блоке. Тег — одной строкой. Рисунки (2026-10-12): деревья — `segment-tree-structure`,
  `avl-tree-structure` (поворот и LR), `trie-structure`, `bst-structure`, `btree-structure`,
  `heap-structure` и `union-find-structure` (с рядом), `tree-bfs` (два: уровни и, с 2026-10-14,
  номера мест под узлами для ширины уровня), `tree-dfs`, `backtracking`;
  ряды — `fenwick-tree-structure`, `sparse-table-structure`, `deque-structure`, `string-algorithms`,
  кольцо канала в `go-stdlib-structures`, гистограмма в `monotonic-stack`, таблицы — матрица в
  `graphs`, треугольник сумм в `prefix-sums`; списки — `linked-list-structure`, `hash-table-structure`;
  графы — два в `graphs`. Текстом оставлены: дерево выбора шаблона (`pattern-selection-guide`,
  135 строк), треугольник Паскаля (сдвиг на полклетки — суть «сумма двух над ним»), цепочка курсов
  в `topological-sort` (заголовок трассы раундов), JWT в `go-crypto-libraries`, таблицы-трассы.
  ASCII-дубли виджетов (`combination-sum` в `backtracking`, куча таймеров и роутер в
  `go-stdlib-structures`) убраны — текст ссылается на виджет. Держит `scripts/fig-check.js`
  (в CI: узлы и рёбра против независимого счёта меток, ряд, сноски, заголовки, подпись; кривые
  данные — видимая ошибка). **Подсветка** выводится из тех же данных, новых атрибутов нет:
  наведение, фокус клавиатуры или касание (закрепляет; повтор или касание мимо — снимает; Esc — снять,
  `stopPropagation`, стрелки рисунок НЕ трогает — их листает mdBook) на узле одного дерева
  отмечает путь к корню, а подпись `[l,r]` при `data-row` — ещё ячейки l…r; у дерева с ★ рядом
  список слов (корень → ★), слово и его ★ подсвечиваются вместе; в последовательности (`;`) — узел
  с той же меткой во всех деревьях (метка в дереве обязана быть уникальной, иначе ошибка); с
  атрибутом `data-diff` (по умолчанию выключен; есть у LR в AVL) рёбра, у которых ребёнок сменил
  родителя относительно прошлого дерева, — всегда янтарём (`--edge--changed`, токен
  `--fig-changed`, с легендой). Цвета со смыслом: зелёный акцент — только наведение, янтарь —
  «изменилось», голубой `--fig-trail` — статичный путь поиска/вставки: суффикс `~` у метки (путь

  отняли бы ←/→ у mdBook (правило книги), а без входа рисунок с 25 ячейками был бы 25 остановками
  Tab. Вершины графа — `role="img"` с `aria-label` («вершина 0, соседи: 1, 2»). Повторные
  раскладки (`ResizeObserver`, `fonts.ready`) — в той же обёртке, что первая отрисовка: исключение —

**Режим «🎯 Предсказывать»** (кнопка в ряду управления, общий для всех виджетов, ключ
`algoVizPredict`): на развилке виджет спрашивает исход ДО показа шага — снимок шага — это
состояние ПОСЛЕ его строки, и статус строки условия уже говорит «— да/— нет». Развилки
берутся из шагов и листинга без разметки (`predictionQuestions`/`branchOf`): строка
`if …{` / `} else if …{` / `for …{`, верный ответ — исход условия. Генератор может назвать его
сам: **`s.branch = true | false`** на шаге-развилке. Иначе исход выводится: попал ли следующий
шаг в тело блока (между строкой и парной скобкой, `blockEnd`; по `L+1` верное «Да» становилось
промахом у генераторов, пропускающих первую строку тела: 16 вопросов в 12 типах, из них 8 в ядре).
Вывод **«да» надёжен** (вошли в тело — условие истинно), вывод **«нет» — нет**: шаг вне тела
бывает и при истинном условии, когда тело не дало кадра (вложенный цикл без итераций,
`continue`, `return`, запись без кадра) — так верное «Да» становилось промахом ещё у 13 вопросов
(`three-sum-naive` ×5, `jump-game-dp`, `num-provinces-naive`, `string-match-naive` ×2,
`count-inversions-naive`, `mutex-bits`, `route-match` ×2). Правило для нового генератора: если
кадр на развилке ставится только при истинном условии или тело может не дать кадра — ставь
`branch`. Исключение из «да надёжно» — таймлайны горутин: следующий кадр там бывает чужой горутиной
(у `bfs-local-timeline` после проигранного G3 CAS идёт append победителя G1, и выведенное «да» было
неверным), поэтому их исход назван генератором, а правило (3) ниже для `bfs-local-timeline` снято
списком `INTERLEAVED` в `predict-check.js`. **Когда спрашивать** (`predCandidates` → `predChoose`,
этап 4, 2026-10-15): сам факт вопроса не выдаёт ответ. Раньше строку спрашивали при первой встрече и

- **Сверка «визуализация против алгоритма»** (все 186 виджетов, 2026-09-29): пошаговый дамп
  (строка кода, статус, чипы, состояние холста и панелей) разобран по четырём вопросам — итог
  против независимого эталона, шаг против строки, холст против переменных, текст главы против
  экрана. Итоговые ответы оказались верны везде; ~90 правок пришлись на подачу. Отсюда правила
  для любого нового генератора:
  1. **Снимок — состояние ПОСЛЕ подсвеченной строки.** Одна строка листинга — один кадр:
     `res[top] = v` и `pop`, `run += d` и `res[i] = run`, запись и `size++`, `swap` и `low++`/`mid++`
     не сливать — иначе строка с ключевым комментарием не подсвечивается никогда.
     Исключение — повторяющаяся подпрограмма (`siftDown` в `heap-sort`, `heap-build`, этап 4):
     построчно один вызов на фазу — первый, который опускает узел хотя бы на уровень (нет такого —
     первый вызов); в фазе 2 `heap-sort` — первый вызов, где на одном уровне срабатывают обе строки
     `largest = l` и `largest = r`, а нет такого — первый спуск. Остальные вызовы — кадр на уровень
     на ключевой строке: обмен — на строке обмена («дети 9 и 8, больший 9 > 5 → обмен»), остановка —
     на `largest == i` / `small == i`; кадра строки вызова у сжатого вызова нет, его называет первый
     кадр уровня. На входах глав каждая строка тела `siftDown` подсвечивается хотя бы раз; на своём
     вводе читателя это не гарантировано: на случайных входах `largest = l` нередко не подсвечивается
     ни разу — левый ребёнок не выигрывает ни в одном построчном вызове (в том числе на входах длиной
     от 3; 2026-10-15).
     Исход заголовков циклов и остановки сжатого вызова назван `s.branch`: за ними идёт кадр вне тела.
  2. **Чип — только переменная, живая на этой строке**: «—» до объявления и вне области
     видимости (тело цикла на заголовке `for`), `nil` — объявлена и пуста. Имя чипа = имя в
     листинге (`rx`/`ry`, `u`, `x`/`root`, `prev.Next`, `child`), а не пересказ.
  3. **Плашка указателя = значение одноимённой переменной.** Если на кадре она показывает не
     переменную (границы окна `text[:m]`, конец вхождения), имя меняет `ptrNames` на шаге.
     Правила 2–3 держит `scripts/check-viz-names.js` (jsdom, в CI): каждый тип проходится по
     всем шагам, имя чипа/плашки обязано состоять из идентификаторов листинга (комментарии и
     строки не в счёт, русская подпись — нарушение). Известные расхождения — в
     `scripts/viz-names-allow.json`: это храповик, новое нарушение И запись, которая больше не
     нарушается, роняют проверку, так что список только сокращается (было 251 в 118 типах; на
     2026-10-01 — 162 в 71, ядро чистое: последними были плашки `root`/`child` сортировки кучей,
     и их убрало тело `siftDown` в листинге виджета — плашки стали `i`/`largest`). Правка —
     переименовать под выражение листинга (`len(freq)`, `res[qi]`, `h.Len()`), дописать
     переменную в листинг (`top := stack[len(stack)-1]` в монотонном стеке — и плашка `top`
     стала честной до конца тела цикла) или убрать чип-пересказ вроде `action` (его место —
     строка шага). Плашку, у которой в коде нет переменной-индекса, скрывают (`name: "—"`),
     а в `range`-цикле без индекса она называется значением (`x`, `v`). Счётчики для
     наглядности («копий», «обменов», «правило» в ДП) — `cfg.metrics`: другой чип (пунктир,
     курсив), линтер их не сверяет с кодом, но требует русскую подпись без идентификаторов.
     Переименование ключа в генераторе ломает другие места конфига, читающие `s.vars.X`
     (`sumValues`, `stepCard`, `mapViz`), — рендер-смоук этого не видит (там будет «undefined»).
  4. **Листинг объявляет всё, что делает генератор** (`seen`, `mid`, `path`, `i--` после `fill`,
     очистка слота `recv`). Порядок перебора — как в коде (соседи по возрастанию индекса, а не в
     порядке рёбер атрибута), выбор при ничьей — одинаковый у генератора и у витрины.
  5. **Рантайм Go — как в рантайме**: escape-анализ решает компилятор (значение сразу в куче,
     ничего не «переезжает»), горутина в syscall не «исполняется» на P.
  Инструменты сверки — в scratchpad сессии (`vizshot/dumpall.mjs`, `trace.mjs`/`analyze.mjs`),
  в репозиторий не входят; эталоны ревьюеров — там же (`review/g*-work/`).

    листьями `nil` (`binaryFigure(..., nils)`), шаг `node == nil` подсвечивает свой. Разностный
    массив показывает «если собрать сейчас» — ступеньку от двух записей в `diff`.

`algo-runner` дополнительно умеет визуализировать РЕАЛЬНОЕ выполнение кода читателя (не
канонический пример, как `algo-viz`): атрибут `data-trace-calls='[{"func":"Имя","call":"Имя(...)"}, ...]'`
(JSON-массив — в файле пакета обычно несколько функций, читатель выбирает нужную в выпадающем
списке) включает кнопку «🎞 Визуализировать», которая шлёт код и выбор на `/api/trace`. Раннер
инструментирует функцию через `go/ast` (`cmd/runner/traceinstr`, см. его doc-комментарий —
поддерживаются циклы `for` И `range` ЛЮБОЙ вложенности (в т.ч. паттерн «сжимающееся окно» —
for внутри for, или for/range вперемешку) и if/else любой вложенности: снимок ставится ПОСЛЕ
КАЖДОГО оператора на любом уровне — это и даёт построчное прохождение, видно, какая именно
ветка/итерация сработала. НЕ поддерживаются: горутины, замыкания, рекурсия и циклы, спрятанные

возвращает пошаговый снимок переменных с номером строки; результат и переменные-указатели
(`*ListNode`/`*TreeNode`) сериализуются через JSON и рендерятся `trace-viz.js` читаемо (цепочка
списка, скобочная запись дерева), а не сырым адресом. `trace-viz.js` — отдельный универсальный
движок (панель кода с подсветкой текущей строки + таблица переменных + подсветка индексов на
массиве + автопроигрывание), НЕ переиспользующий `DASH`/`buildDashboard` из `algo-viz.js`.
Список включённых функций по пакетам — `traceTargets` в `cmd/runner/trace.go`: **133 функции в
42 пакетах**, трассировка есть в 36 главах — то есть покрыты практически все функции, форма
которых вообще инструментируется. Добавление пакета — строка в `traceTargets` +
`data-trace-calls` в его главе; согласованность этих двух мест проверяет

(разведчик: гоняет `traceinstr.Instrument` по ЭТАЛОНАМ — в заготовке тело `panic("TODO")`, там
нет циклов и не проходит ничего). Осталось 3 пригодных и намеренно НЕ подключённых —
`dsu.NewUnionFind` (тривиальный init), `miniredis.SaveSnapshot` (пишет файл),
`profiling.FormatScores` (её глава как раз о том, что по шагам проблему не видно) — причины
записаны рядом с `traceTargets`. Пригодность = экспортирована, не более одного возвращаемого
значения (без возврата — плюс строка в `traceVoidFuncs`: `CyclicSort`/`DutchFlagSort`/

быть воспроизводимой).

## Структура книги

`src/SUMMARY.md` — оглавление (его правка добавляет/убирает главы). 27 паттернов сгруппированы
от базовых (скользящее окно, два указателя) до продвинутых структур (дерево отрезков, Фенвик),
плюс вспомогательные страницы: `pattern-selection-guide.md`, `cheatsheet.md`, `quiz.md`,
`glossary.md`, `appendix-go-memory.md`. Язык контента — русский; код примеров — Go.

Маршрут ядра — порядок глав в `GROUPS` (`assets/progress.js`); второй копии нет. Порядок —
проверяемое правило: `check-registries.js` требует, чтобы порядок `GROUPS` совпадал с `SUMMARY.md`,
а `check-ladder.js` — чтобы «Вспомни» главы ядра опиралось только на главы ядра раньше неё по
маршруту, а его накопительный вопрос (`data-from`) возвращал приём на 2–4 главы назад. С этапа 3d глава об инвариантах стоит сразу за «Двумя указателями» (её примеры — из уже
прочитанных глав), а боковое оглавление приглушает главы расширения и справочника (`markToc`,
абзац о `progress.js` выше). Фундамент — `big-o`, `recursion`, `invariants` (главы языка) и
`hash-table-structure`, `linked-list-structure` (главы-устройства) — без раздела «## 🧭»: правило 1
ниже к ним не применяется, правила 2–5 — да; все главы ядра — в `REBUILT` линта формы, `ENDED` пуст.

Порядок главы-паттерна ядра — порядок открытия, а не проверки. Пять правил (с этапа 3a; механическую
часть держит `scripts/check-chapter-shape.js` для глав из списка `REBUILT`):
1. **«🧭» выводит приём на задаче первого виджета главы и шаблона «⚡»**: задача → перебор на числах → где повторяется работа → идея → жирная фраза-образ. Наивное решение в главе одно — из «🧭»; «📝 Разбор задачи» начинается ссылкой на «🧭» и даёт код и трассу, своего перебора не вводит. Намеренные исключения (не «исправляй»): в `graphs` «🧭» берёт частный случай — подсчёт провинций, а не задачу первого виджета (`graph-bfs`); `sorting` — глава двух приёмов, «🧭» в ней нет, и её «📝» может сохранять шаг через полную сортировку; `sliding-window`: «🧭» на семье B (самое короткое, набравшее цель), семья A — контрастным шагом за ним; первый виджет — окно постоянной длины, первая половина вывода; `dynamic-programming`: «🧭» на `rob` (образец вывода: перебор, счёт вызовов, мемоизация), первый виджет `dp-coins` — перенос вывода на размен монет, его вход не сокращается; `tree-dfs`: «🧭» на диаметре (ответ из ответов детей), первый виджет показывает preorder — первый урок даёт шаблон и прогон руками.
2. **В `<details>` уходит только то, без чего закрывается «основа»**: тяжёлые инженерные и строгие блоки — «⚙️ Второй проход: … — читать, когда освоишься», вывод одной фразой снаружи.
3. **«Основа» решается тем, что показала глава**; соседний приём — в добивке с названием. Названное в карточке, лестнице, вопросе 🧩 или тренажёре объяснено в главе хотя бы абзацем — иначе убрано из практики. В добивке такой пункт без объяснения в главе подписывается «— сверх главы».
4. **У главы есть конец:** после лестницы и виджета пакета — черта `> 🏁 **Глава сдана выше.** Дальше — …`, перед «🔗» — «📌 Что унести» из трёх строк: сигнал; что должно быть верно; где ломается и чем заменить. Конец есть у всех 23 глав ядра. Если у главы есть конкурентный раздел, виджет её пакета стоит выше черты, а конкурентный пакет — в своём разделе за ней (`top-k-elements`, `backtracking`, `graphs`). Строки «Что унести» — источник карточки `ch:` (генератор `scripts/gen-takeaways.js` собирает их в `assets/takeaways.js`). Строка «Что унести», ряд `assets/pairs.js` и карточка «Когда НЕ» об одной паре глав обязаны говорить одно и то же: правишь одно — перечитай два других (смысл машина не сверяет, это держит ревью).
5. **«Запомни» — до трёх пунктов, до 60 слов, без кода** (имя переменной можно, выражение нельзя); отдельный `<p>` рядом со списком тоже считается пунктом.

Определение приёма — вне свёрнутого «📖 Разбора»; «✍️ Прогони руками» — на входе, которого виджет выше не показывал, числа вопросов посчитаны кодом главы. Порядок `algo-challenge` не меняется, и число не уменьшается (id позиционный, `challenge.js`): ненужная задача заменяется на месте, новая — только в конец главы или с `data-id="<слаг>#rN"` (такой узел номера не занимает, см. абзац о `algo-review`). Образцы: `topological-sort` (порядок главы-шаблона), `dynamic-programming` (вывод и перенос), `heap-structure`/`linked-list-structure` (глава-устройство). Главы с «🧭» считает `grep -l '^## 🧭' src/*.md`.

Job `go-tests` (working-directory `exercises/`) проверяет четыре инварианта:
1. `gofmt -l .` — всё отформатировано;
2. `go vet -tags solution ./...` и `go test -tags solution -count=1 ./...` — эталоны корректны;
3. `go vet ./...` (без тега) — заготовки компилируются (ловит рассинхрон сигнатур заготовка/эталон/тест);
4. шаг «Заготовки ещё не решены» — untagged-тесты каждого пакета ДОЛЖНЫ падать (ловит решение, протёкшее в файл-заготовку).

Job `go-tests` также прогоняет `go run ./cmd/checksnippets -src ../src` — РАЗБОР (не компиляцию)
каждого ```go-листинга книги через `go/parser`. Компиляция здесь неприменима принципиально:
листинг намеренно не самодостаточен (показан метод, а не весь тип рядом), полная типизация даёт
под две сотни ложных «undefined» и потребовала бы ухудшить подачу ради зелёного CI. Разбор ловит
только то, что всегда ошибка: оборванная функция, лишняя скобка, потерянная при копировании
строка. Листинг может быть декларациями, фрагментом (тело цикла) или смешанным (import +
функции + пара строк) — инструмент пробует все три формы. Настоящий псевдокод (`for ... {`)
помечается строкой `<!-- snippet:pseudo -->` прямо перед ```go: в собранной книге это HTML-
комментарий, читателю не виден. Метка на листинге, который на самом деле разбирается, тоже
считается ошибкой — иначе метки расползлись бы и перестали что-либо значить.

Job `assets-check` помимо синтаксиса и смоуков виджетов прогоняет
`node scripts/check-registries.js` — сверку РУЧНЫХ реестров с реальностью: трекер прогресса

каталогов, `data-trace-calls`/`data-pkg` в главах против `traceTargets` (`cmd/runner/trace.go`)

(`<pkg>_zrand_test.go`, не `_rand_test.go`: `go test` исполняет тесты в порядке файлов, и со
старым именем первой на заготовке падала самая трудная функция). Расхождение здесь ничего не ломает
на сборке — оно тихо ухудшает книгу (трекер перестаёт считать реальные главы, виджет молча не

Глава [«Postgres: EXPLAIN как pprof»](../src/postgres-plans.md) — упражнение ТРЕТЬЕГО типа:

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Учебник по **алгоритмическим шаблонам для собеседований** (на русском), собранный как
mdBook, с тремя слоями обучения:

1. **Книга** (`src/*.md`) — теория 27 паттернов: когда применять, алгоритм, сложность, код на Go.
2. **Интерактив** (`assets/*.js` + `*.css`) — встроенные в HTML визуализации, квиз-тренажёр
   распознавания паттернов и трекер прогресса.
3. **Go-тренажёр** (`exercises/`) — рабочий Go-модуль с заготовками функций и тестами:
   читатель пишет реализацию сам и проверяет её тестами.

Проект деплоится на GitHub Pages через CI. Репозиторий: `github.com/fazletdinov/algorithms-book`.

## Команды

### Книга (запускать из корня репозитория)
```bash
mdbook serve        # dev-сервер с авто-пересборкой на http://localhost:3000
mdbook build        # компиляция src/ -> book/ (артефакт для GitHub Pages)
```
mdBook читает из `src/`, пишет в `book/`. `book/` — генерируемый вывод, не редактировать вручную.

### Go-тренажёр (запускать из `exercises/`)
```bash
cd exercises
go test ./slidingwindow/                  # прогнать ТЕСТЫ ПОЛЬЗОВАТЕЛЬСКОЙ заготовки (красные, пока не реализовано)
go test -tags solution ./slidingwindow/   # прогнать те же тесты на ЭТАЛОННОМ решении (должны быть зелёные)
go test -tags solution -count=1 ./...      # все эталоны разом — это то, что проверяет CI
go vet  -tags solution ./...               # линт эталонов — тоже в CI
```
Запуск одного пакета — указать его путь (`./trie/`); один тест — `-run TestName`.

### Postgres-лаборатория (запускать из корня)
```bash
make pg-lab        # поднять базу главы «Postgres: EXPLAIN как pprof» и налить данные
make pg-psql       # psql внутрь контейнера
make pg-lab-down   # погасить и стереть данные (volume)
```
Определение — `pglab/` (`docker-compose.yml` + `init.sql`). В CI НЕ участвует: это
упражнение читателя, а не проверяемый артефакт. Порт наружу — **25432**, намеренно ниже
эфемерного диапазона Linux (32768–60999): прежний 55432 лежал внутри него и случайно
оказывался занят чужим исходящим соединением («bind: address already in use» при пустом
списке слушающих). `pglab/n_plus_one.sh [N] [повторов]` — замер N+1 против пачки для главы
«Когда алгоритм не нужен»: время из `\timing` самого psql, по TCP внутри контейнера (то есть
лучший случай для N+1 — без сетевой задержки).

### In-book runner — «решай прямо в книге» (запускать из `exercises/`)
```bash
cd exercises
go run ./cmd/runner          # локальный helper-сервер на http://localhost:8080
```
Книга обращается сюда по fetch: виджет `<div class="algo-runner" data-pkg="X">` отдаёт
заготовку пакета как стартовый код, принимает код читателя и прогоняет НАСТОЯЩИЙ `go test`
(копирует модуль во временную папку, подменяет заготовку, `GOWORK=off`), возвращая
pass/fail. Эталон НЕ показывается — читатель решает сам, как на LeetCode. Виджеты с
`data-race="true"` (concurrency-пакеты) гоняются с `-race` и подсвечивают гонки данных.
`/api/run` принимает необязательный `tests` — список имён, и тогда гоняет только их
(`go test -run '^(A|B)$'`; имена валидируются `^Test[A-Za-z0-9_]*$`, не больше 32 — список
уходит в регэксп; сборка аргументов — `testArgs`, покрыта `cmd/runner/main_test.go`, включая
мутацию «без якорей»). Это нужно мок-интервью: `panic("TODO")` в ЛЮБОЙ функции пакета роняет
весь тестовый бинарник, и тест нужной функции может не запуститься вовсе — проверено вживую:
в `dp` без фильтра первым падает `TestLISRandom`, а `TestCoinChange` не стартует. Ответ
несёт `filtered: true`, и `runner.js` по нему НЕ пишет `algoPkgSolved` — одна зелёная
функция не делает пакет решённым. Атрибуты виджета: `data-tests` (JSON-массив),
`data-fresh="true"` (старт с заготовки, черновик под `algoRunnerCode:mock:<pkg>`, решение
пакета из главы не подсовывается и не затирается). После каждого прогона виджет шлёт
событие `algo-runner:result` с `{pkg, ok, filtered, passed, failed}` — так mixed.js узнаёт
о зелёных тестах, не завязываясь на разметку редактора.
Сервис локальный/однопользовательский, поэтому без песочницы: адрес принудительно приводится к
`localhost` (это инвариант, а не дефолт — `/api/run` исполняет присланный код), CORS ограничен
origin'ами книги. Единственное исключение — флаг `-listen-all` для запуска ВНУТРИ контейнера
(`make docker-runner` = `docker run -p 127.0.0.1:8080:8080 ... go run ./cmd/runner -listen-all`),
где «все интерфейсы» — это всё ещё сеть контейнера, а до хоста порт доводит docker, публикуя его
на петлю. Для «ничего не ставить локально» есть `.devcontainer/` (Go 1.24 + Node + mdBook нужной
версии, порты 3000/8080); в браузерных Codespaces книга ходит не на `localhost`, поэтому адрес
runner'а задаётся через `localStorage.setItem('algoRunnerUrl', ...)` — подсказка об этом есть в
самом виджете, когда сервер не отвечает. Реализация — `cmd/runner/`,
фронт — `assets/runner.js`+`runner.css` (подключены в `book.toml`).

## Архитектура Go-тренажёра (ключевой паттерн)

Каждый пакет шаблона состоит из **трёх файлов** с одинаковыми именами функций,
но взаимоисключающей компиляцией через build-теги:

- `<pkg>.go` — заготовки с `panic("TODO: ...")`, тег `//go:build !solution`
- `<pkg>_solution.go` — эталонная реализация, тег `//go:build solution`
- `<pkg>_test.go` — табличные тесты **без** build-тега (общая спецификация для обоих вариантов)

Без флага `-tags solution` компилируется заготовка (тесты падают), с флагом — эталон
(тесты проходят). Один и тот же тест-файл служит спецификацией обеих версий, поэтому
**сигнатуры функций в заготовке и эталоне должны совпадать дословно**, иначе сломается
компиляция теста. При добавлении/правке функции меняй заготовку, эталон и тест согласованно.

Чтобы добавить шаблон: создай папку `mypattern/` с этими тремя файлами по образцу
любого существующего пакета (см. `exercises/README.md`). Модуль — Go 1.24,
`module github.com/fazletdinov/algorithms-book/exercises`.

## Архитектура интерактива

Визуализации, квиз и трекер прогресса — это vanilla-JS/SVG без зависимостей и сборщика.
Файлы из `assets/` подключаются в HTML через `additional-css`/`additional-js` в `book.toml`,
поэтому **новый JS/CSS работает только после `mdbook build`/`serve`**, а не в сыром Markdown.

Встраивание в главы — через `<div>` с data-атрибутами:
- `<div class="algo-viz" data-viz="ТИП" data-array="..." data-k="..."></div>` — визуализация
  (`algo-viz.js`; типы: `sliding-window-fixed`, `two-pointers-sum`, `binary-search`,
  `cyclic-sort`, `dp-coins`, `tree-bfs`/`tree-dfs`, `graph-bfs` и др.)
- `<div class="algo-quiz"></div>` — квиз распознавания паттернов (`quiz.js`, см. `src/quiz.md`)
- `<div class="algo-progress"></div>` — трекер прогресса в localStorage (`progress.js`, см. `src/cheatsheet.md`).
  У каждой главы в реестре `GROUPS` есть поле **`lvl`** — уровень маршрута: `core` (ядро, 23 главы),
  `ext` (расширение, 25), `ref` (справочник, 18), `tool` (квиз/шпаргалка/руководство — не главы, 3).
  Процент и полоса считаются **только по ядру**, расширение и справочник идут отдельной строкой
  (`.algo-prog__aside`): шестьдесят глав в оглавлении выглядят одинаково обязательными, и именно
  на этом курс бросают. Тот же реестр ставит плашку уровня под заголовком главы —
  функция `markPage()` в `progress.js` работает на КАЖДОЙ странице книги, поэтому размечать
  сорок файлов руками не нужно (две разметки неизбежно разъехались бы). У глав ядра и
  инструментов плашки нет намеренно: молчание означает «ты на пути». Согласованность
  проверяют `scripts/check-registries.js` (у каждой главы есть валидный `lvl`) и
  `scripts/progress-render-check.js` (процент не двигается от отметки главы вне ядра).
  Парная вещь — **лестница задач** в разделе «Прорешать целиком»: три ступени
  (`**🟢 Разогрев**` → `**🔵 Основа**` → `**🔴 Добивка**`) плюс строка «Не пошла задача…»
  с конкретной подсказкой, куда вернуться. Плоский список ссылок на LeetCode не отвечал на
  два вопроса — в каком порядке решать и что делать, когда застрял; ступень «основа» задаёт
  ещё и точку остановки («закрыл основу — глава сдана»). Есть в 18 главах ядра; у остальных
  пяти глав ядра списка задач нет вовсе — там практика это пакет тренажёра, и лестница была
  бы искусственной. Формат держит `scripts/check-ladder.js` (ступени на месте и по порядку,
  ни одна не пуста, подсказка есть; уровень главы берёт из того же `progress.js`);
  там же кнопки экспорта/импорта: выгружают ВСЕ ключи книги (`algoProgress`, `algoChallengeSolved`,
  `algoChallengeMissed`, `algoQuizBest`, `algoRunnerCode:*`, `algoMockLog`, `algoMockCxMissed`, …
  — список `PREFIXES` в `progress.js`) в один JSON и вливают его обратно СЛИЯНИЕМ, а не
  заменой — иначе перенос с другой машины стирал бы уже пройденное здесь. Слияние —
  `mergeStored`: карты объединяются по ключам, МАССИВЫ — по записям без дублей (история
  собеседований — список, и слияние «по ключам» перезаписывало бы его по индексу)
- `<div class="algo-mixed"></div>` — смешанная тренировка (`mixed.js`, страница
  [`mixed.md`](../src/mixed.md)): случайная задача тренажёра БЕЗ имени пакета, главы и
  подсказок; сначала «какой шаблон?» (4 варианта — темы других задач банка, распорки не
  ведутся руками), потом раскрываются подсказки, ссылка на главу и редактор с настоящими
  тестами. Банк — `assets/problems.js`, **генерируется** из док-комментариев заготовок
  (`cd exercises && go run ./cmd/problembank`, в CI `-check`): дублировать условия руками
  значило бы завести второй источник правды. Абзацы, называющие приём («Подсказка: …»,
  «Ожидаемая сложность: …»), отделяются в поле `h` и показываются только ПОСЛЕ ответа —
  на отсортированном массиве «O(log n)» и есть готовый ответ. Промах → `algoMixedMissed`
  → карточка `mix:<pkg>.<fn>` в `srs.js` + приоритет при следующей выдаче. Динамически
  созданный виджет runner'а поднимается через `window.ALGO_RUNNER_INIT` (обычный
  `DOMContentLoaded` к тому моменту давно прошёл). **Режим собеседования** (галочка над
  задачей): таймер 35 мин (не блокирует, фиксирует перебор) → шаблон → план словами ≥ 80
  символов (гейт; длину проверяет сам `onclick`, а не только `disabled` кнопки) → редактор с
  `data-tests` = поле `t` банка и `data-fresh` → после события `algo-runner:result` с `ok` —
  сложность своими словами, ПОТОМ эталон из абзаца «Ожидаемая сложность» и самооценка →
  итог. Подсказки и глава скрыты до итога (среди них эталон). Выдаёт только задачи с
  непустым `t` (176 из 181). История — `algoMockLog`, промах по сложности → `algoMockCxMissed`
  → карточка `cx:<pkg>.<fn>` в `srs.js` (отдельно от `mix:`: узнать приём и оценить свой код
  — разные умения). Поле `t` считает `cmd/problembank`: тест `TestF…` принадлежит функции с
  САМЫМ ДЛИННЫМ совпавшим именем (`TestSubsetsWithDup` — `SubsetsWithDup`, не `Subsets`),
  продолжение со строчной буквы — другое слово (`ownerOf`, покрыт тестом на четырёх реальных
  коллизиях банка). Поведение проверяет `mixed-check.js` сценарием целиком, включая
  детерминированную проверку «задачу без тестов не выдаёт» (все задачи с тестами помечаются
  показанными — иначе 5 из 167 ловились бы случайно)
- `<div class="algo-weakspots"></div>` — диагностика «какой ПРИЁМ не узнаётся по условию»
  (`review.js`, страница «Повторение»): промахи квиза (`algoQuizMissed`, пишется в
  `quiz.js` — до этого хранился только рекорд «40/57», то есть было неизвестно, ЧТО именно
  не далось) и смешанной тренировки, сложенные по шаблонам
- `<div class="algo-explain" data-key="слаг-главы">` — режим «объясни сам» (`explain.js`):
  стоит В НАЧАЛЕ раздела «🧠 Почему это корректно» в 12 главах, где инвариант — суть дела
  (`sliding-window`, `prefix-sums`, `two-pointers`, `monotonic-stack`, `modified-binary-search`, `fast-slow-pointers`,
  `cyclic-sort`, `merge-intervals`, `greedy`, `dynamic-programming`, `topological-sort`,
  `union-find-structure`). Вопросы и эталоны лежат в разметке главы (`__q`/`__ref`), эталон
  скрыт, пока не заполнены ВСЕ поля — единственный жёсткий гейт в книге и он намеренный:
  разбор лежит абзацем ниже, обойти можно, но осознанно. Самооценка пишет `algoExplainDone`
  → карточка `expl:<глава>` в `srs.js`. При повторном заходе поле пустое, прошлый ответ — под
  кнопкой (предзаполненное поле убивает воспроизведение). Линт — `scripts/check-explain.js`
  (ключ = слаг главы, ≥2 вопроса, эталон не заглушка, виджет до разбора), поведение —
  `scripts/explain-check.js` на СОБРАННОЙ странице
- `<div class="algo-today"></div>` — очередь интервальных повторений (`srs.js`, страница
  [«Повторение»](../src/review.md)). Карточки заводятся САМИ (полный список источников — шапка `srs.js`; ниже три исходных): отмеченная в
  трекере глава (`algoProgress`), позеленевший в runner'е пакет (`algoPkgSolved` — пишется в
  `runner.js` при `res.ok && !res.filtered`, единственный момент, когда «пакет решён» вообще известно) и промах
  в задаче (`algoChallengeMissed`). Расписание — упрощённый SM-2: интервалы 1 → 3 → `iv*ease`,
  `ease` ∈ [1.3, 2.8]; «забыл» роняет интервал в день и спрашивает «в чём была ошибка»
  (заметка показывается при следующем повторе этой карточки). Глава и пакет заводятся со
  сроком «завтра», промах — «сегодня». Состояние — ключ `algoSRS`, входит в экспорт прогресса.
  Арифметику расписания проверяет `scripts/srs-check.js`, а не глазами
- `<div class="algo-review"></div>` — «повторить промахи» (`review.js`, см. `src/cheatsheet.md`):
  список задач, которые не дались, сгруппированный по главам, со ссылкой на конкретную задачу.
  Данные копит `challenge.js`. Важная деталь: id задачи выводится сам («страница#порядковый
  номер»), потому что `data-id` не проставлен НИ В ОДНОЙ главе — раньше `markSolved` из-за этого
  молча не сохранял ничего, и `algoChallengeSolved` всегда был пуст. Виджеты задач заодно
  получают якорь `id="task-N"`, чтобы ссылка вела прямо к задаче

Виджеты поддерживают пошаговую навигацию стрелками (←/→, Home/End).

**Пресеты граничных случаев** (идея взята у AlgoMaster): поле `presets` в конфиге типа DASH —
`[{ label, set: { "data-…": "…" }, hint }]`. Под полем ввода встают кнопки «Граничные случаи:»,
первая всегда «пример главы» (исходные атрибуты запоминаются на узле `root.__algoOrig` при
первой отрисовке и переживают перезапуски — `rerun()` строит виджет на том же `root`).
Пресеты задаются на ТИП, а не на главу: граничные случаи — свойство алгоритма («нет
пересечений», «перекрёст скобок», «все равны»), и так они появляются во всех главах с этим
виджетом без правки разметки. Пресет обязан задавать РОВНО поля ввода своего типа —
недостающее поле осталось бы от прошлого пресета, и кнопка показывала бы разное в
зависимости от порядка нажатий; это держит `check-viz.js` (правило 4, проверено поломкой в
обе стороны). Сейчас 86 пресетов у 25 типов (главы ядра плюс циклическая сортировка); все нажаты в
Chrome с прошагиванием до конца, итоговые статусы прочитаны (0 ошибок). После нажатия фокус возвращается на новую
кнопку через `setTimeout` — `focus()` на ещё не вставленном узле молча не срабатывает.

**Раскладка по умолчанию** (подсмотрена у AlgoMaster; `compactLayout()` в `algo-viz.js`): сверху
вниз — ввод (свёрнут, пока читатель его не открыл: `root.__algoInputOpen` переживает перезапуск
пресетом), холст, строка шага, чипы переменных, управление ▶ ‹ › ползунок, счётчик, скорость
0.5×–4×, ⛶, затем код. Итоги, правила, таблица переменных и сложность отсоединены: блок
«Подробнее» убран намеренно — холст и чипы показывают всё, что нужно на шаге. `data-layout="classic"`
на виджете возвращает старую двухколоночную раскладку (в главах не используется, это запасной
выход). Шевроны ‹ › — SVG одного размера: прежние «◀» и «⏵» — разные символы шрифта и рисовались разного размера.

- **Неоновый массив** (`algo-nn`) заменяет сетку у всех типов без `customViz`. Состояния ячеек —
  те же классы `algo-tp__big--*`, что у сетки, поэтому `cellState` конфигов не менялись, но
  выглядят они иначе: `found` — зелёная заливка, `lo` — зелёная рамка, `hi` — голубая рамка,
  `mid` — жёлтая, `span` — голубой оттенок, `dim` — пунктир и тусклость, `out` — красный пунктир.
  Указатели — плашки на ножке, которые ЕЗДЯТ (transform + transition): `ptr2` голубая сверху,
  `ptr1` зелёная снизу. Подпись ряда — `cfg.arrLabel` или имя параметра из сигнатуры листинга
  (`nums`, `arr`, `s`…); для листингов без массива в сигнатуре `arrLabel` задан явно. Из-за
  другой палитры тексты глав описывают цвета по неону («зелёная плашка снизу — `slow`»), а
  легенда получает поле **`legend[].nn`** — состояние неона, образец которого показать
  (двойки флага — фиолетовые в сетке, но голубая рамка в неоне; без `nn` легенда врала).
  Для ячеек не массива (панели, узлы) `nn` не ставится.
- **Перенос значений** (Web Animations API, только на шаге ВПЕРЁД, выключен при
  `prefers-reduced-motion`): пары ячеек с переставленными значениями едут сами по дугам
  (обмен), значение, скопированное из ячейки ПОД указателем, летит янтарным «призраком»
  (копия), вычисленное — только вспыхивает. Копию ищут лишь из-под указателя: «ближайшая
  ячейка с тем же значением» выдумывала переносы, которых в алгоритме нет. Старые значения
  берутся из `steps[prev].values`, а не из DOM — во время полёта в DOM ещё старые тексты, и
  быстрые шаги перезапускали полёт. Для обмена в главе «Два указателя» есть `move-zeroes`
  рядом с `two-pointers-dedup` (там копия — рисовать её обменом было бы неправдой); листинг
  `move-zeroes` — обмен одной строкой, чтобы подсвеченная строка и анимация совпадали буквально.
  Эвристика знает три исключения, найденные сверкой «анимация против строки кода» по всем
  1261 шагу неоновых виджетов: «пустые» значения (`·`, `—`, `?`, `∅`) не летят и не
  меняются местами (очистка слота буфера — запись, а не копия пустоты из-под указателя);
  `cfg.noMoves` — ячейки независимы, всё только вспыхивает (биты мьютекса: CAS меняет два
  бита «навстречу», и это выглядело обменом); 3+ ячейки, переставленные за шаг (свёрнутый
  `partition` в quick-select), летят каждая из своей старой ячейки, а не россыпью копий и
  вспышек. Та же сверка поймала плашки Рабина — Карпа, опережавшие `i++` на шаг.
- **Вкладки** `<div class="algo-viz-tabs">` вокруг нескольких `algo-viz` с `data-tab="Название"`
  — один холст вместо стопки (перебор/оптимум, копия/обмен).
- **Рисунки деревьев** (`treeFigure`) на узком холсте ужимаются `zoom`-ом до 0.6 (дальше
  честнее прокрутка): 8 листьев дерева отрезков шире телефона. Ребро начинается под подписью
  узла, только если подпись НЕ пуста (`__syncEdges`, зовётся после каждого шага): подписи
  диаметра «h=…» появляются по ходу, и ребро от пустого места висело в воздухе. Генератор
  `trie-delete` раньше обнулял `children[ch]`, и рисунок, строящийся ПОСЛЕ прогона, брал
  удалённый узел за корень — остальные узлы слипались в точку.
- **Сверка «визуализация против алгоритма»** (все 186 виджетов, 2026-09-29): пошаговый дамп
  (строка кода, статус, чипы, состояние холста и панелей) разобран по четырём вопросам — итог
  против независимого эталона, шаг против строки, холст против переменных, текст главы против
  экрана. Итоговые ответы оказались верны везде; ~90 правок пришлись на подачу. Отсюда правила
  для любого нового генератора:
  1. **Снимок — состояние ПОСЛЕ подсвеченной строки.** Одна строка листинга — один кадр:
     `res[top] = v` и `pop`, `run += d` и `res[i] = run`, запись и `size++`, `swap` и `low++`/`mid++`
     не сливать — иначе строка с ключевым комментарием не подсвечивается никогда.
  2. **Чип — только переменная, живая на этой строке**: «—» до объявления и вне области
     видимости (тело цикла на заголовке `for`), `nil` — объявлена и пуста. Имя чипа = имя в
     листинге (`rx`/`ry`, `u`, `x`/`root`, `prev.Next`, `child`), а не пересказ.
  3. **Плашка указателя = значение одноимённой переменной.** Если на кадре она показывает не
     переменную (границы окна `text[:m]`, конец вхождения), имя меняет `ptrNames` на шаге.
  4. **Листинг объявляет всё, что делает генератор** (`seen`, `mid`, `path`, `i--` после `fill`,
     очистка слота `recv`). Порядок перебора — как в коде (соседи по возрастанию индекса, а не в
     порядке рёбер атрибута), выбор при ничьей — одинаковый у генератора и у витрины.
  5. **Рантайм Go — как в рантайме**: escape-анализ решает компилятор (значение сразу в куче,
     ничего не «переезжает»), горутина в syscall не «исполняется» на P.
  Инструменты сверки — в scratchpad сессии (`vizshot/dumpall.mjs`, `trace.mjs`/`analyze.mjs`),
  в репозиторий не входят; эталоны ревьюеров — там же (`review/g*-work/`).
- На 320–400px ряд управления — две строки (кнопки + скорость, ползунок + счётчик); холст в
  новой раскладке сжимает боковые поля сильнее классической панели. Оставшиеся переполнения
  холста на 400px (knapsack, rabin-karp, list-reverse-between) — старые широкие таблицы и

`algo-runner` дополнительно умеет визуализировать РЕАЛЬНОЕ выполнение кода читателя (не
канонический пример, как `algo-viz`): атрибут `data-trace-calls='[{"func":"Имя","call":"Имя(...)"}, ...]'`
(JSON-массив — в файле пакета обычно несколько функций, читатель выбирает нужную в выпадающем
списке) включает кнопку «🎞 Визуализировать», которая шлёт код и выбор на `/api/trace`. Раннер
инструментирует функцию через `go/ast` (`cmd/runner/traceinstr`, см. его doc-комментарий —
поддерживаются циклы `for` И `range` ЛЮБОЙ вложенности (в т.ч. паттерн «сжимающееся окно» —
for внутри for, или for/range вперемешку) и if/else любой вложенности: снимок ставится ПОСЛЕ
КАЖДОГО оператора на любом уровне — это и даёт построчное прохождение, видно, какая именно
ветка/итерация сработала. НЕ поддерживаются: горутины, замыкания, рекурсия и циклы, спрятанные
внутри switch/select (`reachableLoop` держит это условие согласованным с тем, куда реально
заходит инструментация, — не даёт молча неполную трассу), прогоняет функцию один раз и
возвращает пошаговый снимок переменных с номером строки; результат и переменные-указатели
(`*ListNode`/`*TreeNode`) сериализуются через JSON и рендерятся `trace-viz.js` читаемо (цепочка
списка, скобочная запись дерева), а не сырым адресом. `trace-viz.js` — отдельный универсальный
движок (панель кода с подсветкой текущей строки + таблица переменных + подсветка индексов на
массиве + автопроигрывание), НЕ переиспользующий `DASH`/`buildDashboard` из `algo-viz.js`.
Список включённых функций по пакетам — `traceTargets` в `cmd/runner/trace.go`: **133 функции в
42 пакетах**, трассировка есть в 36 главах — то есть покрыты практически все функции, форма
которых вообще инструментируется. Добавление пакета — строка в `traceTargets` +
`data-trace-calls` в его главе; согласованность этих двух мест проверяет
`scripts/check-registries.js`. Что ещё МОЖНО подключить, показывает `go run ./cmd/tracescan`
(разведчик: гоняет `traceinstr.Instrument` по ЭТАЛОНАМ — в заготовке тело `panic("TODO")`, там
нет циклов и не проходит ничего). Осталось 3 пригодных и намеренно НЕ подключённых —
`dsu.NewUnionFind` (тривиальный init), `miniredis.SaveSnapshot` (пишет файл),
`profiling.FormatScores` (её глава как раз о том, что по шагам проблему не видно) — причины
записаны рядом с `traceTargets`. Пригодность = экспортирована, не более одного возвращаемого
значения (без возврата — плюс строка в `traceVoidFuncs`: `CyclicSort`/`DutchFlagSort`/

фиксированным зерном (`sampling.Shuffle`/`ReservoirSample` иначе не вызвать, а трасса обязана
быть воспроизводимой).

## CI/CD

`.github/workflows/ci.yml`: job `go-tests`, `assets-check` и `build-book` (`mdbook build`
+ `check-links.js`) должны пройти; затем job `deploy` публикует `book/` на GitHub Pages
**только из ветки main**. Job `build-book` после сборки прогоняет `node scripts/check-links.js`
— целостность внутренних ссылок/якорей по собранному `book/`.

Job `go-tests` (working-directory `exercises/`) проверяет четыре инварианта:
1. `gofmt -l .` — всё отформатировано;
2. `go vet -tags solution ./...` и `go test -tags solution -count=1 ./...` — эталоны корректны;
3. `go vet ./...` (без тега) — заготовки компилируются (ловит рассинхрон сигнатур заготовка/эталон/тест);
4. шаг «Заготовки ещё не решены» — untagged-тесты каждого пакета ДОЛЖНЫ падать (ловит решение, протёкшее в файл-заготовку).

Job `go-tests` также прогоняет `go run ./cmd/checksnippets -src ../src` — РАЗБОР (не компиляцию)
каждого ```go-листинга книги через `go/parser`. Компиляция здесь неприменима принципиально:
листинг намеренно не самодостаточен (показан метод, а не весь тип рядом), полная типизация даёт
под две сотни ложных «undefined» и потребовала бы ухудшить подачу ради зелёного CI. Разбор ловит
только то, что всегда ошибка: оборванная функция, лишняя скобка, потерянная при копировании
строка. Листинг может быть декларациями, фрагментом (тело цикла) или смешанным (import +
функции + пара строк) — инструмент пробует все три формы. Настоящий псевдокод (`for ... {`)
помечается строкой `<!-- snippet:pseudo -->` прямо перед ```go: в собранной книге это HTML-
комментарий, читателю не виден. Метка на листинге, который на самом деле разбирается, тоже
считается ошибкой — иначе метки расползлись бы и перестали что-либо значить.

Job `assets-check` помимо синтаксиса и смоуков виджетов прогоняет
`node scripts/check-registries.js` — сверку РУЧНЫХ реестров с реальностью: трекер прогресса
(`assets/progress.js`) против `src/SUMMARY.md`, таблица пакетов в `exercises/README.md` против
каталогов, `data-trace-calls`/`data-pkg` в главах против `traceTargets` (`cmd/runner/trace.go`)
и списка пакетов, счётчик пакетов в этом файле против факта. Расхождение здесь ничего не ломает
на сборке — оно тихо ухудшает книгу (трекер перестаёт считать реальные главы, виджет молча не
находит пакет, «🎞 Визуализировать» отвечает отказом), поэтому и вынесено в CI. Там же
`node scripts/progress-render-check.js` — jsdom-смоук самого трекера (его содержимое зашито в JS,
`check-viz.js` его не видит): все главы и группы отрисовались, отметка обновляет процент, счётчик
группы и `localStorage`, сброс работает.

Перед коммитом локально прогоняй `gofmt -l exercises`, `go test -tags solution -count=1 ./...`
(из `exercises/`), `mdbook build`, `node scripts/check-links.js` и `node scripts/check-registries.js`
(из корня) — это ровно то, что проверит CI. jsdom-смоуки требуют `npm i --no-save jsdom`; без
него они мягко пропускаются (exit 0), поэтому локально их отсутствие не блокирует, а в CI
jsdom ставится всегда.

В корне есть `go.work` (`use ./exercises`) — он нужен только для IDE/gopls, чтобы при открытии
корня репозитория модуль из `exercises/` был виден (иначе gopls ругается «module not in workspace»).

`ratelimiter`, `streamstats`, `leaderboard`, `cache`. `miniredis` (глава
[«Капстоун»](../src/miniredis.md)) — сквозной проект поверх этих флагманов, растёт по этапам;
с этапа 2 у него обычная пара заготовка/эталон (`miniredis.go`/`miniredis_solution.go` —
на этапе 7: `dispatchSet`/`dispatchGet`/`dispatchDel`/`dispatchExpire`/`dispatchTTL`/
`dispatchZAdd`/`dispatchZScore`/`dispatchZRange`/`dispatchZRank`/`RateLimitReply`/
`SaveSnapshot`/`LoadSnapshot`/`dispatchSave`), а протокол
(`resp.go`), маршрутизация и `PING`/`ECHO` (`dispatch.go`), тип `Store` с TTL/ZSET и `live()`/
`zsetOrdered()` (`store.go`) даны готовыми без тега — общая инфраструктура, не задача с
решением. `Store.now func() time.Time` — впрыск часов для тестов TTL без `time.Sleep`
(протокол `EXPIRE`/`TTL` не пробрасывает время параметром, в отличие от
`cache.TTLCache.Get(key, nowMs)` — значит, часы пришлось внедрить на уровень стора, а не
функции). `zsetOrdered` сортирует ПО ВОЗРАСТАНИЮ очков (в отличие от
`leaderboard.Leaderboard.ordered()`, который по убыванию) — так `ZRANGE`/`ZRANK` ведут себя
как настоящий Redis, а не как таблица лидеров. Этап 5 — не RESP-команда, а мидлварь:
`RateLimitReply` оборачивает `ratelimiter.TokenBucket` (пакет `ratelimiter`, уже реализован
читателем во флагмане) в готовый `Reply`-или-`nil`; ведро заводится НА СОЕДИНЕНИЕ в
`cmd/miniredis/main.go` (не в `Store`, который общий на всех клиентов) — поэтому обычный
`TokenBucket`, без `SafeTokenBucket`, корректен без мьютекса: наглядный контраст со `Store`,
которому мьютекс нужен именно потому, что он shared. Этап 6 (опциональный) не добавляет TODO — `store.mu` был обязателен уже с этапа 2, здесь неявное допущение
делается явным: `miniredis_concurrent_test.go` (дан готовым) гоняет `DEL` по общим 200 ключам из
8 горутин под `-race` и проверяет точный инвариант (сумма удалений по всем горутинам == 200,
как `TestSafeTokenBucketConcurrent` в `ratelimiter`), а не просто «тест не упал». Этап 7
(маршрут капстоуна завершён) — персистентность: `SaveSnapshot`/`LoadSnapshot`/`dispatchSave`
(`SAVE`), автозагрузка при старте и сохранение по SIGINT/SIGTERM даны готовыми в
`cmd/miniredis/main.go` (флаг `-db`, по умолчанию `dump.rdb`; сам файл — в `.gitignore`).
Суть этапа не в команде, а в АТОМАРНОСТИ записи: снапшот пишется во временный файл рядом
с целью (`os.CreateTemp(filepath.Dir(path), ...)` — тот же раздел ФС, иначе `os.Rename`
провалится cross-device) и переносится `os.Rename`; прямой `os.WriteFile` открывает файл с
`O_TRUNC` и делает состояние наблюдаемым «наполовину». `TestSnapshotSaveIsAtomic`
(`persistence_test.go`, дан готовым) это ГОНЯЕТ, а не описывает: 300 раундов SaveSnapshot
против 300 раундов LoadSnapshot в отдельных горутинах, допустимо НОЛЬ ошибок декодирования —
намеренный контраст с этапом 6, где разделяемой была память (её сторожит `store.mu` и видит
`-race`), а здесь разделяемый ресурс — файл, и `-race`/мьютекс про него ничего не знают.
Сериализуется НЕ `*Store` (мьютекс + неэкспортируемые поля), а отдельный `snapshotData` с
экспортируемыми полями (`gob`), причём копия карт снимается под `store.mu`, а кодирование и
запись идут уже без него — критическая секция не включает дисковую операцию (учебный аналог
`BGSAVE`-мотивации настоящего Redis). TTL в снапшоте — АБСОЛЮТНЫЕ `time.Time`, как unix-ms в
настоящем RDB: ключ, протухший за время простоя, после загрузки мёртв, а не воскресает. Проверка
«Заготовки ещё не решены» в CI
(`.github/workflows/ci.yml`)
принципиально смотрит только на пакеты с физическим `<pkg>_solution.go`, поэтому `miniredis`
(и `cmd/*`) сама собой не ловится, пока решать нечего, и сама начинает ловиться, как только
solution-файл появляется — обновлять исключение вручную не нужно. Список функций каждого
пакета — в `exercises/README.md`. При добавлении/
удалении пакета обнови это число (проверка: `ls -d exercises/*/ | grep -v cmd | wc -l`, сейчас 72).

настоящего Redis); упавший вход остался в затравке `FuzzReadCommand` как регрессионный тест.
Раздел в `src/miniredis.md` также оставляет читателю парную самостоятельную задачу — так же
ограничить `readLine` (аналог `proto-inline-max-size`) и дописать для неё свою затравку.

`codereview` (глава [«Ревью чужого кода»](../src/code-review.md)) — один из двух пакетов ДРУГОГО
типа упражнения (второй — `profiling`, см. ниже): три функции уже полностью реализованы (никаких `panic("TODO")`), но в каждой
спрятан один изъян, который ловится только тестом/`-race`, а не чтением сигнатуры — задача не
дописать, а продиагностировать и исправить прямо в `codereview.go` (`!solution`), сверяясь с
`codereview_solution.go` только после. Три сценария: (1) `SumSquaresConcurrent` — двойной изъян:
целочисленное усечение `len(nums)/workers` детерминированно теряет «хвост» (не гонка, ловится
обычным `go test` без `-race` на входе длины 101 при `workers>1`) + разделяемый `total +=` без
синхронизации (отдельная гонка, ловится только `-race`, детектор указывает на конкретную строку);
эталон убирает и то, и другое разом — не мьютексом, а тем, что у каждой горутины своя локальная
сумма и результат идёт через `chan int64` (нечему гонять, если нет разделяемой памяти); (2)
`HasDuplicate` — корректен, но O(n²); ловится не сравнением ответа, а дедлайном по времени
(`TestHasDuplicateScales`: 200000 различных чисел, эталон ~7мс, заготовка ~4.8с, порог 2с — запас
на порядки в обе стороны, откалиброван эмпирически на этой машине); эталон — тот же компромисс
время/память, что и в `hashtable`; (3) `ParseAndSum` — проглатывает ошибку `strconv.Atoi` через
`continue` вместо возврата вызывающему коду (анти-паттерн «error проверили, но не обработали»).

`profiling` (раздел «Практика: найди узкое место сам» в `../src/appendix-go-memory.md`) — второй
пакет другого типа: `FormatScores` (`profiling.go`, `!solution`) уже отвечает ПРАВИЛЬНО (табличный
тест это подтверждает), но по коду не видно, что она на порядки медленнее, чем нужно — задача не
дописать, а измерить (`go test -run='^$' -cpuprofile=cpu.prof -bench=. ./profiling/`, затем
`go tool pprof -top -cum cpu.prof`), понять причину и починить. Автоматическая проверка фикса —
не сравнение ответа, а бюджет аллокаций через `testing.AllocsPerRun` (`TestFormatScoresAllocs`):
заготовка (`result += fmt.Sprintf(...)` в цикле) аллоцирует ~2745 раз за вызов на 1000 элементах,
эталон — ~2 (измерено на этой машине, бюджет теста — 20, запас на порядки в обе стороны). Реально
измеренный CPU-профиль отдаёт больше трети времени под `runtime.concatstrings` (копирование при
каждом `+=`, строки в Go неизменяемы — O(n²) байт скопировано, хотя цикл линеен по итерациям) и
почти столько же — под фоновую сборку мусора (`gcBgMarkWorker`), а не под сам `fmt.Sprintf`, как
подсказывает интуиция «дорого форматирование» — ровно то, что и находит профилирование, а не
чтение кода. Эталон — `strings.Builder.Grow` (одна аллокация под весь отчёт заранее) +
`strconv.AppendInt` в переиспользуемый буфер (не `strconv.Itoa`, который всё ещё аллоцировал бы
новую строку на каждое число).

`ahocorasick` (глава [«Ахо — Корасик»](../src/aho-corasick.md), Группа 6 после Trie,
`lvl: ext`) — связка Trie + префикс-функция KMP: `NewAutomaton` (Trie, ссылки неудачи ОБХОДОМ В
ШИРИНУ, словарные ссылки), `Automaton.FindAll` / `ContainsAny`, `Censor` (звёздочка на РУНУ, не
на байт; незакрытые байты — как есть, даже невалидный UTF-8). `Match`, `NaiveFindAll` и
`SortMatches` даны готовыми в `naive.go` без тега — это и модель для рандомной сверки на
алфавите из трёх букв (там шаблоны постоянно вложены друг в друга). Отдельные табличные случаи:
классика «ushers» из статьи и `abcd`/`bc` на `abcx` — вхождение, видное ТОЛЬКО по словарной
ссылке (без него мутация «ContainsAny без словарных ссылок» ловилась лишь рандомным тестом, без
понятного имени). Девять мутаций — все пойманы. Главный замер главы честный и неудобный:
на 10 шаблонах наивный `strings.Index` в 4.3 раза БЫСТРЕЕ автомата (4.6 против 20 мс на 1 МБ),
на 100 — примерно поровну, на 1000 — автомат в 10 раз быстрее (44 против 435 мс). Причина
проверена профилем, а не придумана: 86% времени автомата — `mapaccess2`, 45% — `aeshashbody`
(переходы в `map[byte]int`, тот же эффект, что в главе про скользящее окно). Плоские массивы
переходов в тренажёр намеренно не введены. Утверждение про `strings.NewReplacer` (Trie без
ссылок неудачи, `lookup(s[i:])` на каждой позиции) сверено с исходниками Go 1.26.

`consistenthash` (глава [«Консистентное хеширование»](../src/consistent-hashing.md), Группа 8,
`lvl: ext`) — кольцо с виртуальными узлами (`NewRing`/`Add`/`Remove`/`Get`), `MovedFraction` и
`JumpHash` (Lamping & Veach); хеши и наивный `ModShard` даны готовыми в `hash.go` без тега.
Тесты — на свойства, а не на ответы: ключи при `Add` переезжают только на новый узел, при
`Remove` — только с удалённого, раскладка не зависит от порядка `Add`, плюс сверка с моделью
«владелец по определению» (`*_rand_test.go`). Две ветки контракта на случайных ключах не
проверить в принципе, поэтому они проверены построенными входами: граница `>=` — ключом,
равным имени точки (`"a#0"` хешируется ровно в неё), правило ничьей — НАСТОЯЩЕЙ коллизией
32-битного хеша, найденной перебором (`n512789#0` и `n749192#0` → `0x5c71ba6`; при смене
`HashKey` тест сам скажет подобрать пару заново). Регрессионные значения `JumpHash` сняты с
эталона и так и подписаны — единственную «другую константу генератора» ловят только они.
**`HashKey` = FNV-1a + `fmix32`**, и финал обязателен: имена виртуальных узлов отличаются
последним символом, а умножение FNV на простое ≈ 2²⁴ превращает разницу в единицу в сдвиг
ровно на 1/256 кольца — точки встают частоколом, и 100 реплик балансируют не лучше одной
(разброс 51.5% против 9.8% с финалом). Все числа главы печатает и проверяет
`TestShardingExperiment` (`go test -tags solution -run ShardingExperiment -v ./consistenthash/`),
хеши детерминированы — у читателя цифры совпадут до знака. `JumpHash` подключён к трассировке.

Глава [«Параллельные алгоритмы»](../src/parallel-algorithms.md) (Группа 8, `lvl: ext`) —
СВОДНАЯ: своего пакета у неё нет, она ставит на один стол пять уже существующих
`Seq`/`Conc`-пар (`parallelnqueens`, `parallelsort`, `parallelbfs`, `wordcount`,
`parallelsearch`) и отвечает на вопрос, разбросанный по их главам, — когда горутины
окупаются. Реализации и виджеты «Реши прямо здесь» НАМЕРЕННО остались в главах-хозяевах
(`backtracking`, `k-way-merge`, `graphs`, `top-k-elements`, `string-algorithms`):
дублировать runner в двух местах значило бы завести вторую поверхность решения одного
пакета. Практика самой главы — воспроизвести замеры. Цифры сняты на этой машине (i5-12400,
**6 физических** ядер / 12 потоков, Go 1.24) — рабочем десктопе с фоновой нагрузкой
(load average 3–6: браузер, IDE, VPN), разброс повторов до ~10%. Опоры главы: (1) три
задачи в одной таблице — N-Queens +6.7×, merge sort +3.7×, конкурентный BFS **почти в 90
раз медленнее** (горутина на вершину + общий мьютекс) и **медленнее с ростом ядер**
(1.8 мс на 1 ядре → 10.5 мс на 12: растёт борьба за замок); `BFSLevelsConcLocal` с
локальными буферами всё равно проигрывает почти в 15 раз; (2) закон Амдала по кривой
`GOMAXPROCS`: у merge sort `P`, выраженное из точек 2/4/6, сходится (0.88/0.89/0.87 →
потолок ≈ 8×, стена — последовательное слияние верхнего уровня), у N-Queens «плывёт»
(1.00/0.99/0.96) — значит, упор не в последовательную часть; (3) гиперпотоки дают
перебору +43% (6→12 потоков), сортировке ≈ 0 — причину глава НАМЕРЕННО не утверждает,
а перечисляет гипотезы (ветвления, пропускная способность памяти, 12 горутин разного

ловушка**: бенчмарки нескольких пакетов гонять только с `-p 1`, иначе `go test` запускает

на этом и споткнулась (merge sort «2.0×» вместо 3.7×, и под испорченный замер было подогнано
объяснение) — это вынесено в «Типичные ошибки» главы. Формула Амдала в ```text, а не в

ругается на метку псевдокода.

Глава [«Postgres: EXPLAIN как pprof»](../src/postgres-plans.md) — упражнение ТРЕТЬЕГО типа:
Go-пакета у неё нет вообще, работа идёт в `psql` (`make pg-lab`, определение — `pglab/`).
Цикл тот же, что у `profiling`, но по другую сторону сетевого соединения: **предскажи план →
посмотри настоящий `EXPLAIN ANALYZE` → пойми, почему ошибся**. Алгоритм здесь выбирает не
читатель, а планировщик, и глава про то, ПОЧЕМУ он выбрал именно этот. Все планы и цифры в
тексте сняты с живой базы (Postgres 16, `work_mem=4MB`, `max_parallel_workers_per_gather=0`,
`jit=off`) и воспроизводимы: версия образа пришпилена, данные детерминированы (город —
`hashtext(id)`, а не `random()`). Три опоры главы, каждую из которых легко сломать правкой
`init.sql`: (1) перекос `status` 80/15/5 — на нём видно, что индекс по неселективному условию
бесполезен; (2) `region` — функция от `city`, из-за чего оценка планировщика промахивается
ровно в 10 раз (195 против 1992), а `CREATE STATISTICS` её чинит (1987); (3) засев кончается
`VACUUM ANALYZE`, а не `ANALYZE` — без карты видимости не появится `Index Only Scan`, и раздел
про `random_page_cost` (703 мс → 465 мс на смене одной константы) не воспроизведётся;
(4) таблица-маркер `lab_ready` — СТРОГО последний оператор `init.sql`: `make pg-lab` ждёт её
через TCP (временный сервер засева слушает только unix-сокет, так что TCP отвечает лишь
финальному). Прежний признак «в orders 2 млн строк» срабатывал на ~2 с раньше индексов и
VACUUM — первый же EXPLAIN читателя показывал бы чужой план. Лаборатория создана в C-локали,
поэтому префиксный `LIKE` там идёт по обычному индексу; в главе это оговорено отдельным
замером с коллацией `en-US` (Seq Scan, лечится `text_pattern_ops`).
В CI лаборатория НЕ участвует — docker с базой в пайплайне книги не нужен.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Учебник по **алгоритмическим шаблонам для собеседований** (на русском), собранный как
mdBook, с тремя слоями обучения:

1. **Книга** (`src/*.md`) — теория 25 паттернов: когда применять, алгоритм, сложность, код на Go.
2. **Интерактив** (`assets/*.js` + `*.css`) — встроенные в HTML визуализации, квиз-тренажёр
   распознавания паттернов и трекер прогресса.
3. **Go-тренажёр** (`exercises/`) — рабочий Go-модуль с заготовками функций и тестами:
   читатель пишет реализацию сам и проверяет её тестами.

Проект деплоится на GitHub Pages через CI. Репозиторий: `github.com/fazletdinov/algorithms-book`.

## Команды

### Книга (запускать из корня репозитория)
```bash
mdbook serve        # dev-сервер с авто-пересборкой на http://localhost:3000
mdbook build        # компиляция src/ -> book/ (артефакт для GitHub Pages)
```
mdBook читает из `src/`, пишет в `book/`. `book/` — генерируемый вывод, не редактировать вручную.

### Go-тренажёр (запускать из `exercises/`)
```bash
cd exercises
go test ./slidingwindow/                  # прогнать ТЕСТЫ ПОЛЬЗОВАТЕЛЬСКОЙ заготовки (красные, пока не реализовано)
go test -tags solution ./slidingwindow/   # прогнать те же тесты на ЭТАЛОННОМ решении (должны быть зелёные)
go test -tags solution -count=1 ./...      # все эталоны разом — это то, что проверяет CI
go vet  -tags solution ./...               # линт эталонов — тоже в CI
```
Запуск одного пакета — указать его путь (`./trie/`); один тест — `-run TestName`.

### In-book runner — «решай прямо в книге» (запускать из `exercises/`)
```bash
cd exercises
go run ./cmd/runner          # локальный helper-сервер на http://localhost:8080
```
Книга обращается сюда по fetch: виджет `<div class="algo-runner" data-pkg="X">` отдаёт
заготовку пакета как стартовый код, принимает код читателя и прогоняет НАСТОЯЩИЙ `go test`
(копирует модуль во временную папку, подменяет заготовку, `GOWORK=off`), возвращая
pass/fail. Эталон НЕ показывается — читатель решает сам, как на LeetCode. Виджеты с
`data-race="true"` (concurrency-пакеты) гоняются с `-race` и подсвечивают гонки данных.
Сервис локальный/однопользовательский, поэтому без песочницы: адрес принудительно приводится к
`localhost` (это инвариант, а не дефолт — `/api/run` исполняет присланный код), CORS ограничен
origin'ами книги. Единственное исключение — флаг `-listen-all` для запуска ВНУТРИ контейнера
(`make docker-runner` = `docker run -p 127.0.0.1:8080:8080 ... go run ./cmd/runner -listen-all`),
где «все интерфейсы» — это всё ещё сеть контейнера, а до хоста порт доводит docker, публикуя его
на петлю. Для «ничего не ставить локально» есть `.devcontainer/` (Go 1.24 + Node + mdBook нужной
версии, порты 3000/8080); в браузерных Codespaces книга ходит не на `localhost`, поэтому адрес
runner'а задаётся через `localStorage.setItem('algoRunnerUrl', ...)` — подсказка об этом есть в
самом виджете, когда сервер не отвечает. Реализация — `cmd/runner/`,
фронт — `assets/runner.js`+`runner.css` (подключены в `book.toml`).

## Архитектура Go-тренажёра (ключевой паттерн)

Каждый пакет шаблона состоит из **трёх файлов** с одинаковыми именами функций,
но взаимоисключающей компиляцией через build-теги:

- `<pkg>.go` — заготовки с `panic("TODO: ...")`, тег `//go:build !solution`
- `<pkg>_solution.go` — эталонная реализация, тег `//go:build solution`
- `<pkg>_test.go` — табличные тесты **без** build-тега (общая спецификация для обоих вариантов)

Без флага `-tags solution` компилируется заготовка (тесты падают), с флагом — эталон
(тесты проходят). Один и тот же тест-файл служит спецификацией обеих версий, поэтому
**сигнатуры функций в заготовке и эталоне должны совпадать дословно**, иначе сломается
компиляция теста. При добавлении/правке функции меняй заготовку, эталон и тест согласованно.

Чтобы добавить шаблон: создай папку `mypattern/` с этими тремя файлами по образцу
любого существующего пакета (см. `exercises/README.md`). Модуль — Go 1.24,
`module github.com/fazletdinov/algorithms-book/exercises`.

## Архитектура интерактива

Визуализации, квиз и трекер прогресса — это vanilla-JS/SVG без зависимостей и сборщика.
Файлы из `assets/` подключаются в HTML через `additional-css`/`additional-js` в `book.toml`,
поэтому **новый JS/CSS работает только после `mdbook build`/`serve`**, а не в сыром Markdown.

Встраивание в главы — через `<div>` с data-атрибутами:
- `<div class="algo-viz" data-viz="ТИП" data-array="..." data-k="..."></div>` — визуализация
  (`algo-viz.js`; типы: `sliding-window-fixed`, `two-pointers-sum`, `binary-search`,
  `cyclic-sort`, `dp-coins`, `tree-bfs`/`tree-dfs`, `graph-bfs` и др.)
- `<div class="algo-quiz"></div>` — квиз распознавания паттернов (`quiz.js`, см. `src/quiz.md`)
- `<div class="algo-progress"></div>` — трекер прогресса в localStorage (`progress.js`, см. `src/cheatsheet.md`);
  там же кнопки экспорта/импорта: выгружают ВСЕ ключи книги (`algoProgress`, `algoChallengeSolved`,
  `algoChallengeMissed`, `algoQuizBest`, `algoRunnerCode:*`) в один JSON и вливают его обратно
  СЛИЯНИЕМ, а не заменой — иначе перенос с другой машины стирал бы уже пройденное здесь
- `<div class="algo-explain" data-key="слаг-главы">` — режим «объясни сам» (`explain.js`):
  стоит В НАЧАЛЕ раздела «🧠 Почему это корректно» в 10 главах, где инвариант — суть дела
  (`sliding-window`, `two-pointers`, `modified-binary-search`, `fast-slow-pointers`,
  `cyclic-sort`, `merge-intervals`, `greedy`, `dynamic-programming`, `topological-sort`,
  `union-find-structure`). Вопросы и эталоны лежат в разметке главы (`__q`/`__ref`), эталон
  скрыт, пока не заполнены ВСЕ поля — единственный жёсткий гейт в книге и он намеренный:
  разбор лежит абзацем ниже, обойти можно, но осознанно. Самооценка пишет `algoExplainDone`
  → карточка `expl:<глава>` в `srs.js`. При повторном заходе поле пустое, прошлый ответ — под
  кнопкой (предзаполненное поле убивает воспроизведение). Линт — `scripts/check-explain.js`
  (ключ = слаг главы, ≥2 вопроса, эталон не заглушка, виджет до разбора), поведение —
  `scripts/explain-check.js` на СОБРАННОЙ странице
- `<div class="algo-today"></div>` — очередь интервальных повторений (`srs.js`, страница
  [«Повторение»](../src/review.md)). Карточки заводятся САМИ из трёх источников: отмеченная в
  трекере глава (`algoProgress`), позеленевший в runner'е пакет (`algoPkgSolved` — пишется в
  `runner.js` при `res.ok`, единственный момент, когда «пакет решён» вообще известно) и промах
  в задаче (`algoChallengeMissed`). Расписание — упрощённый SM-2: интервалы 1 → 3 → `iv*ease`,
  `ease` ∈ [1.3, 2.8]; «забыл» роняет интервал в день и спрашивает «в чём была ошибка»
  (заметка показывается при следующем повторе этой карточки). Глава и пакет заводятся со
  сроком «завтра», промах — «сегодня». Состояние — ключ `algoSRS`, входит в экспорт прогресса.
  Арифметику расписания проверяет `scripts/srs-check.js`, а не глазами
- `<div class="algo-review"></div>` — «повторить промахи» (`review.js`, см. `src/cheatsheet.md`):
  список задач, которые не дались, сгруппированный по главам, со ссылкой на конкретную задачу.
  Данные копит `challenge.js`. Важная деталь: id задачи выводится сам («страница#порядковый
  номер»), потому что `data-id` не проставлен НИ В ОДНОЙ главе — раньше `markSolved` из-за этого
  молча не сохранял ничего, и `algoChallengeSolved` всегда был пуст. Виджеты задач заодно
  получают якорь `id="task-N"`, чтобы ссылка вела прямо к задаче

Виджеты поддерживают пошаговую навигацию стрелками (←/→, Home/End).

`algo-runner` дополнительно умеет визуализировать РЕАЛЬНОЕ выполнение кода читателя (не
канонический пример, как `algo-viz`): атрибут `data-trace-calls='[{"func":"Имя","call":"Имя(...)"}, ...]'`
(JSON-массив — в файле пакета обычно несколько функций, читатель выбирает нужную в выпадающем
списке) включает кнопку «🎞 Визуализировать», которая шлёт код и выбор на `/api/trace`. Раннер
инструментирует функцию через `go/ast` (`cmd/runner/traceinstr`, см. его doc-комментарий —
поддерживаются циклы `for` И `range` ЛЮБОЙ вложенности (в т.ч. паттерн «сжимающееся окно» —
for внутри for, или for/range вперемешку) и if/else любой вложенности: снимок ставится ПОСЛЕ
КАЖДОГО оператора на любом уровне — это и даёт построчное прохождение, видно, какая именно
ветка/итерация сработала. НЕ поддерживаются: горутины, замыкания, рекурсия и циклы, спрятанные
внутри switch/select (`reachableLoop` держит это условие согласованным с тем, куда реально
заходит инструментация, — не даёт молча неполную трассу), прогоняет функцию один раз и
возвращает пошаговый снимок переменных с номером строки; результат и переменные-указатели
(`*ListNode`/`*TreeNode`) сериализуются через JSON и рендерятся `trace-viz.js` читаемо (цепочка
списка, скобочная запись дерева), а не сырым адресом. `trace-viz.js` — отдельный универсальный
движок (панель кода с подсветкой текущей строки + таблица переменных + подсветка индексов на
массиве + автопроигрывание), НЕ переиспользующий `DASH`/`buildDashboard` из `algo-viz.js`.
Список включённых функций по пакетам — `traceTargets` в `cmd/runner/trace.go`: **117 функций в
39 пакетах**, трассировка есть в 33 главах — то есть покрыты практически все функции, форма
которых вообще инструментируется. Добавление пакета — строка в `traceTargets` +
`data-trace-calls` в его главе; согласованность этих двух мест проверяет
`scripts/check-registries.js`. Что ещё МОЖНО подключить, показывает `go run ./cmd/tracescan`
(разведчик: гоняет `traceinstr.Instrument` по ЭТАЛОНАМ — в заготовке тело `panic("TODO")`, там
нет циклов и не проходит ничего). Осталось 3 пригодных и намеренно НЕ подключённых —
`dsu.NewUnionFind` (тривиальный init), `miniredis.SaveSnapshot` (пишет файл),
`profiling.FormatScores` (её глава как раз о том, что по шагам проблему не видно) — причины
записаны рядом с `traceTargets`. Пригодность = экспортирована, не более одного возвращаемого
значения (без возврата — плюс строка в `traceVoidFuncs`: `CyclicSort`/`DutchFlagSort`/
`HeapSort`/`Shuffle`) и форма проходит инструментацию. Харнесс (`renderHarness`) всегда
импортирует `math/rand` с пустой ссылкой `var _ = rand.Int`: вызов может создавать генератор с
фиксированным зерном (`sampling.Shuffle`/`ReservoirSample` иначе не вызвать, а трасса обязана
быть воспроизводимой).

## CI/CD

`.github/workflows/ci.yml`: job `go-tests`, `assets-check` и `build-book` (`mdbook build`
+ `check-links.js`) должны пройти; затем job `deploy` публикует `book/` на GitHub Pages
**только из ветки main**. Job `build-book` после сборки прогоняет `node scripts/check-links.js`
— целостность внутренних ссылок/якорей по собранному `book/`.

Job `go-tests` (working-directory `exercises/`) проверяет четыре инварианта:
1. `gofmt -l .` — всё отформатировано;
2. `go vet -tags solution ./...` и `go test -tags solution -count=1 ./...` — эталоны корректны;
3. `go vet ./...` (без тега) — заготовки компилируются (ловит рассинхрон сигнатур заготовка/эталон/тест);
4. шаг «Заготовки ещё не решены» — untagged-тесты каждого пакета ДОЛЖНЫ падать (ловит решение, протёкшее в файл-заготовку).

Job `go-tests` также прогоняет `go run ./cmd/checksnippets -src ../src` — РАЗБОР (не компиляцию)
каждого ```go-листинга книги через `go/parser`. Компиляция здесь неприменима принципиально:
листинг намеренно не самодостаточен (показан метод, а не весь тип рядом), полная типизация даёт
под две сотни ложных «undefined» и потребовала бы ухудшить подачу ради зелёного CI. Разбор ловит
только то, что всегда ошибка: оборванная функция, лишняя скобка, потерянная при копировании
строка. Листинг может быть декларациями, фрагментом (тело цикла) или смешанным (import +
функции + пара строк) — инструмент пробует все три формы. Настоящий псевдокод (`for ... {`)
помечается строкой `<!-- snippet:pseudo -->` прямо перед ```go: в собранной книге это HTML-
комментарий, читателю не виден. Метка на листинге, который на самом деле разбирается, тоже
считается ошибкой — иначе метки расползлись бы и перестали что-либо значить.

Job `assets-check` помимо синтаксиса и смоуков виджетов прогоняет
`node scripts/check-registries.js` — сверку РУЧНЫХ реестров с реальностью: трекер прогресса
(`assets/progress.js`) против `src/SUMMARY.md`, таблица пакетов в `exercises/README.md` против
каталогов, `data-trace-calls`/`data-pkg` в главах против `traceTargets` (`cmd/runner/trace.go`)
и списка пакетов, счётчик пакетов в этом файле против факта. Расхождение здесь ничего не ломает
на сборке — оно тихо ухудшает книгу (трекер перестаёт считать реальные главы, виджет молча не
находит пакет, «🎞 Визуализировать» отвечает отказом), поэтому и вынесено в CI. Там же
`node scripts/progress-render-check.js` — jsdom-смоук самого трекера (его содержимое зашито в JS,
`check-viz.js` его не видит): все главы и группы отрисовались, отметка обновляет процент, счётчик
группы и `localStorage`, сброс работает.

Перед коммитом локально прогоняй `gofmt -l exercises`, `go test -tags solution -count=1 ./...`
(из `exercises/`), `mdbook build`, `node scripts/check-links.js` и `node scripts/check-registries.js`
(из корня) — это ровно то, что проверит CI. jsdom-смоуки требуют `npm i --no-save jsdom`; без
него они мягко пропускаются (exit 0), поэтому локально их отсутствие не блокирует, а в CI
jsdom ставится всегда.

В корне есть `go.work` (`use ./exercises`) — он нужен только для IDE/gopls, чтобы при открытии
корня репозитория модуль из `exercises/` был виден (иначе gopls ругается «module not in workspace»).

## Покрытие тренажёра

Тренажёр покрывает все паттерны книги (**68 пакетов** — продвинутые графы разбиты на
`dijkstra`/`bellmanford`/`astar`/`mst`, связность — `scc`; конкурентность —
`parallel*`/`wordcount`; потоки — `maxflow`; дискретная математика —
`combinatorics`/`sampling`; классы сложности — `npcomplete`). Пакеты главы «Комбинации паттернов» (все 7 связок): `lru`, `wordladder`,
`alienorder`, `meetingrooms`, `serializetree`, `skyline`, `designtwitter` + `listcrud` (CRUD
односвязного списка). «Боевые мини-проекты» (флагманы, паттерн- + прод-версия в одном пакете):
`ratelimiter`, `streamstats`, `leaderboard`, `cache`. `miniredis` (глава
[«Капстоун»](../src/miniredis.md)) — сквозной проект поверх этих флагманов, растёт по этапам;
с этапа 2 у него обычная пара заготовка/эталон (`miniredis.go`/`miniredis_solution.go` —
на этапе 7: `dispatchSet`/`dispatchGet`/`dispatchDel`/`dispatchExpire`/`dispatchTTL`/
`dispatchZAdd`/`dispatchZScore`/`dispatchZRange`/`dispatchZRank`/`RateLimitReply`/
`SaveSnapshot`/`LoadSnapshot`/`dispatchSave`), а протокол
(`resp.go`), маршрутизация и `PING`/`ECHO` (`dispatch.go`), тип `Store` с TTL/ZSET и `live()`/
`zsetOrdered()` (`store.go`) даны готовыми без тега — общая инфраструктура, не задача с
решением. `Store.now func() time.Time` — впрыск часов для тестов TTL без `time.Sleep`
(протокол `EXPIRE`/`TTL` не пробрасывает время параметром, в отличие от
`cache.TTLCache.Get(key, nowMs)` — значит, часы пришлось внедрить на уровень стора, а не
функции). `zsetOrdered` сортирует ПО ВОЗРАСТАНИЮ очков (в отличие от
`leaderboard.Leaderboard.ordered()`, который по убыванию) — так `ZRANGE`/`ZRANK` ведут себя
как настоящий Redis, а не как таблица лидеров. Этап 5 — не RESP-команда, а мидлварь:
`RateLimitReply` оборачивает `ratelimiter.TokenBucket` (пакет `ratelimiter`, уже реализован
читателем во флагмане) в готовый `Reply`-или-`nil`; ведро заводится НА СОЕДИНЕНИЕ в
`cmd/miniredis/main.go` (не в `Store`, который общий на всех клиентов) — поэтому обычный
`TokenBucket`, без `SafeTokenBucket`, корректен без мьютекса: наглядный контраст со `Store`,
которому мьютекс нужен именно потому, что он shared. Этап 6 (опциональный) не добавляет TODO — `store.mu` был обязателен уже с этапа 2, здесь неявное допущение
делается явным: `miniredis_concurrent_test.go` (дан готовым) гоняет `DEL` по общим 200 ключам из
8 горутин под `-race` и проверяет точный инвариант (сумма удалений по всем горутинам == 200,
как `TestSafeTokenBucketConcurrent` в `ratelimiter`), а не просто «тест не упал». Этап 7
(маршрут капстоуна завершён) — персистентность: `SaveSnapshot`/`LoadSnapshot`/`dispatchSave`
(`SAVE`), автозагрузка при старте и сохранение по SIGINT/SIGTERM даны готовыми в
`cmd/miniredis/main.go` (флаг `-db`, по умолчанию `dump.rdb`; сам файл — в `.gitignore`).
Суть этапа не в команде, а в АТОМАРНОСТИ записи: снапшот пишется во временный файл рядом
с целью (`os.CreateTemp(filepath.Dir(path), ...)` — тот же раздел ФС, иначе `os.Rename`
провалится cross-device) и переносится `os.Rename`; прямой `os.WriteFile` открывает файл с
`O_TRUNC` и делает состояние наблюдаемым «наполовину». `TestSnapshotSaveIsAtomic`
(`persistence_test.go`, дан готовым) это ГОНЯЕТ, а не описывает: 300 раундов SaveSnapshot
против 300 раундов LoadSnapshot в отдельных горутинах, допустимо НОЛЬ ошибок декодирования —
намеренный контраст с этапом 6, где разделяемой была память (её сторожит `store.mu` и видит
`-race`), а здесь разделяемый ресурс — файл, и `-race`/мьютекс про него ничего не знают.
Сериализуется НЕ `*Store` (мьютекс + неэкспортируемые поля), а отдельный `snapshotData` с
экспортируемыми полями (`gob`), причём копия карт снимается под `store.mu`, а кодирование и
запись идут уже без него — критическая секция не включает дисковую операцию (учебный аналог
`BGSAVE`-мотивации настоящего Redis). TTL в снапшоте — АБСОЛЮТНЫЕ `time.Time`, как unix-ms в
настоящем RDB: ключ, протухший за время простоя, после загрузки мёртв, а не воскресает. Проверка
«Заготовки ещё не решены» в CI
(`.github/workflows/ci.yml`)
принципиально смотрит только на пакеты с физическим `<pkg>_solution.go`, поэтому `miniredis`
(и `cmd/*`) сама собой не ловится, пока решать нечего, и сама начинает ловиться, как только
solution-файл появляется — обновлять исключение вручную не нужно. Список функций каждого
пакета — в `exercises/README.md`. При добавлении/
удалении пакета обнови это число (проверка: `ls -d exercises/*/ | grep -v cmd | wc -l`, сейчас 68).

После завершения маршрута в `miniredis` добавлен непронумерованный бонус про fuzzing
(`exercises/miniredis/resp_fuzz_test.go`, дан готовым, без TODO — `FuzzReadCommand`) —

`maxBulkLen`/`maxMultibulkLen` в `resp.go` (аналог `proto-max-bulk-len`/`proto-max-multibulk-len`
настоящего Redis); упавший вход остался в затравке `FuzzReadCommand` как регрессионный тест.

ограничить `readLine` (аналог `proto-inline-max-size`) и дописать для неё свою затравку.

`codereview` (глава [«Ревью чужого кода»](../src/code-review.md)) — один из двух пакетов ДРУГОГО
типа упражнения (второй — `profiling`, см. ниже): три функции уже полностью реализованы (никаких `panic("TODO")`), но в каждой
спрятан один изъян, который ловится только тестом/`-race`, а не чтением сигнатуры — задача не
дописать, а продиагностировать и исправить прямо в `codereview.go` (`!solution`), сверяясь с
`codereview_solution.go` только после. Три сценария: (1) `SumSquaresConcurrent` — двойной изъян:
целочисленное усечение `len(nums)/workers` детерминированно теряет «хвост» (не гонка, ловится
обычным `go test` без `-race` на входе длины 101 при `workers>1`) + разделяемый `total +=` без
синхронизации (отдельная гонка, ловится только `-race`, детектор указывает на конкретную строку);
эталон убирает и то, и другое разом — не мьютексом, а тем, что у каждой горутины своя локальная
сумма и результат идёт через `chan int64` (нечему гонять, если нет разделяемой памяти); (2)
`HasDuplicate` — корректен, но O(n²); ловится не сравнением ответа, а дедлайном по времени
(`TestHasDuplicateScales`: 200000 различных чисел, эталон ~7мс, заготовка ~4.8с, порог 2с — запас
на порядки в обе стороны, откалиброван эмпирически на этой машине); эталон — тот же компромисс
время/память, что и в `hashtable`; (3) `ParseAndSum` — проглатывает ошибку `strconv.Atoi` через
`continue` вместо возврата вызывающему коду (анти-паттерн «error проверили, но не обработали»).

`profiling` (раздел «Практика: найди узкое место сам» в `../src/appendix-go-memory.md`) — второй
пакет другого типа: `FormatScores` (`profiling.go`, `!solution`) уже отвечает ПРАВИЛЬНО (табличный
тест это подтверждает), но по коду не видно, что она на порядки медленнее, чем нужно — задача не
дописать, а измерить (`go test -run='^$' -cpuprofile=cpu.prof -bench=. ./profiling/`, затем
`go tool pprof -top -cum cpu.prof`), понять причину и починить. Автоматическая проверка фикса —
не сравнение ответа, а бюджет аллокаций через `testing.AllocsPerRun` (`TestFormatScoresAllocs`):
заготовка (`result += fmt.Sprintf(...)` в цикле) аллоцирует ~2745 раз за вызов на 1000 элементах,
эталон — ~2 (измерено на этой машине, бюджет теста — 20, запас на порядки в обе стороны). Реально
измеренный CPU-профиль отдаёт больше трети времени под `runtime.concatstrings` (копирование при
каждом `+=`, строки в Go неизменяемы — O(n²) байт скопировано, хотя цикл линеен по итерациям) и
почти столько же — под фоновую сборку мусора (`gcBgMarkWorker`), а не под сам `fmt.Sprintf`, как
подсказывает интуиция «дорого форматирование» — ровно то, что и находит профилирование, а не
чтение кода. Эталон — `strings.Builder.Grow` (одна аллокация под весь отчёт заранее) +
`strconv.AppendInt` в переиспользуемый буфер (не `strconv.Itoa`, который всё ещё аллоцировал бы
новую строку на каждое число).

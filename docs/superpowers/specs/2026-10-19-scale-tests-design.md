# Тесты масштаба: сложность как часть контракта

Дата: 2026-10-19. Источник: пункт 19 плана в `reports/Качество учебника и мировые курсы.md`
и ответ «инженер, а не кодер» (сессия 2026-10-19). Решение пользователя — **строгий контракт**.

## Зачем

Сегодня ни один тест пакетов ядра не ловит решение, хуже задуманного на целый класс сложности:
случайные тесты идут на n ≤ 40, в `dp` наивное решение прямо разрешено комментариями, а
`TestHashMapResize` (n = 100) проходит у хеш-таблицы без расширения. У Princeton и Berkeley 61B
сложность входит в условие задания и проверяется автогрейдером; у книги она — текст абзаца
«Ожидаемая сложность». Цель — чтобы функция, решённая перебором, оставалась красной с
понятной причиной.

## Что считается успехом

1. В 12 пакетах ядра есть тест масштаба; на каждом наивное решение из таблицы ниже падает
   **этим тестом** с сообщением о сложности, эталон проходит с запасом.
2. Тест ловит разрыв класса (n² против n, экспонента против полинома, n·k против n),
   а не лишний log: решение на сортировке там, где задумана куча, проходит.
3. CI зелёный, прибавка ко времени `go test -tags solution ./...` — меньше 2 с суммарно.
4. Заготовки по-прежнему падают (шаг CI «Заготовки ещё не решены»).

## Решение: дедлайн с запасом на порядки

Образец — `codereview.TestHasDuplicateScales`. Функция гоняется в горутине на худшем входе;
не вернулась за срок — `t.Fatalf` с причиной. Вход подбирается так, чтобы эталон делал
≲ 10⁷ простых операций (≲ 50 мс на машине автора), а наивное решение — ≥ 5·10⁹ (≥ 3 с).
Срок **2 с** выдерживает и CI, медленнее в 2–3 раза, и `-race` (замедление ~10× даёт эталону
≲ 0,5 с), поэтому отдельного пропуска под `-race` нет. Под `-short` тесты пропускаются.

Отвергнуто: опыт удвоения (отношение времён на n и 2n шумит на миллисекундах, строгий тест
мигал бы); нормировка калибровочным циклом (лишняя сложность при таком запасе).

## Состав

| Пакет | Тест | Эталон → наивное | Худший вход |
|---|---|---|---|
| `hashtable` | `TestHashMapScales` (Put, затем Get) | O(1) аморт. → цепочка O(n) без расширения | 2·10⁵ различных ключей |
| `slidingwindow` | `TestMaxSlidingWindowScales` | O(n) → O(n·k) | строго убывающий, n = 2·10⁵, k = 10⁵ |
| `prefixsum` | `TestRangeSumsScales` | O(n+q) → O(n·q) | n = q = 10⁵, все запросы на весь ряд |
| `twopointers` | `TestPairWithTargetSumScales` | O(n) → O(n²) | 0…n−1, пары нет, n = 10⁵ |
| `stack` | `TestLargestRectangleScales` | O(n) → O(n²) | все высоты равны, n = 10⁵ |
| `binarysearch` | `TestFindFirstLastScales` | O(log n) → O(n) «нашёл и иди вбок» | все равны, n = 10⁶, 10⁴ вызовов |
| `binheap` | `TestHeapScales` | O(log n) → O(n) на `Pop` | 2·10⁵ `Push`, затем 2·10⁵ `Pop` |
| `graphs` | `TestShortestPathUnweightedScales` | O(V+E) → O(V·E) | путь 0–1–…–(V−1), V = 10⁵ |
| `intervals` | `TestMinMeetingRoomsScales` | O(n log n) → O(n²) | `[i, i+n]`, n = 10⁵ |
| `greedy` | `TestCanJumpScales` | O(n) → O(n·прыжок) | лестница к нулю, ответ `false`, n ≈ 10⁵ |
| `dp` | `TestCoinChangeScales` | O(amount·c) → экспонента | монеты {4, 6, 10}, amount = 10001 (ответ −1) |
| `treedfs` | `TestDiameterOfTreeScales` | O(n) → O(n²) (высота в каждом узле) | левая цепочка, n = 10⁵ |

Точные n и форма входа — по замеру на этапе реализации; таблица задаёт порядок величин.
Имена пакетов сверить с каталогами при реализации.

Сознательно вне состава: `QuickSort` (эталон — схема Ломуто, сам квадратичен на отсортированном
входе); `Power` (наивная рекурсия на e = 2⁴⁰ переполняет стек и роняет бинарник); `HouseRobber`,
`ClimbStairs`, `Knapsack01` (их случайные тесты нарочно разрешают наивное решение — контракт этих
функций не меняется); `LIS` (условие допускает O(n²)); функции, где наивное отстаёт только на log.

## Устройство

- **Помощник** `exercises/internal/scaletest`: одна функция вида
  `Within(t *testing.T, limit time.Duration, what string, run func())` — запускает `run` в
  горутине, ждёт `limit`, при просрочке `t.Fatalf` с текстом `what` (вход, ожидаемый класс,
  измеренные времена эталона и наивного). Под `testing.Short()` — `t.Skip`. Срок по умолчанию —
  константа пакета `Limit = 2 * time.Second`. Проверку результата делает сам тест после `Within`.
  Пакет — служебный, не пакет тренажёра: каталог `internal` исключается везде, где перебираются
  пакеты, — `scripts/check-registries.js` (оба перебора), `exercises/cmd/problembank`,
  `exercises/cmd/tracescan`, `scripts/srs-check.js`. Runner копирует модуль целиком
  (`copyModule`), импорт доступен и во временной копии.
- **Файл** `<pkg>_zscale_test.go`, без build-тега. Сортируется после табличного и `_zrand`:
  наивный вызов после срока продолжает работать в горутине до выхода бинарника и не должен
  тормозить остальные тесты пакета. `check-registries.js` проверяет: тест `Test*Scales` лежит
  только в `_zscale_test.go`.
- **Владелец теста.** `stubdoc.OwnerOf` отдаёт `Test<Func>Scales` функции `<Func>`: тест сам
  входит в прогон одной функции, в поле `t` банка (режим собеседования) и в карточку `pkg:`.
  `TestHashMapScales` и `TestHeapScales` — тесты типа, идут с группой типа.
  Проверить на `stubdoc`-тестах, что владелец назначается так.
- **Условие.** В док-комментарий функции в заготовке добавляется абзац
  `Ограничения: n ≤ 10⁵` (форма — как на LeetCode; для пар величин — обе). Это часть условия, а
  не подсказка: в `hintPrefix` не добавляется и видна в смешанной тренировке, как на настоящем
  собеседовании. В эталоне тот же абзац (комментарии пары совпадают по обычаю пакетов).
  `assets/problems.js` перегенерируется (`go run ./cmd/problembank`).
- **Сообщение при падении** (одна строка, её берёт `reason` runner'а):
  `MaxSlidingWindow не уложилась в 2s на n=200000, k=100000 — похоже на O(n·k) там, где нужен O(n)
  (замер: эталон ~3 мс, перебор ~40 с)`. Числа — из замера на этапе реализации.
- **Память наивных решений.** Наивный граф на матрице смежности при V = 10⁵ — около 10 ГБ.
  В runner'е его остановит предел памяти; при ручном `go test` — нет. В комментарии к тесту
  графа это сказано; мутанты при проверке гоняются только под `scripts/safe-run.sh`.

## Проверка

Для каждого из 12 тестов — наивный мутант (решение из столбца «наивное»), прогон под
`scripts/safe-run.sh`: мутант падает **именно тестом масштаба** с сообщением о сложности и
проходит табличные тесты; эталон проходит. Времена эталона и мутанта записываются в сообщение
теста и в журнал. Мутант самого помощника «`Within` не ждёт срока» (возврат сразу) делает
наивные решения зелёными — его ловят тесты пакета `scaletest` (просроченный `run` обязан уронить
тест). Затем полный набор CI: `gofmt -l`, `go vet` с тегом и
без, `go test -tags solution -count=1 ./...` (с замером прибавки), шаг «Заготовки ещё не решены»,
`go run ./cmd/problembank -check`, `check-registries.js`, `srs-check.js`, `mdbook build`,
`check-links.js`. Всё исполнение непроверенного кода — через `scripts/safe-run.sh`.

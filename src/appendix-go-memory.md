# Приложение: память, GC и профилирование в Go

Эта страница — единый справочник по особенностям Go, которые упоминаются во многих
главах: модель памяти, escape analysis, сборщик мусора и инструменты профилирования.
Главы ссылаются сюда, чтобы не повторять одну и ту же теорию.

## Стек и куча

- **Стек** — локальные переменные, примитивы, небольшие структуры. Аллокация и
  освобождение почти бесплатны (сдвиг указателя стека).
- **Куча** — данные, которые «переживают» функцию или имеют динамический размер.
  За освобождение отвечает сборщик мусора (GC).

Куда поместить переменную, решает **не программист, а компилятор** — на основе escape
analysis.

## Escape Analysis

**Escape analysis** — статический анализ компилятора: «убегает» ли переменная за
пределы функции. Если да — она аллоцируется в куче, если нет — остаётся на стеке.

Типичные причины «побега» в кучу:

1. Возврат указателя на локальную переменную (`return &x`).
2. Сохранение указателя в глобальную переменную или долгоживущую структуру.
3. Упаковка значения в интерфейс (`var i any = x`).
4. Слишком большой объект или срез с неизвестным на этапе компиляции размером.

Проверить решения компилятора:

```bash
go build -gcflags=-m ./...
```

Вывод вида `moved to heap: x` или `x escapes to heap` показывает, что переменная
ушла в кучу.

**Как уменьшить аллокации:**

```go
// ❌ возвращаем указатель — побег в кучу
func bad() *int { x := 42; return &x }

// ✅ возвращаем значение — остаётся на стеке
func good() int { x := 42; return x }

// ✅ заранее выделяем ёмкость среза — меньше перевыделений
buf := make([]int, 0, expectedSize)
```

## Сборщик мусора (GC)

Go использует **конкурентный mark-and-sweep** с трёхцветной маркировкой
(белый/серый/чёрный), работающий параллельно с программой и минимизирующий паузы
Stop-The-World.

- **Триггер**: по умолчанию GC запускается, когда куча вырастает примерно вдвое
  относительно прошлого цикла. Регулируется переменной `GOGC` (меньше значение —
  агрессивнее GC, меньше памяти, больше пауз).
- **Принудительно**: `runtime.GC()` (нужно редко, в основном для тестов/бенчмарков).

**Снижение нагрузки на GC** — это в первую очередь снижение числа аллокаций:

<!-- snippet:pseudo -->
```go
// Переиспользование буфера вместо аллокации на каждой итерации
buf := make([]int, 0, 1024)
for ... {
    buf = buf[:0] // очистка без новой аллокации
    // ... работаем с buf
}

// sync.Pool для переиспользования временных объектов в горячих путях
var pool = sync.Pool{New: func() any { return make([]byte, 0, 1024) }}
```

## Профилирование

Профилирование — это **измерение** перед оптимизацией. Не оптимизируй «на глаз»:
сначала измерь, найди узкое место, потом улучшай и снова измеряй.

### Бенчмарки

```go
func BenchmarkSolve(b *testing.B) {
    data := makeInput(10000)
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        Solve(data)
    }
}
```

```bash
go test -bench=. -benchmem
```

Вывод `1234 ns/op   0 B/op   0 allocs/op` читается так: среднее время на операцию,
байт аллоцировано, число аллокаций. **Идеал в горячем пути — 0 allocs/op.**

### CPU и память (pprof)

```bash
go test -cpuprofile=cpu.prof -memprofile=mem.prof -bench=.
go tool pprof cpu.prof   # команда top покажет самые «дорогие» функции
```

### Чеклист интерпретации

1. Сравнивай время с наивным подходом — есть ли реальный выигрыш.
2. Минимизируй `allocs/op` в горячем пути.
3. Ищи функции, занимающие >10% времени (`top` в pprof).
4. Профилируй на **репрезентативных** данных — результаты на игрушечных входах
   обманчивы.

> 🌍 **Где это в настоящем коде**
>
> - [`concatstrings`](https://github.com/golang/go/blob/go1.24.0/src/runtime/string.go#L26) (Go 1.24) — так рантайм выполняет `a + b`: считает общую длину, выделяет новую строку и копирует в неё все части; поэтому `+=` в цикле каждый раз копирует весь накопленный результат.
> - [`Builder.Grow`](https://github.com/golang/go/blob/go1.24.0/src/strings/builder.go#L69) — заранее выделяет место под `n` байт, и дальнейшие записи идут без новых аллокаций.
> - [`readGOGC`](https://github.com/golang/go/blob/go1.24.0/src/runtime/mgcpacer.go#L1288) — откуда берётся `GOGC`: без переменной окружения — 100, `off` выключает сборщик.
> - [`escape.go`](https://github.com/golang/go/blob/go1.24.0/src/cmd/compile/internal/escape/escape.go#L18) — сам escape-анализ: переменная, чей адрес может пережить функцию, помечается для кучи.

## 🔬 Практика: найди узкое место сам

Чеклист выше — не абстракция: пакет `exercises/profiling` даёт одну функцию,
`FormatScores`, которая всегда отвечает правильно (табличный тест это уже
подтверждает) — и при этом реально медленная так, что по коду это не видно.
Задача — не дописать недостающее (TODO здесь нет), а **измерить, а не
угадать**, куда уходит время и память, и уже потом чинить.

```bash
cd exercises
go test ./profiling/                                          # корректность — уже зелёная
go test -bench=. -benchmem ./profiling/                       # только цена, не судит pass/fail
go test -run='^$' -cpuprofile=cpu.prof -bench=. ./profiling/
go tool pprof -top -cum cpu.prof                               # где ВПРАВДУ горячо
```

Интуиция подсказывает «наверное, дорого именно форматирование строки» — и
ошибается. Реально измеренный профиль на этой машине (n=2000, `-benchtime=2s`):

```
      flat  flat%   sum%        cum   cum%
         0     0%  0.59%      1.76s 34.65%  runtime.concatstrings
         0     0%  0.79%      1.38s 27.17%  runtime.gcBgMarkWorker
     0.05s  0.98%  ...        0.25s  4.92%  fmt.(*pp).doPrintf
```

Больше трети времени — в `runtime.concatstrings`: `result += ...` в цикле
копирует ВЕСЬ накопленный результат заново на каждой итерации (строки в Go
неизменяемы), это O(n²) байт скопировано, хотя цикл выглядит линейным по
числу итераций. Почти столько же — в фоновой сборке мусора: тысячи мелких
аллокаций (`fmt.Sprintf` создаёт новую строку на каждый вызов) создают
достаточно мусора, чтобы GC регулярно вмешивался. Сам `fmt.Sprintf` —
реальная, но куда меньшая доля. Ни то, ни другое не читается из кода —
цикл из четырёх строк выглядит безобидно; это находит только измерение.

Автоматическая проверка фикса — не сравнение ответа (он и так верный), а
бюджет аллокаций через `testing.AllocsPerRun` (`TestFormatScoresAllocs`):
заготовка аллоцирует ~2745 раз за вызов на 1000 элементах, эталон — ~2, за
счёт `strings.Builder.Grow` (одна аллокация под весь отчёт заранее) и
`strconv.AppendInt` в переиспользуемый буфер (без `strconv.Itoa`, который
всё ещё вернул бы новую строку на каждое число).

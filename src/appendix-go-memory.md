## Планировщик: G, M, P

Горутина — это **не** поток ОС. Рантайм запускает немного потоков (`M`; обычно порядка
числа ядер, при блокирующих системных вызовах — больше) и раскладывает на них тысячи
горутин (`G`). Связующее звено — `P` (логический процессор): он держит **локальную
очередь** готовых горутин и кэш аллокатора. Чтобы исполнять Go-код, нужна тройка
**G + M + P**; число `P` задаёт `GOMAXPROCS`.

- **Локальная очередь** у каждого `P` — брать из неё работу можно **без блокировок**.
- **Глобальная очередь** — общая; в неё заглядывают периодически.
- **Кража работы (work stealing)** — простаивающий `P` забирает **половину** очереди у
  занятого соседа.
- **Передача `P` на syscall** — системный вызов (syscall) — это просьба к ядру ОС: прочитать
  файл, принять соединение. Если он блокирующий, поток `M` застревает вместе с горутиной,
  но `P` **передаётся** другому потоку, и остальные горутины бегут дальше.

```go
func schedule() {
    for {
        g := runqget(p)       // из локальной очереди P
        if g == nil {
            g = globrunqget() // из глобальной очереди
        }
        if g == nil {
            g = runqsteal(p)  // украсть половину у другого P
        }
        execute(g)            // запустить на потоке M
    }
}
```

Листай «›»: горутины запускаются из локальных очередей, простаивающий `P` крадёт работу, а
блокирующий syscall не замораживает процессор — его подхватывает другой поток:

<div class="algo-viz" data-viz="scheduler"></div>

**Сеть не держит поток: netpoller.** Горутина, которая ждёт ответа из сокета, поток ОС не
занимает. Рантайм просит ядро следить за сокетом (на Linux — `epoll`, на macOS — `kqueue`:
«скажи, когда в этих сокетах появятся данные»), а саму горутину **паркует** — снимает с
`M` и откладывает. Поток тут же берёт следующую горутину из очереди. Когда ядро сообщает
«сокет готов», планировщик ставит горутину обратно в очередь, и она продолжает с того же
места. Поэтому сервер с 10 000 открытых соединений обходится десятком потоков: ждут
горутины, а не потоки. Блокирующий syscall выше — другой случай: там застревает сам поток.

Горутина дешёвая: стартовый стек ~**2 КБ** (растёт копированием по мере надобности) против
~1 МБ у потока ОС. Поэтому «горутина на задачу» — нормально, а «поток на задачу» — нет.
С Go 1.14 планировщик **вытесняющий**: долгая горутина без точек переключения всё равно
будет приостановлена по сигналу.

## Стек и куча

- **Стек** — кадры вызванных функций с их локальными переменными. Выделение и
  освобождение почти бесплатны: сдвиг указателя стека, кадр исчезает с возвратом из функции.
- **Куча** — данные, которые «переживают» функцию или имеют неизвестный заранее размер.
  За освобождение отвечает сборщик мусора.

Куда поместить переменную, решает **не программист, а компилятор** — escape-анализом.

## Escape Analysis

**Escape-анализ** — проверка компилятора: «убегает» ли значение за пределы функции. Если
нет — оно живёт в кадре стека, и GC его вообще не касается. Если да — едет в кучу.
Решение принимается **при компиляции**, до запуска: нужно сгенерировать правильный код, а
если компилятор не может доказать, что значение не переживёт кадр, он осторожничает и
кладёт его в кучу.

Компилятор смотрит на две вещи. **Главная — переживёт ли значение функцию**:

1. Возврат указателя на локальную переменную (`return &x`).
2. Сохранение указателя в глобальную переменную, поле объекта в куче, замыкание или горутину.
3. Упаковка значения в интерфейс (`var i any = x`, неявно — `fmt.Sprint(x)`).

**Вторая — размер**, даже если значение никуда не убегает: обычная структура или массив на
десятки байт спокойно живут на стеке, но очень большой объект (массив `[1 << 20]int`,
`make([]int, 1<<20)`) идёт в кучу, и срез с размером-переменной (`make([]T, n)`) — тоже:
компилятор не знает, сколько места отвести в кадре. С Go 1.25 для такого среза есть
маленький буфер на стеке, а в кучу он уходит, только если `n` в буфер не влез.

```go
func noEscape() int {
    x := 42      // не покидает функцию → стек
    return x     // вернули КОПИЮ; кадр исчезает
}

func escapes() *int {
    y := 42      // адрес уйдёт наружу...
    return &y    // ...значит y живёт в КУЧЕ (escape)
}
```

Слева — стек (кадры исчезают с возвратом), справа — куча (живёт, пока GC не освободит).
`y` сразу создаётся в куче — во время выполнения ничего со стека в кучу не переезжает:

<div class="algo-viz" data-viz="escape"></div>

Проверить решения компилятора: `go build -gcflags=-m ./...`. Строки `moved to heap: y`
или `x escapes to heap` показывают, что ушло в кучу и почему.

### Аллокатор кучи

Куча устроена как у TCMalloc: у каждого `P` есть **`mcache`** — свой кэш свободных блоков,
из которого мелкие объекты выдаются **без блокировок**. Размер запроса округляется вверх до
одного из 68 **размерных классов** (например, 24 байта → блок 32): блоки одного размера
лежат вместе, и фрагментация не растёт даже без перемещения объектов (это округление видно в
[`growslice → roundupsize`](big-o.md)). Объекты до 16 байт без указателей
**tiny-аллокатор** склеивает в один блок; крупные (> 32 КБ) идут напрямую из общей кучи
`mheap`. Меньше аллокаций → меньше работы аллокатору и GC.

## Сборщик мусора (GC)

GC в Go — **конкурентный** (работает одновременно с программой), **не перемещающий**
(объекты не двигаются) **mark-and-sweep**: сначала пометить (mark) всё живое, потом
подмести (sweep) остальное. Пометка — **трёхцветная**:

- **Белый** — ещё не достигнут, кандидат на удаление.
- **Серый** — достигнут, но его указатели ещё не просмотрены.
- **Чёрный** — достигнут и полностью просмотрен (живой).

Старт — от **корней** (стеки горутин, глобальные переменные): то, на что они указывают,
становится серым. Дальше берём серый объект, его белых соседей красим в серый, сам объект — в
чёрный. Это обход графа объектов, как BFS с очередью серых. Когда серых не осталось, всё
**белое недостижимо** — это мусор.

```go
func markPhase(roots []*obj) {
    grey := roots             // корни сразу серые
    for len(grey) > 0 {
        o := pop(grey)        // берём серый объект
        for _, c := range o.pointers {
            if c.color == white {
                c.color = grey // достижим → серый
                grey = push(grey, c)
            }
        }
        o.color = black       // потомки просканированы → чёрный
    }
    // всё, что осталось белым — мусор → sweep
}
```

Зелёные стрелки — корни; объекты меняют цвет белый → серый → чёрный, а недостижимые (E, F)
в конце остаются белыми и помечаются как мусор:

<div class="algo-viz" data-viz="gc-mark"></div>

Разметка идёт **параллельно** с программой. Чтобы не потерять объект, который программа
переподвесила во время разметки, действует **барьер записи (write barrier)**: при записи
указателя рантайм подкрашивает нужный объект. Полные остановки программы (**STW**,
stop-the-world) нужны лишь на краткие служебные фазы — обычно **меньше миллисекунды**.

- **Триггер**: GC запускается, когда куча выросла примерно **вдвое** относительно живых
  данных прошлого цикла. Регулирует `GOGC` (по умолчанию 100; меньше — чаще GC и меньше
  памяти, `off` — выключить). С Go 1.19 есть мягкий лимит памяти `GOMEMLIMIT`.
- **Принудительно**: `runtime.GC()` — нужно редко, в основном в тестах и бенчмарках.

Снизить нагрузку на GC — значит в первую очередь **реже аллоцировать** (см. «Цена на
практике» ниже).

<details><summary>⚙️ Второй проход: почему рантайм устроен именно так — читать, когда освоишься</summary>

- **Почему GMP, а не «горутина = поток».** Поток ОС дорог: ~1 МБ стека, переключение через
  ядро. Прослойка `P` позволяет планировать горутины в пространстве пользователя (без ядра)
  и держать столько **работающих** потоков, сколько ядер. Локальные очереди убирают борьбу
  за общий замок, кража работы не даёт процессорам простаивать.
- **Почему GC конкурентный и не перемещающий.** Долгие паузы неприемлемы для серверов,
  поэтому разметка идёт одновременно с программой, а цена — барьер записи. Он держит
  правило «чёрный не указывает на белый напрямую»: иначе белый объект, на который ссылается
  уже просмотренный чёрный, ушёл бы в мусор живым. Без перемещения проще работать с C и
  указателями; фрагментацию берут на себя размерные классы аллокатора.

</details>

## ⚙️ Цена на практике

- **`map` против массива.** `map[byte]int` для счётчика символов — хеш на каждом доступе,
  память в куче и нагрузка на GC. `[256]int` (если не убегает) — на стеке, доступ — одно
  обращение по индексу, ложится в кэш. O(…) одинаков, на горячем пути разница в разы —
  поэтому в [скользящем окне](sliding-window.md#-цена-на-практике) для байтов берут массив.
- **Преаллокация.** `make([]int, 0, n)` и `make(map[K]V, n)` выделяют ёмкость сразу —
  `append` и вставка не [копируют при росте](big-o.md).
- **Меньше «убеганий».** Возврат `*T` из горячей функции, `interface{}`, захват в замыкание —
  частые причины кучи. Маленькую структуру дешевле копировать значением: указатель может
  увести её в кучу и добавить промахи кэша.
- **Переиспользуй вместо новой аллокации:**

<!-- snippet:pseudo -->
```go
// Буфер вне цикла: на каждой итерации — очистка без новой аллокации
buf := make([]int, 0, 1024)
for ... {
    buf = buf[:0]
    // ... работаем с buf
}

// sync.Pool — переиспользование частых временных объектов в горячих путях
var pool = sync.Pool{New: func() any { return make([]byte, 0, 1024) }}
```

## Профилирование

Профилирование — это **измерение** перед оптимизацией. Не оптимизируй «на глаз»:
сначала измерь, найди узкое место, потом улучшай и снова измеряй.

Инструменты:

```bash
go build -gcflags=-m ./...        # escape-анализ: что ушло в кучу и почему
go test -bench=. -benchmem ./...  # allocs/op и B/op рядом со временем
GODEBUG=gctrace=1 go run .        # строка на каждый цикл GC: паузы, размер кучи
go test -race ./...               # детектор гонок
```

### Бенчмарки

Бенчмарк — функция `BenchmarkX`, которую `go test` гоняет `b.N` раз и делит время на число
повторов:

```go
func BenchmarkSolve(b *testing.B) {
    data := makeInput(10000)
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        Solve(data)
    }
}
```

Вывод `1234 ns/op   0 B/op   0 allocs/op` читается так: среднее время на операцию,
байт аллоцировано, число аллокаций. **Идеал в горячем пути — 0 allocs/op.**

### CPU и память (pprof)

`pprof` — профилировщик: во время работы несколько раз в секунду запоминает, какая функция
исполняется (или кто аллоцирует), и показывает, куда ушло время и память.

```bash
go test -cpuprofile=cpu.prof -memprofile=mem.prof -bench=.
go tool pprof cpu.prof   # команда top покажет самые «дорогие» функции
```

### Чеклист интерпретации

1. Сравнивай время с наивным подходом — есть ли реальный выигрыш.
2. Минимизируй `allocs/op` в горячем пути.
3. Ищи функции, занимающие >10% времени (`top` в pprof).
4. Профилируй на **репрезентативных** данных — результаты на игрушечных входах
   обманчивы.

### 📝 Разбор: почему этот цикл аллоцирует

> **Задача.** Горячий цикл неожиданно грузит GC. Почему — и как убрать аллокации?

1. **Симптом.** `-benchmem` показывает `allocs/op > 0` там, где «вроде ничего не выделяется».
2. **Диагноз.** `-gcflags=-m` печатает `./x.go:12:9: &buf escapes to heap` — локальный объект
   убегает: вернули адрес, положили в `interface{}` или захватили в замыкание.
3. **Лечение** — из «Цены на практике» выше: значение вместо `*T`, буфер вне цикла,
   `sync.Pool`, без упаковки в интерфейс на горячем пути.
4. **Проверка.** Снова `-benchmem`: `allocs/op` стал нулём, время упало.

## ⚠️ Типичные заблуждения

Остальные заблуждения разобраны выше: горутина — не поток, пауза GC меньше миллисекунды, TCO
в Go нет, указатель не всегда дешевле значения. Ещё два:

1. **«`new`/`&` всегда кладёт в кучу»** — нет, решает escape-анализ; часто это стек.
2. **«Больше горутин — всегда быстрее»** — переключения и синхронизация стоят денег; иногда
   меньше горутин с большей работой на каждую лучше (замеры — в
   [«Параллельных алгоритмах»](parallel-algorithms.md)).

> 🌍 **Где это в настоящем коде**
>
> - [`findRunnable`](https://github.com/golang/go/blob/go1.24.0/src/runtime/proc.go#L3320) (Go 1.24) — раз в 61 такт планировщик заглядывает в глобальную очередь; кражу половины очереди делает [`runqgrab`](https://github.com/golang/go/blob/go1.24.0/src/runtime/proc.go#L6931) (`n = n - n/2`).
> - [`escape.go`](https://github.com/golang/go/blob/go1.24.0/src/cmd/compile/internal/escape/escape.go#L18) — escape-анализ: в кучу идёт переменная, чей адрес может пережить её кадр.
> - [`mallocgcTiny`](https://github.com/golang/go/blob/go1.24.0/src/runtime/malloc.go#L1098) — tiny-аллокатор склеивает мелкие объекты без указателей в один блок; все размерные классы — таблица в [`sizeclasses.go`](https://github.com/golang/go/blob/go1.24.0/src/runtime/sizeclasses.go#L90) (68 классов).
> - [`mgc.go`](https://github.com/golang/go/blob/go1.24.0/src/runtime/mgc.go#L7) — шапка файла: конкурентный mark-and-sweep без поколений и перемещения; барьер — в [`mbarrier.go`](https://github.com/golang/go/blob/go1.24.0/src/runtime/mbarrier.go#L24).
> - [`readGOGC`](https://github.com/golang/go/blob/go1.24.0/src/runtime/mgcpacer.go#L1288) — откуда берётся `GOGC`: без переменной окружения — 100, `off` выключает сборщик.
> - [`concatstrings`](https://github.com/golang/go/blob/go1.24.0/src/runtime/string.go#L26) — `a + b` выделяет новую строку и копирует в неё все части; отсюда цена `+=` в цикле.
> - [`Builder.Grow`](https://github.com/golang/go/blob/go1.24.0/src/strings/builder.go#L69) — место под `n` байт заранее, дальше записи без аллокаций.

## 🔬 Практика: найди узкое место сам

Чеклист выше — не абстракция: пакет `exercises/profiling` даёт одну функцию,
`FormatScores`, которая всегда отвечает правильно (табличный тест это уже
подтверждает) — и при этом реально медленная так, что по коду это не видно.
Задача — не дописать недостающее (TODO здесь нет), а **измерить, а не
угадать**, куда уходит время и память, и уже потом чинить.

```bash
cd exercises
go test ./profiling/                                          # корректность — уже зелёная
go test -bench=. -benchmem ./profiling/                       # только цена, не судит pass/fail
go test -run='^$' -cpuprofile=cpu.prof -bench=. ./profiling/
go tool pprof -top -cum cpu.prof                               # где ВПРАВДУ горячо
```

Интуиция подсказывает «наверное, дорого именно форматирование строки» — и
ошибается. Реально измеренный профиль на этой машине (n=2000, `-benchtime=2s`):

```
      flat  flat%   sum%        cum   cum%
         0     0%  0.59%      1.76s 34.65%  runtime.concatstrings
         0     0%  0.79%      1.38s 27.17%  runtime.gcBgMarkWorker
     0.05s  0.98%  ...        0.25s  4.92%  fmt.(*pp).doPrintf
```

Больше трети времени — в `runtime.concatstrings`: `result += ...` в цикле
копирует ВЕСЬ накопленный результат заново на каждой итерации (строки в Go
неизменяемы), это O(n²) байт скопировано, хотя цикл выглядит линейным по
числу итераций. Почти столько же — в фоновой сборке мусора: тысячи мелких
аллокаций (`fmt.Sprintf` создаёт новую строку на каждый вызов) создают
достаточно мусора, чтобы GC регулярно вмешивался. Сам `fmt.Sprintf` —
реальная, но куда меньшая доля. Ни то, ни другое не читается из кода —
цикл из четырёх строк выглядит безобидно; это находит только измерение.

Автоматическая проверка фикса — не сравнение ответа (он и так верный), а
бюджет аллокаций через `testing.AllocsPerRun` (`TestFormatScoresAllocs`):
заготовка аллоцирует ~2745 раз за вызов на 1000 элементах, эталон — ~2, за
счёт `strings.Builder.Grow` (одна аллокация под весь отчёт заранее) и
`strconv.AppendInt` в переиспользуемый буфер (без `strconv.Itoa`, который
всё ещё вернул бы новую строку на каждое число).

<div class="algo-runner" data-pkg="profiling"></div>

Сверяться с `exercises/profiling/profiling_solution.go` (`-tags solution`) —
только после собственной попытки профилирования: если сразу подсмотреть фикс,
теряется весь смысл — навык здесь не «переписать на `strings.Builder` по
памяти», а «увидеть в `pprof top`, что чинить, прежде чем чинить».

## 1. Как считать сложность

Запись `O(n)` («о большое от n») значит: число шагов растёт не быстрее, чем `n`, умноженное на
какое-то постоянное число. Отсюда главное правило — **отбросить константы и младшие
слагаемые**: `3n + 5` это `O(n)`, `n² + n` это `O(n²)`. Считаем по структуре кода:

```go
// O(n) — один проход
for i := 0; i < n; i++ {
    sum += a[i]
}

// O(n²) — вложенные циклы перемножаются
for i := 0; i < n; i++ {
    for j := 0; j < n; j++ {
        check(a[i], a[j])
    }
}

// O(log n) — размер задачи делится пополам на каждом шаге
for lo < hi {
    mid := (lo + hi) / 2
    // ... отбрасываем половину
}
```

- **Последовательные** блоки складываются: `O(n) + O(n²) = O(n²)` (берём больший).
- **Вложенные** циклы перемножаются: `O(n) · O(n) = O(n²)`. Если длина внутреннего цикла
  зависит от внешнего (`for j := 0; j < i; j++`), посчитай проходы по шагам: 0, 1, 2, …, `n − 1`.
  При `n = 4` это 0 + 1 + 2 + 3 = 6, при `n = 1000` — почти полмиллиона: сумма растёт как квадрат.
- **Вызов функции — не одна операция.** Внутри `slices.Index` и `slices.Max` — цикл по всему
  срезу, `O(n)`; стандартная сортировка стоит `O(n log n)` (этот класс — чуть ниже). Такой вызов
  в теле цикла — это вложенный цикл, просто его не видно.
- **Деление пополам** даёт `log n` шагов — что это за число, разберём сейчас.

### Логарифм — сколько раз делить пополам

Возьми 16 и дели пополам, пока не останется 1: `16 → 8 → 4 → 2 → 1` — четыре деления. Для 1024
их ровно десять. Это число и называют логарифмом: **`log₂ n` — сколько раз надо поделить `n`
пополам, чтобы дошло до 1.** Столько же раз надо удвоить 1, чтобы дорасти до `n`: `1 → 2 → 4 →
8 → 16` — те же четыре шага.

Для тысячи — около 10, для миллиона — около 20, для миллиарда — около 30. Вход вырос в миллион
раз (с тысячи до миллиарда), а шагов прибавилось всего двадцать. Поэтому `O(log n)` на практике почти не отличить от константы: поиск делением пополам по
миллиарду отсортированных чисел (бинарный поиск — цикл `for lo < hi` выше) делает около 30
сравнений.

Основание 2 в `O(log n)` обычно не пишут. Делить можно и на 10: `log₁₀ n` — сколько раз
поделить `n` на 10 до 1 (у миллиона — 6 раз против примерно 20 делений пополам). Такой счёт
всегда меньше `log₂ n` в одно и то же число раз, около 3.3, — а постоянный множитель Big-O
отбрасывает.

Классы, которые встретятся в книге, от быстрого к медленному: `O(1)`, `O(log n)`, `O(n)`,
`O(n log n)`, `O(n²)`, `O(n³)`, `O(2ⁿ)`, `O(n!)`. Здесь `2ⁿ` — число всех подмножеств из `n`
элементов, а `n!` = 1·2·…·`n` — число их перестановок (способов выстроить по порядку). На больших
`n` выигрывает тот, кто в этом ряду левее.

**Посмотри** на них вживую. Листай «›»: кривые добавляются по одной, от самой пологой к самой
крутой; шкала честная линейная, поэтому `n²` и `2ⁿ` буквально **пробивают потолок** графика, пока
`log n` стелется по оси. Последний кадр — срез при `n = 20`: `log n` ≈ 4.3, `n` = 20,
`n log n` ≈ 86, `n²` = 400, `2ⁿ` = 1 048 576.

### Размер входа подсказывает сложность

Ограничение на `n` в условии — это подсказка, какой сложности от тебя ждут. Грубый
ориентир с запасом: за секунду успевает около **10⁸ простых операций**. Подставь `n` в
формулу — и сразу видно, какие решения даже не стоит писать. Правая колонка называет шаблоны
следующих глав (ДП — динамическое программирование), сейчас важна средняя:

| `n` до | Успевает | Что это обычно значит |
|---|---|---|
| 10–11 | `O(n!)` | перебор перестановок ([backtracking](backtracking.md)) |
| 20–25 | `O(2ⁿ)` | перебор подмножеств, ДП по битовым маскам |
| 500 | `O(n³)` | три вложенных цикла, ДП по отрезкам |
| 5 000 | `O(n²)` | два вложенных цикла, ДП по двум строкам |
| 10⁵–10⁶ | `O(n log n)` | сортировка, куча, бинарный поиск внутри цикла |
| 10⁷ | `O(n)` | один проход: окно, два указателя, префиксные суммы, хеш |
| больше | `O(log n)` или `O(1)` | бинарный поиск по ответу, формула |

Например, `n ≤ 10⁵` почти всегда значит «нужен `O(n log n)` или быстрее»: `O(n²)` — это
10¹⁰ операций, минуты вместо секунды. Тот же расчёт работает и в сервисе, только вместо
лимита задачи — бюджет запроса: 50 мс — это около 5·10⁶ простых операций на всё.

## 1.5 O, Ω и Θ — три буквы на одном примере

До сих пор мы писали только `O`. Рядом с ней в книгах и на собеседованиях встречаются ещё две
буквы — `Ω` («омега») и `Θ` («тета»). Различить их проще всего на **поиске максимума в
неотсортированном массиве** — один проход:

- Шагов не больше `c·n`, где `c` — постоянное число, не зависящее от `n`: рост ограничен
  **сверху** прямой. Это **O(n)** — верхняя граница, «растёт не быстрее `n`».
- Может ли какой-нибудь алгоритм быстрее? **Нет**: обязан посмотреть каждый элемент — пропустил
  хоть один, а вдруг максимум именно там. Значит, меньше `n` шагов не бывает: это **Ω(n)** —
  нижняя граница, «растёт не медленнее `n`».
- Раз и сверху `n`, и снизу `n` — оценка **точная**, без зазора: **Θ(n)**.

Тонкость, на которой ловят: **Ω бывает про алгоритм, а бывает про задачу целиком**.
«Сортировка сравнениями — Ω(n log n)» значит, что *никакой* алгоритм, который узнаёт порядок
только сравнениями, не обойдётся в худшем случае меньше чем примерно `n log n` сравнениями —
ни существующий, ни будущий. Почему так и как эту границу обходит сортировка подсчётом — в
[главе о сортировках](sorting.md#почему-сравнениями-не-быстрее-n-log-n).

Ещё одна вещь, которую стоит увидеть заранее: **переменных в оценке может быть несколько**,
и тогда они независимы друг от друга. В главах о графах ты встретишь `O(V + E)` — время обхода
зависит и от числа вершин, и от числа рёбер, и **ни одну не выразить через другую**: граф с
миллионом вершин может иметь и ноль рёбер, и сотни миллиардов. Поэтому `O(V + E)` нельзя «упростить»
до `O(V)` или `O(E)` — сложение здесь значит «кто из двух окажется больше, тот и доминирует».
То же с `O(n·k)`, `O(n + m)` для двух строк: держи каждую переменную отдельно и не подставляй
вместо них «одно общее n».

## 2. Худший, средний, лучший случай и память

Возьми линейный поиск — перебрать срез из `n` элементов по порядку, пока не встретится число `x`:

```go
func indexOf(a []int, x int) int {
    for i, v := range a {
        if v == x {
            return i
        }
    }
    return -1
}
```

Число стоит первым — одно сравнение: это **лучший случай**. Числа нет вовсе — `n` сравнений:
**худший**. Стоит где попало — в среднем около `n/2` (на восьми элементах, если искать каждый
по очереди, выходит 4.5 сравнения): **средний**. Алгоритм один, а оценок три. Когда говорят
«работает за `O(n)`» без уточнений, имеют в виду **худший случай**: только он даёт гарантию.
На собеседовании — так же. Бывает, что случаи расходятся сильнее: у быстрой сортировки в среднем
`O(n log n)`, а в худшем `O(n²)` — это разобрано в
[главе о сортировках](sorting.md#3-быстрая-сортировка-сначала-разбиение).

Отдельно считают **память (space)**: вспомогательные структуры и **глубину рекурсии**. Эта
функция не заводит ни новых массивов, ни `map` (`a[1:]` смотрит в тот же массив):

```go
func sum(a []int) int {
    if len(a) == 0 {
        return 0
    }
    return a[0] + sum(a[1:])
}
```

Но вызов на `n` элементах ждёт ответа от вызова на `n − 1`, тот — от вызова на `n − 2`, и так до
пустого среза. Каждый незавершённый вызов держит в стеке горутины свой **кадр** — память под
его аргументы и локальные переменные. В самый глубокий момент кадров `n + 1`, значит память —
`O(n)`. Та же сумма обычным циклом обошлась бы `O(1)`: одна переменная на весь проход.

## 3. Амортизированный анализ: рост среза

Иногда отдельная операция дорогая, но **редкая** — и в среднем по серии получается дёшево.
Это **амортизированная** стоимость. Канонический пример — `append` к срезу в Go.

Когда ёмкость заполнена, срез **удваивается**: выделяется новый массив, и все элементы
**копируются** (это `O(len)`). Дорого! Но удвоение случается всё реже, и суммарно копий за
`n` добавлений — **меньше 2n**. Значит, на одно добавление приходится `O(1)`
амортизированно.

```go
func appendItem(s []int, x int) []int {
    if len(s) == cap(s) {
        bigger := make([]int, len(s), max(1, 2*cap(s)))
        copy(bigger, s) // O(len): копируем всё в новый массив — дорогой шаг
        s = bigger
    }
    return append(s, x) // обычно на месте: O(1)
}
```

Жёлтым подсвечен дорогой шаг — копирование при удвоении; синие слоты заняты, пунктирные —
запас ёмкости. Дорогие шаги редки, поэтому в среднем `append` — `O(1)`:

и снимается **один раз** за весь проход.

## ⚡ Что помнить на собеседовании

- **Отбрасывай константы и младшие слагаемые**: `O(2n + 100)` = `O(n)`.
- **Вложенные циклы перемножаются**, последовательные — берут больший.
- По умолчанию называют **худший случай**; средний/лучший — отдельно.
- **Амортизированно O(1)** = дёшево в среднем по серии, хотя отдельный шаг бывает `O(n)`.
- Удвоение ёмкости среза или хеш-таблицы (та при росте раскладывает ключи заново) → суммарная работа `O(n)`, а не `O(n²)`.
- Считай и **память**: структуры + глубину рекурсии.

## 🧠 Почему это корректно

### Почему законно отбрасывать константы

Big-O говорит о **поведении при росте n**, а не об абсолютном времени. Формально
`f(n) = O(g(n))`, если найдутся константа `c` и порог `n₀`, что `f(n) ≤ c·g(n)` для всех
`n ≥ n₀`. Например, `3n + 5 ≤ 4n` при всех `n ≥ 5` — подходят `c = 4` и `n₀ = 5`, значит
`3n + 5 = O(n)`. Любая константа поглощается `c`, любое младшее слагаемое — большим при достаточно
большом `n`. Поэтому `100n` и `n` — это один класс `O(n)`: на больших n они отличаются лишь
множителем, не темпом роста.

### Почему удвоение даёт суммарно O(n)

Копирования при росте до размера `n` происходят на размерах `1, 2, 4, …` — это
геометрическая прогрессия. Её сумма `1 + 2 + 4 + … < 2n`. Значит, **полная** работа всех
`append` — линейна, а на одну операцию приходится `O(1)` амортизированно. Удваивали бы
ёмкость не вдвое, а **на константу** (`+1`) — копий было бы `1 + 2 + … + n = O(n²)`, и
амортизация сломалась бы. Именно множитель (а не аддитивный шаг) роста делает append дешёвым.

### Амортизация ≠ средний случай

Средний случай усредняет по **случайным входам** (с вероятностями). Амортизация усредняет
по **последовательности операций** на худшем входе — без всякой вероятности. Гарантия
амортизированного `O(1)` держится **всегда**, а не «в среднем повезёт».

## ⚙️ Цена на практике

### Константы решают на малых n

`O(n log n)` асимптотически бьёт `O(n²)`, но на коротких массивах сортировка вставками
(`O(n²)`, крошечная константа, дружба с кэшем) обгоняет quicksort — поэтому
[`slices.Sort`](sorting.md#-цена-на-практике) переключается на неё для кусков ≤ 12.
«Асимптотически лучше» ≠ «быстрее на твоих данных».

### Преаллокация убирает копии

Если знаешь размер заранее — `make([]int, 0, n)` выделяет ёмкость сразу, и `append` ни разу
не копирует. То же для `map` — `make(map[K]V, n)`. Это убирает амортизированные, но реальные
расходы на рост.

**Сколько именно они стоят — замер.** В тренажёре есть бенчмарк
(`exercises/bigo/append_bench_test.go`): миллион `append` в срез с преаллокацией и без.
Запусти: `go test -bench=Append -benchmem ./bigo/` (из `exercises/`). Реальный вывод
(i5-12400, Go 1.24):

```text
BenchmarkAppend_NoPrealloc-12     68    16 474 477 ns/op    41 678 306 B/op    40 allocs/op
BenchmarkAppend_Prealloc-12      742     1 721 916 ns/op     8 388 623 B/op     1 allocs/op
```

Три колонки рассказывают всю историю амортизации: без преаллокации рост среза сделал
**40 перевыделений** и перелопатил **41.7 МБ** (сумма всех промежуточных массивов — та самая
геометрическая прогрессия из раздела выше), с преаллокацией — **одно выделение ровно на 8.4 МБ**
(2²⁰ × 8 байт = 8 388 608) и **почти в 10 раз быстрее**. Амортизированный `O(1)` честен по времени на
операцию, но «редкие дорогие шаги» — это реальные мегабайты и такты, которые можно просто
не платить, если размер известен.

### Кэш и константа за Big-O

Два `O(n)`-алгоритма различаются в разы из-за **локальности**: проход по срезу (соседние
адреса) быстрее погони за указателями по списку/`map`, хотя Big-O одинаков. Big-O — про
масштабирование; константу за ним меряют профилировщиком (`pprof`, `testing.B`).

## ⚠️ Типичные ошибки

1. **Считать `O(2n)` или `O(n + 5)` чем-то отличным от `O(n)`** — константы отбрасываются.
2. **Складывать вложенные циклы** вместо перемножения (`O(n²)`, а не `O(2n)`).
3. **Путать амортизированный O(1) с гарантией O(1) на каждый шаг** — отдельный append при
   росте всё же `O(n)`.
4. **Забывать про память** — рекурсия глубины n это `O(n)` стека.
5. **Слепо верить асимптотике на малых n** — там правят константы и кэш.
6. **Рост ёмкости на константу вместо умножения** — превращает суммарный `O(n)` в `O(n²)`.
7. **Не замечать цикл внутри вызова** — поиск по срезу (`slices.Index`) в теле цикла по `n`
   элементам стоит `O(n · m)`, где `m` — длина того среза; если он тоже порядка `n` — это
   `O(n²)`, хотя в коде виден один `for`.

## 📝 Разбор задачи: Next Greater Element

> **Задача** ([LeetCode 496](https://leetcode.com/problems/next-greater-element-i/) / 503).
> Для каждого элемента найти ближайший **больший** справа (−1, если нет).
> Пример: `[2, 1, 3, 1]` → `[3, 3, -1, -1]`.

**Шаг 1. Наивно — для каждого ищем вправо, O(n²).**

```go
func nextGreater(nums []int) []int {
    res := make([]int, len(nums))
    for i := range nums {
        res[i] = -1
        for j := i + 1; j < len(nums); j++ {
            if nums[j] > nums[i] {
                res[i] = nums[j]
                break
            }
        }
    }
    return res
}
```

Работает, но вложенный цикл даёт `O(n²)`: на убывающем массиве каждый `i` сканирует весь
хвост.

**Шаг 2. Где повторяется работа.** Возьми `[5, 4, 3, 2, 6]`. Для 5 наивный цикл идёт вправо мимо
4, 3 и 2 и доходит до 6. Для 4 — мимо 3 и 2 до той же 6, для 3 и для 2 — снова до неё. Четыре
прохода подряд кончаются на одной шестёрке: 10 сравнений на пять чисел, а на длинном убывающем
массиве их число растёт как `n²`. Пока шестёрки нет, 5, 4, 3 и 2 просто **ждут** числа больше
себя.

Сложим ждущих в **стопку**: новое кладём сверху и снимаем тоже сверху — такая стопка называется
**стеком** (последним положил — первым снял). Пришло новое число — сравни его с верхним ждущим.
Новое больше — оно и есть ответ для верхнего: сними верхнего, запиши ему ответ и сравни новое со
следующим. Новое не больше — остановись: ниже лежат числа не меньше верхнего (почему —
в следующем абзаце), им новое тем более не ответ. Потом новое число само кладём наверх ждать. На нашем примере 5, 4, 3 и 2 по
очереди ложатся в стопку, а 6 снимает их сверху вниз — 2, 3, 4, 5 — и каждому раздаёт ответ 6.
Сравнений 7 вместо 10, и, главное, каждое число один раз кладётся в стопку и не больше одного
раза снимается — за весь проход не больше `2n` операций.

Числа в такой стопке от дна к вершине никогда не растут: всё, что меньше нового числа, оно сняло,
прежде чем лечь само. Стек, значения в котором идут только в одну сторону, называют
**монотонным стеком**; как шаблон он разобран в [главе о монотонном стеке](monotonic-stack.md).
Храним в стопке индексы, а не сами числа: снимая ждущего, надо знать, в какую ячейку `res`
записать ответ.

**Шаг 3. Оптимум — монотонный стек, амортизированно O(n).**

```go
func nextGreater(nums []int) []int {
    res := make([]int, len(nums))
    stack := []int{} // индексы; значения от дна к вершине не возрастают
    for i, v := range nums {
        res[i] = -1
        for len(stack) > 0 && nums[stack[len(stack)-1]] < v {
            res[stack[len(stack)-1]] = v // нашли больший для вершины
            stack = stack[:len(stack)-1]
        }
        stack = append(stack, i)
    }
    return res
}
```

Листай «›» и следи за столбиком стека: каждый новый элемент **выталкивает всех меньших**
(для них он — ответ, шаг подсвечен), а потом встаёт ждать сам. Ключ к оценке: каждый
индекс кладётся в стек и снимается **не больше одного раза** — суммарно ≤ 2n операций,
поэтому вложенный цикл всё равно O(n):

<div class="algo-viz" data-viz="monotonic-stack" data-array="2,1,3,1"></div>

Вложенный цикл `for len(stack) > 0 …` пугает, но он **амортизированный**: суммарно по всем `i`
он снимает со стека не больше `n` элементов. Это тот же приём подсчёта, что и в анализе роста среза.

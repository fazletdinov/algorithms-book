## 1. Как считать сложность

Главное правило — **отбросить константы и младшие слагаемые**: `3n + 5` это `O(n)`,
`n² + n` это `O(n²)`. Считаем по структуре кода:

```go
// O(n) — один проход
for i := 0; i < n; i++ {
    sum += a[i]
}

// O(n²) — вложенные циклы перемножаются
for i := 0; i < n; i++ {
    for j := 0; j < n; j++ {
        check(a[i], a[j])
    }
}

// O(log n) — размер задачи делится пополам на каждом шаге
for lo < hi {
    mid := (lo + hi) / 2
    // ... отбрасываем половину
}
```

- **Последовательные** блоки складываются: `O(n) + O(n²) = O(n²)` (берём больший).
- **Вложенные** циклы перемножаются: `O(n) · O(n) = O(n²)`.
- **Деление пополам** даёт `log n` уровней.

## 2. Худший, средний, лучший случай и память

Одна функция имеет **разные** оценки для разных входов: быстрая сортировка — `O(n log n)`
в среднем, но `O(n²)` в худшем (зловредный pivot). На собеседовании по умолчанию имеют в
виду **худший случай** (`O`), если не сказано иное.

Отдельно считают **память (space)**: вспомогательные структуры и **глубину рекурсии**.
Сортировка слиянием — `O(n)` памяти, быстрая — `O(log n)` на стек; обход дерева в глубину —
`O(h)`.

## 3. Амортизированный анализ: рост среза

Иногда отдельная операция дорогая, но **редкая** — и в среднем по серии получается дёшево.
Это **амортизированная** стоимость. Канонический пример — `append` к срезу в Go.

Когда ёмкость заполнена, срез **удваивается**: выделяется новый массив, и все элементы
**копируются** (это `O(len)`). Дорого! Но удвоение случается всё реже, и суммарно копий за
`n` добавлений — **меньше 2n**. Значит, на одно добавление приходится `O(1)`
амортизированно.

```go
func appendItem(s []int, x int) []int {
    if len(s) == cap(s) {
        bigger := make([]int, len(s), max(1, 2*cap(s)))
        copy(bigger, s) // O(len): копируем всё в новый массив — дорогой шаг
        s = bigger
    }
    return append(s, x) // обычно на месте: O(1)
}
```

Жёлтым подсвечен дорогой шаг — копирование при удвоении; синие слоты заняты, пунктирные —
запас ёмкости. Дорогие шаги редки, поэтому в среднем `append` — `O(1)`:

## ⚡ Что помнить на собеседовании

- **Отбрасывай константы и младшие слагаемые**: `O(2n + 100)` = `O(n)`.
- **Вложенные циклы перемножаются**, последовательные — берут больший.
- По умолчанию называют **худший случай**; средний/лучший — отдельно.
- **Амортизированно O(1)** = дёшево в среднем по серии, хотя отдельный шаг бывает `O(n)`.
- Удвоение ёмкости / рехеширование → суммарная работа `O(n)`, а не `O(n²)`.
- Считай и **память**: структуры + глубину рекурсии.

## 🧠 Почему это корректно

### Почему законно отбрасывать константы

Big-O говорит о **поведении при росте n**, а не об абсолютном времени. Формально
`f(n) = O(g(n))`, если найдутся константа `c` и порог `n₀`, что `f(n) ≤ c·g(n)` для всех
`n ≥ n₀`. Любая константа поглощается `c`, любое младшее слагаемое — большим при достаточно
большом `n`. Поэтому `100n` и `n` — это один класс `O(n)`: на больших n они отличаются лишь
множителем, не темпом роста.

### Почему удвоение даёт суммарно O(n)

Копирования при росте до размера `n` происходят на размерах `1, 2, 4, …` — это
геометрическая прогрессия. Её сумма `1 + 2 + 4 + … < 2n`. Значит, **полная** работа всех
`append` — линейна, а на одну операцию приходится `O(1)` амортизированно. Удваивали бы
ёмкость не вдвое, а **на константу** (`+1`) — копий было бы `1 + 2 + … + n = O(n²)`, и
амортизация сломалась бы. Именно множитель (а не аддитивный шаг) роста делает append дешёвым.

### Амортизация ≠ средний случай

Средний случай усредняет по **случайным входам** (с вероятностями). Амортизация усредняет
по **последовательности операций** на худшем входе — без всякой вероятности. Гарантия
амортизированного `O(1)` держится **всегда**, а не «в среднем повезёт».

## ⚙️ Цена на практике

### Константы решают на малых n

`O(n log n)` асимптотически бьёт `O(n²)`, но на коротких массивах сортировка вставками
(`O(n²)`, крошечная константа, дружба с кэшем) обгоняет quicksort — поэтому
[`slices.Sort`](sorting.md#-цена-на-практике) переключается на неё для кусков ≤ 12.
«Асимптотически лучше» ≠ «быстрее на твоих данных».

### Преаллокация убирает копии

Если знаешь размер заранее — `make([]int, 0, n)` выделяет ёмкость сразу, и `append` ни разу
не копирует. То же для `map` — `make(map[K]V, n)`. Это убирает амортизированные, но реальные
расходы на рост.

### Кэш и константа за Big-O

Два `O(n)`-алгоритма различаются в разы из-за **локальности**: проход по срезу (соседние
адреса) быстрее погони за указателями по списку/`map`, хотя Big-O одинаков. Big-O — про
масштабирование; константу за ним меряют профилировщиком (`pprof`, `testing.B`).

## ⚠️ Типичные ошибки

1. **Считать `O(2n)` или `O(n + 5)` чем-то отличным от `O(n)`** — константы отбрасываются.
2. **Складывать вложенные циклы** вместо перемножения (`O(n²)`, а не `O(2n)`).
3. **Путать амортизированный O(1) с гарантией O(1) на каждый шаг** — отдельный append при
   росте всё же `O(n)`.
4. **Забывать про память** — рекурсия глубины n это `O(n)` стека.
5. **Слепо верить асимптотике на малых n** — там правят константы и кэш.
6. **Рост ёмкости на константу вместо умножения** — превращает суммарный `O(n)` в `O(n²)`.

## 📝 Разбор задачи: Next Greater Element

> **Задача** ([LeetCode 496](https://leetcode.com/problems/next-greater-element-i/) / 503).
> Для каждого элемента найти ближайший **больший** справа (−1, если нет).
> Пример: `[2, 1, 3, 1]` → `[3, 3, -1, -1]`.

**Шаг 1. Наивно — для каждого ищем вправо, O(n²).**

```go
func nextGreater(nums []int) []int {
    res := make([]int, len(nums))
    for i := range nums {
        res[i] = -1
        for j := i + 1; j < len(nums); j++ {
            if nums[j] > nums[i] {
                res[i] = nums[j]
                break
            }
        }
    }
    return res
}
```

Работает, но вложенный цикл даёт `O(n²)`: на убывающем массиве каждый `i` сканирует весь
хвост.

**Шаг 2. Наблюдение.** Если держать **монотонный стек** индексов (значения убывают), то
каждый элемент попадёт в стек и покинет его **ровно один раз** — суммарно `O(n)`.

**Шаг 3. Оптимум — монотонный стек, амортизированно O(n).**

```go
func nextGreater(nums []int) []int {
    res := make([]int, len(nums))
    stack := []int{} // индексы, значения убывают
    for i, v := range nums {
        res[i] = -1
        for len(stack) > 0 && nums[stack[len(stack)-1]] < v {
            res[stack[len(stack)-1]] = v // нашли больший для вершины
            stack = stack[:len(stack)-1]
        }
        stack = append(stack, i)
    }
    return res
}
```

Вложенный `while` пугает, но он **амортизированный**: суммарно по всем `i` он снимает со
стека не больше `n` элементов. Это тот же приём подсчёта, что и в анализе роста среза.

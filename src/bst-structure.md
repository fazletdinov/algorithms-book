## 🧱 Как устроен узел

Узел дерева поиска — это **значение** и **две ссылки**: на левое и правое поддерево. Дерево
задаётся корнем (`root`); пустое поддерево — `nil`.

```go
type Node struct {
    Val   int
    Left  *Node // поддерево со значениями < Val
    Right *Node // поддерево со значениями > Val
}
```

```
        5
      /   \
     3     8
    / \   / \
   2   4 7   9
```

Инвариант BST держит всё поведение: для **любого** узла все значения слева меньше его, все
справа — больше. Отсюда сразу следует:

1. **Поиск идёт по одному пути.** Сравнил с узлом — и знаешь, в какое из двух поддеревьев идти;
   второе можно отбросить целиком. Поэтому цена — высота дерева `h`, а не число узлов.
2. **In-order обход отсортирован.** «Левое поддерево → узел → правое» по индукции выдаёт
   возрастающую последовательность — это прямое следствие инварианта.
3. **Балансировка решает всё.** При случайных вставках `h ≈ log n`, но отсортированный вход
   делает дерево «палкой» (`h = n`). Сбалансированные варианты (AVL, red-black) держат
   `h = O(log n)` принудительно.

## 🔎 Поиск: `Search`

Поиск — спуск от корня: на каждом узле одно сравнение решает, в какое поддерево идти. Половина
оставшегося дерева отбрасывается на каждом шаге — отсюда O(h).

```go
func (t *BST) Search(val int) bool {
    node := t.root
    for node != nil {
        if val == node.Val {
            return true          // нашли
        } else if val < node.Val {
            node = node.Left     // меньше — влево
        } else {
            node = node.Right    // больше — вправо
        }
    }
    return false                 // дошли до nil
}
```

> 💡 **Демонстрация поиска.** Дерево построено вставкой `5,3,8,2,4,7,9`. Ищем `7`: `5 → вправо
> → 8 → влево → 7`. Видно, как на каждом узле отбрасывается целое поддерево. Попробуй искомое
> `6` — спуск упрётся в `nil`, значения нет.

## ➕ Вставка: `Insert`

Вставка — это тот же спуск, что и поиск: ищем **пустое место** (где должен был бы лежать ключ),
и подцепляем туда новый лист. Инвариант сохраняется автоматически — мы пришли ровно в ту точку,
куда ключ кладёт порядок.

```go
func (t *BST) Insert(val int) {
    if t.root == nil { t.root = &Node{Val: val}; return }
    node, parent := t.root, t.root
    for node != nil {            // ищем место (лист)
        parent = node
        if val < node.Val {
            node = node.Left
        } else {
            node = node.Right
        }
    }
    leaf := &Node{Val: val}      // создаём лист
    if val < parent.Val {
        parent.Left = leaf
    } else {
        parent.Right = leaf
    }
}
```

> 💡 **Демонстрация вставки.** В то же дерево вставляем `6`: спуск `5 → вправо → 8 → влево → 7
> → влево → пусто`, и `6` подцепляется листом слева от `7`. In-order после вставки —
> `2,3,4,5,6,7,8,9`, порядок сохранён.

## 🗑️ Удаление: `Delete` (три случая)

Удаление — самая тонкая операция, потому что узел нельзя просто «стереть»: нужно сохранить
инвариант и связность. Три случая:

1. **Лист** (нет детей) — просто отцепляем (ссылка родителя → `nil`).
2. **Один ребёнок** — родитель перецепляется напрямую на этого ребёнка (узел «выпадает»).
3. **Два ребёнка** — узел нельзя удалить на месте. Берём **преемника** — минимум правого
   поддерева (самый левый узел справа): это следующее по величине значение. **Копируем** его
   значение в удаляемый узел, а затем удаляем сам узел-преемник (у него максимум один — правый —
   ребёнок, то есть случай 1 или 2). Так инвариант сохраняется: на месте узла оказывается
   ровно то значение, что и должно идти следующим по порядку.

```go
func (t *BST) Delete(val int) {
    node, parent := t.root, (*Node)(nil)
    for node != nil && node.Val != val {        // ищем узел
        parent = node
        if val < node.Val { node = node.Left } else { node = node.Right }
    }
    if node == nil { return }                   // значения нет
    if node.Left != nil && node.Right != nil {  // два ребёнка
        succ, sp := node.Right, node            // min правого поддерева
        for succ.Left != nil { sp = succ; succ = succ.Left }
        node.Val = succ.Val                     // копируем значение преемника
        node, parent = succ, sp                 // теперь удаляем узел преемника
    }
    child := node.Left                          // у узла ≤ 1 ребёнка
    if child == nil { child = node.Right }
    switch {                                    // отцепляем узел
    case parent == nil: t.root = child
    case parent.Left == node: parent.Left = child
    default: parent.Right = child
    }
}
```

> 💡 **Демонстрация удаления (случай двух детей).** Удаляем корень `5` (у него два ребёнка).
> Преемник — минимум правого поддерева: `8 → влево → 7`. Значение `7` копируется в корень
> (на миг в дереве два узла `7` — исходный и дубликат), затем узел-преемник `7` отцепляется.
> Новый корень — `7`, in-order остаётся `2,3,4,7,8,9`. Попробуй удалить `2` (лист) или
> значение, которого нет.

## 🔁 In-order = отсортированный порядок

Обход «левое поддерево → узел → правое поддерево» выдаёт значения по возрастанию — это и есть
главный «бесплатный» бонус BST. Сам обход (рекурсия по узлам) разобран в главе
[Tree DFS](tree-dfs.md); здесь важно запомнить связь: **отсортированный вывод — прямое следствие
инварианта**, а не отдельный алгоритм.

## 🧠 Почему это корректно

### Инвариант ведёт поиск по одному пути

Сравнение с узлом делит оставшиеся ключи на два непересекающихся множества (меньше / больше).
Нужное значение, если оно есть, лежит ровно в одном поддереве — второе отбрасывается целиком.
Поэтому путь поиска — это спуск от корня до узла или `nil`, его длина ≤ высоты `h`.

### Почему преемник сохраняет порядок при удалении

В случае двух детей удаляемый узел должен быть заменён значением, которое **не нарушит порядок**:
оно должно быть больше всего левого поддерева и меньше всего правого. Это в точности **минимум
правого поддерева** (следующее по величине значение). У него нет левого ребёнка (иначе он не
минимум), поэтому его собственное удаление — это лёгкий случай 1 или 2. Симметрично подошёл бы
максимум левого поддерева.

### Стоимость = высота, а балансировку никто не гарантирует

Все три операции — это спуск по дереву, поэтому их цена равна высоте `h`. В сбалансированном
дереве `h = O(log n)`. Но обычный BST **не балансируется сам**: вставка уже отсортированных
данных строит «палку» из правых ссылок, `h = n`, и поиск деградирует до O(n). Это не баг
инварианта, а отсутствие балансировки — её добавляют AVL/red-black деревья.

## ⚙️ Цена на практике

### BST против хеш-множества и массива

- **Хеш-множество/словарь:** поиск/вставка/удаление в среднем O(1), но **нет порядка** —
  ни диапазонов, ни «следующего большего», ни сортированного обхода.
- **Отсортированный массив:** бинарный поиск O(log n) и отличная локальность кэша, но
  вставка/удаление в середине — O(n) (сдвиг).
- **BST:** все три операции O(h) **и** порядок «бесплатно» (диапазоны, k-й, in-order). Цена —
  указатели (память, промахи кэша) и необходимость балансировки.

Бери BST, когда нужны **и** изменяемость, **и** порядок. Нужен только быстрый доступ без
порядка — хеш; только максимум/минимум — куча.

### В Go нет встроенного BST

Стандартная библиотека Go не даёт упорядоченного дерева: на практике берут `map` (без порядка),
отсортированный срез + `sort.Search`, или внешнюю реализацию (например, B-дерево). Понимать
устройство BST всё равно нужно — и для собеседований, и чтобы выбрать правильную замену.

### Балансировка — отдельная большая тема

Самобалансирующиеся деревья (AVL, red-black) держат `h = O(log n)` поворотами при вставке/
удалении. Это сложнее базового BST и выходит за рамки главы; для интервью обычно достаточно
уверенно реализовать обычный BST и **проговорить риск вырождения** и способ его лечить.

## ⚠️ Типичные ошибки

1. **Вырождение в список** — забыли про баланс; на отсортированном входе дерево становится «палкой» с O(n).
2. **Удаление с двумя детьми «на месте»** — нельзя; нужен преемник (или предшественник) и копирование значения.
3. **Потеря ссылки на родителя** — при удалении/вставке нужен `parent`, иначе не к чему перецепить.
4. **Разыменование `nil`** — спуск должен проверять `node != nil` перед обращением к полям.
5. **Нарушение инварианта при ручной правке** — любая вставка/удаление должны попадать строго в позицию, заданную порядком.

> 🧭 **Зачем отдельная глава.** B-дерево — это обобщение [BST](bst-structure.md), где узел хранит
> **много** ключей и имеет **много** детей. Зачем? Когда данные лежат на диске, дорого не сравнение,
> а **чтение блока**; широкий узел (десятки-сотни ключей = один блок) делает дерево очень низким,
> и поиск стоит единицы чтений с диска. Это структура за индексами баз данных и файловыми
> системами. Здесь разбираем устройство и ключевой механизм — **разделение узла** при переполнении.

## 🧱 Как устроено

Узел B-дерева хранит **массив отсортированных ключей** и **массив детей** (на один больше, чем
ключей). Ключи делят диапазон на поддиапазоны, и каждый ребёнок отвечает за свой.

```go
type Node struct {
    keys     []int
    children []*Node // len(children) == len(keys)+1 (или 0 у листа)
    leaf     bool
}
```

```
                 [ 2 | 4 ]
                /    |    \
            [1]    [3]    [5 6]
          <2     2..4      >4
```

Инварианты (для минимальной степени `t`):

1. **Размер узла ограничен:** от `t−1` до `2t−1` ключей (кроме корня — он может быть меньше). Это
   держит узлы «плотными» и дерево низким.
2. **Дети между ключами:** ключи внутри узла отсортированы, ребёнок `i` хранит значения строго
   между соседними ключами. Поиск выбирает ровно одну ветку.
3. **Все листья на одной глубине.** Дерево растёт **только вверх** — при переполнении корня; за
   счёт этого оно идеально сбалансировано по высоте без поворотов.

## 🔎 Поиск: `Search`

В каждом узле ищем позицию ключа (линейно или бинарно). Если нашли — готово; если узел лист — ключа
нет; иначе спускаемся в ребёнка между подходящими ключами.

```go
func (t *BTree) Search(k int) bool {
    n := t.root
    for n != nil {
        i := 0
        for i < len(n.keys) && k > n.keys[i] { i++ }    // позиция в узле
        if i < len(n.keys) && k == n.keys[i] { return true } // нашли
        if n.leaf { return false }                      // лист — больше негде
        n = n.children[i]                               // спуск к ребёнку
    }
    return false
}
```

> 💡 **Демонстрация поиска.** Дерево над ключами `1..10` (t=2). Ищем `7`: в каждом узле выбираем
> позицию и спускаемся в нужного ребёнка между ключами — всего пара шагов до листа. Попробуй ключ,
> которого нет.

## ➕ Вставка: `Insert` (с разделением узлов)

Вставка идёт **сверху вниз** и делит **полные** узлы заранее: при переполнении узла средний ключ
поднимается в родителя, а узел распадается на два. Так гарантируется, что спуск всегда приходит в
неполный узел, а дерево растёт строго вверх.

```go
func (t *BTree) Insert(k int) {
    if t.root.full() {               // корень полон — растим высоту
        s := &Node{children: []*Node{t.root}}
        s.splitChild(0); t.root = s  // средний ключ поднимается
    }
    insertNonFull(t.root, k)
}

func insertNonFull(n *Node, k int) {
    if n.leaf { n.insertKey(k); return }       // в лист — по порядку
    i := n.childIndex(k)
    if n.children[i].full() {        // делим полного ребёнка ДО спуска
        n.splitChild(i)
        if k > n.keys[i] { i++ }
    }
    insertNonFull(n.children[i], k)
}
```

> 💡 **Демонстрация вставки.** В дерево над `1..5` (корень `[2]`, листья `[1]` и `[3,4,5]`) вставляем
> `6`. Лист `[3,4,5]` полон — он **делится**: средний ключ `4` поднимается в корень (`[2,4]`), лист
> распадается на `[3]` и `[5]`, и `6` встаёт в `[5,6]`. Все листья остались на одной глубине.

## ➖ Удаление: `Delete` (с заимствованием и слиянием)

Удаление — самая хитрая операция B-дерева, потому что узлу нельзя «похудеть» ниже `t−1` ключей
(иначе сломается баланс). Правило простое: **спускаемся к ключу, но не входим в «бедный» узел**
(у которого ровно `t−1` ключей) — сперва его «подкармливаем». Есть два инструмента:

- **заимствование** — если у соседнего брата ключей с запасом (`≥ t`), проворачиваем один ключ
  через родителя: ключ-разделитель из родителя спускается в бедный узел, а к родителю поднимается
  крайний ключ брата;
- **слияние** — если и у братьев по `t−1` ключей, сливаем бедный узел, ключ-разделитель родителя
  и брата **в один** узел (`t−1 + 1 + t−1 = 2t−1` — как раз влезает).

А сам ключ убираем так: из **листа** — просто вычёркиваем; из **внутреннего** узла — заменяем его
**предшественником или преемником** (взяв из ребёнка, у которого есть запас) и удаляем уже тот
ключ ниже. Если оба ребёнка бедны — сливаем их и удаляем в слитом узле.

```go
func del(n *Node, k int) {
    i := n.find(k)
    if n.leaf {
        n.removeKey(k)                   // лист — просто убираем
    } else if i < len(n.keys) && n.keys[i] == k {
        replaceWithPredOrSucc(n, i)      // заменяем соседним ключом, удаляем ниже
    } else {
        if len(n.children[i].keys) < t {
            fill(n, i)                   // заём у соседа или слияние
            if i > len(n.keys) {         // слияние с ЛЕВЫМ братом сдвинуло ребёнка
                i--                      // (крайний правый случай) — спускаемся в него
            }
        }
        del(n.children[i], k)            // и только теперь спускаемся
    }
}
```

Листай «›»: удаляем `4`. Он лежит в **корне** — во внутреннем узле, поэтому его заменяет
преемник `5` из правого поддерева, а удалять дальше приходится уже `5`. По пути к нему лист `[5]`
оказывается бедным, у соседа `[7]` тоже нет запаса — и они **сливаются** с ключом родителя
(жёлтая обводка), и только потом `5` вычёркивается из слитого листа:

> 💡 Если после удаления **корень** остался без ключей (все ушли в слияние), его единственный
> ребёнок становится новым корнем — так дерево уменьшается на уровень. Это единственный способ,
> которым B-дерево теряет высоту, — симметрично тому, как при вставке оно её набирает через split
> корня.

## 🧠 Почему это корректно

### Почему разделение сохраняет порядок и баланс

Полный узел из `2t−1` ключей делится по медиане: левые `t−1` остаются, правые `t−1` уходят в новый
узел, медиана поднимается в родителя ровно между ссылками на эти две половины. Порядок ключей
сохраняется (медиана больше левых и меньше правых), а высота поддерева не меняется. Дерево
становится выше **только** когда делится корень — и тогда все листья опускаются на один уровень
**одновременно**, поэтому они всегда на одной глубине.

### Почему делим полные узлы заранее (top-down)

Если делить узлы «на обратном пути» (как в AVL-повороте), переполнение могло бы каскадом дойти до
корня. B-дерево вместо этого делит **полный узел до спуска в него**: тогда, дойдя до листа, мы
гарантированно можем вставить ключ без переполнения, и каскад невозможен — одна нисходящая
проходка. Это и делает вставку O(log n) без возвратов.

### Почему высокое ветвление = мало чтений с диска

Высота B-дерева — `O(log_t n)`: основание логарифма — степень ветвления `t`. При большом `t` (узел
= блок диска на сотни ключей) высота крошечная: миллионы ключей укладываются в 3–4 уровня. Каждый
уровень — одно чтение блока, поэтому поиск стоит единицы обращений к диску — ради этого B-деревья и
придуманы.

## ⚙️ Цена на практике

### B-дерево против AVL/red-black

В памяти бинарные сбалансированные деревья (AVL, red-black) обычно лучше: проще и без накладных
расходов на широкие узлы. B-дерево выигрывает **на диске/SSD**, где доминирует стоимость чтения
блока: широкий узел = один блок, низкая высота = мало чтений. Правило: данные в памяти →
[AVL](avl-tree-structure.md)/red-black; данные на диске → B-дерево.

### B+‑дерево для диапазонов

На практике СУБД используют **B+‑дерево**: все значения хранятся в листьях, а листья связаны в
список. Это даёт быстрые **диапазонные сканы** (прошёл по связанным листьям) и ещё более широкие
внутренние узлы (в них только ключи-разделители). Внутренние узлы B+‑дерева — чистый индекс.

### Степень t выбирают под размер блока

`t` подбирают так, чтобы узел занимал ровно один блок диска/страницу (4–16 КБ): больше ключей в
блоке — ниже дерево — меньше чтений. Это инженерная настройка под железо, а не абстрактная
константа.

## ⚠️ Типичные ошибки

1. **Делить узлы на обратном пути** вместо top-down — рискуешь каскадом разделений до корня.
2. **Сбить инвариант «дети = ключи + 1»** при разделении — дерево перестаёт быть корректным.
3. **Забыть, что дерево растёт только вверх** — пытаться «удлинять» отдельную ветку ломает баланс листьев.
4. **Поднять не медиану** при разделении — нарушает порядок и/или баланс размеров половин.
5. **Путать B-дерево и B+‑дерево** — в B+ значения только в листьях, внутренние узлы — лишь ключи-разделители.

## 🧩 Где это нужно

Честно: B-дерево — это **не задача с LeetCode**, а структура из мира хранилищ. На
собеседовании оно всплывает не в кодинге, а в **system design и вопросах про базы
данных** — и здесь важно уметь объяснить *почему именно оно*:

- **«Как устроен индекс в SQL-базе / почему B-tree, а не хеш или BST?»** — ключевой ответ:
  узел = страница диска (один узел держит сотни ключей), высокое ветвление ⇒ малая высота
  ⇒ мало обращений к диску; диапазонные запросы и сортировка идут по листьям подряд.
- **B⁺-дерево vs B-дерево** — где хранятся значения (только в листьях у B⁺) и почему это
  удобнее для range-scan; на этом стоят PostgreSQL/MySQL-индексы и файловые системы.
- **Почему не AVL/красно-чёрное для диска** — у них ветвление 2, высота ~log₂N против
  ~log_tN, то есть в десятки раз больше дорогих обращений к диску.

Для кодинг-секции же ближайшие практические аналоги — это
[BST](bst-structure.md)/[AVL](avl-tree-structure.md) (поиск по упорядоченным данным в
памяти); саму механику split/insert собери в тренажёре выше.

## ⚔️ Антипод B-дерева: LSM-дерево

B-дерево — король **чтений**: 2–4 обращения к диску до любого ключа. Но у этой короны есть цена,
которая вылезает на write-heavy нагрузке — метрики, события, логи, очереди на диске. Каждая
вставка в B-дерево — это **случайная запись**: найди нужный лист где-то на диске, перепиши его
страницу (а иногда и расщепи с обновлением родителя). Миллион вставок в секунду — миллион прыжков
головки/страничных перезаписей по всему файлу. Диски (даже SSD) ненавидят случайную запись.

**LSM-дерево (log-structured merge tree) разворачивает размен на 180°: превращает случайную
запись в последовательную.** Механика из трёх ходов:

1. **Пишем только в память**: вставки идут в **memtable** — отсортированную структуру в RAM
   (обычно [skip-list](probabilistic-structures.md#4-skip-list--дерево-поиска-из-связных-списков) —
   те же O(log n) без поворотов).
2. **Полный memtable сбрасывается на диск целиком** — одной **последовательной** записью — как
   **SSTable**: отсортированный **неизменяемый** файл. Никаких правок на месте, только новые файлы.
3. **Чтение** идёт сверху вниз: memtable → свежие SSTable → старые. Чтобы не читать каждый файл с
   диска, перед каждым SSTable стоит [Bloom-фильтр](probabilistic-structures.md): его «точно нет»
   пропускает файл без единого обращения к диску. А чтобы файлов не становилось сотни, фоновая
   **компакция** сливает их — это в чистом виде [k-way merge](k-way-merge.md), при котором
   перезаписанные ключи схлопываются (остаётся значение из более нового файла).

```go
func (db *LSM) Put(key string, val int) {
    db.memtable.Insert(key, val) // запись всегда в ПАМЯТЬ
    if db.memtable.Len() >= db.cap {
        db.flush() // memtable полон
    }
}
func (db *LSM) flush() {
    sst := db.memtable.Sorted() // неизменяемый отсортированный файл
    db.sstables = append(db.sstables, sst)
    db.memtable = NewMemtable()
}
// фоново: compact() сливает SSTable k-way merge, схлопывая дубликаты
```

Листай «›»: шесть `put` заполняют memtable, два flush рождают два SSTable, а компакция сливает их —
ключ `b` записан дважды, и остаётся его **новое** значение:

### Размен честно, в одной таблице

| | B-дерево | LSM-дерево |
|---|---|---|
| Запись | случайная, правка страниц на месте | **последовательная**, только в память + flush |
| Чтение | **2–4 обращения к диску** | memtable + несколько SSTable (спасают Bloom и компакция) |
| Фоновая работа | почти нет | компакция жрёт диск и CPU (**write amplification**: ключ переписывается при каждом слиянии) |
| Брать когда | чтений больше, чем записей; нужны диапазоны здесь-и-сейчас | **пишем лавинообразно**: метрики, события, time-series, очереди |

> 🔧 **Где это в бою.** LSM — стандарт write-heavy движков: **RocksDB/LevelDB** (внутри — memtable
> на skip-list + levelled compaction), **Cassandra/ScyllaDB** (SSTable — их родной термин),
> **ClickHouse** (семейство движков MergeTree — та же идея «пиши куски, сливай фоном»),
> из Go-мира — [`dgraph-io/badger`](https://github.com/dgraph-io/badger). А B-дерево остаётся
> сердцем PostgreSQL/MySQL/SQLite и bbolt/etcd — двух лагерей ровно по линии этого размена.

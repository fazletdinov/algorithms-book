# 🔍 Ревью чужого кода: чинить, а не писать с нуля

> 🧭 **Зачем эта глава.** Каждый пакет тренажёра до сих пор давал один и тот же вид задачи:
> заготовка с `panic("TODO")`, ты пишешь реализацию по спецификации, тесты подтверждают. Это
> ровно то, чем реальная инженерная работа НЕ является большую часть времени. Гораздо чаще перед
> тобой лежит код, который уже кто-то написал, — компилируется, вроде бы работает, проходит
> ревью беглым взглядом — а изъян прячется там, где спецификация не поможет: в порядке
> синхронизации, в асимптотике, в проглоченной ошибке. Здесь — три таких случая. Ни один не
> выдуман для главы: `SumSquaresConcurrent` — ровно тот overflow-в-партиционировании и гонка,
> которые реально всплывают в fan-out коде; `HasDuplicate` проходит любое код-ревью на глаз,
> потому что даёт правильный ответ; `ParseAndSum` — самый частый анти-паттерн в Go-коде вообще.

## Как устроено это упражнение (и чем отличается от всех остальных)

`exercises/codereview/codereview.go` — не заготовка с TODO. Это ТРИ полностью реализованные
функции, каждая компилируется и на большинстве входов отвечает правильно. Задача — не
дописать недостающее, а **найти изъян тестом (или `-race`), понять его причину, читая код, и
исправить прямо в этом файле**. Сверяться с `exercises/codereview/codereview_solution.go`
(эталон под `-tags solution`) — только после собственной попытки, иначе теряется весь смысл:
в реальном ревью никто заранее не покажет тебе diff с исправлением.

```bash
cd exercises
go test ./codereview/                 # эти три реализации — изъян ловится тестом
go test -race ./codereview/           # ОБЯЗАТЕЛЬНО отдельно — гонка не всегда видна без него
go test -tags solution ./codereview/  # эталон — для сверки ПОСЛЕ собственной попытки
```

## Случай 1: `SumSquaresConcurrent` — два независимых изъяна сразу

```go
func SumSquaresConcurrent(nums []int, workers int) int64 {
	chunk := len(nums) / workers
	var total int64
	var wg sync.WaitGroup
	for w := 0; w < workers; w++ {
		start, end := w*chunk, w*chunk+chunk
		wg.Add(1)
		go func(lo, hi int) {
			defer wg.Done()
			for _, n := range nums[lo:hi] {
				total += int64(n) * int64(n)
			}
		}(start, end)
	}
	wg.Wait()
	return total
}
```

Запусти `go test ./codereview/ -run TestSumSquaresConcurrent -v` — упадёт с числами меньше
ожидаемых, притом **стабильно, на каждом запуске**. Это не гонка (та ещё впереди) — это
целочисленное деление: `chunk := len(nums) / workers` усекается вниз, если `len(nums)` не
делится на `workers` нацело. При `len(nums)=101, workers=4` получаем `chunk=25`, четыре
горутины обрабатывают `4*25=100` элементов — последний, `nums[100]`, не достаётся никому.
Не совпадение и не редкий край: воспроизводится на ЛЮБОМ входе, который не делится ровно.

Дальше — `go test -race ./codereview/ -run TestSumSquaresConcurrentRace`. Детектор укажет
ровно на строку `total += int64(n) * int64(n)`: несколько горутин пишут в одну переменную без
синхронизации — классическая гонка данных, та же категория проблемы, что `store.mu` в
[капстоуне мини-Redis](miniredis.md#этап-2-пройден-setgetdel).

Оба изъяна независимы: почини только партиционирование — `-race` всё равно будет ругаться;
почини только гонку мьютексом — числа всё равно будут неверными на входах, что не делятся
нацело. Нужно исправить оба.

> 💡 Идиоматичный фикс гонки — не всегда мьютекс. Если у каждой горутины может быть СВОЯ
> локальная переменная, а результат отправляется через канал (`results <- partial`), то делить
> вообще нечего — гонка исчезает не потому, что доступ защищён, а потому, что разделяемой
> памяти для записи больше нет. Мьютекс — правильный инструмент, когда состояние
> ДЕЙСТВИТЕЛЬНО должно быть общим (как `store.mu` в `Store`, который живёт дольше одного
> вызова функции); здесь оно нужно только внутри одного вызова, и канал проще.

## Случай 2: `HasDuplicate` — корректно, но незаметно квадратично

```go
func HasDuplicate(nums []int) bool {
	for i := range len(nums) {
		for j := i + 1; j < len(nums); j++ {
			if nums[i] == nums[j] {
				return true
			}
		}
	}
	return false
}
```

Все табличные тесты на маленьких входах зелёные — эта функция **отвечает правильно всегда**.
Изъян не в ответе, а в цене: двойной цикл — O(n²). На собеседовании такое обычно не поймают
(маленький вход), а в проде поймает нагрузка на реальных данных. Тест, который это ловит, —
`TestHasDuplicateScales`: не сравнивает ответ, а проверяет дедлайн по времени на входе без
дубликатов (200 000 элементов — эталон укладывается в ~7мс, эта реализация — ~4.8с). Тот же
приём, что уже применялся к сортировке (`sorting_bench_test.go`) — время эмпирически доказывает
асимптотику там, где табличный тест молчит.

Фикс — тот же компромисс время/память, что в [хеш-таблице](hash-table-structure.md): `map`
вместо вложенного цикла, O(n) по времени ценой O(n) по памяти.

## Случай 3: `ParseAndSum` — ошибка не паникует, она тихо исчезает

```go
func ParseAndSum(strs []string) (int, error) {
	sum := 0
	for _, s := range strs {
		n, err := strconv.Atoi(s)
		if err != nil {
			continue // ← вот он
		}
		sum += n
	}
	return sum, nil
}
```

Это не паника и не гонка — это самый частый анти-паттерн Go-кода: `if err != nil` есть, но
единственное, что он делает, — молча идёт дальше. `ParseAndSum([]string{"1", "abc", "3"})`
вернёт `4, nil` вместо ошибки — вызывающий код никогда не узнает, что вход был испорчен.
`err != nil` без содержательной обработки — не защита, а маскировка проблемы; тест
`TestParseAndSum` требует, чтобы первая же нераспознанная строка немедленно вернула ошибку
вызывающему коду, а не растворилась в `continue`.

## 🧩 Задачи

- Прогони `go test ./codereview/` — прочитай, на каком именно числе/сообщении падает каждый из
  трёх тестов, и только потом смотри на код: попробуй сформулировать причину до правки.
- `go test -race ./codereview/ -run Race` — найди строку, на которую указывает детектор, и
  объясни, почему её не поймал предыдущий пункт (без `-race` вывод часто просто «случайно
  правильный»).
- После собственного фикса сравни с `codereview_solution.go` — какие решения совпали, какие
  нет, и почему альтернативный вариант тоже может быть корректным (например, мьютекс вместо
  канала для случая 1 — тоже правильный фикс гонки, просто другой инструмент).

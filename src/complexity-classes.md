> получай ответ. Но однажды тебе прилетит боевая задача, где это ломается. «Разложи 500 микросервисов
> по серверам так, чтобы уместить в минимум машин». «Составь расписание, чтобы никакие два конфликтующих

> стену и что делать у неё.

## 🎬 Визуализация: во что упирается перебор

> 💡 **Интерактивная демонстрация.** Ниже — генерация **всех подмножеств** множества backtracking'ом:
> «выбрать → рекурсия → откат». Ровно так решается NP-полная **Subset Sum** («есть ли подмножество с
> суммой `target`?») в лоб — перебором всех вариантов. Листай «›» и смотри, как стек вызовов ныряет и возвращается, а строка «Найдено» растёт: на `n`
> элементов — `2ⁿ` подмножеств, и на каждое приходится свой вызов `bt`. На 30 элементах это миллиард, на 60 — уже больше атомов, доступных за
> разумное время. Вот эта экспонента и есть «стена». (Виджет работает в собранной книге.)

На трёх элементах — 8 подмножеств, мелочь. Но число вариантов **удваивается с каждым новым элементом**:

| `n` | вариантов (`2ⁿ`) | при 10⁹ операций/сек |
|-----|------------------|----------------------|
| 20  | ~10⁶             | мгновенно            |
| 40  | ~10¹²            | ~18 минут            |
| 60  | ~10¹⁸            | ~36 лет              |
| 80  | ~10²⁴            | ~38 миллионов лет    |
| 100 | ~10³⁰            | ~40 триллионов лет — в ~3000 раз дольше возраста Вселенной |

`n` вырос всего впятеро (20 → 100) — и «мгновенно» превратилось в «никогда». Именно поэтому на NP-трудной
задаче нельзя просто «дописать перебор побыстрее»: константа не спасает от экспоненты.

## 🔑 P, NP и почему «проверить» легче, чем «найти»

Сердце всей темы — асимметрия между **проверкой** решения и его **поиском**. Возьмём **Subset Sum**:
дан набор чисел и цель `target`; нужно узнать, есть ли подмножество с суммой ровно `target`.

- **Проверить** предъявленный ответ — тривиально. Дали тебе подмножество `{3, 8}` и `target = 11`?
  Складываешь числа за один проход, сравниваешь с целью — `O(n)`. Это и значит «задача в **NP**»:
  **готовый сертификат проверяется за полином.**
- **Найти** подмножество — совсем другое дело. Каких-то `{3, 8}` среди `2ⁿ` вариантов надо ещё
  отыскать, а быстрого способа никто не знает.

```go
// ПРОВЕРКА решения — легко, O(n). Это и есть «принадлежность к NP».
func verifySubsetSum(subset []int, target int) bool {
    sum := 0
    for _, x := range subset { // один проход
        sum += x
    }
    return sum == target
}

// ПОИСК решения — в лоб перебор всех 2ⁿ подмножеств, экспонента.
func hasSubsetSum(nums []int, target int) bool {
    var rec func(i, sum int) bool
    rec = func(i, sum int) bool {
        if sum == target {
            return true
        }
        if i == len(nums) || sum > target {
            return false
        }
        return rec(i+1, sum+nums[i]) || // взять nums[i]
            rec(i+1, sum) //            не взять
    }
    return rec(0, 0)
}
```

> **NP — это не «недетерминированный полином страшных слов», а «проверяемо за полином».** Название
> историческое (Nondeterministic Polynomial), но рабочее определение проще: *если бы кто-то угадал
> ответ, ты бы за полином убедился, что он верный.* Найти ответ при этом может быть сколь угодно трудно.

### NP-трудные, NP-полные и сведение

Есть задачи «не легче любой задачи из NP» — они не обязаны сами лежать в NP. Задача **NP-трудная**, если
умей мы быстро решать её — умели бы быстро решать **все** задачи в NP. Если она вдобавок сама лежит в
NP (её решение проверяемо за полином) — она **NP-полная**.

Держится это на идее **сведения** (reduction): «если бы у меня была быстрая функция для задачи B, я бы
за полином решил задачу A, переупаковав вход». Тогда A **не труднее** B.

> **Интуиция сведения.** Ты умеешь искать конфликты в расписании как раскраску графа. Приходит новая
> задача — «рассадить студентов по аудиториям без конфликтов». Ты замечаешь: это **та же** раскраска,
> просто в других словах. Значит, новая задача не труднее раскраски — и если раскраска NP-трудна, то...
> обычно и новая тоже. Так однажды доказав трудность одной задачи (SAT — теорема Кука—Левина, 1971),
> математики **свели** к ней тысячи других и разом доказали трудность всех.

Практический вывод для тебя: **если ты свёл свою рабочую задачу к известной NP-полной (рюкзак,
коммивояжёр, раскраска, покрытие множества, SAT) — точного быстрого алгоритма не ищи. Его нет.**

## 🧰 Боевые NP-трудные задачи, которые реально встречает инженер

Это не абстракции из учебника — они прячутся в обычных бэкенд-задачах под бытовыми названиями:

| Классическая задача | Как выглядит на работе | Что берут вместо точного оптимума |
|---|---|---|
| **Bin Packing** (упаковка) | Разложить поды/VM по серверам, файлы по дискам, задачи по воркерам | Жадный First-Fit-Decreasing (≤ 11/9 от оптимума) |
| **Коммивояжёр (TSP)** | Маршрут курьера/дрона через N точек | Ближайший сосед + 2-opt; OR-Tools |
| **Раскраска графа** | Расписание без конфликтов, распределение регистров/частот | Жадная раскраска по убыванию степени |
| **Set Cover** (покрытие) | Минимум серверов/CDN-точек, чтобы покрыть всех клиентов | Жадный (лучшее из возможных приближений — `ln n`) |
| **Knapsack** (рюкзак) | Уместить задания в бюджет/память по ценности | ДП по сумме (псевдополином — если числа малы) |
| **SAT / расписание с ограничениями** | Проверка конфигураций, планировщики, верификация | Готовые SAT/ILP-солверы, CP-SAT |

Обрати внимание на последний столбец — он и есть тема следующего раздела.

## 🛠️ Что делать у стены: пять ходов инженера

Самое важное в главе. Задача NP-трудна — но «трудна» **не значит «невозможна»**. Точный оптимум за
полином недостижим, поэтому меняем требование. Вот арсенал по порядку, как его перебирают на практике:

**1. Приближение с гарантией.** Алгоритм, который быстро выдаёт решение и **доказуемо** не хуже
оптимума в `C` раз. Для bin packing First-Fit-Decreasing укладывает в ≤ 11/9·OPT + константа. Для
vertex cover есть простое 2-приближение. Ты платишь известной, ограниченной потерей качества за
полиномиальное время.

```go
// First-Fit-Decreasing: разложить веса по «корзинам» вместимости cap.
// NP-трудный bin packing, но это приближение ≤ 11/9·OPT — и работает мгновенно.
func firstFitDecreasing(weights []int, cap int) int {
    sort.Sort(sort.Reverse(sort.IntSlice(weights))) // крупные — первыми
    var bins []int                                   // остаток места в каждой корзине
    for _, w := range weights {
        placed := false
        for i := range bins {
            if bins[i] >= w { // влезает в существующую корзину
                bins[i] -= w
                placed = true
                break
            }
        }
        if !placed { // не влезло — заводим новую
            bins = append(bins, cap-w)
        }
    }
    return len(bins) // сколько серверов/корзин понадобилось
}
```

**2. Эвристика без гарантии.** Жадность, локальный поиск, имитация отжига, генетические алгоритмы. Нет
теоретической оценки, но на практике даёт хорошие ответы. TSP: старт «ближайшим соседом», потом
улучшаем перестановками рёбер (2-opt), пока становится лучше. Для маршрутов курьеров этого хватает.

**3. Точно, но экспоненциально — при малом `n`.** Если входов реально мало (N ≤ 20–40), экспонента
терпима. Умный перебор бьёт наивный: **branch and bound** отсекает заведомо плохие ветки, **ДП по
подмножествам** (Held–Karp для TSP) даёт `O(2ⁿ·n²)` вместо `O(n!)`. «Экспоненциально» на `n = 15` — это
доли секунды.

**4. Псевдополином: маленькие числа спасают.** Knapsack и Subset Sum NP-трудны, но ДП решает их за
`O(n·target)`. Это **не** полином (зависит от **значения** `target`, а не от длины его записи), но если
суммы невелики — работает отлично. Всегда спрашивай: «а насколько большие тут числа?»

**5. Готовый солвер.** SAT-солверы, ILP (integer linear programming), Google OR-Tools, CP-SAT — за
десятилетия инженеры вложили в них тонну эвристик. Часто правильный ход — **не писать свой алгоритм, а
сформулировать задачу для солвера** и отдать ему. Промышленные планировщики так и устроены.

> **Дисциплина у стены.** (1) Распознал, что задача NP-трудна → (2) уточнил: точный оптимум действительно
> нужен, или сойдёт «хорошо»? → (3) насколько велик `n` и велики ли числа? → (4) выбрал: приближение /
> эвристика / точный при малом `n` / псевдополином / солвер. Кодер бьётся за несуществующий идеальный
> алгоритм; инженер меняет постановку.

## 🧠 Почему это важно понимать

### NP-полнота — это знание, которое экономит недели

Доказательство «задача NP-полна» — не академическая формальность, а **практический сигнал стоп**. Оно
говорит: перестань искать быстрый точный алгоритм, его нет (пока никто не доказал `P = NP`, а на это
никто не ставит). Умение свести свою задачу к известной трудной — это умение **не потратить неделю** на
стену. Обратное тоже ценно: если ты нашёл полиномиальный алгоритм для «похожей на трудную» задачи —
скорее всего, ты неверно понял условие, и стоит перепроверить.

### NP-трудно ≠ неразрешимо

Не путай две разные «невозможности»:

- **NP-трудно** — решение *существует* и проверяемо, просто **найти его долго**. При малом входе,
  приближённо или солвером — вполне берётся. Это про **время**.
- **Неразрешимо** (undecidable) — алгоритма нет **в принципе, никакого, никогда**. Классика — проблема
  остановки (halting problem): нельзя написать программу, которая для *любой* программы скажет,
  зациклится та или нет. Это про **существование алгоритма вообще**.

NP-трудная задача — это «дорого», неразрешимая — это «невозможно». Курьерский маршрут дорог; проблема
остановки невозможна.

## ⚙️ Цена на практике

### «NP-трудно» — приговор задаче, а не твоему дню

Встретив NP-трудную задачу в проде, ты почти никогда не решаешь её точно — и это нормально. Планировщик
Kubernetes раскладывает поды по нодам жадной эвристикой (это bin packing — NP-трудно). Компилятор
распределяет переменные по регистрам жадной раскраской графа (NP-трудно). Никто не ждёт оптимума —
ждут «хорошо и быстро». Оптимум на реальных объёмах просто не досчитается.

### Сначала проверь, что она вообще трудная

Прежде чем сдаваться в приближения, убедись, что задача действительно NP-трудна, а не выглядит так.
Кратчайший путь **кажется** перебором путей, но решается Дейкстрой за полином. Максимальный поток,
паросочетание, MST — всё это полиномиально, хоть и «пахнет» перебором. Поспешно навесить эвристику на
полиномиальную задачу — потерять точность даром.

### Размер входа решает выбор оружия

`n = 15` городов — считай точно (Held–Karp, миллисекунды). `n = 40` — приближение и 2-opt. `n = 10000` —
только быстрые эвристики. Числа малы (`target ≤ 10⁶`) — псевдополиномиальное ДП точное и быстрое. Один и
тот же NP-трудный тип задачи требует **разного** подхода в зависимости от масштаба — оцени его первым.

## ⚠️ Типичные заблуждения

1. **«NP значит экспоненциально».** Нет: NP — про **проверяемость** за полином. Все задачи из P тоже
   лежат в NP. Экспонента — это (предположительно) про NP-**полные**, а не про NP вообще.
2. **«NP-полное = нерешаемо».** Нет: решаемо, просто дорого. Приближения, малый `n`, солверы — рабочие
   пути. Нерешаемость (halting) — совсем другой зверь.
3. **«Не смог придумать быстрый алгоритм — надо ещё подумать».** Иногда — да. Но иногда быстрого
   алгоритма **нет**, и «ещё подумать» — потеря недели. Проверь, не NP-трудна ли задача.
4. **«Псевдополином — это полином».** Нет: `O(n·target)` зависит от **значения** `target`, а не от длины
   его битовой записи. Большие числа — и ДП взрывается.
5. **Навесить эвристику, не проверив, что задача трудна.** Половина «трудных на вид» задач полиномиальна
   (поток, паросочетание, кратчайший путь). Сначала поищи точный алгоритм.

## 📝 Разбор задачи: «разложи сервисы по серверам»

> **Задача.** Дано `n` сервисов с потреблением памяти `weights` и серверы вместимостью `cap` каждый.
> Разложить сервисы по **минимальному** числу серверов. Пример: `weights = [4, 8, 1, 4, 2, 1]`,
> `cap = 10` → можно уложить в **2** сервера (`8+2` и `4+4+1+1`).

**Шаг 1. Распознать задачу.** «Разложить предметы по контейнерам фиксированной вместимости, минимизируя
число контейнеров» — это **bin packing** дословно. Первый рефлекс инженера: *а это не NP-трудно?* Да,
bin packing NP-труден. Значит, **точного быстрого алгоритма искать не будем** — ищем хорошее приближение.

**Шаг 2. Почему перебор не годится.** Точно — это перебрать все способы разбить `n` сервисов на группы
(число Белла, растёт быстрее `2ⁿ`). На 50 сервисах — не досчитается никогда. [Ровно та стена из
визуализации выше.](#-визуализация-во-что-упирается-перебор)

**Шаг 3. Приближение — First-Fit-Decreasing.** Сортируем сервисы по убыванию и кладём каждый в первую
корзину, где он помещается; не влез — заводим новую. Просто, `O(n²)` (или `O(n log n)` с деревом), и
**доказуемо** ≤ 11/9·OPT + константа.

```go
func minServers(weights []int, cap int) int {
    sort.Sort(sort.Reverse(sort.IntSlice(weights)))
    var free []int // остаток места в каждом сервере
    for _, w := range weights {
        placed := false
        for i := range free {
            if free[i] >= w {
                free[i] -= w
                placed = true
                break
            }
        }
        if !placed {
            free = append(free, cap-w)
        }
    }
    return len(free)
}
```

**Шаг 4. Трассировка** на `weights = [4, 8, 1, 4, 2, 1]`, `cap = 10`. После сортировки: `[8, 4, 4, 2, 1, 1]`.

| Кладём | Серверы (остаток места) | Куда лёг |
|--------|--------------------------|----------|
| 8      | `[2]`                    | новый #1 |
| 4      | `[2, 6]`                 | новый #2 |
| 4      | `[2, 2]`                 | в #2     |
| 2      | `[0, 2]`                 | в #1     |
| 1      | `[0, 1]`                 | в #2     |
| 1      | `[0, 0]`                 | в #2     |

Ответ — **2 сервера**, и это оптимум. FFD не гарантирует оптимум *всегда*, но гарантирует, что мы не
промахнёмся сильно, — и считается мгновенно на любом реальном числе сервисов. Кодер бы неделю писал
точный перебор; инженер за час сдал приближение, которое работает в проде.

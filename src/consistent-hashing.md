# 🔀 Консистентное хеширование: шардирование без перетасовки

> 🧭 **Зачем эта глава.** Пока кеш один, вопроса «куда класть ключ» нет. Как только Redis
> становится три, ключи приходится раскладывать по узлам: это и есть **шардирование**. Первое,
> что пишут все, — `node := hash(key) % N`. Работает, пока `N` не
> меняется. А он меняется: узел упал, узел добавили под нагрузку. И тогда остаток от деления
> перетасовывает **почти все** ключи — кеш мгновенно остывает, и весь поток запросов уходит в
> базу. Консистентное хеширование — это ответ на вопрос «как разложить ключи так, чтобы при
> смене состава узлов переезжало как можно меньше».
>
> Глава собрана из деталей, которые ты уже знаешь: [хеш-таблица](hash-table-structure.md)
> даёт хеш, [бинарный поиск](modified-binary-search.md) — поиск по кольцу. Все числа ниже сняты
> с тренажёра и детерминированы: команда из текста выдаст у тебя те же цифры до знака.

## 1. Почему `hash % N` ломается

Остаток от деления раскладывает ключи идеально ровно — и в этом нет проблемы. Проблема в том,
что происходит при `N → N+1`. Ключ остаётся на месте, только если `h % N == h % (N+1)`, а это
редкость: переезжает примерно `N/(N+1)` ключей. Ключ с хешем 7 жил на узле `7 % 3 = 1`, а после
добавления четвёртого уедет на `7 % 4 = 3`. Проверим на 100 000 ключей:

```bash
cd exercises
go test -tags solution -run ShardingExperiment -v ./consistenthash/
```

| Узлов: было → стало | в идеале переезжает | остаток от деления | кольцо (V = 100) | jump hash |
|---|---|---|---|---|
| 3 → 4 | 25.0% | **74.9%** | 28.4% | 24.9% |
| 10 → 11 | 9.1% | **90.9%** | 8.3% | 9.1% |
| 100 → 101 | 1.0% | **99.0%** | 1.0% | 0.9% |

«В идеале» — это `1/(N+1)`: новому узлу надо отдать свою долю, и ни одним ключом больше. На
десяти кешах остаток от деления при добавлении **одного** узла сбрасывает 91% кеша. Для
сервиса, у которого база держится только благодаря кешу, это не деградация, а авария — и
случается она ровно тогда, когда узел добавляют *потому, что* нагрузка выросла.

## 2. Кольцо: хешируем и ключи, и узлы

Идея в одну строку: **хешировать в одно пространство и ключи, и узлы**. Представь числа
`0 … 2³²−1` замкнутыми в окружность. Каждый узел — точка на ней (хеш его имени). Ключ
принадлежит **первому узлу по часовой стрелке** от своего хеша, а за последней точкой снова
идёт первая.

```go
// Точки узлов лежат в отсортированном срезе — это и есть кольцо.
i := sort.Search(len(points), func(i int) bool { return points[i].h >= HashKey(key) })
if i == len(points) {
	i = 0 // за последней точкой — снова первая: прямая замыкается в кольцо
}
owner := points[i].node
```

Поиск владельца — [бинарный поиск](modified-binary-search.md) по отсортированному срезу,
`O(log(N·V))`: «первый элемент, который `>=` цели» — ровно lower_bound из той главы.

## 🧠 Почему это корректно

Главное свойство, ради которого кольцо существует: **при добавлении узла ключи переезжают
только на него**. Доказательство короче формулировки. Владелец ключа — первая точка `≥ h`
среди всех точек кольца. Добавление узла только *вставляет* новые точки, старые остаются на
местах. Для ключа первая точка `≥ h` либо та же, что и была, либо одна из новых. Третьего
варианта нет — значит, ни один ключ не прыгает между старыми узлами.

Зеркально для удаления: убираем только точки удаляемого узла, и ключи переезжают **только
с него**. Оба свойства проверяются в тренажёре не на примерах, а буквально:
`TestRingAddMovesOnlyToNewNode` проходит 20 000 ключей и падает, если хоть один сменил
владельца на кого-то, кроме нового узла.

Сколько переедет, зависит от длины дуг: новый узел забирает столько ключей, сколько
хешей попадает на отрезанные им дуги. При случайном расположении точек в среднем это
`1/(N+1)` окружности. Слово «в среднем» здесь важное — о нём следующий раздел.

## 3. Виртуальные узлы — и почему хеш важнее, чем кажется

Одна точка на узел даёт дуги случайной длины. Один узел может получить вчетверо больше
соседа — просто потому, что его точке не повезло. А когда узел падает, всю его дугу забирает один
сосед по часовой стрелке. Лечится **виртуальными узлами**: каждый
узел ставит на кольцо не одну точку, а `V` (хеши `"cache-1#0"`, `"cache-1#1"`, …). Его доля —
сумма `V` случайных дуг, и её относительный разброс падает как `1/√V`; дуги упавшего узла
расходятся по многим соседям, а мощной машине можно дать больше точек, чем слабой.

Но только если хеш хорошо перемешивает. Имена виртуальных узлов почти одинаковые — они
отличаются последними символами. Вот разброс нагрузки на 10 узлов при 100 000 ключей
(стандартное отклонение доли узла от среднего):

| Виртуальных узлов `V` | голый FNV-1a | FNV-1a + перемешивающий финал |
|---|---|---|
| 1 | 53.4% | 98.4% |
| 10 | 58.4% | 30.2% |
| **100** | **51.5%** | **9.8%** |
| 1000 | 12.3% | 1.8% |

Правая колонка идёт ровно по теории: 1 → 10 → 100 даёт 98% → 30% → 10%, то есть множитель
`1/√10` на каждый шаг. А левая **не улучшается вообще**: сто виртуальных узлов балансируют не
лучше одного. Почему — видно, если посмотреть, куда встают точки одного узла (доля
окружности, та же команда печатает и это):

| Точка | голый FNV-1a | с перемешиванием |
|---|---|---|
| `cache-1#0` | 0.6112 | 0.8631 |
| `cache-1#1` | 0.6151 | 0.6274 |
| `cache-1#2` | 0.6190 | 0.9205 |
| `cache-1#3` | 0.6229 | 0.9245 |

Слева — ровный частокол с шагом 0.0039, то есть ровно `1/256` окружности. Имена отличаются
последним символом на единицу, а последний шаг FNV-1a — умножение на простое `16777619`,
которое чуть больше `2²⁴`. Разница в единицу на входе превращается в сдвиг хеша почти ровно
на `2²⁴` — предсказуемый, одинаковый для всех соседей. Десять «виртуальных узлов» встают
рядом на трёх процентах кольца и работают как один. Финал из MurmurHash3 (`fmix32`: два
умножения и три сдвига с XOR) ломает эту предсказуемость — любое изменение входа
разлетается по всем 32 битам, и точки рассыпаются по кольцу. Тогда виртуальные узлы
начинают делать свою работу.

Урок шире консистентного хеширования: **если алгоритм опирается на «случайность» хеша, хеш
надо проверить на своих данных**. Кольцо было написано верно — плохой была хеш-функция, а
на глаз этого не видно.

## 4. Jump hash: консистентно и без памяти

Кольцо хранит `N·V` точек и тратит на поиск логарифм. В 2014 году Джон Лампинг и Эрик Вич
(Google) опубликовали **jump consistent hash** — функцию на пять строк, которой память не
нужна вовсе:

```go
func JumpHash(key uint64, buckets int) int {
	var b, j int64 = -1, 0
	for j < int64(buckets) {
		b = j
		key = key*2862933555777941757 + 1 // генератор, засеянный ключом
		j = int64(float64(b+1) * (float64(int64(1)<<31) / float64((key>>33)+1)))
	}
	return int(b)
}
```

Идея: ключ «прыгает» по номерам корзин вперёд, и длина прыжков растёт. Прыжок из корзины `b`
приземляется так, что вероятность пролететь любую следующую корзину подобрана под свойство
консистентности: при переходе от `n` к `n+1` корзинам ключ либо остаётся на месте, либо
переезжает **ровно в новую корзину `n`** — и происходит это с вероятностью `1/(n+1)`.
Последний номер, не вышедший за `buckets`, и есть ответ. Прыжков в среднем `O(log n)`.

В таблице из раздела 1 jump hash попадает в идеал точнее кольца (9.1% против 8.3% при идеале
9.1%), а баланс у него почти идеальный: на 10 корзинах самая нагруженная получает лишь на 1.7%
больше средней. Кольцу для такого понадобилась бы тысяча виртуальных узлов на каждый узел.

**Но есть цена, и она решающая.** Jump hash возвращает *номер* корзины от 0 до `n−1`. Добавить
можно только корзину `n`, убрать — только последнюю. Если упал узел номер 5 из 10, jump hash не
умеет «убрать пятый»: перенумерация сдвинет ключи всех узлов после него. Кольцо же удаляет любой
узел: убрать `cache-5` из десяти — переезжает 11.8% ключей при идеале 10%, и только с `cache-5`.

Поэтому jump hash хорош там, где корзины — это номера, а не живые машины: шарды хранилища с
репликацией внутри шарда, партиции, которые никогда не пропадают по одной. Кольцо — там, где узлы
приходят и уходят сами по себе.

## 5. Что выбрать

| | Сколько переезжает | Убрать любой узел | Память | Выбор узла (замер) |
|---|---|---|---|---|
| `hash % N` | почти всё | нет | 0 | 5.7 нс |
| Кольцо, `V = 100` | ≈ `1/(N+1)` | да | `N·V` точек | 71 нс (10 узлов), 100 нс (100) |
| Jump hash | ровно `1/(N+1)` | только последний | 0 | 28 нс (10 корзин), 50 нс (1000) |

Время снято бенчмарком тренажёра, в него входит и хеширование ключа:

```bash
go test -p 1 -tags solution -run='^$' -bench=. -count=5 ./consistenthash/
```

Посмотри на последнюю колонку внимательно — и забудь о ней. Самый медленный вариант тратит 100
наносекунд. Поход в Redis по сети стоит сотни **микро**секунд — в тысячу раз больше. Выбирать
способ шардирования по скорости вычисления — ошибка масштаба: решают первые три колонки.

## 🌍 Где это в реальных системах

- **Redis Cluster** — не кольцо, а его ближайший родственник: **16384 хеш-слота**. Слот ключа —
  `CRC16(key) mod 16384`, а какой слот на каком узле — явная таблица. Добавление узла — это
  перенос части слотов (решардинг), и переезжают только ключи перенесённых слотов. Таблица из
  16384 записей даёт то же, что кольцо, но с полным контролем: каждый узел знает всю карту, а
  перенос идёт слотами, а не вероятностями. Отсюда же **hash tags**: у ключей `{user:42}:cart` и
  `{user:42}:profile` хешируется только часть в фигурных скобках, они гарантированно попадают в
  один слот, и с ними работают многоключевые команды вроде `MGET`.
- **Шардирование на клиенте** (twemproxy, клиенты memcached) — кольцо в варианте **ketama** с
  сотнями точек на сервер. В nginx то же самое включается одной строкой: `hash $key consistent;`.
- **Cassandra и Amazon Dynamo** — кольцо токенов с виртуальными узлами; в Cassandra их число
  задаёт параметр `num_tokens`.
- **Балансировщики** — Envoy умеет `RING_HASH` и `MAGLEV`: запросы одного клиента или ключа
  попадают на один бэкенд, и добавление бэкенда не перетасовывает всех.
- **Go** — в `groupcache` (github.com/golang/groupcache; кеш от автора memcached, работает в
  Google) есть пакет `consistenthash`: то же кольцо с репликами и бинарным поиском, которое ты
  пишешь в тренажёре.

За рамками главы остались ещё два способа, которые стоит знать по имени: **rendezvous hashing**
(HRW — ключ отдаётся узлу с максимальным `hash(ключ, узел)`, без кольца вовсе) и **Maglev**
(Google, 2016 — таблица поиска с почти идеальным балансом, для балансировщиков).

> 🌍 **Где это в настоящем коде**
>
> - [`Map.Get`](https://github.com/golang/groupcache/blob/2c02b8208cf8c02a3e358cb1d9b60950647543fc/consistenthash/consistenthash.go#L65) (groupcache, коммит `2c02b82`: релизных тегов у проекта нет) — кольцо на Go: отсортированные хеши точек, `sort.Search` ищет первую точку не меньше хеша ключа, за концом — переход на начало.
> - [`keyHashSlot`](https://github.com/redis/redis/blob/7.4.1/src/cluster.h#L43) (Redis 7.4.1) — слот ключа: `crc16` по младшим 14 битам (16384 слота), а если в ключе есть `{...}` — хешируется только часть в скобках.

## ⚠️ Типичные ошибки

1. **`hash(key) % N` для кешей, которые масштабируются.** Работает до первого изменения `N` —
   а меняется оно в самый неудобный момент.
2. **Одна точка на узел.** Дуги случайной длины: при `V = 1` разброс нагрузки в замере — под
   100%. Виртуальных узлов нужны десятки или сотни.
3. **Хеш без перемешивания.** См. раздел 3: реплики не помогают, если точки ложатся кучкой.
   Проверяй распределение на своих данных, а не верь названию хеш-функции.
4. **Раскладка, зависящая от порядка добавления узлов.** Если при равных хешах побеждает «тот,
   кого добавили раньше», два сервиса, собравшие кольцо из одного конфига по-разному, отправят
   ключ в разные узлы. Отсюда правило ничьей в контракте тренажёра.
5. **Забытый переход через ноль.** Ключ с хешем больше последней точки принадлежит **первой**
   точке. Без этого `Get` падает с выходом за границы или отдаёт не тот узел.
6. **Jump hash для узлов, которые выпадают по одному.** Он умеет только «добавить в конец» и
   «убрать последний».

## 💻 Тренажёр — пакет `consistenthash`

```bash
cd exercises
go test ./consistenthash/                 # твои решения
go test -tags solution ./consistenthash/  # эталон
```

Реализуй кольцо (`NewRing`, `Add`, `Remove`, `Get`), `MovedFraction` и `JumpHash`. Хеш-функции и
наивный `ModShard` даны готовыми в `hash.go`. Тесты проверяют не отдельные ответы, а свойства: ключи
при добавлении узла переезжают только на него, при удалении — только с него; раскладка не зависит от
порядка `Add`; правило ничьей проверено на настоящей коллизии хешей, найденной перебором. Плюс
рандомизированная сверка кольца с моделью, которая ищет владельца перебором по определению.

Когда `JumpHash` позеленеет, нажми «🎞 Визуализировать»: для десяти корзин видно, что ключ делает
всего пару прыжков — `0 → 1 → 12`, и двенадцать уже за границей. Это и есть логарифм.

## 🎬 Визуализация

> 💡 **Интерактивная демонстрация.** Зелёная плашка снизу — текущий индекс `i`, голубая сверху
> («цель») — куда уходит элемент при обмене; залитые зелёным — числа уже на своих местах.
> Значения массива меняются прямо на месте. Под холстом — строка шага и переменные, ниже — ползунок шагов (или ←/→ на клавиатуре) и код с подсветкой строки. Можно подставить свой массив и нажать «⟲ Запустить».

## ⚡ Шаблон для собеседования

```go
i := 0
for i < len(nums) {
    correct := nums[i] - 1            // место для nums[i]
    if nums[i] != nums[correct] {
        nums[i], nums[correct] = nums[correct], nums[i] // swap, i НЕ растёт
    } else {
        i++
    }
}
```

1. `correct := nums[i] - 1` — правильная позиция текущего числа;
2. не на месте → обмен, **`i` не двигаем**;
3. на месте → `i++`;
4. после — сканируем: первый `nums[i] != i+1` это пропущенное число.

## 📖 Разбор

<details class="algo-details">
<summary>Теория, поиск пропущенного числа и сложность</summary>

**Cyclic Sort** — сортировка массива на месте, когда числа лежат в известном
диапазоне (обычно от 1 до N). Алгоритм использует то, что число `x` должно стоять на
позиции `x - 1` (для диапазона 1..N) или на позиции `x` (для 0..N-1).

Каждый элемент за один цикл перестановок «отправляется» на своё место. Поскольку
после размещения элемент больше не двигается, всего происходит не более N перестановок —
это даёт **O(n)** времени и **O(1)** памяти.

```go
func cyclicSort(nums []int) {
    i, n := 0, len(nums)
    for i < n {
        v := nums[i]
        // Guard: значение вне [1, n] нельзя поставить на «свою» позицию — пропускаем
        if v < 1 || v > n {
            i++
            continue
        }
        correctPos := v - 1 // число x должно стоять на индексе x-1
        if nums[i] != nums[correctPos] {
            nums[i], nums[correctPos] = nums[correctPos], nums[i]
            // i не увеличиваем — на позиции i теперь новый элемент
        } else {
            i++
        }
    }
}
```

Сравнение `nums[i] != nums[correctPos]` (а не `i != correctPos`) защищает от
бесконечного цикла на дубликатах: если на целевой позиции уже такое же значение,
обмен бессмыслен — двигаемся дальше.

После сортировки легко найти первое число, стоящее не на своём месте, — это и есть
отсутствующее (или лишнее).

```go
func findMissingNumber(nums []int) int {
    cyclicSort(nums)
    for i := 0; i < len(nums); i++ {
        if nums[i] != i+1 {
            return i + 1
        }
    }
    return len(nums) + 1 // все числа 1..n на месте
}
```

#### Сложность

| Случай       | Время | Память |
|--------------|-------|--------|
| Любой        | O(n)  | O(1)   |

Cyclic Sort всегда линеен: каждый элемент перемещается максимум один раз на своё
место, перестановка стоит O(1).

Два вопроса: **когда** циклическая сортировка вообще применима и **почему** вложенный
обмен без `i++` не делает её квадратичной.

### Предусловие — числа в известном диапазоне

Алгоритм опирается на биекцию «значение `v` ↦ позиция `v−1`». Она существует **тогда и
только тогда**, когда значения лежат в `[1, n]` (или `[0, n−1]`) — тогда каждому
значению соответствует ровно одна валидная ячейка. Вне диапазона отображение не
определено, поэтому такие значения пропускаются (`guard`). Нет гарантии диапазона —
циклическая сортировка неприменима, нужна обычная сортировка или хеш.

### Почему `O(n)`, хотя `i` не всегда растёт — амортизация

Внутренний обмен без `i++` пугает, как и вложенный `while` в [скользящем окне](sliding-window.md),
но аргумент тот же. Ключевое наблюдение:

> Каждый обмен ставит **хотя бы одно** значение на его финальную позицию, и значение,
> однажды попавшее на своё место, оттуда **больше не двигается**.

Значит, общее число обменов за весь прогон — не более `n`. Плюс `i` продвигается не
более `n` раз. Итого ≤ `2n` операций → **`O(n)`**, хотя двойного прохода нигде нет.

### Завершаемость и роль `nums[i] != nums[correctPos]`

Каждая итерация либо двигает `i` вперёд (прогресс), либо делает обмен, увеличивающий
число правильно стоящих элементов (а оно ограничено `n`). Сравнение **по значению**
(`nums[i] != nums[correctPos]`, а не по индексу) обязательно: при дубликате целевая
ячейка уже содержит такое же значение, обмен ничего не менял бы — без этой проверки на
дубликатах был бы вечный цикл.

## ⚙️ Цена на практике

### `O(1)` памяти вместо «массива посещённых»

Очевидное решение задач «найти пропущенное/дубликат» — булев массив `seen` (`O(n)`
памяти) или сортировка (`O(n log n)`). Циклическая сортировка даёт `O(n)` времени **и
`O(1)` памяти**, переиспользуя сам вход как индекс. Это её главное преимущество.

### Распознать триггер

Связка «массив из `n` чисел в диапазоне `1..n`» + «найти пропущенное / дубликат / все
дубликаты» — почти всегда сигнал к циклической сортировке. Именно **ограничение
диапазона** включает приём.

### Где не подойдёт

- Массив **нельзя мутировать** → приём не применим (он работает на месте).
- XOR-трюк или формула суммы решают *единичное* пропущенное число, но ломаются на
  нескольких пропусках/дубликатах; циклическая сортировка обобщается на **все** сразу.

## ⚠️ Типичные ошибки

1. **Неверная формула позиции** — для диапазона 1..N это `x-1`, для 0..N-1 это `x`.
2. **Бесконечный цикл на дубликатах** — сравнивай *значения*
   (`nums[i] != nums[correctPos]`), а не индексы.
3. **Выход за границы** — добавляй guard для значений вне `[1, n]`, иначе
   `nums[v-1]` упадёт.
4. **Увеличение `i` после обмена** — после swap на позиции `i` стоит новый элемент,
   его тоже нужно проверить; `i++` только когда элемент уже на месте.
5. **Не обработан пустой массив** — цикл `i < n` это покрывает, но проверь, что
   постобработка (поиск пропуска) не падает на пустом входе.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он расточителен по
памяти, и только потом циклическая сортировка. Берём самую жёсткую версию —
**произвольный** массив без гарантии диапазона.

> **Задача.** Дан **неотсортированный** массив целых `nums` (любые значения). Найти
> наименьшее **положительное** число, которого в нём нет. Память — `O(1)`.
> Пример: `nums = [3,4,-1,1]` → ответ `2` (есть `1`, `3`, `4`; первого пропуска — `2`).

**Шаг 1. Наивно: hash-set — O(n) времени, O(n) памяти.**

```go
func firstMissingNaive(nums []int) int {
    seen := make(map[int]bool, len(nums))
    for _, v := range nums {
        seen[v] = true
    }
    for i := 1; ; i++ {
        if !seen[i] {
            return i
        }
    }
}
```

Это **работает и проходит тесты**, но требует `O(n)` дополнительной памяти на множество
(сортировка дала бы `O(n log n)` времени — тоже мимо). А задача явно просит `O(1)`
памяти. Раз ответ лежит в диапазоне `1..n+1`, само множество избыточно: вход уже умеет
быть «таблицей присутствия» — каждое число `v` обязано стоять на индексе `v−1`.

**Шаг 2. Ключевое наблюдение.** Среди `n` чисел первое пропущенное положительное всегда
лежит в `1..n+1`: даже если все числа подряд (`1..n`), ответ — `n+1`, и значения вне
`[1, n]` на ответ не влияют. Значит, можно разложить числа по местам **внутри самого
массива** циклической сортировкой (см.
[«🧠 Почему это корректно»](#почему-on-хотя-i-не-всегда-растёт--амортизация)): число `v`
ставим на индекс `v−1`, а всё, что вне `[1, n]`, просто пропускаем. После раскладки
первый индекс `i`, где `nums[i] != i+1`, и даёт ответ `i+1`.

**Шаг 3. Оптимум: циклическая сортировка на месте — O(n) время, O(1) память.**

```go
func firstMissingPositive(nums []int) int {
    n := len(nums)
    i := 0
    for i < n {
        v := nums[i]
        correct := v - 1
        if v >= 1 && v <= n && nums[i] != nums[correct] {
            nums[i], nums[correct] = nums[correct], nums[i] // на место, i НЕ растёт
        } else {
            i++ // на месте или вне диапазона
        }
    }
    for i := 0; i < n; i++ {
        if nums[i] != i+1 {
            return i + 1 // первый «не на своём месте» индекс
        }
    }
    return n + 1 // массив — это ровно 1..n
}
```

Прогони раскладку на `nums = [3,4,-1,1]`: каждое число едет на индекс `v−1`, значения
вне `[1,n]` пропускаются (зелёные ячейки — уже на месте), затем скан находит первое «не своё»:

**Шаг 4. Трассировка** на `nums = [3,4,-1,1]` (`n = 4`):

| `i` | `nums[i]` | `correct` | действие                              | массив после   |
|-----|-----------|-----------|---------------------------------------|----------------|
| 0   | 3         | 2         | swap с idx 2, `i` стоит               | `[-1,4,3,1]`   |
| 0   | −1        | —         | вне `[1,4]` → `i++`                    | `[-1,4,3,1]`   |
| 1   | 4         | 3         | swap с idx 3, `i` стоит               | `[-1,1,3,4]`   |
| 1   | 1         | 0         | swap с idx 0, `i` стоит               | `[1,-1,3,4]`   |
| 1   | −1        | —         | вне `[1,4]` → `i++`                    | `[1,-1,3,4]`   |
| 2   | 3         | 2         | уже на месте → `i++`                  | `[1,-1,3,4]`   |
| 3   | 4         | 3         | уже на месте → `i++`                  | `[1,-1,3,4]`   |

Скан: `nums[0]=1` ✓, `nums[1]=-1 ≠ 2` → ответ **`2`**. Обрати внимание: обменов было
всего 3 (≤ `n`), а `i` продвинулся 4 раза — тот самый
[амортизированный O(n)](#почему-on-хотя-i-не-всегда-растёт--амортизация) при `O(1)`
памяти, в отличие от hash-set.

## 🏗️ Инженерный кейс

> **Ситуация.** Пришёл массив из `n` идентификаторов, которые **должны** быть перестановкой чисел `1..n`
> (например, порядковые номера страниц/шардов), но один номер **пропущен**, а другой **задублирован**.
> Найти их за O(1) дополнительной памяти — хеш-множество на миллионах номеров держать не хочется.

Секрет — что значения совпадают с диапазоном **индексов**: число можно положить на «своё» место.

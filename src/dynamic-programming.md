## 🧭 Откуда берётся ДП: выведем его сами

Четыре слова из карточки — «состояние, переход, база, порядок» — не заклинание, которое надо
зазубрить. Это то, что **остаётся от обычной рекурсии, если запретить ей переспрашивать**.
Проследим на живой задаче — и дальше вся глава будет читаться сама.

> **Задача (House Robber).** Вдоль улицы — дома с деньгами `nums`. Нельзя брать два соседних.
> Какой максимум можно унести?

Начнём, как рассуждает человек, а не учебник: **какой у меня выбор?** Смотрю на дома `0..i`
и решаю про последний из них, дом `i`. Вариантов ровно два:

- **пропустить** его → остаётся та же задача для домов `0..i-1`;
- **взять** `nums[i]` → сосед `i-1` под запретом, остаётся та же задача для домов `0..i-2`.

```go
// f(i) — максимум добычи с домов 0..i
func f(i int) int {
    if i < 0 {
        return 0                        // домов нет
    }
    return max(f(i-1), nums[i]+f(i-2))  // пропустить или взять
}
```

Это честная рекурсия ([база + шаг](recursion.md)), и она уже **содержит всё ДП** — кроме одной
беды: она экспоненциальна. `f(3)` вызывается и из `f(5)`, и из `f(4)` — дерево вызовов ветвится,
как у наивного Фибоначчи. Но заметь главное: **разных вопросов всего `n`** — «максимум с домов
`0..i`» для каждого `i`, — а задаём мы их `2ⁿ` раз.

Дадим повторяющимся вопросам таблицу — и четыре слова возникнут сами, из уже написанного кода:

| Слово | Что это в нашей рекурсии |
|---|---|
| **Состояние** `dp[i]` | сам ВОПРОС: «максимум добычи с домов `0..i`» |
| **Переход** | её строка выбора: `dp[i] = max(dp[i-1], nums[i] + dp[i-2])` |
| **База** | её условие выхода: до начала массива добыча 0 |
| **Порядок** | отвечать от меньших вопросов к большим — слева направо, чтобы `dp[i-1]` был готов раньше `dp[i]` |

**ДП — это рекурсия, у которой отобрали право переспрашивать.** Рецепт всегда один: напиши
наивную рекурсию через «какой у меня выбор?» → убедись, что её вопросы повторяются → заведи
таблицу по вопросу. Полная трассировка этой задачи, от перебора до `O(1)` памяти, — в
«📝 Разборе задачи» ниже; а пока тот же приём — на новой задаче.

## 🎬 Визуализация

> 💡 **Интерактивная демонстрация (пошаговый дебаг Coin Change).** Для каждой суммы `a` перебирается
> каждая монета `c`. Зелёная рамка и плашка `a` — сумма, которую считаем; голубая рамка — остаток
> `dp[a−c]`. Дуга над ними — сам переход «положить монету `c` последней»: сплошная, если вариант
> лучше прежних, пунктирная — если нет. Под массивом — монеты (текущая жёлтая) и все варианты для
> суммы `a` списком: сразу видно, из чего выбирается минимум. Под холстом — строка шага и переменные (`a`, `c`, `dp[a−c]`, `best`, `dp[a]`), ниже — код с подсветкой строки. Можно подставить свои монеты и `amount`.

## ⚡ Шаблон для собеседования

Тот же вывод для Coin Change, в одну строку рассуждения: вопрос (состояние) — «минимум монет на
сумму `a`»; выбор — **какая монета последняя**: если последней была монета `c`, то до неё была
собрана сумма `a−c`, и вопрос стал меньше. Отсюда переход `dp[a] = min(dp[a−c] + 1)` по всем `c`:

```go
// Coin Change: dp[a] = минимум монет на сумму a
dp := make([]int, amount+1)
for a := 1; a <= amount; a++ {
    dp[a] = INF
    for _, c := range coins {
        if c <= a && dp[a-c]+1 < dp[a] {
            dp[a] = dp[a-c] + 1 // переход через меньшую сумму
        }
    }
}
// dp[amount] — ответ (или INF, если набрать нельзя)
```

1. состояние `dp[a]` — ответ для суммы `a`;
2. база `dp[0] = 0`;
3. переход: пробуем каждую монету `c`, `dp[a] = min(dp[a], dp[a-c]+1)`;
4. идём от меньших сумм к большим.

## 📖 Разбор: два подхода, примеры (1D / 2D / рюкзак) и сложность

ДП разбивает задачу на **перекрывающиеся подзадачи** и сохраняет их результаты. Нужны
два свойства: перекрывающиеся подзадачи и оптимальная подструктура.

#### Мемоизация (сверху вниз)

```go
func fibMemo(n int) int {
    memo := make(map[int]int)
    var f func(int) int
    f = func(k int) int {
        if k < 2 {
            return k
        }
        if v, ok := memo[k]; ok {
            return v
        }
        memo[k] = f(k-1) + f(k-2)
        return memo[k]
    }
    return f(n)
}
```

#### Табуляция (снизу вверх)

```go
func fibTab(n int) int {
    if n < 2 {
        return n
    }
    prev, cur := 0, 1
    for i := 2; i <= n; i++ {
        prev, cur = cur, prev+cur // O(1) памяти
    }
    return cur
}
```

#### Coin Change (минимум монет)

```go
func coinChange(coins []int, amount int) int {
    const INF = 1 << 30
    dp := make([]int, amount+1)
    for i := 1; i <= amount; i++ {
        dp[i] = INF
        for _, c := range coins {
            if c <= i && dp[i-c]+1 < dp[i] {
                dp[i] = dp[i-c] + 1
            }
        }
    }
    if dp[amount] >= INF {
        return -1
    }
    return dp[amount]
}
```

#### 2D ДП: Longest Common Subsequence

Двумерность не меняет рецепта — только вопрос теперь про **две** строки. Состояние `dp[i][j]` —
«LCS первых `i` символов `a` и первых `j` символов `b`». Выбор подсказывают **последние символы**:

- **совпали** (`a[i−1] == b[j−1]`) — брать этот символ в ответ никогда не хуже: приклеиваем его к
  LCS обеих строк **без** последних символов. Отсюда диагональ: `dp[i−1][j−1] + 1`;
- **не совпали** — вместе им в общем ответе не бывать, значит один из двух лишний. Пробуем выкинуть
  последний символ `a` (это `dp[i−1][j]`) или последний символ `b` (это `dp[i][j−1]`) — и берём максимум.

Вот и вся рекуррента; таблица ниже просто отвечает на эти вопросы в правильном порядке.

> 💡 **Интерактивная демонстрация (LCS, 2D-таблица).** Таблица `dp[i][j]` заполняется по
> строкам слева направо. Синяя ячейка — текущая `dp[i][j]`; фиолетовая — **источник** перехода:
> при совпадении символов берётся **диагональ** `dp[i-1][j-1]+1`, иначе **максимум** из верхней и
> левой (бледная — отвергнутый кандидат). Под холстом — строка шага и переменные, ниже — код с подсветкой строки. Можно
> подставить свои строки.

<div class="algo-viz" data-viz="dp-lcs" data-a="AGCAT" data-b="GAC"></div>

```go
func lcs(a, b string) int {
    m, n := len(a), len(b)
    dp := make([][]int, m+1)
    for i := range dp {
        dp[i] = make([]int, n+1)
    }
    for i := 1; i <= m; i++ {
        for j := 1; j <= n; j++ {
            if a[i-1] == b[j-1] {
                dp[i][j] = dp[i-1][j-1] + 1
            } else {
                dp[i][j] = max(dp[i-1][j], dp[i][j-1])
            }
        }
    }
    return dp[m][n]
}
```

#### 0/1 Рюкзак

Состояние `dp[i][w]` — максимальная ценность из первых `i` предметов при вместимости `w`.
Переход — снова вопрос «какой выбор у последнего?», здесь — у предмета `i`:

- **не берём** его → вся ценность набирается первыми `i−1` предметами при той же вместимости:
  `dp[i−1][w]`;
- **берём** (если влезает: `weight[i] ≤ w`) → его ценность плюс лучший ответ для первых `i−1`
  предметов при вместимости, **уменьшенной на его вес**: `dp[i−1][w−weight[i]] + value[i]`.

Оба кандидата — уже посчитанные меньшие состояния; берём максимум:
`dp[i][w] = max(dp[i-1][w], dp[i-1][w-weight[i]] + value[i])`.
Часто сворачивается до 1D-массива по `w` (идём по `w` в обратную сторону — см. «Типичные ошибки»).

> 💡 **Интерактивная демонстрация (0/1 рюкзак).** Строки — предметы (`вес·ценность`), столбцы —
> вместимость `0..W`. Синяя ячейка — текущая `dp[i][c]`; фиолетовые — два источника выбора: «не
> брать» (`dp[i-1][c]`, прямо сверху) и «взять» (`dp[i-1][c-вес]+ценность`); бледная — отвергнутый
> вариант. Если предмет не влезает — берётся только верх. Можно подставить свои предметы и `W`.

## 🧠 Почему это корректно

<div class="algo-explain" data-key="dynamic-programming">
  <div class="algo-explain__item">
    <div class="algo-explain__q">Назови два предусловия ДП и скажи, что ломается без каждого.</div>
    <div class="algo-explain__ref"><b>Оптимальная подструктура</b>: оптимум строится из оптимумов подзадач — без неё ДП даёт <b>неверный</b> ответ (контрпример: самый длинный простой путь в графе). <b>Перекрывающиеся подзадачи</b>: одни и те же подзадачи встречаются многократно — без перекрытия ДП ничего не ускоряет, это просто «разделяй и властвуй».</div>
  </div>
  <div class="algo-explain__item">
    <div class="algo-explain__q">Как понять, что состояние выбрано неправильно? Сформулируй критерий полноты состояния.</div>
    <div class="algo-explain__ref">Состояние обязано быть <b>полным резюме прошлого</b>: содержать всё, что влияет на будущее. Если два разных будущих неразличимы по состоянию — состояние неполно, и ответ поедет. Самый частый баг — забытое измерение (например, «осталось ли право на ещё одну сделку» в задачах про акции).</div>
  </div>
</div>

ДП легко написать неверно: неполное состояние или неправильный порядок заполнения
дают тихо неправильный ответ. Корректность держится на двух предусловиях и одном
правиле порядка.

### Два предусловия — и что ломается без каждого

- **Оптимальная подструктура:** оптимум задачи строится из оптимумов подзадач. Без
  неё ДП даёт **неверный** ответ. Классический контрпример — «самый длинный *простой*
  путь в графе»: оптимальный путь не складывается из оптимальных подпутей, и ДП тут
  неприменимо.
- **Перекрывающиеся подзадачи:** одни и те же подзадачи встречаются многократно. Без
  перекрытия ДП ничего не ускоряет — это просто «разделяй и властвуй».

### Состояние должно быть полным резюме

Рекуррента корректна **тогда и только тогда**, когда состояние содержит всё, что влияет
на будущее. Самый частый баг — забытое измерение состояния (например, «осталось ли
право на ещё одну сделку» в задачах про акции). Если два разных будущих неразличимы по
состоянию — состояние неполно, и ответ поедет.

### Переход: наивная рекурсия → мемоизация → табуляция

Все три — **одна и та же рекуррента**, отсюда и корректность. Возьмём Фибоначчи:

```go
// 1. Наивно: O(2ⁿ) — fib(k) пересчитывается заново снова и снова.
func fib(n int) int {
    if n < 2 {
        return n
    }
    return fib(n-1) + fib(n-2)
}
```

**Мемоизация** (см. `fibMemo` выше) — *та же* функция плюс кэш. Корректность очевидна:
вычисление идентично наивному, кэш лишь убирает повторный счёт → `O(n)`. **Табуляция**
(`fibTab`) переворачивает порядок: считаем подзадачи снизу вверх и храним только нужное.

| Подход | Направление | Хранилище | Память | Когда удобнее |
|---|---|---|---|---|
| Наивная рекурсия | сверху вниз | — | O(глубины) | никогда (экспонента) — лишь как отправная точка мышления |
| Мемоизация | сверху вниз | кэш (`map`/массив) | O(состояний) | разреженные/сложные состояния; легко получить прямо из рекурсии |
| Табуляция | снизу вверх | таблица | O(состояний), часто **O(1)** со скользящим массивом | плотные состояния, нужен контроль порядка и памяти |

Путь почти всегда один: написал наивную рекурренту → навесил кэш (мемоизация) → при желании
развернул в цикл снизу вверх (табуляция) и ужал память.

> **Правило порядка для табуляции.** Подзадачи образуют ориентированный граф
> зависимостей (DAG). Заполнять надо в его **топологическом порядке** — каждое
> `dp[i]` после всех `dp[j]`, от которых оно зависит. В Coin Change это `i` по
> возрастанию (`dp[i]` зависит от `dp[i-c]`), в рюкзаке `w` идёт **в обратную**
> сторону именно ради правильного порядка. Перепутать порядок — взять предмет дважды
> или прочитать ещё не посчитанную ячейку.

## ⚙️ Цена на практике

### Сложность читается прямо из задачи

**Время ≈ (число состояний) × (стоимость перехода).** Это не формула для запоминания, а
способ оценить незнакомую задачу вслух на собеседовании: опиши состояние → посчитай,
сколько их → посчитай цену одного перехода → перемножь. Для LCS: `O(m·n)` состояний ×
`O(1)` переход = `O(m·n)`.

### Память: скользящий массив

Если `dp[i]` зависит только от `dp[i-1]` (Фибоначчи, лестница, рюкзак), весь массив не
нужен — хватит одной-двух строк. `O(n)` → `O(1)`, а 2D `O(m·n)` → `O(min(m, n))`.
Это любимый follow-up интервьюера: «а можешь по памяти?».

### Мемоизация против табуляции — не только стиль

- **Мемоизация** (рекурсия + кэш): считает только **достижимые** состояния — выигрыш,
  когда их меньше, чем всех возможных. Минусы: накладные расходы на вызовы и **глубина
  стека** (риск переполнения на большой `n`).
- **Табуляция** (цикл + массив): быстрее (нет вызовов и хеширования), без риска стека,
  но считает **все** состояния и требует продумать порядок заполнения.

### Сторож «бесконечность» — `1<<30`, не `MaxInt`

Для «недостижимо» нужен INF, к которому **прибавляют** (`dp[i-c] + 1`). Если взять
`math.MaxInt`, то `+1` переполнится и станет отрицательным — сравнение сломается.
Бери `const INF = 1 << 30`: заведомо больше любого реального ответа, но с запасом до
переполнения.

> 🔧 **Где это в Go.** Обратный пример — тоже урок. Движки регулярных выражений многих языков
> перебирают варианты с возвратом, и на «злом» шаблоне такой перебор уходит в экспоненту: одна
> строка во входных данных может подвесить сервис (это называют ReDoS). Пакет
> [`regexp`](https://pkg.go.dev/regexp) в Go так **сознательно не делает**: он идёт по строке один
> раз и держит в уме все варианты сразу (подход библиотеки RE2) — гарантированно `O(len(input))`.
> Это то же «не пересчитывай заново», что у ДП, только возведённое в правило дизайна. А
> классическое ДП в тулчейне — дифф: `git diff` ищет кратчайший способ превратить один файл в
> другой (алгоритм Майерса), и это родня LCS из этой главы.

## 🧵 Восстановление ответа: не «сколько», а «какие»

Все примеры выше возвращают **значение** оптимума: минимум монет, длину LCS, сумму
грабежа. На практике почти всегда нужен сам **ответ-свидетель**: какие именно монеты,
какая подпоследовательность (это буквально `diff` — LCS двух файлов), какой набор
задач взял планировщик. Хорошая новость: таблица уже всё знает.

Приём один и тот же: **пройди таблицу обратным ходом** и в каждом состоянии спроси
«какой переход дал это значение?» — тот выбор и был сделан. Для Coin Change сверху:

```go
// после заполнения dp: dp[i] — минимум монет на сумму i
func restoreCoins(coins, dp []int, amount int) []int {
    // INF — как в coinChange. Сумма недостижима: без этой проверки цикл ниже не закончится.
    if dp[amount] >= INF {
        return nil
    }
    res := []int{}
    for i := amount; i > 0; {
        for _, c := range coins {
            if c <= i && dp[i-c]+1 == dp[i] { // этот переход дал оптимум
                res = append(res, c)
                i -= c
                break
            }
        }
    }
    return res // например, amount=11, coins=[1,2,5] → [1, 5, 5]
}
```

Обратный ход бесплатен по памяти (таблица уже есть) и стоит `O(ответ · |переходов|)`
времени. Альтернатива — хранить **указатель выбора** рядом с каждым состоянием
(`choice[i] = c`): код восстановления упрощается до цепочки переходов, цена — ещё
один массив на все состояния. Для LCS обратный ход читается прямо из рекурренты:
символы совпали — символ в ответ и шаг по диагонали, иначе — шаг в сторону большего
из `dp[i-1][j]` / `dp[i][j-1]`.

Одно «но»: восстановлению нужна **полная таблица**. Оптимизация памяти скользящим
массивом из раздела выше её уничтожает — это честный размен: значение за `O(n)`
памяти *или* ответ за `O(n·m)`. (Для LCS существует компромисс — алгоритм Хиршберга
восстанавливает ответ за `O(min(n,m))` памяти через разделяй-и-властвуй, — знай, что
он есть, но на собеседовании хватает полной таблицы.)

## ⚠️ Типичные ошибки

1. **Неправильная база** — забыли `dp[0]` или задали неверно; вся таблица «съезжает».
2. **Неверный порядок обхода** — состояние используется раньше, чем посчитано.
3. **Путаница индексов строк и таблицы** — для строк длины `m` таблица размера `m+1`, символ `a[i-1]` ↔ `dp[i]`.
4. **Мемоизация без кэша на самом деле** — забыли записать результат перед `return`.
5. **0/1-рюкзак: проход по `w` в прямом порядке** при свёрнутом массиве — предмет берётся несколько раз.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он экспоненциальный,
и только потом ДП со сворачиванием памяти до двух переменных.

> **Задача (House Robber).** Дан массив `nums` — деньги в домах подряд. Грабитель не
> может обчистить **два соседних** дома (сработает сигнализация). Найти максимальную
> сумму. Пример: `nums = [2,7,9,3,1]` → ответ `12` (дома `2 + 9 + 1`).

**Шаг 1. Наивно: рекурсия «брать / не брать» — O(2ⁿ).**

```go
func robNaive(nums []int) int {
    var f func(i int) int // f(i) — лучший грабёж домов 0..i
    f = func(i int) int {
        if i < 0 {
            return 0
        }
        skip := f(i - 1)         // пропускаем дом i
        take := nums[i] + f(i-2) // берём дом i, минуя соседа i-1
        return max(skip, take)
    }
    return f(len(nums) - 1)
}
```

Это **работает и проходит тесты**, но дерево вызовов ветвится надвое на каждом доме —
O(2ⁿ). (Педантично: ветки разной глубины, и точная оценка — Θ(φⁿ) ≈ 1.618ⁿ, как у
наивного Фибоначчи — та же рекуррента T(n) = T(n−1) + T(n−2). O(2ⁿ) — честная верхняя
граница, просто помни, что это O, а не Θ, — [глава Big-O](big-o.md) объясняет разницу.)
Беда в том, что `f(i-1)` снова зовёт `f(i-2)`, которую `f(i)` уже звала сама, и так на
каждом уровне — одни и те же подзадачи пересчитываются снова и снова.

**Шаг 2. Ключевое наблюдение.** Налицо оба предусловия ДП из раздела
[«Почему это корректно»](#два-предусловия--и-что-ломается-без-каждого): подзадачи
**перекрываются** (`f(i)` зависит лишь от индекса `i`, а одинаковые `i` встречаются по
многу раз), и есть **оптимальная подструктура** — лучший «грабёж» домов `0..i`
складывается из лучших решений префиксов `0..i-1` и `0..i-2`. Состояние полно: всё, что
влияет на ответ, — это на каком доме мы остановились. Таблица `dp[i]` — ровно `f(i)`,
только заполняем её не сверху вниз рекурсией, а слева направо циклом. Отсюда рекуррента
`dp[i] = max(dp[i-1], dp[i-2] + nums[i])`: для дома `i` либо **пропускаем** его (берём
лучшее до `i-1`), либо **берём** (`nums[i]` плюс лучшее до `i-2`, минуя соседа `i-1`).

**Шаг 3. Оптимум: ДП со свёрткой до двух переменных — O(n) время, O(1) память.**

```go
func rob(nums []int) int {
    prev2, prev1 := 0, 0 // dp[i-2] и dp[i-1]
    for _, x := range nums {
        cur := max(prev1, prev2+x) // пропустить дом или взять его
        prev2, prev1 = prev1, cur  // сдвигаем окно из двух значений
    }
    return prev1
}
```

`dp[i]` зависит только от двух предыдущих ячеек, поэтому весь массив держать не нужно —
это ровно тот [скользящий массив](#память-скользящий-массив), что и в Фибоначчи.

Прогоните свёртку на `nums = [2,7,9,3,1]`: для каждого дома `cur = max(пропустить prev1,
взять prev2+x)`, и всё ДП живёт в двух переменных `prev2`, `prev1`. Строка `dp[i]` под
домами — полная таблица для наглядности: обведены две ячейки, которые код ещё держит, а
левее всё погашено, потому что уже забыто. На финале зелёным — дома, из которых собран ответ:

**Шаг 4. Трассировка** на `nums = [2,7,9,3,1]` (логически `dp[i] = max(dp[i-1], dp[i-2]+nums[i])`):

| `i` | `nums[i]` | `dp[i-1]` (пропустить) | `dp[i-2]+nums[i]` (взять) | `dp[i]` |
|-----|-----------|-----------------------|---------------------------|---------|
| 0   | 2         | 0                     | 0 + 2 = 2                 | **2**   |
| 1   | 7         | 2                     | 0 + 7 = 7                 | **7**   |
| 2   | 9         | 7                     | 2 + 9 = 11                | **11**  |
| 3   | 3         | 11                    | 7 + 3 = 10                | **11**  |
| 4   | 1         | 11                    | 11 + 1 = 12               | **12**  |

Ответ — `12` (дома `2 + 9 + 1`), и совпадает с наивной рекурсией. Каждое `dp[i]` берёт
**больший** из двух столбцов; в свёрнутой версии вся таблица сжата до пары `prev2, prev1`.

## 🏗️ Инженерный кейс

> **Ситуация.** Тебе дают задачу оптимизации: «минимум монет на сумму», «максимум прибыли», «сколько
> способов». Соблазн — схватить жадность (она проще и быстрее). Но жадность **молча** даёт неверный ответ
> на многих задачах. Как понять, что здесь нужно ДП, а не жадный выбор?

Это решение — распознать природу задачи **до** того, как написан код. Разберём на классической ловушке:

**Вывод.** Цепочка выборов + повторяющиеся подзадачи → **ДП**. Жадность — только когда локальный оптимум
**доказуемо** глобален (и это надо проверять контрпримером, а не надеждой). Не уверен — начни с перебора,
заметь повторяющиеся подзадачи, навесь мемоизацию: перебор превратится в ДП.

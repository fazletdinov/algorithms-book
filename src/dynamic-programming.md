## 🎬 Визуализация

> 💡 **Интерактивная демонстрация (пошаговый дебаг Coin Change).** Для каждой суммы `a` перебирается
> каждая монета `c`; видно, как меняются `best` и ячейка `dp[a]`. Синяя ячейка — текущая сумма,
> фиолетовая — источник `dp[a−c]`. Справа — код с подсветкой строки и панель переменных (`a`, `c`,
> `dp[a−c]`, `best`, `dp[a]`). Можно подставить свои монеты и `amount`. (Виджет работает в собранной
> книге `mdbook serve`/`mdbook build`, а не при просмотре `.md` на GitHub.)

<div class="algo-viz" data-viz="dp-coins" data-coins="1,3,4" data-amount="6"></div>

Монеты `{1, 3, 4}`, сумма `6` — классика, где **жадность ошибается**: жадный взял бы
`4 + 1 + 1 = 3` монеты, а ДП находит оптимум `3 + 3 = 2`.

## ⚡ Шаблон для собеседования

```go
// Coin Change: dp[a] = минимум монет на сумму a
dp := make([]int, amount+1)
for a := 1; a <= amount; a++ {
    dp[a] = INF
    for _, c := range coins {
        if c <= a && dp[a-c]+1 < dp[a] {
            dp[a] = dp[a-c] + 1 // переход через меньшую сумму
        }
    }
}
// dp[amount] — ответ (или INF, если набрать нельзя)
```

1. состояние `dp[a]` — ответ для суммы `a`;
2. база `dp[0] = 0`;
3. переход: пробуем каждую монету `c`, `dp[a] = min(dp[a], dp[a-c]+1)`;
4. идём от меньших сумм к большим.

## 📖 Разбор

<details class="algo-details">
<summary>Два подхода, примеры (1D / 2D / рюкзак) и сложность</summary>

ДП разбивает задачу на **перекрывающиеся подзадачи** и сохраняет их результаты. Нужны
два свойства: перекрывающиеся подзадачи и оптимальная подструктура.

#### Мемоизация (сверху вниз)

```go
func fibMemo(n int) int {
    memo := make(map[int]int)
    var f func(int) int
    f = func(k int) int {
        if k < 2 {
            return k
        }
        if v, ok := memo[k]; ok {
            return v
        }
        memo[k] = f(k-1) + f(k-2)
        return memo[k]
    }
    return f(n)
}
```

#### Табуляция (снизу вверх)

```go
func fibTab(n int) int {
    if n < 2 {
        return n
    }
    prev, cur := 0, 1
    for i := 2; i <= n; i++ {
        prev, cur = cur, prev+cur // O(1) памяти
    }
    return cur
}
```

#### Coin Change (минимум монет)

```go
func coinChange(coins []int, amount int) int {
    const INF = 1 << 30
    dp := make([]int, amount+1)
    for i := 1; i <= amount; i++ {
        dp[i] = INF
        for _, c := range coins {
            if c <= i && dp[i-c]+1 < dp[i] {
                dp[i] = dp[i-c] + 1
            }
        }
    }
    if dp[amount] >= INF {
        return -1
    }
    return dp[amount]
}
```

#### 2D ДП: Longest Common Subsequence

> 💡 **Интерактивная демонстрация (LCS, 2D-таблица).** Таблица `dp[i][j]` заполняется по
> строкам слева направо. Синяя ячейка — текущая `dp[i][j]`; фиолетовая — **источник** перехода:
> при совпадении символов берётся **диагональ** `dp[i-1][j-1]+1`, иначе **максимум** из верхней и
> левой (бледная — отвергнутый кандидат). Справа — код с подсветкой строки и переменные. Можно
> подставить свои строки. (Виджет работает в собранной книге.)

<div class="algo-viz" data-viz="dp-lcs" data-a="AGCAT" data-b="GAC"></div>

```go
func lcs(a, b string) int {
    m, n := len(a), len(b)
    dp := make([][]int, m+1)
    for i := range dp {
        dp[i] = make([]int, n+1)
    }
    for i := 1; i <= m; i++ {
        for j := 1; j <= n; j++ {
            if a[i-1] == b[j-1] {
                dp[i][j] = dp[i-1][j-1] + 1
            } else {
                dp[i][j] = max(dp[i-1][j], dp[i][j-1])
            }
        }
    }
    return dp[m][n]
}
```

#### 0/1 Рюкзак

Состояние `dp[i][w]` — максимальная ценность из первых `i` предметов при вместимости `w`.
Выбор «взять / не взять»: `dp[i][w] = max(dp[i-1][w], dp[i-1][w-weight[i]] + value[i])`.
Часто сворачивается до 1D-массива по `w` (идём по `w` в обратную сторону).

> 💡 **Интерактивная демонстрация (0/1 рюкзак).** Строки — предметы (`вес·ценность`), столбцы —
> вместимость `0..W`. Синяя ячейка — текущая `dp[i][c]`; фиолетовые — два источника выбора: «не
> брать» (`dp[i-1][c]`, прямо сверху) и «взять» (`dp[i-1][c-вес]+ценность`); бледная — отвергнутый
> вариант. Если предмет не влезает — берётся только верх. Можно подставить свои предметы и `W`.
> (Виджет работает в собранной книге.)

#### Сложность

| Задача              | Состояний | Переход | Время       | Память (оптим.) |
|---------------------|-----------|---------|-------------|-----------------|
| Фибоначчи / лестница| O(n)      | O(1)    | O(n)        | O(1)            |

**Время ≈ (число состояний) × (стоимость перехода)**.

## 🧠 Почему это корректно

ДП легко написать неверно: неполное состояние или неправильный порядок заполнения
дают тихо неправильный ответ. Корректность держится на двух предусловиях и одном
правиле порядка.

### Два предусловия — и что ломается без каждого

- **Оптимальная подструктура:** оптимум задачи строится из оптимумов подзадач. Без
  неё ДП даёт **неверный** ответ. Классический контрпример — «самый длинный *простой*
  путь в графе»: оптимальный путь не складывается из оптимальных подпутей, и ДП тут
  неприменимо.
- **Перекрывающиеся подзадачи:** одни и те же подзадачи встречаются many раз. Без
  перекрытия ДП ничего не ускоряет — это просто «разделяй и властвуй».

### Состояние должно быть полным резюме

Рекуррента корректна **тогда и только тогда**, когда состояние содержит всё, что влияет
на будущее. Самый частый баг — забытое измерение состояния (например, «осталось ли
право на ещё одну сделку» в задачах про акции). Если два разных будущих неразличимы по
состоянию — состояние неполно, и ответ поедет.

### Переход: наивная рекурсия → мемоизация → табуляция

Все три — **одна и та же рекуррента**, отсюда и корректность. Возьмём Фибоначчи:

```go
// 1. Наивно: O(φⁿ) — fib(k) пересчитывается заново снова и снова.
func fib(n int) int {
    if n < 2 {
        return n
    }
    return fib(n-1) + fib(n-2)
}
```

**Мемоизация** (см. `fibMemo` выше) — *та же* функция плюс кэш. Корректность очевидна:
вычисление идентично наивному, кэш лишь убирает повторный счёт → `O(n)`. **Табуляция**
(`fibTab`) переворачивает порядок: считаем подзадачи снизу вверх и храним только нужное.

| Подход | Направление | Хранилище | Память | Когда удобнее |
|---|---|---|---|---|
| Наивная рекурсия | сверху вниз | — | O(глубины) | никогда (экспонента) — лишь как отправная точка мышления |
| Мемоизация | сверху вниз | кэш (`map`/массив) | O(состояний) | разреженные/сложные состояния; легко получить прямо из рекурсии |
| Табуляция | снизу вверх | таблица | O(состояний), часто **O(1)** со скользящим массивом | плотные состояния, нужен контроль порядка и памяти |

Путь почти всегда один: написал наивную рекурренту → навесил кэш (мемоизация) → при желании
развернул в цикл снизу вверх (табуляция) и ужал память.

> **Правило порядка для табуляции.** Подзадачи образуют ориентированный граф
> зависимостей (DAG). Заполнять надо в его **топологическом порядке** — каждое
> `dp[i]` после всех `dp[j]`, от которых оно зависит. В Coin Change это `i` по
> возрастанию (`dp[i]` зависит от `dp[i-c]`), в рюкзаке `w` идёт **в обратную**
> сторону именно ради правильного порядка. Перепутать порядок — взять предмет дважды
> или прочитать ещё не посчитанную ячейку.

## ⚙️ Цена на практике

### Сложность читается прямо из задачи

**Время ≈ (число состояний) × (стоимость перехода).** Это не формула для запоминания, а
способ оценить незнакомую задачу вслух на собеседовании: опиши состояние → посчитай,
сколько их → посчитай цену одного перехода → перемножь. Для LCS: `O(m·n)` состояний ×
`O(1)` переход = `O(m·n)`.

### Память: скользящий массив

Если `dp[i]` зависит только от `dp[i-1]` (Фибоначчи, лестница, рюкзак), весь массив не
нужен — хватит одной-двух строк. `O(n)` → `O(1)`, а 2D `O(m·n)` → `O(min(m, n))`.
Это любимый follow-up интервьюера: «а можешь по памяти?».

### Мемоизация против табуляции — не только стиль

- **Мемоизация** (рекурсия + кэш): считает только **достижимые** состояния — выигрыш,
  когда их меньше, чем всех возможных. Минусы: накладные расходы на вызовы и **глубина
  стека** (риск переполнения на большой `n`).
- **Табуляция** (цикл + массив): быстрее (нет вызовов и хеширования), без риска стека,
  но считает **все** состояния и требует продумать порядок заполнения.

### Сторож «бесконечность» — `1<<30`, не `MaxInt`

Для «недостижимо» нужен INF, к которому **прибавляют** (`dp[i-c] + 1`). Если взять
`math.MaxInt`, то `+1` переполнится и станет отрицательным — сравнение сломается.
Бери `const INF = 1 << 30`: заведомо больше любого реального ответа, но с запасом до
переполнения.

## ⚠️ Типичные ошибки

1. **Неправильная база** — забыли `dp[0]` или задали неверно; вся таблица «съезжает».
2. **Неверный порядок обхода** — состояние используется раньше, чем посчитано.
3. **Путаница индексов строк и таблицы** — для строк длины `m` таблица размера `m+1`, символ `a[i-1]` ↔ `dp[i]`.
4. **Мемоизация без кэша на самом деле** — забыли записать результат перед `return`.
5. **0/1-рюкзак: проход по `w` в прямом порядке** при свёрнутом массиве — предмет берётся несколько раз.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он экспоненциальный,
и только потом ДП со сворачиванием памяти до двух переменных.

> **Задача (House Robber).** Дан массив `nums` — деньги в домах подряд. Грабитель не
> может обчистить **два соседних** дома (сработает сигнализация). Найти максимальную
> сумму. Пример: `nums = [2,7,9,3,1]` → ответ `12` (дома `2 + 9 + 1`).

**Шаг 1. Наивно: рекурсия «брать / не брать» — O(2ⁿ).**

```go
func robNaive(nums []int) int {
    var f func(i int) int
    f = func(i int) int {
        if i >= len(nums) {
            return 0
        }
        take := nums[i] + f(i+2) // берём дом i, прыгаем через соседа
        skip := f(i + 1)         // пропускаем дом i
        return max(take, skip)
    }
    return f(0)
}
```

Это **работает и проходит тесты**, но дерево вызовов ветвится надвое на каждом доме —
O(2ⁿ). Беда в том, что `f(i+2)` и `f(i+1)` оба зовут `f(i+3)`, `f(i+4)`… — одни и те же
подзадачи пересчитываются снова и снова.

**Шаг 2. Ключевое наблюдение.** Налицо оба предусловия ДП из раздела
[«Почему это корректно»](#два-предусловия--и-что-ломается-без-каждого): подзадачи
**перекрываются** (`f(i)` зависит лишь от индекса `i`, а одинаковые `i` встречаются по
многу раз), и есть **оптимальная подструктура** — лучший «грабёж» домов `i..n`
складывается из лучших решений хвостов `i+1..n` и `i+2..n`. Состояние полно: всё, что
влияет на будущее, — это с какого дома мы стартуем. Отсюда рекуррента
`dp[i] = max(dp[i-1], dp[i-2] + nums[i])`: для дома `i` либо **пропускаем** его (берём
лучшее до `i-1`), либо **берём** (`nums[i]` плюс лучшее до `i-2`, минуя соседа `i-1`).

**Шаг 3. Оптимум: ДП со свёрткой до двух переменных — O(n) время, O(1) память.**

```go
func rob(nums []int) int {
    prev2, prev1 := 0, 0 // dp[i-2] и dp[i-1]
    for _, x := range nums {
        cur := max(prev1, prev2+x) // пропустить дом или взять его
        prev2, prev1 = prev1, cur  // сдвигаем окно из двух значений
    }
    return prev1
}
```

`dp[i]` зависит только от двух предыдущих ячеек, поэтому весь массив держать не нужно —
это ровно тот [скользящий массив](#память-скользящий-массив), что и в Фибоначчи.

Прогоните свёртку на `nums = [2,7,9,3,1]`: для каждого дома `cur = max(пропустить prev1,
взять prev2+x)`, и всё ДП живёт в двух переменных `prev2`, `prev1`:

<div class="algo-viz" data-viz="house-robber" data-array="2,7,9,3,1"></div>

**Шаг 4. Трассировка** на `nums = [2,7,9,3,1]` (логически `dp[i] = max(dp[i-1], dp[i-2]+nums[i])`):

| `i` | `nums[i]` | `dp[i-1]` (пропустить) | `dp[i-2]+nums[i]` (взять) | `dp[i]` |
|-----|-----------|-----------------------|---------------------------|---------|
| 0   | 2         | 0                     | 0 + 2 = 2                 | **2**   |
| 1   | 7         | 2                     | 0 + 7 = 7                 | **7**   |
| 2   | 9         | 7                     | 2 + 9 = 11                | **11**  |
| 3   | 3         | 11                    | 7 + 3 = 10                | **11**  |
| 4   | 1         | 11                    | 11 + 1 = 12               | **12**  |

Ответ — `12` (дома `2 + 9 + 1`), и совпадает с наивной рекурсией. Каждое `dp[i]` берёт
**больший** из двух столбцов; в свёрнутой версии вся таблица сжата до пары `prev2, prev1`.

> 🧵 **Конкурентность?** Почти нет — у ДП **цепочки зависимостей**: `dp[i]` опирается на уже
> посчитанные `dp[i-1]`, `dp[i-2]`, … Пока не готовы предшественники, клетку не вычислить, поэтому
> наивно параллелить нельзя. Теоретически независимы клетки одной **антидиагонали** (например, в
> `EditDistance`/`LCS`), но работы на клетку — копейки, и горутины тут проиграют. ДП почти всегда
> последовательно.

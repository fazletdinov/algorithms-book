## ⚡ Шаблон для собеседования

Канонический каркас «заяц и черепаха» — обнаружение цикла:

```go
slow, fast := head, head
for fast != nil && fast.Next != nil {
    slow = slow.Next      // на 1 шаг
    fast = fast.Next.Next // на 2 шага
    if slow == fast {     // встретились — цикл есть
        break
    }
}
// fast == nil || fast.Next == nil → цикла нет
```

1. оба стартуют из `head`;
2. `slow` на 1 шаг, `fast` на 2;
3. условие `fast != nil && fast.Next != nil` бережёт от разыменования `nil`;
4. встреча → цикл; выход из цикла по `nil` → цикла нет.

## 📖 Разбор

<details class="algo-details">
<summary>Теория, обнаружение/начало цикла, середина и сложность</summary>

**Fast & Slow Pointers** (алгоритм «заяц и черепаха», обнаружение циклов Флойда) —
два указателя движутся по структуре с разной скоростью: медленный на 1 шаг, быстрый
на 2. Если в списке есть цикл, быстрый рано или поздно догонит медленный внутри цикла;
если цикла нет — быстрый первым достигнет конца.

Техника даёт O(n) по времени и **O(1) по памяти** там, где наивный подход с хеш-таблицей
тратит O(n) дополнительной памяти.

#### Обнаружение цикла

Двигаем `slow` на шаг, `fast` на два. Совпадение указателей означает цикл; выход
`fast` в `nil` — цикла нет. (`ListNode` и работа с указателями `Next` — из главы
[«Связный список: устройство и операции»](linked-list-structure.md); если списки ещё
не в пальцах — начни с неё.)

```go
type ListNode struct {
    Val  int
    Next *ListNode
}

func hasCycle(head *ListNode) bool {
    slow, fast := head, head
    for fast != nil && fast.Next != nil {
        slow = slow.Next
        fast = fast.Next.Next
        if slow == fast {
            return true
        }
    }
    return false
}
```

#### Начало цикла

После встречи возвращаем `slow` в `head` и двигаем оба указателя по одному шагу:
точка их новой встречи — начало цикла. Это работает потому, что расстояние от головы
до начала цикла равно расстоянию от точки встречи до начала цикла.

```go
func detectCycle(head *ListNode) *ListNode {
    slow, fast := head, head
    for fast != nil && fast.Next != nil {
        slow = slow.Next
        fast = fast.Next.Next
        if slow == fast {
            break
        }
    }
    if fast == nil || fast.Next == nil {
        return nil // цикла нет
    }
    slow = head
    for slow != fast {
        slow = slow.Next
        fast = fast.Next
    }
    return slow
}
```

#### Середина списка

Когда `fast` дойдёт до конца, `slow` окажется в середине.

```go
func middleNode(head *ListNode) *ListNode {
    slow, fast := head, head
    for fast != nil && fast.Next != nil {
        slow = slow.Next
        fast = fast.Next.Next
    }
    return slow
}
```

#### Сложность

| Задача             | Время | Память |
|--------------------|-------|--------|
| Обнаружение цикла  | O(n)  | O(1)   |
| Начало цикла       | O(n)  | O(1)   |
| Середина списка    | O(n)  | O(1)   |

</details>

## 🧠 Почему это корректно

  <div class="algo-explain__item">
    <div class="algo-explain__q">Почему быстрый и медленный указатели <b>обязаны</b> встретиться внутри цикла и почему быстрый не может перепрыгнуть медленного?</div>
    <div class="algo-explain__ref">Смотрим на зазор — насколько <code>fast</code> впереди <code>slow</code> вдоль цикла. За шаг <code>fast</code> проходит +2, <code>slow</code> +1, значит зазор меняется ровно на −1 по модулю длины цикла <code>L</code>. Величина, убывающая на 1 по модулю <code>L</code>, обязана обнулиться за ≤ L шагов — это и есть встреча. И именно из-за относительной скорости +1 указатель проходит через <b>каждое</b> значение зазора и перескочить не может: перескок требовал бы шага ≥ +2 относительно.</div>
  </div>
  <div class="algo-explain__item">
    <div class="algo-explain__q">Почему, пустив один указатель из головы, а второй — из точки встречи, они сойдутся ровно в начале цикла?</div>
    <div class="algo-explain__ref">Пусть <code>a</code> — от головы до начала цикла, <code>b</code> — от начала цикла до точки встречи, <code>L</code> — длина цикла. К встрече <code>slow</code> прошёл <code>a+b</code>, <code>fast</code> — вдвое больше и одновременно <code>a+b+kL</code>. Отсюда <code>a+b = kL</code>, то есть <code>a = (k−1)L + (L−b)</code>. За <code>a</code> шагов первый указатель дойдёт до начала цикла, а второй пройдёт <code>b + a ≡ 0</code> вдоль цикла — окажется там же.</div>
  </div>
</div>

Три вопроса: почему указатели **обязательно встретятся**, почему быстрый не
«перепрыгивает» медленный, и почему формула начала цикла работает.

### Почему встреча гарантирована и без перепрыгивания

Когда оба внутри цикла, смотрим на **зазор** — на сколько `fast` впереди `slow` вдоль
цикла. За один шаг `fast` проходит +2, `slow` +1, значит зазор **меняется ровно на −1**
каждый шаг (по модулю длины цикла `L`). Величина, убывающая на 1 по модулю `L`,
обязательно станет `0` за ≤ `L` шагов → встреча. И ровно потому, что относительная
скорость **+1**, `fast` проходит через каждое значение зазора и **не может перескочить**
`slow` (перескок был бы при шаге ≥ +2 относительно).

Если цикла нет — `fast` первым упрётся в `nil` (он же быстрее), цикл `for` завершится.

### Вывод формулы начала цикла

Обозначим: `a` — расстояние от головы до начала цикла, `b` — от начала цикла до точки
встречи, `L` — длина цикла. К моменту встречи:

- `slow` прошёл `a + b`;
- `fast` прошёл `a + b + kL` (сделал `k` лишних кругов);
- и `fast` прошёл вдвое больше: `2(a + b) = a + b + kL`.

Отсюда `a + b = kL`, то есть **`a = (k−1)L + (L − b)`**. Значит, если пустить один
указатель из головы, а другой — из точки встречи, и двигать оба по шагу: за `a` шагов
первый дойдёт до начала цикла, а второй пройдёт `b + a = b + (k−1)L + (L−b) = kL ≡ 0`
вдоль цикла — то есть окажется **ровно в начале цикла**. Поэтому они встречаются именно
там. ∎

Попутно: `slow` до встречи делает **меньше одного круга** (зазор ≤ `L` убывает по
1/шаг), поэтому всё это `O(n)`.

## ⚙️ Цена на практике

### `O(1)` памяти — в этом весь смысл

Цикл легко найти и хеш-множеством посещённых узлов, но это `O(n)` памяти. Заяц и
черепаха дают тот же `O(n)` по времени при `O(1)` памяти — на собеседовании «а можешь
без доп. памяти?» это **ожидаемый** ответ, а не хеш-сет.

### Порядок проверки `fast != nil && fast.Next != nil`

Сначала `fast`, потом `fast.Next` — благодаря короткому замыканию `&&` не будет
разыменования `nil`. Переставишь местами — паника на списке чётной длины.

### Техника шире литерального списка

«Следующий узел» — это любая функция `i → f(i)` (функциональный граф). Поэтому Floyd
ловит цикл и там, где списка нет: **Find the Duplicate Number** (индекс → значение как
указатель), **Happy Number** (число → сумма квадратов цифр). Увидел «неявную ссылку
next» — вспомни про зайца и черепаху.

### Какая «середина» при чётной длине

При `slow, fast := head, head` и цикле `fast != nil && fast.Next != nil` для чётной
длины `slow` останавливается на **втором** среднем узле (соглашение LeetCode). Нужен
первый — стартуй `fast` с `head.Next`.

## ⚠️ Типичные ошибки

1. **Условие цикла `for fast != nil`** без проверки `fast.Next` — разыменование `nil`
   при `fast.Next.Next`. Правильно: `for fast != nil && fast.Next != nil`.
2. **Сдвиг старта** — инициализируйте оба указателя `head`, а не `head.Next`.
3. **Забыли сбросить `slow` в `head`** при поиске начала цикла — иначе указатель
   остаётся внутри цикла и ответ неверный.
4. **Не обработан пустой список или один узел** — проверяйте `head == nil` и
   `head.Next == nil` (self-loop при этом нужно учитывать отдельно).
5. **Поиск K-го с конца, когда K больше длины** — двигая `fast` вперёд на K шагов,
   проверяйте `fast == nil`.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий ответ «в лоб», затем понимание, *почему* он дорог по
памяти, и только потом заяц и черепаха.

> **Задача.** Дан односвязный список. Если в нём есть цикл, верни **узел, с которого
> цикл начинается** (вход в кольцо), иначе — `nil`.
> Пример: `3 → 2 → 0 → -4`, где хвост `-4` указывает обратно на узел `2` → ответ:
> узел `2`.

**Шаг 1. Наивно: хеш-множество посещённых узлов — O(n) времени, O(n) памяти.**

```go
func detectCycleNaive(head *ListNode) *ListNode {
    seen := make(map[*ListNode]bool)
    for cur := head; cur != nil; cur = cur.Next {
        if seen[cur] {  // узел встретился второй раз — это вход в цикл
            return cur
        }
        seen[cur] = true
    }
    return nil          // дошли до nil — цикла нет
}
```

Это **работает и проходит тесты**: первый повторно увиденный узел и есть начало цикла.
Но мы храним указатели на все узлы — `O(n)` дополнительной памяти и нагрузка на GC.
На собеседовании сразу прилетит «а можешь за `O(1)` памяти?» — и вот тут нужен Флойд.

**Шаг 2. Ключевое наблюдение.** Сначала зайцем и черепахой ловим *факт* цикла:
указатели встречаются внутри кольца ([почему встреча гарантирована](#почему-встреча-гарантирована-и-без-перепрыгивания)).
А чтобы найти *вход* в цикл, используем равенство расстояний: если `a` — путь от
головы до начала цикла, `b` — от начала до точки встречи, `L` — длина цикла, то
`a = (k−1)L + (L − b)` ([вывод формулы](#вывод-формулы-начала-цикла)). Значит, пустив
один указатель из головы, а другой — из точки встречи, и двигая оба по одному шагу,
мы сойдёмся **ровно на входе в цикл** — без всякой памяти под посещённые узлы.

**Шаг 3. Оптимум: алгоритм Флойда — O(n) времени, O(1) памяти.**

```go
func detectCycle(head *ListNode) *ListNode {
    slow, fast := head, head
    for fast != nil && fast.Next != nil {
        slow = slow.Next      // на 1 шаг
        fast = fast.Next.Next // на 2 шага
        if slow == fast {     // встреча — цикл есть
            break
        }
    }
    if fast == nil || fast.Next == nil {
        return nil            // вышли в nil — цикла нет
    }
    slow = head               // второй проход: один из головы,
    for slow != fast {        // другой из точки встречи, оба по 1 шагу
        slow = slow.Next
        fast = fast.Next
    }
    return slow               // сошлись на входе в цикл
}
```

Прогоните обе фазы на `3→2→0→-4` с циклом в узел `2`. Сначала быстрый (+2) и медленный (+1)
указатели встречаются внутри цикла, потом `slow` уходит в голову, и по одному шагу оба
сходятся на входе:

по значениям; вход в цикл — узел `2`):

*Фаза 1 — ищем встречу:*

| шаг | `slow` (×1) | `fast` (×2) | встреча? |
|-----|-------------|-------------|----------|
| старт | `3`       | `3`         | —        |
| 1   | `2`         | `0`         | нет      |
| 2   | `0`         | `2`         | нет      |
| 3   | `-4`        | `-4`        | **да**   |

*Фаза 2 — `slow` сброшен в `head`, оба по 1 шагу:*

| шаг | `slow` (из головы) | `fast` (из встречи) | равны? |
|-----|--------------------|---------------------|--------|
| старт | `3`              | `-4`                | нет    |
| 1   | `2`                | `2`                 | **да** |

Ответ — узел `2`, вход в цикл. Оба прохода линейны и не используют доп. памяти: тот
самый `O(n)` времени при `O(1)` памяти, ради которого и нужен Флойд вместо хеш-сета.

## 🏗️ Инженерный кейс

> **Ситуация.** Две родственные задачи. (1) В связном списке (например, цепочке обработчиков) закралось
> **зацикливание** — надо его обнаружить, не съев память под множество посещённых узлов. (2) В массиве из
> `n+1` чисел диапазона `1..n` есть **дубликат** — найти его, **не меняя** массив и за O(1) памяти.

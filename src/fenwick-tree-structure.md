## 🧱 Как устроена структура

BIT — это **один массив** `tree[1..n]` (нулевой индекс не используется). Узел `i` хранит сумму
**`lowbit(i)` элементов, заканчивающихся в позиции `i`**, то есть отрезок `(i − lowbit(i), i]`,
где `lowbit(i) = i & (−i)`. Никакого явного дерева — связи задаются битовой арифметикой.

```go
type Fenwick struct {
    n    int
    tree []int // 1-индексация: tree[0] не используется
}
```

```
индекс i:    1     2     3     4     5     6     7     8
lowbit(i):   1     2     1     4     1     2     1     8
зона [.. i]: [1]  [1,2] [3]  [1..4][5]  [5,6] [7]  [1..8]
```

Три факта, которые держат всё:

1. **Зона ответственности задаётся младшим битом.** Узел `i` покрывает `i & (−i)` элементов;
   `tree[8]` — сумму всех восьми, `tree[6]` — пары `[5,6]`, `tree[7]` — одного `[7]`.
2. **Обновление идёт вверх, запрос — вниз.** `Add` прыгает `i += i&−i` (по всем узлам, чья зона
   накрывает позицию), `PrefixSum` прыгает `i −= i&−i` (по дизъюнктным зонам, замощающим `[1, i]`).
3. **Число прыжков — число единичных битов** в `i`, то есть ≤ `log n`. Отсюда O(log n) у обеих.

## ➕ Обновление: `Add` (подъём `i += i & −i`)

Прибавить `delta` к элементу — значит обновить **все узлы, чья зона ответственности накрывает эту
позицию**. Они получаются прыжками вверх: `i += i & (−i)`.

```go
func (f *Fenwick) Add(i, delta int) {
    i++                   // в 1-индексацию
    for i <= f.n {
        f.tree[i] += delta // зона ответственности узла i
        i += i & (-i)      // следующий ответственный узел
    }
}
```

> 💡 **Демонстрация обновления.** Прибавляем `5` к индексу `2` в массиве из 8 элементов. Узел
> `i = 3` (зона `[2,2]`) обновляется первым, затем прыжок `i += i&−i`: `3 → 4` (зона `[0,3]`)
> `→ 8` (зона `[0,7]`). Подсвечена зона каждого обновляемого узла. Подставь свой индекс и delta.

## 🔎 Запрос: `PrefixSum` (спуск `i −= i & −i`)

Сумма префикса `[0, i]` собирается из **дизъюнктных зон**, замощающих диапазон: берём зону узла
`i`, прыгаем в `i − lowbit` к началу следующего непокрытого куска и так до нуля.

```go
func (f *Fenwick) PrefixSum(i int) int {
    i++                   // в 1-индексацию
    sum := 0
    for i > 0 {
        sum += f.tree[i]  // зона ответственности узла i
        i -= i & (-i)     // переход к родителю
    }
    return sum
}

func (f *Fenwick) RangeSum(l, r int) int { return f.PrefixSum(r) - f.PrefixSum(l-1) }
```

> 💡 **Демонстрация запроса.** Префиксная сумма до индекса `5`: прыжки вниз `i −= i&−i` складывают
> зоны узлов, пока `i > 0`. Подсвечена зона каждого слагаемого узла. `RangeSum(l, r)` — это просто
> две таких суммы: `PrefixSum(r) − PrefixSum(l−1)`.

## 🧠 Почему это корректно

### Зона ответственности узла и почему `i & -i` — это младший бит

`tree[i]` хранит сумму **`lowbit(i)` элементов, заканчивающихся в `i`**, то есть отрезок
`(i − lowbit(i), i]`, где `lowbit(i) = i & (-i)`.

Почему `i & -i` выделяет младший установленный бит? В дополнительном коде `-i = ~i + 1`:
прибавление `1` к инвертированному `i` переворачивает все нули в младшем хвосте обратно в нули,
**сохраняя единственный младший установленный бит** и инвертируя всё выше него. Поэтому `i & -i`
обнуляет всё, кроме этого бита. Например `i = 12 = 1100₂` → `i & -i = 100₂ = 4` → узел отвечает за
4 элемента `(8, 12]`.

### Почему два обхода покрывают ровно что нужно

- **`PrefixSum(i)`** идёт `i -= i & -i`: на каждом шаге берём отрезок `(i−lowbit, i]` и прыгаем в
  `i − lowbit`, то есть к началу следующего непокрытого куска. Эти отрезки **дизъюнктны и в
  точности замощают `[1, i]`** → префиксная сумма верна.
- **`Add(i)`** идёт `i += i & -i`: позиция `i` входит в зону узла `i`, затем `i + lowbit`, и т.д. —
  это ровно все узлы, чьи отрезки накрывают позицию `i`.

Почему подъём `i += lowbit` не промахивается — на пальцах. Зоны устроены как **двоичная
линейка**: зона длины `2^k` всегда кончается на числе, кратном `2^k` (раз `lowbit(i) = 2^k`,
само `i` делится на `2^k`). Теперь спроси: кто, кроме узла `i`, накрывает позицию `i`? Все
индексы **между** `i` и `i + lowbit(i)` — это числа между двумя соседними кратными `2^k`, их
младший бит *меньше* `2^k`, а значит их короткие зоны целиком лежат правее `i` — мимо. А вот
`i + lowbit(i)` — следующее кратное: его младший бит как минимум вдвое больше, и его длинная
зона дотягивается влево за `i` — накрывает. То есть каждый прыжок перескакивает всех «мелких»
соседей и приземляется точно в ближайший следующий накрывающий узел — ни лишних, ни
пропущенных. Проверь по табличке зон выше на `i = 5`: `5 → 6` (зона `[5,6]`) `→ 8` (зона
`[1..8]`), а узел `7` (зона `[7]`) честно пропущен — позицию 5 он не накрывает.

Эти два обхода **взаимно согласованы**: каждый узел, который `Add(i)` обновляет, будет учтён в
`PrefixSum(j)` для всех `j ≥ i`, чьи отрезки его включают. Это и есть инвариант BIT. Число шагов в
каждом — число единичных битов в `i`, то есть ≤ `log n`.

### Почему только обратимые операции

`RangeSum(l, r) = PrefixSum(r) − PrefixSum(l−1)` опирается на **вычитание**. Для суммы и XOR
обратный элемент есть. Для `min`/`max` его нет: из `min[0..r]` и `min[0..l−1]` нельзя получить
`min[l..r]`. Поэтому диапазонный минимум — это [дерево отрезков](segment-tree-structure.md), а не Фенвик.

## ⚙️ Цена на практике

### Легче дерева отрезков, когда задача подходит

Один массив `n+1` против `2n–4n`, крошечная константа, предсказуемые прыжки по памяти. Если нужны
**точечное обновление + префиксная/диапазонная сумма обратимой операции** — BIT короче, быстрее и
экономнее. Нужен range-min/max или range-update — бери [дерево отрезков](segment-tree-structure.md).

### 1-индексация обязательна

`i & -i` для `i = 0` равно `0` → шаг `i += 0` не двигается, цикл зависает (или `PrefixSum` не
стартует). Именно поэтому в `Add`/`PrefixSum` стоит сдвиг `+1`: у позиции `0` нет младшего бита.
Это самый частый баг при реализации BIT.

### Построение за `O(n)` вместо `O(n log n)`

Наивно строим `n` вызовами `Add` — это `O(n log n)`. Но можно за `O(n)`: положить
`tree[i] = arr[i-1]`, затем каждый узел протолкнуть в родителя:

```go
for i := 1; i <= n; i++ {
    if j := i + (i & -i); j <= n {
        tree[j] += tree[i]
    }
}
```

## ⚠️ Типичные ошибки

1. **Путаница 0- и 1-индексации** — держите 1-индексацию строго внутри, конвертируйте на границе.
2. **`Add` как «запись» вместо «прибавления»** — BIT хранит дельты; чтобы *установить* значение, прибавьте `(новое − старое)`.
3. **Попытка хранить min/max** — обычный BIT не поддерживает необратимые операции.
4. **Цикл `i -= i & (-i)` при `i = 0`** — не зайдёт в тело (`i > 0`), корректно вернёт 0.
5. **Зависание при `i += i & (-i)`, если забыли `+1`** — `lowbit(0) = 0`, шаг на месте.

## 🏗️ Инженерный кейс

> **Ситуация.** Дашборд аналитики в реальном времени. Есть 10 000 товаров; каждую секунду прилетают
> события «товар `i` продали на сумму `x`». Одновременно фронт спрашивает: **«сколько наторговали товары с
> 1-го по `k`-й?»** (префиксная сумма) — и так много раз в секунду. И обновления, и запросы должны быть
> быстрыми.

Первая мысль — префиксный массив: сумма любого диапазона за O(1). Но данные **всё время меняются**, и это
рушит наивный план. Подумай, чем платить:

Дерево Фенвика даёт и точечное обновление, и префиксную сумму за O(log n). Префиксный массив хорош только когда данные не меняются.">

Это и есть «зона ответственности» узла — сколько элементов он покрывает. Отсюда O(log n) на прыжки вверх/вниз по неявному дереву.">

**Вывод.** «Диапазонные/префиксные суммы **плюс обновления**» — сигнал дерева Фенвика (или отрезков). А вот
если данные **только читают** и не меняют — префиксный массив проще и быстрее (O(1) запрос). Спроси первым:
«меняются ли данные?» — от ответа зависит структура.

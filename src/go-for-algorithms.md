# 🪤 Go для алгоритмов: ловушки на собеседовании

> Алгоритм может быть верным, а ответ — нет: Go где-то делает не то, что ждёшь. На
> собеседовании такая ошибка стоит дороже, чем незнание приёма: код «правильный», тест красный,
> а время уходит на поиск того, что к алгоритму отношения не имеет. Здесь двенадцать таких мест.
> У каждого — короткий код «как ломается», что ты увидишь и как правильно.

Каждый вывод ниже получен запуском на Go 1.24 (модуль с `go 1.24` в `go.mod`, машина 64-битная).
Время — с одной машины, у тебя числа будут другими, но соотношение — тем же.

**Как читать.** Страница — справочник: не надо проходить её подряд. Пробеги заголовки; на
собеседовании или в тренажёре, когда тест упал «непонятно почему», вернись к нужному пункту.

## 1. `nil`-map: читать можно, писать — паника

`map`, объявленная через `var` и не созданная, равна `nil` — «пустое значение» map, за которым
нет таблицы. Чтение из неё безопасно, запись — нет:

```go
var m map[string]int
fmt.Println(m["a"], len(m)) // 0 0 — читать можно
v, ok := m["a"]             // 0 false
m["a"]++                    // а здесь программа падает
```

Что увидишь:

```text
panic: assignment to entry in nil map
```

**Как правильно** — создать map до первой записи: `m := map[string]int{}` или `make(map[string]int)`.
Тогда `cnt[x]++` работает и для нового ключа (отсутствующий ключ читается как `0`), а список
смежности строится без проверок: `adj[u] = append(adj[u], v)` — отсутствующий ключ даёт `nil`-срез,
и `append` к нему законен.

## 2. Структура в значении map: поле не поменять

```go
type P struct{ x, y int }

m := map[string]P{"a": {1, 2}}
m["a"].x = 10 // не компилируется
```

```text
cannot assign to struct field m["a"].x in map
```

`m["a"]` — это копия значения, а не место в памяти: при росте таблицы значения переезжают, и
адрес поля внутри map взять нельзя. **Как правильно** — один из двух способов:

```go
p := m["a"] // достать копию
p.x = 10    // поменять её
m["a"] = p  // положить обратно

ptr := map[string]*P{"a": {1, 2}} // или хранить указатели
ptr["a"].x = 10                   // меняется сама структура, на которую указывает значение
```

## 3. Порядок обхода map случаен

```go
m := map[string]int{"a": 1, "b": 2, "c": 3, "d": 4, "e": 5}
for k := range m {
    fmt.Print(k)
}
```

Три запуска одного и того же цикла подряд в одной программе:

```text
abcde
bcdea
eabcd
```

Порядок меняется от обхода к обходу — Go делает это нарочно, чтобы на порядок никто не
полагался. Если ответ — список, а тест сравнивает его дословно, он будет то зелёным, то красным.
**Как правильно** — отсортировать ключи перед выдачей: `keys := slices.Sorted(maps.Keys(m))`
(Go 1.23+) или собрать их в срез и вызвать `slices.Sort`.

## 4. `append` и общий массив

Срез — это окно в массив: указатель на начало, длина `len` и ёмкость `cap` (сколько места есть
в массиве после начала окна). Подсрез `a[:2]` смотрит в ТОТ ЖЕ массив. Если ёмкости хватает,
`append` пишет прямо в него — поверх чужих элементов:

```go
a := []int{1, 2, 3, 4}
b := a[:2]         // len 2, cap 4: место после b — это a[2], a[3]
b = append(b, 99)  // места хватило — записали в a[2]
fmt.Println(a, b)
```

```text
[1 2 99 4] [1 2 99]
```

`a` поменялся, хотя к нему никто не обращался. **Как правильно**: если подсрез будет расти,
ограничь его ёмкость третьим индексом — `b := a[:2:2]` (cap = 2, и `append` выделит новый массив;
тогда выйдет `a = [1 2 3 4]`, `b = [1 2 77]` после `append(b, 77)`) — или работай с копией
`slices.Clone(a[:2])`.

**В переборе с возвратом это главная ошибка.** Буфер `cur` один на все ветки; положить в ответ
его самого — значит положить окно в массив, который дальше перепишут:

```go
res = append(res, cur) // ошибка: в ответе — окно в общий буфер
```

Подмножества `[1 2 3]` с этой строкой:

```text
[[] [1] [1 2] [3 3 3] [3 3] [3] [3 3] [3]]
```

Ответов восемь, как и должно быть, но содержимое перезаписано последующими ветками. **Как
правильно** — класть копию: `res = append(res, append([]int(nil), cur...))` (или
`slices.Clone(cur)`), и выходит `[[] [1] [1 2] [1 2 3] [1 3] [2] [2 3] [3]]`. Подробно — в
[«Переборе с возвратом»](backtracking.md).

## 5. Удаление из середины среза — O(n), и оно портит исходный срез

```go
a := []int{1, 2, 3, 4, 5}
b := append(a[:1], a[2:]...) // «удалить a[1]»
fmt.Println(a, b)
```

```text
[1 3 4 5 5] [1 3 4 5]
```

Две беды. Первая — `append` сдвинул хвост внутри того же массива, и `a` теперь испорчен (тот же
общий массив, что в пункте 4). Вторая — сдвиг стоит O(n): каждый элемент хвоста переезжает на
место левее. Удалять так в цикле — уже O(n²). Замер: опустошить срез, каждый раз удаляя первый
элемент (`slices.Delete(s, 0, 1)`), против удаления последнего:

| n | удалять первый | удалять последний |
|---|---|---|
| 50 000 | 0,33 с | 6 мкс |
| 100 000 | 1,3 с | 18 мкс |
| 200 000 | 5,7 с | 0,2 мс |

n вдвое больше — время вчетверо больше: квадрат. **Как правильно**: если порядок не важен —
поставь на место удаляемого последний элемент и укороти срез, O(1):

```go
s[i] = s[len(s)-1]
s = s[:len(s)-1]
```

Если важен — `slices.Delete(s, i, i+1)` (тот же O(n) сдвиг, но без путаницы с `append`), а
частое удаление из середины — повод взять другую структуру (список, дек, куча).

## 6. `q = q[1:]` как очередь: память не отпускается

Очередь BFS на срезе — `q = q[1:]` — работает и стоит O(1). Но голова уходит из окна, а не из
массива: снятые элементы остаются в нём, и если это указатели, сборщик мусора не может
освободить объекты, на которые они указывают.

```go
type Big struct{ buf [1 << 10]byte } // 1 КиБ

q := make([]*Big, 100_000)
for i := range q {
    q[i] = &Big{}
}
for len(q) > 1 {
    q = q[1:] // сняли 99 999 элементов
}
```

Куча после `runtime.GC()`, пока жив `q` из одного элемента:

```text
q = q[1:], осталось 1, cap 1: 98.7 MiB
q[0] = nil; q = q[1:]:        1.0 MiB
```

Окно длиной в один элемент держит все сто тысяч объектов. **Как правильно** — обнулять
снятый элемент перед сдвигом (`q[0] = nil`), а в большой очереди — вести индекс головы `head`
по срезу вместо `q = q[1:]`. Для `[]int` в задаче на собеседовании это не важно: числа ничего не
держат. О том же — в [«Графах»](graphs.md#очередь-срезом-следи-за-массивом-под-срезом).

## 7. Строки: `+=` в цикле — O(n²)

Строка в Go неизменяема, поэтому `s += "ab"` не дописывает, а создаёт новую строку и копирует
в неё всю старую. На k-м шаге копируется k кусков — в сумме квадрат:

```go
s := ""
for i := 0; i < n; i++ {
    s += "ab"
}
```

| n | `+=` | `strings.Builder` |
|---|---|---|
| 20 000 | 29 мс | 40 мкс |
| 40 000 | 127 мс | 111 мкс |
| 80 000 | 526 мс | 207 мкс |

**Как правильно** — `strings.Builder`: он копит байты в растущем буфере, как `append`:

```go
var b strings.Builder
for i := 0; i < n; i++ {
    b.WriteString("ab")
}
s := b.String()
```

Для ответа из отдельных символов годится и `[]byte` с `append` и `string(buf)` в конце.

## 8. Байты и руны: `s[i]` — не буква

Строка — это байты в кодировке UTF-8. Латинская буква — один байт, кириллическая — два.
`len(s)` и `s[i]` считают байты, а `range s` идёт по **рунам** (руна — один символ Юникода, тип
`rune`) и отдаёт номер байта, с которого руна начинается:

```go
s := "кот"
fmt.Println(len(s), s[0]) // 6 208 — шесть байт, s[0] — половинка «к»
for i, r := range s {
    fmt.Print(i, ":", string(r), " ") // 0:к 2:о 4:т
}
```

Разворот такой строки по байтам даёт мусор `"\x82Ѿк\xd0"` вместо `"ток"`. **Как правильно**: если
во входе может быть не только латиница — `r := []rune(s)`, работать с `r[i]`, собрать
`string(r)`. Если условие обещает строчные латинские буквы (так в большинстве задач LeetCode),
байты — это и есть буквы, и счётчик массивом `cnt[s[i]-'a']++` — быстрый и верный.

## 9. Сортировка по нескольким ключам и стабильность

Частая ошибка — склеить два условия через `||`:

```go
sort.Slice(ps, func(i, j int) bool {
    return ps[i].age < ps[j].age || ps[i].name < ps[j].name // ошибка
})
```

На `{b 30} {a 25} {c 25} {a 30}` это даёт `[{a 25} {a 30} {c 25} {b 30}]` — возраст не по
порядку: `{a 30}` «меньше» `{c 25}` по имени, а условие этого не запрещает. Второй ключ должен
решать **только при равенстве первого**. Проще всего — функция сравнения, которая возвращает
`-1`, `0` или `+1`, и `cmp.Or` (Go 1.22+), который берёт первое ненулевое сравнение:

```go
slices.SortFunc(ps, func(a, b P) int {
    return cmp.Or(
        cmp.Compare(a.age, b.age),   // сначала возраст по возрастанию
        cmp.Compare(a.name, b.name), // при равном возрасте — имя
    )
})
```

```text
[{a 25} {c 25} {a 30} {b 30}]
```

По убыванию — поменять аргументы местами: `cmp.Compare(b.age, a.age)`. Не пиши сравнение
вычитанием `return a - b`: на больших числах разность переполняется (пункт 10), и `[-9223372036854775807, 5]`
«сортируется» в `[5 -9223372036854775807]`.

**Стабильность** — сохраняет ли сортировка исходный порядок равных элементов. `slices.SortFunc`
и `sort.Slice` — нет. На 20 элементах с тремя значениями ключа, исходно стоящих по номеру, после
`slices.SortFunc` номера среди равных шли `9 18 15 3 12 0 6` — перемешались. Когда порядок равных
важен (отсортировать по второму ключу, сохранив порядок по первому, или «при равенстве — кто
раньше пришёл»), бери `slices.SortStableFunc` / `sort.SliceStable` — там вышло `0 3 6 9 12 15 18`.

## 10. `container/heap`: пять методов и чей `Pop`

Пакет [`container/heap`](heap-structure.md#в-go-куча--это-containerheap) просеивает сам, а от тебя
ждёт тип с пятью методами: `Len`, `Less`, `Swap` (как для сортировки) и `Push(x any)`, `Pop() any`.
`Push`/`Pop` получают и отдают `any`, потому что пакет не знает типа твоих элементов, — отсюда
приведение `heap.Pop(h).(int)`. И они на указателе (`*IntHeap`): меняют длину среза. Забудешь
указатель — `heap.Push(h, 2)` с `h` типа `IntHeap` не скомпилируется: `method Pop has pointer
receiver`.

Главная ловушка — вызвать свой метод вместо функции пакета:

```go
h := &IntHeap{5, 1, 4}
heap.Init(h)         // теперь срез — куча: [1 5 4]
heap.Push(h, 2)      // [1 2 4 5]
fmt.Println(h.Pop()) // 5 — СВОЙ метод: просто отрезал хвост
```

`h.Pop()` вернул `5`, а не минимум `1`: твой `Pop` только отрезает последний элемент, а
поставить минимум в хвост перед этим должна функция `heap.Pop(h)`. Так же `h.Push(x)` дописывает
в хвост без просеивания — куча ломается: после `h.Push(3); h.Push(1)` на пустой куче
`heap.Pop(h)` вернул `3`. И без `heap.Init` на неупорядоченном срезе `{5, 1, 4}` первый
`heap.Pop` вернул `5`. **Как правильно**: свои `Push`/`Pop` пишешь, но вызываешь только
`heap.Push(h, x)`, `heap.Pop(h)`, а готовый срез сначала превращаешь в кучу `heap.Init(h)`.

## 11. Переполнение `int` и деление с отрицательными

На 64-битной машине `int` — 64 бита: `math.MaxInt` = 9223372036854775807 (≈ 9,2·10¹⁸). Переполнение
не падает, а молча заворачивает число в отрицательное.

**Середина отрезка.** `(lo + hi) / 2` при больших границах переполняется:

```go
lo, hi := math.MaxInt-10, math.MaxInt-2
fmt.Println((lo+hi)/2, lo+(hi-lo)/2) // -7 9223372036854775801
```

На индексах массива до такого не дойдёт, а в бинарном поиске по ответу с `hi = math.MaxInt` —
легко. Пиши `lo + (hi-lo)/2` всегда.

**«Бесконечность» плюс вес.** `dist[u] = math.MaxInt` как «ещё не дошли», а потом `dist[u] + w`:

```go
inf := math.MaxInt
fmt.Println(inf+5, inf+5 < 10) // -9223372036854775804 true
```

Релаксация решит, что через недостижимую вершину путь короче всех. **Как правильно**: проверять
`dist[u] != inf` до сложения или брать запас — `const inf = math.MaxInt / 2`.

**Произведение по модулю.** `3·10⁹ · 4·10⁹ = 1,2·10¹⁹` больше `MaxInt`:

```go
a, b, m := 3_000_000_000, 4_000_000_000, 1_000_000_007
fmt.Println(a * b % m)           // -582343420
fmt.Println(a % m * (b % m) % m) // 588 — верно
```

Бери остаток от каждого множителя ДО умножения: оба меньше `m ≈ 10⁹`, и произведение
укладывается в `int`. Ещё одна мелочь: `-n` для `n = math.MinInt` — снова `math.MinInt`, модуль
самого маленького числа не помещается в `int`.

**Деление и `%` с отрицательными.** Go делит с отбрасыванием дробной части к нулю, и знак
остатка — как у делимого:

```go
fmt.Println(-7/2, -7%2, 7%-2) // -3 -1 1
```

Отсюда две ошибки. Проверка нечётности `n%2 == 1` для `n = -3` даёт `false` (остаток `-1`) —
пиши `n%2 != 0`. Индекс по кругу «на k шагов назад» `k % n` при `k = -2`, `n = 5` даёт `-2` —
выход за границу среза; верно `(k%n + n) % n` = `3`. И `-7 >> 1` — это `-4`, а не `-3`: сдвиг
округляет вниз, деление — к нулю.

## 12. Глубина рекурсии и переменная цикла

**Глубина рекурсии.** Стек горутины растёт сам, но до предела: по умолчанию 1 000 000 000 байт
(`debug.SetMaxStack` возвращает именно это число). Упрёшься — программа падает целиком:

```text
runtime: goroutine stack exceeds 1000000000-byte limit
fatal error: stack overflow
```

Это не паника: `recover` её не ловит (в замере `defer` с `recover` так и не выполнился). Сколько
стоит глубина в памяти и как переписать обход явным стеком — в
[«Графах»](graphs.md#глубина-рекурсии-dfs--цена-и-предел).

**Переменная цикла и замыкания.** Замыкание (функция, созданная внутри другой и видящая её
переменные) захватывает переменную, а не её значение в момент создания:

```go
var fs []func()
for i := 0; i < 3; i++ {
    fs = append(fs, func() { fmt.Print(i, " ") })
}
for _, f := range fs {
    f()
}
```

С `go 1.24` в `go.mod` выводится `0 1 2`: с Go 1.22 у каждой итерации своя переменная `i`. С
`go 1.21` в `go.mod` — даже на новом компиляторе — `3 3 3`: одна `i` на весь цикл, и к вызову она
уже 3. То же со сбором указателей `ps = append(ps, &v)` в `for _, v := range`: `10 20 30` на
новом языке и `30 30 30` на старом. Решает строка `go` в `go.mod`, а не версия установленного Go
— в чужом старом проекте старые правила. Если не уверен, сделай копию явно: `i := i` в начале
тела цикла.

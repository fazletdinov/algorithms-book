## 1. Планировщик: G, M, P

Горутина — это **не** поток ОС. Рантайм запускает немного потоков (`M`; их число динамическое — обычно порядка числа ядер, но при блокирующих syscall создаются дополнительные) и
раскладывает на них тысячи горутин (`G`). Связующее звено — `P` (логический процессор):
он держит **локальную очередь** готовых горутин и состояние аллокатора. Чтобы исполнять
Go-код, нужна тройка **G + M + P** (число `P` задаёт `GOMAXPROCS`).

- **Локальная очередь (LRQ)** у каждого `P` — брать из неё работу можно **без блокировок**.
- **Глобальная очередь (GRQ)** — общая; в неё заглядывают периодически.
- **Кража работы (work stealing)** — простаивающий `P` забирает **половину** очереди у
  занятого соседа, балансируя нагрузку.
- **Handoff на syscall** — если горутина уходит в **блокирующий системный вызов**, её `M`
  блокируется вместе с ней, но `P` **передаётся** другому потоку, и остальные горутины
  продолжают бежать.

```go
func schedule() {
    for {
        g := runqget(p)       // из локальной очереди P
        if g == nil {
            g = globrunqget() // из глобальной очереди
        }
        if g == nil {
            g = runqsteal(p)  // украсть половину у другого P
        }
        execute(g)            // запустить на потоке M
    }
}
```

Листай «›»: горутины запускаются из локальных очередей, простаивающий `P` крадёт работу, а
блокирующий syscall не замораживает процессор — его подхватывает другой поток:

<div class="algo-viz" data-viz="scheduler"></div>

Горутина дешёвая: старт со стека ~**2 КБ** (растёт копированием по мере надобности) против
~1 МБ у потока ОС. Поэтому «запусти горутину на задачу» — нормально, а «запусти поток» —
нет. С Go 1.14 планировщик **вытесняющий**: долгая горутина без точек переключения всё
равно будет приостановлена (асинхронная преемпция по сигналу).

## 2. Сборщик мусора: трёхцветная разметка

GC в Go — **конкурентный**, **не перемещающий** (объекты не двигаются), на основе
**трёхцветной** пометки mark-and-sweep:

- **Белый** — ещё не достигнут, кандидат на удаление.
- **Серый** — достигнут, но его указатели ещё не просмотрены.
- **Чёрный** — достигнут и полностью просмотрен (живой).

Старт — от **корней** (стек горутин, глобальные переменные): на что они указывают,
становится серым. Дальше: берём серый объект, его белых потомков красим в серый, сам объект
— в чёрный. Когда серых не осталось, всё **белое недостижимо** — это мусор, его освобождает
фаза sweep.

```go
func markPhase(roots []*obj) {
    grey := roots             // корни сразу серые
    for len(grey) > 0 {
        o := pop(grey)        // берём серый объект
        for _, c := range o.pointers {
            if c.color == white {
                c.color = grey // достижим → серый
                grey = push(grey, c)
            }
        }
        o.color = black       // потомки просканированы → чёрный
    }
    // всё, что осталось белым — мусор → sweep
}
```

Зелёные стрелки — корни; объекты меняют цвет белый → серый → чёрный, а недостижимые (E, F)
в конце остаются белыми и помечаются как мусор:

<div class="algo-viz" data-viz="gc-mark"></div>

Главное — разметка идёт **параллельно** с работающей программой. Чтобы она не «потеряла»
объект, который программа переподвесила во время марковки, действует **write barrier**
(барьер записи): при изменении указателя рантайм подкрашивает нужный объект. Остановки
«весь мир» (**STW**) — лишь на краткие служебные фазы и обычно **меньше миллисекунды**.
Порог запуска GC задаёт `GOGC` (по умолчанию 100 — собирать, когда куча выросла вдвое);
с Go 1.19 есть мягкий лимит памяти `GOMEMLIMIT`.

## 3. Аллокатор и escape-анализ

Где разместить значение — решает **escape-анализ** на этапе **компиляции**:

- Значение **не покидает** функцию → его кладут в **кадр стека**. Освобождение — бесплатное,
  с возвратом из функции; GC к нему вообще не прикасается.
- Значение/его адрес **«убегает»** наружу (вернули указатель, положили в интерфейс, в
  замыкание, в поле кучи) → оно едет в **кучу**, под надзор GC.

```go
func noEscape() int {
    x := 42      // не покидает функцию → стек
    return x     // вернули КОПИЮ; кадр исчезает
}

func escapes() *int {
    y := 42      // адрес уйдёт наружу...
    return &y    // ...значит y живёт в КУЧЕ (escape)
}
```

Слева — стек (кадры исчезают с возвратом), справа — куча (живёт, пока GC не освободит).
`y` живёт в куче ровно потому, что его адрес возвращают наружу. Решает это компилятор ещё до
запуска (escape-анализ), поэтому `y` сразу создаётся в куче — во время выполнения ничего со стека
в кучу не переезжает:

<div class="algo-viz" data-viz="escape"></div>

Куча устроена как у TCMalloc: у каждого `P` есть **`mcache`** — кэш свободных блоков, из
которого мелкие объекты выдаются **без блокировок**. Размеры округляются вверх до одного
из ~70 **размерных классов** (это видно в [`growslice → roundupsize`](big-o.md)). Объекты
до 16 байт без указателей собирает **tiny-аллокатор** (склеивает их в один блок); крупные
(> 32 КБ) идут напрямую из `mheap`. Меньше аллокаций в куче → меньше работы аллокатору и GC.

## ⚡ Что помнить на собеседовании

- **G/M/P**: горутина / поток ОС / логический процессор. Тройка нужна, чтобы исполнять код.
- Горутина дешёвая (стек ~2 КБ, растёт) — отсюда «горутина на задачу».
- **Блокирующий syscall** не блокирует другие горутины: `P` уходит к другому `M`.
- **GC** — конкурентный трёхцветный mark-sweep; **STW < 1 мс**; страхует **write barrier**.
- **Escape-анализ** (компиляция) решает стек/куча. Проверка — `go build -gcflags=-m`.
- Меньше аллокаций в куче → меньше нагрузки на GC. Стек — даром.

## 🧠 Почему это устроено так

### Почему GMP, а не «горутина = поток»

Поток ОС дорог (≈1 МБ стека, переключение через ядро). Если бы горутина была потоком,
«миллион горутин» лёг бы. Прослойка `P` позволяет рантайму планировать горутины **в
пространстве пользователя** (дёшево, без ядра) и держать ровно столько **работающих**
потоков, сколько ядер (всего потоков может быть больше — из-за блокирующих syscall). Локальные очереди убирают конкуренцию за общий замок, а work stealing не даёт
процессорам простаивать — это классический дизайн масштабируемого планировщика.

### Почему GC конкурентный и не перемещающий

Длинные паузы «весь мир» неприемлемы для серверов. Поэтому марковка идёт **одновременно** с
программой; цена — необходимость **write barrier**, чтобы не потерять объект, переподвешенный
на лету. Не-перемещение упрощает взаимодействие с C и указателями ценой возможной
фрагментации — её берёт на себя аллокатор размерными классами. Трёхцветный инвариант
(«чёрный не указывает на белый напрямую») — это то, что барьер и поддерживает.

### Почему escape-анализ на компиляции, а не в рантайме

Решение «стек или куча» нужно принять **до** исполнения, чтобы сгенерировать правильный код.
Компилятор доказывает, что время жизни значения не выходит за кадр; если доказать нельзя —
консервативно отправляет в кучу. Поэтому одни и те же по виду строки могут аллоцировать или
нет — зависит от того, **убегает** ли значение.

## ⚙️ Цена на практике

Здесь рантайм встречается с алгоритмами — та самая константа за Big-O.

### `map` против массива

`map[byte]int` для счётчика символов — это аллокация в куче, хеш на каждом доступе и
нагрузка на GC. `[256]int` живёт на стеке (если не убегает), доступ — одно обращение по
индексу, отлично ложится в кэш. Big-O одинаков, но на горячем пути разница в разы — поэтому
в [скользящем окне](sliding-window.md#-цена-на-практике) для байтового алфавита берут массив.

### Преаллокация убирает аллокации и копии

`make([]int, 0, n)` и `make(map[K]V, n)` выделяют ёмкость сразу — `append`/вставка не
[копируют при росте](big-o.md). Знаешь размер — задай `cap`. Это убирает амортизированные,
но реальные расходы.

### Меньше «убеганий» — меньше мусора

Возврат `*T` из горячей функции, передача в `interface{}`, захват в замыкание — частые
причины escape в кучу. Где можно — работай со **значениями** и принимай результат через
параметр-срез. Для частых короткоживущих объектов — `sync.Pool` (переиспользование вместо
аллокации).

### Инструменты вместо гаданий

- `go build -gcflags=-m ./...` — escape-анализ: что ушло в кучу и почему.
- `GODEBUG=gctrace=1 ./app` — трасса каждого цикла GC (паузы, размер кучи).
- `go test -bench=. -benchmem` — `allocs/op` и `B/op` рядом с временем.
- `go test -race` — детектор гонок (рантайм инструментирует доступы к памяти).
- `pprof` (heap/allocs/goroutine/block) — где именно аллокации и блокировки.

## ⚠️ Типичные заблуждения

1. **«Горутина — это поток»** — нет, это пользовательская сущность, потоков много меньше.
2. **«GC останавливает программу надолго»** — STW обычно < 1 мс; марковка конкурентна.
3. **«`new`/`&` всегда кладёт в кучу»** — нет, решает escape-анализ; часто это стек.
4. **«Хвостовая рекурсия дешёвая по стеку»** — в Go нет TCO, стек растёт.
5. **«Больше горутин — всегда быстрее»** — переключения и синхронизация имеют цену; иногда
   меньше горутин и больше работы на каждую — лучше.
6. **«Указатель эффективнее значения»** — указатель может вызвать escape в кучу + промахи
   кэша; маленькую структуру дешевле копировать.

## 📝 Разбор: почему этот цикл аллоцирует

> **Задача.** Горячий цикл неожиданно грузит GC. Почему — и как убрать аллокации?

**Шаг 1. Симптом.** `go test -bench=. -benchmem` показывает `allocs/op > 0` там, где
«вроде ничего не выделяется».

**Шаг 2. Диагноз.** `go build -gcflags=-m` печатает строки вида
`./x.go:12:9: &buf escapes to heap`. Значит, локальный объект убегает — например, вернули
его адрес, или положили в `interface{}` (в т.ч. неявно — `fmt.Sprint(x)`), или захватили в
горутину/замыкание.

**Шаг 3. Лечение.**
- работай со значением, а не возвращай `*T` из горячей функции;
- заранее `make([]T, 0, n)` вне цикла, переиспользуй буфер;
- для частых временных объектов — `sync.Pool`;
- избегай боксинга в `interface{}` на горячем пути.

**Шаг 4. Проверка.** Снова `-benchmem`: `allocs/op` стал нулём, время и нагрузка на GC
упали. Привычка инженера — **измерять** (`-m`, `gctrace`, `pprof`), а не угадывать.

<div class="algo-challenge__q">Чем посмотреть, что именно ушло в кучу?</div>
</div>

**Попробуй руками** (на любом своём Go-коде):

```bash
go build -gcflags=-m ./...      # что убежало в кучу и почему
go test -bench=. -benchmem ./...# allocs/op и B/op рядом со временем
GODEBUG=gctrace=1 go run .       # трасса циклов GC: паузы и размер кучи
go test -race ./...              # детектор гонок
```

Конкурентность на практике — в пакетах тренажёра `parallelbfs`, `parallelsort`,
`parallelnqueens`, `wordcount` (запускай с `-race` и `-bench`).

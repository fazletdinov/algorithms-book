## Чего нет в stdlib — но есть в экосистеме

Не всё живёт в стандартной библиотеке. Продвинутые структуры из книги — рабочие лошадки инфраструктуры:

- **[B-дерево / B+дерево](btree-structure.md)** — движки БД и хранилищ: [`bbolt`](https://github.com/etcd-io/bbolt) (B+дерево, лежит под **etcd**/**Kubernetes**), индексы PostgreSQL/SQLite, [`google/btree`](https://github.com/google/btree) (in-memory). Отсортированные диапазоны + дисковая локальность.
- **[LRU-кэш](pattern-combinations.md)** (список + хеш) — [`hashicorp/golang-lru`](https://github.com/hashicorp/golang-lru), `groupcache/lru`, HTTP-кэши. Вытеснение по давности использования.
- **[Дерево отрезков](segment-tree-structure.md) / [Фенвик](fenwick-tree-structure.md)** — диапазонные агрегаты: аналитические БД, оконные метрики, тайм-серии; чаще в специализированном коде, чем в общей stdlib.
- **[Union-Find](union-find-structure.md)** — компоненты связности: компиляторы (алиас-анализ), сегментация изображений, кластеризация.

## 📎 Разбор: почему таймеры Go — это куча (а не список и не map)

Ссылка показывает *где*, но интереснее *почему*. Разберём один пример до конца — на нём виден
способ рассуждать про любой другой.

Каждый `time.After`, `time.NewTimer`, `context.WithTimeout` регистрирует **таймер**. Рантайму нужно
из тысяч живых таймеров постоянно доставать **ближайший по времени** (чтобы разбудить горутину
ровно тогда), при этом таймеры всё время **добавляются** и **отменяются**. Вопрос: какая структура?

- **Отсортированный срез?** get-min за O(1), но каждая вставка сдвигает хвост — **O(n)**. А вставка
  здесь самая частая операция (любой сетевой вызов с таймаутом). O(n)×тысячи = провал.
- **map?** O(1) вставка/удаление, но **порядка нет** — «ближайший» пришлось бы искать полным
  сканом O(n) на каждый тик.
- **Куча** закрывает ровно эти требования: вставка `siftUp` — **O(log n)**, ближайший таймер это
  корень `heap[0]` — доступ **O(1)**, извлечение сработавшего — `siftDown` O(log n). Часто
  вставляем, всегда мгновенно знаем минимум.

Дистиллированная суть (в `runtime/time.go` то же, но без unsafe и координации с планировщиком):

```go
type timer struct {
    when int64 // абсолютное время срабатывания, наносекунды
    // ...callback / канал
}

type timerHeap struct{ h []*timer } // min-heap по полю when

// Add — регистрируем таймер: в конец, затем просеиваем вверх. O(log n).
func (t *timerHeap) Add(tm *timer) {
    t.h = append(t.h, tm)
    i := len(t.h) - 1
    for i > 0 {
        parent := (i - 1) / 2
        if t.h[parent].when <= t.h[i].when {
            break // родитель срабатывает раньше — таймер на своём месте
        }
        t.h[parent], t.h[i] = t.h[i], t.h[parent] // всплываем к корню
        i = parent
    }
}

// Next — ближайший к срабатыванию таймер. O(1): это корень кучи.
func (t *timerHeap) Next() *timer {
    if len(t.h) == 0 {
        return nil
    }
    return t.h[0]
}
```

Куча упорядочена по `when`; корень `heap[0]` — тот, что сработает первым, поэтому `Next()` — O(1).
В виджете ниже — куча таймеров `[10, 40, 25, 90, 50, 30]` мс и `Add(15)`: новый таймер встаёт в
конец — правым ребёнком `25` (индекс 6, родитель `(6−1)/2 = 2`) — и просеивается вверх: `15 < 25`
— меняются местами; `15 > 10` — стоп. Корень `10` по-прежнему ближайший, а новый таймер занял
верхний слой. Покрути вставку: таймер всплывает, пока не встанет под более раннего:

<div class="algo-viz" data-viz="heap-push" data-heap="10,40,25,90,50,30" data-val="15"></div>

**Инженерная деталь: в рантайме куча не двоичная, а 4-арная** (`const timerHeapN = 4` в
`runtime/time.go`) — у каждого узла до **четырёх** детей. Дерево получается **ниже** (log₄ вместо
log₂ — вдвое меньше уровней), значит меньше прыжков по памяти при просеивании → **лучше кэш
процессора**. Плата — больше сравнений на одном уровне (до 4 детей), но сравнение `int64` дешевле
промаха кэша. Это ровно тот компромисс «константа за Big-O», о котором [«Куча»](heap-structure.md)
и [«Цена на практике»](appendix-go-memory.md). Плюс таймеры разбиты **по P** (логическим
процессорам) — каждый со своей кучей, чтобы горутины не толкались за один лок (см.
[Go-рантайм](go-runtime.md)).

Источник целиком: [`runtime/time.go`](https://github.com/golang/go/blob/master/src/runtime/time.go)
— `type timers`, `siftUp`/`siftDown`, `timerHeapN`.

> Тот же ход рассуждения работает везде: выпиши **требования** (какие операции и как часто) →
> сопоставь их с профилями структур (что дёшево, что дорого) → выбор становится очевиден. Ещё два
> разбора тем же способом — ниже.

## 📎 Разбор: почему буфер канала — это кольцо

`make(chan T, n)` создаёт буферизованный канал на `n` элементов. Требования: это **FIFO** (первым
записан — первым прочитан), **фиксированной** ёмкости `n`, с частыми `send`/`recv` на горячем пути,
и **без аллокации на каждый элемент** (каналы — примитив синхронизации, обязаны быть дешёвыми).

- **Срез-очередь (`append` + `[1:]`)?** Чтение сдвигает начало или растит хвост — либо O(n) сдвиг,
  либо срез пухнет и течёт память, плюс аллокации при росте.
- **Связный список?** O(1) вставка, но **аллокация узла на каждый элемент** и погоня за указателями
  (плохой кэш) — недопустимо для примитива, через который гоняют миллионы значений.
- **Кольцевой буфер** — один непрерывный блок из `n` слотов и два индекса по кругу: `send` пишет в
  `buf[sendx]` и двигает `sendx`, `recv` читает `buf[recvx]` и двигает `recvx`; дойдя до конца,
  индекс заворачивается в 0. Ёмкость фиксирована, операции O(1), **ни одной аллокации** после
  создания, данные лежат подряд.

Суть (в `runtime/chan.go` то же, но с unsafe-арифметикой по `buf`):

```go
type ringChan struct {
    buf      []int // n слотов, выделены один раз при make
    dataqsiz uint  // ёмкость n («size of the circular queue»)
    qcount   uint  // сколько сейчас в очереди
    sendx    uint  // куда писать следующий send
    recvx    uint  // откуда читать следующий recv
}

func (c *ringChan) send(v int) {
    c.buf[c.sendx] = v
    c.sendx++
    if c.sendx == c.dataqsiz { // дошли до конца — заворачиваем в начало
        c.sendx = 0
    }
    c.qcount++
}

func (c *ringChan) recv() int {
    v := c.buf[c.recvx]
    c.recvx++
    if c.recvx == c.dataqsiz {
        c.recvx = 0
    }
    c.qcount--
    return v
}
```

`dataqsiz = 4`; `sendx`/`recvx` бегут по кругу, между ними — «живые» элементы:

<div class="algo-fig" data-fig="array" data-array="·,A,B,·" data-rows="buf" data-ptrs="recvx@1,sendx@3" data-ranges="живые, qcount = 2@1-2" data-caption="dataqsiz = 4: recvx — откуда следующий recv, sendx — куда следующий send"></div>

`recv()` отдаёт `A`, и `recvx` становится 2. `send(C)` пишет в слот 3, и `sendx` заворачивается в 0.
Пусто — `qcount == 0`; полно — `qcount == dataqsiz`, тогда `send` блокируется.

Листай «›»: `send` заполняет слот и двигает `sendx`, `recv` освобождает слот и двигает `recvx`;
на границе индекс **заворачивается** в 0, а при заполнении (`qcount == ёмкость`) `send` блокируется:

<div class="algo-viz" data-viz="ring-buffer" data-size="4" data-ops="A,B,C,-,-,D,E,F,G"></div>

Поэтому у **небуферизованного** канала (`make(chan T)`, `dataqsiz == 0`) буфера нет вовсе — `send`
и `recv` встречаются напрямую (rendezvous), кольцо не нужно.

Источник: [`runtime/chan.go`](https://github.com/golang/go/blob/master/src/runtime/chan.go) —
`type hchan` (`buf`/`dataqsiz`/`sendx`/`recvx`), заворот `if c.sendx == c.dataqsiz { c.sendx = 0 }`.

## 📎 Разбор: как канал блокирует и будит горутины (sendq / recvq)

Буфер — только половина канала. Вторая — **синхронизация**: `send` в полный канал и `recv` из пустого
должны **заблокироваться**, а потом проснуться в нужный момент. И «блокировка» здесь не занимает поток —
ровно как в [netpoll](#-разбор-почему-блокирующий-connread-масштабируется-netpoll--epoll).

У канала есть две очереди ждущих горутин: `sendq` (заждавшиеся отправители) и `recvq` (заждавшиеся
получатели). Инвариант: **хотя бы одна из них всегда пуста** — не бывает одновременно и ждущих
отправителей, и ждущих получателей (второй сразу забрал бы у первого).

<div class="algo-viz" data-viz="chan-block"></div>

**Небуферизованный канал** — всегда встреча (rendezvous):

- `ch <- v`: получателя нет (`recvq` пуст) → отправитель кладёт себя и значение в `sendq` и **паркуется**
  (`gopark`); поток свободен.
- `<-ch`: пришедший получатель находит ждущего в `sendq` и **копирует значение напрямую из стека
  отправителя** в свою переменную — минуя буфер — и будит отправителя (`goready`). В обратную сторону так же.

Прямая передача «стек-в-стек» — оптимизация: раз обе стороны уже здесь, незачем гонять значение через буфер.

**Буферизованный канал** добавляет к этому [кольцевой буфер](#-разбор-почему-буфер-канала--это-кольцо):
`send` кладёт в буфер и **не блокируется**, пока есть место; паркуется в `sendq` только на **полном**
буфере. `recv` берёт из буфера, паркуется в `recvq` только на **пустом**. А если при `send` уже кто-то
ждёт в `recvq` — значение отдаётся ему напрямую, минуя буфер.

Отсюда — привычные факты:

- **Небуферизованный канал синхронизирует**: `ch <- v` не вернётся, пока кто-то не прочитает — удобно как
  сигнал «готово».
- **Отправка/приём в `nil`-канал блокирует навсегда** (`sendq`/`recvq` некому разбудить) — источник дедлоков.
- **Закрытие канала** будит всех ждущих в `recvq` (нулевое значение, `ok=false`); отправка в закрытый канал — паника.

Источник: [`runtime/chan.go`](https://github.com/golang/go/blob/master/src/runtime/chan.go)
(`hchan.sendq`/`recvq` — `waitq` из `sudog`, `chansend`/`chanrecv`, прямая передача в `send`/`recv`).

## 📎 Разбор: почему роутер ServeMux — это дерево, а не map

С Go 1.22 `http.ServeMux` понимает паттерны с переменными: `GET /users/{id}/posts`. При запросе
`/users/42/posts` надо найти подходящий паттерн, где часть сегментов — **wildcards**, и при
нескольких совпадениях выбрать **самый конкретный** (литерал важнее переменной).

- **`map[string]Handler` по полному пути?** Не работает: `/users/42/posts` не равно строке
  `/users/{id}/posts` — хеш конкретного пути не найдёт паттерн с переменной. Пришлось бы перебирать
  **все** паттерны и матчить каждый — O(число паттернов) на запрос.
- **Дерево по сегментам пути** решает это естественно: каждый уровень — один сегмент. На литеральный
  сегмент спускаемся через `map[сегмент]узел` (O(1)); нет литерала — пробуем **wildcard-ребёнка**
  (`{id}`). Спуск идёт за длину пути, а не за число паттернов, и приоритет «литерал раньше wildcard»
  встроен в порядок проверки. Это то же префиксное дерево ([Trie](trie-structure.md)), только рёбра —
  целые сегменты пути, а не символы.

Суть (`net/http/routing_tree.go`, `routingNode` — упрощённо):

```go
type node struct {
    handler  Handler          // непусто только в листе (конец паттерна)
    children map[string]*node // литеральный сегмент → ребёнок
    wildcard *node            // ребёнок-переменная {id} (emptyChild в оригинале)
}

func (n *node) match(segs, vals []string) (Handler, []string) {
    if len(segs) == 0 {
        return n.handler, vals // дошли до листа — вот обработчик
    }
    seg := segs[0]
    if c, ok := n.children[seg]; ok { // 1) сперва точный литерал
        if h, v := c.match(segs[1:], vals); h != nil {
            return h, v
        }
    }
    if n.wildcard != nil {            // 2) иначе переменная, запоминаем значение
        return n.wildcard.match(segs[1:], append(vals, seg))
    }
    return nil, nil
}
```

Паттерны `/users/{id}`, `/users/me/posts` и `/posts/{id}` в одном дереве — в виджете ниже: у
`users` два ребёнка, литерал `me` (за ним `posts` с обработчиком `/users/me/posts`) и
wildcard-ребёнок `{id}` (обработчик `/users/{id}`). Листай «›»: запрос спускается по дереву
**сегмент за сегментом** — сперва точный литерал, потом wildcard. Видно, как `/users/me/posts`
идёт через литерал `me` (литерал победил `{id}`); поменяй запрос на `/users/42` — литерала `42`
нет, и тот же путь поймает wildcard с захватом `id=42`:

## 📎 Разбор: почему slices.Sort — это гибрид трёх сортировок

`slices.Sort` / `sort.Sort` должны быть быстрыми на **любых** входах — случайных, уже
отсортированных, почти отсортированных и «злых» (специально подобранных против quicksort). Одной
сортировки для этого мало:

- **Чистый quicksort?** В среднем O(n log n) и отличный кэш, но на неудачном опорном (или на входе,
  подобранном врагом) деградирует до **O(n²)**.
- **Чистый merge sort?** Гарантированные O(n log n), но **O(n) лишней памяти** и медленнее на мелочи.
- **Чистый heap sort?** O(n log n) и на месте, но прыгает по памяти — **плохой кэш**.

Go берёт **pdqsort** (pattern-defeating quicksort) — introsort с тремя защитами:

- куски **≤ 12 элементов** — insertion sort (на мелочи он быстрее из-за нулевых накладных);
- основной проход — quicksort с умным опорным (медиана, «нинтер») и **ломанием паттернов**, чтобы
  уже-отсортированные и одинаковые входы не роняли его в O(n²);
- счётчик плохих разбиений `limit`: как только опорные выбираются слишком неудачно — **переключение
  на heap sort**, что даёт **гарантию O(n log n)** в худшем случае.

Скелет (`slices/zsortordered.go`, `pdqsortOrdered`):

```go
func pdqsort(data []E, a, b, limit int) {
    const maxInsertion = 12
    for b-a > maxInsertion {
        if limit == 0 {
            heapSort(data, a, b) // слишком много плохих опорных → гарантия O(n log n)
            return
        }
        mid := partition(data, a, b) // как в quicksort; при «паттерне» опорный ломается
        // рекурсия в меньшую половину, итерация по большей; limit-- на плохом разбиении
    }
    insertionSort(data, a, b) // хвост из ≤ 12 элементов
}
```

Основа — тот же `partition` из quicksort; покрути его вживую:

<div class="algo-viz" data-viz="quick-sort" data-array="7,2,9,4,3,8,1,5"></div>

Так `slices.Sort` совмещает лучшее: скорость и кэш quicksort, гарантию heap sort и дешевизну
insertion на мелочи — и не роняется ни на «злом», ни на уже отсортированном входе.

Источник: [`slices/zsortordered.go`](https://github.com/golang/go/blob/master/src/slices/zsortordered.go)
(`pdqsortOrdered`, `maxInsertion = 12`, fallback `heapSortOrdered`).

## 📎 Разбор: почему map с Go 1.24 — это Swiss Tables

`map` обязан быть **очень** быстрым — это базовая структура языка. До Go 1.23 он был таблицей с
**цепочками** (бакет + overflow-бакеты по указателям). С Go 1.24 — **Swiss Tables**: open addressing
группами по 8 слотов с **control-словом**.

- **Цепочки?** Коллизия — новый узел по указателю. Но это аллокации overflow-бакетов и **погоня за
  указателями** (каждый прыжок — потенциальный промах кэша).
- **Swiss Tables** держат рядом **control-слово** — по байту `h2` (младшие 7 бит хеша) на каждый из
  8 слотов группы. Поиск: вычислить `h2` и **одним сравнением** (`matchH2`) найти сразу все слоты
  группы с этим `h2` — кандидатов; затем сверить настоящий ключ только у них. Control-слово и слоты
  лежат в одной-двух кэш-линиях — почти без промахов.

Скелет (`internal/runtime/maps`):

```go
func (t *table) get(key K) (V, bool) {
    h := hash(key)
    g := &t.groups[h1(h)%len(t.groups)]    // группа из 8 слотов
    h2 := h2(h)                            // младшие 7 бит хеша
    for _, i := range g.ctrl.matchH2(h2) { // 1 сравнение → все кандидаты
        if g.slot[i].key == key {          // сверяем сам ключ
            return g.slot[i].val, true
        }
    }
    return zero, false
}
```

Листай «›»: `h2` сравнивается со всеми 8 control-байтами **разом**, кандидаты подсвечиваются;
затем сверяется ключ (иногда `h2` совпал по редкой 7-битной коллизии — тогда идём к следующему):

<div class="algo-viz" data-viz="swiss-lookup" data-ctrls="42,7,-,42,13,99,-,5" data-h2="42" data-hit="3"></div>

Выигрыш — не в асимптотике (она та же, O(1) в среднем), а в **константе**: одно параллельное
сравнение вместо цепочки прыжков по указателям, и данные в кэше. Тот самый «за Big-O прячется
константа» из [«Хеш-таблицы»](hash-table-structure.md).

Источник: [`internal/runtime/maps`](https://github.com/golang/go/tree/master/src/internal/runtime/maps)
(`matchH2`, `ctrls`, `SwissMapGroupSlots = 8`).

## 📎 Разбор: почему пул соединений — это список + map (LRU)

HTTP-клиент переиспользует TCP-соединения (keep-alive): после запроса соединение не закрывается, а
кладётся в пул «праздных». Требования: быстро **взять** праздное к нужному хосту, быстро **вернуть**,
и при переполнении (`MaxIdleConns`) **выбросить самое давнее** — то есть LRU.

- **Только map?** O(1) по ключу, но «самое давнее» не найти — нет порядка.
- **Только список?** Есть порядок (свежие — в начало, старые — в конец), но поиск конкретного
  соединения — O(n).
- **Двусвязный список + map** (классический LRU): map даёт O(1) доступ к узлу списка, а список
  держит порядок по давности. Взяли/вернули — переставили узел в начало за O(1) (перецепили
  `.Next`/`.Prev`); переполнилось — сняли хвост (самый давний) за O(1).

Именно так устроен `idleLRU` в `net/http.Transport`: `connLRU` — это `container/list` (двусвязный)
плюс map от соединения к его элементу списка. `add` кладёт в начало, `removeOldest` снимает хвост.

Покрути вживую ровно эту связку — map + двусвязный список: `get` переставляет узел в голову,
переполнение снимает хвост, всё за O(1) (тот же приём, что в `connLRU`):

## 📎 Разбор: почему sort.Search — это бинпоиск по предикату

Искать нужно не только в массиве чисел, а в **любой монотонной** последовательности «нет…нет, да…да»:
первый элемент ≥ x, минимальная скорость Коко, наименьшая ёмкость корабля. `sort.Search` обобщает
бинпоиск до **предиката** `f(i)`.

- **Линейный поиск?** O(n) — на больших `n` недопустимо.
- **`sort.Search(n, f)`** сужает `[i, j)`, пока не найдёт **границу** между `f==false` и `f==true`.
  Инвариант `f(i-1)==false, f(j)==true` держится на каждом шаге, а середина считается **без
  переполнения**: `h := int(uint(i+j) >> 1)`.

Это тот же `firstTrue` из главы [«Модифицированный бинарный поиск»](modified-binary-search.md), только середина считается сдвигом:

```go
func Search(n int, f func(int) bool) int {
    i, j := 0, n
    for i < j {
        h := int(uint(i+j) >> 1) // середина без переполнения
        if !f(h) {
            i = h + 1 // f(i-1)==false сохраняется
        } else {
            j = h     // f(j)==true сохраняется
        }
    }
    return i // первый индекс, где f истинно
}
```

`sort.SearchInts` и её соседи для `float64` и строк построены поверх `sort.Search`, а `slices.BinarySearch` повторяет тот же цикл у себя (встроенный, без вызова функции-предиката: так быстрее).
Ниже — тот же поиск границы в другой, «закрытой» записи: `left <= right`, найденное запоминаем в
`res` и продолжаем искать левее (`right = mid − 1`). Если `target` в массиве есть, ответ тот же —
первый индекс, где `arr[i] ≥ target`; если нет, этот вариант вернёт `−1`, а `sort.Search` — место
вставки. Сравни, как по-разному два варианта хранят инвариант:

Источник: [`sort/search.go`](https://github.com/golang/go/blob/master/src/sort/search.go)
(`Search`, инвариант `f(i-1)==false, f(j)==true`).

## 📎 Разбор: почему порядок инициализации переменных — это топосорт

Переменные уровня пакета можно объявлять в любом порядке, но **инициализировать** надо так, чтобы
зависимость шла раньше зависящего: `var a = b + 1; var b = 2` → сперва `b`, потом `a`. Компилятор
строит **граф зависимостей** и укладывает его **топологически**.

- **Просто по порядку в файле?** Сломается: `a` объявлена раньше `b`, но зависит от неё.
- **Топологическая сортировка** графа даёт порядок, где каждая переменная инициализируется после
  всех, от которых зависит. Есть **цикл** (`a=b; b=a`) — валидного порядка нет, компилятор выдаёт
  ошибку (ровно «топосорт уложил не все вершины» из главы). `go/types` ведёт это через кучу — для
  детерминированного порядка.

## 📎 Разбор: почему context.Context — это дерево отмены

В обработчике HTTP-запроса запускается куча подзадач: запрос в БД, вызов другого сервиса, чтение из
кэша. Если клиент отключился или вышел таймаут — **всю эту работу надо свернуть разом**, иначе горутины
и соединения утекут. Требование: одним сигналом отменить целую ветку связанных операций.

- **Флаг `bool` «отменено»?** Каждую подзадачу надо опрашивать вручную, вложенность не учитывается,
  таймауты не складываются.
- **`context.Context` образует ДЕРЕВО.** `WithCancel`/`WithTimeout`/`WithDeadline` создают **дочерний**
  контекст; каждый дочерний регистрируется у родителя (`c.children`). Отмена или таймаут узла вызывает
  `cancel()`, который **перебирает `c.children` и отменяет каждого** — каскадом вниз по поддереву.
  Родитель и соседи не затронуты.

<div class="algo-viz" data-viz="context-tree"></div>

Ключевое свойство — **отмена течёт только вниз**: отменили `req` (по таймауту) — свернулись `db` и
`http` под ним, а сосед `req2` и родитель `srv` живут дальше. Подзадача узнаёт об отмене, слушая канал:

```go
ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
defer cancel() // ОБЯЗАТЕЛЬНО: иначе контекст и его таймер утекут

select {
case res := <-doWork(ctx):   // работа с тем же ctx
    return res
case <-ctx.Done():           // отменили/таймаут → сворачиваемся
    return ctx.Err()         // context.Canceled или context.DeadlineExceeded
}
```

Правила, вытекающие из этого дерева: **всегда `defer cancel()`** (иначе утечка узла и его таймера);
**пробрасывай `ctx` первым аргументом** во все блокирующие вызовы (`db.QueryContext(ctx, …)`,
`http.NewRequestWithContext`); **не клади в контекст бизнес-данные** — только request-scoped (id запроса,
дедлайны, трейс).

Источник: [`context/context.go`](https://github.com/golang/go/blob/master/src/context/context.go)
(`cancelCtx.children`, `propagateCancel`, `cancel` перебирает `c.children`).

## 📎 Разбор: почему sync.Pool срезает нагрузку на GC

Сервер на каждый запрос создаёт временные буферы (JSON-энкодер, `bytes.Buffer`, срезы). Тысячи
запросов в секунду → миллионы короткоживущих аллокаций → **GC работает без передышки** (см.
[Go-рантайм](go-runtime.md) и [приложение о памяти](appendix-go-memory.md)). Хочется **переиспользовать**
буферы между запросами, а не аллоцировать заново.

- **Свой список свободных объектов + мьютекс?** Работает, но мьютекс на каждый Get/Put — точка раздора
  под нагрузкой, и чистить надо самому.
- **`sync.Pool`** — пул переиспользуемых объектов: `Get()` берёт готовый из пула (аллокации нет) или
  создаёт новый через `New`; `Put()` возвращает объект обратно. Внутри — **отдельный пул на каждый P**
  (логический процессор), поэтому быстрый путь без блокировок. При GC пул не пропадает сразу:
  он уезжает в запасной `victim` и выбрасывается только на следующем GC.

<div class="algo-viz" data-viz="sync-pool" data-ops="get,get,put,put,get,put,gc,get,gc,get"></div>

Пока в пуле есть объекты, `Get` их переиспользует — каждая такая операция это **аллокация, которой не
было**, и на столько же меньше работы сборщику. Пул опустел → `Get` зовёт `New`. Классический паттерн:

```go
var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}

func handler(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()            // объект «грязный» от прошлого использования — чистим
    defer bufPool.Put(buf) // вернуть в пул после работы
    // ...используем buf...
}
```

Две оговорки прямо из устройства пула:

- **Пул — это кэш, а не хранилище.** GC его очищает (объекты живут ~пару циклов в victim-кэше), и `Get`
  может в любой момент вернуть свежий `New`. Нельзя класть туда то, что обязано сохраниться.
- **Объект из пула «грязный».** Его использовали до тебя — всегда `Reset()` перед работой, иначе
  утащишь чужие данные.

`sync.Pool` уместен для **частых короткоживущих** объектов (буферы, парсеры); для долгоживущих или
уникальных бесполезен. Так делают `encoding/json`, `net/http`, `fmt` — переиспользуют внутренние буферы
через пулы.

Источник: [`sync/pool.go`](https://github.com/golang/go/blob/master/src/sync/pool.go)
(`Pool.Get`/`Put`, per-P `local`, `victim`, `poolCleanup` при GC).

## 📎 Разбор: почему regexp в Go линеен (RE2), а не экспоненциален

Многие regex-движки (PCRE в PHP/Python/JS) используют **бэктрекинг**: пробуют один путь, при неудаче
откатываются и пробуют другой. На «злом» шаблоне вроде `(a+)+$` и строке из десятков `a` это взрывается
**экспоненциально** — знаменитая уязвимость **ReDoS** (regex denial of service), кладущая сервис одной
строкой ввода.

Go `regexp` устроен иначе — это **RE2 (Thompson NFA)**, и документация гарантирует **линейное время**:
«guaranteed to run in time linear in the size of the input… without the expense of backtracking».

- **Бэктрекинг** идёт по одному пути и откатывается — число путей может расти как 2ⁿ.
- **RE2** держит **множество активных состояний** автомата и читает вход по символу: из каждого
  активного состояния берёт все переходы. Размер множества **не превышает числа состояний**, поэтому
  один проход по строке — линейно, независимо от шаблона.

<div class="algo-viz" data-viz="nfa-match" data-input="abcc"></div>

Обрати внимание на шаг с `c`: активны **сразу два** состояния — «ещё в цикле `(b|c)*`» и «это финальная
`c`». Бэктрекинг перебирал бы эти варианты по очереди (и мог бы застрять), а RE2 держит их одновременно и
не возвращается. Поменяй ввод на `abcb` — финальное состояние не активно, строка не подходит.

Цена: RE2 не поддерживает обратные ссылки (`\1`) и lookaround — их нельзя выразить конечным автоматом.
Зато никакого ReDoS: **пользовательский ввод в Go-regexp безопасен по времени**, чего не скажешь про
движки с бэктрекингом.

Это прямое продолжение [строковых алгоритмов](string-algorithms.md): KMP — тоже конечный автомат по
образцу; RE2 обобщает идею на произвольные регэкспы.

Источник: [`regexp`](https://pkg.go.dev/regexp) («linear in the size of the input»),
[`regexp/syntax`](https://pkg.go.dev/regexp/syntax); теория — RE2 (Russ Cox, «Regular Expression Matching
Can Be Simple And Fast»).

## 📎 Разбор: почему errgroup — это структурная конкурентность

Обработчику надо параллельно сходить в 3 источника (БД, HTTP-сервис, кэш) и собрать результат. Упал
один — остальные продолжать бессмысленно, надо **быстро отменить их и вернуть ошибку**. Голыми
горутинами это муторно: свой `WaitGroup`, канал ошибок, ручная отмена — легко получить гонки.

`golang.org/x/sync/errgroup` инкапсулирует этот паттерн поверх
[context](go-stdlib-structures.md#-разбор-почему-contextcontext--это-дерево-отмены):

- `g, ctx := errgroup.WithContext(parent)` — общий дочерний `ctx` на всю группу.
- `g.Go(fn)` — запускает подзадачу в своей горутине.
- **Первая же вернувшая ошибку** подзадача отменяет общий `ctx`; остальные видят `<-ctx.Done()` и
  сворачиваются, не делая лишнюю работу.
- `g.Wait()` дожидается всех и возвращает **первую** ошибку.

<div class="algo-viz" data-viz="errgroup"></div>

Это **fail-fast fan-out**: `db` успел, `http` упал → его ошибка отменяет группу → `cache` сворачивается,
не доделав; `Wait()` возвращает ошибку `http`. Без errgroup та же логика — ручной `WaitGroup` + `sync.Once`
для первой ошибки + `context.CancelFunc`, и всё это легко написать с гонками.

```go
g, ctx := errgroup.WithContext(r.Context())
results := make([]Data, len(sources))
for i, src := range sources {
    i, src := i, src
    g.Go(func() error {
        d, err := fetch(ctx, src) // ОБЯЗАТЕЛЬНО принимает ctx
        results[i] = d
        return err
    })
}
if err := g.Wait(); err != nil {
    return err // остальные подзадачи уже отменены
}
```

`g.SetLimit(n)` ограничивает число одновременных горутин (bounded fan-out) — чтобы не запустить тысячу
запросов разом. Подзадачи **обязаны** принимать и слушать `ctx`, иначе отмена не сработает и группа будет
ждать зависшую.

Источник: [`golang.org/x/sync/errgroup`](https://pkg.go.dev/golang.org/x/sync/errgroup) — поверх `context`
и `sync.WaitGroup`.

## 📎 Разбор: почему atomic (CAS) обходится без мьютекса

Инкремент счётчика из нескольких горутин (`counter++`) — это гонка: `counter++` не атомарен (read →
+1 → write), два потока затрут друг друга, обновление потеряется. Мьютекс решает, но на **очень частом
и коротком** обновлении лок дорог. Альтернатива — **лок-free** через `sync/atomic`.

Сердце подхода — **Compare-And-Swap**: аппаратная инструкция «поменяй значение на new, но только если
оно всё ещё old». Инкремент строится как цикл optimistic concurrency:

<div class="algo-viz" data-viz="cas-loop"></div>

- Читаем текущее значение (`old`), считаем `old+1`.
- `CompareAndSwap(old, old+1)`: если между чтением и CAS никто не влез — успех. Если влез (значение уже
  не `old`) — CAS **проваливается**, перечитываем и повторяем.
- Так оба инкремента доходят (`5 → 6 → 7`) без потерь и без блокировки: проигравший в гонке просто
  повторяет с актуальным значением.

```go
var counter atomic.Int64
counter.Add(1)                    // готовый атомарный +1 — этого хватает для счётчика
// а вот общий паттерн CAS-цикла (для нетривиальных обновлений):
for {
    old := counter.Load()
    if counter.CompareAndSwap(old, old+1) {
        break
    }
}
```

Для простого счётчика хватает `atomic.Add`; CAS-цикл нужен, когда новое значение — **функция** от
старого сложнее, чем `+delta` (лок-free стеки, очереди, флаги состояния). На том же CAS построен и
`sync.Mutex` ([разбор](go-stdlib-structures.md#-разбор-почему-syncmutex--это-биты-в-одном-слове) — CAS
по биту `locked`).

Оговорка: лок-free выигрывает при **низкой** конкуренции; при высокой CAS-цикл крутится вхолостую (много
провалов), и мьютекс может оказаться лучше. Меряй (`go test -bench`, `-race`), а не угадывай.

Источник: [`sync/atomic`](https://pkg.go.dev/sync/atomic) (`Int64.CompareAndSwap`/`Add`/`Load`).

## 📎 Разбор: почему sync.Once инициализирует ровно один раз

Ленивая инициализация из многих горутин — классическая ловушка: «проверил флаг, не готово —
инициализирую» под нагрузкой запускает init **несколько раз** (или отдаёт недоинициализированный объект).
Нужен гарант: `f` выполнится **ровно один раз**, а остальные вызовы дождутся результата.

`sync.Once` делает это через **double-checked locking**, соединяя [atomic](go-stdlib-structures.md#-разбор-почему-atomic-cas-обходится-без-мьютекса)
(быстрый чек) и [мьютекс](go-stdlib-structures.md#-разбор-почему-syncmutex--это-биты-в-одном-слове)
(гарант единственности):

<div class="algo-viz" data-viz="sync-once"></div>

- **Быстрый путь:** атомарно читаем флаг `done`. Уже инициализировано → сразу выходим (один дешёвый Load).
- **Медленный путь** (первый раз): берём мьютекс, **ещё раз** проверяем `done` (вдруг кто-то успел между
  чтением и локом), выполняем `f`, ставим `done`.
- Параллельные `Do()` во время init уже прошли быстрый чек и ждут на мьютексе; получив его, они
  выходят через **повторную** проверку `done` — ради них она и нужна. По быстрому пути без лока уходят
  только вызовы, пришедшие после init.

Итог: `init` запускается **ровно один раз** независимо от числа горутин, а «горячая» проверка после
инициализации — всего один атомарный Load, без блокировок.

```go
var (
    once sync.Once
    cfg  *Config
)
func Config() *Config {
    once.Do(func() { cfg = loadConfig() }) // выполнится один раз на всю программу
    return cfg
}
```

Применение: ленивый синглтон, загрузка конфига, компиляция regexp, установка соединения. Оговорка: если
`f` **паникует**, `Once` всё равно считает попытку сделанной (`done` ставится через `defer`) — повторного
запуска не будет; для повтора при ошибке нужен свой механизм.

Источник: [`sync/once.go`](https://github.com/golang/go/blob/master/src/sync/once.go)
(`done atomic.Bool`, `m Mutex`, `Do`/`doSlow` — double-checked locking).

## 📎 Разбор: почему defer — это LIFO-стек

`defer` откладывает вызов до выхода из функции — им закрывают файлы, отпускают локи, пишут трейсы.
Порядок неочевиден: несколько `defer` выполняются **в обратном порядке** объявления. Почему?

Рантайм держит отложенные вызовы [**стеком**](recursion.md) на горутине (`gp._defer` — связанный список,
каждый новый defer встаёт в голову). На `return` **или panic** стек разворачивается сверху вниз:
последний отложенный — первым.

<div class="algo-viz" data-viz="defer-stack"></div>

Это ровно то, что нужно для **вложенных ресурсов**: открыл файл → залочил → подключился; закрывать надо в
**обратном** порядке (отключиться → разлочить → закрыть файл), иначе разлочишь мьютекс, который ещё нужен.
LIFO делает это автоматически:

```go
f, _ := os.Open(name)
defer f.Close()        // выполнится ПОСЛЕДНИМ
mu.Lock()
defer mu.Unlock()      // выполнится вторым
conn, _ := dial()
defer conn.Close()     // выполнится ПЕРВЫМ
```

Две тонкости, на которых спотыкаются:

- **Аргументы defer вычисляются в момент `defer`, а не вызова.** `defer log(x)` запомнит *текущее* `x`;
  чтобы взять финальное значение — оберни в замыкание: `defer func() { log(x) }()`.
- **defer в цикле копится до конца функции**, а не итерации: `for … { f, _ := os.Open(...); defer f.Close() }`
  откроет тысячу файлов и закроет их все разом в конце. В цикле закрывай явно или выноси тело в функцию.

Ключевое: defer срабатывает **и при panic** — раскрутка стека выполняет отложенные вызовы, а `recover()`
в одном из них ловит панику. Поэтому очистка через defer надёжна даже на аварийном пути.

Источник: [`runtime/panic.go`](https://github.com/golang/go/blob/master/src/runtime/panic.go)
(`_defer`, `gp._defer`, `d.link` — стек defer; open-coded defers как оптимизация).

## 📎 Разбор: почему append амортизированно O(1) (рост среза)

Срез (`slice`) — это указатель на backing-массив + `len` + `cap`. `append` добавляет элемент, но массив
фиксированного размера, и когда `len == cap`, места нет. Наивное «расширять на +1» давало бы на каждый
append копирование всего — суммарно O(n²). Go растит **геометрически**.

<div class="algo-viz" data-viz="dynarray" data-n="9"></div>

- Пока `len < cap` — append просто кладёт элемент в запас: **O(1)**.
- Когда `len == cap` — выделяется **новый массив вдвое больше** (для малых срезов), старые элементы
  копируются, и только тогда добавляется новый.
- Удвоения редки (cap: 1 → 2 → 4 → 8…), а между ними — дешёвые вставки. Сумма копирований за `n` append —
  это `1 + 2 + 4 + …` < `2n`, поэтому на один append приходится в среднем **константа**. Это и есть
  [амортизированный анализ](big-o.md) из главы Big-O — вживую.

Практические следствия:

- **Знаешь итоговый размер — задай cap заранее:** `make([]T, 0, n)`. Тогда ни одного перевыделения и
  копирования — заметно быстрее в горячем коде.
- **`append` может вернуть НОВЫЙ массив.** После роста срезы, указывавшие на прежний backing, «отвязываются»
  — поэтому результат `append` всегда присваивают обратно: `s = append(s, …)`.
- Для больших срезов (cap ≥ 256) Go растит не ×2, а **≈×1.25** — компромисс между запасом памяти и числом
  копирований.

Источник: [`runtime/slice.go`](https://github.com/golang/go/blob/master/src/runtime/slice.go)
(`growslice`: `doublecap`, порог 256, для больших `newcap += (newcap + 3*256) >> 2`).

## 📎 Разбор: почему encoding/json — это reflection

`json.Marshal(v)` сериализует **любой** тип — структуру, срез, map — одной функцией. Но Go статически
типизирован: как одна функция работает с типом, которого не знала при компиляции? Ответ — **рефлексия**:
`reflect` позволяет в рантайме узнать тип значения, перечислить поля, прочитать теги и значения.

<div class="algo-viz" data-viz="json-marshal"></div>

Обход структуры:

- `reflect.TypeOf(v)` даёт описание типа; `t.NumField()` / `t.Field(i)` перечисляют поля.
- Имя ключа берётся из **тега** `json:"name"` (а не из имени поля Go); опция `omitempty` пропускает пустые
  значения; `json:"-"` исключает поле.
- `reflect.ValueOf(v).Field(i)` достаёт значение поля, оно кодируется рекурсивно.

Именно рефлексия делает `encoding/json` универсальным. Цена — **скорость**: инспекция типа в рантайме
дороже прямого кода. Поэтому `encoding/json` кэширует разбор структуры (`typeFields`), а на горячих путях
берут кодогенерацию (`easyjson`, `ffjson`) или ускоренные парсеры (`jsoniter`, `sonic`), где marshaler
сгенерирован под конкретный тип и рефлексии нет.

Практические следствия рефлексии и тегов:

- **Сериализуются только публичные поля** (с большой буквы): `reflect` не видит приватных, `json` их
  молча пропускает — частый сюрприз с «пропавшими» полями.
- **Теги — это контракт API:** `json:"user_id"` фиксирует имя в JSON независимо от имени поля Go.
- **`omitempty`** убирает пустые значения из вывода — но `0`, `false`, `""` тоже считаются «пустыми».

Источник: [`encoding/json`](https://pkg.go.dev/encoding/json), [`reflect`](https://pkg.go.dev/reflect)
(`Type.Field`, `StructTag.Get`, `Value.Field`; кэш полей — `typeFields`).

## 📎 Разбор: почему «блокирующий» conn.Read() масштабируется (netpoll → epoll)

Самая недооценённая магия рантайма Go. Ты пишешь **простой блокирующий** код — `n, err := conn.Read(buf)`
— а сервер держит **сотни тысяч** одновременных соединений на горстке потоков ОС. Как?

**Проблема.** «Блокирующий Read = поток ОС ждёт» не масштабируется: 100k соединений = 100k потоков, а
поток — это килобайты-мегабайты стека и дорогие переключения контекста в ядре. Классическое решение
(C/nginx/Node) — **epoll + event loop**: один поток следит за тысячами сокетов и дёргает колбэки на
готовность. Быстро, но код превращается в лапшу из колбэков. Go хочет **и то, и другое**: простой
последовательный код *и* масштаб event-loop. Секрет — рантайм **прячет event-loop внутри планировщика**.

<div class="algo-viz" data-viz="netpoll"></div>

Как это работает по шагам:

1. **fd — неблокирующий и уже в epoll.** Сокет ставится в **неблокирующий** режим (`SetNonblock`),
   и **один раз, при создании соединения**, рантайм регистрирует его в epoll (Linux; kqueue на
   BSD/macOS, IOCP на Windows) — сразу на чтение и запись, в режиме edge-triggered. `Read` на пустом
   сокете не усыпляет поток, а сразу возвращает `EAGAIN` («данных нет»).
2. **Нет данных → парковка горутины.** Поймав `EAGAIN`, рантайм ничего не регистрирует — только
   записывает горутину ждущей в дескриптор fd и **паркует её** (`netpollblock` → `gopark`), снимая с
   потока `M`. Горутина «спит», но **поток свободен**.
3. **Поток берёт другую работу.** Освободившийся `M` идёт в планировщик и выполняет **другую готовую
   горутину**. Тысячи припаркованных на I/O горутин — но заняты лишь `GOMAXPROCS` потоков.
4. **Данные пришли → epoll помечает fd готовым** (ядро уведомляет epoll).
5. **Планировщик будит горутину.** В цикле поиска работы (`findRunnable`) планировщик периодически зовёт
   `netpoll()`: тот спрашивает epoll о готовых fd и через `goready` возвращает горутины **обратно в
   очередь**. Если другой работы нет — `netpoll` вызывается **блокирующе**, и поток спит прямо в
   `epoll_wait`, а не крутится вхолостую.
6. **Read возвращает данные.** Разбуженная горутина снова получает поток, `Read` дочитывает. Для твоего
   кода это был обычный блокирующий вызов — всю асинхронность рантайм скрыл.

**Почему это важно:**

- **Простота без потери масштаба.** Никаких колбэков и async/await — последовательный код, а под капотом
  epoll. Ключевая причина, почему на Go удобно писать сетевые сервисы.
- **Дёшево на соединение.** Спящая горутина — это несколько КБ стека и запись в epoll, а не поток ОС.
- **Единый механизм.** Та же парковка/пробуждение — у таймеров ([куча](go-stdlib-structures.md#-разбор-почему-таймеры-go--это-куча-а-не-список-и-не-map))
  и каналов; netpoll — часть [планировщика GMP](go-runtime.md).

Оговорка: netpoll — про **сетевые сокеты и пайпы**. Обычные файлы через epoll не следятся, поэтому
блокирующий `read` файла занимает поток; на застрявший в syscall `M` у планировщика есть **sysmon**,
который отбирает у него `P` и отдаёт другому потоку (чтобы остальные горутины не стояли).

Источник: [`runtime/netpoll.go`](https://github.com/golang/go/blob/master/src/runtime/netpoll.go)
(`netpoll`, `netpollblock`/`gopark`, `goready`), интеграция —
[`runtime/proc.go`](https://github.com/golang/go/blob/master/src/runtime/proc.go) (`findRunnable` зовёт
`netpoll`), неблокирующие fd — `internal/poll`.

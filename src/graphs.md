## 🧭 Откуда берётся обход графа: выведем его сами

Задача: города соединены дорогами, и все города, связанные хоть через кого-то, — одна
**провинция**. Сколько провинций? Город — **вершина** графа, дорога — **ребро**.

Пять городов: треугольник `0–1–2` и пара `3–4`. Глазами видно — провинций две.

<div class="algo-fig" data-fig="graph" data-nodes="0,1,2,3,4" data-edges="0-1,0-2,1-2,3-4" data-caption="Пять городов: треугольник 0–1–2 и пара 3–4 — две провинции"></div>

В лоб: встань в город и гуляй по дорогам — к соседям, от них к их соседям, пока есть куда.
Все, до кого дошёл, — твоя провинция. И так из каждого города.

Беда первая: прогулка без памяти не кончается. `0 → 1 → 0 → 1 → …` — дорога двусторонняя,
по ней можно ходить туда-обратно вечно. Нужна пометка «здесь я уже был» — `visited`.

Беда вторая: если у каждой прогулки своя пометка, провинцию `0–1–2` найдут трижды — из `0`,
из `1` и из `2`. Заходов в города `3 + 3 + 3 + 2 + 2 = 13`, а городов всего 5; потом ещё
выбрасывать одинаковые провинции.

Лекарство — одна пометка на все прогулки. Город уже помечен — его провинцию уже посчитали,
пропускаем. Прогулок остаётся две, из `0` и из `3`, заходов в города — ровно 5.

**Обход графа — это «Заливка» в Paint: одна заливка закрашивает всю провинцию, закрашенное
второй раз не заливают, и число заливок — это ответ.**

Прогулка с общей пометкой — это **обход графа**, а число её запусков — число **компонент
связности**. Дальше — как граф лежит в коде и в каком порядке заливать; одна заливка из
вершины `0` на графе побольше — в виджете под ними.

### Как граф лежит в коде

Рисунок с кружками — для человека. Коду нужен ответ на один вопрос: **кто соседи у вершины `u`?**
Его и храним — по срезу соседей на каждую вершину. Это называется **список смежности**:

<div class="algo-fig" data-fig="graph" data-nodes="0,1,2,3,4" data-edges="0-1,0-2,1-2,3-4" data-adj data-caption="Тот же граф и его список смежности. Наведи на вершину или строку adj — загорятся её рёбра и соседи"></div>

```go
adj := make([][]int, n)        // adj[u] — соседи вершины u
for _, e := range edges {      // ребро — пара [u, v]
    u, v := e[0], e[1]
    adj[u] = append(adj[u], v)
    adj[v] = append(adj[v], u) // дорога двусторонняя — пишем в обе стороны
}
```

Здесь рёбра `edges` — `[0,1]`, `[0,2]`, `[1,2]`, `[3,4]`, в этом порядке. Дорога `0–1` записана
дважды: у `0` в соседях `1`, у `1` в соседях `0`. Забудешь вторую строку — из города `1` дороги
назад не будет, и провинции посчитаются неверно. Во всех листингах главы `adj` — именно это.

### В каком порядке заливать: в ширину или в глубину

Заливка не говорит, какого соседа красить следующим. Вариантов два, и вся разница между ними —
одна структура данных.

- **В ширину (BFS):** найденные вершины ждут в **очереди** — кого раньше нашли, того раньше
  обработали. Получается волна: сначала все соседи старта, потом соседи соседей.
- **В глубину (DFS):** найденные ждут в **стеке** (обычно это стек вызовов рекурсии) — идём от
  последней найденной, пока есть куда, потом возвращаемся к развилке.

Закрасят оба одно и то же — всю провинцию. Поэтому «сколько групп», «связаны ли», «острова»
решаются любым; бери тот, что короче пишется, — обычно это рекурсивный DFS.

Разница появляется в одном вопросе: **за сколько шагов?** Волна доходит до вершины кратчайшей
дорогой — раньше, чем любой окольной. DFS может прийти туда же длинным путём, и число его шагов
ничего не значит.

| Что спрашивает задача | Что брать | Почему |
|---|---|---|
| сколько групп, можно ли дойти, «острова» | любой; короче — DFS | важен факт «дошли», а не порядок |
| **кратчайший** путь, минимум ходов | только BFS | волна первой приходит по кратчайшему пути |
| у рёбер разные веса, нужен самый **дешёвый** путь | [Дейкстра](#веса-на-рёбрах-алгоритм-дейкстры) — куча вместо очереди | волна считает рёбра, а не сумму весов |
| граф может быть цепочкой на 10⁵ вершин и длиннее | BFS или [DFS с явным стеком](#глубина-рекурсии-dfs--цена-и-предел) | рекурсия уйдёт на столько же кадров вглубь: стек растёт, а на 10⁷ упрётся в предел |
| порядок «сначала зависимости» | [следующая глава](topological-sort.md) | там нужен счётчик, а не просто пометка |

## ⚡ Шаблон для собеседования

```go
// BFS по списку смежности
func bfs(adj [][]int, start int) []int {
    visited := make([]bool, len(adj))
    queue := []int{start}
    visited[start] = true
    var order []int
    for len(queue) > 0 {
        node := queue[0]
        queue = queue[1:]
        order = append(order, node)
        for _, next := range adj[node] {
            if !visited[next] {
                visited[next] = true // помечаем ПРИ добавлении
                queue = append(queue, next)
            }
        }
    }
    return order
}
```

1. `visited[start] = true`, кладём старт в очередь;
2. извлекаем вершину, добавляем в порядок;
3. соседей кладём в очередь, помечая сразу;
4. DFS — тот же обход, только вместо очереди рекурсия: код — [ниже, в «📖 Разборе»](#обход-в-глубину-dfs).

## 📖 Разбор

**Граф** — набор вершин, соединённых рёбрами; может содержать циклы и несколько
компонент. Большинство задач сводятся к **обходу**: посетить вершины, не зайдя в одну
дважды.

### Обход в глубину (DFS)

BFS — шаблон выше. DFS делает то же самое без очереди: пометил вершину, записал её и сразу
уходит в первого непомеченного соседа, а к следующему соседу возвращается, только когда всё
достижимое из первого уже закрашено. Стек здесь — стек вызовов рекурсии.

```go
func dfs(adj [][]int, node int, visited []bool, order *[]int) {
    visited[node] = true
    *order = append(*order, node)
    for _, next := range adj[node] {
        if !visited[next] {
            dfs(adj, next, visited, order)
        }
    }
}
```

### Компоненты связности

Решение задачи из «🧭»: одна общая пометка на все заливки, а ответ — число запусков. Граф дан
списком рёбер, поэтому сначала строим `adj` — тем же циклом, что в
[«Как граф лежит в коде»](#как-граф-лежит-в-коде).

```go
func countComponents(n int, edges [][]int) int {
    adj := make([][]int, n)
    for _, e := range edges {
        u, v := e[0], e[1]
        adj[u] = append(adj[u], v)
        adj[v] = append(adj[v], u)
    }
    visited := make([]bool, n)
    count := 0
    for i := 0; i < n; i++ {
        if !visited[i] {
            count++
            var order []int
            dfs(adj, i, visited, &order)
        }
    }
    return count
}
```

### Двудольность: обход в два цвета

Граф **двудольный**, если его вершины можно раскрасить в два цвета так, что у каждого ребра
концы разного цвета. Проверяет это тот же обход: старт красим первым цветом, каждого нового
соседа — цветом, противоположным текущей вершине. Встретили уже окрашенного соседа того же
цвета, что текущая вершина, — ребро между одноцветными, граф не двудольный.

Квадрат `0–1–2–3–0` раскрашивается: `0` и `2` — первым цветом, `1` и `3` — вторым. Треугольник
`0–1–2` — нет: обход в ширину из `0` красит `1` и `2` вторым цветом, а между ними ребро. Конфликт
бывает ровно тогда, когда в графе есть цикл нечётной длины: цвета на цикле чередуются, и
вернуться в старт тем же цветом можно только за чётное число рёбер. Граф может быть несвязным — тогда
красят по компонентам, запуская обход из каждой ещё не окрашенной вершины, как в
`countComponents`.

### Сам путь, а не только длина: массив `parent`

BFS отвечает «до `5` — три ребра». Навигатору мало числа: нужен сам маршрут. Его не надо
искать вторым обходом — он уже был, его просто не записали.

Каждая вершина попадает в очередь один раз — в момент брони, и в этот момент известно, **кто её
привёл**: та вершина `node`, чьих соседей сейчас перебираем. Запишем это в `parent[next] = node`.
Возьмём граф из виджета (`0-1, 0-2, 1-3, 2-3, 2-4, 4-5`) и старт `0`:

```text
достали 0 → бронируем 1 и 2      parent[1] = 0, parent[2] = 0
достали 1 → бронируем 3          parent[3] = 1
достали 2 → 3 уже в брони; 4     parent[4] = 2
достали 3 → новых соседей нет
достали 4 → бронируем 5          parent[5] = 4
```

Теперь идём от конца: `5 → parent[5] = 4 → parent[4] = 2 → parent[2] = 0`, у старта родителя
нет (`-1`). Собрали `5, 4, 2, 0` — путь задом наперёд; разворачиваем: `0 → 2 → 4 → 5`. Путь
кратчайший по той же причине, по которой кратчайшая длина: каждый шаг по `parent` — это шаг
волны на уровень ближе к старту.

```go
func shortestRoute(adj [][]int, src, dst int) []int {
    parent := make([]int, len(adj))
    for i := range parent {
        parent[i] = -1 // у старта и недостижимых родителя нет
    }
    visited := make([]bool, len(adj))
    visited[src] = true
    queue := []int{src}
    for len(queue) > 0 {
        node := queue[0]
        queue = queue[1:]
        for _, next := range adj[node] {
            if !visited[next] {
                visited[next] = true
                parent[next] = node // кто привёл — пишем в момент брони
                queue = append(queue, next)
            }
        }
    }
    if !visited[dst] {
        return nil // волна не дошла — пути нет
    }
    var path []int
    for v := dst; v != -1; v = parent[v] {
        path = append(path, v) // от dst к src
    }
    slices.Reverse(path) // шли с конца — разворачиваем
    return path
}
```

Кратчайших путей бывает несколько: до `3` ведут и `0 → 1 → 3`, и `0 → 2 → 3`. BFS запишет тот,
по которому волна пришла первой (здесь через `1`), — оба верны, и тренажёр принимает любой
кратчайший. Почему не собирать путь сразу в нужном порядке, вставляя вершину в начало
(`append([]int{v}, path...)`)? Каждая вставка копирует весь путь: на цепочке из 2·10⁵ вершин это
~33 с против ~15 мс с разворотом (замер теста `TestShortestPathRouteScales`). Хранить в очереди
путь целиком вместо одной вершины — та же беда, ~31 с.

### Веса на рёбрах: алгоритм Дейкстры

Теперь у дорог есть длина — **вес**, например минуты в пути, и нужен самый **дешёвый** путь: с
наименьшей суммой весов, а не с наименьшим числом рёбер. Дороги пусть будут односторонними —
граф **ориентированный**, ребро `[u, v, w]` ведёт из `u` в `v` и стоит `w` (двустороннюю дорогу
записывают в обе стороны, как в `adj` выше).

**BFS здесь ошибается.** Рёбра: `0→3` весом 10 и цепочка `0→1`, `1→2`, `2→3` по 1. Волна из `0`
доходит до `3` первой — по одному ребру — и бронирует её с ценой 10. А `0 → 1 → 2 → 3` стоит
`1 + 1 + 1 = 3`. Волна считает рёбра, а веса не видит.

**Что известно наверняка.** Из `0` видны `1` за 1 и `3` за 10. Дешевле, чем за 1, до `1` не
добраться: любой другой путь уходит из `0` по ребру за 10, а веса не отрицательные — дальше путь
только дорожает. Значит, ближайшую вершину можно **закрыть** — её цена окончательна. Дальше то
же самое по кругу:

```text
кандидаты {1: 1, 3: 10}   закрываем 1 (цена 1)  → из 1: 2 за 1+1 = 2
кандидаты {2: 2, 3: 10}   закрываем 2 (цена 2)  → из 2: 3 за 2+1 = 3 < 10, улучшили
кандидаты {3: 3}          закрываем 3 (цена 3)  — ответ 3, а не 10
```

**Дейкстра — это BFS, у которого очередь пропускает вперёд того, кто ближе:** всегда раскрывай
ближайшую из ещё не закрытых вершин.

**Кто ближайшая — спрашиваем у кучи.** Искать минимум перебором всех вершин — `V` шагов на
каждую закрытую вершину, `O(V²)`; на разреженном графе из 2·10⁵ вершин это ~28 с (замер теста
`TestDijkstraScales`). Мин-куча из главы [«Куча: устройство»](heap-structure.md) отдаёт минимум
за `O(log V)`. В Go её даёт пакет `container/heap`: заводишь свой тип-срез с пятью методами —
`Len`, `Less`, `Swap` (как для сортировки) и `Push`, `Pop` (дописать и снять последний элемент), —
а `heap.Push` и `heap.Pop` сами держат порядок кучи. В кучу кладём пары «вершина, цена».

**Устаревшие записи — пропускаем.** В примере `3` попала в кучу дважды: сначала `(3, 10)`, потом
`(3, 3)`. Найти и поправить старую запись внутри кучи `container/heap` не умеет, поэтому кладут
новую, а старую отбрасывают, когда она всплывёт: достали `(3, 10)`, а `dist[3]` уже 3 — запись
устарела, `continue`. Это **ленивое удаление**. Без проверки ответ не испортится, но вершина
будет заново перебирать свои рёбра на каждую устаревшую запись: у вершины с 10⁵ улучшениями и 10⁵
исходящими рёбрами это 10¹⁰ шагов — ~7.6 с против ~60 мс (тот же тест).

```go
type item struct{ node, dist int } // запись кучи: вершина и цена, с которой её положили

type minHeap []item

func (h minHeap) Len() int           { return len(h) }
func (h minHeap) Less(i, j int) bool { return h[i].dist < h[j].dist } // наверху — самая дешёвая
func (h minHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *minHeap) Push(x any)        { *h = append(*h, x.(item)) }
func (h *minHeap) Pop() any {
    old := *h
    it := old[len(old)-1]
    *h = old[:len(old)-1]
    return it
}

// adj[u] — пары {v, w}: ребро u→v веса w
func dijkstra(adj [][][2]int, src int) []int {
    const inf = 1 << 62 // «ещё не дошли»
    dist := make([]int, len(adj))
    for i := range dist {
        dist[i] = inf
    }
    dist[src] = 0
    h := &minHeap{{node: src, dist: 0}}
    for h.Len() > 0 {
        cur := heap.Pop(h).(item) // ближайшая из незакрытых
        if cur.dist > dist[cur.node] {
            continue // устаревшая запись: вершину уже закрыли дешевле
        }
        for _, e := range adj[cur.node] {
            to, w := e[0], e[1]
            if nd := cur.dist + w; nd < dist[to] {
                dist[to] = nd // нашли путь дешевле — новая запись в кучу
                heap.Push(h, item{node: to, dist: nd})
            }
        }
    }
    return dist
}
```

Каркас — тот же BFS: вместо очереди куча, вместо «помечен ли» — «стало ли дешевле». Нужен сам
путь — тот же `parent`: пиши `parent[to] = cur.node` рядом с `dist[to] = nd` (каждое улучшение
перезаписывает родителя, последнее и верное).

**Сложность `O((V + E) log V)`.** Каждая вершина закрывается один раз и один раз перебирает свои
рёбра; каждое ребро кладёт в кучу не больше одной записи, а операция с кучей стоит `O(log V)`.

**Отрицательный вес всё ломает.** Рёбра `0→1` весом 2, `0→2` весом 3 и `2→1` весом **−2**.
Дейкстра закроет `1` первой — за 2, а настоящий путь `0 → 2 → 1` стоит `3 − 2 = 1`: «скидка»
пришла, когда вершину уже закрыли. Довод «дальше путь только дорожает» держится лишь на
неотрицательных весах. С отрицательными — [Bellman–Ford](advanced-graph-algorithms.md).

Дальше — [«Сетки и кратчайшие пути»](grids-and-shortest-paths.md) (Дейкстра на виджете и сетка
как граф) и [«Графы: продвинутые»](advanced-graph-algorithms.md) (Bellman–Ford, A*); там же пакет
`dijkstra`, где эта функция зовётся `ShortestPathsFrom`.

## 🧠 Почему это корректно

Граф **содержит циклы** — без аккуратной пометки посещённого обход зациклится или
взорвётся по времени. Четыре вопроса: почему обход конечен и полон, почему `visited` ставится
именно при добавлении в очередь, почему BFS даёт кратчайший путь и как обход ловит цикл.

### Почему обход конечен и полон

`visited` поддерживает инвариант: **каждая вершина обрабатывается ровно один раз**.
Флаг ставим, как только вершину нашли (в BFS — кладём в очередь, в DFS — входим в вызов), а
помеченную второй раз не берём. Значит:

- **конечность:** даже при циклах мы не зайдём в вершину дважды → не более `V` заходов;
- **полнота:** обработанная вершина `u` кладёт в очередь всех своих непомеченных соседей, а
  помеченные уже в очереди или обработаны. Значит, по любой цепочке рёбер от старта обход
  дойдёт до её конца — ни одна достижимая вершина не пропущена;
- **стоимость:** каждая вершина обрабатывается один раз, каждое ребро `(u, v)` просматривается
  из `u` один раз (у неориентированного — по разу с каждого конца). Итого `O(V + E)`.

Без `visited` цикл `a → b → a` крутился бы вечно — это не оптимизация, а условие
корректности.

### Когда ставить пометку: при добавлении в очередь

Возьми граф из виджета выше: рёбра `0-1, 0-2, 1-3, 2-3, 2-4, 4-5`. В вершину `3` ведут две
дороги — через `1` и через `2`.

Помечаем **при добавлении**, как в шаблоне:

```text
достали 0 → кладём 1, 2              очередь [1, 2]   помечены 0 1 2
достали 1 → 3 свободна, кладём       очередь [2, 3]   помечены 0 1 2 3
достали 2 → 3 уже помечена; кладём 4 очередь [3, 4]   помечены 0 1 2 3 4
достали 3                            очередь [4]
достали 4 → кладём 5                 очередь [5]      помечены 0 1 2 3 4 5
достали 5                            order = [0 1 2 3 4 5]
```

Теперь перенесём строку `visited[next] = true` туда, где вершину достают:

```text
достали 0 → кладём 1, 2              очередь [1, 2]      помечена 0
достали 1 → 3 свободна, кладём       очередь [2, 3]      помечены 0 1
достали 2 → 3 всё ещё свободна: она в очереди, но не помечена; кладём 3, 4
                                     очередь [3, 3, 4]   помечены 0 1 2
достали 3, достали 3 ещё раз         очередь [4]         помечены 0 1 2 3
достали 4 → кладём 5, достали 5      order = [0 1 2 3 3 4 5]
```

Вершина `3` обработана дважды — по разу на каждую дорогу к ней, и ответ уже неверен. Дальше
хуже: каждая копия кладёт в очередь своих непомеченных соседей, и копии множатся. На слоистом
графе из 25 вершин и 46 рёбер (старт, за ним 12 слоёв по две вершины, каждая вершина соединена
с обеими вершинами следующего слоя) их число удваивается с каждым слоем — такой обход достаёт
из очереди 8191 элемент вместо 25.

Правило: **пометка — это бронь.** Положил вершину в очередь — сразу пометил, и второй раз её
никто не положит. Тогда каждая вершина бывает в очереди ровно один раз. В рекурсивном DFS бронь
— первая строка вызова: пометил, потом соседи. В Clone Graph (построить копию графа со всеми рёбрами) пометкой служит `map` «оригинал →
копия»: копию кладут в неё до рекурсии по соседям, иначе ребро назад начнёт копировать вершину
заново.

(Можно помечать и при извлечении, если первым делом проверять «уже обработана — пропусти».
Ответ будет верным и время тем же `O(V + E)`, но через очередь пройдёт не `V` элементов, а до
`E + 1`: на слоистом графе — 47 вместо 25. Бронь проще.)

### Почему BFS даёт кратчайший путь (невзвешенный граф)

BFS обходит вершины по **неубыванию расстояния** от старта: сначала весь уровень `d`,
потом `d+1`. Почему: вершину уровня `d+1` кладёт в очередь только вершина уровня `d`, поэтому в
очереди всегда сначала хвост уровня `d`, за ним — начало уровня `d+1`, и никто из `d+2` не
обгонит их. Раз вершину помечают при первом добавлении, **первый раз мы достигаем её
по кратчайшему пути** — более длинный путь пришёл бы позже и упёрся бы в уже
посещённую вершину. Для взвешенных рёбер это рассуждение ломается (нужен
[Дейкстра](#веса-на-рёбрах-алгоритм-дейкстры)).

### Цикл в неориентированном графе ловит сам обход

Каждое неориентированное ребро лежит в списке смежности дважды — у обоих концов. Поэтому
«сосед уже посещён» само по себе ничего не значит: из вершины видно и то ребро, по которому в
неё пришли. Обход, который помнит это ребро и пропускает только его, видит цикл в любой другой
встрече с посещённой вершиной: к ней уже есть путь по дереву обхода (рёбрам, по которым обход
впервые входил в вершины), а это ребро — второй.

Пример — треугольник `0–1–2`. DFS идёт `0 → 1 → 2`; из `2` видно ребро в `0` — оно не то, по
которому пришли, а `0` уже посещена: путь `0 → 1 → 2` плюс это ребро замыкают цикл. Помнят
именно ребро, а не вершину-родителя: при двух рёбрах между одной парой второе ведёт в родителя,
и это тоже цикл. Так устроен эталон `HasCycleUndirected` в тренажёре; петля `[v, v]` (ребро из
вершины в неё саму) при таком счёте — тоже цикл.

Тот же вопрос решает Union-Find (структура, которая склеивает группы вершин и быстро отвечает,
в одной ли группе две вершины) — удобно, когда рёбра приходят по одному. Это отдельный приём
из [главы расширения](union-find-structure.md); здесь всё решается обходом.

## ⚙️ Цена на практике

### Список смежности против матрицы — по плотности

`O(V + E)` против `O(V²)`. Для разреженного графа (`E ≈ V`) список экономит память на
порядки. Матрица оправдана только на плотном графе (`E ≈ V²`) или когда нужна проверка
«есть ли ребро `u→v`» за `O(1)`. По умолчанию — список.

### Глубина рекурсии DFS — цена и предел

Рекурсивный DFS на «цепочке» из 10⁵ вершин уходит на 10⁵ кадров вглубь. В Go это обычно не
падает: стек горутины растёт сам — переезжает в новый, вдвое больший, с копированием — до предела
1 ГБ на 64-битной машине (`debug.SetMaxStack`). Замер на цепочке: 10⁵ вершин — около 17 МБ стека,
5·10⁶ — около 540 МБ, а 10⁷ упираются в предел, и программа падает с `fatal error: stack
overflow` — переполнением стека; это не паника, `recover` её не поймает. Так что глубина стоит памяти и времени на
переезды стека. В языках с фиксированным стеком (C, Java по умолчанию) такая глубина роняет
программу намного раньше. На больших или потенциально вырожденных графах пиши **итеративный
DFS с явным стеком (`[]int`)** — предсказуемая память и никакого переполнения:

```go
func dfsIter(adj [][]int, start int) []int {
    visited := make([]bool, len(adj))
    stack := []int{start}
    var order []int
    for len(stack) > 0 {
        node := stack[len(stack)-1] // снимаем верхнюю
        stack = stack[:len(stack)-1]
        if visited[node] {
            continue // уже вошли в неё по другой дороге
        }
        visited[node] = true // помечаем при снятии, а не при добавлении
        order = append(order, node)
        for i := len(adj[node]) - 1; i >= 0; i-- { // соседей кладём с конца
            if next := adj[node][i]; !visited[next] {
                stack = append(stack, next)
            }
        }
    }
    return order
}
```

От шаблона BFS он отличается в трёх местах, и два из них — ради того же порядка, что у
рекурсии. **Соседей кладут с конца:** стек отдаёт последнего положенного, и при обычном порядке
первым пошёл бы последний сосед. **Пометка — при снятии:** рекурсия помечает вершину, когда в неё
входит. Если бронировать при добавлении, сосед старта останется «за стартом», хотя рекурсия
дошла бы до него глубже раньше. На рёбрах `0-1, 0-2, 1-3, 1-4, 2-3` рекурсия из `0` даёт
`0 1 3 2 4` (в `2` она входит из `3`), а стек с бронью — `0 1 3 4 2`. Цена пометки при снятии —
вершина может лежать в стеке несколько раз, всего до `E` записей. Когда порядок не важен
(компоненты, острова), бронь при добавлении тоже годится.

Тест `DFSOrder` в тренажёре сверяет порядок дословно, и листинг выше его сдаёт (проверено); стек с
бронью при добавлении падает на случае «сосед старта достижим глубже».

### Очередь срезом: следи за массивом под срезом

Идиома `queue = queue[1:]` сдвигает голову, но **не освобождает** начало массива под
срезом — на большом BFS память держится до переаллокации. Для огромных графов веди
индекс головы (`head++`) по фиксированному срезу или используй `container/list`.

### `visited`: срез против `map`

Когда вершины пронумерованы `0..V-1` — `[]bool` (непрерывная память, доступ по индексу,
дружелюбно к кэшу). `map[ключ]bool` нужен только для разреженных или строковых
идентификаторов — он медленнее из-за хеширования и аллокаций.

> 🔧 **Где это в Go.** Твой проект — уже граф: пакеты — вершины, импорты — рёбра. Компилятор
> обходит его и запрещает циклы (знаменитое `import cycle not allowed` — это обнаружение цикла в
> ориентированном графе); [`go mod graph`](https://go.dev/ref/mod#go-mod-graph) печатает граф
> зависимостей модулей, а `go list -deps` — все пакеты, достижимые по импортам, включая непрямые. Сборка идёт в
> порядке, где все зависимости пакета собраны раньше него, — привет топологической сортировке
> из [соседней главы](topological-sort.md).

## ⚠️ Типичные ошибки

1. **Забыли `visited`** — на графе с циклом обход уходит в бесконечность.
2. **В BFS помечают при извлечении, а не при добавлении** — вершина дублируется в очереди.
3. **Для неориентированного графа добавили ребро только в одну сторону** — половина связей теряется.
4. **Глубокая рекурсия DFS** на большом графе — переполнение стека; бери итеративный DFS со стеком.
5. **Изолированные вершины** — вершина без рёбер это отдельная компонента.
6. **BFS на весах** — он находит путь с наименьшим числом рёбер, а не самый дешёвый; нужен Дейкстра. А Дейкстра на отрицательных весах ошибается — там Bellman–Ford.

> 🌍 **Где это в настоящем коде**
>
> - [`ReachableBlocks`](https://github.com/golang/go/blob/go1.24.0/src/cmd/compile/internal/ssa/deadcode.go#L22) (Go 1.24) — компилятор ищет недостижимый код: обход в глубину по блокам функции со стеком и массивом `reachable` вместо `visited`; блоки, до которых обход не дошёл, выбрасываются.
> - [`deadcodePass.flood`](https://github.com/golang/go/blob/go1.24.0/src/cmd/link/internal/ld/deadcode.go#L136) (Go 1.24) — линкер начинает с `main.main` и функций `init` и обходит граф «символ → на кого он ссылается»; символ, до которого обход не добрался, в бинарник не попадает.

## 📝 Разбор задачи

Перебор и наблюдение — в [«🧭 Откуда берётся обход графа»](#-откуда-берётся-обход-графа-выведем-его-сами):
прогулка из каждого города со своей пометкой против одной пометки на все прогулки. Здесь — код и
трасса той же задачи, только граф задан не списком рёбер, а матрицей.

> **Задача (Number of Provinces).** Дана матрица смежности `isConnected` размера `n×n`:
> `isConnected[i][j] == 1`, если города `i` и `j` напрямую связаны. Связь
> транзитивна — города одной провинции достижимы друг из друга. Найти число
> **провинций** (компонент связности).
> Пример: `[[1,1,0],[1,1,0],[0,0,1]]` → `2` (города `0,1` — одна провинция, `2` — отдельная).

**Код: DFS по матрице, считаем запуски — O(V²).** Соседи вершины `v` — все `u` с
`isConnected[v][u] == 1`, то есть вся её строка.

```go
func numProvinces(isConnected [][]int) int {
    n := len(isConnected)
    visited := make([]bool, n)
    var dfs func(v int)
    dfs = func(v int) {
        visited[v] = true
        for u := 0; u < n; u++ {
            if isConnected[v][u] == 1 && !visited[u] {
                dfs(u)
            }
        }
    }
    count := 0
    for i := 0; i < n; i++ {
        if !visited[i] {
            count++ // начали новую компоненту
            dfs(i)
        }
    }
    return count
}
```

Здесь O(V²) — а не O(V+E), — потому что вход задан **матрицей**: чтобы найти соседей
вершины, мы просматриваем всю её строку. На списке смежности тот же подсчёт даёт
O(V+E). Без рекурсии считают так же — обходом в ширину или DFS с явным стеком.

Прогони DFS по компонентам: каждая незатронутая вершина запускает новую провинцию и
красит всё достижимое из неё, число запусков и есть ответ. В виджете граф побольше, чем в
условии: 8 городов, три провинции, в третьей есть цикл 5–6–7 — из 7 видна дорога обратно в уже
покрашенный 5, и DFS по ней не идёт. Трассировка ниже — на графе из «🧭».

Что на холсте. Вершина `v` текущего вызова залита жёлтым, проверяемый сосед `u` обведён жёлтым
пунктиром, как в BFS выше, а дорога `v–u` между ними — жёлтая; рядом с вершинами подписаны `v` и `u`
(во внешнем цикле — `i`). Под графом — стек вызовов. Первым стоит кадр `numProvinces` со своими
`i` и `count`, за ним — кадры `dfs(v)`; текущий — последний, в синей рамке. У каждого кадра `dfs`
подписан `u`, на котором он сейчас: проверяет соседа или ждёт возврата из `dfs(u)`; у только что
вызванного `u` ещё нет. Пока идёт `dfs`, чипы
`i` и `count` стоят на «—»: функция объявлена раньше них и их не видит, а значения лежат в нижнем
кадре. Шаг на закрывающей скобке `dfs` — возврат: верхний кадр снят. Проверку `if` виджет
показывает только для `u`, связанных с `v` дорогой; нули строки и диагональ он пропускает.

## 🧵 Конкурентный BFS (Go)

BFS обходит граф **уровнями**: сначала старт, потом все его соседи, потом соседи соседей. Внутри
одного уровня вершины независимы — их можно обрабатывать **параллельно** горутинами, а переход на
следующий уровень — это барьер (дождались всех). Естественный кандидат на конкурентность… в теории.

**Главное:** на обычных графах конкурентный BFS **медленнее** последовательного — в замере
из тренажёра почти в 90 раз: горутина на каждую вершину и захват общего мьютекса на каждое ребро стоят дороже самой работы.
«Сделать конкурентно» ≠ «сделать быстрее» — сначала измерь. Когда горутины всё-таки окупаются,
разобрано в главе [«Параллельные алгоритмы»](parallel-algorithms.md).

<details class="algo-details">
<summary>⚙️ Второй проход: где прячется гонка, честная цена и вариант без мьютекса — читать, когда освоишься</summary>

### Где прячется гонка

Наивно — горутина на вершину фронта, и каждая сама проверяет-и-помечает общий `visited`:

```go
for _, u := range frontier {
    go func(u int) {
        for _, v := range adj[u] {
            if !visited[v] {        // ← ЧИТАЕМ общую память
                visited[v] = true   // ← и ПИШЕМ без синхронизации
                next = append(next, v)
            }
        }
    }(u)
}
```

Это **гонка данных**: две горутины могут одновременно увидеть `visited[v] == false` и обе добавить
`v` в `next` — вершина продублируется (а конкурентный `append` в общий срез вообще способен
повредить память). `go test -race` подсветит конфликт чтения/записи. Лечится замком вокруг всей
проверки-и-пометки:

```go
mu.Lock()
if !visited[v] { visited[v] = true; next = append(next, v) }
mu.Unlock()
```

Прошагай гонку по таймлайну: у каждой горутины (`G1`, `G2`, …) своя колонка,
время идёт сверху вниз.
Все читают `visited[3]` как `false` (красное окно гонки — никто ещё не записал), и каждая в итоге
добавляет `3` в `next` — вершина дублируется. Поле «горутин» меняет их число: на трёх — 3 копии,
на четырёх — 4.

### Честная цена

А теперь главное, чего не говорят туториалы: на обычных графах конкурентный BFS **медленнее**
последовательного. Бенчмарк из тренажёра (слоистый граф 20×60): конкурентная версия проиграла
последовательной почти **в 90 раз** (≈10.5 мс против ≈0.12 мс) — создание горутины и борьба за
мьютекс на каждое ребро дороже самой работы. Параллелизм окупается, только когда **работы на
вершину много** (тяжёлая обработка, I/O) и **фронт широкий** — иначе синхронизация съедает выигрыш.

> 💡 Вывод инженера: «сделать конкурентно» ≠ «сделать быстрее». Сначала измерь (`-bench`),
> убедись, что есть что параллелить, и только потом плати за горутины и замки.

### А если убрать мьютекс? Atomic + локальные фронты

Мьютекс на каждое ребро — наивная синхронизация, её можно почти убрать. Вершину «столбят»
**атомарным CAS** (compare-and-swap: записать новое значение, только если там ещё старое;
`atomic.CompareAndSwapInt32(&visited[v], 0, 1)` — кто перевёл `0→1`, тот и взял `v`), а каждая горутина копит **свой локальный фронт**, и сливаются они раз в уровень. На горячем
пути тогда нет ни блокировок, ни общей записи — а значит, нет и гонки:

```go
if atomic.CompareAndSwapInt32(&visited[v], 0, 1) {
    local = append(local, v) // в СВОЙ срез; общий next собираем после барьера
}
```

Сравни с таймлайном гонки выше: тут несколько горутин тоже метят одну вершину, но `CAS` пропускает
ровно одну (зелёный ✓), остальные получают «занято» и ничего не добавляют — **красного окна гонки
нет**, дубля нет (сколько бы горутин ни было).

<div class="algo-viz" data-viz="bfs-local-timeline" data-goroutines="3"></div>

И это правда быстрее. Но вот числа из бенчмарка тренажёра (тот же граф 20×60):

| версия | время | против Seq |
|---|---|---|
| `Seq` (синхронно) | ≈0.12 мс | — |
| `Conc` (мьютекс на каждое ребро) | ≈10.5 мс | почти ×90 медленнее |
| `ConcLocal` (atomic + локальные фронты) | ≈1.7 мс | всё ещё почти ×15 медленнее |

Atomic-версия обошла мьютексную в **6 раз** — и всё равно **проиграла синхронной почти в 15 раз**.
Почему? Работа на вершину здесь — «пометить бит», она ничтожна, а накладные расходы (запуск
горутин, атомарные операции, слияние локальных фронтов, лишние аллокации) — нет. Убрать борьбу за
замок **необходимо, но недостаточно**.

**Значит, интуиция «тогда уж лучше синхронно» верна** — для обычного BFS в памяти. Конкурентный
BFS выигрывает, только когда **работа на вершину тяжёлая** (дорогая обработка, сетевой/дисковый
запрос): тогда она доминирует, накладные расходы амортизируются, и `ConcLocal` обгонит `Seq`. На
«пометить бит» — никогда. Дело не в алгоритме, а в соотношении «работа на вершину / стоимость
синхронизации».

**Тренажёр** — пакет `parallelbfs` (три версии бок о бок):

go test -tags solution -bench=. ./parallelbfs/  # Seq vs Conc(mutex) vs ConcLocal

`-race` стережёт корректность синхронизации обеих конкурентных версий.

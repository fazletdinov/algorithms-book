## 🎬 Визуализация

> 💡 **Интерактивная демонстрация.** Жёлтая вершина — текущая (извлечённая из очереди), синие —
> посещённые. BFS расходится волной по уровням от старта. Справа — код с подсветкой строки и
> переменные (очередь, порядок), внизу — кликабельные шаги. (Виджет работает в собранной книге
> `mdbook serve`/`mdbook build`, а не при просмотре `.md` на GitHub.)

## ⚡ Шаблон для собеседования

```go
// BFS по списку смежности
func bfs(adj [][]int, start int) []int {
    visited := make([]bool, len(adj))
    queue := []int{start}
    visited[start] = true
    var order []int
    for len(queue) > 0 {
        node := queue[0]
        queue = queue[1:]
        order = append(order, node)
        for _, next := range adj[node] {
            if !visited[next] {
                visited[next] = true // помечаем ПРИ добавлении
                queue = append(queue, next)
            }
        }
    }
    return order
}
```

1. `visited[start] = true`, кладём старт в очередь;
2. извлекаем вершину, добавляем в порядок;
3. соседей кладём в очередь, помечая сразу;
4. DFS — то же, но рекурсией/стеком.

## 📖 Разбор

<details class="algo-details">
<summary>Представление, BFS/DFS, компоненты, Union-Find и сложность</summary>

**Граф** — набор вершин, соединённых рёбрами; может содержать циклы и несколько
компонент. Большинство задач сводятся к **обходу**: посетить вершины, не зайдя в одну
дважды.

#### Представление: список смежности

```go
func buildAdjacency(n int, edges [][]int, directed bool) [][]int {
    adj := make([][]int, n)
    for _, e := range edges {
        u, v := e[0], e[1]
        adj[u] = append(adj[u], v)
        if !directed {
            adj[v] = append(adj[v], u)
        }
    }
    return adj
}
```

| Представление        | Память   | Проверка ребра | Обход соседей |
|----------------------|----------|----------------|---------------|
| Список смежности     | O(V + E) | O(deg(u))      | O(deg(u))     |
| Матрица смежности    | O(V²)    | O(1)           | O(V)          |

#### BFS и DFS

```go
func dfs(adj [][]int, node int, visited []bool, order *[]int) {
    visited[node] = true
    *order = append(*order, node)
    for _, next := range adj[node] {
        if !visited[next] {
            dfs(adj, next, visited, order)
        }
    }
}
```

В BFS вершину помечают посещённой **в момент добавления в очередь**, иначе она попадёт в
очередь несколько раз.

#### Компоненты связности

```go
func countComponents(n int, edges [][]int) int {
    adj := buildAdjacency(n, edges, false)
    visited := make([]bool, n)
    count := 0
    for i := 0; i < n; i++ {
        if !visited[i] {
            count++
            var order []int
            dfs(adj, i, visited, &order)
        }
    }
    return count
}
```

#### Union-Find (DSU)

> 📦 Устройство DSU, сжатие пути и объединение по размеру **с визуализациями** разобраны в
> отдельной главе [«Union-Find (DSU): устройство и операции»](union-find-structure.md). Здесь —
> краткая реализация для применения в графовых задачах.

Отвечает на «в одной ли группе две вершины» почти за O(1) (со сжатием пути и
объединением по рангу — O(α(n))).

```go
type UnionFind struct{ parent, rank []int }

func (uf *UnionFind) Find(x int) int {
    for uf.parent[x] != x {
        uf.parent[x] = uf.parent[uf.parent[x]] // сжатие пути
        x = uf.parent[x]
    }
    return x
}

func (uf *UnionFind) Union(x, y int) bool {
    rx, ry := uf.Find(x), uf.Find(y)
    if rx == ry {
        return false // уже в одном множестве — ребро замыкает цикл
    }
    if uf.rank[rx] < uf.rank[ry] {
        rx, ry = ry, rx
    }
    uf.parent[ry] = rx
    if uf.rank[rx] == uf.rank[ry] {
        uf.rank[rx]++
    }
    return true
}
```

**Цикл в ориентированном графе** ловится DFS с тремя состояниями (белый/серый/чёрный):
встретили серую вершину → цикл. Это основа [топологической сортировки](topological-sort.md).

#### Сложность

| Операция                       | Время          | Память |
|--------------------------------|----------------|--------|
| BFS / DFS (список смежности)   | O(V + E)       | O(V)   |
| Компоненты связности           | O(V + E)       | O(V)   |
| Union-Find (на операцию)       | O(α(n)) ≈ O(1) | O(V)   |

</details>

## 🧠 Почему это корректно

Граф **содержит циклы** — без аккуратной пометки посещённого обход зациклится или
взорвётся по времени. Три вопроса: почему обход конечен, почему `visited` ставится
именно при добавлении в очередь, и почему BFS даёт кратчайший путь.

### Почему обход конечен и полон

`visited` поддерживает инвариант: **каждая вершина обрабатывается ровно один раз**.
Перед заходом проверяем флаг, после захода — ставим. Значит:

- **конечность:** даже при циклах мы не зайдём в вершину дважды → не более `V` заходов;
- **полнота:** каждое ребро `(u, v)` рассматривается из `u` один раз (для
  неориентированного — дважды, по разу с каждого конца). Суммарно `O(V + E)` — ни одна
  достижимая вершина не пропущена, ни одна не обработана лишний раз.

Без `visited` цикл `a → b → a` крутился бы вечно — это не оптимизация, а условие
корректности.

### Почему `visited` — при добавлении в очередь, а не при извлечении

Самая тонкая деталь BFS. Если помечать вершину посещённой **в момент извлечения**, то
между добавлением и извлечением её успеют положить в очередь несколько соседей —
вершина окажется в очереди многократно. На плотном графе это раздувает очередь и
ломает `O(V + E)`.

Помечаем **при добавлении** — тогда каждая вершина попадает в очередь ровно один раз.
Инвариант: *в очереди и `visited` находятся только вершины, которые уже «забронированы»
к обработке*, поэтому повторно никто не добавится.

### Почему BFS даёт кратчайший путь (невзвешенный граф)

BFS обходит вершины по **неубыванию расстояния** от старта: сначала весь уровень `d`,
потом `d+1`. Раз вершину помечают при первом добавлении, **первый раз мы достигаем её
по кратчайшему пути** — более длинный путь пришёл бы позже и упёрся бы в уже
посещённую вершину. Для взвешенных рёбер это рассуждение ломается (нужен
[Дейкстра](grids-and-shortest-paths.md)).

### Union-Find: почему почти `O(1)`

Сжатие пути (`Find` подтягивает узлы к корню) и объединение по рангу (меньшее дерево
вешаем под большее) держат деревья плоскими. Амортизированная стоимость операции —
`O(α(n))`, где `α` — обратная функция Аккермана, на практике `≤ 4` для любого
мыслимого `n`. Возврат `false` из `Union` (корни совпали) — это и есть детектор цикла:
ребро соединяет уже связанные вершины.

## ⚙️ Цена на практике

### Список смежности против матрицы — по плотности

`O(V + E)` против `O(V²)`. Для разреженного графа (`E ≈ V`) список экономит память на
порядки. Матрица оправдана только на плотном графе (`E ≈ V²`) или когда нужна проверка
«есть ли ребро `u→v`» за `O(1)`. По умолчанию — список.

### Глубина рекурсии DFS — реальный риск

Рекурсивный DFS на «цепочке» из 10⁵ вершин уходит на 10⁵ кадров вглубь. Go растит стек
горутины динамически, но очень глубокая рекурсия — это и медленно, и близко к пределу.
На больших или потенциально вырожденных графах пиши **итеративный DFS с явным стеком
(`[]int`)** — предсказуемая память и никакого переполнения.

### Очередь срезом: следи за backing-массивом

Идиома `queue = queue[1:]` сдвигает голову, но **не освобождает** начало нижележащего
массива — на большом BFS память держится до переаллокации. Для огромных графов веди
индекс головы (`head++`) по фиксированному срезу или используй `container/list`.

### `visited`: срез против `map`

Когда вершины пронумерованы `0..V-1` — `[]bool` (непрерывная память, доступ по индексу,
дружелюбно к кэшу). `map[ключ]bool` нужен только для разреженных или строковых
идентификаторов — он медленнее из-за хеширования и аллокаций.

## ⚠️ Типичные ошибки

1. **Забыли `visited`** — на графе с циклом обход уходит в бесконечность.
2. **В BFS помечают при извлечении, а не при добавлении** — вершина дублируется в очереди.
3. **Для неориентированного графа добавили ребро только в одну сторону** — половина связей теряется.
4. **Глубокая рекурсия DFS** на большом графе — переполнение стека; берите итеративный DFS со стеком.
5. **Изолированные вершины** — вершина без рёбер это отдельная компонента.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он медленный, и
только потом обход с подсчётом запусков.

> **Задача (Number of Provinces).** Дана матрица смежности `isConnected` размера `n×n`:
> `isConnected[i][j] == 1`, если города `i` и `j` напрямую связаны. Связь
> транзитивна — города одной провинции достижимы друг из друга. Найти число
> **провинций** (компонент связности).
> Пример: `[[1,1,0],[1,1,0],[0,0,1]]` → `2` (города `0,1` — одна провинция, `2` — отдельная).

**Шаг 1. Наивно: посчитать достижимость между всеми парами — O(V³).**

```go
func numProvincesNaive(isConnected [][]int) int {
    n := len(isConnected)
    reach := make([][]bool, n)
    for i := range reach {
        reach[i] = make([]bool, n)
        for j := range reach[i] {
            reach[i][j] = i == j || isConnected[i][j] == 1
        }
    }
    for k := 0; k < n; k++ { // транзитивное замыкание (Флойд–Уоршелл)
        for i := 0; i < n; i++ {
            for j := 0; j < n; j++ {
                if reach[i][k] && reach[k][j] {
                    reach[i][j] = true
                }
            }
        }
    }
    seen := make([]bool, n)
    count := 0
    for i := 0; i < n; i++ {
        if seen[i] {
            continue
        }
        count++ // новая провинция
        for j := 0; j < n; j++ {
            if reach[i][j] {
                seen[j] = true
            }
        }
    }
    return count
}
```

Это **работает и проходит тесты**, но тройной цикл замыкания делает O(V³) операций.
Мы вычисляем достижимость *между всеми парами*, хотя для подсчёта компонент это
избыточно: нам не нужно знать, кто с кем связан, — достаточно знать, **сколько раз
пришлось начинать новый обход**.

Прогоните Флойда–Уоршелла: матрица `reach[i][j]` заполняется тройным циклом — для каждой
промежуточной `k` проверяем все пары `(i, j)`, отсюда O(V³):

<div class="algo-viz" data-viz="num-provinces-naive" data-nodes="0,1,2" data-edges="0-1"></div>

**Шаг 2. Ключевое наблюдение.** Компонент связности ровно столько, сколько раз обход
**стартует из непосещённой вершины**: один запуск целиком «съедает» одну компоненту,
помечая все её вершины (см. [почему обход конечен и
полон](#почему-обход-конечен-и-полон)). Считать достижимость между всеми парами не
нужно — достаточно одного флага `visited` на вершину.

**Шаг 3. Оптимум: DFS по матрице, считаем запуски — O(V²).**

```go
func numProvinces(isConnected [][]int) int {
    n := len(isConnected)
    visited := make([]bool, n)
    var dfs func(v int)
    dfs = func(v int) {
        visited[v] = true
        for u := 0; u < n; u++ {
            if isConnected[v][u] == 1 && !visited[u] {
                dfs(u)
            }
        }
    }
    count := 0
    for i := 0; i < n; i++ {
        if !visited[i] {
            count++ // начали новую компоненту
            dfs(i)
        }
    }
    return count
}
```

Здесь O(V²) — а не O(V+E), — потому что вход задан **матрицей**: чтобы найти соседей
вершины, мы просматриваем всю её строку. На списке смежности тот же подсчёт даёт
O(V+E). Альтернатива без рекурсии — **Union-Find**: объединяем `i` и `j` для каждого
ребра `isConnected[i][j]==1`, ответ — число различных корней; см. раздел
[Union-Find](#union-find-dsu) выше.

Прогоните DFS по компонентам: каждая незатронутая вершина запускает новую провинцию и
красит всё достижимое из неё, число запусков и есть ответ:

<div class="algo-viz" data-viz="num-provinces" data-nodes="0,1,2" data-edges="0-1"></div>

**Шаг 4. Трассировка** на `isConnected = [[1,1,0],[1,1,0],[0,0,1]]`:

| `i` | `visited[i]`? | действие         | заход DFS помечает | `visited` после | `count` |
|-----|---------------|------------------|--------------------|-----------------|---------|
| 0   | нет           | `count++`, `dfs(0)` | 0 → 1 (сосед)   | `[T,T,F]`       | **1**   |
| 1   | да            | пропуск          | —                  | `[T,T,F]`       | 1       |
| 2   | нет           | `count++`, `dfs(2)` | 2 (соседей нет) | `[T,T,T]`       | **2**   |

Ответ — `2`. Обрати внимание: `dfs(0)` за один запуск пометил всю первую провинцию
(`0` и `1`), поэтому на `i=1` мы лишь убедились во флаге и пошли дальше. Число
`count++` и есть число компонент.

## 🧵 Конкурентный BFS (Go)

BFS обходит граф **уровнями**: сначала старт, потом все его соседи, потом соседи соседей. Внутри
одного уровня вершины независимы — их можно обрабатывать **параллельно** горутинами, а переход на
следующий уровень — это барьер (дождались всех). Естественный кандидат на конкурентность… в теории.

### Где прячется гонка

Наивно — горутина на вершину фронта, и каждая сама проверяет-и-помечает общий `visited`:

```go
for _, u := range frontier {
    go func(u int) {
        for _, v := range adj[u] {
            if !visited[v] {        // ← ЧИТАЕМ общую память
                visited[v] = true   // ← и ПИШЕМ без синхронизации
                next = append(next, v)
            }
        }
    }(u)
}
```

Это **гонка данных**: две горутины могут одновременно увидеть `visited[v] == false` и обе добавить
`v` в `next` — вершина продублируется (а конкурентный `append` в общий срез вообще способен
повредить память). `go test -race` подсветит конфликт чтения/записи. Лечится замком вокруг всей
проверки-и-пометки:

```go
mu.Lock()
if !visited[v] { visited[v] = true; next = append(next, v) }
mu.Unlock()
```

Прошагай гонку по таймлайну: несколько горутин (`G1`, `G2`, …) идут по времени слева направо.
Все читают `visited[3]` как `false` (красное окно гонки — никто ещё не записал), и каждая в итоге
добавляет `3` в `next` — вершина дублируется. Поле «горутин» меняет их число: на трёх — 3 копии,
на четырёх — 4.

### Честная цена

А теперь главное, чего не говорят туториалы: на обычных графах конкурентный BFS **медленнее**
последовательного. Бенчмарк из тренажёра (слоистый граф 20×60): конкурентная версия проиграла
последовательной примерно **в 70 раз** (≈15 мс против ≈0.2 мс) — создание горутины и борьба за
мьютекс на каждое ребро дороже самой работы. Параллелизм окупается, только когда **работы на
вершину много** (тяжёлая обработка, I/O) и **фронт широкий** — иначе синхронизация съедает выигрыш.

> 💡 Вывод инженера: «сделать конкурентно» ≠ «сделать быстрее». Сначала измерь (`-bench`),
> убедись, что есть что параллелить, и только потом плати за горутины и замки.

### А если убрать мьютекс? Atomic + локальные фронты

Мьютекс на каждое ребро — наивная синхронизация, её можно почти убрать. Вершину «столбят»
**атомарным CAS** (`atomic.CompareAndSwapInt32(&visited[v], 0, 1)` — кто перевёл `0→1`, тот и взял
`v`), а каждая горутина копит **свой локальный фронт**, и сливаются они раз в уровень. На горячем
пути тогда нет ни блокировок, ни общей записи — а значит, нет и гонки:

```go
if atomic.CompareAndSwapInt32(&visited[v], 0, 1) {
    local = append(local, v) // в СВОЙ срез; общий next собираем после барьера
}
```

Сравни с таймлайном гонки выше: тут несколько горутин тоже метят одну вершину, но `CAS` пропускает
ровно одну (зелёный ✓), остальные получают «занято» и ничего не добавляют — **красного окна гонки
нет**, дубля нет (сколько бы горутин ни было).

<div class="algo-viz" data-viz="bfs-local-timeline" data-goroutines="3"></div>

И это правда быстрее. Но вот числа из бенчмарка тренажёра (тот же граф 20×60):

| версия | время | против Seq |
|---|---|---|
| `Seq` (синхронно) | ≈0.22 мс | — |
| `Conc` (мьютекс на каждое ребро) | ≈15 мс | ×70 медленнее |
| `ConcLocal` (atomic + локальные фронты) | ≈2.1 мс | всё ещё ×9 медленнее |

Atomic-версия обошла мьютексную в **7 раз** — и всё равно **проиграла синхронной в 9 раз**.
Почему? Работа на вершину здесь — «пометить бит», она ничтожна, а накладные расходы (запуск
горутин, атомарные операции, слияние локальных фронтов, лишние аллокации) — нет. Убрать контеншн
**необходимо, но недостаточно**.

**Значит, интуиция «тогда уж лучше синхронно» верна** — для обычного in-memory BFS. Конкурентный
BFS выигрывает, только когда **работа на вершину тяжёлая** (дорогая обработка, сетевой/дисковый
запрос): тогда она доминирует, накладные расходы амортизируются, и `ConcLocal` обгонит `Seq`. На
«пометить бит» — никогда. Дело не в алгоритме, а в соотношении «работа на вершину / стоимость
синхронизации».

**Тренажёр** — пакет `parallelbfs` (три версии бок о бок):

```bash
cd exercises
go test ./parallelbfs/                          # ваши решения (красные)
go test -tags solution ./parallelbfs/           # эталон (зелёные)
go test -tags solution -race ./parallelbfs/     # проверка на гонки
go test -tags solution -bench=. ./parallelbfs/  # Seq vs Conc(mutex) vs ConcLocal
```

`BFSLevelsSeq`, `BFSLevelsConc` (мьютекс) и `BFSLevelsConcLocal` (atomic + локальные фронты)
обязаны давать **одинаковый** результат (уровни, отсортированные внутри) — это и проверяет тест, а
`-race` стережёт корректность синхронизации обеих конкурентных версий.

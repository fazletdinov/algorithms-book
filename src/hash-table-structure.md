> 🧭 **Зачем отдельная глава.** Доступ по индексу в срезе — O(1): адрес ячейки `vals[i]`
> вычисляется, а не ищется. Будь ключами числа от 0 до 99, хватило бы среза на сто ячеек:
> `vals[key]`. Но ключи — номера заказов, строки, что угодно, и срез «на все возможные ключи» не
> построить. Идея хеш-таблицы — сжать ключ до номера ячейки: хеш-функция превращает любой ключ в
> число, а остаток `% m` (m — число ячеек) — в номер ячейки. Адрес снова вычисляется за O(1).
> Цена сжатия: два разных ключа иногда получают один номер — 1 и 5 при m = 4 оба дают
> остаток 1 и попадают в ячейку 1. Это **коллизия**, и вся глава —
> о том, как с ней жить. В Go такая структура — встроенный `map`, которым ты пользуешься каждый
> день; здесь строим её сами, чтобы стало видно, почему доступ «в среднем O(1)», но «в худшем O(n)».

## 🧱 Как устроено

Хеш-таблица — это **массив бакетов**. Хеш-функция отображает ключ в индекс бакета; при разрешении
коллизий **цепочками** каждый бакет хранит маленький список записей `{ключ, значение}`.

```go
type entry struct{ key, val int }

type HashMap struct {
    buckets [][]entry // массив бакетов; каждый бакет — цепочка записей
}

// Упрощённо: реальная хеш-функция перемешивает биты ключа. Здесь только снимаем знак:
// в Go -7 % 4 == -3, и отрицательный ключ дал бы отрицательный индекс бакета — паника.
func hash(key int) int { return key & math.MaxInt } // бит знака — в ноль
```

<div class="algo-fig" data-fig="list" data-list="8; 1,5; ; 3" data-rows="бакет 0; бакет 1; бакет 2; бакет 3" data-end="" data-caption="Ключи 1, 5, 3, 8 в 4 бакетах, бакет = hash(key) % 4. Коллизия: 1 и 5 дают бакет 1 и стоят в одной цепочке; бакет 2 пуст"></div>

Три факта, которые держат всё:

1. **Ключ → индекс за O(1).** Хеш-функция мгновенно говорит, в каком бакете искать; не нужно
   просматривать всю таблицу. Это и есть источник «O(1) в среднем».
2. **Коллизии неизбежны.** Бакетов меньше, чем возможных ключей, поэтому разные ключи иногда
   делят бакет. Цепочка (список в бакете) разруливает это: внутри бакета — линейный поиск.
3. **Скорость зависит от загрузки.** **Коэффициент загрузки** (load factor) — сколько записей в
   среднем приходится на бакет: n записей на m бакетов дают `n/m`. Пока он не больше константы,
   цепочки коротки и операции O(1). Когда таблица заполняется, её **расширяют** (удваивают `m`) и
   перехешируют — иначе цепочки растут и всё замедляется.

## ➕ Вставка: `Put`

`Put` вычисляет бакет по хешу, проверяет, нет ли уже такого ключа (тогда обновляет значение), и
иначе **добавляет запись в цепочку** бакета. Коллизия — это просто непустая цепочка.

```go
func (h *HashMap) Put(key, val int) {
    i := hash(key) % len(h.buckets)   // в какой бакет
    for j := range h.buckets[i] {     // уже есть такой ключ?
        if h.buckets[i][j].key == key {
            h.buckets[i][j].val = val // обновляем по индексу (range даёт КОПИЮ — правка через e потерялась бы)
            return
        }
    }
    h.buckets[i] = append(h.buckets[i], entry{key, val}) // коллизия → в цепочку
}
```

> 💡 **Демонстрация вставки.** Пустая таблица на 4 бакета, кладём по очереди `1, 5, 3, 8, 9, 6`
> и ещё раз `5`. Хеш здесь — сам ключ, поэтому бакет — просто остаток от деления на 4 (он виден
> над таблицей на каждом шаге). Следи за бакетом `1`: туда попадают `1`, `5` и `9` — цепочка
> растёт до `1 → 5 → 9`, и каждая новая вставка сначала сравнивает ключ со всеми, кто уже там.
> Повторный `5` новой записи не создаёт: цикл находит его и **обновляет значение на месте**.
> В «Граничных случаях» — худший вариант (все ключи в одном бакете) и тот же набор на 8 бакетах.

## 🔎 Поиск: `Get`

`Get` идёт в тот же бакет (хеш детерминирован) и **сканирует его цепочку**, сравнивая ключи. Пока
цепочки коротки, это O(1).

```go
func (h *HashMap) Get(key int) (int, bool) {
    i := hash(key) % len(h.buckets)   // тот же бакет
    for _, e := range h.buckets[i] {  // сканируем цепочку
        if e.key == key {
            return e.val, true        // нашли
        }
    }
    return 0, false                   // нет в бакете
}
```

> 💡 **Демонстрация поиска.** Таблица — та, что получилась после вставок выше. Ищем `9`:
> `hash(9) % 4 = 1`, в бакете `1` цепочка `1 → 5 → 9` — два промаха и совпадение на третьем
> сравнении. Потом `7`: бакет `3`, там только `3` — цепочка кончилась, ключа нет. Заметь, что
> остальные бакеты поиск не трогает вовсе: если `7` где-то и есть, то только в бакете `3`.

## 🗑️ Удаление: `Delete`

Удаление — это тот же поиск бакета по хешу, затем **вырезание записи из цепочки** (как удаление из
[связного списка](linked-list-structure.md) или среза). Бакет остаётся, цепочка укорачивается.

```go
func (h *HashMap) Delete(key int) {
    i := hash(key) % len(h.buckets)
    chain := h.buckets[i]
    for j, e := range chain {
        if e.key == key {
            h.buckets[i] = append(chain[:j], chain[j+1:]...) // вырезаем из цепочки
            return
        }
    }
}
```

## 🔄 Рост таблицы: rehashing

Скорость хеш-таблицы держится, **пока цепочки коротки**. Но с каждым `Put` их средняя длина
(коэффициент загрузки `n/m`) растёт, и в какой-то момент `Get` из «в среднем O(1)» деградирует в
скан длинной цепочки. Решение: когда коэффициент загрузки превышает порог (обычно `~0.75`), таблицу
**расширяют** — как правило, **удваивают** число бакетов — и **перехешируют все ключи**.

Важнейшая деталь: индекс бакета — это `hash(key) % m`, и при удвоении `m` **меняется**, поэтому
старое размещение недействительно — каждый ключ надо переложить по **новому** остатку `% 2m`.
Просто «скопировать бакеты» нельзя: `Get` и `Put` находят ключ, только пока считают бакет по
одному и тому же `m`, и после роста `Get` пошёл бы не в тот бакет.

```go
func (h *HashMap) resize(newM int) {
    nb := make([][]entry, newM)
    for _, chain := range h.buckets {
        for _, e := range chain {
            i := hash(e.key) % newM  // НОВЫЙ индекс (по 2m, не по старому m!)
            nb[i] = append(nb[i], e)
        }
    }
    h.buckets = nb
}
```

Листай «›»: таблица из 4 бакетов перегружена, коэффициент загрузки 1.5 (на виджете — load
factor). Таблица удваивается до 8 и перехеширует ключи. Обрати внимание на `8` и `12`: при
`m=4` оба падали в бакет 0 (`8%4 = 12%4 = 0` — коллизия), а при `m=8` **расходятся** (`8%8=0`, `12%8=4`) — цепочки
разъезжаются, и коэффициент загрузки падает до `0.75`:

<div class="algo-viz" data-viz="hash-resize" data-keys="8,3,12,5,7,11" data-buckets="4"></div>

> ⚙️ Один resize стоит **O(n)** — надо потрогать все ключи. Но случается он редко (после
> удвоения до следующего порога надо снова столько же вставок), поэтому в пересчёте на одну
> вставку добавляет лишь **O(1) амортизированно** — тот же аргумент, что и у роста динамического
> массива. Именно так работает встроенный `map` в Go (только он растёт **частями**, чтобы не было
> разовой паузы, — об этом во «втором проходе» раздела о `map` ниже).

> 🌐 **Тот же остаток — для серверов.** Приём `hash(key) % N` тянет раскладывать ключи и по
> серверам: кэш не влез на одну машину — ставим три и шлём ключ на сервер `hash(key) % 3`; такая
> раскладка данных по нескольким серверам называется **шардированием**. Но добавь четвёртый сервер —
> и `hash(key) % 4` разойдётся с `hash(key) % 3` у трёх ключей из четырёх: кэш разом промахивается,
> и весь поток запросов уходит в базу. Как раскладывать так, чтобы переезжала лишь малая доля ключей, —
> в главе [«Консистентное хеширование»](consistent-hashing.md).

> 🌍 **Где это в настоящем коде**
>
> - [`(*table).getWithKey`](https://github.com/golang/go/blob/go1.24.0/src/internal/runtime/maps/table.go#L166) (Go 1.24) — поиск ключа во встроенном `map`: тот же путь, что у нашего `Get`, — хеш выбирает место, где искать, и ключи сравниваются только там.
> - [`(*table).rehash`](https://github.com/golang/go/blob/go1.24.0/src/internal/runtime/maps/table.go#L1009) (Go 1.24) — рост таблицы `map`: тот же смысл, что у нашего `resize`, — места кончились, и записи переезжают в бо́льшую таблицу.

## 📝 Разбор задачи: Two Sum

Ради этого хеш-таблицу и учат: она убирает вложенный цикл поиска. Задача (Two Sum): дан срез
`nums` и число `target`; найди индексы двух разных элементов, сумма которых равна `target`.

**Перебор.** Проверить все пары `i < j`. При n = 6 пар 15: каждый из шести элементов встаёт в
пару с пятью другими, это 30, и каждая пара посчитана дважды. В общем случае пар n·(n−1)/2 — при
n = 1000 уже 499 500, это O(n²). На `nums = [3, 8, 4, 1, 9, 5]`, `target = 10` перебор проверит
13 пар, пока дойдёт до `1 + 9`.

**Где повторяется работа.** Для каждого `x` перебор заново пробегает массив в поисках числа
`target − x`. Но «встречалось ли уже такое число» — это ровно вопрос к хеш-таблице, и `map`
отвечает на него в среднем за O(1). Значит, хватит одного прохода: для каждого `x` спрашиваем
таблицу о `target − x`, а потом кладём в неё сам `x` с его индексом.

```go
func twoSum(nums []int, target int) []int {
    seen := map[int]int{} // значение → индекс, где мы его видели
    for i, x := range nums {
        if j, ok := seen[target-x]; ok { // пара для x уже встречалась?
            return []int{j, i}
        }
        seen[x] = i // запоминаем ПОСЛЕ проверки
    }
    return nil
}
```

Трасса на том же входе (`seen` — то, что лежит в таблице до проверки):

```text
i  x  target−x  seen до проверки    итог
0  3  7         {}                  нет → seen[3]=0
1  8  2         {3:0}               нет → seen[8]=1
2  4  6         {3:0 8:1}           нет → seen[4]=2
3  1  9         {3:0 8:1 4:2}       нет → seen[1]=3
4  9  1         {3:0 8:1 4:2 1:3}   1 есть, j=3 → [3 4]
```

Пять шагов вместо тринадцати проверок пар. В худшем случае шагов n, каждый в среднем O(1): время
O(n), память O(n) на `seen`.

**Почему проверка до записи.** Пока мы спрашиваем таблицу о `target − x`, в ней лежат только
элементы левее `i`, — значит, найденный `j` всегда другой элемент. Запиши `x` раньше вопроса, и
при `x = target − x` (ровно половина `target`) таблица найдёт сам `x`: «пару» из одного элемента.

Две родственные идиомы — та же мысль «спроси у `map` вместо вложенного цикла»:

- **счётчик частот** — `count := map[string]int{}` и `count[w]++`: отсутствующий ключ читается как 0;
- **множество «видели ли»** — `seen := map[int]bool{}`, `if seen[x] { … }` и `seen[x] = true`.

## 🧰 Хеширование как приём: четыре формы

Two Sum — не единственный случай. На собеседованиях `map` снимает вложенный цикл в задачах
четырёх узнаваемых форм. Всё время работает одна мысль: решение «в лоб» для каждого элемента
снова пробегает массив, а `map` отвечает на тот же вопрос за O(1). Формы различаются тем, **что
мы кладём в таблицу**. Цена у всех одна: **O(n) памяти** под таблицу.

| Форма | Сигнал в условии | Ключ → значение |
|---|---|---|
| (а) видел ли я дополнение | пара с суммой (разностью) `target`, массив не отсортирован | число → индекс |
| (б) каноническая форма | «сгруппируй», «одинаковые с точностью до порядка» | форма → список элементов |
| (в) множество для соседа | «подряд идущие», «есть ли x+1» | число → есть / нет |
| (г) счётчик частот | «сколько раз», «уникальный», «та же раскладка букв» | элемент → сколько раз |

**(а) Видел ли я дополнение** — разобрано выше на Two Sum. Для каждого `x` нужен партнёр
`target − x`. Мы ищем его среди уже пройденных элементов, а не среди всех. Поэтому хватает
одного прохода, и элемент не встанет в пару сам с собой.

**(б) Ключ — каноническая форма.** Задача Group Anagrams: разложи слова на группы
**анаграмм** — слов из одних и тех же букв в разном порядке (`eat`, `tea`, `ate`). Перебор
сравнивает каждое слово с каждой группой: O(n²) сравнений. Но у всех анаграмм есть общая
**каноническая форма** — одна запись, которая одинакова для всей группы. Здесь это буквы по
алфавиту: `eat` → `aet`, `tea` → `aet`. Делаем её ключом, и группа находится одним обращением
к `map`:

```go
func groupAnagrams(words []string) [][]string {
    groups := map[string][]string{} // каноническая форма → слова группы
    for _, w := range words {
        b := []byte(w)
        slices.Sort(b) // "tea" → "aet"
        key := string(b)
        groups[key] = append(groups[key], w)
    }
    res := make([][]string, 0, len(groups))
    for _, g := range groups {
        res = append(res, g)
    }
    return res
}
```

Вместо сортировки ключом может быть счётчик букв `[26]int`: в Go массив фиксированной длины
можно сравнивать, поэтому он годится в ключ `map` (срез — нет). Цена — O(n·k) на построение
ключей (k — длина слова; с сортировкой O(n·k log k)) и O(n·k) памяти.

**(в) Множество для O(1) проверки соседа.** Задача Longest Consecutive Sequence: найди длину
самой длинной цепочки чисел подряд (`x`, `x+1`, `x+2`, …) в неотсортированном массиве. На
`[100, 4, 200, 1, 3, 2]` ответ 4: это цепочка `1, 2, 3, 4`. Сортировка решает задачу за
O(n log n). Множество — `map[int]bool` — отвечает на вопрос «есть ли `x+1`?» за O(1). Но если
считать цепочку от **каждого** числа, на входе `0, 1, …, n−1` выйдет n + (n−1) + … = O(n²)
шагов. Поэтому цепочку считаем только от её **начала** — от `x`, у которого нет `x−1`:

```go
func longestConsecutive(nums []int) int {
    set := map[int]bool{}
    for _, x := range nums {
        set[x] = true
    }
    best := 0
    for x := range set { // по множеству: повторы в nums не пересчитываются
        if set[x-1] {
            continue // x — не начало цепочки
        }
        n := 1
        for set[x+n] {
            n++
        }
        best = max(best, n)
    }
    return best
}
```

На примере начала — это `100`, `200` и `1`. Числа `2`, `3`, `4` пропускаются сразу, зато
от `1` цикл проходит их по разу. Так каждое число трогается O(1) раз: время O(n), память O(n).
Обходить надо множество, а не `nums`: иначе каждая копия начала цепочки пересчитает всю
цепочку заново.

**(г) Счётчик частот.** Задача First Unique Character: найди индекс первой буквы, которая
встречается в строке один раз. Перебор для каждой позиции считает её букву по всей строке —
O(n²). Счётчик делает два прохода: первый считает, сколько раз встречается каждая буква,
второй ищет первую позицию со счётом 1.

```go
func firstUniqChar(s string) int {
    var count [26]int // буквы a–z: ключ — номер буквы
    for i := 0; i < len(s); i++ {
        count[s[i]-'a']++
    }
    for i := 0; i < len(s); i++ {
        if count[s[i]-'a'] == 1 {
            return i
        }
    }
    return -1
}
```

Здесь вместо `map` стоит массив на 26 ячеек — тот самый случай из начала главы: ключи — небольшие
числа (номер буквы), и номер ячейки вычисляется без хеша. Для произвольных ключей (слова, числа)
бери `map[K]int`. Тот же счётчик проверяет **анаграммы**: для первой строки прибавь, для второй
вычти — у анаграмм все счётчики вернутся в ноль. Время O(n), память O(σ), где σ — число разных
символов (здесь 26).

> 🔍 **Как выбрать форму.** Сначала спроси себя: что перебор ищет вложенным циклом для каждого
> элемента? Партнёра — это (а). Элемент с той же формой — (б). Соседа по значению — (в). Сколько
> раз встречался — (г). Ответ подскажет, что сделать ключом и что значением, и это стоит назвать
> до кода.

## 🧠 Почему это корректно

### Почему в среднем `O(1)`, а в худшем `O(n)`

Хорошая хеш-функция раскладывает ключи по бакетам **равномерно**, поэтому при `n` ключах и `m`
бакетах средняя длина цепочки — `n/m`: в виджете роста выше это 6 ключей на 8 бакетов, меньше
одного на бакет. Пока таблица растёт вовремя, `n/m` не больше константы, и операция в среднем
стоит O(1). Но гарантий нет: если все ключи дают один бакет (плохой хеш или подобранный
злоумышленником вход), цепочка вырастает до `n`, и Get/Put/Delete становятся O(n). Поэтому
хеш-таблица — про **среднее**, а не про худший случай.

Корректность от качества хеша не зависит: хватает того, что для одного ключа он всегда даёт одно
число. А скорость зависит целиком. Хорошая хеш-функция перемешивает биты ключа, и даже близкие
ключи расходятся по разным бакетам.

## 🐹 Как устроен `map` в Go (под капотом)

Встроенный `map[K]V` — хеш-таблица, та же идея, что выше: ключ превращается в номер ячейки,
операции в среднем O(1), а когда записей становится много, таблица перестраивается — переезжает в
бо́льшую. Внутри она устроена хитрее учебных цепочек, но для работы сейчас хватит четырёх следствий.

### Практические следствия

- **Хеш ключа не бесплатен.** Для строкового ключа хеш считается за O(длины) — `Get`/`Put` это
  O(L), где L — длина ключа, а не «O(1) из воздуха».
- **`map` не потокобезопасен.** Конкурентная запись из нескольких горутин — это **фатальная
  ошибка** `fatal error: concurrent map writes`: в отличие от паники, её не перехватить
  `recover`, процесс падает целиком. Нужен `sync.RWMutex` или `sync.Map`.
- **Нельзя взять адрес элемента** (`&m[k]` запрещён): рост двигает записи в памяти.
- **Порядок обхода случаен** и меняется от запуска к запуску — нужен порядок, собирай ключи в
  срез и сортируй.

### Цепочки против открытой адресации

Здесь коллизии решены **цепочками** (список в бакете) — просто и устойчиво к высокой загрузке.
Альтернатива — **открытая адресация**: при коллизии ищут следующий свободный слот в том же массиве
(линейное/квадратичное пробирование — перебор слотов подряд или с растущим шагом). Она плотнее по
памяти и дружелюбнее к кэшу (нет отдельных списков), но чувствительна к загрузке и сложнее в
удалении: нужны «надгробия» — метки «здесь удалили», чтобы поиск не обрывался на дыре. Выбор —
компромисс память/скорость; промышленные таблицы (включая Go `map`) — это инженерные гибриды.

Ниже — как устроен такой гибрид в рантайме Go: сначала прежнее устройство (до Go 1.23 включительно, его до сих пор спрашивают на собеседованиях), потом нынешнее.

### Бакеты по 8 слотов и `tophash` (исторический дизайн, Go ≤ 1.23)

- map описывается заголовком `hmap`: число элементов, `B` (log₂ числа бакетов), указатель на массив
  бакетов, `oldbuckets` (для роста) и **случайный сид `hash0`** (seed — случайное число, подмешиваемое в хеш).
- Бакет (`bmap`) хранит **до 8** пар ключ/значение. В памяти: 8 байт `tophash`, затем 8 ключей,
  затем 8 значений (ключи и значения сгруппированы отдельно — экономит выравнивание), затем
  указатель на overflow-бакет.
- Номер бакета — это **младшие `B` бит** хеша; `tophash` (старший байт хеша) кэшируется для
  быстрого отсева до полного сравнения ключа.
- Коллизия: линейный скан 8 слотов бакета; не влезло — **overflow-бакет** (цепочка *бакетов*, а не
  отдельных записей). То есть Go использует бакетное хеширование, а не «одна запись на бакет».

### Load factor 6.5 и инкрементальный рост (тоже Go ≤ 1.23)

- Порог загрузки — **6.5** элемента на бакет в среднем (не 0.75 — бакеты вместительные). Превысили
  → таблица **удваивается**. Бывает и «рост того же размера», чтобы уплотнить разросшиеся
  overflow-цепочки.
- Рост **инкрементальный**: старые бакеты (`oldbuckets`) не перехешируются разом. Каждая вставка
  или удаление заодно переносит один-два старых бакета в новые — поэтому нет долгой паузы на
  rehash, цена размазана по операциям.

### Случайный сид — это про безопасность

`hash0` случаен для каждого map. Отсюда два следствия: **порядок итерации намеренно
рандомизирован** (полагаться на него нельзя) и, главное, это **защита от hash-flooding** (атаки
подбором ключей) — без случайного сида злоумышленник подобрал бы ключи в один бакет и превратил
O(1) в O(n), то есть положил бы сервис (DoS — отказ в обслуживании). Та же идея — в пакете
`hash/maphash` с `MakeSeed`.

### Go 1.24: переход на Swiss Tables

С **Go 1.24** встроенный map переписан на **Swiss Tables**
([`internal/runtime/maps`](https://github.com/golang/go/tree/go1.24.0/src/internal/runtime/maps)):
открытая адресация группами по 8 слотов с компактным **control word** (по байту на слот: пусто /
удалён / 7 бит хеша), который сканируется параллельно (SIMD-дружелюбно: одна инструкция
процессора проверяет сразу несколько байт). Это заметно быстрее и экономнее по памяти на больших
map. Рост тоже другой: map делится на таблицы не больше 1024 слотов, и за раз удваивается одна
такая таблица, — пауза ограничена её размером; порог — 7 занятых слотов из 8. Для программиста
поведение не изменилось — map по-прежнему неупорядочен и со случайным сидом. Почему именно Swiss
Tables, с виджетом `matchH2`, — в главе [«Структуры данных в экосистеме
Go»](go-stdlib-structures.md#-разбор-почему-map-с-go-124--это-swiss-tables).

## ⚠️ Типичные ошибки

1. **Считать O(1) гарантированным** — это среднее; при плохом хеше или высокой загрузке — O(n).
2. **Забыть про коллизии** в собственной реализации — без разрешения коллизий ключи затирают друг друга.
3. **Не расширять таблицу** — растущая загрузка превращает цепочки в линейный поиск.
4. **Рассчитывать на порядок** ключей `map` в Go — его нет, итерация случайна (и сид случаен).
5. **Мутировать ключ после вставки** (для сложных ключей) — хеш «уедет», и ключ не найдётся.
6. **Конкурентная запись в `map`** из нескольких горутин — фатальная ошибка «concurrent map writes» (`recover` не спасёт — процесс падает); нужен `sync.RWMutex` или `sync.Map`.
7. **Брать адрес элемента `map`** (`&m[k]`) — запрещено: рост таблицы перемещает записи в памяти.

**Прорешать целиком** — лестница из трёх ступеней, снизу вверх. Это не список «решить
всё», а маршрут с точкой остановки: закрыл **основу** — глава сдана, добивка не обязательна.

**🟢 Разогрев** — одна форма приёма в чистом виде:

- [Contains Duplicate](https://leetcode.com/problems/contains-duplicate/) (LeetCode 217) — множество «видели ли», форма (в) без соседей
- [Valid Anagram](https://leetcode.com/problems/valid-anagram/) (LeetCode 242) — счётчик: прибавь за одну строку, вычти за другую
- [First Unique Character in a String](https://leetcode.com/problems/first-unique-character-in-a-string/) (LeetCode 387) — счётчик и второй проход; в тренажёре: `hashtable.FirstUniqueChar`

**🔵 Основа** — планка главы: три задачи подряд без подглядывания в разбор:

- [Two Sum](https://leetcode.com/problems/two-sum/) (LeetCode 1) — в тренажёре: `hashtable.TwoSum`
- [Group Anagrams](https://leetcode.com/problems/group-anagrams/) (LeetCode 49) — в тренажёре: `hashtable.GroupAnagrams`
- [Longest Consecutive Sequence](https://leetcode.com/problems/longest-consecutive-sequence/) (LeetCode 128) — в тренажёре: `hashtable.LongestConsecutive`

**🔴 Добивка** — когда основа идёт уверенно:

- [4Sum II](https://leetcode.com/problems/4sum-ii/) (LeetCode 454) — Two Sum на двух парах массивов: в `map` кладём, сколько раз встретилась сумма пары
- [Isomorphic Strings](https://leetcode.com/problems/isomorphic-strings/) (LeetCode 205) — две таблицы «буква → буква», в обе стороны
- [Subarray Sum Equals K](https://leetcode.com/problems/subarray-sum-equals-k/) (LeetCode 560) — сверх главы: форма (а) на префиксных суммах, разбор — в главе [«Префиксные суммы»](prefix-sums.md)

> 🧭 **Не пошла задача из основы?** Чаще всего ключ выбран раньше, чем вопрос. Вернись к
> [таблице форм](#-хеширование-как-приём-четыре-формы) и назови вслух, что перебор ищет вложенным
> циклом. Затем реши, что будет ключом и что значением. Two Sum: ключ — число, значение —
> индекс, и проверка идёт до записи. Group Anagrams: ключ — буквы по алфавиту. Longest
> Consecutive: цепочку считай только от `x` без `x−1` и обходи множество, а не `nums`.

> 🏁 **Глава сдана выше.** Дальше — инженерный кейс: ключ идемпотентности в платёжном сервисе —
> почему здесь хеш-множество, а не Bloom-фильтр.

## 🏗️ Инженерный кейс

> **Ситуация.** Ты пишешь платёжный сервис. Клиент шлёт запрос с заголовком `Idempotency-Key` —
> уникальной строкой на каждую операцию. Твоя задача: **не обработать один и тот же ключ дважды** (иначе
> спишешь деньги повторно). Поток — десятки миллионов ключей в сутки, ответ «видели ли уже» нужен за
> миллисекунды.

Соблазн — вспомнить [Bloom-фильтр](probabilistic-structures.md) (вероятностное множество: мало памяти,
но иногда ложно отвечает «видели»): он же дёшев по памяти. Но здесь цена
ошибки — **чужие деньги**, и это меняет выбор. Прежде чем писать код, ответь на три вопроса инженера:

При объёме — шардирование или Redis SET, но именно точная, не вероятностная.">
<div class="algo-challenge__q">Чем проверять, что ключ уже обработан, если ошибка недопустима?</div>

**Вывод.** Первый вопрос инженера — **«нужна точность или сойдёт приближение?»**. Деньги и безопасность →
точная структура (хеш-множество), пусть ценой памяти и шардирования. Приблизительное «видели ли» с дешёвой
ценой промаха → вероятностная. Одна и та же задача «дедуп», а выбор — противоположный.

## 🔗 Связанные шаблоны

**Не спутай с соседом** (вся таблица — в [руководстве по выбору](pattern-selection-guide.md#путаемые-пары-что-обязано-быть-верно)):

- если массив уже отсортирован и нужна пара с заданной суммой — [Два указателя](two-pointers.md), а не Хеш-таблица: оба решения линейны, но хеш-таблица хранит виденные числа в памяти O(n), а указателям хватает O(1).
- если массив не отсортирован, а сортировать нельзя или потеряются нужные исходные индексы — Хеш-таблица, а не [Два указателя](two-pointers.md): сортировка потеряет исходные индексы и сама стоит O(n log n), а таблица «значение → индекс» отвечает за один проход.
- если цепочка, где у каждого узла не больше одного следующего, а память нужна O(1) — [Быстрый и медленный указатели](fast-slow-pointers.md), а не Хеш-таблица: хеш-множество посещённых тоже найдёт цикл, но платит O(n) памяти.
<!-- pairs:end -->

- **[Two Pointers](two-pointers.md)** — хеш-таблица часто заменяет два указателя, когда нужен индекс/порядок исходных элементов.
- **[Trie](trie-structure.md)** — для префиксных операций по строкам, где хеш-множество не помогает.
- **[Строковые алгоритмы](string-algorithms.md)** — rolling hash (Рабин–Карп: хеш окна строки, пересчитываемый при сдвиге за O(1)) использует ту же идею хеширования.
- **[BST](bst-structure.md)** — когда нужен порядок ключей, которого хеш-таблица не даёт.
- **[Ревью чужого кода](code-review.md)** — случай 2 меняет «случайно квадратичный» вложенный
  цикл на `map` ровно за счёт этого компромисса время/память.

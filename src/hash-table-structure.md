> 🎬 **Интерактив устроен по принципу «функция → её визуализация».** Каждая операция ниже идёт со
> своим виджетом сразу после кода: вставка и поиск. Подсвечен текущий бакет и сканируемая запись.
> Виджеты работают в собранной книге.

## 🧱 Как устроено

Хеш-таблица — это **массив бакетов**. Хеш-функция отображает ключ в индекс бакета; при разрешении
коллизий **цепочками** каждый бакет хранит маленький список записей `{ключ, значение}`.

```go
type entry struct{ key, val int }

type HashMap struct {
    buckets [][]entry // массив бакетов; каждый бакет — цепочка записей
}

func hash(key int) int { return key } // упрощённо; реальная — перемешивает биты ключа
```

```
hash(key) % 4:

бакет 0:  [8]
бакет 1:  [1] → [5]        ← коллизия: 1 и 5 дают один бакет
бакет 2:  ∅
бакет 3:  [3]
```

Три факта, которые держат всё:

1. **Ключ → индекс за O(1).** Хеш-функция мгновенно говорит, в каком бакете искать; не нужно
   просматривать всю таблицу. Это и есть источник «O(1) в среднем».
2. **Коллизии неизбежны.** Бакетов меньше, чем возможных ключей, поэтому разные ключи иногда
   делят бакет. Цепочка (список в бакете) разруливает это: внутри бакета — линейный поиск.
3. **Скорость зависит от загрузки.** Если записей примерно столько же, сколько бакетов
   (`n/m ≈ const`), цепочки коротки и операции O(1). Когда таблица заполняется, её **расширяют**
   (удваивают `m`) и перехешируют — иначе цепочки растут и всё замедляется.

## ➕ Вставка: `Put`

`Put` вычисляет бакет по хешу, проверяет, нет ли уже такого ключа (тогда обновляет значение), и
иначе **добавляет запись в цепочку** бакета. Коллизия — это просто непустая цепочка.

```go
func (h *HashMap) Put(key, val int) {
    i := hash(key) % len(h.buckets)   // в какой бакет
    for _, e := range h.buckets[i] {  // уже есть такой ключ?
        if e.key == key {
            e.val = val               // обновляем на месте
            return
        }
    }
    h.buckets[i] = append(h.buckets[i], entry{key, val}) // коллизия → в цепочку
}
```

> 💡 **Демонстрация вставки.** В таблице с 4 бакетами лежат ключи `1,5,3,8`. Вставляем `9`:
> `hash(9) % 4 = 1` — бакет `1`, где уже есть цепочка `[1, 5]`. Ключа `9` там нет, поэтому он
> **дописывается в конец цепочки** (коллизия!). Подставь свои ключи и число бакетов.

## 🔎 Поиск: `Get`

`Get` идёт в тот же бакет (хеш детерминирован) и **сканирует его цепочку**, сравнивая ключи. Пока
цепочки коротки, это O(1).

```go
func (h *HashMap) Get(key int) (int, bool) {
    i := hash(key) % len(h.buckets)   // тот же бакет
    for _, e := range h.buckets[i] {  // сканируем цепочку
        if e.key == key {
            return e.val, true        // нашли
        }
    }
    return 0, false                   // нет в бакете
}
```

> 💡 **Демонстрация поиска.** Ищем `5` в той же таблице: `hash(5) % 4 = 1` — бакет `1`, сканируем
> цепочку `[1, 5]`: `1` — мимо, `5` — совпало. Попробуй ключ `7` (бакет `3`, где только `3`) —
> цепочка пройдена, ключа нет.

## 🗑️ Удаление: `Delete`

Удаление — это тот же поиск бакета по хешу, затем **вырезание записи из цепочки** (как удаление из
[связного списка](linked-list-structure.md) или среза). Бакет остаётся, цепочка укорачивается.

```go
func (h *HashMap) Delete(key int) {
    i := hash(key) % len(h.buckets)
    chain := h.buckets[i]
    for j, e := range chain {
        if e.key == key {
            h.buckets[i] = append(chain[:j], chain[j+1:]...) // вырезаем из цепочки
            return
        }
    }
}
```

## 🧠 Почему это корректно

### Почему в среднем `O(1)`, а в худшем `O(n)`

Хеш-функция (хорошая) распределяет ключи по бакетам **равномерно**, поэтому при `n` ключах и `m`
бакетах средняя длина цепочки — `n/m`. Держа `n/m` ограниченным константой (расширяя таблицу),
получаем O(1) на операцию в среднем. Но гарантий нет: если все ключи дают один бакет (плохой хеш
или враждебный вход), цепочка вырастает до `n`, и Get/Put/Delete становятся O(n). Поэтому хеш-
таблица — про **среднее**, а не про худший случай.

### Почему Get и Put согласованы

Обе операции вычисляют бакет **одним и тем же** `hash(key) % m`, поэтому ключ всегда ищется ровно
там, куда был положен. Это ломается при изменении `m`: после расширения таблицы **все** ключи
надо перехешировать (`% m` изменился) — иначе Get пойдёт не в тот бакет. Поэтому resize — это
дорогая O(n) операция, но редкая (амортизированно дешёвая).

### Почему хеш-функция критична

Корректность поиска не зависит от качества хеша (лишь бы он был детерминирован), а вот
**скорость** — целиком. Плохой хеш (например `key % m`, где ключи кратны `m`) скучивает всё в
немногих бакетах. Хорошая хеш-функция перемешивает биты ключа так, что даже близкие ключи
расходятся по разным бакетам.

## ⚙️ Цена на практике

### Цепочки против открытой адресации

Здесь коллизии решены **цепочками** (список в бакете) — просто и устойчиво к высокой загрузке.
Альтернатива — **открытая адресация**: при коллизии ищут следующий свободный слот в том же массиве
(линейное/квадратичное пробирование). Она плотнее по памяти и дружелюбнее к кэшу (нет отдельных
списков), но чувствительна к загрузке и сложнее в удалении (нужны «надгробия»). Выбор — компромисс
память/скорость; промышленные таблицы (включая Go `map`) — это инженерные гибриды.

### Коэффициент загрузки и перехеширование

Ключевой параметр — **load factor** `n/m`. Когда он превышает порог (часто ~0.75), таблицу
**расширяют** (обычно удваивают `m`) и перехешируют все ключи. Это O(n), но происходит редко,
поэтому амортизированная стоимость вставки остаётся O(1). Забыл расширять — цепочки растут, и
«O(1)» превращается в O(n).

## 🐹 Как устроен `map` в Go (под капотом)

`map[K]V` в Go — это не учебные цепочки из этой главы, а сильно оптимизированная хеш-таблица в
рантайме. Знать её устройство полезно и для собеседований по Go, и чтобы понимать её поведение.

### Бакеты по 8 слотов и `tophash` (исторический дизайн, Go ≤ 1.23)

- map описывается заголовком `hmap`: число элементов, `B` (log₂ числа бакетов), указатель на массив
  бакетов, `oldbuckets` (для роста) и **случайный сид `hash0`**.
- Бакет (`bmap`) хранит **до 8** пар ключ/значение. В памяти: 8 байт `tophash`, затем 8 ключей,
  затем 8 значений (ключи и значения сгруппированы отдельно — экономит выравнивание), затем
  указатель на overflow-бакет.
- Номер бакета — это **младшие `B` бит** хеша; `tophash` (старший байт хеша) кэшируется для
  быстрого отсева до полного сравнения ключа.
- Коллизия: линейный скан 8 слотов бакета; не влезло — **overflow-бакет** (цепочка *бакетов*, а не
  отдельных записей). То есть Go использует бакетное хеширование, а не «одна запись на бакет».

### Load factor 6.5 и инкрементальный рост

- Порог загрузки — **6.5** элемента на бакет в среднем (не 0.75 — бакеты вместительные). Превысили
  → таблица **удваивается**. Бывает и «рост того же размера», чтобы уплотнить разросшиеся
  overflow-цепочки.
- Рост **инкрементальный**: старые бакеты (`oldbuckets`) не перехешируются разом. Каждая запись
  **эвакуирует** один-два старых бакета в новые — поэтому нет долгой паузы на rehash, цена размазана
  по операциям.

### Случайный сид — это про безопасность

`hash0` случаен для каждого map. Отсюда два следствия: **порядок итерации намеренно
рандомизирован** (полагаться на него нельзя) и, главное, это **защита от hash-flooding** — без
случайного сида злоумышленник подобрал бы ключи в один бакет и превратил O(1) в O(n) (DoS-атака).
Та же идея — в пакете `hash/maphash` с `MakeSeed`.

### Go 1.24: переход на Swiss Tables

С **Go 1.24** встроенный map переписан на **Swiss Tables** (`internal/runtime/maps`): открытая
адресация группами по 8 слотов с компактным **control word** (по байту на слот: пусто / удалён /
7 бит хеша), который сканируется параллельно (SIMD-дружелюбно). Это заметно быстрее и экономнее по
памяти на больших map. Для программиста поведение не изменилось — map по-прежнему неупорядочен и со
случайным сидом; переключатель — `GODEBUG=swissmap`.

### Практические следствия

- **Хеш ключа не бесплатен.** Для строкового ключа хеш считается за O(длины) — `Get`/`Put` это
  O(L), а не «O(1) из воздуха».
- **`map` не потокобезопасен.** Конкурентная запись из нескольких горутин — это паника
  («concurrent map writes»); нужен `sync.RWMutex` или `sync.Map`.
- **Нельзя взять адрес элемента** (`&m[k]` запрещён): рост двигает записи в памяти.
- **Порядок итерации случаен** — нужен порядок, собирай ключи в срез и сортируй.

## ⚠️ Типичные ошибки

1. **Считать O(1) гарантированным** — это среднее; при плохом хеше или высокой загрузке — O(n).
2. **Забыть про коллизии** в собственной реализации — без разрешения коллизий ключи затирают друг друга.
3. **Не расширять таблицу** — растущая загрузка превращает цепочки в линейный поиск.
4. **Рассчитывать на порядок** ключей `map` в Go — его нет, итерация случайна (и сид случаен).
5. **Мутировать ключ после вставки** (для сложных ключей) — хеш «уедет», и ключ не найдётся.
6. **Конкурентная запись в `map`** из нескольких горутин — паника «concurrent map writes»; нужен `sync.RWMutex` или `sync.Map`.
7. **Брать адрес элемента `map`** (`&m[k]`) — запрещено: рост таблицы перемещает записи в памяти.

## 🏋️ Тренажёр

Реализовать `Put`/`Get`/`Delete` на цепочках (срез бакетов) — отличное упражнение, и в нём
прячется вся механика главы: индекс бакета по хешу, обновление против вставки, вырезание из
цепочки и, главное, **ресайз с перехешированием** при росте загрузки.

```bash
cd exercises
go test ./hashtable/                 # ваша реализация (красные)
go test -tags solution ./hashtable/  # эталон (зелёные)
```

Пакет `hashtable`: `NewHashMap`, `HashMap.Put` / `Get` / `Delete` / `Len`. Цепочки — срез
бакетов `[][]entry`, расширение при коэффициенте загрузки выше `0.75`. Подумай, почему индекс
бакета надо нормализовать по знаку (`key % m` в Go бывает отрицательным) и почему после resize
старые `% m` уже не годятся.

На практике же хеш-таблица (`map`) — рабочая лошадка почти во всех пакетах тренажёра: частоты в
[скользящем окне](sliding-window.md), множество посещённых в [графах](graphs.md), Two Sum в
[двух указателях](two-pointers.md).

> 🧭 **Зачем нужна куча.** Нужен минимум из набора, который всё время меняется: задачи по
> приоритету, события по времени, таймеры. Несортированный срез добавляет за O(1), но минимум
> ищет полным просмотром — O(n). Отсортированный отдаёт минимум за O(1), но каждая вставка
> сдвигает хвост — O(n). Куча берёт середину: вставка и извлечение минимума — за O(log n), а
> посмотреть минимум — O(1). Платит она тем, что порядка в ней нет: известен только минимум.
> Как она этого добивается — массив, читаемый как дерево, и два просеивания — вся эта глава.
> Просеивание — элемент обменами с родителем или ребёнком поднимается или опускается на своё
> место. Применения ([Две кучи](two-heaps.md), [Top K](top-k-elements.md),
> [K-way Merge](k-way-merge.md)) — в главах-паттернах.

## 🧱 Как устроена куча

Куча хранится в **обычном массиве**, но читается как полное двоичное дерево. Никаких указателей:
связь «родитель–ребёнок» задаётся арифметикой индексов. Здесь строим **min-кучу**: родитель ≤
детей, минимум в корне; у **max-кучи** наоборот.

```go
type Heap struct {
    data []int // min-куча: data[(i-1)/2] <= data[i]
}

func parent(i int) int { return (i - 1) / 2 }
func left(i int) int   { return 2*i + 1 }
func right(i int) int  { return 2*i + 2 }
```

Один и тот же массив — деревом сверху и рядом снизу:

<div class="algo-fig" data-fig="tree" data-tree="1|[0](3|[1](7|[3],4|[4]),2|[2](5|[5],_))" data-array="1,3,2,7,4,5" data-array-label="data" data-link="index" data-caption="Min-куча [1, 3, 2, 7, 4, 5]: под узлом — его индекс в массиве; дети i — это 2i+1 и 2i+2. Наведи на узел — загорится его ячейка, и наоборот"></div>

Три факта, которые держат всё:

1. **Инвариант кучи — частичный, а не полный порядок.** Родитель ≤ детей, но `3` и `2` (соседи)
   между собой не упорядочены. Поэтому куча **не** заменяет отсортированный массив — она даёт
   только быстрый доступ к экстремуму (минимуму или максимуму), а не полный порядок.
2. **Дерево всегда полное.** Узлы заполняют уровни слева направо без дыр — поэтому массив плотный,
   а высота — `log₂ n`, округлённый вниз: столько рёбер от корня до самого глубокого листа (в узлах — на один больше,
   как в главе об обходе в глубину). Отсюда O(log n) у обеих операций.
3. **Минимум — в корне.** Из инварианта по индукции: корень ≤ всех. `Peek` (посмотреть минимум, не вынимая) — это `data[0]`, O(1).

## ➕ Вставка: `Push` (просеивание вверх)

Кладём новый элемент **листом в конец массива** (чтобы дерево осталось полным), а затем
**просеиваем вверх**: пока он меньше родителя — меняем их местами. Так нарушение инварианта
«всплывает» к корню, остальное дерево не трогаем.

```go
func (h *Heap) Push(val int) {
    h.data = append(h.data, val)   // новый лист в конец массива
    i := len(h.data) - 1
    for i > 0 {                    // просеивание вверх
        parent := (i - 1) / 2
        if h.data[parent] <= h.data[i] {
            break                  // порядок восстановлен
        }
        h.data[i], h.data[parent] = h.data[parent], h.data[i]
        i = parent
    }
}
```

> 💡 **Демонстрация вставки.** В кучу `[1,3,5,7,4,6]` добавляем `2`. Новый лист встаёт в конец
> (индекс 6), его родитель — индекс 2, там `5`: `5 <= 2` ложно — обмен. Новый родитель — корень
> `1`: `1 <= 2` истинно — стоп. `2` остановилась посреди дерева: всплытие идёт не до корня, а до
> первого родителя, который не больше. Подставь `0` — всплывёт до самого корня.

## 🔺 Извлечение: `Pop` (просеивание вниз)

Минимум — это корень. Чтобы его извлечь и сохранить полноту дерева: забираем корень,
**последний лист переносим в корень**, отрезаем хвост и **просеиваем вниз** — меняем узел с
**меньшим из детей**, пока он не окажется не больше обоих.

```go
func (h *Heap) Pop() int {
    min := h.data[0]               // корень — минимум
    last := len(h.data) - 1
    h.data[0] = h.data[last]       // последний лист → в корень
    h.data = h.data[:last]         // отрезаем хвост
    i, n := 0, len(h.data)
    for {                          // просеивание вниз
        l, r, small := 2*i+1, 2*i+2, i
        if l < n && h.data[l] < h.data[small] { small = l }
        if r < n && h.data[r] < h.data[small] { small = r }
        if small == i { break }    // порядок восстановлен
        h.data[i], h.data[small] = h.data[small], h.data[i]
        i = small
    }
    return min
}
```

> 💡 **Демонстрация извлечения.** Из `[1,2,5,4,3,6,7,9,8,10,11,12]` извлекаем минимум `1`.
> Последний лист `12` переезжает в корень, затем тонет на три уровня: на каждом сравниваем его с
> детьми и меняем с меньшим — сначала с `2`, потом с `3`, потом с `10`, — пока оба ребёнка не
> станут больше или детей не останется. Возвращается `1`, итог — `[2,3,5,4,10,6,7,9,8,12,11]`.

## 🏗️ Построение кучи из массива за O(n)

Часто куча нужна не пустая, а сразу из готового массива. Наивно — сделать `n` вставок `Push`, это
`O(n log n)`. Но есть способ лучше: **heapify** (построение Флойда — того же Флойда, которому приписывают поиск цикла, но алгоритм другой) строит кучу
**на месте за O(n)**.

Идея: берём массив как есть и **просеиваем вниз** каждый узел, начиная с **последнего внутреннего** узла (у
него есть дети; индекс `n/2−1`) и двигаясь к корню. Почему `n/2−1`: левый ребёнок узла `i` —
`2i+1`, он существует, пока `2i+1 ≤ n−1`, то есть `i ≤ n/2−1`. При `n = 9` (виджет ниже) это
узлы 0…3. Вторая половина массива — индексы `n/2 … n−1` — это **листья**: каждый лист уже
куча из одного элемента, их трогать не нужно.

Листай «›»: массив превращается в min-кучу. Зелёная рамка — узел, чьё поддерево уже куча: сначала
это только листья, потом после каждого `siftDown(i)` к ним добавляется всё поддерево `i`. Так видно,
что просеивание всегда опирается на готовые кучи под собой, а внизу, где узлов больше всего, пути
самые короткие. Синий — просеиваемое значение (после обмена оно уже на месте ребёнка), синяя
обводка — дети, с которыми его сравнивают (на кадре обмена — место, откуда оно ушло). Первый вызов
(узел 1, `i = 3`) — один кадр остановки: 1 не больше детей 2 и 5, опускать нечего. Первый спуск
(узел 7, `i = 2`) идёт по строкам `siftDown`, и видно, как `small` выбирает меньшего из троих.
Остальные вызовы — кадр на уровень: обмен («дети 1 и 8, меньший 1 < 4 → обмен») или остановка:

### Почему это O(n), а не O(n log n)

Ключ — **где живёт большинство узлов**. В полном дереве **половина** узлов — листья (просеивать 0),
четверть — на уровень выше (просеивать ≤1), восьмая часть — ≤2, и так далее. Дорогих просеиваний
(близких к `log n`) — единицы, у самого корня. Складывая «число узлов × их высота» (Σ ниже — сумма по всем k = 0, 1, 2, …):

```
n/2·0 + n/4·1 + n/8·2 + n/16·3 + … = n·Σ k/2^(k+1) ≈ n
```

Читается так: половина узлов не двигается, четверть — на шаг, восьмая — на два… Каждая
следующая группа вдвое меньше, а шаг у неё лишь на один больше, поэтому сумма не разгоняется:
сложи хоть все слагаемые, выйдет не больше `n`. На полном дереве это видно и на числах: сумма
высот всех узлов при `n = 1023` равна 1013, при `n = 2²⁰` — 1 048 575, то есть почти ровно `n`. Контринтуитивно, но **построить кучу дешевле,
чем один раз её отсортировать**: сортировка — `O(n log n)`, а heapify — `O(n)`. (Именно с heapify
начинается [пирамидальная сортировка](#-пирамидальная-сортировка): построили кучу за `O(n)`,
потом `n − 1` раз сняли корень за `O(log n)`.)

Замер подтверждает выигрыш, но скромнее теории: на 100 тысячах и миллионе элементов Флойд
быстрее `n` вставок вдвое, а не в `log n` раз, и делает 2 выделения памяти вместо 28–38.

## 🔃 Пирамидальная сортировка

Куча даёт ещё один способ отсортировать массив за `O(n log n)` — на месте, без дополнительной
памяти. Строим из массива кучу (heapify за O(n)), затем `n − 1` раз снимаем корень в конец
массива и восстанавливаем кучу просеиванием вниз. Здесь куча **максимальная**: родитель ≥
детей, хотя глава до сих пор строила минимальную. Почему — снятый корень кладём в конец
массива, на место, которое куча освободила, а в конце массива по возрастанию стоит наибольший.
Гарантированные O(n log n) и **O(1) памяти** — но прыжки по индексам кучи плохо ложатся в кэш.

```go
func heapSort(a []int) {
    n := len(a)
    for i := n/2 - 1; i >= 0; i-- { // построить кучу за O(n)
        siftDown(a, i, n)
    }
    for end := n - 1; end > 0; end-- {
        a[0], a[end] = a[end], a[0] // максимум — в конец
        siftDown(a, 0, end)         // восстановить кучу на [0, end)
    }
}

func siftDown(a []int, i, size int) {
    for {
        l, r, largest := 2*i+1, 2*i+2, i
        if l < size && a[l] > a[largest] {
            largest = l
        }
        if r < size && a[r] > a[largest] {
            largest = r
        }
        if largest == i {
            return
        }
        a[i], a[largest] = a[largest], a[i]
        i = largest
    }
}
```

Листай «›»: сначала строится максимальная куча, затем максимум (корень) меняется с концом кучи —
**отсортированный хвост справа растёт**, а куча чинится просеиванием. Под массивом — он же в
виде дерева кучи. Листинг виджета включает тело `siftDown`, и по одному вызову в каждой фазе идёт
по строкам. В построении это узел 2 (`i = 1`), первый, который опускается: вызов перед ним (узел 8,
`i = 2`) — один кадр остановки, 8 не меньше детей 3 и 7. В извлечении — корень 3 при `end = 5`:
в этом вызове работают все строки тела. Здесь синий узел и плашка `i` — позиция `i` (после обмена
там уже больший ребёнок), синяя обводка и плашка `largest` — больший (на кадре обмена там уже
опущенное значение), янтарный пунктир — дети, с которыми сравнивают. Видно, на каком уровне
`largest == i` останавливает спуск. Остальные вызовы — кадр на уровень: «дети 9 и 8,
больший 9 > 5 → обмен». Узлы хвоста уже вне кучи, их рёбра пунктирные:

Пирамидальная сортировка неустойчива: обмен корня с концом кучи перебрасывает элемент через
весь массив, мимо равных ему. Сравнение с остальными сортировками — в
[главе о сортировках](sorting.md#-сравнение-алгоритмов); функция `HeapSort` для тренировки лежит
в пакете `sorting` — [решай её прямо в книге](sorting.md#-реши-прямо-здесь--пакет-sorting).

## 🧠 Почему это корректно

### Почему минимум всегда в корне

Инвариант «родитель ≤ детей» по индукции даёт: корень ≤ своих детей ≤ их детей ≤ … ≤ всех узлов.
Значит наименьший элемент — в корне, и `Peek` берёт его за O(1). (Для max-кучи симметрично:
родитель ≥ детей, максимум в корне.)

### Почему просеивание восстанавливает инвариант

И `Push`, и `Pop` создают **ровно одно** локальное нарушение: новый лист может быть меньше
родителя (Push), а перенесённый в корень лист — больше детей (Pop). Просеивание двигает это
нарушение по **одному ребру за шаг** к листу или к корню, меняя местами с родителем или ребёнком; в
остальном дереве инвариант не трогается. Когда менять больше не нужно, единственное нарушение
исчезло, а в остальных местах его и не было. Длина пути ≤ высоты, поэтому O(log n).

### Почему именно с меньшим ребёнком вниз

При просеивании вниз меняться надо с **меньшим** из двух детей. Иначе наверх поднимется не
наименьший — и больший ребёнок окажется родителем меньшего, снова нарушив инвариант. Меньший
ребёнок ≤ и узла, и второго ребёнка, поэтому после обмена он корректно становится родителем.

## ⚙️ Цена на практике

### Куча против отсортированной структуры

Если нужен **только** экстремум, куча бьёт отсортированный массив/дерево: `Push`/`Pop` за
O(log n) против O(n) на поддержание полного порядка, который тебе не нужен. Но куча **не**
отвечает на «найди произвольный ключ» или «дай k-й по порядку» — там нужен BST или сортировка.

### Массив вместо указателей — и это важно

Куча на массиве плотная и дружелюбна к кэшу (никаких разбросанных узлов, как в дереве на
указателях), а связи — это арифметика индексов. Поэтому на практике куча часто быстрее «честного»
дерева той же асимптотики.

### В Go куча — это `container/heap`

[`container/heap`](https://pkg.go.dev/container/heap) — та же куча, что ты написал выше,
разрезанная пополам. Просеивания делает пакет; от тебя — срез и пять методов. `Len`, `Less` и
`Swap` говорят пакету, как сравнивать и менять местами; `Push` и `Pop` только дописывают элемент
в хвост и отрезают его с хвоста:

```go
type IntHeap []int // min-куча

func (h IntHeap) Len() int           { return len(h) }
func (h IntHeap) Less(i, j int) bool { return h[i] < h[j] } // < — min-куча, > — max-куча
func (h IntHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }

func (h *IntHeap) Push(x any) { *h = append(*h, x.(int)) } // только дописать в хвост

func (h *IntHeap) Pop() any { // только отрезать хвост
    old := *h
    n := len(old)
    x := old[n-1]
    *h = old[:n-1]
    return x
}
```

Пользуются кучей через функции пакета, а не через свои методы:

```go
h := &IntHeap{5, 2, 8, 1}
heap.Init(h)           // heapify за O(n): [1 2 8 5]
heap.Push(h, 0)        // твой Push, затем просеивание вверх: [0 1 8 5 2]
x := heap.Pop(h).(int) // 0 — минимум
```

**Почему твой `Pop` возвращает последний элемент, а не минимум.** На строке `x := old[n-1]`
спотыкаются все: кажется, что это ошибка. Нет: `heap.Pop(h)` работает в три шага. Меняет корень
с последним элементом: `h.Swap(0, n)`, где `n := h.Len() - 1`. Просеивает новый корень вниз, не
трогая хвост: `down(h, 0, n)`. И только потом зовёт твой `Pop` — минимум к этому моменту уже в
хвосте. В примере выше твой
`Pop` получает срез `[1 2 8 5 0]`: ноль — в конце. Это тот же `Pop`, что в разделе об извлечении
(последний лист — в корень, отрезать хвост, просеять вниз), только хвост отрезаешь ты. Так же
`heap.Push` сначала зовёт твой `Push` — лист в конец, — а потом просеивает его вверх. Отсюда
правило: свои `Push` и `Pop` напрямую не зовут — в обход пакета никто не просеет, и инвариант
сломается.

## ⚠️ Типичные ошибки

1. **Путают кучу с сортировкой** — куча даёт только экстремум, соседи по уровню не упорядочены.
2. **Просеивание вниз с бо́льшим ребёнком** — снова ломает инвариант; меняться надо с меньшим (для min-кучи).
3. **Pop без переноса последнего листа** — нарушает полноту дерева; нельзя просто «удалить корень».
4. **0/1-индексация детей** — для 0-индексации дети это `2i+1`/`2i+2`, родитель `(i−1)/2`; перепутал — выход за границы.
5. **Сравнение не туда (min vs max)** — знак в сравнении задаёт тип кучи; перепутал — получишь не тот экстремум.

## 🏗️ Инженерный кейс: таймеры рантайма Go

> **Ситуация.** В Go-сервисе одновременно живут тысячи таймеров: `time.Sleep`, `time.AfterFunc`,
> `context.WithTimeout` на каждый вызов с таймаутом. Рантайму всё время нужно знать, какой из них
> сработает первым, чтобы разбудить горутину ровно в срок, — а таймеры то и дело добавляются,
> срабатывают и отменяются.

Это приоритетная очередь в чистом виде: вставок много, и всё время нужен минимум. В
[`runtime/time.go`](https://github.com/golang/go/blob/master/src/runtime/time.go) у каждого
P — логического процессора планировщика Go, их столько, сколько `GOMAXPROCS`, — своя куча
таймеров, упорядоченная по сроку срабатывания `when`. Новый таймер встаёт в хвост и всплывает
(`addHeap`: `append`, затем `siftUp`) — это твой `Push`. Одно отличие: куча в рантайме
четверичная, у узла до четырёх детей, — дерево вдвое ниже, а операции те же. Почему не отсортированный срез и не map — в
[разборе на странице «Структуры данных в экосистеме Go»](go-stdlib-structures.md#-разбор-почему-таймеры-go--это-куча-а-не-список-и-не-map).

Отмена устроена хитрее. Остановленный таймер (`Stop`) может лежать в куче другого P, поэтому
рантайм его не вынимает, а только помечает — в исходнике такие таймеры зовутся зомби. Зомби,
добравшийся до корня, уходит обычным `Pop`; остальные копятся, и когда их набирается больше
четверти кучи, P-владелец чистит её одним проходом: на место
каждого мёртвого ставит последний элемент и отрезает хвост. После такой чистки порядок кучи сломан
во многих местах сразу.

Комментарий в исходнике говорит прямо: O(n), а не O(n log n) от n повторных вставок. Сортировка тоже даёт кучу, но платит O(n log n) за полный порядок, который не нужен.">
<div class="algo-challenge__q">Чем рантайм чинит порядок кучи после такой чистки?</div>
</div>

**Вывод.** Таймеры рантайма — все операции этой главы в одном месте: новый таймер всплывает,
ближайший срок лежит в корне, сработавший вынимается как `Pop`, а массовая чистка заканчивается
heapify за O(n). (Сверено с исходником Go 1.26.5: `addHeap`, `deleteMin`, `adjust` и `initHeap` в
`runtime/time.go`.)

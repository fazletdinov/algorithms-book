# 🧭 Инварианты и индукция: как доказывать, что код правильный

У каждой из восьми глав, которые ты уже прочитал, был раздел «🧠 Почему это корректно». В главе
о рекурсии он стоял на индукции, а начиная с разворота списка в нём всё чаще звучало слово
*инвариант* — утверждение, верное перед каждой итерацией цикла. В трёх последних главах —
окно, префиксные суммы, два указателя — на инварианте держался весь довод. Дальше по книге эти
разделы говорят на том же языке: *инвариант сохраняется*, *по индукции*, *граница монотонна*
(условие по индексу, раз став истинным, дальше истинно — граница «нет → да» одна).

Эта полуглава — про сам язык. Она короче остальных, но окупается во всех: научившись
формулировать инвариант, ты перестаёшь «верить, что работает» и начинаешь **знать,
почему работает** — а заодно получаешь самый надёжный способ находить off-by-one
(ошибку на единицу в границе цикла: `<` вместо `<=`) ещё до запуска тестов.

Разница между «прошло тесты» и «корректно» — инженерная, не академическая: тесты
проверяют конечный набор входов, инвариант — все сразу.

## 1. Инвариант цикла: утверждение, которое переживает итерацию

**Инвариант цикла** — утверждение о переменных, которое истинно перед первой
итерацией и остаётся истинным после каждой. Доказательство корректности цикла —
всегда одна и та же триада:

1. **Инициализация**: инвариант истинен до входа в цикл.
2. **Сохранение**: если он истинен в начале итерации, то истинен и в конце.
3. **Завершение**: инвариант вместе с условием выхода дают то, что мы хотели доказать.

Простейший пример, чтобы увидеть схему целиком:

```go
sum := 0
for i, x := range a {
    sum += x
    // здесь sum == a[0] + a[1] + ... + a[i] — инвариант для следующей итерации
}
```

Запись `a[0..i)` — **полуинтервал**: `[lo, hi)` значит, что `lo` входит, а `hi` нет. Так
`a[0..i)` — первые `i` элементов, `a[0]`, …, `a[i-1]`, ровно срез `a[:i]` в Go. Перед итерацией
с номером `i` утверждение звучит так: `sum` — сумма `a[0..i)`. Комментарий в коде стоит в конце
тела — там то же утверждение уже для следующего номера: сумма `a[0..i+1)`.

- Инициализация: до цикла `sum == 0` — сумма пустого префикса `a[0..0)`. ✓
- Сохранение: перед итерацией `i` было `sum == сумма a[0..i)`, прибавили `a[i]` — стало
  `сумма a[0..i+1)`, то есть утверждение верно перед итерацией `i+1`. ✓
- Завершение: после последней итерации `i+1 == len(a)`, значит `sum` — сумма `a[0..len(a))`,
  всего массива. ✓

Скучно? Да. Но ровно эта схема доказывает и окно из [главы о скользящем окне](sliding-window.md),
и бинарный поиск ниже, и алгоритм кратчайших путей Дейкстры дальше в книге — меняется только само
утверждение.

### Рабочий пример: бинарный поиск без страха off-by-one

Бинарный поиск — рекордсмен по ошибкам на границах. Инвариант превращает выбор
границ из гадания в вывод. Ищем первую позицию, где `a[i] >= target`
(lower bound — так её зовут в C++; с нижней границей Ω из главы о Big-O не путай) на полуинтервале `[lo, hi)`: позиция `lo` проверяется, `hi` — нет, он стоит за
последним проверяемым (`hi = len(a)`):

```go
lo, hi := 0, len(a) // ответ лежит в [lo, hi]: hi включён — ответом может быть len(a)
for lo < hi {
    mid := lo + (hi-lo)/2
    if a[mid] < target {
        lo = mid + 1 // a[mid] < target: ответ правее mid
    } else {
        hi = mid // a[mid] >= target: mid — кандидат, ответ не правее
    }
}
// lo == hi — интервал схлопнулся в единственную точку: это и есть ответ
```

Прогон на `a = [1, 3, 3, 5, 8]`, `target = 4` — по строке на итерацию:

```text
lo  hi  mid  a[mid]  ветка    что теперь знаем
0   5   2    3 < 4   lo = 3   a[0..3) меньше 4 — ответ не левее 3
3   5   4    8 ≥ 4   hi = 4   a[4] подходит — ответ не правее 4
3   4   3    5 ≥ 4   hi = 3   a[3] подходит — ответ не правее 3
3   3                выход    lo == hi: ответ 3
```

Каждая строка отрезает часть кандидатов, но ответ 3 всё время остаётся между `lo` и `hi`.
**Инвариант: ответ всегда лежит в `[lo, hi]`** — все позиции левее `lo` точно `< target`, все
позиции от `hi` и правее — `>= target` (или `hi` — это `len(a)`, конец массива). Проверяем мы полуинтервал `[lo, hi)`: `mid`
никогда не равен `hi`. А ответ держим в отрезке с закрытой скобкой, потому что ответом может
оказаться и сам `hi = len(a)` — «такого числа нет». Теперь каждая строчка *выводится*, а не
вспоминается:

- почему `lo = mid + 1`, а `hi = mid` без `-1`? Потому что `a[mid] < target`
  исключает `mid` из кандидатов, а `a[mid] >= target` — нет: `mid` сам может быть
  ответом, выкидывать его нельзя;
- почему условие `lo < hi`, а не `lo <= hi`? Потому что при `lo == hi` в интервале
  осталась одна точка — искать больше нечего;
- почему не зациклимся? `mid` всегда строго меньше `hi`, поэтому обе ветки строго
  сужают интервал.

Сравни с «запомнил шаблон и молюсь»: инвариант отвечает на все три вопроса сразу.

[Modified Binary Search](modified-binary-search.md), она впереди.

## 2. Завершаемость — отдельная теорема: вариантная функция

Инвариант доказывает: «*если* цикл завершится, ответ верен». Что он завершится —
отдельное утверждение, и у него свой инструмент. **Вариантная функция** (вариант) —
целочисленная величина, которая:

1. строго убывает на каждой итерации;
2. ограничена снизу (обычно нулём).

Целое число не может убывать бесконечно, оставаясь ≥ 0, — значит, цикл конечен. На трассе
бинарного поиска выше длина интервала `hi - lo` была 5, потом 2, 1 и 0 — каждая строка её
уменьшала, а на нуле цикл кончился.

Три строки таблицы — из того, что ты уже прочитал; Евклид — для контраста, там убывает не
расстояние между указателями.

| Цикл | Вариант | Почему убывает |
|------|---------|----------------|
| бинарный поиск | `hi - lo` | обе ветки строго сужают интервал |
| встречные указатели ([два указателя](two-pointers.md)) | `right - left` | каждая итерация двигает `left` вправо или `right` влево |
| [скользящее окно](sliding-window.md) | `2n - right - left` | каждый шаг двигает `right` или `left` вперёд |
| алгоритм Евклида (НОД — наибольший общий делитель): пара `(a, b)` → `(b, a % b)` | `b` | `a % b < b` на каждом шаге (подробнее — в справочнике [«Теория чисел»](number-theory.md)) |

`2n - right - left` читается так: сколько шагов ещё могут сделать оба указателя окна вместе
(`n` — длина массива). Каждый пройдёт по массиву не больше `n` позиций, поэтому величина не уходит ниже нуля, а любой
сдвиг отнимает от неё единицу. В обходах графов (они впереди) вариант — число вершин, ещё не
извлечённых из очереди; разберёшь в их главах.

Пара «инвариант + вариант» — это полное доказательство: *ответ верный* и *мы до
него дойдём*. Когда цикл подозрительно виснет — ищи, какая величина у тебя
**обязана** убывать, и найди итерацию, где она не убывает: это и есть баг.

## 3. Индукция: тот же приём для рекурсии

Инвариант цикла — это **индукция по номеру итерации**: база = инициализация,
переход = сохранение. Для рекурсии индукция применяется по **размеру входа**:

1. **База**: функция верна на минимальном входе (пустой список, один элемент).
2. **Переход**: *предположим*, что рекурсивный вызов на меньшем входе верен, —
   и докажем, что тогда верен и текущий уровень.

Пункт «предположим» — то самое «верь вызову» («скачок веры») из главы
[Рекурсия и мастер-теорема](recursion.md). Это не самообман, а гипотеза индукции —
допущение, что для меньших входов уже доказано. Сортировка слиянием из
[главы о сортировках](sorting.md) корректна, потому что (база) массив из одного элемента
отсортирован, (переход) если обе половины отсортированы — а это гипотеза, — то `merge` двух
отсортированных даёт отсортированное целое. Всё, доказательство закончено; лезть
внутрь рекурсивных вызовов не нужно — за тебя работает индукция.

Отсюда практическое правило: доказывая (и отлаживая!) рекурсию, проверяй **три
места** — базу, переход и то, что рекурсия зовётся на *строго меньшем* входе
(это её вариантная функция; без этого — бесконечная рекурсия и переполнение стека).
Например, рекурсивный разворот списка: `reverse(head)` вызывает себя на хвосте, начинающемся с
`head.Next`, — список на один узел короче — и цепляет `head` в конец развёрнутого хвоста; база — пустой список
или один узел.

## 4. Как придумать инвариант: четыре эвристики

Сформулировать инвариант к чужому циклу — навык чтения. Придумать к своему —
навык проектирования. Эвристики (правила без гарантии успеха), которые срабатывают чаще всего:

1. **Обобщи цель с «всё» до «первые i»**. Хочешь в конце «sum — сумма массива» — инвариант
   «sum — сумма первых i», как в разделе 1. Хочешь «массив отсортирован» — «префикс `a[0..i)`
   отсортирован и состоит из тех же первых `i` элементов, что были там с самого начала», как у
   [сортировки вставками](sorting.md#1-сортировка-вставками-точка-отсчёта). Вторая половина
   нужна, иначе «отсортирован» выполнил бы и массив, переписанный нулями. Цикл кончается на
   `i == len(a)` — префикс стал всем массивом.
2. **Спроси: что гарантированно сделано к началу итерации?** Ответ словами — уже
   черновик инварианта. У префиксных сумм с хеш-таблицей: «в `seen` лежат все префиксы
   строго до текущего».
3. **Опиши смысл каждой переменной одним предложением.** Не «left — индекс», а
   «левее `left` валидных начал окна нет». Если предложение не формулируется —
   переменная перегружена, и баг близко.
4. **Инвариант не сохраняется? Вини не только код.** Либо код неверен, либо
   инвариант слишком силён (обещает лишнее) или слишком слаб (из него не следует
   ответ). Подгонка утверждения под честное доказательство — это и есть
   проектирование алгоритма.

Почему сортировке вставками не нужно обещание «префикс не больше остатка»? Вставка правит сам
префикс: чтобы поставить `key` на место, она сдвигает бо́льшие элементы префикса вправо, поэтому
любой меньший элемент из остатка позже просто встанет внутрь. Сортировке выбором (на шаге `i`
она находит минимум остатка и ставит его в позицию `i`, а префикс потом не трогает) это обещание
нужно: без него нельзя доказать сохранение — минимум остатка мог бы оказаться меньше последнего
элемента префикса и, поставленный за ним, сломал бы порядок.

Проверь на виджете: вход `[3, 7, 1, 6, 2, 5]`, зелёные клетки — отсортированный префикс. Найди
шаг, на котором префикс впервые вырос до длины 3. Какой он и что лежит в остатке? Сколько раз
после этого сдвинется семёрка? (Шаг 17, «a[0] = key (1)»: префикс `[1 3 7]`, в остатке
`[6 2 5]` есть двойка — «префикс не больше остатка» неверно, а вставкам это не мешает. Семёрка
сдвинется ещё трижды — когда вставляют 6, 2 и 5 — и закончит на последнем месте.)

## 5. 🔧 Логический минимум для отладки условий

Единственный кусок формальной логики, который окупается ежедневно, — отрицания.

- **Де Морган**: `!(A && B) == !A || !B`, `!(A || B) == !A && !B` — «неверно, что A и B» значит
  «неверно A или неверно B», и наоборот: отрицание меняет `&&` на `||`. Половина багов
  в «отрицании сложного if» — потерянная замена `&&` на `||`.
- **Отрицание кванторов** (слов «все» и «хотя бы один»): не «все элементы валидны» = «*хотя бы один* невалиден»
  (не «все невалидны»!). Условие выхода из цикла — почти всегда отрицание
  инварианта продолжения; путаница «все/хотя бы один» даёт цикл, который выходит
  слишком рано или поздно.
- **Контрапозиция**: «если A, то B» равносильно «если не B, то не A» — и *не*
  равносильно «если не A, то не B». «Если ключ есть в кэше, ответ за O(1)» не
  значит «если ключа нет — ответ медленный».

## ⚡ Что помнить на собеседовании

- Проговаривай инвариант вслух («держу окно так, что…») — интервьюеры слышат
  разницу между шаблоном и пониманием, а ты бесплатно получаешь проверку границ.
- Триада: инициализация → сохранение → завершение. Завершаемость — отдельно,
  через убывающую величину.
- Рекурсия: база + переход + «вход строго уменьшается».
- Off-by-one лечится не перебором ±1, а вопросом «какой полуинтервал я держу?».

## ⚠️ Типичные ошибки

1. **Инвариант проверен «на примере»** — прогон одного входа это тест, не
   доказательство. Сохранение доказывается для *произвольной* итерации.
2. **Слишком слабый инвариант**: «sum — какая-то частичная сумма» ничего не даёт
   на выходе. Из инварианта + условия выхода должен *следовать* ответ.
3. **Индукция без базы**: переход «если верно для n−1, верно для n» повисает в
   воздухе — классика ложных доказательств.
4. **Забытая завершаемость**: корректный инвариант + цикл, который не двигает
   вариантную функцию = вечное «почти готово».
5. **Инверсия квантора в условии выхода**: `for !allDone` (пока хоть кто-то не готов) и
  `for !anyDone` (пока не готов никто) — разные циклы, хотя на слух оба — «пока не готово»; проверь отрицание по Де Моргану, а не на глаз.

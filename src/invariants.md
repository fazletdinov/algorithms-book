# 🧭 Инварианты и индукция: как доказывать, что код правильный

Почти в каждой главе этой книги есть раздел «Почему это корректно», и все они говорят
на одном языке: *инвариант сохраняется*, *по индукции*, *граница монотонна*. Эта
полуглава — про сам язык. Она короче остальных, но окупается во всех: научившись
формулировать инвариант, ты перестаёшь «верить, что работает» и начинаешь **знать,
почему работает** — а заодно получаешь самый надёжный способ находить off-by-one
ещё до запуска тестов.

Разница между «прошло тесты» и «корректно» — инженерная, не академическая: тесты
проверяют конечный набор входов, инвариант — все сразу.

## 1. Инвариант цикла: утверждение, которое переживает итерацию

**Инвариант цикла** — утверждение о переменных, которое истинно перед первой
итерацией и остаётся истинным после каждой. Доказательство корректности цикла —
всегда одна и та же триада:

1. **Инициализация**: инвариант истинен до входа в цикл.
2. **Сохранение**: если он истинен в начале итерации, то истинен и в конце.
3. **Завершение**: инвариант + условие выхода ⇒ то, что мы хотели доказать.

Тривиальный пример, чтобы увидеть схему целиком:

```go
sum := 0
for i, x := range a {
    sum += x
    // инвариант: sum == a[0] + a[1] + ... + a[i]
}
```

- Инициализация: до цикла `sum == 0` — сумма пустого префикса. ✓
- Сохранение: было `sum == сумма a[0..i-1]`, прибавили `a[i]` — стало `сумма a[0..i]`. ✓
- Завершение: цикл кончился на `i == len(a)-1`, значит `sum` — сумма всего массива. ✓

Скучно? Да. Но ровно эта схема доказывает и бинарный поиск, и Дейкстру — меняется
только само утверждение.

### Рабочий пример: бинарный поиск без страха off-by-one

Бинарный поиск — рекордсмен по ошибкам на границах. Инвариант превращает выбор
границ из гадания в вывод. Ищем первую позицию, где `a[i] >= target`
(lower bound), на полуинтервале:

```go
lo, hi := 0, len(a) // ответ лежит в [lo, hi] — это и есть инвариант
for lo < hi {
    mid := lo + (hi-lo)/2
    if a[mid] < target {
        lo = mid + 1 // a[mid] < target ⇒ ответ правее mid
    } else {
        hi = mid // a[mid] >= target ⇒ mid — кандидат, ответ не правее
    }
}
// lo == hi — интервал схлопнулся в единственную точку: это и есть ответ
```

**Инвариант: ответ всегда лежит в `[lo, hi]`** (все позиции левее `lo` точно
`< target`, все от `hi` и правее — кандидаты либо конец массива). Теперь каждая
строчка *выводится*, а не вспоминается:

- почему `lo = mid + 1`, а `hi = mid` без `-1`? Потому что `a[mid] < target`
  исключает `mid` из кандидатов, а `a[mid] >= target` — нет: `mid` сам может быть
  ответом, выкидывать его нельзя;
- почему условие `lo < hi`, а не `lo <= hi`? Потому что при `lo == hi` в интервале
  осталась одна точка — искать больше нечего;
- почему не зациклимся? `mid` всегда строго меньше `hi`, поэтому обе ветки строго
  сужают интервал.

Сравни с «запомнил шаблон и молюсь»: инвариант отвечает на все три вопроса сразу.
Подробный разбор вариаций — в главе
[Modified Binary Search](modified-binary-search.md).

## 2. Завершаемость — отдельная теорема: вариантная функция

Инвариант доказывает: «*если* цикл завершится, ответ верен». Что он завершится —
отдельное утверждение, и у него свой инструмент. **Вариантная функция** (вариант) —
целочисленная величина, которая:

1. строго убывает на каждой итерации;
2. ограничена снизу (обычно нулём).

Целое число не может убывать бесконечно, оставаясь ≥ 0, — значит, цикл конечен.

| Цикл | Вариант | Почему убывает |
|------|---------|----------------|
| бинарный поиск | `hi - lo` | обе ветки строго сужают интервал |
| алгоритм Евклида | `b` | `a % b < b` на каждом шаге ([теория чисел](number-theory.md)) |
| скользящее окно | `2n - right - left` | каждый шаг двигает `right` или `left` вперёд |
| BFS/DFS | число вершин, ещё не извлечённых из очереди (стека) | каждая итерация извлекает одну, а попасть в очередь вершина может лишь раз |

Пара «инвариант + вариант» — это полное доказательство: *ответ верный* и *мы до
него дойдём*. Когда цикл подозрительно виснет — ищи, какая величина у тебя
**обязана** убывать, и найди итерацию, где она не убывает: это и есть баг.

## 3. Индукция: тот же приём для рекурсии

Инвариант цикла — это **индукция по номеру итерации**: база = инициализация,
переход = сохранение. Для рекурсии индукция применяется по **размеру входа**:

1. **База**: функция верна на минимальном входе (пустой список, один элемент).
2. **Переход**: *предположим*, что рекурсивный вызов на меньшем входе верен, —
   и докажем, что тогда верен и текущий уровень.

Пункт «предположим» — то самое «доверься рекурсии» из главы
[Рекурсия и мастер-теорема](recursion.md). Это не самообман, а гипотеза индукции:
merge sort корректен, потому что (база) массив из одного элемента отсортирован,
(переход) если обе половины отсортированы — а это гипотеза, — то `merge` двух
отсортированных даёт отсортированное целое. Всё, доказательство закончено; лезть
внутрь рекурсивных вызовов не нужно — за тебя работает индукция.

Отсюда практическое правило: доказывая (и отлаживая!) рекурсию, проверяй **три
места** — базу, переход и то, что рекурсия зовётся на *строго меньшем* входе
(это её вариантная функция; без этого — бесконечная рекурсия и переполнение стека).

## 4. Как придумать инвариант: четыре эвристики

Сформулировать инвариант к чужому циклу — навык чтения. Придумать к своему —
навык проектирования. Эвристики, которые срабатывают чаще всего:

1. **Обобщи цель с «всё» до «первые i»**. Хочешь в конце «массив отсортирован» —
   инвариант «префикс `a[0..i)` отсортирован и не больше остальных» (селектсорт),
   хочешь «sum — сумма массива» — «sum — сумма первых i».
2. **Спроси: что гарантированно сделано к началу итерации?** Ответ словами — уже
   черновик инварианта. У Дейкстры: «для всех извлечённых из кучи вершин
   кратчайшее расстояние финально».
3. **Опиши смысл каждой переменной одним предложением.** Не «left — индекс», а
   «левее `left` валидных начал окна нет». Если предложение не формулируется —
   переменная перегружена, и баг близко.
4. **Инвариант не сохраняется? Вини не только код.** Либо код неверен, либо
   инвариант слишком силён (обещает лишнее) или слишком слаб (из него не следует
   ответ). Подгонка утверждения под честное доказательство — это и есть
   проектирование алгоритма.

Инварианты, на которых уже стоит эта книга — теперь ты знаешь, как они устроены:

| Глава | Инвариант |
|-------|-----------|
| [Скользящее окно](sliding-window.md) | `[left, right]` — лучшее валидное окно с концом в `right`; две семьи предиката |
| [Cyclic Sort](cyclic-sort.md) | всё до `i` стоит на своих местах: `a[j] == j+1` |
| [Куча](heap-structure.md) | после sift поддерево снова удовлетворяет свойству кучи |
| [Dijkstra](grids-and-shortest-paths.md) | извлечённые вершины имеют финальную `dist` |
| [ДП](dynamic-programming.md) | к моменту вычисления `dp[i]` все меньшие состояния уже верны |

## 5. 🔧 Логический минимум для отладки условий

Единственный кусок формальной логики, который окупается ежедневно, — отрицания.

- **Де Морган**: `!(A && B) == !A || !B`, `!(A || B) == !A && !B`. Половина багов
  в «отрицании сложного if» — потерянная замена `&&` на `||`.
- **Отрицание кванторов**: не «все элементы валидны» = «*хотя бы один* невалиден»
  (не «все невалидны»!). Условие выхода из цикла — почти всегда отрицание
  инварианта продолжения; путаница «все/хотя бы один» даёт цикл, который выходит
  слишком рано или поздно.
- **Контрапозиция**: «если A, то B» равносильно «если не B, то не A» — и *не*
  равносильно «если не A, то не B». «Если ключ есть в кэше, ответ за O(1)» не
  значит «если ключа нет — ответ медленный».

## ⚡ Что помнить на собеседовании

- Проговаривай инвариант вслух («держу окно так, что…») — интервьюеры слышат
  разницу между шаблоном и пониманием, а ты бесплатно получаешь проверку границ.
- Триада: инициализация → сохранение → завершение. Завершаемость — отдельно,
  через убывающую величину.
- Рекурсия: база + переход + «вход строго уменьшается».
- Off-by-one лечится не перебором ±1, а вопросом «какой полуинтервал я держу?».

## ⚠️ Типичные ошибки

1. **Инвариант проверен «на примере»** — прогон одного входа это тест, не
   доказательство. Сохранение доказывается для *произвольной* итерации.
2. **Слишком слабый инвариант**: «sum — какая-то частичная сумма» ничего не даёт
   на выходе. Из инварианта + условия выхода должен *следовать* ответ.
3. **Индукция без базы**: переход «если верно для n−1, верно для n» повисает в
   воздухе — классика ложных доказательств.
4. **Забытая завершаемость**: корректный инвариант + цикл, который не двигает
   вариантную функцию = вечное «почти готово».
5. **Инверсия квантора в условии выхода**: `for !allDone` (пока хоть кто-то не готов) и
  `for !anyDone` (пока не готов никто) — разные циклы, хотя на слух оба — «пока не готово»; проверь отрицание по Де Моргану, а не на глаз.

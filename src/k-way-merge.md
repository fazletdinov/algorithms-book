## 🎬 Визуализация

> 💡 **Интерактивная демонстрация.** Строка «куча» — её содержимое в нотации таблицы ниже
> (`значение₍список₎`, минимум слева); у списков синей рамкой отмечены элементы, лежащие сейчас в
> куче: ровно по одной голове на список. Жёлтым — извлечённый минимум, он уходит в `out`, а
> зелёной рамкой — преемник из того же списка, вставший в кучу на его место. Вход — пример из
> LeetCode 23: минимумы идут не по кругу, а откуда придётся, и решает это только куча. Под холстом — строка шага и переменные, ниже — ползунок шагов (или ←/→ на клавиатуре) и код с подсветкой строки. Можно подставить свои списки (через `;`) и нажать «⟲ Запустить».

## ⚡ Шаблон для собеседования

```go
h := &MinHeap{} // элемент: (значение, номер списка, индекс)
for i := range lists {
    if len(lists[i]) > 0 {
        h.Push(lists[i][0], i, 0) // головы всех списков
    }
}
var out []int
for h.Len() > 0 {
    v, li, ci := h.Pop()           // минимальная голова
    out = append(out, v)
    if ci+1 < len(lists[li]) {     // следующий из того же списка
        h.Push(lists[li][ci+1], li, ci+1)
    }
}
```

1. кладём в кучу первый элемент каждого непустого списка;
2. извлекаем глобальный минимум в результат;
3. подкладываем следующий элемент из того же списка;
4. повторяем, пока куча не пуста.

## 📖 Разбор

<details class="algo-details">
<summary>Теория, реализация с container/heap и сложность</summary>

**K-way Merge** объединяет K отсортированных массивов (списков, потоков) в один
отсортированный результат — обобщение слияния двух отсортированных массивов.

Ключевая идея: следующий минимальный элемент результата — это минимум среди *первых*
непрочитанных элементов всех K массивов. Min-heap позволяет находить этот минимум за
O(log k), храня по одному «текущему» элементу от каждого массива.

```go
import "container/heap"

// Элемент кучи: значение + откуда оно пришло
type Element struct {
    Val      int // значение
    ArrayIdx int // индекс массива
    ElemIdx  int // позиция в этом массиве
}

type MinHeap []Element

func (h MinHeap) Len() int            { return len(h) }
func (h MinHeap) Less(i, j int) bool  { return h[i].Val < h[j].Val }
func (h MinHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *MinHeap) Push(x interface{}) { *h = append(*h, x.(Element)) }
func (h *MinHeap) Pop() interface{} {
    old := *h
    n := len(old)
    x := old[n-1]
    *h = old[:n-1]
    return x
}

func mergeKSortedArrays(arrays [][]int) []int {
    h := &MinHeap{}
    heap.Init(h)
    for i := range arrays {
        if len(arrays[i]) > 0 {
            heap.Push(h, Element{Val: arrays[i][0], ArrayIdx: i, ElemIdx: 0})
        }
    }

    result := make([]int, 0)
    for h.Len() > 0 {
        minElem := heap.Pop(h).(Element) // глобальный минимум среди непрочитанных
        result = append(result, minElem.Val)

        next := minElem.ElemIdx + 1
        if next < len(arrays[minElem.ArrayIdx]) {
            heap.Push(h, Element{
                Val:      arrays[minElem.ArrayIdx][next],
                ArrayIdx: minElem.ArrayIdx,
                ElemIdx:  next,
            })
        }
    }
    return result
}
```

#### Сложность

| Подход                     | Время       | Память |
|----------------------------|-------------|--------|
| Наивный (минимум из k каждый раз) | O(n·k) | O(1)   |
| K-way merge с кучей        | O(n log k)  | O(k)   |

Где `n` — общее число элементов, `k` — количество массивов. Каждый из `n` элементов
проходит через push/pop кучи размера ≤ k за O(log k).

</details>

## 🧠 Почему это корректно

### Почему минимум среди голов — это глобальный минимум

Каждый массив отсортирован, поэтому его **голова** (первый непрочитанный) — наименьший
непрочитанный в нём. Значит наименьший непрочитанный **во всём наборе** обязательно одна
из `k` голов. Min-heap обнажает этот минимум за `O(log k)`.

> **Инвариант:** в куче всегда ровно по одному элементу (текущая голова) от каждого
> неисчерпанного массива. Извлекли минимум — подложили следующий **из того же** массива
> → инвариант восстановлен.

Так в результат выходят элементы строго по возрастанию, ничего не пропущено.

### Почему в куче достаточно `k` элементов, а не больше

Второй элемент любого массива `≥` его головы, поэтому он **не может** оказаться
глобальным минимумом, пока голова этого массива не извлечена. Держать в куче что-то,
кроме одной головы на массив, бессмысленно — эти кандидаты заведомо не выиграют ближайшее
сравнение. Отсюда строго `O(k)` памяти: не эвристика «обычно мало», а доказанная граница.
Подкладывание ровно одного следующего элемента на каждый pop поддерживает её точно.

### Стабильность: tie-break при равных значениях

Если `Less` сравнивает **только** значения, равные элементы из разных массивов выходят в
произвольном порядке — для чистого слияния чисел это незаметно, но ломается, как только
элемент несёт нагрузку (запись с ключом) и слияние должно быть **стабильным**. Чтобы
сохранить порядок «сначала меньший номер массива, потом меньшая позиция», доводим
сравнение до лексикографического:

```go
func (h MinHeap) Less(i, j int) bool {
    if h[i].Val != h[j].Val {
        return h[i].Val < h[j].Val
    }
    if h[i].ArrayIdx != h[j].ArrayIdx {
        return h[i].ArrayIdx < h[j].ArrayIdx // tie-break: раньше идёт меньший список
    }
    return h[i].ElemIdx < h[j].ElemIdx
}
```

Та же проблема в [Top K](top-k-elements.md) и любых задачах, где куча решает «кого
взять первым» среди равных.

## ⚙️ Цена на практике

### `O(n log k)`, куча размера `k` — и работает на потоках

Наивный «минимум из `k` голов каждый раз» — `O(n·k)`. Куча даёт `O(n log k)`, и, что
важнее, держит лишь `k` элементов, а не все `n`: исходные данные **не обязаны** помещаться
в память — нужны только `k` голов. Поэтому k-way merge — основа **внешней сортировки**
(слияние отсортированных кусков с диска). При `k = 2` это вырождается в обычное слияние
двух массивов.

### Конкатенация + sort: когда проще и не хуже

Очевидная альтернатива — сложить всё в один срез и отсортировать за `O(n log n)`. Сравни
с `O(n log k)`: выигрыш кучи — это `log n` против `log k`. При **малом** `k` (слить 10
файлов из миллионов строк) куча кратно быстрее. Но если массивов почти столько же,
сколько элементов (`k ≈ n`, много крошечных списков), `log k ≈ log n` — асимптотика та же,
а один `sort.Slice` короче в коде, дружелюбнее к кэшу и не платит за `heap.Push/Pop`.
И главное преимущество кучи теряется лишь тогда, когда **все данные и так в памяти**: на
потоке/диске конкатенация невозможна, а куче хватает `k` голов.

### Турнирное дерево (loser tree) — константа внешней сортировки

Бинарная куча тратит `~2 log k` сравнений на элемент (просеивание вверх и вниз).
**Турнирное дерево проигравших** (loser tree) на тех же `k` источниках делает **одно**
сравнение на каждый уровень пути от листа к корню — `~log k` на выданный элемент. Асимптотика та же —
`O(n log k)`, — но вдвое меньше сравнений; именно его используют движки БД и классическая
внешняя сортировка, где константа на терабайтах решает. На собеседовании достаточно
назвать его как оптимизацию, кодить редко просят.

### `interface{}` в `container/heap` — скрытый боксинг

Стандартный `container/heap` принимает `interface{}` в `Push`/`Pop` — каждый `Element`
**боксится** (уходит в кучу Go с аллокацией), а на `Pop` идёт type assertion. Big-O это не
меняет, но на горячем пути ощутимо. Лекарство — **дженерик-куча** (`heap` поверх
`[]Element` со своими методами без `interface{}`) или ручной типизированный min-heap на
срезе. Это тот же приём «`O(...)` скрывает константу», что и `map` против `[256]int` в
[скользящем окне](sliding-window.md).

> 🔧 **Где это в Go.** Инструмент паттерна — [`container/heap`](https://pkg.go.dev/container/heap):
> его документационный пример PriorityQueue — ровно та куча, что сливает k потоков. В самом
> рантайме та же идея: таймеры каждого P лежат в 4-арной куче (см.
> [go-stdlib-structures](go-stdlib-structures.md)), а внешняя сортировка в БД, написанных на Go,
> сливает отсортированные чанки с диска именно k-way merge'ем — как PostgreSQL в
> [карте реальных систем](real-world-map.md).

## ⚠️ Типичные ошибки

1. **Не сохранён источник элемента** — в куче нужно хранить индекс массива и позицию,
   иначе непонятно, какой элемент подкладывать следующим.
2. **Добавление пустых массивов на старте** — клади в кучу только первый элемент
   *непустых* массивов.
3. **Выход за границу при подкладывании** — проверяй `next < len(arrays[idx])`
   перед push.
4. **Сравнение в `Less` наоборот** — для min-heap это `h[i].Val < h[j].Val`; знак `>`
   даст max-heap и неверный порядок.
5. **Забыли `heap.Init`** — куча, собранная без Init/Push, не поддерживает инвариант.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он медленный, и
только потом куча.

> **Задача.** Даны `k` отсортированных по возрастанию массивов `lists`. Слить их в один
> отсортированный массив из всех `N` элементов.
> Пример: `lists = [[1,4,7], [2,5,8], [3,6,9]]` → ответ `[1,2,3,4,5,6,7,8,9]`.

**Шаг 1. Наивно: ссыпать всё в один срез и отсортировать — O(N log N).**

```go
import "sort"

func mergeNaive(lists [][]int) []int {
    var all []int
    for _, l := range lists {
        all = append(all, l...) // забываем про порядок — просто собираем всё
    }
    sort.Ints(all)
    return all
}
```

Это **работает и проходит тесты**, но мы **выбрасываем** ценную информацию: каждый
массив *уже* отсортирован. `sort.Ints` сортирует `N` элементов с нуля за `O(N log N)`,
будто они пришли в полном беспорядке. Вся проделанная заранее работа по упорядочиванию
источников уходит впустую.

**Шаг 2. Ключевое наблюдение.** Следующий элемент результата — это глобально
наименьший непрочитанный, а он, [как показано выше](#почему-минимум-среди-голов--это-глобальный-минимум),
обязательно одна из `k` *голов* (первых непрочитанных элементов массивов). Значит, не
нужно сравнивать все `N` — достаточно держать `k` голов и быстро доставать из них
минимум. Min-heap делает это за `O(log k)` вместо линейного перебора `k` голов.

**Шаг 3. Оптимум: min-heap из голов — O(N log k).** Переиспользуем `Element` и
`MinHeap` из раздела «📖 Разбор» — меняется лишь точка входа:

```go
import "container/heap"

func mergeKWay(lists [][]int) []int {
    h := &MinHeap{}
    for i := range lists { // в кучу — только головы непустых списков
        if len(lists[i]) > 0 {
            *h = append(*h, Element{Val: lists[i][0], ArrayIdx: i, ElemIdx: 0})
        }
    }
    heap.Init(h) // выстроить инвариант кучи за O(k)

    out := make([]int, 0)
    for h.Len() > 0 {
        e := heap.Pop(h).(Element) // глобальный минимум среди голов за O(log k)
        out = append(out, e.Val)
        if next := e.ElemIdx + 1; next < len(lists[e.ArrayIdx]) {
            // подкладываем следующий из того же списка — инвариант восстановлен
            heap.Push(h, Element{Val: lists[e.ArrayIdx][next], ArrayIdx: e.ArrayIdx, ElemIdx: next})
        }
    }
    return out
}
```

Куча держит ≤ `k` элементов, каждый из `N` проходит ровно один `Pop` и ≤ один `Push`
за `O(log k)` → суммарно `O(N log k)` и `O(k)` памяти. Выигрыш — `log k` против `log n`
наивного: при малом `k` и огромном `N` это кратно быстрее.

Прогони слияние через min-heap на тех же списках: на каждом шаге извлекается
минимальная голова, а на её место встаёт следующий элемент того же списка:

**Шаг 4. Трассировка** на `lists = [[1,4,7], [2,5,8], [3,6,9]]` (куча голов после
каждого pop; `(значение от списка)`):

| шаг | минимум (pop) → out | подложили из списка | куча голов после      |
|-----|---------------------|---------------------|-----------------------|
| —   | (старт)             | головы 1,2,3        | `1₀ 2₁ 3₂`            |
| 1   | `1` → `[1]`         | `4` из списка 0     | `2₁ 3₂ 4₀`           |
| 2   | `2` → `[…2]`        | `5` из списка 1     | `3₂ 4₀ 5₁`           |
| 3   | `3` → `[…3]`        | `6` из списка 2     | `4₀ 5₁ 6₂`           |
| 4   | `4` → `[…4]`        | `7` из списка 0     | `5₁ 6₂ 7₀`           |
| 5   | `5` → `[…5]`        | `8` из списка 1     | `6₂ 7₀ 8₁`           |
| 6   | `6` → `[…6]`        | `9` из списка 2     | `7₀ 8₁ 9₂`           |
| 7   | `7` → `[…7]`        | список 0 исчерпан   | `8₁ 9₂`              |
| 8   | `8` → `[…8]`        | список 1 исчерпан   | `9₂`                 |
| 9   | `9` → `[…9]`        | список 2 исчерпан   | `∅`                  |

Ответ — `[1,2,3,4,5,6,7,8,9]`, совпадает с наивным. Обрати внимание: в куче **никогда
не больше трёх** элементов (по одной голове на список), хотя всего слили 9 — та самая
граница `O(k)` памяти, доказанная [выше](#почему-в-куче-достаточно-k-элементов-а-не-больше).

## 🧵 Конкурентная сортировка слиянием (Go)

Слияние — сердце и k-way merge, и **сортировки слиянием**. А merge sort — это
divide-and-conquer: массив делится пополам, половины сортируются **независимо**, потом
сливаются. Независимость = идеальный кандидат на параллелизм, и здесь — в отличие от
[конкурентного BFS](graphs.md#-конкурентный-bfs-go) — он реально ускоряет.

```go
func MergeSortConc(a []int) []int {
    if len(a) < cutoff {        // ← порог: мелочь сортируем последовательно
        return MergeSortSeq(a)
    }
    mid := len(a) / 2
    var l, r []int
    var wg sync.WaitGroup
    wg.Add(2)
    go func() { defer wg.Done(); l = MergeSortConc(a[:mid]) }() // половины
    go func() { defer wg.Done(); r = MergeSortConc(a[mid:]) }() // независимы
    wg.Wait()
    return merge(l, r)
}
```

**Гонки тут нет by design:** каждая горутина пишет в свою переменную (`l` или `r`) и читает
свою половину входа — общей изменяемой памяти нет, замок не нужен. Это важный контраст с BFS:
там данные общие (`visited`) и без мьютекса гонка, а здесь задача *разделяется* на независимые
куски — и параллелизм почти бесплатен.

**Но порог обязателен.** Без `cutoff` на каждый двухэлементный кусок родится горутина — их
станут миллионы, и накладные расходы всё убьют. С порогом конкурентная версия в бенчмарке
тренажёра обгоняет последовательную примерно **в 3–4 раза** на массиве в миллион элементов.

> 💡 Правило: параллель divide-and-conquer окупается, когда (1) ветви независимы и (2) есть
> порог, ниже которого ты возвращаешься к последовательной версии.

> 💡 **Интерактивная демонстрация (fan-out + cutoff).** Листай «›»: дерево деления на подзадачи
> строится сверху вниз. Внутренний узел ≥ `cutoff` делает **fan-out** — порождает **2 горутины** на
> половины (фиолетовые). Кусок меньше `cutoff` — **лист**: сортируется **последовательно** (синий), без
> новой горутины. На подъёме узлы **сливаются** (`merge`, зелёные). Под холстом — режим и счётчик
> запущенных горутин. Шаги идут по **тактам**: всё, что горутины делают одновременно, подсвечено
> вместе — видно, что время упирается в глубину дерева, а не в число узлов. Это тот случай, где конкурентность **выигрывает** — ветви независимы, гонки нет
> (контраст с [конкурентным BFS](graphs.md#-конкурентный-bfs-go), где общий `visited` заставляет
> проигрывать). Меняй `cutoff`: маленький — горутин много (накладные съедают выигрыш), большой — их мало.

## 🎬 Визуализация: как растёт поток

> 💡 **Интерактивная демонстрация.** Ниже — сеть с истоком `s` (зелёный) и стоком `t` (красный). На рёбрах —
> подпись **`поток/пропускная`**. Листай «›»: BFS находит **дополняющий путь** s→t (подсвечен), считает
> **узкое место** и проталкивает по нему поток — подписи рёбер растут. Когда путей больше нет, поток
> максимален, и подсвечивается **минимальный разрез** (синяя S-сторона; красные пунктирные рёбра — тот
> самый «перерез», чья сумма равна потоку). Под холстом — путь, узкое место и накопленный поток.

<div class="algo-viz" data-viz="max-flow" data-nodes="s,a,b,c,d,t" data-edges="s-a-10,s-b-8,a-c-5,a-b-2,b-c-10,b-d-7,c-t-10,d-t-10" data-source="s" data-sink="t"></div>

В этой сети BFS везёт: каждый следующий путь находится по прямым рёбрам, и «передумывать» не
приходится. Так бывает не всегда. Во второй сети ниже первый путь `s→a→c→t` забирает ребро `c→t`
целиком, и второй путь существует **только через обратное ребро** `c→a`: поток, уже пущенный по
`a→c`, частично «отменяется» и уходит в обход через `d`. Без обратных рёбер алгоритм остановился
бы на 10, с ними доходит до истинного максимума 14:

<div class="algo-viz" data-viz="max-flow" data-nodes="s,a,b,c,d,t" data-edges="s-a-10,s-b-10,a-c-10,a-d-4,b-c-6,c-t-10,d-t-10" data-source="s" data-sink="t"></div>

**«Остаточная сеть» на пальцах — три числа.** Пусть у ребра `u→v` пропускная способность `3`, и мы
протолкнули по нему `2` единицы. После этого:

- **остаток прямого ребра**: `3 − 2 = 1` — столько ещё можно протолкнуть по `u→v`;
- **остаток обратного ребра** `v→u`: `0 + 2 = 2` — столько уже пущенного потока можно **отменить**,
  если позже найдётся маршрут получше;
- сумма всегда сходится: `1 + 2 = 3` — исходная пропускная никуда не делась, она просто поделена
  на «ещё можно» и «можно передумать».

Остаточная сеть — это и есть граф из таких остатков. Алгоритм ищет пути не в исходной сети,
а в ней: поэтому «передумать» — легальный ход, а не хак.

## 📖 Разбор: от дополняющего пути до Эдмондса—Карпа

<details class="algo-details">
<summary>Постановка, остаточная сеть, обратные рёбра и сложность</summary>

**Транспортная сеть** — ориентированный граф, где у каждого ребра `u→v` есть **пропускная способность**
`c(u,v) ≥ 0`. Выделены **исток** `s` (только выпускает) и **сток** `t` (только принимает). **Поток** `f(u,v)`
вдоль ребра — сколько «единиц» по нему реально идёт, при двух правилах:

- **ограничение:** `0 ≤ f(u,v) ≤ c(u,v)` — больше пропускной не протолкнуть;
- **сохранение:** для любой вершины, кроме `s` и `t`, сколько втекло — столько и вытекло.

**Величина потока** — сколько всего вышло из `s` (= вошло в `t`). Задача: сделать её **максимальной**.

#### Идея Форда—Фалкерсона

Пока в сети есть **дополняющий путь** — путь из `s` в `t`, вдоль которого у каждого ребра остался запас, —
проталкиваем по нему поток, равный **узкому месту** (минимальному остатку на пути). Нет пути — поток
максимален.

#### Остаточная сеть и обратные рёбра

Ключевой трюк. Для каждого ребра `u→v` заводим **обратное** `v→u`. Протолкнув `b` единиц по `u→v`, мы:

- уменьшаем остаток прямого ребра на `b` (заняли);
- увеличиваем остаток обратного на `b` — теперь по `v→u` можно пустить до `b`, что означает **«отменить»**
  ранее протолкнутый поток.

Без этой «возможности передумать» жадное проталкивание застревало бы в неоптимуме. Обратные рёбра — то, что
делает Форда—Фалкерсона **корректным**.

#### Эдмондс—Карп: искать путь именно BFS

Форд—Фалкерсон не говорит, *как* выбирать дополняющий путь. Если брать **кратчайший по числу рёбер** (искать
**BFS**), получается алгоритм **Эдмондса—Карпа** со сложностью `O(V·E²)` — и, что важно, гарантированно
завершается (наивный выбор пути на **иррациональных** пропускных мог бы вообще не сойтись, а на целых —
делать до `O(E·maxflow)` шагов).

```go
// Эдмондс—Карп: cap[u][v] — остаточная пропускная способность (для ребра u→v
// заводим и обратное v→u с исходным остатком 0).
func maxFlow(n int, cap [][]int, s, t int) int {
    flow := 0
    for {
        // BFS ищет кратчайший дополняющий путь s→t по рёбрам с остатком > 0.
        parent := make([]int, n)
        for i := range parent {
            parent[i] = -1
        }
        parent[s] = s
        queue := []int{s}
        for len(queue) > 0 && parent[t] == -1 {
            u := queue[0]
            queue = queue[1:]
            for v := 0; v < n; v++ {
                if parent[v] == -1 && cap[u][v] > 0 {
                    parent[v] = u
                    queue = append(queue, v)
                }
            }
        }
        if parent[t] == -1 {
            break // дополняющего пути нет — поток максимален
        }
        // Узкое место — минимум остатка вдоль найденного пути.
        b := 1 << 30
        for v := t; v != s; v = parent[v] {
            u := parent[v]
            if cap[u][v] < b {
                b = cap[u][v]
            }
        }
        // Проталкиваем: прямым рёбрам −b, обратным +b.
        for v := t; v != s; v = parent[v] {
            u := parent[v]
            cap[u][v] -= b
            cap[v][u] += b
        }
        flow += b
    }
    return flow
}
```

#### Сложность

| Алгоритм        | Время      | Идея                                   |
|-----------------|------------|----------------------------------------|
| Форд—Фалкерсон  | O(E·maxflow) | любой дополняющий путь (DFS) — зависит от величин |
| **Эдмондс—Карп**| **O(V·E²)** | путь — всегда кратчайший (BFS)         |
| Диниц           | O(V²·E)    | слоистая сеть + блокирующий поток       |

## ✂️ Теорема о максимальном потоке и минимальном разрезе

Самый красивый факт темы. **Разрез** — разбиение вершин на две группы: `S` (с истоком) и `T` (со стоком).
**Пропускная способность разреза** — сумма пропускных рёбер, идущих из `S` в `T`. Это «стоимость» разорвать
сеть по этой линии.

> **Теорема (max-flow min-cut).** Величина **максимального потока** равна **минимальной** пропускной
> способности разреза. Максимум, что можно протолкнуть, ограничен самым узким «перерезом» — и этот предел
> всегда достижим.

Практический смысл — прямой:

- **Надёжность сети.** Минимальный разрез — это **слабое звено**: набор каналов, вырубив которые, противник
  (или авария) полностью разорвёт связь `s`—`t`. Их суммарная пропускная и есть «запас прочности».
- **Как найти сам разрез.** Досчитай максимальный поток, затем в **остаточной** сети запусти BFS из `s`.
  Достижимые вершины — это `S`, остальные — `T`. Рёбра из `S` в `T` (в исходном графе) и есть минимальный
  разрез. Именно это подсвечивает виджет выше на последнем шаге.

## 🔗 Двудольное паросочетание = поток

Отдельный, очень частый на практике случай. **Двудольный граф**: слева — воркеры, справа — задачи; ребро
`w—t` значит «воркер `w` умеет задачу `t`». **Паросочетание** — назначение без конфликтов: один воркер — одна
задача, одна задача — одному воркеру. Нужно назначить **максимум** пар.

**Это ровно задача о потоке.** Сведение механическое:

1. добавляем **исток** `s` и ребро `s→w` пропускной **1** к каждому воркеру (воркер берёт ≤ 1 задачи);
2. каждое ребро `w→t` (совместимость) — пропускной **1**;
3. каждой задаче — ребро `t→z` пропускной **1** к **стоку** `z` (задачу берёт ≤ 1 воркер).

Максимальный поток `s→z` = размер максимального паросочетания. Единичные пропускные гарантируют, что каждый
занят не больше одного раза.

> 💡 **Тот же виджет — но паросочетание.** Сеть ниже: исток `s`, воркеры `w1..w3`, задачи `t1..t3`, сток `z`,
> все пропускные — 1. Каждая протолкнутая единица потока = одна назначенная пара. Обрати внимание, как поток
> при необходимости **перекидывает** уже назначенную задачу другому воркеру через обратное ребро — это и есть
> «увеличивающая цепь» из алгоритма Куна ниже.

<div class="algo-viz" data-viz="max-flow" data-nodes="s,w1,w2,w3,t1,t2,t3,z" data-edges="s-w1-1,s-w2-1,s-w3-1,w1-t1-1,w1-t2-1,w2-t1-1,w3-t2-1,w3-t3-1,t1-z-1,t2-z-1,t3-z-1" data-source="s" data-sink="z" data-matching="true"></div>

На практике для паросочетания редко строят полную сеть — используют её «свёрнутую» форму, **алгоритм Куна**:
для каждой левой вершины ищем **увеличивающую цепь** поиском в глубину. Если задача свободна или её текущего
исполнителя можно **пересадить** на другую — занимаем.

```go
// Алгоритм Куна: размер максимального паросочетания.
// adj[w] — задачи, которые умеет воркер w. matchR[task] — назначенный воркер (или -1).
func maxMatching(nLeft, nRight int, adj [][]int) int {
    matchR := make([]int, nRight)
    for i := range matchR {
        matchR[i] = -1
    }
    var augment func(w int, seen []bool) bool
    augment = func(w int, seen []bool) bool {
        for _, task := range adj[w] {
            if seen[task] {
                continue
            }
            seen[task] = true
            // задача свободна ИЛИ её исполнителя можно пересадить
            if matchR[task] == -1 || augment(matchR[task], seen) {
                matchR[task] = w
                return true
            }
        }
        return false
    }
    result := 0
    for w := 0; w < nLeft; w++ {
        seen := make([]bool, nRight)
        if augment(w, seen) {
            result++
        }
    }
    return result
}
```

## 🧠 Почему это корректно

### Почему обратные рёбра дают именно максимум

Форд—Фалкерсон останавливается, когда дополняющего пути нет. Докажем, что тогда поток максимален — через
разрез. Пусть `S` — вершины, достижимые из `s` в остаточной сети (раз пути до `t` нет, `t ∉ S`). Любое
исходное ребро из `S` в `T` **насыщено** (иначе по нему был бы остаток, и сосед попал бы в `S`), а поток по
рёбрам из `T` в `S` равен нулю. Значит, поток через этот разрез = его полной пропускной способности. Но поток
**никогда** не превосходит пропускной любого разреза. Мы упёрлись в конкретный разрез — следовательно, это
**и максимальный поток, и минимальный разрез одновременно**. Обратные рёбра — то, что позволяет «размотать»
неудачное назначение и добраться до этого предела.

### Почему Эдмондс—Карп завершается

Наивный Форд—Фалкерсон с неудачным выбором пути на иррациональных пропускных (вида √2) теоретически
может считать вечно, а на целых — делать до `maxflow` аугментаций по единичке (каждый поиск пути стоит `O(E)` — итого `O(E·maxflow)` времени). BFS
(кратчайший путь) это чинит: можно доказать, что кратчайшее расстояние `s→t` в остаточной сети только **растёт**,
а каждое ребро становится «узким местом» не больше `O(V)` раз. Отсюда `O(V·E)` аугментаций и `O(V·E²)` всего.

## ⚙️ Цена на практике

### Целочисленность — бесплатный бонус

Если все пропускные способности **целые**, максимальный поток тоже целый, и на каждом шаге проталкивается
целое число. Поэтому паросочетание (пропускные = 1) даёт ровно 0/1 на рёбрах — назначение, а не «полтора
воркера». Это **теорема о целочисленности**, и она — причина, почему поток так удобно ложится на дискретные
задачи назначения.

### Где это действительно в проде

Поток редко пишут руками в вебе, но он — движок под многими системами: **сегментация изображений**
(графовый min-cut разделяет объект и фон), **project selection** (какие проекты взять при зависимостях и
бюджете), распределение **водителей по заказам**, рекламы по слотам, **baseball elimination** (может ли
команда ещё выйти в плей-офф). В Go готовый макс-поток — в
[`gonum.org/v1/gonum/graph/flow`](https://pkg.go.dev/gonum.org/v1/gonum/graph/flow) (в т.ч. Push–Relabel,
быстрее Эдмондса—Карпа на плотных графах).

### Выбор алгоритма по размеру

Эдмондс—Карп `O(V·E²)` хватает для учебных и средних графов. На больших/плотных берут **Диница** `O(V²·E)`
(особенно быстр на единичных пропускных — паросочетание за `O(E·√V)`) или **Push–Relabel**. Для назначения с
**ценами** (минимизировать стоимость) — это уже min-cost max-flow или **венгерский алгоритм**, отдельная тема.

## ⚠️ Типичные ошибки

1. **Забыть обратные рёбра.** Без остаточных `v→u` алгоритм не сможет «передумать» и застрянет в неоптимуме —
   самая частая и коварная ошибка.
2. **Искать путь DFS вместо BFS.** Без BFS это уже не Эдмондс—Карп: на больших целых пропускных возможно
   очень долгое схождение (до `maxflow` путей, `O(E·maxflow)` времени), а на иррациональных — в теории бесконечное.
3. **Антипараллельные рёбра.** Если в исходном графе есть и `u→v`, и `v→u`, обычная матрица `cap` их путает —
   разнеси одно через промежуточную вершину или используй списки рёбер с индексами.
4. **Путать направление.** Поток ориентирован: ребро `u→v` не даёт течь из `v` в `u` (кроме как отменой уже
   пущенного потока по остаточному ребру).
5. **Тянуть поток туда, где хватило бы паросочетания.** Для чистого назначения Кун проще и быстрее полной
   сети — не строй лишнего.

## 📝 Разбор задачи: назначить воркеров на задачи

> **Задача.** Три воркера, три задачи. `w1` умеет `{t1, t2}`, `w2` умеет `{t1}`, `w3` умеет `{t2, t3}`.
> Назначить максимум пар (воркер—задача), никого не перегружая. Это ровно двудольная сеть из виджета выше.

**Шаг 1. Распознать.** «Назначить максимум пар без конфликтов» — двудольное **паросочетание**. Значит, либо
поток (сведением), либо алгоритм Куна. Возьмём Куна.

**Шаг 2. Жадно — и почему мало.** Пойдём по воркерам. `w1` берёт первую свободную — `t1`. `w2` умеет только
`t1`, а она занята → `w2` **застрял**. Наивная жадность даёт 2 пары. Но оптимум — 3, и чтобы его достать,
нужно **пересадить** `w1`.

**Шаг 3. Увеличивающая цепь.** `w2` хочет `t1`, но там `w1`. Спросим `w1`: есть ли у него **другая** задача?
Да — `t2`, она свободна. `w1` уходит на `t2`, освобождая `t1` для `w2`. Это и есть увеличивающая цепь
`w2 → t1 → w1 → t2`: чередование «занять/освободить» вдоль пути увеличивает паросочетание на 1.

**Шаг 4. Трассировка Куна.**

| Воркер | Пробует | Что происходит | Паросочетание после |
|--------|---------|----------------|---------------------|
| `w1`   | `t1`    | свободна → занимает | `t1←w1` |
| `w2`   | `t1`    | занята `w1`; пересаживаем `w1` на `t2` (свободна) | `t2←w1`, `t1←w2` |
| `w3`   | `t2`    | занята `w1`; у `w1` других свободных нет → пробуем дальше | — |
| `w3`   | `t3`    | свободна → занимает | `t3←w3` |

Итог — **3 пары**: `t1←w2`, `t2←w1`, `t3←w3`. Ровно та величина потока `3`, что находит виджет-сеть выше.
Жадность дала бы 2 — разницу делает умение **отменить** прежнее назначение (обратное ребро в потоке =
пересадка в Куне).

## 🎬 Визуализация

> 💡 **Интерактивная демонстрация.** Сверху — исходные интервалы на числовой прямой (жёлтым
> подсвечен текущий), снизу — результат слияния, который растёт по мере прохода. Справа — код
> с подсветкой строки и переменные, внизу — кликабельные шаги. Можно подставить свои интервалы
> и нажать «⟲ Запустить». (Виджет работает в собранной книге `mdbook serve`/`mdbook build`, а не
> при просмотре `.md` на GitHub.)

## ⚡ Шаблон для собеседования

```go
sort.Slice(intervals, func(i, j int) bool {
    return intervals[i][0] < intervals[j][0] // по началу
})
result := [][]int{intervals[0]}
for i := 1; i < len(intervals); i++ {
    cur, last := intervals[i], result[len(result)-1]
    if cur[0] <= last[1] {                 // перекрытие
        last[1] = max(last[1], cur[1])     // расширяем конец
    } else {                               // разрыв
        result = append(result, cur)       // новый интервал
    }
}
return result
```

1. сортируем по началу;
2. кладём первый интервал в результат;
3. для каждого следующего сравниваем `cur.start` с `last.end`;
4. перекрытие → расширяем `last.end`; разрыв → добавляем новый.

## 📖 Разбор

<details class="algo-details">
<summary>Теория, слияние, вставка интервала и сложность</summary>

**Merge Intervals** — техника для работы с перекрывающимися интервалами: их слияния,
поиска пересечений и вставки новых интервалов в отсортированный список.

Ключевая идея: если интервалы отсортированы по начальной точке, то для проверки
перекрытия достаточно сравнить начало текущего интервала с концом последнего
объединённого. Два интервала `[a, b]` и `[c, d]` перекрываются при `a <= d && c <= b`;
при слиянии получаем `[min(a, c), max(b, d)]`. Сортировка превращает задачу из O(n²)
в O(n log n).

```go
func mergeIntervals(intervals [][]int) [][]int {
    if len(intervals) == 0 {
        return [][]int{}
    }
    sort.Slice(intervals, func(i, j int) bool {
        return intervals[i][0] < intervals[j][0]
    })

    result := [][]int{intervals[0]}
    for i := 1; i < len(intervals); i++ {
        current := intervals[i]
        last := result[len(result)-1]
        if current[0] <= last[1] { // перекрытие
            if current[1] > last[1] {
                last[1] = current[1] // расширяем конец до максимума
            }
        } else {
            result = append(result, current) // разрыв — новый интервал
        }
    }
    return result
}
```

#### Вставка интервала

Для вставки нового интервала в уже отсортированный список делаем один проход:
интервалы, заканчивающиеся до нового, копируем как есть; пересекающиеся поглощаем,
расширяя границы нового; остальные добавляем после.

```go
func insertInterval(intervals [][]int, newInterval []int) [][]int {
    var result [][]int
    i, n := 0, len(intervals)

    for i < n && intervals[i][1] < newInterval[0] { // целиком слева
        result = append(result, intervals[i])
        i++
    }
    merged := []int{newInterval[0], newInterval[1]}
    for i < n && intervals[i][0] <= merged[1] { // перекрытие — поглощаем
        if intervals[i][0] < merged[0] {
            merged[0] = intervals[i][0]
        }
        if intervals[i][1] > merged[1] {
            merged[1] = intervals[i][1]
        }
        i++
    }
    result = append(result, merged)

    for i < n { // целиком справа
        result = append(result, intervals[i])
        i++
    }
    return result
}
```

#### Сложность

| Операция          | Время       | Память |
|-------------------|-------------|--------|
| Слияние интервалов | O(n log n) | O(n)   |
| Вставка интервала  | O(n)       | O(n)   |

Для слияния доминирует сортировка O(n log n), сам проход линеен. Вставка не требует
сортировки — вход уже упорядочен.

## 🧠 Почему это корректно

### Почему сортировки по началу достаточно

После сортировки по началу действует ключевой факт:

> Расширить текущий интервал может **только** последний добавленный в результат. Все
> более ранние результирующие интервалы заканчиваются раньше, чем начинается текущий
> (начала отсортированы, а эти интервалы уже были отделены разрывом).

Поэтому сравнение лишь с `result[last]` ничего не пропускает. Это тот же принцип, что у
[двух указателей](two-pointers.md): сортировка делает решение **локальным**. Инвариант:
`result` всегда хранит непересекающиеся интервалы по возрастанию; очередной либо
продлевает последний (`current.start <= last.end`), либо начинает новый.

При сортировке по началу условие перекрытия `a <= d && c <= b` упрощается до
`current.start <= last.end` — вторая половина выполнена автоматически.

### Почему по началу, а не по концу

Сортировка **по началу** — не произвольный выбор: именно она делает «расширить может только
последний» истинным. Раз начала упорядочены, любой будущий интервал начинается не раньше
текущего, поэтому достать «через голову» уже отделённый разрывом интервал невозможно.
Сортировка **по концу** решает *другую* задачу — жадный выбор максимума непересекающихся
отрезков (*Non-overlapping Intervals*, *Burst Balloons*): там берём отрезок с самым ранним
концом, оставляя больше места справа. Перепутать эти две сортировки — классический баг:
по концу слияние пропустит перекрытия.

### Касание границ — это решение из условия, а не деталь

Сливаются ли `[1,2]` и `[2,3]`? Ответ зависит от того, **закрыты** интервалы или
полуоткрыты — то есть от постановки. Поэтому выбор `current.start <= last.end` против
`<` — не мелочь реализации, а часть определения корректности: для отрезков на прямой
(касание = перекрытие) берут `<=`, для полуоткрытых `[start, end)` — `<`. Зафиксируй
семантику в начале и держи её во всех сравнениях, иначе ответ «поедет» именно на стыках.

## ⚙️ Цена на практике

### Сортировка — это и есть стоимость

Слияние — `O(n log n)`, где доминирует **сортировка**; сам проход линеен. Не заявляй
`O(n)`. А вот **вставка** интервала — честные `O(n)`: вход уже отсортирован, сортировать
не нужно. Увидел «список уже упорядочен» — не сортируй заново.

### `sort.Slice` мутирует вход

`sort.Slice(intervals, …)` переставляет элементы **на месте** — порядок исходного среза
меняется. Если вызывающий код не должен заметить перестановку (срез ещё нужен в исходном
виде), копируй перед сортировкой: `cp := append([][]int(nil), intervals...)`. Это `O(n)`
памяти — та же дилемма «на месте против копии», что у затопления сетки в
[обходе графов](grids-and-shortest-paths.md): экономия памяти ценой мутации входа.

### Sweep line обобщает интервалы

Слияние — простейший случай **сканирующей прямой** (sweep line). Когда задача не «слить»,
а «сколько максимум одновременно» (*Meeting Rooms II* — минимум переговорок), переходи к
событиям: на каждом начале `+1`, на каждом конце `−1`, отсортируй события и веди счётчик —
его максимум и есть ответ. Та же идея решает пересечения и объединения. Знать sweep line
как общий инструмент полезнее, чем заучивать каждую задачу по интервалам отдельно.

### Динамические интервалы — не пересортировывать

Если интервалы приходят по одному и между вставками нужны запросы, пересортировка каждый
раз — `O(n log n)` на операцию. **Дерево интервалов** или сбалансированное BST по началам
даёт `O(log n)` на вставку/поиск пересечений. Для статического входа это лишнее, но при
потоке правок асимптотика на операцию падает принципиально.

## ⚠️ Типичные ошибки

1. **Забыли отсортировать** перед проходом — без сортировки сравнение только с
   последним интервалом некорректно.
2. **Неверное объединение концов** — берите `max(last[1], current[1])`, иначе
   присваивание `last[1] = current[1]` может *уменьшить* интервал.
3. **Неправильная проверка перекрытия** — условие именно `current[0] <= last[1]`
   (с учётом равенства, если касание считается перекрытием).
4. **Пустой вход** — обращение к `intervals[0]` упадёт; обработайте `len == 0`.
5. **Некорректный интервал** (`start > end`) — при необходимости валидируйте вход.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он медленный, и
только потом сортировка с одним проходом.

> **Задача.** Дан список интервалов `intervals`, каждый — пара `[start, end]`. Слить
> все **перекрывающиеся** интервалы и вернуть список непересекающихся (касание границ
> считаем перекрытием).
> Пример: `[[1,3],[2,6],[8,10],[15,18]]` → `[[1,6],[8,10],[15,18]]` (`[1,3]` и `[2,6]`
> перекрываются → `[1,6]`).

**Шаг 1. Наивно: сливать пары, пока что-то меняется — O(n²).**

```go
func mergeNaive(intervals [][]int) [][]int {
    res := append([][]int(nil), intervals...)
    for changed := true; changed; {
        changed = false
        for i := 0; i < len(res); i++ {
            for j := i + 1; j < len(res); j++ {
                a, b := res[i], res[j]
                if a[0] <= b[1] && b[0] <= a[1] { // пара перекрывается
                    res[i] = []int{min(a[0], b[0]), max(a[1], b[1])}
                    res = append(res[:j], res[j+1:]...) // удаляем j
                    changed = true
                    j--
                }
            }
        }
    }
    return res
}
```

Это **работает и проходит тесты**, но мы заново перебираем все пары `O(n²)` на каждом
из возможных `O(n)` проходов до стабилизации. Соседние интервалы сравниваются снова и
снова, хотя их взаимное расположение давно известно — вот эта повторная работа и есть
то, что убирает сортировка.

**Шаг 2. Ключевое наблюдение.** Отсортируем по началу. Тогда любой будущий интервал
начинается **не раньше** текущего, а значит расширить незакрытый «хвост» результата
может только последний добавленный — все более ранние уже отделены разрывом и
заканчиваются левее. Сравнивать с остальными бессмысленно: проверка одной пары
`cur.start ≤ last.end` за проход исчерпывает все слияния. Подробнее, *почему* сортировка
именно по началу даёт этот инвариант — в разделе
[«Почему сортировки по началу достаточно»](#почему-сортировки-по-началу-достаточно).

**Шаг 3. Оптимум: сортировка + один проход — O(n log n).**

```go
func mergeOpt(intervals [][]int) [][]int {
    if len(intervals) == 0 {
        return [][]int{}
    }
    sort.Slice(intervals, func(i, j int) bool {
        return intervals[i][0] < intervals[j][0] // по началу
    })
    result := [][]int{intervals[0]}
    for i := 1; i < len(intervals); i++ {
        cur := intervals[i]
        last := result[len(result)-1]
        if cur[0] <= last[1] {        // перекрытие
            if cur[1] > last[1] {
                last[1] = cur[1]      // расширяем конец до максимума
            }
        } else {
            result = append(result, cur) // разрыв — новый интервал
        }
    }
    return result
}
```

**Шаг 4. Трассировка** на `[[1,3],[2,6],[8,10],[15,18]]` (уже отсортирован по началу):

| `i` | `cur` | `last` | `cur.start ≤ last.end`? | действие | `result` |
|-----|-------|--------|-------------------------|----------|----------|
| —   | —     | —      | —                       | первый в результат | `[[1,3]]` |
| 1   | `[2,6]`  | `[1,3]`  | `2 ≤ 3` ✓ | слить: `end=max(3,6)=6` | `[[1,6]]` |
| 2   | `[8,10]` | `[1,6]`  | `8 ≤ 6` ✗ | разрыв → новый | `[[1,6],[8,10]]` |
| 3   | `[15,18]`| `[8,10]` | `15 ≤ 10` ✗ | разрыв → новый | `[[1,6],[8,10],[15,18]]` |

Ответ — `[[1,6],[8,10],[15,18]]`, совпадает с наивным. Обрати внимание: проход линеен,
каждый интервал смотрим ровно один раз — вся стоимость ушла в
[сортировку O(n log n)](#сортировка--это-и-есть-стоимость).

## 🎬 Визуализация

> 💡 **Интерактивная демонстрация.** Жёлтым отмечен `mid`, синим/фиолетовым — границы `left`/`right`,
> затемнены отброшенные половины. Справа — код с подсветкой строки и таблица переменных, внизу —
> кликабельные шаги. Можно подставить свой массив и `target` и нажать «⟲ Запустить». (Виджет
> работает в собранной книге `mdbook serve`/`mdbook build`, а не при просмотре `.md` на GitHub.)

## ⚡ Шаблон для собеседования

```go
left, right := 0, len(arr)-1
for left <= right {
    mid := left + (right-left)/2
    switch {
    case arr[mid] == target:
        return mid
    case arr[mid] < target:
        left = mid + 1  // ответ правее
    default:
        right = mid - 1 // ответ левее
    }
}
return -1
```

1. границы по краям, инвариант «ответ в `[left, right]`»;
2. `mid := left + (right-left)/2`;
3. сравнили `arr[mid]` с целью → сдвинули **одну** границу;
4. цикл, пока `left <= right`.

## 📖 Разбор

<details class="algo-details">
<summary>Теория, варианты (первое вхождение, повёрнутый массив, sort.Search) и сложность</summary>

**Modified Binary Search** расширяет классический бинарный поиск на задачи, где
ищут не точное значение, а **границу монотонного предиката**: первое/последнее
вхождение, позицию вставки, минимум в повёрнутом массиве, элемент в 2D-матрице.

Ключевая идея: бинарный поиск работает для любого монотонного условия. Меняя
условие сравнения и правило обновления границ, мы решаем разные задачи поиска за
**O(log n)**, сохраняя инвариант «решение, если оно есть, лежит в `[left, right]`».

#### Классический поиск значения

```go
func binarySearch(arr []int, target int) int {
    left, right := 0, len(arr)-1
    for left <= right {
        mid := left + (right-left)/2
        switch {
        case arr[mid] == target:
            return mid
        case arr[mid] < target:
            left = mid + 1 // ищем в правой половине
        default:
            right = mid - 1 // ищем в левой половине
        }
    }
    return -1 // не найдено
}
```

#### Первое вхождение

При равенстве не останавливаемся, а продолжаем сжимать правую границу — так находим
самый левый индекс с `target`.

```go
func findFirstOccurrence(arr []int, target int) int {
    left, right := 0, len(arr)-1
    result := -1
    for left <= right {
        mid := left + (right-left)/2
        switch {
        case arr[mid] == target:
            result = mid    // запоминаем и продолжаем влево
            right = mid - 1
        case arr[mid] < target:
            left = mid + 1
        default:
            right = mid - 1
        }
    }
    return result
}
```

#### Повёрнутый массив

Одна из половин `[left..mid]` или `[mid..right]` всегда отсортирована. Проверяем
`arr[left] <= arr[mid]`: если да — отсортирована левая половина, иначе правая. Ищем
`target` только в отсортированной половине.

#### Идиоматичный Go

`sort.Search` находит наименьший индекс, для которого предикат истинен:

```go
import "sort"

func searchIdiomatic(arr []int, target int) int {
    i := sort.Search(len(arr), func(i int) bool {
        return arr[i] >= target
    })
    if i < len(arr) && arr[i] == target {
        return i
    }
    return -1
}
```

#### Сложность

| Случай       | Время    | Память |
|--------------|----------|--------|
| Лучший       | O(1)     | O(1)   |
| Средний/худший | O(log n) | O(1)   |

На каждом шаге интервал уменьшается вдвое, отсюда не более `log₂(n)` шагов; память
константна — храним только индексы.

## 🧠 Почему это корректно

  <div class="algo-explain__item">
    <div class="algo-explain__q">Настоящее предусловие бинарного поиска — это не «массив отсортирован». Что это?</div>
    <div class="algo-explain__ref"><b>Монотонность предиката</b>: есть <code>p(i)</code> вида <code>false … false true … true</code> с единственной точкой переключения, и поиск находит эту границу. Отсортированность — лишь частый способ получить монотонность (<code>p(i) = arr[i] >= target</code>), но, скажем, «минимум в повёрнутом массиве» даёт монотонный предикат <code>arr[i] <= arr[last]</code> на неотсортированном массиве. Предикат не монотонен — ответ будет <b>неверным</b>, а не просто промахом.</div>
  </div>
  <div class="algo-explain__item">
    <div class="algo-explain__q">Почему присваивание <code>left = mid</code> (без <code>+1</code>) даёт вечный цикл, а <code>left = mid + 1</code> — нет?</div>
    <div class="algo-explain__ref"><code>mid = left + (right-left)/2</code> округляет вниз, поэтому при <code>left <= right</code> всегда <code>left <= mid <= right</code>. Тогда <code>left = mid + 1</code> строго больше прежнего <code>left</code>, а <code>right = mid - 1</code> строго меньше прежнего — интервал сужается каждый шаг. С <code>left = mid</code> при <code>right - left == 1</code> получаем <code>mid == left</code>, и присваивание не двигает границу: прогресса нет, цикл вечный. Отсюда правило: конвенция <code>left <= right</code> идёт в паре с <code>mid±1</code>, полуинтервал <code>[left, right)</code> — с <code>right = mid</code>; смешивать нельзя.</div>
  </div>
</div>

Бинарный поиск — это не «поиск в отсортированном массиве», а **поиск границы
монотонного предиката**. Эта переформулировка и есть ключ к корректности.

### Настоящее предусловие — монотонность предиката

Введём предикат `p(i)` со значениями `false … false true … true` (одна точка
переключения). Бинарный поиск находит границу — первый индекс, где `p` истинно.

- классический поиск: `p(i) = arr[i] >= target` (монотонно, т.к. массив отсортирован);
- первое вхождение: та же `p`, плюс проверка `arr[i] == target` на границе;
- минимум в повёрнутом массиве: `p(i) = arr[i] <= arr[last]` — тоже монотонно.

Если `p` **не монотонна** (нет единственной точки переключения), бинарный поиск даст
неверный ответ, а не просто промахнётся. Прежде чем писать — убедись, что предикат
монотонен. Это сильнее, чем «массив отсортирован».

### Инвариант и почему ответ не теряется

> **Инвариант.** Граница (искомый индекс), если она существует, всегда лежит в
> `[left, right]`.

Каждый шаг отбрасывает половину, про которую предикат **гарантирует**, что границы
там нет: если `arr[mid] < target`, то и все элементы левее меньше target → граница
правее, безопасно `left = mid + 1`. Инвариант сохраняется, ответ остаётся в диапазоне.

### Завершаемость — почему именно `mid+1` и `mid-1`

Это место, где рождаются бесконечные циклы. Цикл завершается, только если интервал
`[left, right]` **строго сужается** каждый шаг. Разберём, почему выбранные границы это
гарантируют:

`mid = left + (right-left)/2` округляет **вниз**, поэтому при `left <= right` всегда
`left <= mid <= right`. Тогда:

- `left = mid + 1` строго больше прежнего `left` (т.к. `mid >= left`);
- `right = mid - 1` строго меньше прежнего `right` (т.к. `mid <= right`).

Любая ветка двигает границу — прогресс гарантирован, интервал в худшем случае
обнуляется за `log₂ n` шагов. **Опасная альтернатива** — присвоить `left = mid` (без
`+1`): когда `right - left == 1`, получаем `mid == left`, и `left = mid` оставляет
`left` на месте → **вечный цикл**. Поэтому конвенция `left <= right` идёт в паре с
`mid±1`, а не с `mid`.

Практический совет: выбери **одну** конвенцию границ — замкнутый отрезок `[left,
right]` с `left <= right` и `mid±1`, либо полуинтервал `[left, right)` с `left <
right` и `right = mid` — и не смешивай их. Смешение конвенций — причина №1 багов в
бинарном поиске.

## ⚙️ Цена на практике

`O(log n)` выглядит непобедимо, но у константы есть нюансы.

### `O(log n)` не всегда быстрее линейного прохода

Бинарный поиск **прыгает** по памяти и ветвится — это промахи кэша и ошибки
предсказателя переходов. На маленьких массивах (десятки элементов) обычный линейный
`for` часто быстрее: данные лежат подряд, процессор префетчит, ветвлений нет.
`O(log n)` выигрывает на больших `n`, но «асимптотически лучше» ≠ «быстрее на твоих
данных» — меряй.

### Предпочитай `sort.Search` ручному циклу

`sort.Search` инкапсулирует всю арифметику границ — меньше шансов на off-by-one. Твоя
задача — сформулировать **монотонный** предикат, остальное стандартная библиотека
сделает корректно. Ручной цикл пиши, только если нужен нестандартный шаг (повёрнутый
массив, 2D).

### Граница может быть не в массиве, а в пространстве ответов

Самое мощное обобщение: предикат `p` не обязан читать заранее посчитанный массив — это
может быть функция «достижимо ли значение `X`?», монотонная по `X`. Тогда бинарный
поиск идёт **по диапазону ответов**, а не по индексам. Это отдельный приём — [бинарный
поиск по ответу](#бинарный-поиск-по-ответу) ниже.

## Бинарный поиск по ответу

Самый недооценённый приём бинарного поиска — когда массива для поиска **нет**, а
ищем мы сам ответ в диапазоне его возможных значений. Это решает целый класс задач
вида «минимальное/максимальное `X`, при котором что-то выполнимо».

### Идея

Если по ответу можно построить **монотонный** предикат `feasible(X)` —
«достижима ли цель при значении `X`?» — то бинарный поиск ищет границу этого предиката
по диапазону `X`, а не по индексам массива. `feasible` обычно проверяется отдельной
функцией за `O(n)`, поэтому итог — `O(n · log(диапазона))`.

Работает **тогда и только тогда**, когда `feasible` монотонна: если цель достижима при
`X`, она достижима и при всех «более щедрых» значениях (бо́льшая скорость, бо́льшая
вместимость, бо́льший бюджет). Это та же монотонность предиката, что и [выше](#настоящее-предусловие--монотонность-предиката),
только по пространству ответов.

### Пример: Koko Eating Bananas

Коко ест бананы со скоростью `speed` штук в час; за кучу `pile` тратит
`ceil(pile/speed)` часов. Найти **минимальную** скорость, чтобы успеть за `h` часов.

Предикат `feasible(speed)` = «успеет за `h` часов» — монотонен: чем больше скорость,
тем меньше суммарное время. Ищем левую границу «успевает» по диапазону скоростей
`[1, max(piles)]`:

```go
func minEatingSpeed(piles []int, h int) int {
    feasible := func(speed int) bool {
        hours := 0
        for _, p := range piles {
            hours += (p + speed - 1) / speed // ceil(p/speed)
        }
        return hours <= h
    }
    lo, hi := 1, 0
    for _, p := range piles {
        if p > hi {
            hi = p
        }
    }
    // ищем минимальный speed, при котором feasible == true
    for lo < hi {
        mid := lo + (hi-lo)/2
        if feasible(mid) {
            hi = mid // успеваем — пробуем медленнее
        } else {
            lo = mid + 1 // не успеваем — нужно быстрее
        }
    }
    return lo
}
```

Обрати внимание на конвенцию `[lo, hi)` с `lo < hi` и `hi = mid` (без `−1`) — здесь
она удобнее, потому что мы ищем **первое** `true`, а не точное значение. Главное —
не смешивать её с конвенцией `lo <= hi` + `mid±1` из примеров выше.

### Как распознать на собеседовании

- В условии «**минимальное/максимальное** `X`, при котором…» + ответ лежит в числовом
  диапазоне.
- Прямой перебор `X` дал бы правильный ответ, но слишком медленно.
- Есть функция-проверка `feasible(X)` за полином, **монотонная** по `X`.

## ⚠️ Типичные ошибки

1. **Переполнение `mid`** — считайте `left + (right-left)/2`, а не
   `(left + right)/2`.
2. **Неверное условие цикла** — `left <= right` ищет в закрытом интервале;
   `left < right` (с `right = mid`) — для поиска границы. Смешивать нельзя.
3. **Неправильное обновление границ** — для первого вхождения при равенстве надо
   двигать `right = mid - 1`, а не возвращать `mid` сразу.
4. **Повёрнутый массив**: забыли определить отсортированную половину перед
   отбрасыванием — тогда теряете `target`.
5. **Не обработаны границы** — пустой массив, один элемент, `target` вне диапазона.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* через предикат
выходит логарифм, и только потом два бинарных поиска.

> **Задача.** Дан отсортированный по неубыванию массив `nums` (возможны дубликаты) и
> число `target`. Вернуть **первую и последнюю** позицию `target` как `[first, last]`.
> Если значения нет — `[-1, -1]`. Требуется `O(log n)`.
> Пример: `nums = [5,7,7,8,8,10]`, `target = 8` → `[3, 4]`.

**Шаг 1. Наивно: линейный проход — O(n).**

```go
func searchRangeNaive(nums []int, target int) [2]int {
    res := [2]int{-1, -1}
    for i, v := range nums {
        if v == target {
            if res[0] == -1 {
                res[0] = i // первое совпадение
            }
            res[1] = i     // последнее совпадение перетирается
        }
    }
    return res
}
```

Это **работает и проходит тесты**, но игнорирует отсортированность: один проход по
всем `n` элементам. На массиве из миллионов дубликатов `target` мы трогаем каждый из
них, хотя нужны только два крайних индекса. Условие просит `O(log n)` — линейный
проход в него не укладывается.

Прогоните линейный скан на `[5,7,7,8,8,10]`, `target = 8`: трогаем каждый элемент,
`res[0]` фиксируется на первом совпадении, `res[1]` обновляется на каждом:

**Шаг 2. Ключевое наблюдение.** Задача распадается на два независимых поиска
**границы**, а не значения. Введём `lowerBound(x)` — наименьший индекс, где
`nums[i] >= x` (это `false … false true … true` по `i`, предикат монотонен, см.
[настоящее предусловие](#настоящее-предусловие--монотонность-предиката)). Тогда:

- `first = lowerBound(target)` — первый индекс, где значение «дотянулось» до `target`;
- `last  = lowerBound(target+1) - 1` — на единицу левее первого индекса, где значение
  уже **превысило** `target`, то есть последний `target`.

Существование проверяем один раз: если `first` вышел за массив или `nums[first] != target`,
значения нет → `[-1, -1]`. Два логарифма дают `O(log n)`.

**Шаг 3. Оптимум: два бинарных поиска границы — O(log n).**

```go
// наименьший индекс, где nums[i] >= target (может быть len(nums))
func lowerBound(nums []int, target int) int {
    lo, hi := 0, len(nums)
    for lo < hi {                 // полуинтервал [lo, hi), ищем границу
        mid := lo + (hi-lo)/2
        if nums[mid] < target {
            lo = mid + 1          // граница строго правее
        } else {
            hi = mid              // mid — кандидат, сужаем вправо
        }
    }
    return lo
}

func searchRange(nums []int, target int) [2]int {
    first := lowerBound(nums, target)
    if first == len(nums) || nums[first] != target {
        return [2]int{-1, -1}     // значения нет
    }
    last := lowerBound(nums, target+1) - 1
    return [2]int{first, last}
}
```

Здесь конвенция `[lo, hi)` с `lo < hi` и `hi = mid` (без `−1`) — она для поиска
**границы**, и её нельзя смешивать с `lo <= hi` + `mid±1` из примеров выше.

Прогоните поиск левой границы `target = 8` в `[5,7,7,8,8,10]`: найдя совпадение,
запоминаем позицию и продолжаем искать ещё левее (правый поиск — зеркально):

**Шаг 4. Трассировка** `lowerBound([5,7,7,8,8,10], 8)` (находит `first`):

| `lo` | `mid` | `hi` | `nums[mid]` | решение            |
|------|-------|------|-------------|--------------------|
| 0    | 3     | 6    | 8           | `8 < 8` ложно → `hi = 3` |
| 0    | 1     | 3    | 7           | `7 < 8` → `lo = 2`       |
| 2    | 2     | 3    | 7           | `7 < 8` → `lo = 3`       |
| 3    | —     | 3    | —           | `lo == hi` → выход, `first = 3` |

Затем `lowerBound([5,7,7,8,8,10], 9)` даёт `5`, поэтому `last = 5 - 1 = 4`. Итог —
`[3, 4]`. Тот же ответ, что и у наивного перебора, но за два логарифма вместо прохода
по всем дубликатам.

## 🏗️ Инженерный кейс

> **Ситуация.** Капасити-планирование. Нужно перевезти весь груз за `D` дней; корабль грузят по порядку, и
> вопрос — **минимальная грузоподъёмность**, при которой уложишься в срок. Или: минимальная мощность
> воркера, чтобы разгрести очередь за час. Диапазон возможных значений огромен — перебирать каждое дорого.

Ключевое наблюдение: ответ **монотонен** — чем больше мощность, тем точно не хуже. А раз так, искать можно
не перебором, а делением пополам — но не массива, а **диапазона ответов**:

## 1. НОД и алгоритм Евклида

`gcd(a, b)` не меняется, если большее заменить на остаток от деления: `gcd(a, b) = gcd(b, a mod b)`.
Повторяем, пока второе число не станет нулём — тогда первое и есть НОД. Сходится за
**O(log min(a, b))** шагов.

```go
func gcd(a, b int) int {
    for b != 0 {
        a, b = b, a%b // большее → остаток
    }
    return a
}

// НОК через НОД; делим ДО умножения, чтобы не переполниться.
// lcm(0, x) = 0 по определению — и этот же guard спасает от деления на gcd(0,0) = 0.
func lcm(a, b int) int {
    if a == 0 || b == 0 {
        return 0
    }
    return a / gcd(a, b) * b
}
```

Из НОД сразу получаются: **сокращение дроби** (`a/g`, `b/g`), проверка **взаимной
простоты** (`gcd == 1`), выравнивание периодов.

Листай «›»: ячейки — **цепочка остатков** `a, b, a%b, …`, сходящаяся к нулю; последний
ненулевой остаток и есть НОД. Внизу попутно считаются коэффициенты Безу (расширенный Евклид,
подробнее — в главе [Криптография](cryptography.md)):

## 2. Быстрое возведение в степень

Наивное `aⁿ` — это n−1 умножений. Но `a⁸ = ((a²)²)²` — всего 3. Идея: разложить степень
по битам и на каждом шаге возводить базу в квадрат, домножая результат там, где бит равен 1.
**O(log n)** умножений.

```go
// (base^exp) mod m — версия «по модулю» (без неё число взорвётся)
func powMod(base, exp, m int) int {
    result := 1 % m
    base %= m
    for exp > 0 {
        if exp&1 == 1 {           // младший бит степени стоит
            result = result * base % m
        }
        base = base * base % m    // base, base², base⁴, base⁸, …
        exp >>= 1
    }
    return result
}
```

Без `mod` тот же каркас даёт обычное `aⁿ` (или `float64` для `Pow(x, n)`). Модульная
версия — основа комбинаторики «по модулю 1e9+7» и полиномиальных хешей.

Листай «›»: ячейки — **биты степени** `exp`; указатель идёт справа налево, как код читает
`exp&1` и делает `exp>>=1`. На бите 1 `result` домножается на `base`, каждый шаг `base`
возводится в квадрат — всё по модулю:

## 3. Решето Эратосфена и проверка простоты

Чтобы узнать, простое ли **одно** число, хватает пробного деления до корня — делителей
больше √n быть не может (они шли бы в паре с меньшим):

```go
func isPrime(n int) bool {
    if n < 2 {
        return false
    }
    for i := 2; i*i <= n; i++ { // до √n включительно
        if n%i == 0 {
            return false
        }
    }
    return true
}
```

Чтобы найти **все** простые до `n`, по числу пробное деление расточительно. Решето идёт
наоборот: берём очередное невычеркнутое число (оно простое) и вычёркиваем все его
кратные. **O(n log log n)** — почти линейно.

```go
func sieve(n int) []int {
    isComposite := make([]bool, n+1)
    var primes []int
    for p := 2; p <= n; p++ {
        if isComposite[p] {
            continue
        }
        primes = append(primes, p) // p простое
        for m := p * p; m <= n; m += p {
            isComposite[m] = true  // вычёркиваем кратные
        }
    }
    return primes
}
```

Зелёные клетки — подтверждённые простые, серые — вычеркнутые составные; `p` (текущий
кандидат) идёт слева, `m` вычёркивает свои кратные начиная с `p·p`:

## ⚡ Что помнить на собеседовании

- **НОД** — `for b != 0 { a, b = b, a%b }`. Короче не бывает, выучи наизусть.
- **НОК** = `a / gcd * b` (делить до умножения).
- **Степень** — `O(log n)` через квадраты; «по модулю» — домножай `% m` на каждом шаге.
- **Решето** — внешний цикл по `p`, внутренний вычёркивает кратные **с `p·p`**.
- В Go нет встроенного `gcd` для `int` (есть `math/big.Int.GCD` для больших) — пиши Евклида сам.

## 🧠 Почему это корректно

### Евклид: почему остаток сохраняет НОД

Если число делит и `a`, и `b`, оно делит и остаток `a mod b` — ведь остаток это `a` минус
несколько раз по `b`. Пример: `48` и `18` делятся на `6`, и остаток `48 mod 18 = 12` тоже
делится на `6`. Поэтому замена `(a, b) → (b, a mod b)` не меняет НОД, а числа быстро
уменьшаются: за два шага остаток падает минимум вдвое → **O(log n)**.

### Быстрая степень: почему хватает log n умножений

`13 = 8 + 4 + 1` (в двоичном виде `1101`), поэтому `3¹³ = 3⁸·3⁴·3¹`. Множители `3, 3², 3⁴,
3⁸` получаются друг из друга возведением в квадрат, а нужных из них столько, сколько у `n`
двоичных разрядов — около `log₂ n`. Отсюда логарифм. Для «по модулю» добавляем `% m` после каждого
умножения — это законно, потому что `(x·y) mod m = ((x mod m)·(y mod m)) mod m`.

### Решето: почему вычёркивать с `p·p`, а не с `2p`

К моменту, когда мы дошли до простого `p`, все составные с **меньшим** простым делителем
уже вычеркнуты. У любого составного `m < p·p` наименьший простой делитель `< p`, значит,
оно уже зачёркнуто. Первое ещё не зачёркнутое кратное `p` — это `p·p`. Старт с `p·p`
убирает повторную работу. Итог — `O(n log log n)`, почти линейно.

## ⚙️ Цена на практике

### Переполнение в умножении — главная ловушка

`base * base` и `result * base` могут переполнить `int64` ещё до взятия `% m`: оба
сомножителя доходят до `m − 1`, и уже при `m` больше ~3·10⁹ их произведение не влезает
в 64 бита (`(3·10⁹)² ≈ 9·10¹⁸` — у самой границы `int64`). На собеседовании оговори это:
для `m` до ~3·10⁹ на 64-битном `int` всё помещается (обычные `10⁹+7` — с запасом), для
больших — `math/big` либо 128-битное умножение через `math/bits.Mul64` + `bits.Div64`.
Именно поэтому `mod` берут **после каждого** умножения, а не в конце.

### Решето или пробное деление — что выбрать

- **Одно** число на простоту → пробное деление `O(√n)`, без памяти.
- **Много** запросов или «все простые до n» → решето `O(n log log n)`, но `O(n)` памяти.
  Для `n = 10⁸` это ~100 МБ булевого массива — иногда берут битовую упаковку или
  сегментное решето.

«Асимптотически лучше» снова не значит «всегда»: на одном числе решето проигрывает —
оно тратит память и время на весь диапазон ради одного ответа.

И честная граница обоих подходов: для **настоящих 64-битных** чисел не годится ни тот,
ни другой. `O(√n)` при `n ≈ 10¹⁸` — это ~10⁹ делений на один вызов, решето до 10¹⁸
не поместится ни в какую память. Промышленный ответ — вероятностный **тест
Миллера — Рабина**: `O(k · log³ n)` независимо от величины числа; именно он живёт в
`math/big.Int.ProbablyPrime`. Он подробно разобран (и реализуется тобой в тренажёре)
в следующей главе — [Криптография](cryptography.md), потому что стоит на быстром
возведении в степень, которое ты уже знаешь.

### Модуль вместо длинной арифметики

Если в задаче «ответ может быть очень большим, верните по модулю 1e9+7» — это **подсказка**:
считать надо по модулю на каждом шаге, а не вычислять гигантское число и потом брать
остаток. Так обходятся без `big.Int` и его аллокаций.

## ⚠️ Типичные ошибки

1. **НОК через `a*b/gcd` без деления первым** — `a*b` переполняется. Пиши `a/gcd*b`.
2. **`gcd` зациклился** — перепутаны `a` и `b` в `a, b = b, a%b`, либо забыт выход по `b == 0`.
3. **Пробное деление до `n`, а не до `√n`** — `O(n)` вместо `O(√n)`; условие `i*i <= n`.
4. **Решето с `2p` вместо `p*p`** — корректно, но делает лишнюю работу: все составные меньше `p*p` уже вычеркнуты меньшими простыми. И осторожно с самой проверкой `p*p <= n`: квадрат переполняется, если считать в 32-битном типе (`int32`/`uint32`); в Go `int` на 64-битных платформах спасает, но в переносимом коде надёжнее писать `p <= n/p`.
5. **Степень без `% m` после каждого умножения** — переполнение или гигантские числа.
6. **`isPrime` без отсечки `n < 2`** — `0` и `1` ошибочно считаются простыми.

> 🌍 **Где это в настоящем коде**
>
> - [`euclidUpdate`](https://github.com/golang/go/blob/go1.24.0/src/math/big/int.go#L734) (Go 1.24) — один шаг Евклида в `big.Int.GCD`: делим с остатком и сдвигаем пару, `A, B = B, A mod B`. Сам [`lehmerGCD`](https://github.com/golang/go/blob/go1.24.0/src/math/big/int.go#L758) — тот же Евклид, ускоренный для огромных чисел: несколько шагов подряд прикидывает по старшим разрядам.
> - [`bytealg.HashStr`](https://github.com/golang/go/blob/go1.24.0/src/internal/bytealg/bytealg.go#L32) (Go 1.24) — быстрое возведение в степень в поиске подстроки: множитель `PrimeRK` в степени длины образца считается циклом `if i&1 != 0 { pow *= sq }; sq *= sq; i >>= 1`. По модулю 2³² — его даёт само переполнение `uint32`.

## 📝 Разбор задачи: Count Primes

> **Задача** ([LeetCode 204](https://leetcode.com/problems/count-primes/)).
> Сколько простых чисел строго меньше `n`? Пример: `n = 10` → `4` (2, 3, 5, 7).

**Шаг 1. Наивно: каждое число проверить на простоту — O(n·√n).**

```go
func countPrimesNaive(n int) int {
    count := 0
    for i := 2; i < n; i++ {
        if isPrime(i) {
            count++
        }
    }
    return count
}
```

Работает, но для `n = 5·10⁶` это уже миллиарды операций — TLE. Мы перепроверяем делимость
каждого числа независимо, не используя то, что уже узнали.

**Шаг 2. Наблюдение.** Если вычёркивать кратные простых, каждое составное вычеркнется
своими простыми делителями — и проверять ничего не надо. Это решето.

**Шаг 3. Оптимум: решето — O(n log log n).**

```go
func countPrimes(n int) int {
    if n < 3 {
        return 0
    }
    composite := make([]bool, n)
    count := 0
    for p := 2; p < n; p++ {
        if composite[p] {
            continue
        }
        count++
        for m := p * p; m < n; m += p {
            composite[m] = true
        }
    }
    return count
}
```

Переход от «проверять каждое» к «вычёркивать кратные» — типичный для теории чисел сдвиг:
вместо `√n` работы на число получаем почти константу амортизированно.

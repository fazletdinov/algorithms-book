# 🧵 Параллельные алгоритмы: когда горутины помогают, а когда мешают

> 🧭 **Зачем эта глава.** Пять глав книги уже показали конкурентную версию своего алгоритма:
> [BFS](graphs.md), [перебор с возвратом](backtracking.md),
> [сортировка слиянием](k-way-merge.md), [подсчёт частот](top-k-elements.md),
> [поиск подстроки](string-algorithms.md). Каждая — про свой алгоритм. Эта глава ставит все
> пять на один стол и отвечает на вопрос, который в них разбросан по кусочкам: **когда
> горутины вообще окупаются**. Ответ неочевиден: из трёх замеров ниже один даёт ускорение
> в 5 раз, второй — всего вдвое на шести ядрах, а третий **замедляет работу в 75 раз**.
>
> Для Go-бэкендера это не академия. «Сделаем конкурентно» — первая мысль при виде медленного
> кода, и она неверна чаще, чем кажется.
>
> Все цифры сняты на i5-12400 (**6 физических ядер**, 12 потоков), Go 1.24. У тебя будут свои,
> но соотношения и форма кривых — те же. Каждую можно перепроверить командой из текста.

## 1. Три замера на одном столе

Пакеты тренажёра устроены одинаково: в каждом есть `...Seq` и `...Conc` — один алгоритм в
двух версиях. Значит, их можно честно сравнить:

```bash
cd exercises
go test -tags solution -run='^$' -bench=. -benchtime=3s ./parallelnqueens/ ./parallelsort/ ./parallelbfs/
```

| Задача | Последовательно | Конкурентно | Итог |
|---|---|---|---|
| N-Queens, `n = 12` ([backtracking](backtracking.md)) | 46.4 мс | 8.7 мс | **быстрее в 5.3 раза** |
| Merge sort, 2²⁰ элементов ([k-way merge](k-way-merge.md)) | 205 мс | 102 мс | быстрее в 2.0 раза |
| BFS, слоистый граф 20×60 ([графы](graphs.md)) | **0.13 мс** | **9.7 мс** | **медленнее в 75 раз** |

Три строки — три разных мира, хотя во всех трёх «работа распараллелена по независимым
кускам». Разница не в том, насколько удачно написан код: все три версии корректны и проходят
тесты под `-race`. Разница в **свойствах задачи**, и вся глава — про то, как эти свойства
распознавать до того, как писать горутины.

## 2. Закон Амдала, но измеренный

Интуиция «в 6 раз больше ядер — в 6 раз быстрее» ломается сразу. Прогоним ту же
конкурентную версию, меняя число доступных ядер:

```bash
for p in 1 2 4 6 8 12; do GOMAXPROCS=$p go test -tags solution -run='^$' \
  -bench=BenchmarkConc$ -benchtime=3s ./parallelnqueens/; done
```

| `GOMAXPROCS` | N-Queens | ускорение | Merge sort | ускорение |
|---|---|---|---|---|
| 1 | 45.7 мс | 1.00× | 180 мс | 1.00× |
| 2 | 24.5 мс | 1.87× | 101 мс | 1.78× |
| 4 | 13.9 мс | 3.29× | 60.0 мс | 3.00× |
| **6** | 10.0 мс | **4.57×** | 50.0 мс | **3.60×** |
| 8 | 9.26 мс | 4.94× | 50.5 мс | 3.56× |
| 12 | 9.00 мс | 5.08× | 50.8 мс | 3.54× |

Две вещи видно сразу.

**Кривая выполаживается на шести.** Не на двенадцати — на **шести**, ровно по числу
физических ядер. Дальше идут гиперпотоки, и для счётной задачи они почти ничего не дают:
у двух потоков одного ядра общие исполнительные блоки. `runtime.NumCPU()` вернёт 12, и это
честное число *логических* процессоров — но планировать выигрыш надо по физическим.
У merge sort после шести даже лёгкий регресс: потоков больше, работы не прибавилось,
зато прибавилось переключений.

**Потолок у задач разный.** Шесть ядер, идеал — 6×. N-Queens берёт 4.57×, merge sort —
только 3.60×. Это и есть **закон Амдала**: ускорение ограничено долей кода, которая обязана
исполняться последовательно. Если `P` — доля распараллеливаемой работы, а `N` — число ядер:

```text
S(N) = 1 / ((1 − P) + P/N)
```

Подставим измеренное. Для N-Queens `S(6) = 4.57` даёт `P ≈ 0.94`, для merge sort
`S(6) = 3.60` даёт `P ≈ 0.87`. Разница в семь процентных пунктов — и вот её цена:

| | доля параллельной работы | потолок при ∞ ядер (`1/(1−P)`) |
|---|---|---|
| N-Queens | ≈ 94% | ≈ 16× |
| Merge sort | ≈ 87% | ≈ 7.5× |

**Merge sort не ускорить больше чем в 7.5 раза никаким железом.** Причина прямо в
алгоритме: половины сортируются независимо, а **слияние — последовательно**, и слияние
верхнего уровня обрабатывает весь массив целиком в один поток. Этот последний merge и есть
те самые 13%.

Практический вывод, который дороже формулы: **сначала измерь долю последовательного кода,
потом решай, стоит ли добавлять ядра**. Купить вдвое больше процессоров, когда `P = 0.87`,
значит заплатить вдвое за плюс 8% скорости.

## 3. Гранулярность: на что заводить горутину

Теперь к BFS, который проиграл в 75 раз. Смотрим, как написана конкурентная версия:

```go
for _, u := range frontier {
    wg.Add(1)
    go func(u int) {            // ← горутина на ОДНУ вершину
        defer wg.Done()
        for _, v := range adj[u] {
            mu.Lock()           // ← и общий замок на КАЖДОЕ ребро
            if !visited[v] {
                visited[v] = true
                next = append(next, v)
            }
            mu.Unlock()
        }
    }(u)
}
```

Полезной работы на горутину — несколько сравнений. Накладных расходов — создание горутины,
планирование, и борьба за один мьютекс со всеми остальными. Мьютекс здесь хуже всего: он
**сериализует** именно ту часть, ради которой всё затевалось, и добавляет к ней стоимость
блокировки. Получается медленнее последовательной версии, которая просто идёт по массиву.

В том же пакете есть третья версия, `BFSLevelsConcLocal`: каждая горутина копит соседей
**в свой локальный буфер**, а общий срез собирается один раз после `wg.Wait()`.

| Версия | Время | Против последовательной |
|---|---|---|
| `BFSLevelsSeq` | 0.13 мс | — |
| `BFSLevelsConc` (общий мьютекс) | 9.7 мс | в 75 раз медленнее |
| `BFSLevelsConcLocal` (локальные буферы) | 1.20 мс | в 9 раз медленнее |

Убрали борьбу за замок — стало **в 8 раз быстрее**. И всё равно **в 9 раз медленнее
обычного цикла**. Вот это и есть главный урок главы: даже безупречно написанная
конкурентная версия не обязана выигрывать. Работы на вершину слишком мало — её не хватает,
чтобы окупить само существование горутины.

> 💡 **Правило гранулярности.** Горутину заводят не на единицу данных, а на **кусок работы,
> который стоит дороже, чем её создание**. Практически: не `go` на каждый элемент, а
> разбиение на `GOMAXPROCS` чанков — по горутине на ядро, и каждая обрабатывает свой
> диапазон. Именно так устроены выигрывающие `parallelsort` и `parallelnqueens`.

## 4. Что съедает выигрыш

Четыре статьи расходов, по убыванию частоты.

**Синхронизация.** Мьютекс вокруг горячего участка превращает параллельный код обратно в
последовательный, но уже с накладными расходами — см. BFS выше. Лечится не «более быстрым
замком», а **устранением разделяемого состояния**: локальные накопители и слияние в конце.

**Аллокации и GC.** Горутины аллоцируют параллельно, а сборщик мусора — общий ресурс.
Конкурентная версия, порождающая мусор, упирается в GC и перестаёт масштабироваться; в
профиле это видно как `runtime.gcBgMarkWorker` (как в
[приложении про профилирование](appendix-go-memory.md)). Отсюда `2.0×` вместо `3.6×` у
merge sort в первой таблице: бенчмарк сортирует с аллокацией новых срезов.

**Ложное разделение (false sharing).** Самая коварная: гонки нет, замков нет, код выглядит
идеально — а он медленный. Процессор работает с памятью не байтами, а **кэш-линиями по 64
байта**. Если счётчики разных горутин лежат в одной линии, запись одной горутины
инвалидирует линию у всех остальных ядер, и они перечитывают её из общего кэша. Проверить —
две минуты, вот полный бенчмарк:

```go
const iters = 2_000_000

// 8 счётчиков подряд = 64 байта = ровно одна кэш-линия на всех
func BenchmarkFalseSharing(b *testing.B) {
	for range b.N {
		var counters [8]int64
		var wg sync.WaitGroup
		for w := range 8 {
			wg.Add(1)
			go func(w int) {
				defer wg.Done()
				for i := 0; i < iters; i++ {
					counters[w]++
				}
			}(w)
		}
		wg.Wait()
	}
}

// то же самое, но каждый счётчик занимает свою линию
type padded struct {
	v int64
	_ [56]byte
}
```

```text
BenchmarkFalseSharing-12    11.6 мс
BenchmarkPadded-12           4.4 мс
```

**Разница в 2.6 раза** — при одинаковом коде, одинаковом числе горутин, без единой блокировки
и без гонок. Изменилась только раскладка в памяти. Это та же история, что
`map` против `[256]int` в [скользящем окне](sliding-window.md): Big-O одинаковый, платит
константа.

**Логические ядра ≠ физические.** Уже видели: после шести гиперпотоки не дают ничего.
`runtime.NumCPU()` говорит 12 — для счётной нагрузки планируй по шести.

## 5. Четыре схемы и когда какая

| Схема | Когда | Чем платишь |
|---|---|---|
| **Разбиение на чанки** (по горутине на ядро) | работы много, куски независимы, результат склеивается в конце | нужен способ поделить вход |
| **Worker pool** (`N` горутин читают из канала) | задачи разного размера, надо выровнять нагрузку | канал на каждую задачу — сам по себе синхронизация |
| **Fan-out / fan-in** | у каждой задачи свой результат, порядок не важен | сборка результатов и закрытие каналов |
| **Барьер по уровням** (`WaitGroup` на слой) | шаги зависят от предыдущих (BFS, волновые алгоритмы) | самый узкий слой определяет темп |

Для счётной работы по срезу почти всегда правильный ответ — **первая строка**, и только
она. Worker pool с каналом на элемент выглядит «по-гошному», но канал — это та же
синхронизация: на дешёвых задачах он повторит судьбу мьютекса из BFS.

**Отмена и ошибки.** Как только горутин больше одной, появляются два обязательных вопроса:
кто их остановит и куда денется ошибка. Ответ в стандартной библиотеке —
`golang.org/x/sync/errgroup`: он совмещает `WaitGroup`, передачу первой ошибки наверх и
отмену остальных через `context`.

```go
g, ctx := errgroup.WithContext(ctx)
for _, chunk := range chunks {
	g.Go(func() error {
		select {
		case <-ctx.Done():
			return ctx.Err() // соседняя горутина упала — выходим
		default:
		}
		return process(chunk)
	})
}
if err := g.Wait(); err != nil { // первая ошибка, остальные отменены
	return err
}
```

У каждой горутины должен быть **явный владелец и способ остановки**. Горутина, которую
некому остановить, — это утечка: она держит память и живёт до конца процесса.
Подробнее о том, как это исполняется рантаймом, — в [главе про GMP](go-runtime.md).

## 6. Чеклист: стоит ли параллелить

Пройди сверху вниз, не пропуская. Первое «нет» — значит не стоит.

1. **Есть замер?** Если нет — стоп. Параллелят не «медленный на вид» код, а измеренное
   узкое место (`-bench`, `pprof`).
2. **Куски независимы?** Если между ними нужна общая изменяемая память — оцени, сколько
   останется после сериализации доступа к ней.
3. **Работы на кусок хватает?** Сравни с ценой горутины и синхронизации. Несколько операций
   на элемент — не хватает.
4. **Какова доля последовательной части?** Посчитай потолок `1/(1−P)`. Потолок 2× за
   удвоение сложности кода — плохая сделка.
5. **Померил после?** Конкурентная версия обязана побить последовательную **на реальных
   данных**, а не на удобных. И обязана быть зелёной под `-race`.

> 🧭 Инженерный итог всей главы: «сделать конкурентно» — это не оптимизация, а **размен**.
> Ты платишь сложностью кода, риском гонок и накладными расходами, а получаешь ускорение,
> потолок которого задан алгоритмом, а не железом. Иногда размен выгоден в 5 раз, иногда
> убыточен в 75. Отличить можно только замером — и это ровно та же привычка, что в
> [профилировании](appendix-go-memory.md) и в [планах Postgres](postgres-plans.md).

## ⚠️ Типичные ошибки

1. **Горутина на элемент.** Самая частая. Цена запуска и синхронизации превышает работу —
   см. BFS, проигрыш в 75 раз.
2. **Мьютекс вокруг всей полезной работы.** Код параллельный только по виду: критическая
   секция исполняется строго по одному.
3. **Захват переменной цикла в старых версиях Go.** До Go 1.22 `for _, v := range xs { go f(v) }`
   с использованием `v` внутри замыкания давал всем горутинам последнее значение. С 1.22
   переменная своя на каждой итерации, но код из старых статей всё ещё попадается.
4. **`WaitGroup.Add` внутри горутины.** `Add` должен выполниться **до** `go`, иначе
   `Wait` может пройти раньше, чем горутина стартовала.
5. **Ошибка, потерянная в горутине.** Без `errgroup` или канала ошибок она просто исчезает,
   и сбой выглядит как «иногда неверный ответ».
6. **Вывод «работает» после одного прогона без `-race`.** Гонка проявляется не каждый раз —
   именно поэтому детектор запускают всегда, а не когда что-то сломалось.

## 💻 Практика: перепроверь эти замеры сам

Главное упражнение этой главы — не написать код, а **воспроизвести измерения** и получить
свои числа. Порядок:

```bash
cd exercises
# 1. три задачи на одном столе — где выигрыш, где проигрыш
go test -tags solution -run='^$' -bench=. -benchtime=3s ./parallelnqueens/ ./parallelsort/ ./parallelbfs/
# 2. кривая масштабирования: найди, на скольких ядрах она выполаживается у тебя
for p in 1 2 4 6 8 12; do GOMAXPROCS=$p go test -tags solution -run='^$' \
  -bench=BenchmarkConc$ -benchtime=3s ./parallelsort/; done
# 3. профиль конкурентной версии: на что уходит время на самом деле
go test -tags solution -run='^$' -bench=BenchmarkConc$ -cpuprofile=cpu.prof ./parallelbfs/
go tool pprof -top -cum cpu.prof
```

Посчитай по своим числам `P` и потолок `1/(1−P)` для обеих задач. Если кривая выполаживается
не на шести — посмотри `lscpu` и сверь с числом физических ядер.

Сами реализации живут в главах, которым принадлежат алгоритмы: конкурентный
[BFS](graphs.md), [перебор](backtracking.md), [сортировка](k-way-merge.md),
[подсчёт частот](top-k-elements.md), [поиск подстроки](string-algorithms.md). Там же —
виджеты «Реши прямо здесь»; `parallelbfs` и `parallelnqueens` гоняются с `-race`.

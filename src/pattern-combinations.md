## 1. LRU Cache — хеш-таблица + двусвязный список

> **Задача.** Спроектируй кэш на `capacity` элементов с операциями `Get(key)` и
> `Put(key, value)` **за O(1)**. При переполнении вытесняется *давно не используемый*
> (least recently used) элемент. Любое обращение делает элемент «свежим».

**Как я пришёл — 4 шага.**

1. **Что конфликтует.** `Get` ищет элемент по ключу, а вытеснение — по давности обращения. Это
   два разных порядка, и оба нужны за O(1).
2. **Первый приём и его дыра.** [Хеш-таблица](hash-table-structure.md) находит ключ за O(1), но не
   помнит, кого трогали последним: чтобы найти самый старый, пришлось бы пройти всю map — O(n).
3. **Чем закрыть дыру.** Порядок свежести держит [двусвязный список](linked-list-structure.md):
   подвинуть узел в голову и снять хвост — перецепка указателей, O(1) (в массиве сдвиг стоил бы
   O(n)). Сам список узел по ключу не найдёт — это O(n), но это уже умеет map.
4. **Как стыкуются.** Map хранит `key → *узел списка`, список — порядок. `Get`/`Put`: map находит
   узел, список двигает его в голову. Вытеснение идёт с другой стороны: список отдаёт `tail.prev`,
   а `key` внутри узла говорит, что удалить из map. Map даёт «где элемент», список — «насколько он
   свежий».

```go
type Node struct {
    key, val   int
    prev, next *Node
}

type LRUCache struct {
    cap        int
    m          map[int]*Node
    head, tail *Node // фиктивные границы: head.next — самый свежий, tail.prev — самый старый
}

func Constructor(capacity int) LRUCache {
    head, tail := &Node{}, &Node{}
    head.next, tail.prev = tail, head
    return LRUCache{cap: capacity, m: make(map[int]*Node), head: head, tail: tail}
}

func (c *LRUCache) remove(n *Node) { n.prev.next, n.next.prev = n.next, n.prev }

func (c *LRUCache) addFront(n *Node) {
    n.prev, n.next = c.head, c.head.next
    c.head.next.prev = n
    c.head.next = n
}

func (c *LRUCache) Get(key int) int {
    n, ok := c.m[key]
    if !ok {
        return -1
    }
    c.remove(n)
    c.addFront(n) // обращение делает узел свежим
    return n.val
}

func (c *LRUCache) Put(key, value int) {
    if n, ok := c.m[key]; ok {
        n.val = value
        c.remove(n)
        c.addFront(n)
        return
    }
    if len(c.m) == c.cap {
        lru := c.tail.prev // самый старый — перед хвостом
        c.remove(lru)
        delete(c.m, lru.key)
    }
    n := &Node{key: key, val: value}
    c.m[key] = n
    c.addFront(n)
}
```

Прошагай последовательность операций (ёмкость 2): `map` даёт O(1) доступ, а
список держит порядок свежести — видно, как обращение двигает узел в голову, а
переполнение вытесняет хвост (старый конец):

<div class="algo-viz" data-viz="lru" data-cap="2" data-ops="put 1 1; put 2 2; get 1; put 3 3; get 2; put 4 4; get 1; get 3; get 4"></div>

> ⚠️ Узел хранит **и `key`, и `val`**. `val` нужен для `Get`, а `key` — чтобы при
> вытеснении `tail.prev` знать, *что удалить из map*. Без `key` в узле вытеснение
> деградирует до O(n) поиска по map.

**Трассировка** (`capacity = 2`). Список показан от свежего к старому:

| операция     | map        | список (свежий→старый) | результат |
|--------------|------------|------------------------|-----------|
| `Put(1,1)`   | {1}        | `1`                    |           |
| `Put(2,2)`   | {1,2}      | `2 1`                  |           |
| `Get(1)`     | {1,2}      | `1 2`                  | `1` (1 стал свежим) |
| `Put(3,3)`   | {1,3}      | `3 1`                  | вытеснен `2` (был старейшим) |
| `Get(2)`     | {1,3}      | `3 1`                  | `-1` |

Ключевой момент — `Get(1)` переставил `1` вперёд, поэтому при `Put(3,3)` вылетел
именно `2`, а не `1`.

### 💻 Что реально в проде: LRU + TTL

Обычный LRU по ёмкости — половина дела. Реальный кэш почти всегда добавляет **TTL** (время жизни): запись
протухает через заданный срок, даже если место есть. Это «sweet spot» продовых кэшей — так устроены
[`hashicorp/golang-lru`](https://github.com/hashicorp/golang-lru) (expirable-вариант),
[`ccache`](https://github.com/karlseguin/ccache). Собери его сам в пакете `cache` — тот же LRU, но у записи
есть `expireAt`, а `Get` протухшую считает промахом (и удаляет лениво):

```go
func NewTTLCache(capacity int, ttlMs int64) *TTLCache
func (c *TTLCache) Put(key, value int, nowMs int64)
func (c *TTLCache) Get(key int, nowMs int64) (int, bool) // промах, если ключа нет ИЛИ он протух
```

<div class="algo-runner" data-pkg="cache" data-flagship="true"></div>

**Тренажёр** — пакет `cache` (`go test -tags solution ./cache/` — эталон, если застрял).

А вот что стоит знать про кэши на масштабе — это и отличает инженера:

- **Redis не держит точный LRU.** Точный LRU требует держать указатели/порядок на **каждый** ключ — дорого
  по памяти. Поэтому Redis использует **приближённый LRU**: при вытеснении сэмплит несколько случайных
  ключей и выкидывает старейший из выборки. Дешевле ценой лёгкой неточности — тот же размен «точность ↔
  ресурсы», что и у [вероятностных структур](probabilistic-structures.md).
- **Cache stampede.** Когда протухает **популярный** ключ, сотни горутин разом промахиваются и все бегут в
  БД за одним и тем же значением — база складывается. Лечится дедупликацией: `golang.org/x/sync/singleflight`
  пропускает к загрузке ровно **одну** горутину, остальные ждут её результат (привет [конкурентности](graphs.md#-конкурентный-bfs-go)).
- **Многоуровневость.** Локальный LRU перед Redis: локальный TTL держат коротким (10–30с), Redis — длиннее
  (минуты). Локальный кэш снимает нагрузку, Redis остаётся источником истины.

Мораль инженера: LRU из хеша и списка — это **скелет**; продовый кэш живёт на **TTL, приближённом
вытеснении и защите от stampede**. Ты собрал скелет — и знаешь, что на него навешивают в бою.

## 2. Word Ladder — BFS + хеш-множество

> **Задача.** Дано `beginWord`, `endWord` и словарь. За один шаг можно изменить **одну
> букву**, и полученное слово должно быть в словаре. Верни длину кратчайшей цепочки
> превращений (число слов в ней) или 0, если её нет.
> Пример: `hit → hot → dot → dog → cog` = 5.

**Как я пришёл — 4 шага.**

1. **Что конфликтует.** Нужна кратчайшая цепочка — это вопрос о порядке обхода. Но графа нет:
   соседей слова приходится искать в словаре, и искать быстро.
2. **Первый приём и его дыра.** «Кратчайшая цепочка, где каждый шаг стоит 1» — буквально
   определение [BFS](graphs.md): слова — вершины, ребро — «отличаются одной буквой». BFS идёт
   волной по слоям, но ему нужны готовые соседи и пометка «уже был». Построить граф заранее —
   сравнить все пары слов, O(N²).
3. **Чем закрыть дыру.** [Хеш-множество](hash-table-structure.md) словаря. Для слова длины `L`
   перебираем `L·25` кандидатов (одна буква заменена) и проверяем каждого за O(L) — столько стоит
   хеш строки длины `L`. Рёбра рождаются на лету.
4. **Как стыкуются.** BFS снимает слово из очереди, порождает кандидатов и спрашивает множество.
   Найденного кандидата **удаляем из словаря** и ставим в очередь: удаление и есть пометка
   «посещён», отдельный `visited` не нужен. Одна структура служит и рёбрами, и посещённостью.

```go
func ladderLength(beginWord, endWord string, wordList []string) int {
    dict := make(map[string]bool, len(wordList))
    for _, w := range wordList {
        dict[w] = true
    }
    if !dict[endWord] {
        return 0
    }
    queue := []string{beginWord}
    steps := 1
    for len(queue) > 0 {
        next := []string{}
        for _, w := range queue {
            if w == endWord {
                return steps
            }
            b := []byte(w)
            for i := 0; i < len(b); i++ {
                orig := b[i]
                for ch := byte('a'); ch <= 'z'; ch++ {
                    b[i] = ch
                    if cand := string(b); dict[cand] {
                        delete(dict, cand) // помечаем посещённым, удаляя из словаря
                        next = append(next, cand)
                    }
                }
                b[i] = orig
            }
        }
        queue = next
        steps++ // перешли на следующий уровень = +1 слово в цепочке
    }
    return 0
}
```

Обход по уровням (вершины: `0=hit, 1=hot, 2=dot, 3=dog, 4=lot, 5=log, 6=cog`): BFS
расходится волной от `hit`, и `cog` достигается за 5 слоёв — это и есть длина цепочки.

<div class="algo-viz" data-viz="graph-bfs" data-nodes="0,1,2,3,4,5,6" data-edges="0-1,1-2,1-4,2-3,2-4,4-5,3-5,3-6,5-6" data-start="0"></div>

> ⚠️ Удалять кандидата из словаря нужно **сразу при добавлении в очередь**, а не при
> извлечении. Иначе одно слово попадёт в очередь несколько раз с разных вершин одного
> слоя — и сложность взорвётся.

## 3. Alien Dictionary — граф из строк + топологическая сортировка

> **Задача.** Дан список слов, отсортированный по правилам **неизвестного** алфавита.
> Восстанови порядок букв. Пример: `["wrt","wrf","er","ett","rftt"]` → `"wertf"`.

**Как я пришёл — 4 шага.**

1. **Что конфликтует.** Просят порядок при зависимостях («какая буква раньше»), а дан не граф
   зависимостей, а список слов.
2. **Первый приём и его дыра.** Порядок по зависимостям — [топологическая
   сортировка](topological-sort.md): «буква A раньше буквы B» — ребро A→B, а цикл значит
   «порядка нет». Но рёбер во входе нет, сортировать нечего.
3. **Чем закрыть дыру.** Граф **строим из соседних слов**: первая позиция, где два соседних слова
   различаются, даёт ровно одно ребро. Длинное слово перед своим же префиксом (`"abc"` перед
   `"ab"`) — противоречие сразу. Рёбра лежат в map «буква → множество следующих», входящие степени
   — в map «буква → число».
4. **Как стыкуются.** Сначала целиком строим `adj` и `indeg`, потом по ним идёт Кан. Общие данные
   — эти две map. Если Кан выдал меньше букв, чем есть в графе, остался цикл — словарь
   противоречив, ответ пустой.

```go
func alienOrder(words []string) string {
    adj := make(map[byte]map[byte]bool)
    indeg := make(map[byte]int)
    for _, w := range words { // все буквы попадают в граф, даже изолированные
        for i := 0; i < len(w); i++ {
            if adj[w[i]] == nil {
                adj[w[i]] = make(map[byte]bool)
            }
            if _, ok := indeg[w[i]]; !ok {
                indeg[w[i]] = 0
            }
        }
    }
    for i := 0; i+1 < len(words); i++ {
        a, b := words[i], words[i+1]
        if len(a) > len(b) && a[:len(b)] == b {
            return "" // "abc" перед "ab" — невозможный словарь
        }
        for j := 0; j < len(a) && j < len(b); j++ {
            if a[j] != b[j] {
                if !adj[a[j]][b[j]] {
                    adj[a[j]][b[j]] = true
                    indeg[b[j]]++ // нашли первое различие — одно ребро, дальше выходим
                }
                break
            }
        }
    }
    // Kahn: буквы с нулевой входящей степенью идут первыми
    queue := []byte{}
    for ch, d := range indeg {
        if d == 0 {
            queue = append(queue, ch)
        }
    }
    res := []byte{}
    for len(queue) > 0 {
        ch := queue[0]
        queue = queue[1:]
        res = append(res, ch)
        for nb := range adj[ch] {
            if indeg[nb]--; indeg[nb] == 0 {
                queue = append(queue, nb)
            }
        }
    }
    if len(res) != len(indeg) {
        return "" // остались буквы со входящими рёбрами = цикл = противоречие
    }
    return string(res)
}
```

Топологический разбор графа из примера (рёбра `t→f`, `w→e`, `r→t`, `e→r`): Kahn снимает
буквы с нулевой входящей степенью слой за слоем — это и даёт алфавит:

<div class="algo-viz" data-viz="topo-kahn" data-nodes="w,e,r,t,f" data-edges="t-f,w-e,r-t,e-r"></div>

> ⚠️ Два подводных камня: (1) **префиксный конфликт** `["abc","ab"]` — невозможный
> словарь, не пропусти проверку; (2) порядок обхода `map` в Go **недетерминирован** —
> при нескольких валидных алфавитах ответ может отличаться от запуска к запуску. Если
> нужен стабильный/лексикографически минимальный — замени очередь на

## 4. Serialize / Deserialize Binary Tree — DFS + парсинг

> **Задача.** Преврати произвольное бинарное дерево в строку и восстанови его обратно.
> `serialize(deserialize(s))` должно давать ту же строку.

**Как я пришёл — 4 шага.**

1. **Что конфликтует.** Дерево ветвится (у узла два ребёнка), а строка — одна линия. Надо уложить
   форму дерева в линию так, чтобы её можно было однозначно развернуть обратно.
2. **Первый приём и его дыра.** [DFS-обход](tree-dfs.md) в прямом порядке (корень → лево → право)
   укладывает узлы в линию. Но одной последовательности значений мало: в `1 2` двойка может быть и
   левым, и правым ребёнком.
3. **Чем закрыть дыру.** Пишем **явный маркер пустоты** `#` на месте каждого отсутствующего
   ребёнка, а при чтении разбиваем строку на токены (парсинг) и ведём по ним курсор `i`.
4. **Как стыкуются.** Десериализация — тот же DFS в том же порядке, только он не читает дерево, а
   потребляет токены: `#` → `nil`, число → узел, затем рекурсия влево и вправо. Общее у двух
   половин — порядок обхода: разойдётся порядок — разъедутся токены.

```go
type TreeNode struct {
    Val         int
    Left, Right *TreeNode
}

func serialize(root *TreeNode) string {
    var sb strings.Builder
    var dfs func(*TreeNode)
    dfs = func(n *TreeNode) {
        if n == nil {
            sb.WriteString("# ") // явный маркер пустоты — ключ к восстановлению формы
            return
        }
        sb.WriteString(strconv.Itoa(n.Val))
        sb.WriteByte(' ')
        dfs(n.Left)
        dfs(n.Right)
    }
    dfs(root)
    return sb.String()
}

func deserialize(data string) *TreeNode {
    tokens := strings.Fields(data)
    i := 0
    var build func() *TreeNode
    build = func() *TreeNode {
        tok := tokens[i]
        i++
        if tok == "#" {
            return nil
        }
        val, _ := strconv.Atoi(tok)
        n := &TreeNode{Val: val}
        n.Left = build()  // тот же порядок: сначала левое поддерево...
        n.Right = build() // ...затем правое — токены идут ровно как при serialize
        return n
    }
    return build()
}
```

## 5. Meeting Rooms II — сортировка + мин-куча

> **Задача.** Дан список интервалов встреч `[начало, конец]`. Сколько минимум нужно
> переговорок, чтобы ни одна встреча не пересеклась во времени? Пример:
> `[[0,30],[5,10],[15,20]]` → `2`.

**Как я пришёл — 4 шага.**

1. **Что конфликтует.** Встречи надо рассматривать по времени, как в календаре, и в каждый момент
   знать, какая из занятых комнат освободится раньше всех. Порядок обработки и меняющийся набор, из
   которого нужен минимум.
2. **Первый приём и его дыра.** [Сортировка](sorting.md) по началу задаёт порядок: встречи
   приходят одна за другой. Но о занятых комнатах она ничего не знает: искать свободную перебором —
   O(n) на встречу, O(n²) всего.
3. **Чем закрыть дыру.** [Мин-куча](heap-structure.md) времён окончания занятых комнат: самый ранний
   конец — на вершине, посмотреть его — O(1), снять или добавить — O(log n).
4. **Как стыкуются.** Проход по отсортированным встречам; у каждой сравниваем вершину кучи с её
   началом: конец ≤ начала — `Pop` (комната освободилась), затем `Push` своего конца. За шаг куча
   растёт на 1 или не меняется, поэтому её размер в конце и есть пик. Сортировка задаёт *порядок
   обработки*, куча хранит *активное состояние*.

```go
func minMeetingRooms(intervals [][]int) int {
    if len(intervals) == 0 {
        return 0
    }
    sort.Slice(intervals, func(i, j int) bool {
        return intervals[i][0] < intervals[j][0] // по времени начала
    })
    h := &minHeap{} // в куче — времена окончания занятых комнат
    heap.Init(h)
    for _, iv := range intervals {
        if h.Len() > 0 && (*h)[0] <= iv[0] {
            heap.Pop(h) // самая ранняя встреча кончилась к началу текущей — переиспользуем комнату
        }
        heap.Push(h, iv[1])
    }
    return h.Len() // сколько комнат заняты одновременно в пике
}

type minHeap []int

func (h minHeap) Len() int            { return len(h) }
func (h minHeap) Less(i, j int) bool  { return h[i] < h[j] }
func (h minHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *minHeap) Push(x any)         { *h = append(*h, x.(int)) }
func (h *minHeap) Pop() any {
    old := *h
    n := len(old)
    x := old[n-1]
    *h = old[:n-1]
    return x
}
```

## 6. Design Twitter — хеш-таблица + K-way merge

> **Задача.** Спроектируй ленту: `PostTweet`, `Follow`, `Unfollow` и `GetNewsFeed(user)`
> — 10 самых свежих твитов самого пользователя и тех, на кого он подписан.

**Как я пришёл — 4 шага.**

1. **Что конфликтует.** Подписки и твиты меняются по одному, и нужен быстрый доступ по
   пользователю. А лента — 10 самых свежих твитов сразу из многих чужих лент.
2. **Первый приём и его дыра.** [Хеш-таблицы](hash-table-structure.md) `user → []твит` и
   `user → множество подписок` делают `PostTweet`/`Follow`/`Unfollow` за O(1). Но «10 свежих из
   всех подписок» map не знает: собрать все твиты и отсортировать — O(T log T), где T — число всех
   твитов подписок.
3. **Чем закрыть дыру.** Лента каждого автора **уже отсортирована** по времени (твит дописывается в
   конец). Слить k отсортированных списков — [K-way merge](k-way-merge.md): куча из «голов» списков
   отдаёт самый свежий за O(log k).
4. **Как стыкуются.** `GetNewsFeed` берёт из map подписки, для каждого автора кладёт в кучу курсор
   на его последний твит и 10 раз снимает вершину, подтягивая следующий твит того же автора. Итого
   O((k + 10)·log k) на ленту, а не O(T log T). Хеши дают *откуда брать потоки*, K-way merge — *как их
   слить по свежести*.

```go
type tweet struct{ time, id int }

type Twitter struct {
    clock   int
    tweets  map[int][]tweet      // user -> его твиты, по возрастанию времени
    follows map[int]map[int]bool // user -> на кого подписан
}

func Constructor() Twitter {
    return Twitter{tweets: map[int][]tweet{}, follows: map[int]map[int]bool{}}
}

func (t *Twitter) PostTweet(userId, tweetId int) {
    t.clock++
    t.tweets[userId] = append(t.tweets[userId], tweet{t.clock, tweetId})
}

func (t *Twitter) Follow(a, b int) {
    if t.follows[a] == nil {
        t.follows[a] = map[int]bool{}
    }
    t.follows[a][b] = true
}

func (t *Twitter) Unfollow(a, b int) { delete(t.follows[a], b) }

func (t *Twitter) GetNewsFeed(userId int) []int {
    users := []int{userId}
    for u := range t.follows[userId] {
        if u != userId {
            users = append(users, u)
        }
    }
    h := &feed{} // max-heap по времени: на вершине самый свежий твит среди голов
    for _, u := range users {
        if lst := t.tweets[u]; len(lst) > 0 {
            heap.Push(h, cursor{u, len(lst) - 1, lst[len(lst)-1]})
        }
    }
    res := []int{}
    for h.Len() > 0 && len(res) < 10 {
        c := heap.Pop(h).(cursor)
        res = append(res, c.tw.id)
        if c.i > 0 { // подтягиваем следующий по свежести твит того же автора
            lst := t.tweets[c.u]
            heap.Push(h, cursor{c.u, c.i - 1, lst[c.i-1]})
        }
    }
    return res
}

type cursor struct {
    u, i int
    tw   tweet
}
type feed []cursor

func (h feed) Len() int            { return len(h) }
func (h feed) Less(i, j int) bool  { return h[i].tw.time > h[j].tw.time } // max по времени
func (h feed) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *feed) Push(x any)         { *h = append(*h, x.(cursor)) }
func (h *feed) Pop() any {
    old := *h
    n := len(old)
    x := old[n-1]
    *h = old[:n-1]
    return x
}
```

K-way merge: в куче всегда «головы» всех потоков, мы снимаем самую свежую и подтягиваем
следующую из того же потока — пока не наберём 10. Виджет ниже показывает общий вариант слияния
K отсортированных списков — по возрастанию, через min-кучу; лента — то же самое зеркально:
max-куча по времени, первой снимается самая свежая голова:

## 7. The Skyline Problem — sweep line + макс-куча (капстоун)

> **Задача.** Здания заданы как `[left, right, height]`. Верни силуэт города — список
> «ключевых точек» `[x, height]`, где высота крыши меняется. Это самая известная задача
> «на связку» и хороший финальный тест на распознавание.

**Как я пришёл — 4 шага.**

1. **Что конфликтует.** Силуэт меняется только на краях зданий — точки идут по порядку координаты.
   А высота в точке — максимум среди зданий, которые её накрывают, и этот набор всё время
   меняется.
2. **Первый приём и его дыра.** **Sweep line** («заметающая прямая»): края зданий превращаем в
   события «вход»/«выход», сортируем по x и проходим слева направо. Но на каждом событии нужен
   максимум активных высот: перебирать активные здания — O(n) на событие, O(n²) всего.
3. **Чем закрыть дыру.** [Макс-куча](heap-structure.md) активных высот: максимум — на вершине.
   Вынуть высоту из середины `container/heap` не умеет, поэтому удаляем лениво: map `toRemove`
   помнит ушедшие высоты, и высота снимается, только когда всплывёт на вершину.
4. **Как стыкуются.** Проход по событиям: вход — `Push`, выход — `toRemove++`, затем чистим вершину
   от мёртвых; вершина отличается от прошлой высоты — новая точка силуэта. Порядок событий при
   равном x (входы раньше выходов) — тоже часть стыка. Sweep задаёт *где смотреть*, куча отвечает
   *какая сейчас высота*.

```go
func getSkyline(buildings [][]int) [][]int {
    type ev struct{ x, h int } // h<0 — вход здания (левый край), h>0 — выход (правый)
    var events []ev
    for _, b := range buildings {
        events = append(events, ev{b[0], -b[2]}, ev{b[1], b[2]})
    }
    sort.Slice(events, func(i, j int) bool {
        if events[i].x != events[j].x {
            return events[i].x < events[j].x
        }
        return events[i].h < events[j].h // при равном x: входы (отриц.) раньше выходов
    })

    h := &maxHeap{0} // 0 — уровень земли, всегда в куче
    toRemove := map[int]int{}
    prev := 0
    var res [][]int
    for _, e := range events {
        if e.h < 0 {
            heap.Push(h, -e.h) // здание началось — высота активна
        } else {
            toRemove[e.h]++ // здание кончилось — пометим к ленивому удалению
        }
        for h.Len() > 0 && toRemove[(*h)[0]] > 0 { // чистим вершину от «удалённых»
            toRemove[(*h)[0]]--
            heap.Pop(h)
        }
        if cur := (*h)[0]; cur != prev { // силуэт изменился — фиксируем точку
            res = append(res, []int{e.x, cur})
            prev = cur
        }
    }
    return res
}

type maxHeap []int

func (h maxHeap) Len() int            { return len(h) }
func (h maxHeap) Less(i, j int) bool  { return h[i] > h[j] }
func (h maxHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *maxHeap) Push(x any)         { *h = append(*h, x.(int)) }
func (h *maxHeap) Pop() any {
    old := *h
    n := len(old)
    x := old[n-1]
    *h = old[:n-1]
    return x
}
```

**Трассировка** для `buildings = [[2,9,10],[3,7,15],[5,12,12]]`. Куча активных высот, на
вершине — текущая высота силуэта:

| событие | x | действие | куча активных | вершина | точка силуэта |
|---------|---|----------|---------------|---------|---------------|
| вход 10 | 2 | push 10  | {10,0}        | 10      | `[2,10]`      |
| вход 15 | 3 | push 15  | {15,10,0}     | 15      | `[3,15]`      |
| вход 12 | 5 | push 12  | {15,12,10,0}  | 15      | — (без изменений) |
| выход 15| 7 | удалить 15 | {12,10,0}   | 12      | `[7,12]`      |
| выход 10| 9 | удалить 10 | {12,0}      | 12      | — |
| выход 12| 12| удалить 12 | {0}         | 0       | `[12,0]`      |

Итог: `[[2,10],[3,15],[7,12],[12,0]]`. Заметь — на `x=5` и `x=9` вершина кучи не
поменялась, поэтому точек там нет: силуэт фиксируется только при смене максимума.

> ⚠️ Удалять из произвольного места `container/heap` напрямую не умеет — отсюда **ленивое
> удаление**: помечаем высоту в `toRemove` и снимаем её, лишь когда она всплывёт на
> вершину. Это типовой приём «куча + отложенное удаление», он же встречается в
> [Dijkstra](advanced-graph-algorithms.md).

## 🧠 Как это переносится на любую задачу

Во всех семи разборах работали одни и те же четыре шага «Как я пришёл»:

1. **Что конфликтует?** Найди в условии два требования, которые один приём не тянет разом:
   «по ключу» и «по свежести», «по времени» и «текущий минимум», «кратчайший путь» и «граф не дан».
   Каждое требование — формулировка-триггер своего паттерна.
2. **Что умеет первый приём и где его дыра?** Возьми приём под главное требование и честно
   назови, во что упирается второе: «тут пришлось бы перебрать всё — O(n)».
3. **Что закрывает дыру?** Хеш — для O(1) доступа, куча — для «текущего экстремума», сортировка —
   для «порядка обработки». Часто недостающее — сама структура: граф или потоки приходится
   **построить из входных данных** (рёбра из соседних слов, потоки из твитов автора).
4. **Как стыкуются?** Назови, кто кого вызывает и какие данные у них общие (`key → *узел`,
   словарь как visited, `adj`/`indeg`). Это общее и есть инвариант, который надо держать в каждом
   методе.

Если на собеседовании задача «не похожа ни на что» — почти наверняка это **связка двух
знакомых**. Ищи, какой паттерн даёт *структуру*, а какой — *порядок обработки*.

## ⚙️ Цена на практике: чем платят связки

У комбинированной структуры цена — не сумма цен частей, а сумма **плюс хрупкость инварианта между ними**.

- **LRU (map + список)**: обе части обязаны меняться **согласованно** — обновил map, забыл
  перецепить узел списка — и кэш молча отдаёт протухшую «свежесть». В конкурентном коде это
  означает **один мьютекс вокруг обеих структур** (нельзя лочить по отдельности — рассинхрон);
  прод-версию с TTL ты собираешь во флагмане `cache` (см. [главу про LRU выше](#1-lru-cache--хеш-таблица--двусвязный-список)).
- **Skyline / Meeting Rooms (сортировка + куча)**: куча с «ленивым удалением» платит памятью —
  мёртвые элементы живут в куче, пока не всплывут. На длинных потоках это надо чистить, иначе
  `O(n)` памяти превращается в «сколько накапало».
- **Design Twitter (map + k-way merge)**: слияние k лент дешево, пока k мало; при тысячах подписок
  куча слияния сама становится горячей точкой — реальные ленты предвычисляют (fan-out on write).

Мораль: связка добавляет **инвариант-мостик** между структурами. Прежде чем комбинировать, назови
его вслух («порядок списка = порядок свежести map») — и охраняй в каждом методе.

> 🌍 **Где это в настоящем коде**
>
> - [`simplelru.LRU`](https://github.com/hashicorp/golang-lru/blob/v2.0.7/simplelru/lru.go#L16) (`hashicorp/golang-lru` 2.0.7) — ровно связка из разбора 1: `map` от ключа к узлу плюс двусвязный список; [`Add`](https://github.com/hashicorp/golang-lru/blob/v2.0.7/simplelru/lru.go#L50) двигает узел в начало и выкидывает самый старый, когда места нет.
> - [`initOrder`](https://github.com/golang/go/blob/go1.24.0/src/go/types/initorder.go#L20) (Go 1.24) — граф + топологическая сортировка + куча: проверка типов строит граф зависимостей переменных пакета и достаёт из кучи вершину без оставшихся зависимостей; так выбирается порядок инициализации.

## 🧪 Незнакомые условия: собери связку сам

Семь разборов выше — задачи, которые ты теперь узнаешь в лицо. Ниже десять условий, которых в книге
нет. Для каждого сначала пройди четыре шага сам, на бумаге: что конфликтует → первый приём и его
дыра → что закрывает дыру → как стыкуются. Только потом раскрывай ответ. Все приёмы — из глав книги;
новых нет.

**1. Конфиг на момент времени.** Сервис настроек: `Set(key, value, ts)` записывает значение ключа
с отметкой времени `ts`, `Get(key, ts)` возвращает значение, действовавшее в момент `ts`, — то, что
записано последним с отметкой ≤ `ts`, или `""`, если такого нет. У одного ключа отметки приходят
строго по возрастанию. *Ограничения:* до 2·10⁵ вызовов, `ts` до 10⁷.

<details class="algo-details">
<summary>Связка</summary>

**Хеш-таблица + бинарный поиск.**

1. **Конфликт:** ключ ищется точно, а время — нет: нужна не отметка `ts`, а ближайшая слева от неё.
2. **Первый приём:** [хеш-таблица](hash-table-structure.md) `key → история записей` находит ключ за
   O(1). Но в истории искать «последнюю ≤ ts» перебором — O(m), где m — длина истории.
3. **Добор:** история уже отсортирована — отметки растут, запись дописывается в конец. Значит,
   [бинарный поиск](modified-binary-search.md) границы: первая отметка `> ts`, ответ — элемент перед
   ней.
4. **Стык:** `map[string][]entry{ts, value}`. `Set` — `append` в срез ключа; `Get` — map отдаёт
   срез, `sort.Search` находит первую отметку больше `ts`, берём индекс на 1 меньше (если он −1 —
   `""`).

*Сложность:* `Set` — O(1) (амортизированно, из-за `append`), `Get` — O(log m), память O(n).

</details>

**2. Биржевой тикер с исправлениями.** Приходит поток записей `(время, цена)`. Запись с уже
встречавшимся временем **исправляет** прежнюю цену в этот момент. В любой момент спрашивают: текущую
цену (у самого позднего времени), а также максимум и минимум среди всех актуальных цен.
*Ограничения:* до 10⁵ операций всего.

<details class="algo-details">
<summary>Связка</summary>

**Хеш-таблица + две кучи с ленивым удалением.**

1. **Конфликт:** цену исправляют по времени (доступ по ключу), а максимум и минимум считаются по
   ценам, которые меняются задним числом.
2. **Первый приём:** map `время → цена` делает исправление за O(1), текущую цену даёт запомненное
   самое позднее время. Но максимум по map — проход по всем записям, O(n) на запрос.
3. **Добор:** [макс-куча и мин-куча](heap-structure.md) пар `(цена, время)` — экстремум на вершине.
   Старую цену из середины кучи не вынуть — значит, удаление ленивое, как в Skyline выше.
4. **Стык:** исправление пишет в map и кладёт новую пару в обе кучи. Запрос максимума: пока у
   вершины `(p, t)` цена не совпадает с `map[t]` — пара мёртвая, `Pop`; первая живая вершина и есть
   ответ. Map — источник правды, кучи — кандидаты, а сверка с map отличает живых от мёртвых.

*Сложность:* исправление — O(log n); максимум и минимум — O(log n) амортизированно (каждая пара
снимается не больше одного раза); память O(n).

</details>

**3. Склейка клиентов в CRM.** Выгрузка — список записей `[имя, почта1, почта2, …]`. Две записи — один
человек, если у них есть общая почта, и это работает цепочкой: A и B делят одну почту, B и C — другую,
значит A, B и C — один человек. Верни людей: имя и отсортированный список всех их почт.
*Ограничения:* до 1000 записей, до 10 почт в каждой.

<details class="algo-details">
<summary>Связка</summary>

**Union-Find + хеш-таблица + сортировка.**

1. **Конфликт:** группы складываются цепочкой через общие почты — это вопрос связности. Но почты —
   строки, и их надо сопоставлять между записями; а на выходе почты ещё и отсортированы.
2. **Первый приём:** [Union-Find](union-find-structure.md) объединяет записи и отвечает «в одной ли
   группе» почти за O(1). Но он работает с номерами записей `0…n−1` и не знает, у каких из них
   почта общая.
3. **Добор:** map `почта → номер первой записи с ней`. Встретили почту второй раз — `Union` текущей
   записи с той. В конце — сортировка почт каждой группы.
4. **Стык:** проход 1 — map находит пары записей, DSU их склеивает. Проход 2 — для каждой почты
   `Find(её запись)` даёт корень, почта уходит в группу `корень → []почта`. Затем `sort.Strings` по
   каждой группе, имя — из записи-корня.

*Сложность:* при E почтах всего — O(E log E): сортировка дороже всего остального (Union-Find почти
O(1) на почту); память O(E).

</details>

**4. Однопоточный процессор.** Задачи заданы парами `[момент поступления, длительность]`, процессор
один. Освободившись, он берёт из уже поступивших задач **самую короткую** (при равенстве — с меньшим
номером); если поступивших нет — простаивает до следующей. Верни номера задач в порядке выполнения.
*Ограничения:* до 10⁵ задач, моменты и длительности до 10⁹.

<details class="algo-details">
<summary>Связка</summary>

**Сортировка + мин-куча** — как в Meeting Rooms, но куча упорядочена по другому ключу.

1. **Конфликт:** задачи появляются по времени поступления, а выбирать надо по длительности — из
   тех, что уже появились.
2. **Первый приём:** [сортировка](sorting.md) номеров задач по моменту поступления; указатель по
   отсортированному списку отдаёт «всё, что поступило к моменту t». Но среди поступивших искать
   кратчайшую перебором — O(n) на выбор, O(n²) всего.
3. **Добор:** [мин-куча](heap-structure.md) пар `(длительность, номер)` поступивших задач.
4. **Стык:** текущее время `t`. Пока у указателя задача с поступлением ≤ `t` — `Push` её в кучу.
   Куча пуста — перематываем `t` на поступление следующей задачи. Иначе `Pop`, номер — в ответ,
   `t += длительность`. Время копится до 10⁵·10⁹ = 10¹⁴ — `int` в Go 64-битный, хватает.

*Сложность:* O(n log n) — и сортировка, и n операций с кучей; память O(n).

</details>

**5. Острова после каждой засыпки.** Карта `m × n` сначала вся — вода. Приходят k запросов «насыпать
сушу в клетку (r, c)»; после каждого верни число островов (остров — суша, связанная по четырём
сторонам). Повторная засыпка той же клетки ничего не меняет. *Ограничения:* `m·n` до 10⁴, k до 10⁴.

<details class="algo-details">
<summary>Связка</summary>

**Union-Find + номер клетки в сетке.**

1. **Конфликт:** число компонент нужно после **каждого** добавления. Пересчитать острова обходом
   [BFS](grids-and-shortest-paths.md) — O(m·n) на запрос, 10⁴ · 10⁴ = 10⁸ всего.
2. **Первый приём:** [Union-Find](union-find-structure.md) склеивает группы почти за O(1) и сам ведёт
   счётчик: новая суша — +1 группа, каждое `Union` разных групп — −1. Но он не знает, какие клетки
   соседние.
3. **Добор:** сетка: клетка `(r, c)` получает номер `r·n + c`, массив `land[]` говорит, суша ли она;
   четыре соседа находятся за O(1).
4. **Стык:** запрос → клетка уже суша — ответ прежний. Иначе `land = true`, `count++`, и для каждого
   соседа-суши: если `Find` у них разный — `Union` и `count--`. Ответ на запрос — `count`.

*Сложность:* O(m·n + k) с точностью до почти константы Union-Find; память O(m·n).

</details>

**6. Зарядки вдоль трассы.** Вдоль трассы n мест, где можно поставить зарядную станцию (координаты в
км, не отсортированы). Нужно поставить k станций так, чтобы **самый короткий** промежуток между
соседними станциями был как можно длиннее. Верни эту длину. Пример: места `[1, 2, 3, 4, 7]`, k = 3 →
`3` (станции в 1, 4, 7). *Ограничения:* n до 10⁵, координаты до 10⁹, 2 ≤ k ≤ n.

<details class="algo-details">
<summary>Связка</summary>

**Сортировка + бинарный поиск по ответу + жадная проверка.**

1. **Конфликт:** просят максимизировать минимум — оптимум по ответу. Перебрать все расстановки —
   C(n, k) вариантов, нереально.
2. **Первый приём:** [бинарный поиск по ответу](modified-binary-search.md#бинарный-поиск-по-ответу):
   пополам делим не массив, а диапазон длин `D` от 1 до `max − min`. Если промежуток `D` достижим,
   то достижим и любой меньший — монотонно, пополам можно. Но поиску нужен ответ на вопрос «можно ли
   с промежутками ≥ D?».
3. **Добор:** [жадная](greedy.md) проверка по отсортированным координатам: первую станцию — в самое
   левое место, каждую следующую — в первое место на расстоянии ≥ `D` от последней поставленной.
   Набралось ≥ k — «можно». Ставить раньше выгодно: от левой станции до следующей остаётся
   больше выбора.
4. **Стык:** сортировка один раз; бинарный поиск зовёт проверку O(n) на каждом из ~30 шагов
   (log₂ 10⁹ ≈ 30). На примере: `D = 3` — станции 1, 4, 7, «можно»; `D = 4` — 1, затем 7, только две,
   «нельзя». Ответ 3.

*Сложность:* O(n log n + n log R), где R = max − min — разброс координат; память O(1) сверх сортировки.

</details>

**7. Инкассация.** Выручка смены — массив чеков `nums`. Инкассатор берёт только суммы, кратные `p`.
Убери **один непрерывный кусок** чеков, как можно короче (убрать все нельзя), чтобы сумма оставшихся
делилась на `p`. Верни длину куска или −1. Пример: `[3, 1, 4, 2]`, p = 6 → `1` (убрать `4`, останется
6). *Ограничения:* n до 10⁵, числа и `p` до 10⁹.

<details class="algo-details">
<summary>Связка</summary>

**Префиксные суммы + хеш-таблица остатков.**

1. **Конфликт:** нужна сумма произвольного куска — и не любого, а самого короткого с нужным
   остатком. Перебор всех кусков — O(n²).
2. **Первый приём:** [префиксные суммы](prefix-sums.md): сумма куска `(j, i]` = `pre[i] − pre[j]`.
   Пусть `r` = (сумма всех) mod `p`; если `r = 0`, ответ 0. Иначе убрать нужно кусок с остатком `r`.
   Но парный префикс `j` для каждого `i` всё ещё ищется перебором.
3. **Добор:** [хеш-таблица](hash-table-structure.md) `остаток префикса → последний индекс, где он
   был`. Последний — потому что чем ближе `j` к `i`, тем короче кусок.
4. **Стык:** один проход: `cur = (cur + x) % p`, нужный остаток `want = (cur − r + p) % p`; есть в map —
   кандидат `i − map[want]`; затем `map[cur] = i`. Стартовая запись `map[0] = −1` — пустой префикс.
   Лучший кандидат равен n — значит, пришлось бы убрать всё: ответ −1. На примере: r = 10 mod 6 = 4;
   на `i = 2` префикс 8, `cur = 2`, `want = 4`, а остаток 4 был у префикса `3 + 1` на `i = 1` — кусок
   длины 1.

*Сложность:* O(n) время, O(min(n, p)) память.

</details>

**8. Буквы без повторов.** Из строки строчных латинских букв оставь каждую букву ровно один раз
(порядок букв не меняется, лишние вычёркиваются) так, чтобы результат был наименьшим по алфавиту
среди всех возможных. Пример: `"cbacdcbc"` → `"acdb"`. *Ограничения:* длина до 10⁴.

<details class="algo-details">
<summary>Связка</summary>

**Монотонный стек + таблица последних вхождений + множество «уже в стеке».**

1. **Конфликт:** хочется поставить маленькую букву раньше, выкинув большие перед ней. Но выкинуть
   можно только букву, которая **ещё встретится** дальше, и каждая должна остаться ровно один раз.
2. **Первый приём:** [монотонный стек](monotonic-stack.md), как в удалении k цифр: пока вершина
   больше текущей буквы — снимаем. Но он не знает, встретится ли снятая буква снова, и пропустит
   дубли.
3. **Добор:** `last[ch]` — индекс последнего вхождения буквы (один проход заранее) и `inStack[ch]` —
   уже ли буква в ответе. Оба — массивы на 26.
4. **Стык:** идём по строке; буква уже в стеке — пропуск. Иначе, пока вершина > `ch` и
   `last[вершина] > i` (вершина ещё встретится) — `pop` и снять отметку `inStack`; затем `push`. На
   примере: `c` вытесняется `b`, `b` — `a`; потом `a c d`; на втором `b` вершина `d` больше не
   встретится — остаётся, и выходит `acdb`.

*Сложность:* O(n) время (каждая буква кладётся и снимается не больше раза), O(1) память — 26 ячеек.

</details>

**9. Кодовый замок.** Замок из четырёх колёс с цифрами 0–9, сейчас стоит `0000`. Ход — повернуть одно
колесо на одну цифру вверх или вниз (9 и 0 соседние). Есть список «ловушек» — комбинаций, на которых
замок блокируется: вставать на них нельзя. За сколько минимум ходов открыть код `target`? Нельзя —
верни −1. *Ограничения:* до 500 ловушек.

<details class="algo-details">
<summary>Связка</summary>

**BFS по состояниям + хеш-множество** — перенос Word Ladder: «слово» здесь — комбинация замка.

1. **Конфликт:** минимум ходов, каждый ход стоит 1 — кратчайший путь. Но графа нет, а часть вершин
   запрещена.
2. **Первый приём:** [BFS](graphs.md) по состояниям: всего 10⁴ комбинаций, у каждой 8 соседей
   (4 колеса × 2 направления). Но ему надо быстро отвечать «это ловушка?» и «тут уже были?».
3. **Добор:** [хеш-множество](hash-table-structure.md) ловушек и посещённых (или массив на 10⁴:
   комбинация — это число 0…9999).
4. **Стык:** ловушки заранее кладём в «посещённые» — BFS просто не войдёт в них; если `0000` — сама
   ловушка, ответ −1. Дальше BFS по слоям: соседей порождаем на лету, проверяем по множеству,
   отмечаем при постановке в очередь. Слой, на котором встретился `target`, — ответ.

*Сложность:* не больше 10⁴ состояний × 8 соседей = 8·10⁴ проверок; память O(10⁴).

</details>

**10. Самая дорогая витрина без повторов.** Массив `nums`, длина отрезка k. Среди всех отрезков из k
подряд идущих чисел, в которых **все числа разные**, найди наибольшую сумму; таких отрезков нет —
верни 0. Пример: `[1, 5, 4, 2, 9, 9, 9]`, k = 3 → `15` (отрезок `4, 2, 9`). *Ограничения:* n до 10⁵.

<details class="algo-details">
<summary>Связка</summary>

**Скользящее окно постоянной длины + хеш-таблица счётчиков.**

1. **Конфликт:** сумма отрезка длины k (окно) плюс условие «все разные» внутри этого окна.
2. **Первый приём:** [скользящее окно](sliding-window.md) постоянной длины: при сдвиге прибавить
   вошедшее, вычесть вышедшее — сумма за O(1). Но есть ли в окне повтор, окно не знает: проверять
   заново — O(k) на сдвиг.
3. **Добор:** [хеш-таблица](hash-table-structure.md) `число → сколько раз оно в окне`; ключ с нулём
   удаляем, тогда `len(count)` — число разных значений в окне.
4. **Стык:** на сдвиге — `sum += nums[i]`, `count[nums[i]]++`; вышедшее `nums[i−k]`: `sum -=`,
   `count--`, на нуле — `delete`. Окно полное и `len(count) == k` — все разные, `sum` — кандидат. На
   примере: окна `1 5 4` = 10, `5 4 2` = 11, `4 2 9` = 15, дальше в каждом окне есть повтор девяток.

*Сложность:* O(n) время, O(k) память.

</details>

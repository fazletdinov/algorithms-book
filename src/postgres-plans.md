# 🐘 Postgres: EXPLAIN как pprof

> 🧭 **Зачем эта глава.** [Карта структур в реальных системах](real-world-map.md) рассказала,
> что внутри Postgres живут B-дерево, хеш-таблица и K-way merge. Это знание для чтения. Здесь
> — то же самое руками: поднимаешь базу на два миллиона строк, **предсказываешь план,
> потом смотришь настоящий `EXPLAIN ANALYZE`** и видишь, где ошибся. Привычка та же, что в
> [приложении про профилирование](appendix-go-memory.md): не угадывай, измеряй. Разница
> одна, и она делает главу интереснее: в Go алгоритм выбираешь ты, а здесь его выбирает
> **планировщик** — и твоя работа не написать алгоритм, а понять, почему он выбрал этот и
> что мешает ему выбрать лучший.
>
> Все планы и цифры ниже сняты с живой базы из `pglab/` (Postgres 16, `work_mem=4MB`,
> параллельные планы выключены). У тебя они воспроизведутся: данные детерминированы, версия
> образа пришпилена. Абсолютное время будет своё, **соотношения** — те же.

## Лаборатория: одна команда

```bash
make pg-lab        # поднять базу и налить данные (в первый раз дольше — качается образ)
make pg-psql       # psql внутрь
make pg-lab-down   # погасить и стереть
```

Внутри — две таблицы: `users` (200 000 строк) и `orders` (2 000 000). Схема нарочно
простая, интерес в распределениях: `users.status` перекошен (80% `active`, 15% `blocked`,
5% `deleted`), `users.region` **однозначно определяется** городом, `email` — текст с общими
префиксами. Именно на таких данных планировщик вынужден выбирать между разными алгоритмами,
а не идти по одному пути всегда.

Дальше в каждом разделе: сначала вопрос, **ответь до запуска**, потом настоящий план.

## Как читать `EXPLAIN ANALYZE` за пять шагов

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```

1. **Читай снизу вверх и изнутри наружу** — дерево исполняется от листьев к корню.
2. `cost=X..Y` — **оценка** планировщика в условных единицах (не миллисекунды!): `X` до
   первой строки, `Y` до последней. `actual rows` — **факт**.
3. **Сравни `rows=` оценку с `actual rows`.** Разошлись в разы — планировщик выбирал
   алгоритм по неверным цифрам, и дальше всё плохо именно из-за этого.
4. `Buffers: shared hit=N read=M` — сколько страниц по 8 КБ прочитано из кэша и с диска.
   **Это честнее времени**: не зависит от того, прогрет ли кэш и что ещё делает машина.
5. `Execution Time` — итог. `Planning Time` рядом: на коротких запросах планирование иногда
   дороже исполнения.

Дальше по книге `Buffers` — главная метрика. Время скачет, буферы — нет.

## 1. Seq Scan против Index Scan — это выбор алгоритма, который ты уже знаешь

Линейный поиск против поиска по [B-дереву](btree-structure.md). Казалось бы, индекс всегда
выигрывает. Три запроса к **одной** таблице `users`, у которой есть индексы и по `status`, и
по `created_at`:

<div class="algo-challenge__q">Три запроса: <code>WHERE id = 42</code>, <code>WHERE status = 'deleted'</code> (5% строк), <code>WHERE status = 'active'</code> (80% строк). Индексы есть везде. Сколькими из трёх планировщик воспользуется индексом?</div>

**Точечный поиск — индекс, 4 страницы:**

```text
 Index Scan using users_pkey on users  (cost=0.42..8.44 rows=1 width=51) (actual rows=1 loops=1)
   Index Cond: (id = 42)
   Buffers: shared hit=4
 Execution Time: 0.064 ms
```

Четыре буфера — это высота B-дерева плюс страница с самой строкой. Ровно то, что обещает
глава про [B-дерево](btree-structure.md): дерево «толстое и низкое», до любой строки три-четыре
чтения.

**5% строк — индекс, но уже через битовую карту:**

```text
 Bitmap Heap Scan on users  (cost=112.35..2297.01 rows=9813 width=4) (actual rows=10130 loops=1)
   Recheck Cond: (status = 'deleted'::text)
   Heap Blocks: exact=2049
   Buffers: shared hit=2060
   ->  Bitmap Index Scan on users_status_idx  (...) (actual rows=10130 loops=1)
         Buffers: shared hit=11
 Execution Time: 2.407 ms
```

Смотри внимательно на две строки. `Bitmap Index Scan` прочитал **11 страниц индекса** и
построил битовую карту нужных строк ([битовые операции](bit-manipulation.md) в проде). А
`Heap Blocks: exact=2049` — это сколько страниц таблицы пришлось потом прочитать. Вся таблица
занимает 2062 страницы. То есть **5% строк размазаны почти по всем страницам таблицы**:
выбрали двадцатую часть данных, а прочитали всё равно всю таблицу.

Вот он, тот самый «промах кэша» из раздела «Цена на практике» по всей книге, только на уровне
диска. Индекс сэкономил не чтения, а **проверку условия на 200 000 строк** — оттого 2.4 мс
против 12.2 мс, а не против бесконечности.

**80% строк — планировщик отказывается от индекса:**

```text
 Seq Scan on users  (cost=0.00..4562.00 rows=159980 width=4) (actual rows=159542 loops=1)
   Filter: (status = 'active'::text)
   Rows Removed by Filter: 40458
   Buffers: shared hit=2062
 Execution Time: 12.203 ms
```

Индекс `users_status_idx` существует и **не используется**. Это не ошибка и не «база не видит
индекс» — это решение по модели стоимости: у Seq Scan `cost=4562`, а Index Scan, если его
навязать (`SET enable_seqscan = off; SET enable_bitmapscan = off;` — только для эксперимента),
оценён почти вдвое дороже:

```text
 Index Scan using users_status_idx on users  (cost=0.29..8677.21 rows=159487 width=4) (actual rows=159542 loops=1)
   Index Cond: (status = 'active'::text)
   Buffers: shared hit=2198
```

Теперь факт — по двум метрикам. **По буферам планировщик прав: 2198 против 2062.** 2198 — это те
же 2062 страницы таблицы плюс 136 страниц индекса: 80% строк лежат на всех страницах, и
сэкономить чтения таблицы тут нечем. Россыпи случайных чтений при этом не случилось: страницы
таблицы индекс отдал строго по возрастанию, каждую по одному разу (почему — ниже, в разделе
[про 2049 страниц](#посмотри-откуда-берутся-2049-страниц)).

**По времени на прогретом кэше навязанный план на ~2 мс быстрее:** 9.4 мс против 11.5 мс у Seq
Scan (медианы девяти чередующихся запусков `SELECT sum(id) FROM users WHERE status = 'active'`).
Seq Scan проверил условие на всех 200 000 строках (`Rows Removed by Filter: 40458`), Index Scan
взял из индекса ровно нужные 159 542 — без фильтра. Но `cost` считает и цену чтения страницы с
диска (`random_page_cost`), а на прогретом кэше, где все страницы уже в памяти, эта цена не
проявляется; холодный кэш здесь не мерился. В оценку входит константа `random_page_cost`: при
`SET random_page_cost = 1.1` вместо 4.0 тот же Index Scan оценён в 4935, а не в 8677, — всё ещё
дороже 4562, то есть дело не только в ней. Что это за константа и почему её дефолт описывает
чужое железо — в разделе [«Почему планировщик выбирает именно так»](#-почему-планировщик-выбирает-именно-так).

Это иллюстрация ошибок 1 и 3 из [«Типичных ошибок»](#-типичные-ошибки) в конце главы — `cost` не
миллисекунды, а время на прогретом кэше — не мерило, — а не повод навязывать индекс: флаги
`enable_*` — инструмент диагностики, а не настройка (ошибка 6).

> 💡 **Практический вывод.** «Запрос медленный — навешу индекс» работает, только если условие
> отсекает **большую часть** таблицы, а где проходит эта граница, решает стоимость планов, а не
> круглая цифра. Индекс по полю `status`, у которого три значения и перекос 80/15/5,
> планировщик берёт для двух значений из трёх: для `'deleted'` (5%) и для `'blocked'` (15%).
> Оба раза это `Bitmap Heap Scan`, и на 15% он читает все 2062 страницы таблицы
> (`Heap Blocks: exact=2062`) — столько же, сколько Seq Scan, — но планировщик оценивает его
> дешевле (`cost` 2797 против 4562): страниц то же число, значит, экономия может быть только в
> работе над строками. Для `'active'` (80%) индекс не берётся, а навязанный, как видно выше, не
> экономит ни одной страницы таблицы. Прежде чем создавать индекс, спроси: какую долю таблицы
> отсечёт условие и сколько страниц всё равно придётся прочитать?

### Посмотри, откуда берутся 2049 страниц

Представь библиотеку: 12 полок, на каждой по 8 книг. Тебе нужны 5 книг, и стоят они на 5
разных полках. Собрать их можно тремя способами.

1. **Обойти все полки подряд** и на каждой просмотреть все книги. Двенадцать подходов, сколько
   бы книг ни понадобилось: пять, семьдесят или ни одной.
2. **Идти по каталогу.** Каталог — список книг по алфавиту, у каждой записан номер полки. Берёшь
   книги в порядке каталога: следующая стоит на той же полке, что предыдущая, — снимаешь её, не
   отходя; на другой — идёшь туда. Только алфавит ничего не знает о полках: каталог может увести
   в другой конец зала, а потом вернуть к полке, у которой ты уже стоял, — и к ней придётся
   подойти снова.
3. **Сначала выписать из каталога номера полок** (и какие книги на каждой), вычеркнуть повторы,
   расставить по порядку — и только потом пройти вдоль стеллажей, к каждой нужной полке ровно
   один раз.

Полка — это страница таблицы, книга — строка, каталог — индекс, а «подойти к полке» — одно
чтение страницы, то самое, что считает `Buffers`. Индекс хранит при каждом ключе `ctid` — номер
страницы и номер строки на ней (это из [предыдущей главы](postgres-storage.md)) — и отдаёт их
**в порядке ключа**, а не в порядке страниц. Три способа — три плана: **Seq Scan**, **Index
Scan** и **Bitmap Heap Scan**. Выписка номеров полок — это и есть битовая карта из плана для 5%
строк (`Bitmap Heap Scan`).

> 💡 **Что смотреть в виджете.** Три вкладки — три способа на одной таблице: 12 страниц по 8
> строк, условию подходят 5 строк, разбросанных по разным страницам. Карточка — страница,
> квадратики в ней — строки: зелёные подходят под условие, светло-зелёные уже попали в результат.
> Прочитанная страница синеет и получает «✓», прочитанная повторно — «×2», «×3»; янтарная рамка —
> страница, о которой текущий шаг. Главное число — над сеткой: «Чтений страницы таблицы». Пройди
> каждую вкладку кнопкой **›** до конца: Seq Scan — 12, Index Scan и Bitmap Scan — по 5. На пяти
> разбросанных строках индексным способам делить нечего. Теперь раскрой «Ввод и граничные
> случаи» над сеткой и во вкладке Index Scan нажми **«70% строк»**: чтений станет 62 — больше, чем
> страниц в таблице, потому что порядок индекса уводит с одной страницы на другую и возвращает
> обратно. Ключ в виджете — разные значения, разбросанные по таблице; у `status = 'active'` выше
> ключ один на все 80% строк, и там порядок другой — об этом ниже. Та же кнопка во вкладке
> Bitmap Scan даст 12: каждая страница по разу. А **«те же строки подряд»** — пять строк на одной
> странице: индексу хватает одного чтения против двенадцати у Seq Scan. Включи 🎯 во вкладке
> Index Scan — и на строке `if tid.Page != cur` виджет спросит, придётся ли читать страницу,
> прежде чем это покажет.

Виджет считает только чтения страниц **таблицы**: страницы индекса, кэш против диска и `cost`, по
которому планировщик выбирает план, в нём не моделируются, — поэтому 12 страниц против 2062
показывают механизм, а не выбор плана. Сам механизм стоит сверить с живой базой. В лаборатории
таблица `scan_demo` сделана ровно такой, как в виджете: 12 страниц по 8 строк, строки лежат по
порядку `id`. Ключ `k` перемешан относительно `id`: соседние по `k` строки стоят через 13 строк
друг от друга, то есть на разных страницах. Каждый план включали по очереди флагами `enable_*`
(только для эксперимента — так же, как Index Scan для 80% выше), считали страницы **таблицы**, а
список подходящих `id` в порядке ключа прогоняли через модель виджета. В каждой клетке — модель /
живой Postgres:

| Условие | Какие строки подходят | Seq Scan | Index Scan | Bitmap Heap Scan |
|---|---|---|---|---|
| `k < 5` | 5 строк на 5 разных страницах | 12 / 12 | 5 / 5 | 5 / 5 |
| `id < 5` | 5 строк на одной странице | 12 / 12 | 1 / 1 | 1 / 1 |
| `k < 67` | 67 из 96 (70%) | 12 / 12 | **67 / 67** | 12 / 12 |
| `k < 0` | ни одной | 12 / 12 | 0 / 0 | 0 / 0 |

Самая важная строка — `k < 67`: Index Scan 67 раз прочитал страницу таблицы, в которой их всего
12, — каждую в среднем больше пяти раз. (В виджете на «70% строк» выходит 62: строки там
другие, правило то же.) Хочешь увидеть в виджете ровно строки `k < 5` — впиши в поле
«Подходящие строки» `0,13,26,39,52`: это их `id` в порядке ключа, и `ctid` в шагах совпадут с
настоящими — от `(0,1)` до `(6,5)`.

План для 5% строк выше — та же картина в масштабе 200 000 строк. Битовая карта собрала 2049
страниц из 2062 (`Heap Blocks: exact=2049`), и каждую прочитала один раз. Откуда почти все
страницы: 10 130 строк `'deleted'` на 2062 страницах — в среднем по пять на страницу (из примерно
97 строк на ней, см. [предыдущую главу](postgres-storage.md)), а `status` в лаборатории раздаётся
случайно, строка за строкой (`random()` после `setseed` в `init.sql`), — вот пятёрка и попадает
почти на каждую страницу: на 2049 из 2062. `Buffers: shared hit=2060` — это они же плюс 11 страниц
индекса; у нас на `k < 5` так же: 6 = 5 + 1. Слово `exact` значит, что карта точная: помнит не
только страницы, но и номера строк на них, и со страницы берутся только эти строки.

А если битовую карту запретить? Обычный Index Scan по `status = 'deleted'` на той же базе
прочитал **те же 2060 буферов**, а не 10 130. Ключ у всех этих строк один — `'deleted'`, и
равные ключи индекс отдал строго по возрастанию `ctid`: ни одного возврата на уже прочитанную
страницу. С `'active'` выше — то же самое: 159 542 строки, 2062 страницы, каждая по одному разу.
Так устроено B-дерево Postgres (с 12-й версии): среди равных ключей записи лежат по порядку
`ctid`. Перечитывания начинаются, когда ключи разные и их порядок не совпадает с порядком строк
в таблице, — как у `k` в `scan_demo` и в виджете на «70% строк». Мораль у виджета и у живой
базы одна: **считай не строки, а страницы, на которых они лежат.**

<summary>⚙️ Второй проход: как снять эти числа самому — читать, когда освоишься</summary>

Таблица — в `make pg-psql`:

```sql
CREATE TABLE scan_demo (id int PRIMARY KEY, k int NOT NULL, pad text NOT NULL);
ALTER TABLE scan_demo ALTER COLUMN pad SET STORAGE PLAIN;  -- не сжимать текст
ALTER TABLE scan_demo SET (autovacuum_enabled = off);
INSERT INTO scan_demo SELECT g, (g * 37) % 96, repeat('x', 967) FROM generate_series(0, 95) g;
CREATE INDEX scan_demo_k_idx ON scan_demo (k);
VACUUM ANALYZE scan_demo;
SELECT (ctid::text::point)[0]::int AS page, count(*) FROM scan_demo GROUP BY 1 ORDER BY 1;
```

Последний запрос покажет 12 страниц по 8 строк. Строка занимает 1003 байта (заголовок 24 +
`id` 4 + `k` 4 + заголовок `text` 4 + 967 символов), с выравниванием — 1008, с указателем — 1012.
Восемь таких — 8096 байт, они влезают в 8168 байт страницы за вычетом её заголовка, девятая — уже
нет. Как это считается, разобрано в [предыдущей главе](postgres-storage.md).

```sql
SET enable_seqscan = off; SET enable_bitmapscan = off; SET enable_indexonlyscan = off;
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF) SELECT * FROM scan_demo WHERE k < 67;
```

```text
 Index Scan using scan_demo_k_idx on scan_demo (actual rows=67 loops=1)
   Index Cond: (k < 67)
   Buffers: shared hit=68
```

68 — это 67 страниц таблицы и 1 страница индекса. Как их разделить: у Bitmap Heap Scan страницы
таблицы напечатаны отдельно (`Heap Blocks: exact=…`), а страницу индекса показывает его дочерний
узел `Bitmap Index Scan` — `Buffers: shared hit=1`. Ту же одну страницу индекса читает Index
Scan, которому ничего не подошло (`k < 0`: `Buffers: shared hit=1`). Независимая проверка —
`pg_statio_user_tables`: там обращения к таблице (`heap_blks_hit`) считаются отдельно от
обращений к индексу, и после того же запроса без `EXPLAIN` таблице досталось ровно 67.

И про слово `exact`. Карта точная, пока помещается в `work_mem`. Урежь его до минимума —
`SET work_mem = '64kB'` — и запрос по `users` для 5% строк покажет
`Heap Blocks: exact=1016 lossy=1033` и `Rows Removed by Index Recheck: 95062`. На «потерявших
точность» (lossy) страницах карта помнит только номер страницы, поэтому все строки на них
перепроверяются условием. Строку `Recheck Cond` EXPLAIN печатает у любого Bitmap Heap Scan — она
есть и в точном плане для 5% (`exact=2049`), — но работу она делает только на lossy-страницах, а
сколько строк при этом отбраковано, показывает `Rows Removed by Index Recheck`: в точном плане
этой строки нет вовсе, при 64kB — 95062. А `Buffers` остались те же 2060: страниц не стало больше,
работы на каждой — стало.

</details>

### Index Only Scan: когда строка вообще не нужна

Тот же диапазон по `created_at`, но два разных запроса. `SELECT id, email` — 294 буфера:

```text
 Bitmap Heap Scan on users  (...) (actual rows=1918 loops=1)
   Heap Blocks: exact=291
   Buffers: shared hit=294
 Execution Time: 0.554 ms
```

А `SELECT count(*)` по тому же условию — **4 буфера**:

```text
 Aggregate  (cost=45.78..45.79 rows=1 width=8) (actual rows=1 loops=1)
   ->  Index Only Scan using users_created_at_idx on users  (...) (actual rows=1918 loops=1)
         Heap Fetches: 0
         Buffers: shared hit=4
 Execution Time: 0.160 ms
```

294 → 4 страницы, потому что ответ целиком собран **из индекса**, в таблицу заходить не
пришлось (`Heap Fetches: 0`). Отсюда индустриальный приём — **покрывающий индекс**: добавить в
индекс столбцы, которые запрос только читает (`INCLUDE (email)`), и заход в таблицу исчезнет.
Цена — индекс становится толще, а значит дороже в записи.

## 2. Три алгоритма соединения — это три главы этой книги

Postgres умеет соединять таблицы тремя способами, и все три ты уже писал руками.

| План | Что это | Глава |
|---|---|---|
| **Nested Loop** | для каждой строки внешней таблицы — поиск во внутренней; с индексом это `O(n log m)`, без индекса — вложенный перебор `O(n·m)` | [Big-O](big-o.md) |
| **Hash Join** | построить хеш-таблицу по меньшей стороне (фаза build), прогнать по ней большую (фаза probe) | [Хеш-таблица](hash-table-structure.md) |
| **Merge Join** | оба входа отсортированы — идём по обоим вперёд, у каждого свой указатель | [Два указателя](two-pointers.md) |

Теория говорит: у каждого своя область. Проверим на одном запросе, запрещая планировщику
алгоритмы по очереди (`SET enable_hashjoin = off` — только для экспериментов, не для прода).

**Запрос 1: соединяем целиком, 2 000 000 заказов × 200 000 пользователей.**

Выбрал Hash Join:

```text
 ->  Hash Join  (cost=7539.00..64098.11 rows=2000000 width=9) (actual rows=2000000 loops=1)
       Hash Cond: (o.user_id = u.id)
       Buffers: shared hit=2468 read=14300, temp read=3362 written=3362
       ->  Seq Scan on orders o  (actual rows=2000000 loops=1)
       ->  Hash  (actual rows=200000 loops=1)
             Buckets: 262144  Batches: 2  Memory Usage: 6749kB
 Execution Time: 733.412 ms
```

`Batches: 2` — хеш-таблица не поместилась в `work_mem` и **поделилась надвое с выгрузкой на
диск** (`temp written=3362`). Это в точности то, что делает внешний алгоритм, когда данные не
влезают в память.

Теперь запретим hash join и посмотрим на Merge Join:

```text
 ->  Merge Join  (cost=1.16..71841.26 rows=2000000 width=9) (actual rows=2000000 loops=1)
       Merge Cond: (u.id = o.user_id)
       Buffers: shared hit=4873
       ->  Index Scan using users_pkey on users u  (actual rows=200000 loops=1)
       ->  Index Only Scan using orders_user_id_idx on orders o  (actual rows=2000000 loops=1)
 Execution Time: 301.460 ms
```

**301 мс против 733 мс — запрещённый алгоритм оказался вдвое быстрее выбранного.** И видно,
почему: 4873 буфера против 16 768 плюс временные файлы. Merge join взял оба входа уже
отсортированными **из индексов** (сортировать не пришлось вовсе) и прошёл их двумя указателями
— ровно [шаблон two-pointers](two-pointers.md), только по двум B-деревьям.

И третий, nested loop:

```text
 ->  Nested Loop  (cost=0.43..159138.00 rows=2000000 width=9) (actual rows=2000000 loops=1)
       Buffers: shared hit=602063
       ->  Seq Scan on users u  (actual rows=200000 loops=1)
       ->  Index Only Scan using orders_user_id_idx on orders o  (actual rows=10 loops=200000)
             Buffers: shared hit=600001
 Execution Time: 396.076 ms
```

Обрати внимание на `loops=200000` — внутренний узел выполнился двести тысяч раз. Отсюда
**602 063 буфера**: в 124 раза больше, чем у merge join. Работает он при этом за 396 мс — и все
600 тысяч обращений попали в кэш: `shared hit=600001`, а `read` в строке нет вовсе. Сколько стоил бы
этот план на холодной базе, здесь не мерилось.

**Запрос 2: то же соединение, но внешняя сторона — 19 строк** (`WHERE u.id < 20`).

| Алгоритм | Буферов | Время |
|---|---|---|
| **Nested Loop** (выбор планировщика) | 244 | **0.384 мс** |
| Hash Join (навязан) | ~14 710 | 105.695 мс |

Разница — **275 раз**, и теперь в пользу nested loop. Хеш-соединению, чтобы отдать 183 строки,
пришлось прочитать все два миллиона заказов, хотя сам хеш построен всего по 19 пользователям
(`Hash (actual rows=19)`). Nested loop сделал 19 обращений к индексу.

> **Мораль, знакомая по всей книге.** Нет «лучшего» алгоритма соединения — есть подходящий
> размеру входа. Ровно как [`O(n)` не всегда быстрее `O(n log n)`](sliding-window.md) на твоих
> данных. Планировщик каждый раз решает эту задачу заново, и решает по **оценке числа строк** —
> отсюда [раздел 5](#5-весь-выбор-стоит-на-оценке-числа-строк).

### Посмотри пошагово: три способа соединить две таблицы

Представь две стопки карточек. В тонкой — пользователи, по карточке на каждого. В толстой —
заказы, и на каждом записан номер его пользователя. Нужно собрать пары «пользователь — его
заказ». Способов три.

1. **Для каждой карточки из тонкой стопки сходить в картотеку.** Кроме стопки, заказы разложены
   ещё и по ящикам картотеки — ящик на каждый номер пользователя. Берёшь пользователя, открываешь
   его ящик, выписываешь всё, что там лежит. Походов в картотеку столько, сколько карточек в
   тонкой стопке, — и к пустому ящику ты тоже сходишь: что он пуст, узнаёшь, только открыв его.
2. **Разложить тонкую стопку по ячейкам** — ячейка на номер пользователя — и один раз пройти всю
   толстую: на каждом заказе заглядываешь в ячейку его номера. Картотека не нужна, зато толстую
   стопку проходишь целиком, сколько бы пар в ней ни нашлось.
3. **Взять обе стопки, уже сложенные по номеру пользователя, и идти по ним двумя пальцами.**
   Номера под пальцами совпали — пара; не совпали — двигаешь палец, под которым номер меньше.
   Кончилась одна стопка — остаток другой смотреть незачем: пар в нём не будет.

Картотека — это индекс `orders(user_id)`, ячейки — хеш-таблица, два пальца — два указателя. Три
способа — три алгоритма из таблицы в начале раздела: **Nested Loop**, **Hash Join** и **Merge
Join**. Тонкую стопку у Nested Loop называют **внешней** таблицей: по её строкам идёт внешний цикл.

> 💡 **Что смотреть в виджете.** Три вкладки — три алгоритма на одних и тех же таблицах: в `users`
> 8 строк (id от 1 до 8), в `orders` 14 заказов. Верхний ряд — `users`, нижний — заказы (в клетке —
> `user_id` заказа); у Hash Join между ними ряд хеш-таблицы. Серая клетка ещё не читалась, синяя
> прочитана, зелёная вошла в результат, клетка в янтарной рамке — та, о которой текущий шаг.
> Главная строка — над рядами: «заказов прочитано» и счётчик алгоритма. Пример главы соединяет
> таблицы целиком, как запрос 1 выше, и в нём два неудобных места: у пользователей 3 и 8 заказов
> нет, а у двух заказов `user_id = 10` — такого пользователя нет. Пройди каждую вкладку до конца.
> Nested Loop сделает 8 обращений к индексу — по одному на пользователя, как `loops=200000` в
> запросе 1 на каждого из 200 000, — и к пользователям 3 и 8 сходит впустую. Hash Join положит в
> хеш 8 строк и прочитает все 14 заказов, включая два заказа пользователя 10, которым пары не
> нашлось. Merge Join прочитает 8 пользователей и 13 заказов из 14: на первом заказе с
> `user_id = 10` пользователи кончились, и второй такой заказ он уже не берёт. Теперь раскрой «Ввод
> и граничные случаи» и нажми в каждой вкладке **«в users всего 3 строки»** — это другие таблицы,
> 12 пользователей и 24 заказа, с фильтром `u.id < 4`: запрос 2 в миниатюре. Обращений к индексу у
> Nested Loop — 3. Hash Join по-прежнему читает все 24 заказа — то самое, что в запросе 2 стоило
> ему двух миллионов прочитанных заказов ради 183 строк. А Merge Join читает только 7 заказов из 24.
> Кнопка **«заказы без пользователя»** (тоже в каждой вкладке): пользователи 2–4, а у заказов
> `user_id` 1, 2, 3, 7, 8 и 9 — заказам с `user_id` 1, 7, 8 и 9 соединиться не с кем. Nested Loop
> их не касается вовсе, Hash Join читает все шесть и лишние отбрасывает, а Merge Join пропускает
> заказ с `user_id = 1` веткой `else if` (`j++`) и из 7, 8, 9 читает только первый. Включи 🎯 — и
> виджет будет спрашивать до показа: у Merge Join — какой указатель сдвинется (строки `if` и
> `else if`), у Nested Loop — найдёт ли индекс хоть один заказ (строка
> `for _, o := range idx.Lookup(u.ID)`).

Виджет считает только строки и обращения к индексу — не время, не `cost`, не кэш и не то, какой
алгоритм выбрал бы планировщик: на таблицах из 8 и 14 строк он показывает механизм, а не план.
Чего в нём нет вовсе — памяти: его хеш всегда помещается целиком, а `Batches: 2` из запроса 1 —
хеш, который не влез в `work_mem` и поделился с выгрузкой на диск, — так не нарисовать.

Механизм сверен с живой базой. В лаборатории таблицы `j_users` и `j_orders` сделаны ровно такими,
как в виджете: те же пользователи, те же заказы с теми же `user_id`, индекс по
`j_orders(user_id)`. Алгоритм навязывали флагами `enable_*` (только для эксперимента — так же, как
Index Scan для 80% в разделе 1) и сравнивали с моделью то, что считает виджет: у Nested Loop —
`loops` внутреннего узла, то есть сколько раз сходили в индекс; у Hash Join — `actual rows` у
`Seq Scan` по заказам; у Merge Join — `actual rows` обоих его входов, то есть сколько строк слияние
успело взять с каждой стороны. В каждой клетке — модель / живой Postgres:

| Вход в виджете | Nested Loop: обращений к индексу | Hash Join: заказов прочитано | Merge Join: прочитано `users` и заказов |
|---|---|---|---|
| пример главы: 8 пользователей, 14 заказов | 8 / 8 | 14 / 14 | 8 и 13 / 8 и 13 |
| «в users всего 3 строки» (12 и 24 строки, `u.id < 4`) | 3 / 3 | 24 / 24 | 3 и 7 / 3 и 7 |
| «у части пользователей нет заказов» | 6 / 6 | 6 / 6 | 6 и 6 / 6 и 6 |
| «заказы без пользователя» | 3 / 3 | 6 / 6 | 3 и 4 / 3 и 4 |
| «много заказов у одного» | 4 / 4 | 8 / 8 | 4 и 8 / 4 и 8 |

Совпало не с первого раза, и правили виджет, а не таблицу. В строках «у части пользователей нет
заказов» и «много заказов у одного» первая версия модели насчитала у Merge Join на одну строку
`users` меньше: 5 и 3 вместо 6 и 4. Заказы там кончаются сразу после пары, и Postgres на этом не
останавливается: он читает следующую строку `users` и сверяет её с ключом только что пройденной
группы заказов — в общем случае у неё мог бы оказаться тот же ключ, и эту группу пришлось бы
пройти заново (так и написано в исходниках, в `nodeMergejoin.c`). Ещё два коротких пути сверка
поймала на пустом входе, когда после фильтра `u.id < 1` в `users` не осталось ни одной строки:
Merge Join заказы не читает вовсе (`never executed`), а Hash Join читает ровно один — его Postgres
берёт ещё до построения хеша, проверить, что заказы вообще есть, — и, получив пустой хеш, дальше
не идёт. Виджет теперь считает и это так же, как база.

Одна оговорка про Nested Loop: чтобы внешней в эксперименте была именно `users`, как в виджете,
запрос для него записан через `LATERAL` (ниже). С одними флагами планировщик на таких крошечных
таблицах иногда ставил наружу `orders` — какую таблицу сделать внешней, он тоже решает сам.

<details>
<summary>⚙️ Второй проход: как снять эти числа самому — читать, когда освоишься</summary>

Таблицы кнопки «в users всего 3 строки» — 12 пользователей и 24 заказа (сам фильтр `u.id < 4` стоит в
запросах ниже), в `make pg-psql`:

```sql
DROP TABLE IF EXISTS j_orders, j_users;  -- скрипт можно запускать повторно
CREATE TABLE j_users (id int PRIMARY KEY);
CREATE TABLE j_orders (id int PRIMARY KEY, user_id int NOT NULL);
INSERT INTO j_users SELECT generate_series(1, 12);
-- те же 24 заказа, что у кнопки (r24): user_id заказов с id 1, 2, … 24
INSERT INTO j_orders SELECT n, (ARRAY[5,12,6,4,1,1,7,4,7,3,12,3,4,9,6,6,12,8,11,10,10,2,3,4])[n]
FROM generate_series(1, 24) n;
CREATE INDEX j_orders_user_id_idx ON j_orders (user_id);
VACUUM ANALYZE j_users; VACUUM ANALYZE j_orders;
```

Nested Loop с внешней `users`. `LATERAL` разрешает подзапросу справа смотреть на строку `u` слева —
это буквально «для каждой строки `users` выполни подзапрос». А `OFFSET 0` не даёт планировщику слить
такой подзапрос обратно в обычное соединение, поэтому заказы ищутся заново для каждой строки `users`:

```sql
SET enable_seqscan = off;
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
SELECT * FROM j_users u
CROSS JOIN LATERAL (SELECT * FROM j_orders o WHERE o.user_id = u.id OFFSET 0) o
WHERE u.id < 4;
RESET ALL;
```

```text
 Nested Loop (actual rows=6 loops=1)
   ->  Index Only Scan using j_users_pkey on j_users u (actual rows=3 loops=1)
         Index Cond: (id < 4)
   ->  Index Scan using j_orders_user_id_idx on j_orders o (actual rows=2 loops=3)
         Index Cond: (user_id = u.id)
```

`loops=3` — три обращения к индексу, по одному на пользователя. `actual rows=2` у внутреннего
узла — среднее на одно обращение (ошибка 5 в конце главы), а сумма — 6 строк у самого `Nested
Loop`.

Hash Join и Merge Join — тем же запросом, без `LATERAL`:

```sql
SET enable_nestloop = off; SET enable_mergejoin = off;   -- Hash Join
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
SELECT * FROM j_users u JOIN j_orders o ON o.user_id = u.id WHERE u.id < 4;
RESET ALL;
SET enable_hashjoin = off; SET enable_nestloop = off; SET enable_seqscan = off;   -- Merge Join
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
SELECT * FROM j_users u JOIN j_orders o ON o.user_id = u.id WHERE u.id < 4;
RESET ALL;
```

```text
 Hash Join (actual rows=6 loops=1)
   Hash Cond: (o.user_id = u.id)
   ->  Seq Scan on j_orders o (actual rows=24 loops=1)
   ->  Hash (actual rows=3 loops=1)
         ->  Seq Scan on j_users u (actual rows=3 loops=1)
               Filter: (id < 4)

 Merge Join (actual rows=6 loops=1)
   Merge Cond: (u.id = o.user_id)
   ->  Index Only Scan using j_users_pkey on j_users u (actual rows=3 loops=1)
         Index Cond: (id < 4)
   ->  Index Scan using j_orders_user_id_idx on j_orders o (actual rows=7 loops=1)
```

Хеш построен по `users` — 3 строки, — а заказы прочитаны все 24. Merge Join взял из индекса по
`user_id` только 7 заказов: у седьмого `user_id = 4`, пользователи 1–3 к этому моменту кончились, и
сравнивать его стало не с кем. Остальные входы из таблицы — те же запросы на других данных:

## 3. Сортировка и `work_mem`: тот самый K-way merge

`ORDER BY amount` по двум миллионам строк при `work_mem = 4MB`:

```text
 Sort  (cost=298712.69..303712.69 rows=2000000 width=6) (actual rows=2000000 loops=1)
   Sort Key: amount
   Sort Method: external merge  Disk: 21560kB
   Buffers: shared hit=345 read=14364, temp read=5381 written=5401
 Execution Time: 964.445 ms
```

`external merge` — это [K-way merge](k-way-merge.md) собственной персоной: данные нарезаны на
куски по `work_mem`, каждый отсортирован в памяти и сброшен на диск, затем куски слиты. Тот же
алгоритм, который ты писал в пакете `kwaymerge`, только вместо `k` отсортированных массивов —
`k` временных файлов.

Поднимем `work_mem` до 256 МБ:

```text
   Sort Method: quicksort  Memory: 80403kB
 Execution Time: 596.779 ms
```

`Sort Method` переключился на `quicksort` — всё влезло в память, диск не понадобился. 964 мс →
597 мс.

## 4. Почему `LIKE 'abc%'` идёт по индексу, а `LIKE '%abc'` — нет

Это не причуда Postgres, а прямое следствие того, что B-дерево **упорядочено**. Посмотри, во
что планировщик превратил условие:

```text
 Index Scan using users_email_idx on users  (...)
   Index Cond: ((email >= 'user000123'::text) AND (email < 'user000124'::text))
   Filter: (email ~~ 'user000123%'::text)
 Execution Time: 0.022 ms
```

Он **переписал `LIKE` в диапазон**. Все строки с данным префиксом лежат в отсортированном
порядке подряд — между самим префиксом и следующим за ним значением. Префикс — это
непрерывный отрезок, а непрерывный отрезок B-дерево отдаёт за `O(log n)` плюс длина ответа.
Та же мысль, что в [Trie](trie-structure.md): по префиксу ищут структуры, упорядоченные по
префиксу.

> ⚠️ **Работает это только в C-локали — а лаборатория создана именно в ней.** Порядок «между
> префиксом и следующим значением» — это побайтовый порядок. В базе с коллацией вроде
> `en_US.UTF-8` строки упорядочены по правилам языка, и планировщик не может превратить
> префикс в диапазон. Проверено на той же таблице, пересозданной с коллацией `en-US`:
>
> | Индекс | План | Время |
> |---|---|---|
> | обычный `(email)` | **Seq Scan** — индекс есть, но не используется | 13.4 мс |
> | `(email text_pattern_ops)` | Index Only Scan, условие `~>=~ … ~<~` | 0.064 мс |
>
> `text_pattern_ops` строит индекс в побайтовом порядке специально под `LIKE 'abc%'`. Цена —
> для `ORDER BY email` планировщик по-прежнему берёт **обычный** индекс, так что на боевой базе
> нужны часто оба. Первое, что стоит проверить, когда префиксный поиск на проде «почему-то»
> медленный: `SHOW lc_collate;`.

Суффикс такого свойства не имеет — строки, кончающиеся на `@corp.io`, разбросаны по всему
дереву:

```text
 Seq Scan on users  (cost=0.00..4562.00 rows=64646 width=4) (actual rows=66667 loops=1)
   Filter: (email ~~ '%@corp.io'::text)
 Execution Time: 14.054 ms
```

Что с этим делают инженеры — три приёма, все сводятся к «сделай искомое префиксом»:

- **индекс по обратной строке**: `CREATE INDEX ON users (reverse(email))`, искать
  `reverse(email) LIKE reverse('%@corp.io')` — суффикс становится префиксом;
- **триграммный индекс** `pg_trgm` + GIN: строка режется на трёхбуквенные куски, и по ним
  строится обратный индекс (inverted index) — тот же принцип, что у поисковых движков;
- **вынести в отдельный столбец**: домен почты как поле `email_domain` с обычным индексом.
  Скучно, и почти всегда правильно.

## 5. Весь выбор стоит на оценке числа строк

Планировщик не видит данных — он видит **статистику**. И у него есть допущение, которое в
реальных схемах почти всегда ложно: **столбцы независимы**.

В лаборатории `region` жёстко определяется городом: `city-042` всегда лежит в `r4`. Спросим обе
колонки сразу:

```text
 Seq Scan on users  (cost=0.00..5062.00 rows=195 width=4) (actual rows=1992 loops=1)
   Filter: ((city = 'city-042'::text) AND (region = 'r4'::text))
```

**`rows=195` против `actual rows=1992`** — промах на порядок. (Оценка у тебя будет чуть
другой — `ANALYZE` строит её по случайной выборке строк, — но останется около двухсот против
двух тысяч факта.) Арифметика планировщика:
«город отсекает до 1/100, регион — до 1/10, вместе 1/1000». На самом деле второе условие не
отсекает ничего: оно уже следует из первого.

Здесь запрос простой, и промах безвреден. Но представь такой узел **внутри** соединения:
планировщик думает, что получит 195 строк, выбирает под них nested loop — а приходит две
тысячи, и каждая идёт в индекс отдельным обращением. Так «внезапно» деградируют запросы,
которые год работали нормально.

Лечится встроенной **расширенной статистикой**:

```sql
CREATE STATISTICS users_city_region (dependencies, ndistinct) ON city, region FROM users;
ANALYZE users;
```

```text
 Seq Scan on users  (cost=0.00..5062.00 rows=1987 width=4) (actual rows=1992 loops=1)
```

`rows=1987` против факта `1992` — планировщик узнал про функциональную зависимость между
столбцами и стал точен. Это первое, что стоит проверять, когда план выглядит бессмысленно:
**не ошибка выбора, а ошибка оценки**.

## 🧠 Почему планировщик выбирает именно так

Планировщик — это **оптимизатор с моделью стоимости**. Он перебирает планы и для каждого
считает число, а потом берёт минимальное. Числа складываются из констант, описывающих
железо:

| Константа | По умолчанию | Смысл |
|---|---|---|
| `seq_page_cost` | 1.0 | прочитать страницу подряд |
| `random_page_cost` | **4.0** | прочитать страницу по случайному адресу |
| `cpu_tuple_cost` | 0.01 | обработать одну строку |
| `cpu_index_tuple_cost` | 0.005 | обработать одну запись индекса |

Вот и вся «магия»: `random_page_cost = 4.0` означает «случайное чтение вчетверо дороже
последовательного». Для вращающегося диска, где головка физически переезжает, это правда. **Для
SSD — нет**, там разница ближе к 1.1.

То есть дефолт Postgres описывает железо, которого у тебя, скорее всего, нет. Проверим на том
самом соединении, где merge join обыгрывал hash join:

```sql
SET random_page_cost = 1.1;   -- «у нас SSD»
```

| `random_page_cost` | Что выбрал для `orders` | Время |
|---|---|---|
| 4.0 (дефолт) | `Seq Scan` | 703 мс |
| 1.1 | `Index Only Scan` | **465 мс** |

Полтора раза, **без единого изменения в запросе, схеме и индексах** — поменяли одну
константу в модели стоимости. Это и есть та самая константа, которую прячет `O(...)`, только
здесь она вынесена в конфиг и её можно потрогать руками. Если хочешь одну мысль из всей
главы — вот она: **асимптотика выбирает семейство алгоритмов, константы выбирают победителя
внутри семейства**, и Postgres честно показывает обе половины этого выбора.

> ⚠️ Менять `random_page_cost` глобально на бою — решение уровня «поменять GOGC»: обоснованное,
> но не вслепую. Сначала убедись, что данные реально на SSD и что база помещается в память, а
> потом меняй и **меряй**, а не наоборот.

## ⚙️ Цена на практике: индекс не бесплатен

Книжный B-дерево-индекс «ускоряет поиск». Прод добавляет три пункта счёта:

- **Запись.** Каждый `INSERT` пишет во **все** индексы таблицы, и почти каждый `UPDATE` —
  тоже: новая версия строки получает новые записи в индексах. Исключение — HOT-обновление
  (heap-only tuple), когда не меняется ни один индексированный столбец и на странице есть
  место; тогда индексы не трогаются. Отсюда неочевидное следствие: лишний индекс по часто
  меняемому столбцу ломает HOT для всех обновлений. Пять индексов — это пятикратная работа на
  вставку плюс WAL; классическая беда таблицы, в которую пишут тысячи строк в секунду, а
  индексов на ней десяток «на всякий случай».
- **Место.** Индекс — это отдельная копия ключей. На `orders` три индекса (первичный ключ,
  `user_id`, `created_at`) весят 103 МБ при 115 МБ самой таблицы — почти столько же, сколько
  данные, и всё это конкурирует за кэш.
- **Раздувание (bloat).** Postgres не удаляет строки на месте, а помечает мёртвыми; страницы
  освобождает `VACUUM`. Таблица с интенсивными обновлениями и без нормального автовакуума
  распухает, и по ней начинают читаться страницы, где живых строк почти нет.

Неиспользуемые индексы видно прямо из базы:

```sql
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes WHERE idx_scan = 0 ORDER BY relname;
```

`idx_scan = 0` за месяц работы — индекс только берёт плату за запись и не приносит ничего.
Одна оговорка перед удалением: индекс первичного ключа или `UNIQUE` может ни разу не
использоваться для поиска и всё равно быть нужным — он обеспечивает уникальность.

## ⚠️ Типичные ошибки

1. **Читать `cost` как миллисекунды.** Это условные единицы модели. Сравнивать их можно между
   планами одного запроса, а переводить во время — нельзя.
2. **`EXPLAIN` без `ANALYZE`** показывает только оценку, а вся диагностика — в расхождении
   оценки с фактом. (Но помни: `EXPLAIN ANALYZE` **действительно выполняет** запрос. Для
   `UPDATE`/`DELETE` — внутри транзакции с `ROLLBACK`.)
3. **Мерить по времени, а не по буферам.** Время зависит от прогретости кэша; повтори запрос
   дважды и сравни — второй раз будет быстрее без всяких изменений. Живой пример — запрос на 80%
   строк в разделе 1: по времени навязанный индекс быстрее, по буферам — нет.
4. **Навесить индекс на неселективное условие.** Поле с тремя значениями и перекосом 80/15/5
   индексом не лечится — см. раздел 1.
5. **Игнорировать `loops=N`.** Во вложенном узле `actual rows` и время показаны **в среднем
   на одну итерацию** — чтобы получить итог, умножай на `loops`. А вот `Buffers` — уже **сумма**
   по всем итерациям: в nested loop из раздела 2 внутренний узел с `loops=200000` показывает
   `hit=600001`, то есть по три страницы на итерацию, а не шестьсот тысяч на каждую.
6. **`SET enable_hashjoin = off` в проде.** Это инструмент диагностики, а не настройка.
   Планировщик подсказывает симптом, чинить надо причину: статистику, индекс или сам запрос.

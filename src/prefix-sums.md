## 🧭 Откуда берутся префиксы: выведем их сами

Правило из «Запомни» — «кусок с суммой k = пара префиксов с разностью k» — не фокус. Оно
вылезает само из обычного перебора. Проследим на задаче.

> **Задача.** Дан массив целых `nums` (числа любого знака) и число `k`. Сколько непрерывных
> кусков имеют сумму ровно `k`?

В лоб: для каждого начала `i` идём вправо, копим сумму и на каждом шаге сравниваем её с `k`.
Возьмём маленький пример `nums = [2, 4, −1, 3]`, `k = 3` и выпишем все суммы перебора — по
строке на каждое начало:

<div class="algo-fig" data-fig="array" data-array="2,4,−1,3; 2@0,6@0-1,5@0-2,8@0-3; _,4@1,3!@1-2,6@1-3; _,_,−1@2,2@2-3; _,_,_,3!@3" data-rows="nums; i = 0; i = 1; i = 2; i = 3" data-index-label="j" data-caption="Строка i — суммы кусков nums[i..j]; зелёные — равные k = 3. Наведи на сумму — загорится её кусок"></div>

Ровно `3` дали два куска: `[4, −1]` и `[3]`. Теперь сравни строки сумм. Строка `i = 1` — это
строка `i = 0` минус 2: `6 − 2 = 4`, `5 − 2 = 3`, `8 − 2 = 6`. Строка `i = 2` — она же минус 6,
`i = 3` — минус 5. Перебор насчитал десять сумм, но вся информация лежит в строке `i = 0`.
Остальные — она же со сдвигом.

Строка `i = 0` — суммы «с самого начала массива», то есть префиксы. Любой кусок — разность
двух префиксов: `[4, −1]` = `5 − 2`, `[3]` = `8 − 5`. Значит, на шаге, где сумма с начала стала
`5`, вопрос «сколько кусков с суммой 3 кончается здесь» превращается в «сколько раз раньше
сумма с начала была `5 − 3 = 2`». На это отвечает хеш-таблица за O(1), и перебирать начала
больше не нужно. Чтобы и кусок от самого начала был разностью, префиксом считают и пустое
начало: его сумма — `0`.

**Префикс — это счётчик вроде `http_requests_total` над массивом: хранишь «всего с начала»,
а сумма любого куска — разность двух показаний.**

Это префиксные суммы (prefix sums); в паре с хеш-таблицей они решают задачу за O(n) вместо
O(n²). Первую половину вывода — сумму отрезка как разность двух показаний — виджет ниже
показывает на запросах к отрезкам. Вторую — хеш-таблицу прошлых префиксов — с кодом и трассой
разбирает [«📝 Разбор задачи»](#-разбор-задачи).

## 🎬 Визуализация

> 💡 **Интерактивная демонстрация.** Сверху — массив, под ним ряд `prefix`: на ячейку длиннее,
> `prefix[i]` — сумма первых `i` элементов. Сначала он строится одним проходом, затем каждый
> запрос `[l, r]` отвечается одним вычитанием: зелёная ячейка минус красная. Под холстом — строка шага и переменные, ниже — ползунок шагов (или ←/→ на клавиатуре) и код с подсветкой строки. Можно подставить свой
> массив и запросы в формате `l:r` через запятую и нажать «⟲ Запустить» — или выбрать готовый
> граничный случай под полем ввода.

## ⚡ Шаблон для собеседования

```go
// 1) Сумма отрезка [l, r] за O(1) после O(n) предподсчёта
prefix := make([]int, len(nums)+1) // prefix[0] = 0 — пустой префикс
for i, v := range nums {
    prefix[i+1] = prefix[i] + v
}
rangeSum := prefix[r+1] - prefix[l]

// 2) Сколько подмассивов с суммой k — O(n), числа любого знака
seen := map[int]int{0: 1} // пустой префикс «встречен» до начала
sum, count := 0, 0
for _, v := range nums {
    sum += v
    count += seen[sum-k] // сначала ищем прошлые префиксы...
    seen[sum]++          // ...потом запоминаем текущий
}
```

1. `prefix[i]` — сумма первых `i` элементов, поэтому массив на ячейку длиннее входа;
2. отрезок `[l, r]` — «первые `r+1`» минус «первые `l`»;
3. подмассив, кончающийся на текущем элементе, имеет сумму `k` ровно тогда, когда какой-то
   **прошлый** префикс равен `sum − k`: хеш-таблица отвечает «сколько таких было» за O(1);
4. `{0: 1}` — пустой префикс: без него потеряются подмассивы, начинающиеся с индекса 0.

## 📖 Разбор

**Префиксная сумма** — массив `prefix`, где `prefix[i]` равен сумме первых `i` элементов:
`prefix[0] = 0`, `prefix[i+1] = prefix[i] + nums[i]`. Сумма любого отрезка выражается через
две его ячейки: `sum(l..r) = prefix[r+1] − prefix[l]`. Предподсчёт — один проход O(n),
каждый запрос — O(1).

Длина `n+1`, а не `n`, — сознательный выбор. Вариант «`prefix[i]` — сумма `nums[0..i]`»
тоже встречается, но в нём отрезок с начала массива — особый случай
(`prefix[r]` вместо `prefix[r] − prefix[l−1]`), и именно на нём живёт ошибка на единицу
(off-by-one: граница отрезка сдвинута на один элемент).
Лишняя ячейка с нулём делает формулу единой.

Из той же формулы — суммы по обе стороны от `i`: слева `prefix[i]`, справа
`prefix[n] − prefix[i+1]`. Их равенство и ищет Find Pivot Index (724).

### Подсчёт подмассивов: префикс + хеш-таблица

Сумма подмассива `[i..j]` — это `prefix[j+1] − prefix[i]`. Значит, «подмассив с суммой
`k`, кончающийся в `j`» — это «прошлый префикс, равный `prefix[j+1] − k`». Идём слева
направо с текущей суммой и храним в хеш-таблице, **сколько раз** встречался каждый
префикс. Почему прошлый префикс ищут в таблице раньше, чем записывают туда текущий, разберём в «🧠»
через инвариант — утверждение, верное перед каждой итерацией цикла. Та же схема решает целое семейство задач — меняется только,
что именно хранить и как сравнивать:

| Задача | Что считаем | Что храним в map | Особенность |
|---|---|---|---|
| сумма ровно `k` (число) | `sum` | префикс → сколько раз | заводим `{0: 1}` |
| делится на `k` | `sum % k` (остаток) | остаток → сколько раз | остаток в Go бывает отрицательным |
| поровну 0 и 1 (длина) | `+1` за 1, `−1` за 0 | сумма → **первый** индекс | заводим `{0: −1}`: баланс 0 — на индексе −1, до начала |
| сумма ровно `k` (длина) | `sum` | префикс → **первый** индекс | самый длинный — от первого вхождения |

**Самый длинный кусок — по первому индексу.** Возьми `[0, 1, 1, 0, 1, 1, 1, 0]` и считай баланс:
`+1` за единицу, `−1` за ноль. После каждого элемента он равен `−1, 0, 1, 0, 1, 2, 3, 2`. Баланс
повторился — значит, между двумя его вхождениями нулей и единиц поровну. Чтобы кусок был самым
длинным, левый край нужен как можно левее, поэтому запоминаем **первый** индекс каждого баланса
и не перезаписываем: `{0: −1, −1: 0, 1: 2, 2: 5, 3: 6}`. Длина куска — текущий индекс минус
первый индекс того же баланса: баланс 0 «до начала» стоит на индексе `−1`, и кусок `[0..3]`
получает длину `3 − (−1) = 4` — это ответ.

**Кратно `k` — по остаткам.** Сумма куска делится на `k` ровно тогда, когда два его префикса
дают одинаковый остаток от деления на `k`. Например, на `[4, 5, 0, −2, −3, 1]`, `k = 5` префиксы
после первого и второго числа — 4 и 9, остаток у обоих 4, и кусок между ними `[5]` делится на 5. Значит, в таблице считаем остатки, а не суммы.
Остаток в Go берёт знак делимого: `-2 % 5 == -2`, поэтому отрицательный остаток доводят до
`[0, k)`, прибавив `k`.

<details class="algo-details">
<summary>Если застрял: код подсчёта по остаткам</summary>

```go
func countDivisible(nums []int, k int) int {
    seen := make([]int, k) // остатки лежат в [0, k) — хватает среза
    seen[0] = 1
    sum, count := 0, 0
    for _, v := range nums {
        sum += v
        r := sum % k
        if r < 0 {
            r += k // в Go остаток берёт знак делимого: -2 % 5 == -2
        }
        count += seen[r] // равные остатки — разность делится на k
        seen[r]++
    }
    return count
}
```

</details>

### Разностный массив: обратная операция

Если префиксная сумма превращает массив в «накопленный итог», то **разностный массив**
делает обратное: `diff[i] = nums[i] − nums[i−1]` (и `diff[0] = nums[0]`). На `[3, 5, 5, 2]` это
`diff = [3, 2, 0, −3]`: накопи его — получишь `3, 5, 5, 2` обратно. Префиксная сумма
разностей возвращает исходный массив — это телескопическая сумма: в `(b − a) + (c − b)` средние `b` сокращаются, остаётся `c − a`. Отсюда трюк: чтобы
прибавить `d` ко всем элементам `[l, r]`, достаточно изменить две разности: `nums[l]` стал на
`d` больше своего соседа слева, а `nums[r+1]` — на `d` меньше своего. Прибавим 4 к `[1..2]`:
`diff = [3, 6, 0, −7]`, накопленное — `3, 9, 9, 2`. В `applyRangeAdds` исходный массив — нули,
поэтому `diff` стартует нулями:

```go
func applyRangeAdds(n int, updates [][3]int) []int {
    diff := make([]int, n+1) // лишняя ячейка — для обновления до последнего индекса
    for _, u := range updates {
        diff[u[0]] += u[2]
        diff[u[1]+1] -= u[2]
    }
    res := make([]int, n)
    run := 0
    for i := 0; i < n; i++ {
        run += diff[i]
        res[i] = run
    }
    return res
}
```

Каждое обновление — O(1) вместо O(длины отрезка), итог собирается одним проходом.
Это тот же приём, что у сканирующей прямой из [слияния интервалов](merge-intervals.md) — прохода по событиям во времени:
«на начале +1, после конца −1, потом накопить» — разностный массив, только по
событиям, а не по индексам.

В виджете под массивом есть строка «если собрать сейчас» — префиксные суммы текущего `diff`.
Смотри на неё на двух шагах каждого обновления: после `diff[l] += d` прибавку получают **все**
клетки от `l` до конца, а после `diff[r+1] −= d` хвост возвращается на место, и прибавка
остаётся ровно на отрезке `[l..r]` — «ступенька» из двух записей:

### Двумерный префикс

Сумма любого прямоугольника матрицы за O(1) после одного прохода — задача 304 и
`MatrixRegionSums`.

<details class="algo-details">
<summary>Двумерный префикс: построение и запрос</summary>

`P[i][j]` — сумма прямоугольника от `(0, 0)` до `(i−1, j−1)`. Строится включениями-
исключениями: прямоугольник «сверху» плюс «слева» считают верхний левый угол дважды,
поэтому его вычитают:

```go
P[i+1][j+1] = m[i][j] + P[i][j+1] + P[i+1][j] - P[i][j]
```

Запрос прямоугольника `(r1, c1)–(r2, c2)` — та же логика в обратную сторону: большой
прямоугольник минус полоса сверху минус полоса слева плюс угол, вычтенный дважды:

```go
sum := P[r2+1][c2+1] - P[r1][c2+1] - P[r2+1][c1] + P[r1][c1]
```

</details>

### Произведение всех, кроме себя

Произведение всех элементов, кроме `i`-го, без деления: префикс слева на суффикс справа —
задача 238 и `ProductExceptSelf`.

<details class="algo-details">
<summary>Произведение всех, кроме себя: почему без деления и как в два прохода</summary>

Ответ для `i` — произведение **префикса** слева от `i` на произведение **суффикса**
справа. Деление по условию запрещено, и не зря: «общее произведение / nums[i]» ломается на
нуле (нужен разбор: нулей нет, один, два и больше), а общее произведение может переполниться,
даже когда каждый ответ помещается. Два прохода: первый кладёт в `res` префиксы, второй справа налево
домножает на суффикс, который копится в одной переменной. На `[1, 2, 3, 4]` префиксы слева —
`1, 1, 2, 6`, суффиксы справа — `24, 12, 4, 1`, ответ — `[24, 12, 8, 6]`.

</details>

### Кадане — вернись после главы о ДП

Самая большая сумма куска подряд за O(n) и O(1) памяти: текущий префикс минус наименьший из
прошлых — задача 53 и `MaxSubarraySum`. В главе о динамическом программировании та же задача
решается как ДП; сравнить два взгляда удобнее, когда пройдёшь обе.

<details class="algo-details">
<summary>Кадане через префиксы и сложность всех приёмов главы</summary>

Максимальная сумма подмассива, кончающегося в `j`, — это `prefix(j+1)` минус
**наименьший** из более ранних префиксов. Значит, достаточно идти слева направо и
держать минимум префиксов:

```go
func maxSubarraySum(nums []int) int {
    sum, minPrefix, best := 0, 0, nums[0]
    for _, v := range nums {
        sum += v
        best = max(best, sum-minPrefix) // лучший подмассив, кончающийся здесь
        minPrefix = min(minPrefix, sum) // обновляем ПОСЛЕ: подмассив не может быть пустым
    }
    return best
}
```

Классическая запись Кадане — `cur = max(v, cur+v)` — то же самое другими словами: `cur` — это
`sum − minPrefix`, и он уходит в минус ровно тогда, когда `sum` опустился ниже прежнего минимума, —
тогда и «начинаем заново». В главе
[«Динамическое программирование»](dynamic-programming.md) эта задача решается как ДП;
здесь видно, почему у неё O(1) памяти: всё прошлое сжимается в одно число — минимум. На
`[−2, 1, −3, 4, −1, 2, 1, −5, 4]` ответ — 6 (кусок `[4, −1, 2, 1]`).

#### Сложность

| Операция | Время | Память |
|---|---|---|
| Построить префикс | O(n) | O(n) |
| Сумма отрезка | O(1) | — |
| Подсчёт подмассивов (sum / mod / баланс) | O(n) | O(n) на map; для остатков — O(k) срезом |
| Разностный массив: u обновлений + сборка | O(u + n) | O(n) |
| Двумерный префикс: построить / запрос | O(R·C) / O(1) | O(R·C) |
| Кадане | O(n) | O(1) |

</details>

### Инвариант прохода «префикс + хеш-таблица»

Перед обработкой элемента `j` выполнено: `sum` — сумма `nums[0..j−1]`, а `seen[p]` — сколько
раз среди префиксов `prefix[0], …, prefix[j]` встретилось значение `p`. Шаг сохраняет
инвариант: прибавили `nums[j]` к `sum`, посчитали пары с новым концом, добавили новый
префикс. Каждый непустой подмассив `[i..j]` посчитан ровно один раз — на шаге своего правого
конца `j`, когда его левая граница `i` представлена в `seen` префиксом `prefix[i]`.

### Пустой префикс — не костыль

`{0: 1}` в инициализации выглядит как особый случай, но это просто честная запись
`prefix[0] = 0` — ячейки, которую цикл никогда не кладёт сам, потому что она случилась до
первого элемента. Та же ячейка превращает `prefix[r+1] − prefix[l]` в формулу без
исключений для `l = 0`. Когда хранится **индекс** первого вхождения (самый длинный
подмассив), у пустого префикса индекс `−1`: отрезок от него до `j` имеет длину `j − (−1) = j + 1`.

### Почему для суммы работает, а для максимума нет

Приём работает для любой операции, у которой есть **обратная**: сложение (вычитание),
XOR (он сам себе обратный — префиксный XOR отвечает на «XOR отрезка» так же),
умножение ненулевых чисел (деление). Для максимума, минимума и НОД обратной нет — отсюда
граница применимости из карточки «Когда НЕ применять». Для них идемпотентность (`max(a, a)
= a`) даёт другой приём: максимум отрезка можно взять по двум перекрывающимся кускам — общий
элемент ответ не испортит. На этом стоит [sparse table](sparse-table-structure.md), а для
изменяемых данных — [дерево отрезков](segment-tree.md).

### Разностный массив восстанавливает исходный

Префиксная сумма разностей телескопируется:
`diff[0] + diff[1] + … + diff[i] = nums[0] + (nums[1] − nums[0]) + … + (nums[i] − nums[i−1]) = nums[i]`.
Прибавка `d` к отрезку `[l, r]` меняет ровно две разности: `nums[l] − nums[l−1]` выросла на
`d`, `nums[r+1] − nums[r]` уменьшилась на `d`, внутри отрезка соседи выросли одинаково и
разность не изменилась. Поэтому две записи в `diff` — точное, а не приближённое
представление обновления.

## ⚙️ Цена на практике

### Счётчики Prometheus — это префиксные суммы

Счётчик вроде `http_requests_total` только растёт и хранит «всего с запуска процесса»,
а не «за последнюю минуту». Это префиксная сумма по времени: число запросов за любой
интервал — разность двух отсчётов, `increase(x[5m])` — примерно «сейчас минус пять минут
назад». Поэтому экспортеру не нужно знать, какие окна тебе понадобятся: он хранит префикс,
а окно выбирается при запросе — ровно как `prefix[r+1] − prefix[l]`. Единственная тонкость —
рестарт процесса обнуляет счётчик, и `rate`/`increase` распознают сброс по тому, что
значение уменьшилось. Это объяснение, а не замер: в книге Prometheus не поднимается.

### Ограниченные ключи — срез вместо map

Когда ключи известны заранее (остаток в `[0, k)`, баланс в `[−n, n]`), `map` меняется на срез
без хеширования — как `[256]int` вместо `map[byte]int` в [замере главы про скользящее
окно](sliding-window.md#-цена-на-практике); так написан `countDivisible` под «Если застрял» выше, а для суммы
ровно `k` ключи не ограничены, и остаётся `map`.

### Изменяемый массив — Фенвик, неизменяемый — префикс

`prefix` — снимок. Одна правка `nums[i]` меняет `prefix[i+1..n]`: O(n) на обновление. Если
правок много, нужно [дерево Фенвика](fenwick-tree.md) — те же префиксные суммы,
но O(log n) и на обновление, и на запрос. Обратное тоже верно: если данные не меняются,
Фенвик и дерево отрезков — лишняя цена. В главе [«Когда алгоритм не нужен»](skip-the-work.md)
это замерено: на неизменных данных префикс отвечает за 1.6 нс, дерево отрезков — за 101 нс.

### Память и переполнение

Двумерный префикс занимает `(R+1)·(C+1)` целых: для матрицы 10 000 × 10 000 это 10⁸ `int`
по 8 байт — 800 МБ. Тот же приём в компьютерном зрении называется *integral image*: на нём
детектор Виолы — Джонса считает суммы прямоугольных признаков за O(1).

Префикс копит сумму **всего** массива, а не отрезка, поэтому переполняется раньше любого
отрезка: миллион значений до 10⁴ дают около 5·10⁹, в `int32` это уже не влезает. В Go
переполнение оборачивается: старшие биты отбрасываются, и `3·10⁹` становится `−1 294 967 296`.
Любопытно, что **разность** двух префиксов при этом остаётся точной, если сама сумма отрезка
влезает в `int32`: ошибки двух префиксов взаимно гасятся. А вот **сравнивать** сами префиксы
уже нельзя: минимум префиксов в [Кадане](#кадане--вернись-после-главы-о-дп) или их сортировка
дадут неверный ответ.
Проще всего хранить префиксы в `int` — на 64-битных платформах это 64 бита.

<details>
<summary>Замер: что именно ломается при переполнении</summary>

Миллион случайных чисел от 0 до 10⁴, префиксы в `int32`: полная сумма 4 999 360 543
превратилась в 704 393 247, все 100 000 проверенных сумм отрезков длиной до тысячи вышли
точными, а «минимальный префикс» нашёлся на позиции 429 721 вместо 0 — хотя все числа
неотрицательны и настоящий минимум — пустой префикс. В C и C++ знаковое переполнение —
неопределённое поведение, и там не гарантирована даже точность разности.

</details>

## ⚠️ Типичные ошибки

1. **`prefix` длиной n** и особый случай для `l = 0` — классическая ошибка на единицу.
   Бери длину `n+1` с нулём в начале.
2. **Забыли `{0: 1}`** — теряются все подмассивы, начинающиеся с индекса 0.
3. **`seen[sum]++` до поиска** — при `k = 0` каждый префикс находит сам себя, ответ
   завышается на n. При `k ≠ 0` баг молчит.
4. **Отрицательный остаток**: в Go `-7 % 5 == -2`, а не 3. Два префикса с остатками −2 и 3
   равны по модулю 5 — их разность делится на 5, — но попадут в разные ключи. Приводи: `if r < 0 { r += k }`.
5. **Не то вхождение**: для самого длинного подмассива нужен **первый** индекс суммы
   (перезаписывать нельзя), для числа подмассивов — **количество**, а не индекс.
6. **Префикс для меняющихся данных** — O(n) на каждую правку. Это работа для Фенвика.
7. **Произведение через деление** — на нуле нужен разбор случаев, а общее произведение может
   переполниться; префикс и суффикс обходятся без обоих.

## 📝 Разбор задачи

Перебор и наблюдение — в [«🧭 Откуда берутся префиксы»](#-откуда-берутся-префиксы-выведем-их-сами):
строки перебора — одна и та же строка префиксов со сдвигом, и кусок с суммой `k` — пара
префиксов с разностью `k`. Здесь — код и трасса той же задачи на входе побольше.

> **Задача.** Дан массив целых `nums` (числа любого знака) и число `k`. Сколько
> **непрерывных** подмассивов имеют сумму ровно `k`?
> Пример: `nums = [1, 2, −2, 3, −1]`, `k = 3` → **4**: `[1, 2]`, `[2, −2, 3]`, `[3]` и весь
> массив.

**Почему не окно.** Для неотрицательных чисел это было бы скользящее окно: сумма
растёт при расширении и падает при сужении. Здесь есть `−2` и `−1`: расширение может
уменьшить сумму, и правило «сумма больше нужной — сдвинь левый край» ведёт мимо ответа. Нужен другой
способ не перебирать левые границы.

**Оптимум — O(n) времени, O(n) памяти.**

```go
func countSubarrays(nums []int, k int) int {
    seen := map[int]int{0: 1} // пустой префикс
    sum, count := 0, 0
    for _, v := range nums {
        sum += v
        count += seen[sum-k] // столько подмассивов с суммой k кончается здесь
        seen[sum]++
    }
    return count
}
```

Прогони его. Под массивом — лента префиксов: все суммы «от начала до элемента», которые уже
лежат в `seen`, и текущая `sum` в янтарной пунктирной рамке. На шаге поиска зелёным загораются
прошлые префиксы, равные `sum − k`: от каждого из них до текущего элемента сумма ровно `k`. Сами
эти подмассивы подсвечены в массиве, рамка — их начала:

<div class="algo-viz" data-viz="prefix-sum-hash" data-array="1,2,-2,3,-1" data-k="3"></div>

**Трассировка** на `[1, 2, −2, 3, −1]`, `k = 3`:

| `j` | `v` | `sum` | `sum − k` | `seen` до обновления | прибавка | `count` |
|---|---|---|---|---|---|---|
| — | — | 0 | — | `{0:1}` | — | 0 |
| 0 | 1 | 1 | −2 | `{0:1}` | 0 | 0 |
| 1 | 2 | 3 | 0 | `{0:1, 1:1}` | 1 — `[0..1]` | 1 |
| 2 | −2 | 1 | −2 | `{0:1, 1:1, 3:1}` | 0 | 1 |
| 3 | 3 | 4 | 1 | `{0:1, 1:2, 3:1}` | 2 — `[1..3]`, `[3..3]` | 3 |
| 4 | −1 | 3 | 0 | `{0:1, 1:2, 3:1, 4:1}` | 1 — `[0..4]` | 4 |

Ответ 4 — те же четыре куска, что в условии. Пустой префикс сработал дважды (`j = 1` и `j = 4`) — это
оба подмассива, начинающиеся с индекса 0; без `{0: 1}` ответ был бы 2. А на `j = 3` одно
значение `1` встречалось дважды (после индексов 0 и 2) — отсюда сразу два подмассива.

## 🔗 Связанные шаблоны

**Не спутай с соседом** (вся таблица — в [руководстве по выбору](pattern-selection-guide.md#путаемые-пары-что-обязано-быть-верно)):

- если числа неотрицательны, расширение куска не уменьшает сумму, а нужен один самый короткий или длинный кусок подряд с порогом суммы — [Скользящее окно](sliding-window.md), а не Префиксные суммы: окно даёт ответ за один проход без лишней памяти, а префиксы хранят n сумм.
- если в массиве есть отрицательные числа, а спрашивают, сколько кусков подряд дают сумму ровно k — Префиксные суммы, а не [Скользящее окно](sliding-window.md): отрицательное число ломает правило «расширил — сумма выросла», и окно сдвинет левый край мимо ответа.
- если массив между запросами суммы не меняется, а запросов много — Префиксные суммы, а не [Дерево Фенвика](fenwick-tree.md): Фенвик платит O(log n) за запрос ради обновлений, которых нет, а префикс отвечает за O(1).
- если массив меняется между запросами суммы, точечные правки идут вперемешку с запросами — [Дерево Фенвика](fenwick-tree.md), а не Префиксные суммы: одна правка меняет весь хвост префиксов за O(n), а Фенвик и обновляет, и отвечает за O(log n).

- **[Sliding Window](sliding-window.md)** — для неотрицательных чисел решает «один отрезок с
  условием» без лишней памяти; префиксы начинаются там, где окно ломается.
- **[Хеш-таблица](hash-table-structure.md)** — вторая половина связки «префикс + map».
- **[Дерево Фенвика](fenwick-tree.md)** — префиксные суммы для изменяемого массива.
- **[Sparse Table](sparse-table-structure.md)** и **[дерево отрезков](segment-tree.md)** —
  для операций без обратной (min, max, НОД).
- **[Merge Intervals](merge-intervals.md)** — сканирующая прямая «+1 на начале, −1 после
  конца» — это разностный массив по событиям.
- **[Dynamic Programming](dynamic-programming.md)** — Кадане как ДП; здесь — как префиксы.

## 1. Bloom-фильтр — «точно нет / возможно да»

Вернёмся к нашему краулеру. Ему нужно отвечать на один вопрос миллиарды раз: **«этот URL я уже
видел?»** Если да — не обходим повторно. Точное хеш-множество из всех URL не помещается в память.

**Идея Bloom-фильтра — гениально простая: не хранить URL вообще.** Заводим длинную полоску бит
(скажем, `m` штук), сначала все нули. И берём несколько (`k`) хеш-функций. Дальше — как отметки
маркером:

- **Добавить URL** («я его обошёл») — прогоняем URL через все `k` хешей. Каждый хеш показывает
  на какой-то бит. **Ставим эти `k` бит в 1** — как поставить `k` галочек.
- **Проверить URL** («видел ли?») — снова считаем те же `k` хешей и смотрим на те же биты:
  - если **хоть один** бит = 0 — этот URL мы **точно** не добавляли (мы бы поставили галочку, а её нет);
  - если **все `k` бит = 1** — URL, **скорее всего**, видели… но, может, эти галочки поставили *другие* URL.

Вот и вся гарантия, которую надо запомнить:

> **«Точно нет» или «возможно да».** Промахнуться в сторону «нет» фильтр **не может**: если URL
> добавляли, все его биты стоят. А вот сказать «да» про то, чего не было, — может, с маленькой
> вероятностью. Такое ложное «да» называют **ложным срабатыванием**.

Для краулера это идеально: ложное «да» значит, что мы **изредка** пропустим страницу, которую на
самом деле ещё не видели. Не страшно — пропустили сотую долю процента, зато уложились в память.
А вот наоборот (обойти одну и ту же страницу дважды) — фильтр не допустит.

### Добавляем URL

```go
type Bloom struct {
    bits []uint8 // битовый массив (для наглядности — по байту на бит)
    m    uint    // всего бит
    k    uint    // число хеш-функций
}

// k позиций получаем из ДВУХ базовых хешей: p_i = (h1 + i*h2) % m.
// Считать k отдельных хеш-функций не нужно (приём Кирша — Миценмахера).
func (b *Bloom) Add(url string) {
    h1, h2 := hash1(url), hash2(url)
    for i := uint(0); i < b.k; i++ {
        p := (h1 + i*h2) % b.m
        b.bits[p] = 1 // зажигаем бит p
    }
}
```

Нажми «▶» и посмотри, как краулер добавляет три сайта — `reddit`, `github`, `medium`. Каждый
зажигает по 3 бита; замечай, где биты **пересекаются** (один бит на двоих) — это и есть будущий
источник ложных срабатываний:

### Проверяем URL

```go
func (b *Bloom) MightContain(url string) bool {
    h1, h2 := hash1(url), hash2(url)
    for i := uint(0); i < b.k; i++ {
        p := (h1 + i*h2) % b.m
        if b.bits[p] == 0 {
            return false // нашли нулевой бит → ТОЧНО не добавляли
        }
    }
    return true // все биты стоят → ВОЗМОЖНО добавляли (или ложное «да»)
}
```

А теперь — самый поучительный момент. Спросим фильтр про `discord`, которого краулер **никогда не
видел**. Проследи: все три его бита случайно оказались зажжены другими сайтами (`reddit` и
`github`), и фильтр отвечает «возможно да» — **ложное срабатывание**:

<div class="algo-viz" data-viz="bloom-check" data-add="reddit,github,medium" data-check="discord"></div>

### Прогони руками

Возьмём тот же фильтр: `m = 16` бит, `k = 3` хеша. Числа — ровно как в виджетах выше:

| Операция | биты (позиции) | что происходит | ответ |
|---|---|---|---|
| `Add("reddit")` | 14, 12, 10 | ставим 3 бита | — |
| `Add("github")` | 3, 10, 1 | бит **10 уже стоял** (общий с reddit) | — |
| `Add("medium")` | 5, 14, 7 | бит **14 уже стоял** (общий с reddit) | — |
| `MightContain("reddit")` | 14, 12, 10 → все 1 | все биты на месте | **да** (верно) |
| `MightContain("twitter")` | 3, 9, 15 → бит **9 = 0** | нашли ноль → обрываемся | **нет** (верно, точно) |
| `MightContain("discord")` | 12, 3, 10 → **все 1** | а ведь не добавляли! | **да** ⚠️ ложное |

`discord` не добавляли, но бит 12 зажёг `reddit`, а биты 3 и 10 — `github`. Три чужие галочки
случайно сложились в «да». Заметь ещё: **удалить** URL из фильтра нельзя — сбросив бит 10 при
удалении `reddit`, мы бы сломали `github`, который на нём тоже стоит.

## 🧠 Почему это корректно

**Промаха в сторону «нет» не бывает — это железно.** Если URL добавляли, `Add` поставил все его
`k` бит в 1, и погасить их нечем (в обычном Bloom удаления нет). Значит, `MightContain` для
добавленного URL обязан увидеть все биты стоящими и вернуть «да». Ошибиться наоборот — сказать
«нет» про то, что было, — структура **не может по построению**. Именно поэтому краулер никогда не
обойдёт страницу дважды.

**Ложные «да» есть, но их вероятность мы контролируем.** «Да» ошибочно, только если все `k` бит
нашего URL случайно зажгли **другие** URL. Чем плотнее забита полоска (больше единиц), тем это
вероятнее. Отсюда простое правило: под ожидаемое число элементов `n` подбирают размер `m` и число
хешей `k` так, чтобы ложных срабатываний было, скажем, меньше 1%.

<details class="algo-details">
<summary>Формула вероятности ложного срабатывания (для любопытных)</summary>

После вставки `n` элементов в `m` бит с `k` хешами вероятность, что **конкретный** бит остался
нулём, ≈ `e^(−kn/m)`. Ложное срабатывание — когда все `k` проверяемых бит оказались единицами:

```
p ≈ (1 − e^(−kn/m))^k
```

Из неё выводятся готовые инженерные рецепты (их обычно и берут из библиотеки):

- **оптимальное число хешей:** `k = (m/n)·ln 2 ≈ 0.693 · m/n`;
- **нужный размер массива** под заданную ошибку `p`: `m = −n·ln p / (ln 2)²`.

Прикидка «на пальцах»: на **1% ошибки** нужно примерно **9.6 бита на элемент** и **7 хешей**.
Миллиард URL при 1% лжи — это ~1.2 ГБ, тогда как хеш-множество тех же URL заняло бы десятки-сотни
гигабайт. Вот за что платят точностью.

</details>

## ⚙️ Цена на практике

- **Память — главный выигрыш.** ~10 бит на элемент против десятков байт в хеш-множестве. Поэтому
  Bloom ставят **перед** дорогим хранилищем: «точно нет» отвечает мгновенно из памяти и экономит
  поход на диск или в сеть.
- **`k` хешей, но не `k` хеш-функций.** Приём Кирша — Миценмахера (`p_i = h1 + i·h2`) даёт `k`
  позиций из **двух** реальных хешей без потери качества. Считать `k` разных хешей — пустая трата
  тактов.
- **Удаления нет.** Нужна «забывчивость» — бери **Counting Bloom** (вместо бит — маленькие
  счётчики: `Add` инкрементит, `Delete` декрементит) ценой ~4× памяти, или **Cuckoo filter**.
- **Ложные «да» складываются вниз по конвейеру.** Если Bloom стоит перед кэшем, 1% лжи — это 1%
  лишних дорогих проверок. Закладывай это в расчёт нагрузки, а не считай ошибку «бесплатной».

> 🔧 **Где это в Go и в реальных системах.** Bloom-фильтры — рабочая лошадка инфраструктуры:
> в **Cassandra, HBase, RocksDB, Bigtable** они стоят перед SSTable, чтобы не читать с диска ключ,
> которого там нет; **Chrome Safe Browsing** проверял URL по локальному Bloom перед запросом на
> сервер (ровно наш пример!); **Redis** даёт Bloom через модуль RedisBloom; веб-краулеры — дедуп
> уже посещённых URL. В Go-экосистеме — [`bits-and-blooms/bloom`](https://github.com/bits-and-blooms/bloom)
> (тот самый приём с двумя хешами) и Bloom-фильтры внутри
> [CockroachDB](https://github.com/cockroachdb/cockroach). Механизм — ровно тот, что выше.

## 2. HyperLogLog — «сколько уникальных» почти даром

Новая задача. У тебя сайт, и начальник спрашивает: **сколько уникальных посетителей было за
день?** Не всего заходов (это просто счётчик), а именно **разных** людей. Наивно: держать
множество всех ID и в конце взять его размер. Но уникальных — десятки миллионов, а таких вопросов
(по часам, по странам, по разделам) — тысячи. Множества съедят всю память.

**HyperLogLog оценивает число уникальных, почти ничего не запоминая** — миллиард разных
элементов он посчитает с ошибкой ~2%, заняв всего **~1.5 КБ**. Как? Через красивый трюк с
теорией вероятностей.

**Интуиция — про подбрасывание монетки.** Представь, ты подбрасываешь монету и записываешь только
**самую длинную серию решек подряд**, что тебе встретилась. Если самая длинная серия — 3 решки,
ты, наверное, бросал монету немного раз. А если встретилась серия из **20 решек подряд** — ты
почти наверняка бросал её **очень** много раз (около 2²⁰ ≈ миллион), потому что редкое событие
«20 решек» просто не выпадет за пару бросков. **Длина самой редкой серии выдаёт, сколько всего
было попыток.**

HyperLogLog делает ровно это. Каждый ID он хешует — получается «случайная» цепочка бит. Смотрит,
**сколько нулей идёт подряд** в начале (это и есть «серия решек»). И запоминает **максимум** —
самую длинную серию, что видел. Одинаковые ID дают одинаковый хеш и не портят счёт (потому и
считаются уникальные, а не все). Чтобы уменьшить разброс, заводят не один счётчик, а много
(**регистров**): старшие биты хеша выбирают регистр, и оценки усредняют.

```go
func (h *HLL) Add(id string) {
    x := hash(id)
    j := x >> (32 - p)            // старшие биты → номер регистра
    rho := leadingZeros(x<<p) + 1 // длина серии нулей в остатке
    if rho > h.reg[j] {
        h.reg[j] = rho            // храним МАКСИМУМ серии
    }
}
```

Нажми «▶»: восемь уникальных ID заполняют регистры. Замечай — регистр хранит не сумму и не
количество, а **самую длинную серию нулей**, что в него попала:

<div class="algo-viz" data-viz="hll-add" data-elems="user_8143,user_2290,user_5561,user_9033,user_1204,user_7788,user_4415,user_6672"></div>

> ⚠️ На восьми элементах оценка гуляет — HyperLogLog честно точен только на **масштабе**
> (миллионы). Виджет показывает **механику**, а не точность: важно понять, что регистр — это
> «рекорд серии нулей», а из рекордов по формуле восстанавливают число уникальных.

**Почему это работает** (в двух словах): вероятность увидеть серию из `r` нулей подряд — примерно
`1/2ʳ`. Значит, если в бакете **максимальная** серия дотянула до `r`, то элементов через него,
скорее всего, прошло порядка `2ʳ`. HyperLogLog усредняет `2^(reg)` по всем регистрам (специальным
«гармоническим» способом, чтобы выбросы не портили картину) и получает оценку. Строгий вывод и
поправочные коэффициенты — в оригинальной статье Flajolet; на практике берут готовую реализацию.

> 🔧 **Где это в Go и в реальных системах.** `PFADD`/`PFCOUNT` в **Redis** — это HyperLogLog
> (12 КБ на структуру, ошибка 0.81%); **Presto/BigQuery** — `APPROX_DISTINCT`; аналитика уникальных
> посетителей у всех крупных систем. В Go — [`axiomhq/hyperloglog`](https://github.com/axiomhq/hyperloglog),
> [`clarkduvall/hyperloglog`](https://github.com/clarkduvall/hyperloglog).

## 3. Count-Min Sketch — «как часто» в бесконечном потоке

Ещё задача из мира бэкенда. Через тебя идёт поток событий — миллиарды в день: хештеги в соцсети,
IP-адреса запросов, ID товаров. Вопрос: **как часто встречается вот этот конкретный элемент?**
(Какие хештеги в тренде? Какой IP долбит нас чаще всех — не DDoS ли?) Точно — это счётчик на
каждый элемент, но разных элементов миллиарды, память не потянет.

**Count-Min Sketch считает частоты в фиксированной памяти.** Идея — как у Bloom, но вместо бит
храним **счётчики**, и не в одном массиве, а в **таблице**: `d` строк × `w` столбцов, и `d`
хеш-функций (по одной на строку).

- **Добавить элемент** — в **каждой** строке хешируем его в свой столбец и делаем **+1**.
- **Спросить частоту** — снова считаем те же `d` ячеек и берём из них **минимум**.

Почему минимум, а не любую ячейку? Из-за коллизий счётчик иногда **завышен**: в ячейку попал не
только наш элемент, но и чужой. Но завысить коллизия может только **вверх** — вниз никогда. Значит
**наименьший** из `d` счётчиков пострадал от коллизий меньше всех и ближе всего к правде.

```go
func (c *CMS) Add(item string) {
    for r := 0; r < c.d; r++ {
        col := hash(item, r) % c.w
        c.count[r][col]++
    }
}
```

Скормим фильтру поток хештегов, где `#cats` — явный тренд (5 раз), остальные реже. Смотри, как в
каждой из трёх строк растёт своя ячейка:

<div class="algo-viz" data-viz="cms-add" data-stream="#cats,#cats,#cats,#cats,#cats,#go,#go,#news,#rust"></div>

Теперь — тот самый трюк с минимумом. Спросим про редкий `#rust` (был всего 1 раз). В двух строках
его ячейка **завышена** до 3 (туда попали чужие хештеги), но в третьей строке коллизии не случилось
— там честная 1. **Минимум по строкам восстанавливает правду:**

```go
func (c *CMS) Count(item string) int {
    est := math.MaxInt
    for r := 0; r < c.d; r++ {
        col := hash(item, r) % c.w
        if c.count[r][col] < est {
            est = c.count[r][col] // МИНИМУМ по строкам
        }
    }
    return est
}
```

> **Гарантия — как у Bloom, но про числа.** Count-Min **никогда не занижает** частоту (`est ≥`
> истинной), может лишь **завысить** — и то редко и немного. Для «кто в тренде / кто заваливает
> нас запросами» этого достаточно: мы не пропустим тяжёлого нарушителя, максимум изредка примем
> тихого за чуть более активного.

> 🔧 **Где это в Go и в реальных системах.** Count-Min — стандарт для «тяжёлых элементов» (heavy
> hitters) в потоке: сетевой мониторинг и защита от DDoS, подсчёт частот в **Spark**/аналитике,
> трендовые хештеги. В Go — [`shenwei356/countminsketch`](https://github.com/shenwei356/countminsketch),
> реализации внутри систем мониторинга.

## 4. Skip-list — «дерево поиска» из связных списков

Последняя структура — немного из другой оперы: она **точная**, но её баланс держится на
**случайности**. Задача: нужен отсортированный набор с быстрыми `поиск`, `вставка`, `удаление` за
`O(log n)`. Классический ответ — сбалансированное дерево ([AVL](avl-tree-structure.md),
красно-чёрное). Но их балансировка (повороты, перекраска) — муторная и легко ошибиться в коде.

**Skip-list даёт те же `O(log n)`, но вместо поворотов — подбрасывание монеты.** Это обычный
отсортированный связный список, к которому добавили **express-полосы** — как экспресс-линии в
метро, что проезжают мимо мелких станций.

Идея: у каждого узла есть **высота**. Все узлы связаны на уровне 0 (обычный список). Часть узлов
(примерно половина — решил «бросок монеты») поднимается на уровень 1 и связывается между собой,
перепрыгивая соседей. Из них половина лезет на уровень 2, и так далее. Верхние полосы редкие и
«длинные» — прыгают через много узлов.

**Поиск идёт сверху вниз:** встаём на верхнюю полосу и бежим вправо, пока следующий ключ не
больше цели; уперлись — **спускаемся** на уровень ниже и продолжаем. Верхние полосы отсекают
большие куски списка, поэтому в среднем — `O(log n)`, как спуск по дереву.

```go
func (s *SkipList) Search(target int) bool {
    node := s.head
    for lvl := s.maxLevel; lvl >= 0; lvl-- {
        for node.next[lvl] != nil && node.next[lvl].key <= target {
            node = node.next[lvl] // прыжок по express-полосе
        }
    }
    // node — наибольший ключ ≤ target; если это не голова и ключ совпал — нашли
    return node != s.head && node.key == target
}
```

Ищем `19`. Проследи, как поиск скачет по верхним полосам (`head → 7`), проскакивая узлы, и
спускается только когда следующий ключ перелетает цель:

<div class="algo-viz" data-viz="skip-search" data-keys="3,6,7,9,12,17,19,21,25,26" data-target="19"></div>

> **Вставка и удаление** идут по той же логике: сначала тем же спуском находим место (запоминая
> на каждом уровне узел, после которого свернули вниз), затем для нового узла бросаем монетку —
> определяем его высоту — и перецепляем `next`-ссылки на всех его уровнях (при удалении —
> наоборот, выкидываем узел из полос, где он был). Всё та же `O(log n)`, здесь показан поиск как
> самый наглядный представитель.

**Почему `O(log n)` без всякой балансировки?** Высоту каждого узла выбирает монетка: на уровне
`L` оказывается примерно `1/2ᴸ` узлов. Значит уровней всего ~`log₂ n`, а на каждом поиск делает
константное число шагов вправо (в среднем). Дерево гарантирует баланс **структурой** и платит
сложностью кода; skip-list гарантирует его **в среднем, вероятностно** — и платит крошечным
шансом, что монетка навыдаёт кривые высоты. На практике этот шанс ничтожен, а код — в разы проще
поворотов.

> 🔧 **Где это в Go и в реальных системах.** Skip-list — не экзотика: **Redis** хранит на нём
> sorted sets (`ZADD`/`ZRANGE` — команды поверх skip-list); memtable в **LevelDB** и на нём
> основанных движках; **Apache Lucene**. В Go — skip-list внутри
> [`dgraph-io/badger`](https://github.com/dgraph-io/badger) (memtable) и множество отдельных
> пакетов. Выбирают его именно за простоту относительно красно-чёрных деревьев.

## 📝 Разбор задачи: подобрать параметры Bloom-фильтра

Все формулы главы оживают, когда надо ответить на вопрос из ТЗ. Прорешаем его целиком.

> **Задача.** Сервис коротких ссылок генерирует случайные слаги и должен проверять «слаг уже
> занят?» до похода в БД. Ожидается `n = 100 млн` занятых слагов; допустимая доля ложных «занят» —
> `p = 1%` (тогда просто перегенерируем слаг). Сколько памяти нужно фильтру и сколько хешей брать?

**Шаг 1. Размер битового массива.** Оптимум по теории: `m = −n·ln(p) / (ln 2)²`. Подставляем:
`ln(0.01) ≈ −4.6`, `(ln 2)² ≈ 0.48`, значит `m ≈ 100·10⁶ · 4.6 / 0.48 ≈ 9.6·10⁸ бит` — на ключ
приходится **~9.6 бита**. Итого `9.6·10⁸ / 8 ≈ 120 МБ`.

**Шаг 2. Число хешей.** `k = (m/n)·ln 2 ≈ 9.6 · 0.69 ≈ 6.6` → берём `k = 7`. Меньше — биты
недоиспользуются (FP растёт), больше — фильтр забивается единицами быстрее (FP снова растёт):
у `k` есть «долина», и `7` — её дно для наших `m/n`.

**Шаг 3. Санити-проверка масштаба.** Точное множество: 100 млн слагов по ~8 байт + накладные
расходы хеш-таблицы — единицы гигабайт. Фильтр — **120 МБ**, в ~20–30 раз меньше, и вся проверка
«занят?» происходит в памяти без похода в БД. Цена — 1% лишних перегенераций слага, которые
стоят ничего.

**Шаг 4. Что будет, если наврать в `n`.** Заложились на 100 млн, а слагов стало 300 млн: `m/n`
упало втрое, и реальный FP взлетит с 1% до десятков процентов — фильтр «протухает» молча. Прод-вывод:
параметры фиксируют **ёмкость**; при её превышении фильтр перестраивают на новый размер (или
используют scalable Bloom — цепочку фильтров растущей ёмкости).

## ⚠️ Типичные ошибки

1. **«Удалю элемент — сброшу его биты».** Нельзя: биты общие, сбросишь — сломаешь другие ключи
   (мы видели это на `discord`/`reddit`). Удаление — это counting Bloom (счётчики вместо бит)
   или пересборка фильтра.
2. **Доверять HyperLogLog на малых наборах.** Погрешность ~2% — это про миллионы; на десятках
   элементов оценка гуляет в разы (мы честно видели это в примере). Реальные реализации на малых
   n переключаются на точный подсчёт — делай так же.
3. **Использовать вероятностную структуру там, где ошибка стоит денег.** Bloom для
   идемпотентности платежей — авария (см. [кейс в главе о хеш-таблице](hash-table-structure.md#-инженерный-кейс)):
   выбор «точно/приближённо» диктуется ценой промаха, а не модой.
4. **Забыть, что Count-Min только завышает.** Оценка частоты — верхняя граница; вычитать из неё
   «средний шум» без понимания, что делаешь, — способ получить произвольные числа.
5. **Переполнить фильтр сверх расчётной ёмкости.** FP-гарантия живёт при спроектированном `m/n`
   (см. разбор выше); тихое переполнение — тихая деградация.

## 🏗️ Инженерный кейс

> **Ситуация.** Входной шлюз event-пайплайна аналитики: ~миллиард событий в сутки, у каждого —
> `event_id`. Дубликаты (ретраи клиентов, повторная доставка очередью) надо отсечь. Точное
> множество всех `event_id` за сутки — сотни гигабайт в Redis. Бюджет — пара гигабайт памяти,
> и **терять события нельзя**.

**Вывод.** Вероятностная структура в проде почти никогда не работает одна: она — **дешёвый фильтр
перед дорогой точной проверкой**. Односторонность ошибки Bloom («точно нет» не врёт) — это не
математический курьёз, а то самое свойство, которое делает схему корректной.

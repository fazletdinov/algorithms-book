## 1. Минимальный язык: исходы, события, P

Для всей главы хватает четырёх понятий, и все они операциональные:

- **Исход** — один конкретный результат эксперимента: «выпала грань 4», «ключ попал в корзину 7».
  Все исходы вместе — конечное множество.
- **Событие** — набор исходов: «выпало чётное» = {2, 4, 6}. Событие «произошло», если реальный
  исход попал в набор.
- **Вероятность P(A)** — доля события среди исходов. Если все m исходов равновозможны
  (честный кубик, хороший хеш), то `P(A) = |A| / m`. Считать вероятности = считать исходы —
  поэтому рядом с этой главой живёт [комбинаторика](combinatorics.md).
- **Независимость**: события A и B независимы, если знание одного не меняет шансов другого;
  формально `P(A и B) = P(A)·P(B)`. Умножать вероятности можно **только** для независимых
  событий — это ошибка №1 в инженерных расчётах.

Если события зависимы, работает **условная вероятность**: `P(A | B)` — вероятность A, когда
известно, что B произошло; `P(A и B) = P(B)·P(A | B)`. Пример: вероятность, что два ключа
попали в одну корзину из m, — это `1 · (1/m)`: первый ключ падает куда угодно, второй должен
попасть именно в его корзину.

Больше из «языка» ничего не понадобится. Вся сила главы — в следующем разделе.

## 2. Линейность матожидания и индикаторы

**Матожидание E[X]** — среднее значение случайной величины по всем исходам с учётом их
вероятностей: `E[X] = Σ x·P(X = x)`. Для кубика `E = (1+2+…+6)/6 = 3.5`.

Считать E[X] по определению почти всегда больно. Спасают два факта:

1. **Линейность**: `E[X + Y] = E[X] + E[Y]` — **всегда**, даже если X и Y зависимы.
   Никаких условий. Это главная теорема главы.
2. **Индикатор**: величина `Iₐ`, равная 1, если событие A произошло, и 0 иначе. Тогда
   `E[Iₐ] = 1·P(A) + 0·(1−P(A)) = P(A)` — матожидание индикатора равно вероятности.

Рецепт: **разбей сложную величину на сумму индикаторов, посчитай вероятность каждого,
сложи**. Три применения — три формулы, которые ты раньше принимал на веру.

### Применение 1: сколько коллизий у n ключей в m корзинах

Кидаем n ключей в m корзин случайно (это модель хорошей хеш-функции). Сколько **пар**
ключей столкнётся? Для каждой пары ключей (i, j) заведём индикатор «i и j в одной корзине».
Его вероятность — `1/m` (см. выше). Пар всего `C(n,2) = n(n−1)/2` (почему столько — в главе
про [комбинаторику](combinatorics.md)). По линейности:

```text
E[коллизий] = C(n,2) · 1/m = n(n−1) / 2m
```

Пары зависимы (если i и j в корзине 3, шансы j и k тоже сдвинуты) — и это **не важно**:
линейность не спрашивает про независимость. В этом вся мощь приёма.

### Применение 2: средняя длина цепочки в хеш-таблице

Возьмём одну корзину. Для каждого из n ключей — индикатор «ключ попал сюда», вероятность
`1/m`. Ожидаемая длина цепочки: `E = n · 1/m = n/m`. Это и есть **коэффициент загрузки α**
из главы про [хеш-таблицу](hash-table-structure.md): пока `α = n/m` держат константой
(старая `map` Go, до 1.24, расширялась при α ≈ 6.5 записей на бакет; нынешние Swiss Tables — при заполнении 7 слотов из 8), средняя цепочка — константа, и
`Get`/`Put` в среднем O(1). «Среднее O(1)» — не лозунг, а одна строчка линейности.

### Применение 3: quicksort — O(n log n) в среднем

Quicksort со случайным pivot делает в среднем около `2n·ln n ≈ 1.39·n·log₂ n` сравнений —
то есть **O(n log n) в среднем**, та самая строчка из таблицы в главе про
[сортировки](sorting.md). Интуиция: случайный pivot обычно оказывается «где-то в середине»,
поэтому массив раз за разом делится примерно пополам. Совсем неудачный pivot (самый
маленький или самый большой) выпадает редко, и такие промахи в среднем почти не портят счёт.

## 3. Парадокс дней рождения

В группе из 23 человек два совпадающих дня рождения — вероятнее, чем ни одного. Интуиция
кричит «мало!», потому что сравнивает n с m = 365. А сравнивать надо **число пар** с m:
пар `C(23,2) = 253` — уже порядка 365.

Отсюда **правило √m**: если раскладывать n случайных значений по m вариантам, коллизия
становится вероятной уже при `n ≈ √m`, а не при `n ≈ m`. Для дней рождения `√365 ≈ 19` —
и действительно, к 23 людям шанс совпадения переваливает за половину (точнее, 50/50
наступает при `n ≈ 1.18·√m`).

Инженерные следствия:

- **32-битный хеш** (m = 2³²): √m = 65 536, коллизия 50/50 при n ≈ 77 000. Дедупликация
  по 32-битному хешу «ломается» на смешных семидесяти тысячах элементов — не на миллиардах.
- **64-битный хеш**: n ≈ 5·10⁹ — уже терпимо для многих задач, но не для всех.
- **git short hash**: 7 hex-цифр = 28 бит, √(2²⁸) ≈ 16 000 — поэтому в больших репозиториях
  git молча удлиняет сокращённые хеши: коллизии коротких префиксов реально случаются.
- **UUID v4**: 122 случайных бита, коллизия 50/50 при n ≈ 2⁶¹ ≈ 2·10¹⁸. Поэтому UUID
  генерируют без координации и не боятся — √m здесь астрономический.

Обратная сторона правила: ожидаемое **число** коллизий `C(n,2)/m` достигает 1 при
`n ≈ √(2m)` — удобный порог «первая коллизия уже где-то рядом» (в тренажёре ты его
реализуешь как `BirthdayThreshold`).

## 4. Геометрическое распределение

Попытка удаётся с вероятностью p, попытки независимы. Сколько попыток до первого успеха?
Это **геометрическое распределение**, и его матожидание выводится одной строчкой. Пусть
`E` — искомое среднее. Первая попытка есть всегда; с вероятностью `1 − p` она провалилась,
и мы в исходной ситуации (попытки независимы — прошлое не в счёт):

```text
E = 1 + (1 − p)·E   ⟹   E = 1/p
```

Успех с шансом 1/6 — в среднем 6 попыток. Три места, где это уже работало на тебя:

- **Open addressing**: в хеш-таблице с открытой адресацией при загрузке α доля свободных
  слотов `1 − α`. В идеализированной модели каждая проба «попадает в свободный» с вероятностью
  `1 − α` независимо ⟹ среднее число проб `1/(1−α)`. При α = 0.5 — 2 пробы, при α = 0.9 —
  уже 10: вот почему открытую адресацию (и Go-шный swiss map из главы про
  [хеш-таблицу](hash-table-structure.md)) не загружают под завязку.
- **Ретраи**: запрос проходит с вероятностью 0.99 ⟹ в среднем `1/0.99 ≈ 1.01` попытки —
  ретраи почти бесплатны. Но при деградации до 0.5 среднее уже 2, а хвост длинный:
  вероятность, что понадобится больше k попыток, — `(1−p)^k`, убывает геометрически.
- **Skip-list**: узел монетой «повышается» на следующий уровень с p = 1/2 ⟹ средняя высота
  узла `1/p = 2` — константа памяти на узел, а уровней всего ~log n (глава про
  [вероятностные структуры](probabilistic-structures.md)).

## 5. Fisher–Yates: честное перемешивание

Задача «перемешать массив равновероятно» выглядит тривиально и почти всегда пишется
неправильно. Правильный алгоритм — **Fisher–Yates**: идём с конца, каждый элемент меняем
со случайным из **ещё не зафиксированной** части (включая себя):

```go
// Вручную: O(n) времени, O(1) памяти, перемешивание на месте.
func shuffle(a []int, rng *rand.Rand) {
    for i := len(a) - 1; i > 0; i-- {
        j := rng.Intn(i + 1) // j ∈ [0..i] — включая сам i!
        a[i], a[j] = a[j], a[i]
    }
}

// В stdlib то же самое — rand.Shuffle; сам алгоритм внутри тот же Fisher–Yates.
rand.Shuffle(len(a), func(i, j int) { a[i], a[j] = a[j], a[i] })
```

**Почему равномерно.** Инвариант: на шаге i каждый из ещё не зафиксированных элементов
попадает в позицию i с вероятностью `1/(i+1)`. Разворачивая с конца: конкретная
перестановка требует конкретного j на каждом шаге, вероятность —
`1/n · 1/(n−1) · … · 1/2 = 1/n!` — одинаково для **любой** перестановки. Все n! исходов
равновероятны, это и есть определение честного shuffle.

**Классическая ошибка** — писать `rng.Intn(n)` вместо `rng.Intn(i+1)`: «каждый с каждым
случайным». Выглядит даже «случайнее», но смещено, и это доказывается подсчётом исходов:
алгоритм с `Intn(n)` делает n случайных выборов по n вариантов — всего `nⁿ` равновероятных
путей. Перестановок же `n!`, и `nⁿ` **не делится** на `n!` нацело (уже при n = 3:
27 путей на 6 перестановок — по 4.5 не раздашь). Значит, какие-то перестановки выпадают
чаще других — без единого вычисления вероятностей мы доказали смещение. Для n = 3 перебор всех 27 путей
даёт: три перестановки выпадают по 5 раз, три — по 4, то есть с вероятностями 5/27 и 4/27 вместо
честных 4.5/27 = 1/6; с ростом n перекос растёт.

## 6. Reservoir sampling: k случайных из потока

Задача: по потоку записей неизвестной заранее длины (лог, курсор БД, kafka-топик) выбрать
**k записей равновероятно**, за один проход и O(k) памяти. Дважды прочитать поток нельзя,
длину узнать заранее — тоже.

**Алгоритм R**: первые k элементов кладём в «резервуар». Каждый следующий, i-й по счёту
(нумеруя с нуля), с вероятностью `k/(i+1)` **заменяет случайный** элемент резервуара:

```go
func reservoirSample(stream []int, k int, rng *rand.Rand) []int {
    res := make([]int, 0, k)
    for i, x := range stream {
        if i < k {
            res = append(res, x) // первые k — просто берём
            continue
        }
        j := rng.Intn(i + 1) // j ∈ [0..i]
        if j < k {           // с вероятностью k/(i+1)
            res[j] = x       // новичок вытесняет случайного старожила
        }
    }
    return res
}
```

Одна строчка `j := rng.Intn(i+1); if j < k` делает сразу два случайных выбора: событие
`j < k` происходит с вероятностью `k/(i+1)` («брать ли новичка»), и при этом j равномерен
по резервуару («кого вытеснить»).

**Почему равновероятно.** После того как прочитано n элементов, каждый из них лежит в
резервуаре с вероятностью `k/n` — неважно, пришёл он первым или последним. Проще всего
увидеть это при k = 1 и трёх элементах: первый берём сразу, второй заменяет его с шансом
1/2, третий — с шансом 1/3. Итог: третий остался с вероятностью 1/3, второй — `1/2 · 2/3 = 1/3`,
первый — `1/2 · 2/3 = 1/3`, всем поровну.

Все элементы равноправны в любой момент — можно остановить поток когда угодно и забрать
честную выборку. Именно так сэмплируют логи и трейсы: «сохранить 1000 случайных запросов
за час», не зная заранее, сколько их будет, и не храня всё. При k = 1 алгоритм вырождается
в «i-й элемент становится ответом с вероятностью 1/(i+1)» — классика собеседований
(случайный узел связного списка за один проход).

## ⚡ Что помнить на собеседовании

- **Линейность матожидания** работает для зависимых величин. «Ожидаемое число X» → сумма
  индикаторов → сумма вероятностей.
- **E[коллизий]** n ключей в m корзинах = `C(n,2)/m`; средняя цепочка = `n/m = α`.
- **Правило √m**: коллизии вероятны при `n ≈ √m`. 32 бита → ~77 тыс., 64 бита → ~5·10⁹.
- **Геометрическое**: успех с вероятностью p → в среднем `1/p` попыток; open addressing —
  `1/(1−α)` проб.
- **Fisher–Yates**: `j := rng.Intn(i+1)`, не `Intn(n)`. В Go есть готовый `rand.Shuffle`.
- **Reservoir**: i-й элемент берём с вероятностью `k/(i+1)`, он вытесняет случайного.
  Один проход, O(k) памяти.
- Quicksort со случайным pivot в среднем: около `2n·ln n ≈ 1.39·n·log₂ n` сравнений.

## ⚙️ Цена на практике

### math/rand/v2 против crypto/rand

В Go два мира случайности, и путать их нельзя:

- **`math/rand/v2`** — быстрые статистические генераторы: PCG и ChaCha8 (глобальные функции
  пакета используют ChaCha8 и автоматически засеяны). Порядок цены — единицы наносекунд на
  число, можно звать в горячем цикле. Для shuffle, сэмплирования, jitter в ретраях,
  рандомизированных алгоритмов — то, что нужно. Старый `math/rand` (v1) жив, но в новом коде
  бери v2: у v1 устаревший ритуал `rand.Seed`, и стоит его вызвать, как глобальный генератор
  переходит на источник с мьютексом (горутины толкаются на нём локтями); без `Seed` глобальные
  функции v1 с Go 1.20 берут числа из быстрого генератора рантайма.
- **`crypto/rand`** — криптографический источник (ОС-энтропия). Порядок цены — сотни
  наносекунд и дороже за вызов, зато вывод непредсказуем для противника. Токены, ключи,
  соли, nonce, ID сессий — **только** отсюда: значение, которое кто-то не должен угадать,
  из `math/rand` доставаемо на раз (у PCG восстанавливают состояние по нескольким выводам).

Отдельная классика — **модульное смещение**: наивное `Uint32() % n` даёт неравномерность,
когда n не делит 2³² (младшие остатки выпадают чуть чаще; для n близких к 2³¹ перекос —
почти двукратный). Стандартная библиотека от этого защищает: `Intn`/v1 использует
rejection sampling, `IntN`/v2 — метод Лемира; опасность возникает, когда «остаток от
деления» пишут руками поверх сырых байт из `crypto/rand` или старых/чужих генераторов.
Если пишешь сам — либо rejection loop, либо готовый `IntN`.

### Ожидание — это не гарантия

Все формулы главы — про **среднее**. Средняя цепочка n/m не запрещает одной корзине
вырасти до O(n) при плохом хеше или атаке (потому map в Go засеян случайным сидом на
процесс). Средние 1/(1−α) проб при α → 1 превращаются в лавину. Quicksort в среднем
O(n log n), но naive-версия на подобранном входе — O(n²). Инженерный вывод: формулы среднего
говорят, как система живёт **обычно**; проектировать надо ещё и хвосты — p99, worst case,
поведение под атакой.

## ⚠️ Типичные ошибки

1. **Умножение вероятностей зависимых событий.** «Каждый из 10 сервисов доступен с P = 0.99,
   значит все вместе — 0.99¹⁰» — верно, только если отказы независимы. Общий рубильник
   питания, общая зона облака, каскадная перегрузка — и «независимые девятки» схлопываются
   разом. Прежде чем перемножать — спроси, что у событий общего.
2. **Ошибка игрока.** «После 10 орлов решка вероятнее» — нет: независимые броски не помнят
   прошлого. Симметричная ошибка — «горячая рука» у генератора UUID: прошлые значения не
   влияют на будущие.
3. **Ожидание ≠ типичный случай.** Среднее число ретраев 1.01 совместимо с запросом,
   который ретраится 50 раз. Среднее время ответа 10 мс — с p99 в секунду. Распределения
   с хвостами живут не там, где их среднее.
4. **Shuffle сортировкой по случайному ключу.** Сортировать с компаратором, зовущим
   `rand.Float64()` на каждое сравнение, нельзя: компаратор несогласован (a < b и b < a
   одновременно), поведение сортировки не определено, распределение смещено. Вариант
   «присвоить каждому случайный ключ и отсортировать» корректен, но это O(n log n) и
   лишняя память против O(n)/O(1) у Fisher–Yates. В Go просто есть `rand.Shuffle`.
5. **Сид и горутины.** Сид, взятый из `time.Now().Unix()` в цикле, повторяется в пределах
   секунды — «случайные» данные совпадают. Один `*rand.Rand` из нескольких горутин без
   синхронизации — гонка данных (в отличие от глобальных функций пакета, которые
   потокобезопасны). Практика: в проде — глобальные функции `math/rand/v2`; в тестах —
   свой `rand.New` с **фиксированным** сидом, чтобы падение воспроизводилось.

> 🌍 **Где это в настоящем коде**
>
> - [`rand.Rand.Shuffle`](https://github.com/golang/go/blob/go1.24.0/src/math/rand/v2/rand.go#L233) (Go 1.24) — Fisher–Yates из этой главы в `math/rand/v2`: цикл с конца, `j` берётся из `[0, i]` (`uint64n(i + 1)`), а не из всего массива.
> - [`rand.Rand.Perm`](https://github.com/golang/go/blob/go1.24.0/src/math/rand/v2/rand.go#L221) (Go 1.24) — случайная перестановка `0…n−1`: заполняет срез по порядку и перемешивает тем же `Shuffle`.

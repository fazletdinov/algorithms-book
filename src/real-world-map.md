# 🌍 Карта: структуры данных в реальных системах

> 🧭 **Зачем эта глава.** B-деревья, кучи, хеш-таблицы и топологическая сортировка — не
> «материал для собеседований», а **несущие конструкции** систем, с которыми ты работаешь каждый
> день: базы данных, Kubernetes, Docker, git, ядро Linux.

Эта глава — **карта, а не учебник**: на каждый пример одна-две фразы, ссылка на главу книги и, где
можно, на исходник. Устройство самих систем здесь не разбирается — оно в курсе по системному
дизайну; нам важно узнать в них знакомый алгоритм. Структуры внутри самого Go — на отдельных
страницах: [Go изнутри](appendix-go-memory.md) и [экосистема Go](go-stdlib-structures.md).

## 1. PostgreSQL: дерево, хеш и слияние под каждым запросом

Обычный индекс — **B-дерево**: широкие узлы под страницу диска, малая высота
([B-дерево](btree-structure.md)). **Hash join** строит хеш-таблицу по одной таблице и пробегает
другую с поиском за O(1); не влезающая в память сортировка режет данные на отсортированные куски и
**сливает их кучей** ([K-way merge](k-way-merge.md)). Порядок соединения таблиц планировщик ищет
**динамическим программированием** по подмножествам таблиц, но от `geqo_threshold` (по умолчанию
**12**) таблиц перебор взрывается, и включается **GEQO** — генетическая эвристика вместо оптимума
([классы сложности](complexity-classes.md)). Несколько условий по разным индексам объединяются
битовыми `AND`/`OR` над картами строк ([битовые операции](bit-manipulation.md)).

| Структура / алгоритм | Где именно | Глава |
|---|---|---|
| B-дерево | индексы (`CREATE INDEX` по умолчанию) | [B-дерево](btree-structure.md) |
| Хеш-таблица | hash join, `GROUP BY` | [Хеш-таблица](hash-table-structure.md) |
| K-way merge | внешняя сортировка, merge join | [K-way Merge](k-way-merge.md) |
| DP, затем эвристика | порядок JOIN'ов; GEQO при ≥ 12 таблиц | [DP](dynamic-programming.md), [Классы сложности](complexity-classes.md) |
| Битовые операции | `BitmapAnd` / `BitmapOr` | [Битовые операции](bit-manipulation.md) |

> 🌍 **В коде:** [`make_rel_from_joinlist`](https://github.com/postgres/postgres/blob/REL_16_4/src/backend/optimizer/path/allpaths.c#L3382) (PostgreSQL 16) — развилка «GEQO или `standard_join_search`», а последний по комментарию — «простое динамическое программирование»: сначала все пары таблиц, потом тройки.

## 2. Redis: skip list, постепенный rehash и подсчёт на 12 КБ

**Sorted set** — **skip list** (порядок и диапазоны за O(log n)) плюс хеш-таблица (доступ по имени),
см. [вероятностные структуры](probabilistic-structures.md). Главный словарь растёт **постепенно**:
две таблицы сразу, на каждой операции переносится несколько бакетов — механизм из виджета rehash в
[главе про хеш-таблицы](hash-table-structure.md). `PFCOUNT` — **HyperLogLog**: число уникальных
элементов с ошибкой ~0.81% в ~12 КБ. А вытеснение `allkeys-lru` — **не** честный LRU из
[комбинаций паттернов](pattern-combinations.md): берутся несколько случайных ключей и вытесняется
самый давний из них — знать точное решение нужно, чтобы осознанно от него отступать.

| Структура / алгоритм | Где именно | Глава |
|---|---|---|
| Skip list + хеш | sorted set (ZSET) | [Вероятностные структуры](probabilistic-structures.md) |
| Хеш-таблица с постепенным rehash | словарь ключей | [Хеш-таблица](hash-table-structure.md) |
| HyperLogLog | `PFADD` / `PFCOUNT` | [Вероятностные структуры](probabilistic-structures.md) |
| LRU (приближённый) | вытеснение при `maxmemory` | [Комбинации паттернов](pattern-combinations.md) |

> 🌍 **В коде:** [`dictRehash`](https://github.com/redis/redis/blob/7.4.1/src/dict.c#L385) (Redis 7.4) — шаг постепенного rehash: несколько бакетов из старой таблицы в новую.

## 3. RocksDB, Cassandra, ClickHouse: LSM из знакомых деталей

LSM-хранилище целиком собрано из глав книги: запись падает в упорядоченную структуру в памяти
(в RocksDB и Cassandra по умолчанию — **skip list**), заполнившись, она ложится на диск
отсортированным файлом (SSTable), перед чтением файла спрашивается его **Bloom-фильтр** («ключа
точно нет» — диск не трогаем), а фоновая компакция сливает файлы — снова
[K-way merge](k-way-merge.md). Сравнение LSM с B-деревом — в главе про [B-дерево](btree-structure.md).

| Структура / алгоритм | Где именно | Глава |
|---|---|---|
| Skip list | memtable | [Вероятностные структуры](probabilistic-structures.md) |
| Bloom-фильтр | по одному на SSTable | [Вероятностные структуры](probabilistic-structures.md) |
| K-way merge | компакция, мёрджи MergeTree | [K-way Merge](k-way-merge.md) |

> 🌍 **В коде:** [`CompactionMinHeap`](https://github.com/facebook/rocksdb/blob/v9.6.1/table/compaction_merging_iterator.cc#L184) (RocksDB 9.6) — компакция сливает входные файлы итератором на min-куче.

## 4. etcd и Kubernetes: B-деревья под кластером, куча в каждом контроллере

Состояние кластера лежит в etcd, а у того на диске — **B+-дерево** (bbolt), в памяти — индекс
ключей на **B-дереве** ([B-дерево](btree-structure.md)). Раскладка подов по узлам — bin packing,
задача NP-трудная, поэтому планировщик не ищет оптимум: отсеивает узлы фильтрами и ставит
оставшимся баллы эвристиками ([классы сложности](complexity-classes.md)). Очередь контроллера
(client-go workqueue) ограничивает ретраи **общим token bucket** плюс **экспоненциальным backoff
на каждый элемент**, а отложенные элементы держит в **куче** по времени готовности
([куча](heap-structure.md)) — на стандартном
[`container/heap`](https://github.com/golang/go/blob/go1.24.0/src/container/heap/heap.go).
Каскадное удаление по `ownerReferences` — обход **графа** владельцев ([графы](graphs.md)).

| Структура / алгоритм | Где именно | Глава |
|---|---|---|
| B+-дерево / B-дерево | etcd: bbolt на диске, индекс ключей в памяти | [B-дерево](btree-structure.md) |
| Эвристики вместо оптимума | kube-scheduler: фильтры + баллы | [Классы сложности](complexity-classes.md) |
| Token bucket | workqueue: общий темп ретраев | [Скользящее окно](sliding-window.md) |
| Куча | workqueue: отложенные элементы | [Куча](heap-structure.md) |
| Граф + обход | сборщик мусора по `ownerReferences` | [Графы](graphs.md) |

> 🌍 **В коде:** [`waitForPriorityQueue`](https://github.com/kubernetes/kubernetes/blob/v1.31.0/staging/src/k8s.io/client-go/util/workqueue/delaying_queue.go#L183) (client-go, Kubernetes 1.31) — отложенные элементы в `container/heap`, в корне — тот, кому раньше всех пора.

## 5. Docker и BuildKit: хеши как адреса и DAG сборки

Слой образа адресуется **SHA-256 своего содержимого**: одинаковый слой хранится один раз, а
манифест, ссылающийся на слои по хешам, — **структура Меркла**: подмена байта меняет корневой хеш
([криптография](cryptography.md)). BuildKit превращает Dockerfile в **DAG** шагов: каждый шаг
стартует после своих входов, независимые ветви идут параллельно
([топологическая сортировка](topological-sort.md)).

| Структура / алгоритм | Где именно | Глава |
|---|---|---|
| Криптохеш + структура Меркла | адреса слоёв и манифестов | [Криптография](cryptography.md) |
| DAG + топологический порядок | BuildKit: граф шагов сборки | [Топологическая сортировка](topological-sort.md) |

> 🌍 **В коде:** [`marshal`](https://github.com/moby/buildkit/blob/v0.16.0/client/llb/state.go#L195) (BuildKit 0.16) — сначала рекурсивно входы, потом сам шаг: обход в глубину, дающий топологический порядок.

## 6. Ядро Linux: деревья на горячих путях

Очередь готовых задач планировщика — **красно-чёрное дерево**: в CFS по `vruntime`, с ядра **6.6**
в EEVDF — по виртуальному дедлайну, структура та же
([красно-чёрное дерево](red-black-tree-structure.md)). В RB-дереве и дескрипторы **epoll** — того
самого, на котором стоит сетевой поллер Go
([`netpoll_epoll.go`](https://github.com/golang/go/blob/go1.24.0/src/runtime/netpoll_epoll.go)).
Страничный кэш индексирует radix-дерево — родня [Trie](trie-structure.md); области памяти процесса
с 6.1 лежат в широком **maple tree** — довод B-дерева, где «дорогой носитель» — промах кэша CPU.
«Близнец» блока в buddy-аллокаторе — один XOR: `pfn ^ (1 << order)`
([битовые операции](bit-manipulation.md)).

| Структура / алгоритм | Где именно | Глава |
|---|---|---|
| Красно-чёрное дерево | планировщик CFS/EEVDF; epoll | [Красно-чёрное дерево](red-black-tree-structure.md) |
| Radix-дерево | page cache (xarray) | [Trie](trie-structure.md) |
| Широкое дерево | VMA процесса → maple tree | [B-дерево](btree-structure.md) |
| Битовые операции | buddy-аллокатор | [Битовые операции](bit-manipulation.md) |

> 🌍 **В коде:** [`__pick_eevdf`](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/fair.c#L875) (Linux 6.6) — задача с ближайшим дедлайном за O(log n) по красно-чёрному дереву.

## 7. git и diff: Merkle DAG и динамика

Объекты git адресуются хешем содержимого, коммит ссылается на дерево и родителей по хешам — вся
история **Merkle DAG** ([графы](graphs.md)), и `git merge-base` — обход этого графа. `git diff` —
кратчайший скрипт редактирования, родня LCS из [динамического программирования](dynamic-programming.md);
по умолчанию git берёт алгоритм Майерса за O(ND), быстрый на похожих файлах. Сам Go в `gofmt -d`
выбирает другой вариант — **patience diff**: общая подпоследовательность ищется только по строкам,
уникальным в обоих файлах, за O(n log n)
([`internal/diff`](https://github.com/golang/go/blob/go1.24.0/src/internal/diff/diff.go), функция `tgs`).

| Структура / алгоритм | Где именно | Глава |
|---|---|---|
| Криптохеш + Merkle DAG | объекты и история коммитов | [Криптография](cryptography.md), [Графы](graphs.md) |
| DP: LCS / скрипт правок | `git diff`, `gofmt -d` | [DP](dynamic-programming.md) |

## 8. Компилятор Go: стена NP на ровном месте

Планировщик горутин, GC и аллокатор — в [Go изнутри](appendix-go-memory.md#аллокатор-кучи), кучи
таймеров, Swiss Tables и pdqsort — в [экосистеме Go](go-stdlib-structures.md). Здесь один штрих:

«a version of a linear scan register allocator»).

## 9. Балансировщики, кэши и мониторинг

`hash(key) % N` при смене N перемешивает почти все ключи; **консистентное хеширование** двигает
лишь ~1/N ([консистентное хеширование](consistent-hashing.md)). Кэш-узлы вытесняют по
[LRU](pattern-combinations.md) и его приближениям. Перцентили задержек
([две кучи](two-heaps.md)) Prometheus считает **гистограммами** — фиксированные бакеты-счётчики,
которые складываются между серверами (а «среднее двух p99» — бессмыслица); это флагман `streamstats`.

| Структура / алгоритм | Где именно | Глава |
|---|---|---|
| Консистентное хеширование | распределённые кэши, шардирование | [Консистентное хеширование](consistent-hashing.md) |
| LRU и приближения | кэш-серверы, CDN | [Комбинации паттернов](pattern-combinations.md) |
| Гистограммы перцентилей | Prometheus | [Две кучи](two-heaps.md) |

> 🌍 **В коде:** [`simplelru.LRU`](https://github.com/hashicorp/golang-lru/blob/v2.0.7/simplelru/lru.go#L16) (`hashicorp/golang-lru` 2.0.7) — LRU как map плюс двусвязный список, на Go.

## 10. Дедлоки и циклические импорты: поиск цикла в деле

Две транзакции ждут блокировки друг друга. СУБД строит **граф ожиданий** («кто кого ждёт») и ищет
в нём цикл ([графовая связность](graph-connectivity.md)); нашёлся — одну транзакцию откатывают.
`go build` отвергает циклический импорт тем же приёмом: пакет, который ещё загружается, встретился
снова — цикл ([`load/pkg.go`](https://github.com/golang/go/blob/go1.24.0/src/cmd/go/internal/load/pkg.go),
«import cycle not allowed»). Искать цикл можно алгоритмом Кана из `toposort.CanFinish`, обходом в
глубину с раскраской ([топологическая сортировка](topological-sort.md)) или компонентами сильной
связности из `scc.SCC`. **Мосты и точки сочленения** — единые точки отказа в сети или в графе
вызовов сервисов.

| Структура / алгоритм | Где именно | Глава |
|---|---|---|
| Цикл в графе ожиданий | дедлок-детекторы СУБД | [Графовая связность](graph-connectivity.md) |
| Цикл в графе зависимостей | `go build`: циклический импорт | [Топологическая сортировка](topological-sort.md) |
| Мосты / точки сочленения | резервирование сети, граф вызовов сервисов | [Графовая связность](graph-connectivity.md) |

> 🌍 **В коде:** [`DeadLockCheck`](https://github.com/postgres/postgres/blob/REL_16_4/src/backend/storage/lmgr/deadlock.c#L217) (PostgreSQL 16) — ищет цикл в графе ожиданий, когда ожидание блокировки затянулось дольше `deadlock_timeout`.

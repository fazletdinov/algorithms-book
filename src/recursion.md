## 1. База и шаг: факториал

Простейшая, **линейная** рекурсия — один вызов на уровень, глубина n:

```go
func factorial(n int) int {
    if n == 0 {
        return 1 // база: 0! = 1
    }
    return n * factorial(n-1) // шаг: приближаемся к базе
}
```

Здесь видно главное: **база** (`n == 0`) и **шаг**, который уменьшает `n` и потому
обязательно до базы дойдёт. Убери базу — и получишь бесконечную рекурсию и переполнение
стека.

## 2. Дерево вызовов и стек: Фибоначчи

Когда шаг делает **два** рекурсивных вызова, дерево ветвится. Наивный Фибоначчи —
канонический пример, как ветвление превращается в **экспоненту**:

```go
func fib(n int) int {
    if n < 2 {
        return n // база: fib(0)=0, fib(1)=1
    }
    return fib(n-1) + fib(n-2) // два вызова — дерево ветвится
}
```

Проблема — **пересекающиеся подзадачи**: `fib(3)` вызывается несколько раз, `fib(2)` —
ещё чаще. Дерево вызовов раздувается до O(2ⁿ). Лечится **мемоизацией** — запоминаем
ответ подзадачи и не пересчитываем:

```go
func fib(n int) int {
    memo := make([]int, n+1)
    for i := range memo {
        memo[i] = -1
    }
    var f func(k int) int
    f = func(k int) int {
        if k < 2 {
            return k
        }
        if memo[k] >= 0 {
            return memo[k] // уже считали — берём готовое
        }
        memo[k] = f(k-1) + f(k-2)
        return memo[k]
    }
    return f(n)
}
```

Каждая подзадача `fib(k)` теперь решается **один раз** — O(n). Это и есть мост от
рекурсии к [динамическому программированию](dynamic-programming.md): ДП «сверху вниз» — это
рекурсия с мемоизацией.

## 3. Ханойская башня

Эталон рекурсии «разбей на две подзадачи + одно действие». Чтобы перенести `n` дисков
с `A` на `C` (запасной `B`): перенеси `n−1` верхних на `B`, сдвинь самый большой на `C`,
перенеси `n−1` с `B` на `C`. Рекуррента `T(n) = 2·T(n−1) + 1`, ходов ровно `2ⁿ − 1`.

```go
func hanoi(n, from, to, via int) {
    if n == 0 {
        return // база: нет дисков — нечего двигать
    }
    hanoi(n-1, from, via, to) // (n−1) на запасной стержень
    move(from, to)            // самый большой диск — на целевой
    hanoi(n-1, via, to, from) // (n−1) поверх большого
}
```

Листайте «›» и проследите, как каждый ход рождается из дерева рекурсии. Сверху — дерево
**всех** вызовов: синий узел выполняется сейчас, узлы в янтарной рамке ждут на стеке, зелёные
закончились, бледные ещё не вызваны. Под узлом — номер хода, который сделал этот вызов: прочитай
номера слева направо — это ходы по порядку. Рядом со стержнями — стек: те же ждущие вызовы, у
каждого **свои** `n`, `from`, `to`, `via` и строка, на которой он замер. Самый большой диск
переезжает ровно один раз — на полпути, когда корень дерева делает свой ход:

## 4. Мастер-теорема

Мастер-теорема — это **готовая шпаргалка** для рекуррент вида
**`T(n) = a·T(n/b) + f(n)`**, чтобы не рисовать дерево рекурсии каждый раз. Читается так:

- `a` — на **сколько подзадач** разбиваем (сколько рекурсивных вызовов);
- `b` — во **сколько раз меньше** каждая подзадача (`n/b`);
- `f(n)` — работа **вне** рекурсии: разбить вход и склеить ответы.

Вся идея — «перетягивание каната» между двумя силами: работой `f(n)` наверху дерева и
**лавиной листьев** внизу. Размер лавины листьев — это число `n^(log_b a)` (откуда оно
берётся — в разделе [«Почему корректно»](#откуда-в-мастер-теореме-nlog_b-a) ниже; пока
достаточно считать его «весом базовых случаев»). Кто перетянет — тот и задаёт ответ:

| Случай | Кто перетягивает | Итог `T(n)` |
|--------|------------------|-------------|
| 1 | **Листья**: `f(n)` заметно **меньше** `n^(log_b a)` | `Θ(n^(log_b a))` |
| 2 | **Ничья**: `f(n)` примерно **равна** `n^(log_b a)` | `Θ(n^(log_b a)·log n)` |
| 3 | **Корень**: `f(n)` заметно **больше** `n^(log_b a)` | `Θ(f(n))` |

Как пользоваться на практике — три шага: (1) выпиши `a` и `b`, посчитай `n^(log_b a)`;
(2) сравни с `f(n)`; (3) прочитай ответ из строки таблицы. Примеры:

- **Сортировка слиянием**: `T(n) = 2·T(n/2) + O(n)`. `log₂2 = 1`, значит `n^(log_b a) = n¹ = n`.
  А `f(n) = n` — **ровно столько же** → ничья, случай 2 → **Θ(n log n)**.
- **Бинарный поиск**: `T(n) = T(n/2) + O(1)`. `log₂1 = 0`, значит `n^(log_b a) = n⁰ = 1`.
  И `f(n) = 1` — тоже ничья, случай 2 → **Θ(log n)**.
- **Обход дерева**: `T(n) = 2·T(n/2) + O(1)`. `n^(log_b a) = n`, а `f(n) = 1` **меньше** →
  перетягивают листья, случай 1 → **Θ(n)**.

<details class="algo-details">
<summary>⚠️ Точная формулировка (важная оговорка — читать, когда освоишься)</summary>

Слова «заметно меньше/больше» выше — намеренное упрощение. Строго теорема требует, чтобы
разрыв был **полиномиальным**, а не любым:

- **Случай 1** работает, если `f(n) = O(n^(log_b a − ε))` для некоторого `ε > 0` —
  то есть `f(n)` меньше «веса листьев» не на чуть-чуть, а в `nᵉ` раз.
- **Случай 3** работает, если `f(n) = Ω(n^(log_b a + ε))` **и** выполнено условие
  регулярности `a·f(n/b) ≤ c·f(n)` для некоторого `c < 1` (по сути: `f` не должна
  «скакать» — работа на слияние убывает вниз по дереву предсказуемо).

Практический вывод: **у теоремы есть «дыра»**. Если `f(n)` отличается от `n^(log_b a)` лишь
в **логарифмическое** число раз — в любую сторону: `f(n) = n·log n` (больше `n`, но не в `nᵉ`
раз) или `f(n) = n/log n` (меньше `n`, но не в `nᵉ` раз) при `n^(log_b a) = n` — разрыв **не
полиномиальный**: ни один из трёх случаев не подходит, и мастер-теорема просто **молчит**.
Такие рекурренты берут более общими средствами (метод Акра — Бацци или прямой подсчёт по
дереву). Знать про эту дыру важнее, чем зубрить `ε`: не всякую рекурренту закрывает мастер-теорема.

</details>

## ⚡ Что помнить на собеседовании

- Любая рекурсия = **база + шаг к базе**. Нет базы или шаг не уменьшает размер →
  бесконечность и stack overflow.
- **Два вызова на одни и те же подзадачи** → экспонента; спасает мемоизация (O(n)).
- **Глубина стека** = высота дерева рекурсии. Для линейной рекурсии это O(n) — на больших
  `n` разворачивай в цикл.
- **Мастер-теорема** мгновенно даёт оценку divide-and-conquer: сравни `f(n)` с `n^(log_b a)`.
- Go **не делает** tail-call оптимизацию: хвостовой вызов не превращается в цикл сам.

## 🧠 Почему это корректно

### Индукция = рекурсия

Корректность рекурсии доказывается **математической индукцией**, и это та же структура:
**база** индукции = база рекурсии; **шаг** индукции («если верно для меньших, то верно
для n») = рекурсивный шаг. Поэтому «скачок веры» (предположить, что вызов для `n−1` уже
корректен) — не магия, а индукционное предположение.

### Почему два условия обязательны

Рекурсия завершается и верна, только если: (1) есть **достижимая база**, и (2) каждый шаг
**строго приближается** к ней (уменьшает меру: `n`, длину, глубину). Нарушь любое — и
либо бесконечный спуск (нет базы / шаг не уменьшает), либо неверный ответ (база неверна).

### Откуда в мастер-теореме `n^(log_b a)`

Дерево рекурсии имеет глубину `log_b n` (делим на `b` до базы), а на уровне `i` —
`aⁱ` подзадач. На последнем уровне листьев `a^(log_b n) = n^(log_b a)`. Это число и есть
«вес базовых случаев». Мастер-теорема просто спрашивает: что перевешивает — суммарная
работа `f(n)` ближе к корню или лавина листьев? Три случая — три ответа.

## ⚙️ Цена на практике

### Глубина стека — это память

Каждый незавершённый вызов держит кадр на стеке. Линейная рекурсия глубины `n` тратит
O(n) памяти стека, которой у итеративной версии нет. Горутины Go стартуют с крошечного
стека (минимум 2 КБ) и растят его автоматически, но глубокая рекурсия (миллионы кадров) всё равно
упрётся в лимит (`runtime: goroutine stack exceeds...`). Глубокую линейную рекурсию —
**в цикл**.

### Go не оптимизирует хвостовую рекурсию

В некоторых языках хвостовой вызов (рекурсия последним действием) компилятор превращает в
цикл с O(1) стека. **Go этого не делает** намеренно — ради читаемых трасс и стектрейсов.
Так что в Go «хвостовая» рекурсия по стеку не дешевле обычной; нужна O(1) память — пиши цикл
руками.

### Рекурсия ⇄ итерация и мемоизация

Любую рекурсию можно развернуть в цикл (иногда — с явным стеком). Стоит это делать, когда:
глубина велика (риск переполнения) или нужен жёсткий контроль памяти. А вот при
**пересекающихся** подзадачах сначала добавь мемоизацию — это превращает экспоненту в
линию, не теряя ясности рекурсивной записи.

## ⚠️ Типичные ошибки

1. **Нет базы или она недостижима** — бесконечная рекурсия, переполнение стека.
2. **Шаг не уменьшает размер** (забыли `n-1`, передали то же самое) — тоже бесконечность.
3. **Наивная рекурсия на пересекающихся подзадачах** — `fib`, `grid paths` без мемоизации:
   экспонента вместо линии/полинома.
4. **Глубина рекурсии ~ n на больших данных** — stack overflow; нужна итерация.
5. **Неверная мера** — рекурсия не сходится, потому что уменьшается не то, что приближает к базе.
6. **Ожидание tail-call оптимизации в Go** — её нет, стек всё равно растёт.

## 📝 Разбор задачи: Фибоначчи от экспоненты к линии

> **Задача.** Вычислить n-е число Фибоначчи. Пример: `fib(10) = 55`.

**Шаг 1. Наивно — прямая рекурсия, O(2ⁿ).**

```go
func fib(n int) int {
    if n < 2 {
        return n
    }
    return fib(n-1) + fib(n-2)
}
```

Работает и читается как определение. Но `fib(40)` уже считается заметно: дерево вызовов
содержит ~330 **миллионов** узлов (точно: `2·fib(41)−1`; растёт это как `φⁿ ≈ 1.618ⁿ`, так что
`O(2ⁿ)` — щедрая верхняя оценка). Пересчёт нарастает лавиной к мелким подзадачам: `fib(38)`
внутри `fib(40)` вычисляется всего 2 раза, `fib(30)` — уже 89 раз, а `fib(20)` — 10 946 раз.

**Шаг 2. Наблюдение.** Различных подзадач всего `n` (`fib(0)..fib(n)`), а наивная версия
решает их экспоненциально много раз. Запомним результат каждой.

**Шаг 3. Мемоизация — O(n).** (Код выше в разделе 2.) Каждое `fib(k)` считается один раз;
дерево «схлопывается» в линию. Это и есть ДП «сверху вниз».

**Шаг 4. Свёртка до O(1) памяти.** Раз нужны только два последних значения — рекурсия и
вовсе не нужна:

```go
func fib(n int) int {
    a, b := 0, 1
    for i := 0; i < n; i++ {
        a, b = b, a+b
    }
    return a
}
```

Путь «наивная рекурсия → мемоизация → итерация» — типичный для divide-and-conquer и ДП:
сначала ясная рекурсивная формула, потом борьба с её ценой.

**🔴 Добивка** — когда основа идёт уверенно:

- [Pow(x, n)](https://leetcode.com/problems/powx-n/) (LeetCode 50) — рекурсия «дели степень пополам»

> 🧭 **Не пошла задача из основы?** Проверь **три места, и ровно эти три**: база (на чём
> рекурсия останавливается), переход (как ответ склеивается из ответа для меньшего входа) и
> то, что вход убывает **строго**. Зависла или переполнила стек — виновато третье. Отвечает
> неверно — первое или второе. Отдельно про 50: `n` бывает отрицательным (`x⁻ⁿ = 1/xⁿ`), а
> наивное `x * pow(x, n-1)` делает `n` вызовов — при `n ≈ 2³¹` это два миллиарда кадров, и
> горутина упрётся в лимит стека. Отсюда «дели пополам»: `pow(x, n) = pow(x, n/2)²`, глубина
> `log n`. (В C++ и Java есть ещё ловушка: `-n` при `n = INT_MIN` переполняет 32-битный `int`.
> В Go `int` 64-битный, и она не срабатывает — но если пишешь на обоих, помни о ней.)

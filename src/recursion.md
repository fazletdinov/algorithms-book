## 1. База и шаг: факториал

Простейшая, **линейная** рекурсия — каждый вызов, кроме базы, зовёт себя ровно один раз:

```go
func factorial(n int) int {
    if n == 0 {
        return 1 // база: 0! = 1
    }
    return n * factorial(n-1) // шаг: приближаемся к базе
}
```

Здесь видно главное: **база** (`n == 0`) и **шаг**, который уменьшает `n` и потому
обязательно до базы дойдёт. Проследим `factorial(3)` по вызовам:

```text
factorial(3)                    ждёт factorial(2)
  factorial(2)                  ждёт factorial(1)
    factorial(1)                ждёт factorial(0)
      factorial(0)  → 1         база: никого не зовёт
    factorial(1)  = 1 · 1 = 1
  factorial(2)  = 2 · 1 = 2
factorial(3)  = 3 · 2 = 6
```

Вниз идут только вызовы — все умножения случаются на обратном пути. Пока `factorial(0)` не
вернулся, три вызова выше ждут, и у каждого своя `n`. Незавершённые вызовы — три ждущих и тот,
что выполняется сейчас, — лежат в **стеке вызовов** (call stack): последний вызванный
заканчивается первым. Запись об одном вызове — его аргументы,
локальные переменные и место, куда вернуть ответ, — называется **кадром** (frame); в
[главе о Big-O](big-o.md#2-худший-средний-лучший-случай-и-память) кадр уже мелькал как память
вызова. Здесь в самый глубокий момент на стеке 4 кадра, от `factorial(3)` до `factorial(0)`; в
общем случае `n + 1`, то есть память `O(n)`.

Убери базу — и вызовы будут класть кадры без конца, пока стек горутины не упрётся в свой
предел: это **переполнение стека**.

## 2. Дерево вызовов и стек: Фибоначчи

Нарисуй каждый вызов узлом, а вызовы, которые он сделал, — его детьми: получится **дерево
вызовов**. У факториала оно вытянуто в цепочку. Его форма и задаёт цену: время — сумма работы всех
узлов (если работа у вызовов одинакова — число узлов на работу одного вызова); память стека —
число узлов на самой длинной ветке.

Когда шаг делает **два** рекурсивных вызова, дерево ветвится. Наивный Фибоначчи —
канонический пример, как ветвление превращается в **экспоненту**:

```go
func fib(n int) int {
    if n < 2 {
        return n // база: fib(0)=0, fib(1)=1
    }
    return fib(n-1) + fib(n-2) // два вызова — дерево ветвится
}
```

Проблема — **пересекающиеся подзадачи**: `fib(3)` вызывается несколько раз, `fib(2)` —
ещё чаще. Дерево вызовов раздувается до O(2ⁿ): у `fib(40)` в нём уже 331 160 281 узел, и
`fib(20)` внутри считается 10 946 раз.

Лечится это **мемоизацией** — запоминаем ответ подзадачи и не пересчитываем:

```go
func fib(n int) int {
    memo := make([]int, n+1)
    for i := range memo {
        memo[i] = -1
    }
    var f func(k int) int
    f = func(k int) int {
        if k < 2 {
            return k
        }
        if memo[k] >= 0 {
            return memo[k] // уже считали — берём готовое
        }
        memo[k] = f(k-1) + f(k-2)
        return memo[k]
    }
    return f(n)
}
```

Каждая подзадача `fib(k)` теперь решается **один раз** — O(n). Это и есть мост от
рекурсии к [динамическому программированию](dynamic-programming.md): ДП «сверху вниз» — это
рекурсия с мемоизацией.

## 3. Ханойская башня

Эталон рекурсии «разбей на две подзадачи + одно действие». Чтобы перенести `n` дисков
с `A` на `C` (запасной `B`): перенеси `n−1` верхних на `B`, сдвинь самый большой на `C`,
перенеси `n−1` с `B` на `C`.

```go
func hanoi(n, from, to, via int) {
    if n == 0 {
        return // база: нет дисков — нечего двигать
    }
    hanoi(n-1, from, via, to) // (n−1) на запасной стержень
    move(from, to)            // самый большой диск — на целевой
    hanoi(n-1, via, to, from) // (n−1) поверх большого
}
```

Сколько это ходов? Обозначим `T(n)` число ходов для `n` дисков. Код делает два вызова на
`n − 1` дисках и один ход между ними: `T(n) = T(n−1) + 1 + T(n−1)`, а `T(0) = 0`. Посчитаем:
`T(1) = 1`, `T(2) = 3`, `T(3) = 7` — каждый раз «удвой и прибавь один», то есть `2ⁿ − 1`. Запись, где
ответ для `n` выражен через ответ для меньшего входа, называется **рекуррентой**; у Ханоя она
`T(n) = 2·T(n−1) + 1`.

Листай «›»: дерево сверху — все вызовы, что сделает `hanoi(3, …)`, а что значат цвета узлов,
подписано в легенде. Под узлом — номер хода, который сделал этот вызов: прочитай номера слева
направо — это ходы по порядку.

## 4. Мастер-теорема

Рекурсию «раздели на части» оценивают по дереву вызовов: **сколько уровней × сколько работы на
уровне**. Два примера на `n = 8`:

- **Сортировка слиянием** режет массив пополам, сортирует половины и сливает их за `n` шагов (её
  разбирает [глава о сортировках](sorting.md), она впереди). Уровней 4: 8 → 4 → 2 → 1 —
  [логарифм](big-o.md#логарифм--сколько-раз-делить-пополам) плюс уровень листьев. На каждом уровне
  куски вместе дают все 8 элементов — 8 шагов. Всего `4 · 8 = 32` — порядка `n·log n`, то есть **O(n log n)**.
- **Поиск делением пополам** делает один вызов на половине и одно сравнение. Уровней те же 4, на
  каждом 1 шаг — всего 4, порядка `log n`, то есть **O(log n)**.

**Мастер-теорема** — готовая формула для таких деревьев, чтобы не рисовать уровни каждый раз; на
первом проходе хватит посчитать уровни руками.

<details class="algo-details">
<summary>⚙️ Второй проход: мастер-теорема — читать, когда освоишься</summary>

Рекурсия, которая режет вход на части, даёт рекурренту другого вида. Пусть функция делит вход
пополам, вызывает себя на обеих половинах и ещё тратит `n` шагов на то, чтобы склеить ответы:
`T(n) = 2·T(n/2) + n`. Разложим работу по уровням дерева вызовов при `n = 8`: узел размера `m`
тратит `m` шагов на склейку, лист размера 1 стоит 1:

```text
T(n) = 2·T(n/2) + n,  n = 8          работа на уровне
уровень 0:   8                        8
уровень 1:   4 + 4                    8
уровень 2:   2 + 2 + 2 + 2            8
уровень 3:   1+1+1+1+1+1+1+1          8
                                     всего 32
```

Уровней `log₂8 + 1 = 4`: восьмёрку можно трижды поделить пополам
([логарифм](big-o.md#логарифм--сколько-раз-делить-пополам)), и ещё уровень листьев. На каждом
уровне по 8 — всего 32, то есть `n·(log n + 1)`. Работа размазана по уровням поровну — это
**ничья**, итог `Θ(n log n)`.

Замени `+ n` на `+ 1` (склейка за один шаг) — уровни дадут 1, 2, 4, 8, всего 15. Каждый уровень
вдвое тяжелее прошлого, поэтому вся сумма меньше удвоенного нижнего уровня, а он — `n` листьев
по 1: работа копится в листьях, итог `Θ(n)`. Замени на `+ n²` — уровни дадут 64, 32, 16, 8, всего 120.
Теперь каждый уровень вдвое легче прошлого, сумма меньше удвоенного корня, а он стоит `n²`:
работа сосредоточена наверху, итог `Θ(n²)`. **Мастер-теорема — эти три картинки, записанные формулой.**

Она даёт **готовый ответ** для рекуррент вида **`T(n) = a·T(n/b) + f(n)`**, чтобы не рисовать
уровни каждый раз. Читается так:

- `a` — на **сколько подзадач** разбиваем (сколько рекурсивных вызовов);
- `b` — во **сколько раз меньше** каждая подзадача (`n/b`);
- `f(n)` — работа **вне** рекурсии: разбить вход и склеить ответы.

Вся идея — «перетягивание каната» между двумя силами: работой `f(n)` наверху дерева и
**лавиной листьев** внизу (лист — вызов-база, который никого больше не зовёт). Размер лавины
листьев — это число `n^(log_b a)`, то есть `n` в степени «[логарифм](big-o.md#логарифм--сколько-раз-делить-пополам)
`a` по основанию `b`» (в картинках выше `a = b = 2`, `log₂2 = 1`, и при `n = 8` листьев `n¹ = 8`; откуда оно
берётся в общем случае — в последнем абзаце этого блока; пока
достаточно считать его «весом базовых случаев»). Кто перетянет — тот и задаёт ответ:

| Случай | Кто перетягивает | Итог `T(n)` |
|--------|------------------|-------------|
| 1 | **Листья**: `f(n)` заметно **меньше** `n^(log_b a)` | `Θ(n^(log_b a))` |
| 2 | **Ничья**: `f(n)` примерно **равна** `n^(log_b a)` | `Θ(n^(log_b a)·log n)` |
| 3 | **Корень**: `f(n)` заметно **больше** `n^(log_b a)` | `Θ(f(n))` |

Как пользоваться на практике — три шага: (1) выпиши `a` и `b`, посчитай `n^(log_b a)`;
(2) сравни с `f(n)`; (3) прочитай ответ из строки таблицы. Сначала — три картинки выше
(у всех `a = 2`, `b = 2`, значит `n^(log_b a) = n`):

- `T(n) = 2·T(n/2) + n`: `f(n) = n` — **ровно столько же** → ничья, случай 2 → **Θ(n log n)**.
  Это сортировка слиянием.
- `T(n) = 2·T(n/2) + 1`: `f(n) = 1` **меньше** → перетягивают листья, случай 1 → **Θ(n)**.
  Так обходят дерево, у которого поддеревья поровну: вызов на каждом и O(1) работы в узле.
- `T(n) = 2·T(n/2) + n²`: `f(n) = n²` **больше** → перетягивает корень, случай 3 → **Θ(n²)**.

И один вызов вместо двух: `T(n) = T(n/2) + 1` — так поиск делением пополам отбрасывает половину
за одно сравнение. `a = 1`, `log₂1 = 0`, значит `n^(log_b a) = n⁰ = 1`. И `f(n) = 1` — тоже
ничья, случай 2 → **Θ(log n)**: уровней `log n`, на каждом одна единица работы. Делишь не на 2, а
на `k` (`T(n) = T(n/k) + 1`) — уровней `log_k n`, и это тоже `Θ(log n)`: основание логарифма
Big-O не различает.

**Откуда `n^(log_b a)`.** Это просто число листьев дерева рекурсии: каждый уровень делит задачу на `b` и умножает число
подзадач на `a`, и к самому низу листьев набирается `n^(log_b a)` — «вес базовых случаев». На
картинке в начале блока (`a = b = 2`, `n = 8`) дерево глубины 3, и внизу `8` листьев, то есть `n`.
Мастер-теорема просто спрашивает: что перевешивает — суммарная
работа `f(n)` ближе к корню или лавина листьев? Три случая — три ответа.

</details>

## ⚡ Что помнить на собеседовании

- Любая рекурсия = **база + шаг к базе**. Нет базы или шаг не уменьшает размер →
  бесконечный спуск и переполнение стека.
- **Два вызова на одни и те же подзадачи** → экспонента; спасает мемоизация (O(n)).
- **Глубина стека** = высота дерева рекурсии. Для линейной рекурсии это O(n) — на больших
  `n` разворачивай в цикл.
- **«Разделяй и властвуй»** оценивай деревом вызовов: уровни × работа на уровне (слияние — O(n log n),
  поиск пополам — O(log n)); готовая формула — мастер-теорема.
- Go **не превращает** хвостовой вызов в цикл: стек растёт и у хвостовой рекурсии.

## 🧠 Почему это корректно

### Индукция = рекурсия

Корректность рекурсии доказывается **математической индукцией**, и это та же структура:
**база** индукции = база рекурсии; **шаг** индукции («если верно для меньших, то верно
для n») = рекурсивный шаг. Поэтому «скачок веры» (предположить, что вызов для `n−1` уже
корректен) — не магия, а индукционное предположение.

### Почему два условия обязательны

Нет **достижимой базы** или шаг **не уменьшает меру** (`n`, длину, глубину) — спуск бесконечен;
база неверна — неверен и ответ.

## ⚙️ Цена на практике

Глубокую рекурсию в Go разворачивай в цикл: каждый вызов держит кадр на стеке, а хвостовой вызов Go
в цикл не превращает.

<details class="algo-details">
<summary>⚙️ Второй проход: стек, хвостовой вызов и итерация — читать, когда освоишься</summary>

**Глубина стека — это память.** Каждый незавершённый вызов держит кадр на стеке. Линейная рекурсия глубины `n` тратит
O(n) памяти стека, которой у итеративной версии нет. Горутины Go стартуют с крошечного
стека (минимум 2 КБ) и растят его автоматически, но очень глубокая рекурсия всё равно упрётся в
предел 1 ГБ (`runtime: goroutine stack exceeds...`); подробнее и замер — в главе о графах, раздел
[«Глубина рекурсии DFS»](graphs.md#глубина-рекурсии-dfs--цена-и-предел). Глубокую линейную рекурсию —
**в цикл**.

**Go не оптимизирует хвостовую рекурсию.** В некоторых языках хвостовой вызов (рекурсия последним действием) компилятор превращает в
цикл с O(1) стека. **Go этого не делает** намеренно — ради читаемых трасс и стектрейсов.
Так что в Go «хвостовая» рекурсия по стеку не дешевле обычной; нужна O(1) память — пиши цикл
руками.

**Рекурсия ⇄ итерация и мемоизация.** Любую рекурсию можно развернуть в цикл (иногда — с явным стеком). Стоит это делать, когда:
глубина велика (риск переполнения) или нужен жёсткий контроль памяти. А вот при
**пересекающихся** подзадачах сначала добавь мемоизацию — это превращает экспоненту в
линию, не теряя ясности рекурсивной записи.

</details>

## ⚠️ Типичные ошибки

1. **Нет базы или шаг к ней не приближает** (забыли `n-1`, уменьшается не то) — бесконечная рекурсия, переполнение стека.
2. **Наивная рекурсия на пересекающихся подзадачах** (`fib` без мемоизации) — экспонента вместо линии.
3. **Глубина рекурсии ~ n на больших данных** — переполнение стека; нужна итерация (и хвостовой вызов Go не спасёт).

> 🌍 **Где это в настоящем коде**
>
> - [`ast.Walk`](https://github.com/golang/go/blob/go1.24.0/src/go/ast/walk.go#L33) (Go 1.24) — обход дерева разбора Go-программы: функция вызывает себя для каждого ребёнка узла; на ней же построен `ast.Inspect`.
> - [`walkDir`](https://github.com/golang/go/blob/go1.24.0/src/path/filepath/path.go#L309) (Go 1.24) — сердце `filepath.WalkDir`: для каждой вложенной папки вызывает себя же, а на файле (база рекурсии) сразу возвращается.

## 📝 Разбор задачи: Фибоначчи от экспоненты к линии

> **Задача.** Вычислить n-е число Фибоначчи. Пример: `fib(10) = 55`.

**Шаги 1–3** — в [разделе 2](#2-дерево-вызовов-и-стек-фибоначчи): наивно O(2ⁿ), различных
подзадач всего `n + 1`, мемоизация даёт O(n). Но остаются массив `memo` и около `n` кадров на стеке.

**Шаг 4. Свёртка до O(1) памяти.** Раз нужны только два последних значения — рекурсия и
вовсе не нужна:

```go
func fib(n int) int {
    a, b := 0, 1
    for i := 0; i < n; i++ {
        a, b = b, a+b
    }
    return a
}
```

Путь «наивная рекурсия → мемоизация → цикл» — типичный для ДП:
сначала ясная рекурсивная формула, потом борьба с её ценой.

<details class="algo-details">
<summary>Если застрял: Pow(x, n)</summary>

`n` бывает отрицательным (`x⁻ⁿ = 1/xⁿ`), а наивное `x * pow(x, n-1)` делает `n` вызовов — при
`n ≈ 2³¹` это два миллиарда кадров, и горутина упрётся в предел стека. Отсюда «дели пополам»:
`pow(x, n) = pow(x, n/2)²` (и ещё один множитель `x` при нечётном `n`), глубина `log n`. (В C++
и Java есть ещё ловушка: `-n` при `n = INT_MIN` переполняет 32-битный `int`. В Go `int`
64-битный, и она не срабатывает — но если пишешь на обоих, помни о ней.)

</details>

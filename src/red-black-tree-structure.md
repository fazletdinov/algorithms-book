> 🧭 **Зачем отдельная глава.** Когда тебе в Go нужен упорядоченный набор, ты берёшь срез и
> сортируешь. А вот в C++ `std::map`/`std::set`, в Java `TreeMap`/`TreeSet`, в планировщике задач
> **ядра Linux** (CFS) под капотом — **красно-чёрное дерево**. Это *рабочий по умолчанию*
> самобалансирующийся BST индустрии. Почему не [AVL](avl-tree-structure.md), который мы уже
> знаем? Потому что AVL держит баланс строже и потому **чаще делает повороты при вставке и
> удалении** — а красно-чёрное соглашается на чуть большую высоту ради того, чтобы **реже
> перестраиваться**. Для структуры, куда постоянно пишут, это выгодный размен. Разберём, как
> «покраска узлов» заменяет строгую балансировку.

## 🧱 Как это держит баланс

Ключевая мысль на пальцах: раз **на всех путях поровну чёрных**, а красные не могут идти
подряд, то **самый длинный путь не более чем вдвое длиннее самого короткого**. Короткий путь —
это одни чёрные узлы; длинный — чёрные, между которыми воткнуты красные, но не два подряд.
«Вдвое» — это константа, поэтому высота остаётся `O(log n)`. Вот и весь секрет: не считаем
точные высоты поддеревьев (как AVL), а держим грубее — «пути не различаются больше, чем вдвое».

## Вставка

Вставляем как в обычный BST — спускаемся к листу. Новый узел красим в **красный** (чтобы не
нарушить правило про равное число чёрных — красный не добавляет чёрного на пути). Но красный
узел может оказаться под красным родителем — тогда чиним нарушение, поднимаясь вверх, двумя
инструментами:

- **дядя красный** → *перекраска*: родителя и дядю в чёрный, деда в красный (проблема «красный
  под красным» уезжает на два уровня выше, повторяем);
- **дядя чёрный** → *поворот* деда (как в AVL) + перекраска — и нарушение исчезает локально.

```go
func (t *RBTree) Insert(val int) {
    z := t.bstInsert(val)  // спуск как в BST
    z.color = RED          // новый узел — красный
    for z.parent.color == RED {   // пока есть «красный под красным»
        if uncle.color == RED {
            recolor(parent, uncle, grandparent) // перекраска
            z = grandparent    // поднимаемся выше
        } else {
            z = rotateToLine(z)   // ломаный случай → прямой
            rotateGrandparent()   // поворот + перекраска
        }
    }
    t.root.color = BLACK   // корень всегда чёрный
}
```

Нажми «▶»: в готовое дерево вставляется новый **красный** узел, и видно, как нарушение
«красный-красный» чинится перекраской/поворотом, пока все правила не восстановятся (жёлтая
обводка — узлы, которые сейчас чиним):

## 🧠 Почему это O(log n)

Обозначим **чёрную высоту** `bh(x)` — число чёрных узлов на пути от `x` вниз до листа (одинаковое
по правилу ⭐). Два коротких шага рассуждения:

1. В поддереве с корнем `x` не меньше `2^bh(x) − 1` узлов (доказывается индукцией: у ребёнка
   чёрная высота либо та же, либо на 1 меньше, и дерево «набирается» вглубь).
2. Из-за запрета «красный-красный» на любом пути красных не больше, чем чёрных. Значит вся высота
   `h ≤ 2·bh(root)`.

Соединяя: `n ≥ 2^(h/2) − 1`, откуда `h ≤ 2·log₂(n+1)` — то есть `O(log n)`. Все операции идут
по одному пути вниз плюс починка вверх (константа поворотов), поэтому тоже `O(log n)`.

<details class="algo-details">
<summary>Почему поворотов при вставке ≤ 2, а перекрасок может быть много</summary>

Перекраска (случай «дядя красный») не меняет структуру — только цвета — и «поднимает» проблему
на два уровня вверх. Таких шагов может быть до `O(log n)`, но они дёшевы. Как только встречается
случай «дядя чёрный», делается **один-два поворота** — и всё, цикл завершается. Поэтому
структурных перестроений (поворотов) на вставку — не больше двух, тогда как AVL иногда каскадит
повороты. Это и есть причина, почему RB-деревья предпочитают там, где много записей.

</details>

## ⚙️ Цена на практике: почему RB, а не AVL

Обе структуры дают `O(log n)` и обе балансируются поворотами. Разница — в характере:

| | AVL | Красно-чёрное |
|---|---|---|
| Строгость баланса | жёсткая (`|hL−hR| ≤ 1`) | слабее (пути ≤ ×2) |
| Высота | ниже → **поиск чуть быстрее** | чуть выше |
| Повороты на запись | может каскадить | **≤ 2, реже** |
| Где применяют | много чтений, мало записей | универсальный default (`std::map`, `TreeMap`, ядро Linux) |

Вывод инженера: **AVL — когда доминирует поиск; красно-чёрное — когда баланс чтений и записей**
(и потому это дефолт стандартных библиотек). В Go в stdlib упорядоченной map нет (есть `map` —
хеш, без порядка), поэтому за упорядоченным набором идут либо к отсортированному срезу +
[`slices.BinarySearch`](https://pkg.go.dev/slices#BinarySearch), либо к [B-дереву](btree-structure.md)
(`google/btree`) — на практике его дисковая/кэш-локальность часто важнее, чем у бинарных деревьев.

> 🔧 **Где это в реальных системах.** `std::map`/`std::set`/`std::multimap` в C++; `TreeMap`/
> `TreeSet` в Java; **ядро Linux** — планировщик CFS (дерево процессов по vruntime), тайминги,
> управление памятью (`vm_area_struct`); `epoll` внутри. Красно-чёрное дерево — самая
> используемая балансировка «общего назначения» в системном коде.

## ⚠️ Типичные ошибки

1. **Забыть, что новый узел красный** — если вставлять чёрным, сразу ломается равенство чёрных
   высот (правило ⭐), и чинить куда труднее.
2. **Перепутать случаи дяди** — красный дядя лечится *перекраской*, чёрный — *поворотом*; смешать
   их значит зациклиться или сломать инвариант.
3. **Забыть перекрасить корень в чёрный** в конце — корень обязан быть чёрным.
4. **«Ломаный» случай** (узел — правый ребёнок левого родителя, или наоборот) — сперва малый
   поворот, сводящий к «прямому», и только потом основной.

> сортируешь. А вот в C++ `std::map`/`std::set`, в Java `TreeMap`/`TreeSet`, в планировщике задач

> **красно-чёрное дерево**. Это *рабочий по умолчанию*
> самобалансирующийся BST индустрии. Почему не [AVL](avl-tree-structure.md), который мы уже
> знаем? Потому что AVL держит баланс строже и потому **перестраивается чаще** (а при удалении
> может каскадить повороты до самого корня) — красно-чёрное же соглашается на чуть большую высоту
> ради того, чтобы **реже перестраиваться**. Для структуры, куда постоянно пишут, это выгодный
> размен. Разберём, как «покраска узлов» заменяет строгую балансировку.

## 🧱 Как это держит баланс

Ключевая мысль на пальцах: раз **на всех путях поровну чёрных**, а красные не могут идти
подряд, то **самый длинный путь не более чем вдвое длиннее самого короткого**. Короткий путь —
это одни чёрные узлы; длинный — чёрные, между которыми воткнуты красные, но не два подряд.
«Вдвое» — это константа, поэтому высота остаётся `O(log n)`. Вот и весь секрет: не считаем
точные высоты поддеревьев (как AVL), а держим грубее — «пути не различаются больше, чем вдвое».

## 🎭 Откуда взялись правила: это 2-3-4-дерево в гриме

Четыре правила выглядят как заклинание — пока не увидишь, **что именно они кодируют**.
Представь дерево, в узле которого живёт не один ключ, а **от одного до трёх**, у узла —
от двух до четырёх детей, и **все листья на одной глубине** (вставка при переполнении
не углубляет дерево, а *расщепляет* узел и отдаёт средний ключ наверх). Это 2-3-4-дерево —
младший брат [B-дерева](btree-structure.md) с шириной 4.

Красно-чёрное дерево — **побитовая кодировка такого дерева обычными бинарными узлами**:

- узел 2-3-4-дерева = **чёрный узел + его красные дети**, «приклеенные» сверху:
  один ключ — одинокий чёрный; два ключа — чёрный с одним красным ребёнком;
  три ключа — чёрный с двумя красными;
- **красный цвет** значит ровно одно: «я не отдельный узел, я ключ, вклеенный
  в узел родителя».

Теперь правила перестают быть магией:

- «нет двух красных подряд» — в узел помещается не больше трёх ключей: красный под
  красным означал бы узел из четырёх+ ключей, которого в 2-3-4-дереве не бывает;
- «на всех путях поровну чёрных» — это «все листья 2-3-4-дерева на одной глубине»:
  **чёрная высота КЧ-дерева = высота 2-3-4-дерева**. Идеальный баланс широкого дерева
  и есть источник `O(log n)`;
- **перекраска** (случай «дядя красный») — это *расщепление переполненного узла*:
  средний ключ (дед) «всплывает» наверх и краснеет — то есть вклеивается в узел уровнем
  выше, а проблема уезжает туда же. Вот почему перекраска поднимается по дереву;
- **поворот** (случай «дядя чёрный») — перекладывание ключей внутри одного узла
  2-3-4-дерева, локальная операция. Вот почему поворотов нужно не больше двух.

Держи эту картинку рядом при чтении следующих двух разделов — каждый случай вставки и
удаления «переводится» на язык 2-3-4-дерева одной фразой, и запоминать становится нечего.

## Вставка

Вставляем как в обычный BST — спускаемся к листу. Новый узел красим в **красный** (чтобы не
нарушить правило про равное число чёрных — красный не добавляет чёрного на пути). Но красный
узел может оказаться под красным родителем — тогда чиним нарушение, поднимаясь вверх, двумя
инструментами:

- **дядя красный** → *перекраска*: родителя и дядю в чёрный, деда в красный (проблема «красный
  под красным» уезжает на два уровня выше, повторяем);
- **дядя чёрный** → *поворот* деда (как в AVL) + перекраска — и нарушение исчезает локально.

Ниже — **псевдокод на мотив Go** (обозначения случаев, не компилируемая реализация:
`uncle`/`recolor` — это «что делаем», а не готовые функции). Рабочую версию с полным
разбором случаев ты соберёшь сам в тренажёре `rbtree` в конце главы.

```go
func (t *RBTree) Insert(val int) {
    z := t.bstInsert(val)  // спуск как в BST
    z.color = RED          // новый узел — красный
    for z.parent.color == RED {   // пока есть «красный под красным»
        if uncle.color == RED {
            recolor(parent, uncle, grandparent) // перекраска
            z = grandparent    // поднимаемся выше
        } else {
            z = rotateToLine(z)   // ломаный случай → прямой
            rotateGrandparent()   // поворот + перекраска
        }
    }
    t.root.color = BLACK   // корень всегда чёрный
}
```

## ➖ Удаление

Удаление сложнее вставки, но идея та же — локальный ремонт вверх по дереву. Сначала убираем
узел **как в BST** (у узла с двумя детьми — копируем значение преемника и физически убираем
преемника). Дальше всё решает **цвет ушедшего узла**:

- ушёл **красный** — чёрная высота не изменилась, чинить нечего, готово;
- ушёл **чёрный** — на его месте образуется **«двойной чёрный»**: путь через это место потерял
  один чёрный узел, нарушив правило ⭐. Этот «долг» проталкиваем вверх, пока не погасим.

Гасят «двойной чёрный» по **цвету брата** узла и цвету детей брата — это четыре случая
(перекраски и повороты). Пусть `x` — узел с долгом, и он **левый** ребёнок; для правого всё
зеркально. **Ближний** ребёнок брата — тот, что ближе к `x` (левый), **дальний** — правый.

| Случай | Что видим | Что делаем | Что дальше |
|---|---|---|---|
| 1 | брат **красный** | брата — в чёрный, родителя — в красный, левый поворот родителя | у `x` новый брат, чёрный — переходим к случаям 2–4 |
| 2 | брат чёрный, **оба** его ребёнка чёрные | брата — в красный | долг переходит к родителю: он красный — красим в чёрный, конец; чёрный — повторяем с ним |
| 3 | брат чёрный, **ближний** ребёнок красный, дальний чёрный | ближнего — в чёрный, брата — в красный, правый поворот брата | теперь дальний ребёнок красный — это случай 4 |
| 4 | брат чёрный, **дальний** ребёнок красный | брат берёт цвет родителя, родителя и дальнего — в чёрный, левый поворот родителя | долг погашен, конец |

Долг, дошедший до красного узла или до корня, гасится сам: узел просто красят в чёрный. Каждый
случай — это константа работы, а подниматься вверх умеет только случай 2, поэтому всё
удаление — `O(log n)`.

Схема тоже псевдокодом — `deleteFixup` и есть таблица выше в цикле:

```go
func (t *RBTree) Delete(val int) {
    z := t.find(val)
    if z == nil { return }
    y := z
    if z.left != nil && z.right != nil {
        y = min(z.right)   // преемник
        z.val = y.val      // копируем значение
    }
    x := y.child()         // у y ≤ 1 ребёнка
    removed := y.color
    t.transplant(y, x)     // y уходит, на место — x
    if removed == BLACK {
        t.deleteFixup(x)   // гасим «двойной чёрный» вверх по дереву
    }
}
```

## 🧠 Почему это O(log n)

Чёрных узлов на всех путях от корня вниз поровну (правило ⭐), а из-за запрета «красный-красный»
красных на любом пути не больше, чем чёрных. Поэтому самый длинный путь не длиннее самого короткого
вдвое, и высота не больше `2·log₂n` — то есть `O(log n)`. Все операции идут по одному пути вниз плюс
починка вверх (константа поворотов), поэтому тоже `O(log n)`.

<details class="algo-details">
<summary>Почему поворотов при вставке ≤ 2, а перекрасок может быть много</summary>

Перекраска (случай «дядя красный») не меняет структуру — только цвета — и «поднимает» проблему
на два уровня вверх. Таких шагов может быть до `O(log n)`, но они дёшевы. Как только встречается
случай «дядя чёрный», делается **один-два поворота** — и всё, цикл завершается. Поэтому
структурных перестроений (поворотов) на вставку — не больше двух.

Честное сравнение с AVL: при **вставке** AVL тоже обходится одним поворотом (возможно, двойным) —
тут паритет. Разница проявляется при **удалении**: AVL может каскадить повороты до самого корня
(до `O(log n)` структурных правок за одну операцию), а красно-чёрное дерево и при удалении
ограничено **тремя** поворотами. Плюс жёсткий инвариант AVL просто *срабатывает чаще* — больше
записей заканчиваются перестройкой. Это и есть причина, почему RB-деревья предпочитают там, где
много записей.

</details>

## ⚙️ Цена на практике: почему RB, а не AVL

Обе структуры дают `O(log n)` и обе балансируются поворотами. Разница — в характере:

| | AVL | Красно-чёрное |
|---|---|---|
| Строгость баланса | жёсткая (перекос высот детей ≤ 1) | слабее (пути ≤ ×2) |
| Высота | ниже → **поиск чуть быстрее** | чуть выше |
| Повороты: вставка | ≤ 1 (возможно, двойной) | ≤ 2 |
| Повороты: удаление | **может каскадить до O(log n)** | **≤ 3** |
| Где применяют | много чтений, мало записей | универсальный default (`std::map`, `TreeMap`, ядро Linux) |

Вывод инженера: **AVL — когда доминирует поиск; красно-чёрное — когда баланс чтений и записей**
(и потому это дефолт стандартных библиотек). В Go в stdlib упорядоченной map нет (есть `map` —
хеш, без порядка), поэтому за упорядоченным набором идут либо к отсортированному срезу +
[`slices.BinarySearch`](https://pkg.go.dev/slices#BinarySearch), либо к [B-дереву](btree-structure.md)
(`google/btree`) — на практике его дисковая/кэш-локальность часто важнее, чем у бинарных деревьев.

> 🔧 **Где это в реальных системах.** `std::map`/`std::set`/`std::multimap` в C++; `TreeMap`/
> `TreeSet` в Java; **ядро Linux** — планировщик задач (дерево по vruntime/дедлайну: CFS, с ядра
> 6.6 — EEVDF, см. [карту реальных систем](real-world-map.md)), тайминги,
> `epoll` внутри (области памяти процесса до ядра 6.1 тоже лежали в нём, теперь — в другом
> дереве, maple tree). Красно-чёрное дерево — самая
> используемая балансировка «общего назначения» в системном коде.

> 🌍 **Где это в настоящем коде**
>
> - [`__rb_insert`](https://github.com/torvalds/linux/blob/v6.6/lib/rbtree.c#L85) (ядро Linux 6.6) — починка после вставки красного узла: красный дядя — перекрасить и подняться к деду, чёрный — повернуть. Те же случаи, что в разделе о вставке.
> - [`__enqueue_entity`](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/fair.c#L831) (ядро Linux 6.6) — планировщик кладёт готовую к запуску задачу в красно-чёрное дерево, упорядоченное по `vruntime` (сколько процессорного времени задача уже получила).

## 📝 Разбор задачи: «следующий свободный слот»

Проверим устройство дерева на задаче, ради которой упорядоченные деревья и держат в проде.

> **Задача.** Планировщик заданий хранит занятые тайм-слоты (целые метки времени). Поток
> операций: `занять(t)`, `освободить(t)` и главный запрос — `ближайший занятый слот ≥ t`
> (successor/ceiling). Всего до миллионов слотов, операции перемешаны. Чем и как?

**Шаг 1. Почему не хеш и не массив.** `map` отвечает только «занят ли ровно t» — вопрос
«ближайший ≥ t» для него означает перебор. Отсортированный срез умеет ceiling бинарным поиском за
`O(log n)`, но `занять`/`освободить` — это вставка/удаление со сдвигом `O(n)`. Нужны **все три
операции за `O(log n)`** — это ровно ниша сбалансированного дерева (и причина, почему планировщик
задач в ядре Linux живёт на красно-чёрном дереве).

**Шаг 2. Сeiling — это спуск с запоминанием.** Идём от корня, как при обычном поиске, и держим
`best` — последнего кандидата, у которого `val ≥ t`:

```go
func (t *RBTree) Ceiling(x int) (int, bool) {
    best, found := 0, false
    for n := t.root; n != t.nil; {
        if n.val >= x {
            best, found = n.val, true // кандидат; попробуем найти ближе
            n = n.left                // всё ещё ≥ x, но меньше — только слева
        } else {
            n = n.right               // n.val < x — ответ строго правее
        }
    }
    return best, found
}
```

Инвариант спуска: ответ всегда в поддереве, куда мы идём, либо уже записан в `best`. Свернули
влево — значит `n.val ≥ x` и всё правое поддерево `n` ещё больше (дальше от `x`); свернули
вправо — значит `n.val < x`, и слева от `n` всё тоже меньше `x`. Путь — один спуск по высоте:
`O(log n)` **благодаря балансировке** — в перекошенном BST тот же код деградирует до `O(n)`.

**Шаг 3. Куда тут вставка и удаление.** `занять(t)` — обычная вставка красным узлом с ремонтом
(≤ 2 поворотов), `освободить(t)` — удаление с «двойным чёрным» (≤ 3 поворотов). Заметь: `Ceiling`
не знает о цветах вообще — вся «красно-чёрность» нужна лишь затем, чтобы высота, по которой он
спускается, оставалась `O(log n)` при любом порядке занятий и освобождений.

## ⚠️ Типичные ошибки

1. **Забыть, что новый узел красный** — если вставлять чёрным, сразу ломается равенство чёрных
   высот (правило ⭐), и чинить куда труднее.
2. **Перепутать случаи дяди** — красный дядя лечится *перекраской*, чёрный — *поворотом*; смешать
   их значит зациклиться или сломать инвариант.
3. **Забыть перекрасить корень в чёрный** в конце — корень обязан быть чёрным.
4. **«Ломаный» случай** (узел — правый ребёнок левого родителя, или наоборот) — сперва малый
   поворот, сводящий к «прямому», и только потом основной.

## 🎬 Визуализация

> 💡 **Интерактивная демонстрация.** Синяя ячейка — `curr`, жёлтая — `next` (сохранённый следующий),
> зелёные — уже развёрнутая часть (её голова — `prev`). Под холстом — строка шага и переменные, ниже — ползунок шагов (или ←/→ на клавиатуре) и код с подсветкой строки. Можно подставить свой список и нажать «⟲ Запустить».

## ⚡ Шаблон для собеседования

```go
var prev *ListNode
curr := head
for curr != nil {
    next := curr.Next // 1. сохранить остаток
    curr.Next = prev  // 2. развернуть указатель
    prev = curr       // 3. сдвинуть prev
    curr = next       // 4. сдвинуть curr
}
return prev           // новая голова
```

1. сохраняем `next`;
2. разворачиваем `curr.Next = prev`;
3. двигаем `prev` на `curr`;
4. двигаем `curr` на `next`. В конце возвращаем `prev`.

## 📖 Разбор

<details class="algo-details">
<summary>Итеративный и рекурсивный подходы, сложность</summary>

**Reverse Linked List** — разворот связанного списка на месте (in-place): мы меняем
направление каждого указателя `next`, не создавая новых узлов. Итеративный вариант
хранит три ссылки (предыдущий, текущий, следующий) и стоит O(1) памяти; рекурсивный
короче, но тратит O(n) на стек вызовов.

#### Итеративный подход

```go
type ListNode struct {
    Val  int
    Next *ListNode
}

func reverseListIterative(head *ListNode) *ListNode {
    var prev *ListNode
    curr := head
    for curr != nil {
        next := curr.Next // сохраняем остаток списка
        curr.Next = prev  // разворачиваем указатель
        prev = curr       // двигаемся вперёд
        curr = next
    }
    return prev
}
```

#### Рекурсивный подход

Базовый случай — пустой список или один узел. Иначе разворачиваем хвост, затем
переключаем единственный указатель: `head.Next.Next = head`, `head.Next = nil`.

```go
func reverseListRecursive(head *ListNode) *ListNode {
    if head == nil || head.Next == nil {
        return head
    }
    newHead := reverseListRecursive(head.Next)
    head.Next.Next = head
    head.Next = nil
    return newHead
}
```

#### Сложность

| Подход      | Время | Память        |
|-------------|-------|---------------|
| Итеративный | O(n)  | O(1)          |
| Рекурсивный | O(n)  | O(n) (стек)   |

Каждый узел посещается ровно один раз. Для длинных списков предпочтительнее
итеративный вариант — он не рискует переполнением стека.

</details>

## 🧠 Почему это корректно

### Инвариант трёх указателей

> В начале каждой итерации `prev` указывает на **уже развёрнутый префикс** (в обратном
> порядке), а `curr` — на голову **ещё не тронутого** остатка.

Шаг сдвигает границу ровно на один узел и сохраняет инвариант: разворачиваем ссылку
текущего узла назад (`curr.Next = prev`), затем оба указателя идут вперёд. Когда `curr`
становится `nil`, развёрнут весь список, и `prev` — его новая голова.

### Почему `next` сохраняют ДО перезаписи

`curr.Next = prev` **уничтожает** единственную ссылку на остаток списка. Если не
запомнить `next := curr.Next` заранее, продолжить обход будет неоткуда. Это общий принцип
любой in-place правки указателей: **сначала сохрани то, что перезапишешь**.

### Краевые случаи держит сам инвариант

Отдельные проверки на пустой список и список из одного узла **не нужны** — их закрывает
инвариант. Пустой список: `curr == nil` сразу, тело цикла не выполняется, возвращается
`prev == nil` (исходный). Один узел: одна итерация разворачивает его `Next` в `nil`
(он и так был `nil`), `prev` становится этим узлом. Хороший инвариант тем и ценен, что
вырожденные входы — не спецслучаи, а его частные значения. Тот же приём разворачивает и
**участок** `[m, n]`: фиктивная голова (dummy) перед `m` убирает спецобработку первого
узла, а внутри — тот же танец трёх указателей.

## ⚙️ Цена на практике

### `O(1)` на месте против нового списка

Разворот переписывает существующие `next` — никаких новых узлов, отсюда `O(1)` памяти.
Наивная альтернатива «собрать значения в срез и построить новый список» — `O(n)` лишней
памяти и аллокации. На месте — быстрее и экономнее.

### Рекурсия красивее, но стек `O(n)`

Рекурсивный вариант короче, но тратит `O(n)` кадров стека и **рискует переполнением** на
длинном списке. На собеседовании итеративный с тремя указателями — предпочтительный
ответ: та же `O(n)` по времени, но `O(1)` памяти и без риска стека.

### Развернул для проверки — верни обратно

Разворот часто не цель, а **инструмент**: например, проверка списка на палиндром
разворачивает вторую половину и сравнивает с первой за `O(1)` памяти. Но это **мутирует**
вход — после ответа корректное решение **разворачивает половину назад**, восстанавливая
список. Если вызывающий код ещё пользуется списком, оставить его перевёрнутым — скрытый
баг (та же дилемма мутации входа, что у `sort.Slice` в
[слиянии интервалов](merge-intervals.md)). На собеседовании об этом стоит сказать вслух,
даже если просят только `bool`.

## ⚠️ Типичные ошибки

1. **Потеря хвоста** — обязательно сохраняй `next := curr.Next` *до* присваивания
   `curr.Next = prev`, иначе остаток списка теряется.
2. **Возврат не того узла** — возвращай `prev`; `curr` в конце равен `nil`.
3. **Не обработан пустой список** — проверка `head == nil` (в рекурсии это часть
   базового случая).
4. **Рекурсия на длинном списке** — глубина равна длине списка, возможно переполнение
   стека; для больших данных бери итеративный вариант.
5. **Разворот списка с циклом** — цикл `for curr != nil` даже завершится (перевёрнутые
   ссылки в итоге выводят обход на `nil`), но часть узлов будет пройдена дважды, и на
   выходе — молча испорченная структура, а не разворот. Сначала убедись, что цикла
   нет ([Флойд](fast-slow-pointers.md)).

## 📝 Разбор задачи

Базовый разворот всего списка уже разобран выше. Возьмём задачу на ступень
интереснее — **разворот только участка** `[m, n]`: так, как стоит рассуждать на
собеседовании — сначала рабочий, но «жульнический» подход, затем разворот на месте.

> **Задача.** Дан односвязный список и две позиции `1 ≤ m ≤ n ≤ len`. Развернуть
> узлы с `m`-го по `n`-й включительно (1-индексация), остальные оставить как есть.
> Пример: `1→2→3→4→5`, `m = 2`, `n = 4` → `1→4→3→2→5`.

**Шаг 1. Наивно: значения в срез — O(n) времени и O(n) памяти.**

```go
func reverseBetweenNaive(head *ListNode, m, n int) *ListNode {
    var vals []int
    for node := head; node != nil; node = node.Next {
        vals = append(vals, node.Val)
    }
    for i, j := m-1, n-1; i < j; i, j = i+1, j-1 { // развернули срез [m-1..n-1]
        vals[i], vals[j] = vals[j], vals[i]
    }
    dummy := &ListNode{}
    cur := dummy
    for _, v := range vals {
        cur.Next = &ListNode{Val: v} // пересобрали список заново
        cur = cur.Next
    }
    return dummy.Next
}
```

Это **работает и проходит тесты**, но платит `O(n)` лишней памятью и аллокацией под
срез и новые узлы — ровно то, чего разворот указателей призван избежать. Мы вообще не
используем то, что структура уже связана: переписать пару ссылок дешевле, чем копировать
все значения.

**Шаг 2. Ключевое наблюдение.** Развернуть участок — это тот же танец трёх указателей,
что и для всего списка, но с двумя поправками. Первая: чтобы не городить спецслучай для
`m = 1` (когда меняется сама голова), ставим **фиктивную голову** (dummy) перед списком —
у участка всегда есть «предыдущий» узел `prev`. Вторая: тот же принцип
[«сначала сохрани то, что перезапишешь»](#почему-next-сохраняют-до-перезаписи) — каждую
ссылку трогаем только запомнив остаток. Удобнее не «переворачивать» по одному, а
**вытаскивать** узел сразу за `curr` и вставлять его в начало участка (head-insertion):
за `n − m` шагов участок оказывается развёрнут на месте.

**Шаг 3. Оптимум: разворот участка указателями — O(n) времени, O(1) памяти.**

```go
func reverseBetween(head *ListNode, m, n int) *ListNode {
    dummy := &ListNode{Next: head}
    prev := dummy
    for i := 0; i < m-1; i++ { // дошли до узла перед участком
        prev = prev.Next
    }
    curr := prev.Next                  // первый узел участка (останется последним)
    for i := 0; i < n-m; i++ {
        next := curr.Next              // 1. сохранить вынимаемый узел
        curr.Next = next.Next          // 2. вырезать его из текущей позиции
        next.Next = prev.Next          // 3. вставить в начало участка
        prev.Next = next               // 4. подцепить к узлу перед участком
    }
    return dummy.Next
}
```

Прогони `reverseBetween` на участке `[2, 4]`: `prev` и `curr` стоят на месте, а узел за
`curr` вынимается (шаг 2 — он на миг выпадает из списка) и встаёт в начало участка:

<div class="algo-viz" data-viz="list-reverse-between" data-list="1,2,3,4,5" data-m="2" data-n="4"></div>

**Шаг 4. Трассировка** на `1→2→3→4→5`, `m = 2`, `n = 4` (после установки `prev` на узел
`1` и `curr` на узел `2`; делается `n − m = 2` итерации):

| итерация | `next` (вынимаем) | список после шага        | `prev.Next` (голова участка) | `curr` |
|----------|-------------------|--------------------------|------------------------------|--------|
| старт    | —                 | `1→2→3→4→5`              | `2`                          | `2`    |
| 1        | `3`               | `1→3→2→4→5`              | `3`                          | `2`    |
| 2        | `4`               | `1→4→3→2→5`              | `4`                          | `2`    |

`curr` всё время указывает на узел `2`: он въезжает в хвост участка, а свежевынутые узлы
встают перед ним. Прошли `prev` за `m − 1` шагов плюс `n − m` вставок — суммарно `O(n)`,
без единой новой аллокации. Граничные входы (`m = n` — ноль итераций, список не меняется;
`m = 1` — участок с самой головы, спецслучай снял dummy) проходят тем же кодом.

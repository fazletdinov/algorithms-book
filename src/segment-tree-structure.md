> 🧭 **Зачем отдельная глава.** Дерево отрезков — это **дерево над массивом**, где каждый узел
> хранит готовый агрегат (сумму/минимум/…) своего диапазона. Вся механика — три операции:
> построить дерево, обновить элемент, ответить на запрос по диапазону. Пока не увидел, как узел =
> сумма детей и как запрос собирается из O(log n) готовых узлов, задачи кажутся магией. Здесь
> строим саму структуру; ленивое проталкивание (range-update) и задачи — в главе
> [«Дерево отрезков: разбор задач»](segment-tree.md).

## 🧱 Как устроено дерево

Дерево отрезков строится **над массивом**: корень покрывает весь диапазон `[0, n−1]`, каждый
внутренний узел делит свой диапазон пополам на двух детей, а листья — это отдельные элементы.
В узле хранится **агрегат** его диапазона (здесь — сумма).

```go
type Seg struct {
    sum []int // sum[node] — сумма на диапазоне узла node
    n   int
}
```

```
                 [0,3]=11
               /          \
          [0,1]=3        [2,3]=8
          /     \        /     \
     [0,0]=2 [1,1]=1 [2,2]=5 [3,3]=3
        2       1       5       3      ← исходный массив
```

Три факта, которые держат всё:

1. **Узел = агрегат диапазона.** Корень — сумма всего массива, лист — один элемент, внутренний
   узел — сумма своих детей. Это инвариант: `tree[node] = tree[left] + tree[right]`.
2. **Запрос собирается из готовых узлов.** Любой диапазон `[l, r]` покрывается O(log n) узлами,
   чьи диапазоны целиком внутри `[l, r]` — их суммы уже посчитаны, складывать поэлементно не нужно.
3. **Обновление чинит один путь.** Меняется один лист — пересчитать надо только его предков
   (O(log n) узлов на пути к корню), остальное дерево не трогается.

## 🔨 Построение: `Build` (снизу вверх)

Дерево строится рекурсивно: лист получает значение элемента, а внутренний узел — **сумму уже
построенных детей**. Пост-обход (сначала дети, потом узел) гарантирует, что к моменту вычисления
узла его дети готовы.

```go
func build(node, lo, hi int) {
    if lo == hi { tree[node] = arr[lo]; return }   // лист
    mid := (lo + hi) / 2
    build(2*node,   lo,    mid)                     // левое поддерево
    build(2*node+1, mid+1, hi)                      // правое поддерево
    tree[node] = tree[2*node] + tree[2*node+1]      // узел = сумма детей
}
```

> 💡 **Демонстрация построения.** Дерево над массивом `[2,1,5,3]` заполняется снизу вверх: листья
> получают элементы, затем каждый внутренний узел становится суммой детей, и корень — суммой всего
> массива (`11`). Подставь свой массив.

## ✏️ Точечное обновление: `Update`

Изменить один элемент — значит спуститься до его листа, записать новое значение и на обратном
пути **пересчитать суммы всех предков**. Трогается ровно один путь от листа к корню.

```go
func update(node, lo, hi, i, val int) {
    if lo == hi { tree[node] = val; return }        // дошли до листа
    mid := (lo + hi) / 2
    if i <= mid {
        update(2*node, lo, mid, i, val)             // i в левом
    } else {
        update(2*node+1, mid+1, hi, i, val)         // i в правом
    }
    tree[node] = tree[2*node] + tree[2*node+1]       // пересчёт узла
}
```

> 💡 **Демонстрация обновления.** В дереве над `[2,1,5,3]` меняем индекс `2` на `9`: спуск к листу
> `[2,2]`, запись `9`, затем пересчёт по пути — `[2,3]` становится `12`, корень `[0,3]` — `15`.
> Видно, что меняются только узлы на пути.

## 🔎 Запрос на диапазоне: `Query`

Запрос суммы на `[l, r]` спускается от корня. На каждом узле — три случая: его диапазон **вне**
запроса (вклад 0, пропуск), **целиком внутри** (берём готовую сумму, не спускаясь глубже) или
**пересекает частично** (спускаемся к обоим детям и складываем).

```go
func (t *Seg) Query(node, lo, hi, ql, qr int) int {
    if hi < ql || qr < lo {
        return 0 // вне запроса
    }
    if ql <= lo && hi <= qr {
        return t.sum[node] // целиком внутри
    }
    mid := (lo + hi) / 2
    return t.Query(2*node, lo, mid, ql, qr) +
        t.Query(2*node+1, mid+1, hi, ql, qr)
}
```

> 💡 **Демонстрация запроса.** Сумма на `[2,5]` в дереве над `[1,3,5,7,9,11,13,15]`: зелёные узлы
> берутся целиком (их сумма готова), серые пропускаются, синие — частичное пересечение (спуск к
> детям). Видно, что ответ собран из нескольких готовых узлов, а не из восьми листьев.

## 🧠 Почему это корректно

### Почему запрос — O(log n)

Спускаясь, на каждом уровне дерева запрос «расходится» максимум на 2 узла, которые пересекают
границу `[l, r]` частично; всё, что целиком внутри, берётся одной суммой без спуска, всё, что
снаружи, отсекается. Частично пересекающих узлов на каждом из O(log n) уровней — не больше двух,
поэтому всего посещается O(log n) узлов. Диапазон `[l, r]` всегда раскладывается на O(log n)
**канонических** узлов — это и есть суть структуры.

### Почему обновление — O(log n) и сохраняет инвариант

Точечное обновление меняет ровно один лист и пересчитывает `tree[node] = tree[left] + tree[right]`
для каждого предка на пути к корню. Высота дерева — O(log n), значит и предков столько же. Инвариант
«узел = сумма детей» восстанавливается снизу вверх: к моменту пересчёта узла оба его ребёнка уже
актуальны.

### Инвариант — это и есть корректность

Всё опирается на один инвариант: значение узла всегда равно агрегату его диапазона. `Build` его
устанавливает, `Update` восстанавливает по пути, `Query` им пользуется (берёт готовую сумму узла
целиком внутри запроса). Операция должна быть **ассоциативной** (сумма, min, max, gcd), иначе
агрегат детей не собирается в агрегат родителя.

## ⚙️ Цена на практике

### Когда дерево отрезков избыточно

- **Массив не меняется** → префиксные суммы: запрос на диапазоне O(1), без всякого дерева.
- **Нужны только суммы с точечным обновлением** → [дерево Фенвика](fenwick-tree-structure.md): тот же
  O(log n), но один массив, крошечная константа и куда меньше кода.

Дерево отрезков берут, когда нужно больше: обновление диапазона (lazy), некоммутативные агрегаты,
запросы вида «первый элемент ≥ x». Не доставай его, когда хватает меньшего.

### Рекурсия против итеративного layout

Рекурсивная версия (как выше) нагляднее и легко обобщается на lazy и сложные агрегаты.
Итеративная на массиве `2n` плотнее, без накладных вызовов и дружелюбнее к кэшу, но менее
очевидна. На собеседовании рекурсивная с публичной обёрткой `Query(l, r)` (скрывающей служебные
`node, lo, hi`) — обычно лучший ответ.

### Обновление диапазона — это уже lazy

Обновить **целый** диапазон за O(log n) (а не каждый элемент) позволяет **ленивое проталкивание**:
узел хранит отложенное обновление и проталкивает его детям только при спуске. Это отдельная
большая тема — см. главу [«Дерево отрезков: разбор задач»](segment-tree.md).

## ⚠️ Типичные ошибки

1. **Путают индексацию диапазонов** — `[lo, mid]` и `[mid+1, hi]`; ошибка на границе ломает дерево.
2. **Забыли пересчитать предков** при обновлении — суммы в верхних узлах устаревают.
3. **Неверный нейтральный элемент** — для суммы это 0, для min — `+∞`, для max — `−∞`; перепутал — неверный ответ «вне запроса».
4. **Неассоциативная операция** — агрегат детей не складывается в агрегат родителя, структура не работает.
5. **Дерево там, где хватало префиксных сумм или Фенвика** — лишняя сложность и константа.

> 🧭 **О чём глава.** Дерево отрезков — **дерево над массивом**, где каждый узел хранит
> **агрегат** своего отрезка — одно число, сведённое из всех элементов отрезка (сумма, минимум,
> максимум). Вся механика — три операции: построить дерево, обновить элемент, ответить на запрос по
> отрезку. Сначала строим саму структуру, потом — компактную итеративную версию, обновление целого
> отрезка (lazy) и задачу Range Sum Query — Mutable.

## 🧱 Как устроено дерево

Корень покрывает весь массив `[0, n−1]`, каждый внутренний узел делит свой отрезок пополам на
двух детей, листья — отдельные элементы. В узле хранится агрегат его отрезка (здесь — сумма).

```go
type Seg struct {
    sum []int // sum[node] — сумма на отрезке узла node
    n   int
}
```

<div class="algo-fig" data-fig="tree" data-tree="11|[0,3](3|[0,1](2|[0,0],1|[1,1]),8|[2,3](5|[2,2],3|[3,3]))" data-row="2,1,5,3" data-row-label="исходный массив" data-caption="Дерево отрезков над [2, 1, 5, 3]: в узле — сумма, под ним — его отрезок [l, r]"></div>

> 🔢 **Почему в коде всюду `2*node` и `2*node+1`.** Дерево не хранит указателей — оно лежит в
> обычном массиве по «кучному» правилу нумерации: корень — индекс `1`, у узла `i` левый ребёнок
> `2i`, правый — `2i+1`, родитель — `i/2`. Та же идея, что в [бинарной куче](heap-structure.md)
> (там корень `0`, дети `2i+1`/`2i+2`). Под массив берут с запасом — около `4n` ячеек
> (`make([]int, 4*n)`): при `n`, не равном степени двойки, крайние индексы «разъезжаются», и `2n`
> уже не хватает.

Три факта держат всё:

1. **Узел = агрегат отрезка.** Это инвариант: `tree[node] = tree[left] + tree[right]`.
2. **Запрос собирается из готовых узлов.** Любой отрезок `[l, r]` покрывается O(log n) узлами,
   лежащими целиком внутри него, — их суммы уже посчитаны.
3. **Обновление чинит один путь.** Меняется один лист — пересчитать надо только его предков.

## 🔨 Построение: `Build` (снизу вверх)

Лист получает значение элемента, внутренний узел — **сумму уже построенных детей**. Сначала дети,
потом узел (пост-обход) — так к моменту вычисления узла его дети готовы.

```go
func build(node, lo, hi int) {
    if lo == hi { tree[node] = arr[lo]; return }   // лист
    mid := (lo + hi) / 2
    build(2*node,   lo,    mid)                     // левое поддерево
    build(2*node+1, mid+1, hi)                      // правое поддерево
    tree[node] = tree[2*node] + tree[2*node+1]      // узел = сумма детей
}
```

Дерево над `[2,1,5,3]` заполняется снизу вверх, корень — сумма всего массива (`11`). Подставь свой массив:

## ✏️ Точечное обновление: `Update`

Спускаемся до листа элемента, записываем новое значение и на обратном пути **пересчитываем всех
предков**. Трогается ровно один путь от листа к корню.

```go
func update(node, lo, hi, i, val int) {
    if lo == hi { tree[node] = val; return }        // дошли до листа
    mid := (lo + hi) / 2
    if i <= mid {
        update(2*node, lo, mid, i, val)             // i в левом
    } else {
        update(2*node+1, mid+1, hi, i, val)         // i в правом
    }
    tree[node] = tree[2*node] + tree[2*node+1]       // пересчёт узла
}
```

Меняем индекс `2` на `9`: лист `[2,2]` получает `9`, затем `[2,3]` становится `12`, корень — `15`.

## 🔎 Запрос на отрезке: `Query`

Запрос суммы на `[ql, qr]` спускается от корня. У каждого узла три случая: его отрезок **вне**
запроса (вклад 0), **целиком внутри** (берём готовую сумму, глубже не идём) или **пересекает
частично** (спускаемся к обоим детям и складываем).

```go
func (t *Seg) Query(node, lo, hi, ql, qr int) int {
    if hi < ql || qr < lo {
        return 0 // вне запроса
    }
    if ql <= lo && hi <= qr {
        return t.sum[node] // целиком внутри
    }
    mid := (lo + hi) / 2
    return t.Query(2*node, lo, mid, ql, qr) +
        t.Query(2*node+1, mid+1, hi, ql, qr)
}
```

`0` здесь — **нейтральный элемент** суммы: значение, которое не меняет результат (`x + 0 = x`).
У минимума нейтраль `+∞`, у максимума — `−∞`.

Сумма на `[2,5]` над `[1,3,5,7,9,11,13,15]`: зелёные узлы берутся целиком, серые пропускаются,
синие пересекаются частично (спуск к детям). Ответ собран из нескольких готовых узлов, а не из
восьми листьев:

## 🔁 Итеративная реализация: массив `2n`

Та же структура без рекурсии: массив `tree` размера `2n`, листья — в `[n, 2n)`, родитель `i` — `i/2`.
Строим снизу вверх, обновляем подъёмом от листа, а запрос ведём двумя границами навстречу друг другу.

```go
type SegmentTree struct {
    n    int
    tree []int
}

func NewSegmentTree(arr []int) *SegmentTree {
    n := len(arr)
    st := &SegmentTree{n: n, tree: make([]int, 2*n)}
    for i := 0; i < n; i++ {
        st.tree[n+i] = arr[i]
    }
    for i := n - 1; i > 0; i-- {
        st.tree[i] = st.tree[2*i] + st.tree[2*i+1]
    }
    return st
}

func (st *SegmentTree) Update(i, val int) {
    i += st.n
    st.tree[i] = val
    for i > 1 {
        i /= 2
        st.tree[i] = st.tree[2*i] + st.tree[2*i+1]
    }
}

func (st *SegmentTree) Query(l, r int) int { // включительный [l, r]
    res := 0
    l += st.n
    r += st.n + 1
    for l < r {
        if l&1 == 1 {
            res += st.tree[l]
            l++
        }
        if r&1 == 1 {
            r--
            res += st.tree[r]
        }
        l /= 2
        r /= 2
    }
    return res
}
```

`Query` держит **полуоткрытый** отрезок `[l, r)` — правая граница указывает за последний нужный
лист, отсюда `r += n + 1`. Если `l` — правый ребёнок (`l&1 == 1`), его родитель захватил бы лишнее
слева: забираем сам `l` и сдвигаемся вправо; симметрично для `r`. Потом обе границы поднимаются на
уровень. Пошагово это показано в [трассировке задачи](#-разбор-задачи).

## 🐢 Lazy propagation: обновление целого отрезка

Прибавить `delta` к каждому элементу `[ql, qr]` по одному — это O(n). **Ленивое проталкивание**
делает это за O(log n): узел, целиком покрытый обновлением, меняет свою сумму сразу и записывает
«долг» в `lazy[node]` — детям его передадут потом, когда к ним действительно спустятся.

```go
type LazySegmentTree struct {
    n          int
    tree, lazy []int // lazy[node] — дельта, учтённая в tree[node], но ещё не спущенная детям
}

// публичная обёртка: наружу — только границы отрезка
func (l *LazySegmentTree) UpdateRange(ql, qr, delta int) { l.update(1, 0, l.n-1, ql, qr, delta) }

func (l *LazySegmentTree) apply(node, lo, hi, delta int) {
    l.tree[node] += (hi - lo + 1) * delta
    l.lazy[node] += delta
}
func (l *LazySegmentTree) push(node, lo, hi int) {
    if l.lazy[node] != 0 {
        mid := (lo + hi) / 2
        l.apply(2*node, lo, mid, l.lazy[node])
        l.apply(2*node+1, mid+1, hi, l.lazy[node])
        l.lazy[node] = 0
    }
}
func (l *LazySegmentTree) update(node, lo, hi, ql, qr, delta int) {
    if qr < lo || hi < ql {
        return
    }
    if ql <= lo && hi <= qr {
        l.apply(node, lo, hi, delta)
        return
    }
    l.push(node, lo, hi)
    mid := (lo + hi) / 2
    l.update(2*node, lo, mid, ql, qr, delta)
    l.update(2*node+1, mid+1, hi, ql, qr, delta)
    l.tree[node] = l.tree[2*node] + l.tree[2*node+1]
}
```

Листай «›». Сначала `UpdateRange(1, 4, +10)`: узел, целиком попавший в отрезок, получает новую
сумму и **оранжевый бейдж lazy** — его листья остаются старыми. Затем `Query(4, 5)`: спускаясь
сквозь помеченный узел, запрос делает `push` — долг доезжает до листьев ровно тогда, когда стал нужен:

<div class="algo-viz" data-viz="lazy-range" data-array="1,3,5,7,9,11" data-add="10" data-l="1" data-r="4" data-ql="4" data-qr="5"></div>

Главное правило: **перед спуском к детям — всегда `push`**, и в обновлении, и в запросе. Lazy-версия
`query` устроена как обычный `Query` выше, только при частичном пересечении сначала зовёт
`push(node, lo, hi)`.

## 📝 Разбор задачи

> **Задача (Range Sum Query — Mutable).** Дан массив `nums`. Вперемешку приходят операции
> `update(i, val)` — присвоить `nums[i] = val` — и `query(l, r)` — вернуть сумму на `[l, r]`
> включительно. Обработать все за минимум времени на операцию.
> Пример: `nums = [2,1,5,3,4,7,6,8]`; `query(1,4)=13`, затем `update(2,10)`, снова `query(1,4)=18`.

**Шаг 1. Наивно: префиксные суммы — запрос O(1), но обновление O(n).**

```go
type Naive struct{ pre []int } // pre[i] = nums[0]+...+nums[i-1]

func NewNaive(nums []int) *Naive {
    pre := make([]int, len(nums)+1)
    for i, v := range nums {
        pre[i+1] = pre[i] + v
    }
    return &Naive{pre}
}

func (n *Naive) Query(l, r int) int { return n.pre[r+1] - n.pre[l] } // O(1)

func (n *Naive) Update(i, val int) { // O(n): пересчитать хвост префиксов
    delta := val - (n.pre[i+1] - n.pre[i])
    for k := i + 1; k < len(n.pre); k++ {
        n.pre[k] += delta
    }
}
```

Работает, но каждое обновление пересчитывает все префиксы правее `i` — O(n), на потоке из `m`
обновлений O(n·m). Обратный вариант (сырой массив: обновление O(1), запрос O(n)) переносит ту же
цену на запросы. Одна из операций всегда линейна: префиксы по природе статичны.

**Шаг 2. Наблюдение.** Сумму на `[l, r]` можно собрать из O(log n) **заранее посчитанных частичных
сумм**. Если держать их в дереве (лист = элемент, узел = сумма детей), обновление трогает только
O(log n) узлов на пути к корню, а не весь хвост. Обе операции становятся O(log n).

**Шаг 3. Оптимум** — итеративное дерево из [раздела выше](#-итеративная-реализация-массив-2n),
без изменений:

```go
st := NewSegmentTree([]int{2, 1, 5, 3, 4, 7, 6, 8})
st.Query(1, 4)   // 13
st.Update(2, 10) // nums[2] = 10, обновятся O(log n) узлов на пути к корню
st.Query(1, 4)   // 18
```

Тот же запрос рекурсивным `Query` — спуск от корня; он забирает ровно те узлы, чьё поддерево целиком
внутри `[1, 4]`. Итеративная версия в трассировке ниже поднимается от листьев и берёт те же узлы:

**Шаг 4. Трассировка** итеративного `Query(1, 4)` (n = 8, листья в `[8, 16)`): старт `l = 1+8 = 9`,
`r = 4+8+1 = 13`:

| итерация | `l`, `r` | `l&1==1` → take | `r&1==1` → take | взятый узел (отрезок) | `res` |
|----------|----------|-----------------|-----------------|------------------------|-------|
| 1 | `l=9`, `r=13` | да: `tree[9]` | да: `r→12`, `tree[12]` | лист `[1]`=1, лист `[4]`=4 | 5 |
| —        | `l→5`, `r→6` | (поднялись)     | (поднялись)     | —                      | 5 |
| 2 | `l=5`, `r=6` | да: `tree[5]` | нет | узел `[2,3]`=5+3=8 | 13 |
| —        | `l→3`, `r→3` | `l<r` ложно — стоп | | | **13** |

Запрос разложился на **3 готовых узла** (`[1]`, `[2,3]`, `[4]`) вместо четырёх элементов. После
`update(2, 10)` обновятся лист `[2]`, узел `[2,3]` и их предки, и тот же запрос вернёт `18`.

## 🧠 Почему это корректно

**Один инвариант:** значение узла всегда равно агрегату его отрезка. `Build` его устанавливает,
`Update` восстанавливает снизу вверх (к моменту пересчёта узла оба ребёнка уже актуальны), `Query`
им пользуется. Операция обязана быть **ассоциативной** — `(a ⊕ b) ⊕ c = a ⊕ (b ⊕ c)`, то есть
отрезок можно сворачивать по частям: сумма, min, max, НОД подходят.

**Почему запрос — O(log n).** На каждом уровне дерева частично пересекают границы запроса не больше
двух узлов — у левой и у правой границы. Всё между ними покрыто целыми узлами, всё снаружи
отсекается. Уровней O(log n), значит и посещённых узлов O(log n). Итеративный обход делает то же
снизу: на каждом уровне `[l, r)` — ещё не учтённая середина, всё левее `l` и правее `r` уже в `res`.

**Почему lazy корректно.** `tree[node]` всегда верен для всего отрезка узла, а `lazy[node]` — это
обновления, уже учтённые в нём, но не спущенные детям. Отсюда три правила: полное покрытие → `apply`
(детей не трогаем); перед спуском при частичном пересечении → `push`; после обновления детей →
пересчитать `tree[node]`. Нарушь любое — дерево тихо вернёт неверную сумму.

<details class="algo-details">
<summary>⚙️ Второй проход: массив <code>2n</code>, когда n — не степень двойки — читать, когда освоишься</summary>

При `n`, не равном степени двойки, листья в `[n, 2n)` оказываются «провёрнуты» по кругу, и неявное
дерево не идеально сбалансировано. Для **коммутативных** агрегатов (сумма, min, max — порядок
операндов не важен) это неважно: набор собранных листьев верен. Для **некоммутативной** операции
(склейка строк, умножение матриц) граничные узлы собираются «вперемешку», и левый и правый вклад
надо копить раздельно — проще взять рекурсивную версию с явными `[lo, hi]`.

</details>

## ⚙️ Цена на практике

**Не доставай дерево, когда хватает меньшего.** Бери его, только если **обновления и запросы на
отрезке идут вперемешку**. Массив статичен → префиксные суммы (запрос O(1), подготовка O(n)). Только
точечные обновления и суммы → [дерево Фенвика](fenwick-tree.md): та же O(log n), один массив,
меньше кода. Дерево отрезков оправдано на обновлении отрезка (lazy), некоммутативных агрегатах,
запросах вида «первый элемент ≥ x».

**Итеративная или рекурсивная.** Итеративная на `2n` — плотная память, дружелюбная к кэшу, без
накладных расходов на вызовы и самый короткий корректный код для суммы. Рекурсивная (массив `4n` +
кадры стека) медленнее, но гибче: на неё легко навесить lazy, явные границы и некоммутативные операции.

**Дай рекурсии публичную обёртку.** Сигнатура `query(node, lo, hi, ql, qr)` требует от вызывающего
помнить `node=1, lo=0, hi=n-1` — частый источник ошибок. Прячь её за `Query(l, r)`, как `UpdateRange`
в `LazySegmentTree` выше.

**Переполнение.** В `apply` множитель `(hi-lo+1) * delta` на большом отрезке растёт быстро.

## ⚠️ Типичные ошибки

1. **Границы детей** — `[lo, mid]` и `[mid+1, hi]`; ошибка на границе ломает дерево.
2. **Включительный против полуоткрытого** — в итеративном `Query` `r` сдвигается на `+1`, превращая `[l, r]` в `[l, r)`.
3. **Забыли пересчитать предков** при обновлении — суммы в верхних узлах устаревают.
4. **Неверный нейтральный элемент** — для суммы 0, для min `+∞`, для max `−∞` (и в «вне запроса», и в стартовом `res`).
5. **Lazy: забыли `push`** перед спуском — дети вернут устаревшие данные.
6. **Неассоциативная операция** или **дерево там, где хватало префиксных сумм или Фенвика**.

> 🌍 **Где это в настоящем коде**
>
> - [`pageAlloc.update`](https://github.com/golang/go/blob/go1.24.0/src/runtime/mpagealloc.go#L485) (Go 1.24) — распределитель страниц памяти в рантайме Go держит дерево сводок по отрезкам адресного пространства (у вершины 8 детей, каждый уровень — плоский массив без указателей, как `tree[]` в этой главе). После выделения или освобождения страниц он пересчитывает лист, а затем поднимается уровень за уровнем вверх, собирая каждого родителя из его детей, — тот же `Update`, что выше.
> - [`mergeSummaries`](https://github.com/golang/go/blob/go1.24.0/src/runtime/mpagealloc.go#L1038) (Go 1.24) — вершина того же дерева хранит не сумму, а тройку: сколько свободных страниц в начале отрезка, в конце и самая длинная свободная полоса. Родитель собирается из детей: самая длинная полоса — это `max(лучшая слева, конец левого + начало правого, лучшая справа)`.
> - [`pageAlloc.find`](https://github.com/golang/go/blob/go1.24.0/src/runtime/mpagealloc.go#L647) (Go 1.24) — запрос «дай n свободных страниц подряд»: спуск от верхнего уровня к листьям в первое поддерево, где по сводке такая полоса есть; если полоса ложится на стык соседей, её видно по их концу и началу, и спуск останавливается раньше.

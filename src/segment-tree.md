## 📖 Разбор

<details class="algo-details">
<summary>Итеративная реализация, lazy propagation и сложность</summary>

Лист хранит элемент, внутренний узел — агрегат детей. Запрос разбивается на O(log n)
узлов. Сравнение: массив (запрос O(n)), префиксные суммы (запрос O(1), но обновление
O(n)), дерево отрезков (и то, и другое O(log n)).

#### Итеративная реализация (сумма)

Массив `tree` размера `2n`, листья в `[n, 2n)`, родитель `i` — это `i/2`.

```go
type SegmentTree struct {
    n    int
    tree []int
}

func NewSegmentTree(arr []int) *SegmentTree {
    n := len(arr)
    st := &SegmentTree{n: n, tree: make([]int, 2*n)}
    for i := 0; i < n; i++ {
        st.tree[n+i] = arr[i]
    }
    for i := n - 1; i > 0; i-- {
        st.tree[i] = st.tree[2*i] + st.tree[2*i+1]
    }
    return st
}

func (st *SegmentTree) Update(i, val int) {
    i += st.n
    st.tree[i] = val
    for i > 1 {
        i /= 2
        st.tree[i] = st.tree[2*i] + st.tree[2*i+1]
    }
}

func (st *SegmentTree) Query(l, r int) int { // включительный [l, r]
    res := 0
    l += st.n
    r += st.n + 1
    for l < r {
        if l&1 == 1 {
            res += st.tree[l]
            l++
        }
        if r&1 == 1 {
            r--
            res += st.tree[r]
        }
        l /= 2
        r /= 2
    }
    return res
}
```

#### Lazy propagation (обновление диапазона)

Если узел целиком покрыт диапазоном обновления — применяем изменение сразу, а к детям
проталкиваем лениво. Так range-update и range-query оба O(log n).

```go
func (l *LazySegmentTree) apply(node, lo, hi, delta int) {
    l.tree[node] += (hi - lo + 1) * delta
    l.lazy[node] += delta
}
func (l *LazySegmentTree) push(node, lo, hi int) {
    if l.lazy[node] != 0 {
        mid := (lo + hi) / 2
        l.apply(2*node, lo, mid, l.lazy[node])
        l.apply(2*node+1, mid+1, hi, l.lazy[node])
        l.lazy[node] = 0
    }
}
func (l *LazySegmentTree) update(node, lo, hi, ql, qr, delta int) {
    if qr < lo || hi < ql {
        return
    }
    if ql <= lo && hi <= qr {
        l.apply(node, lo, hi, delta)
        return
    }
    l.push(node, lo, hi)
    mid := (lo + hi) / 2
    l.update(2*node, lo, mid, ql, qr, delta)
    l.update(2*node+1, mid+1, hi, ql, qr, delta)
    l.tree[node] = l.tree[2*node] + l.tree[2*node+1]
}
```

Ключевое правило: **перед спуском к детям всегда `push`**, иначе они вернут устаревшие
данные.

#### Сложность

| Операция   | Время    | Память |
|------------|----------|--------|
| Построение | O(n)     | O(n)   |
| Query      | O(log n) | —      |
| Update     | O(log n) | —      |

</details>

## 🧠 Почему это корректно

### Почему запрос — `O(log n)`

Любой отрезок `[l, r]` раскладывается на `O(log n)` **канонических** узлов дерева. На
каждом из `log n` уровней частично задеты максимум два узла (на левой и правой границе),
а всё, что между ними, покрыто целиком узлами-предками. Итеративный обход с `l&1` / `r&1`
именно это и делает: когда `l` — правый ребёнок, его поддерево целиком внутри запроса —
забираем его и сдвигаем границу; симметрично для `r`. За проход вверх собирается ≤ `2 log n`
узлов — отсюда логарифм.

> **Инвариант обхода:** на каждом уровне `[l, r)` — это ещё не учтённая середина
> диапазона; всё, что левее `l` и правее `r`, уже просуммировано. Поднимаясь, мы
> поддерживаем его, пока границы не сойдутся.

### Почему ленивое проталкивание корректно

Инвариант: **`tree[node]` всегда верен для всего отрезка узла**, а `lazy[node]` хранит
обновления, которые *уже учтены в `tree[node]`, но ещё не спущены детям*. Отсюда правила:

- **полное покрытие** → `apply` меняет агрегат узла и копит `lazy` (детей не трогаем —
  они станут нужны только при заходе глубже);
- **перед спуском при частичном пересечении** → `push`: переносим `lazy` детям, чтобы
  они стали консистентны, иначе вернут устаревшее;
- **после обновления детей** → пересчитываем `tree[node]` из детей.

Нарушь любое из трёх — и дерево тихо вернёт неверную сумму. Правило «перед спуском всегда
`push`» — это и есть поддержание инварианта.

### Тонкость компактного layout `2n` для не-степеней двойки

Итеративная версия кладёт листья в `[n, 2n)`. При `n`, не равном степени двойки, листья
оказываются «провёрнуты» по кругу — неявное дерево не идеально-сбалансированное. Для
**коммутативных** агрегатов (сумма, min, max) это неважно: набор собираемых листьев
верен, а порядок сложения роли не играет. Но для **некоммутативной** операции (конкатенация
строк, умножение матриц) граничные узлы собираются «вперемешку», и левый/правый вклад надо
аккумулировать раздельно — проще взять рекурсивную версию с явными `[lo, hi]` на узле.

## ⚙️ Цена на практике

### Итеративная против рекурсивной

Компактный массив `2n` без указателей — это плотная память, дружелюбная к кэшу, и
обновление/запрос «снизу вверх» без накладных расходов на рекурсию. Рекурсивная версия
(обычно массив `4n` + кадры стека) медленнее, но гибче: легко навесить lazy, работать с
явными границами и некоммутативными операциями. Для собеседования итеративная сумма —
кратчайший корректный код.

### Дай рекурсии публичную обёртку

Сигнатура `query(node, lo, hi, ql, qr)` требует от вызывающего знать `node=1, lo=0,
hi=n-1` — частый источник ошибок. Прячь её за `RangeQuery(l, r)`, который зовёт
`query(1, 0, n-1, l, r)` (как в `LazySegmentTree` выше). Наружу — только `(l, r)`.

### Не доставай дерево отрезков, когда хватает меньшего

Дерево отрезков — тяжёлый универсальный инструмент. Бери его, только если **есть и
обновления, и диапазонные запросы вперемешку**. Иначе:

- массив **статичен** → префиксные суммы (`O(1)` запрос, `O(n)` препроцессинг);
- только точечные обновления + префиксная сумма → [дерево Фенвика](fenwick-tree-structure.md)
  (проще, меньше памяти, та же `O(log n)`).

И помни про переполнение: в `apply` множитель `(hi-lo+1) * delta` на большом отрезке
растёт быстро.

## ⚠️ Типичные ошибки

1. **Путаница включительного/полуоткрытого диапазона** — в `Query` `r` сдвигается на `+1`, превращая `[l, r]` в `[l, r)`.
2. **Забыли обновить предков** в `Update` — запрос вернёт устаревшие данные.
3. **Неверный нейтральный элемент** для min/max-дерева (`0` вместо `±∞`).
4. **Lazy: забыли `push`** перед спуском — дети вернут устаревшие данные.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он медленный, и
только потом дерево отрезков.

> **Задача (Range Sum Query — Mutable).** Дан массив `nums`. Поступает поток операций
> двух видов **вперемешку**: `update(i, val)` — присвоить `nums[i] = val`, и
> `query(l, r)` — вернуть сумму на `[l, r]` включительно. Обработать все за минимум
> времени на операцию.
> Пример: `nums = [2,1,5,3,4,7,6,8]`; `query(1,4)=13`, затем `update(2,10)`,
> снова `query(1,4)=18`.

**Шаг 1. Наивно: префиксные суммы — запрос O(1), но обновление O(n).**

```go
type Naive struct{ pre []int } // pre[i] = nums[0]+...+nums[i-1]

func NewNaive(nums []int) *Naive {
    pre := make([]int, len(nums)+1)
    for i, v := range nums {
        pre[i+1] = pre[i] + v
    }
    return &Naive{pre}
}

func (n *Naive) Query(l, r int) int { return n.pre[r+1] - n.pre[l] } // O(1)

func (n *Naive) Update(i, val int) { // O(n): пересчитать хвост префиксов
    delta := val - (n.pre[i+1] - n.pre[i])
    for k := i + 1; k < len(n.pre); k++ {
        n.pre[k] += delta
    }
}
```

Это **работает и проходит тесты**: запрос — мгновенный. Но `update` рушит весь смысл
префиксов — меняя один элемент, мы обязаны пересчитать все префиксы правее него, это
O(n). При потоке из `m` обновлений выходит O(n·m). Симметричный наивный вариант (хранить
сырой массив: `update` за O(1), но `query` суммирует диапазон за O(n)) переносит ту же
цену на запросы. Перекос неустраним: одна из двух операций линейна, потому что **префиксы
статичны по своей природе**, а у нас они меняются.

**Шаг 2. Ключевое наблюдение.** Сумму на `[l, r]` не обязательно собирать из `n`
отдельных элементов или одного жёсткого префикса — её можно собрать из `O(log n)`
**заранее посчитанных частичных сумм**, покрывающих диапазон целиком. Если эти частичные
суммы держать в дереве (лист = элемент, узел = сумма детей), то точечное обновление
затрагивает лишь `O(log n)` узлов на пути от листа к корню — а не весь хвост. Так
**обе** операции становятся O(log n): ни запрос, ни обновление больше не линейны. Это
ровно [инвариант «`tree[node]` верен для всего отрезка узла»](#почему-запрос--olog-n)
из раздела выше.

**Шаг 3. Оптимум: дерево отрезков — запрос и обновление по O(log n).**

Берём итеративную реализацию из [«Разбора»](#-разбор) выше (`NewSegmentTree`, `Update`,
`Query`) — повторять её код здесь незачем. На потоке операций из условия применяем как есть:

```go
st := NewSegmentTree([]int{2, 1, 5, 3, 4, 7, 6, 8})
st.Query(1, 4)   // 13
st.Update(2, 10) // nums[2] = 10, обновятся O(log n) узлов на пути к корню
st.Query(1, 4)   // 18
```

И `Update`, и `Query` трогают по одному узлу на каждом из `log n` уровней — перекоса
наивного решения больше нет.

Прогоните `Query(1, 4)` на дереве по шагам: итеративный обход поднимается снизу вверх и
забирает ровно те узлы, чьё поддерево целиком лежит внутри `[1, 4]` — их `O(log n)`, а не
четыре отдельных элемента:

**Шаг 4. Трассировка** запроса `Query(1, 4)` на `nums = [2,1,5,3,4,7,6,8]` (n=8). Листья
лежат в индексах `[8, 16)`; итеративный обход стартует с `l=1+8=9`, `r=4+8+1=13` и поднимается
вверх, забирая узлы, чьё поддерево целиком внутри `[1, 4]`:

| итерация | `l`, `r` | `l&1==1` → take | `r&1==1` → take | взятый узел (отрезок) | `res` |
|----------|----------|-----------------|-----------------|------------------------|-------|
| 1 | `l=9`, `r=13` | да: `tree[9]` | да: `r→12`, `tree[12]` | лист `[1]`=1, лист `[4]`=4 | 5 |
| —        | `l→5`, `r→6` | (поднялись)     | (поднялись)     | —                      | 5 |
| 2 | `l=5`, `r=6` | да: `tree[5]` | нет | узел `[2,3]`=5+3=8 | 13 |
| —        | `l→3`, `r→3` | `l<r` ложно — стоп | | | **13** |

Запрос `[1, 4]` разложился ровно на **3 канонических узла** (`[1]`, `[2,3]`, `[4]`) вместо
четырёх отдельных элементов — наглядно, почему `O(log n)`. После `update(2, 10)` лист `[2]`
и узел `[2,3]` на пути к корню обновятся, и тот же запрос вернёт `18`.

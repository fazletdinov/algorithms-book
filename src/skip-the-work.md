# 🧘 Когда алгоритм не нужен: лучшая работа — несделанная

> 🧭 **Зачем эта глава.** Вся книга учит делать работу быстрее: `O(n)` вместо `O(n²)`, куча
> вместо сортировки, окно вместо перебора. Эта глава — противовес. В проде самые большие
> выигрыши чаще всего приносит не более быстрый алгоритм, а работа, которую **не сделали**:
> не отсортировали всё ради десяти строк, не пошли в базу тысячу раз, не пересчитали то, что
> не менялось. Такие правки дают не проценты, а порядки — и замеры ниже это показывают.
>
> Глава построена как шесть вопросов, которые стоит задать **до** выбора алгоритма. Первые
> четыре подкреплены замерами на [Postgres-лаборатории](postgres-plans.md) (`make pg-lab`) и в
> тренажёре — все команды в тексте. Пятый и шестой — рассуждение: честного замера для очередей
> в рамках книги нет, и выдумывать его я не стал.

## 1. Нужна ли эта работа вообще?

Нужны 10 самых дорогих заказов из двух миллионов. Три способа, один и тот же ответ:

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT id, amount FROM orders ORDER BY amount DESC;           -- всё
EXPLAIN (ANALYZE, BUFFERS) SELECT id, amount FROM orders ORDER BY amount DESC LIMIT 10;  -- 10
EXPLAIN (ANALYZE, BUFFERS) SELECT id, created_at FROM orders ORDER BY created_at DESC LIMIT 10;
```

| Что просим | Что делает Postgres | Время (медиана из 5) |
|---|---|---|
| отсортировать всё | внешняя сортировка через диск, 41 МБ временных файлов | 1121 мс |
| `LIMIT 10`, индекса нет | `Sort Method: top-N heapsort  Memory: 25kB` | 201 мс |
| `LIMIT 10`, индекс есть | `Index Scan Backward`: 10 записей с конца B-дерева, 13 страниц | 0.033 мс |

Вторая строка — это [глава про Top-K](top-k-elements.md), сделанная за тебя: увидев `LIMIT`,
планировщик заменил полную сортировку кучей на десять элементов. Время упало в пять с лишним
раз, но совсем не ушло: каждую из двух миллионов строк всё равно надо прочитать и сравнить с
вершиной кучи. `EXPLAIN ANALYZE` с таймингом узлов делит его примерно поровну — около 120 мс
на чтение и около 150 на кучу. Третья строка убирает и то, и другое: индекс уже упорядочен, и
базе достаточно прочитать десять записей. От первой строки до третьей — в
**34 000 раз**, при одинаковом ответе.

То же на каждом шагу в бэкенде — пагинация через `OFFSET`:

```sql
-- страница 50 000: база находит и ВЫБРАСЫВАЕТ миллион строк, чтобы отдать 20
SELECT id, created_at FROM orders ORDER BY created_at DESC OFFSET 1000000 LIMIT 20;
-- keyset: клиент присылает created_at последней строки прошлой страницы
SELECT id, created_at FROM orders WHERE created_at < $1 ORDER BY created_at DESC LIMIT 20;
```

| Пагинация на глубине миллиона строк | Страниц прочитано | Время (медиана из 5) |
|---|---|---|
| `OFFSET 1000000 LIMIT 20` | ≈ 1 000 000 | ~430 мс |
| keyset (`WHERE created_at < …`) | 23 | 0.05 мс |

`OFFSET` не «перепрыгивает» строки — базе негде взять миллионную строку, кроме как пройти
все предыдущие. Keyset превращает «пропусти миллион» в «найди в B-дереве точку и прочитай
20 после неё», то есть в тот же `O(log n)`, что и поиск по индексу. На первой странице разницы
нет; она растёт вместе с номером страницы — ровно там, куда заходят боты и выгрузки.

Одна деталь, которую упрощение прячет: если значения `created_at` могут совпадать, граница
страницы неоднозначна. В проде keyset делают по паре `(created_at, id)` с составным индексом.

## 2. Можно ли сделать её пачкой?

Сервис показывает заказы тысячи пользователей. Цикл в коде выглядит невинно:

```go
for _, id := range userIDs {
	rows, err := db.Query(ctx, "SELECT id, amount FROM orders WHERE user_id = $1", id) // запрос на каждого
	// ...
}
```

Это **N+1**: один запрос за списком и ещё по одному на каждый его элемент. Пачка — один запрос:

```sql
SELECT user_id, id, amount FROM orders WHERE user_id = ANY($1::int[]);
```

Замер — `./pglab/n_plus_one.sh` (тысяча пользователей, около 10 000 заказов):

| Способ | Время запросов (медиана из 5) |
|---|---|
| N+1 — 1000 запросов | 89–95 мс |
| пачка — 1 запрос | 13 мс |

**В семь раз — и это лучший случай для N+1.** Замер идёт внутри контейнера, где сети почти
нет. Каждый из тысячи запросов платит постоянную цену: разобрать SQL, построить план, отдать
ответ. В проде к этому добавляется сетевая задержка до базы — от десятых долей миллисекунды
в одном дата-центре до миллисекунды и больше между зонами. Дальше уже **расчёт, а не замер**:
при задержке 0.5 мс тысяча запросов добавит ещё полсекунды, а пачка — те же 0.5 мс один раз.
Алгоритм выборки при этом одинаковый; отличается только число походов.

Тот же вопрос работает далеко за пределами SQL: `MGET` вместо тысячи `GET` в Redis, пакетная
отправка в Kafka вместо сообщения на каждое событие, один HTTP-запрос с массивом вместо цикла
по ID. Это [амортизация](big-o.md) в прикладном виде: постоянную цену одного похода делят на
всю пачку.

## 3. Можно ли сделать её один раз?

[Дерево отрезков](segment-tree-structure.md) отвечает на сумму на отрезке за `O(log n)` и
позволяет обновлять элементы. Но если данные **не меняются** — справочник, итоги за прошлые
дни, снимок — обновлять нечего. Тогда всю работу можно сделать заранее и один раз:
префиксные суммы за `O(n)`, и любая сумма на `[l, r]` — одно вычитание.

```go
prefix := make([]int, len(arr)+1) // prefix[i] — сумма arr[0..i-1]
for i, v := range arr {
	prefix[i+1] = prefix[i] + v
}
sum := prefix[r+1] - prefix[l] // O(1) на запрос
```

```bash
cd exercises
go test -p 1 -tags solution -run='^$' -bench=StaticRangeSum -count=5 ./segtree/
```

| Сумма на отрезке, 100 000 элементов, данные не меняются | нс на запрос |
|---|---|
| префиксные суммы | 1.6 |
| дерево отрезков | 101 |

В 64 раза, и без единой строчки сложного кода. Дерево окупается ровно тогда, когда между
запросами есть обновления: тогда префиксные суммы пришлось бы пересчитывать за `O(n)` каждый
раз. Это не «дерево плохое» — это вопрос, который задают **до** выбора структуры: меняются ли
данные между запросами?

Тот же приём в других обличьях — [мемоизация в ДП](dynamic-programming.md) («не пересчитывай
подзадачу»), [LRU-кэш](pattern-combinations.md) перед медленным сервисом, материализованное
представление в базе, счётчик, который обновляют при записи, а не пересчитывают при чтении.
Везде один размен: память и сложность инвалидации в обмен на повторную работу.

## 4. Может ли её сделать кто-то другой — лучше?

Тот, у кого нужная структура данных уже есть. Сортировать в Go то, что можно получить из базы
уже упорядоченным по индексу, — значит повторить работу, которую B-дерево сделало при записи.
Считать топ игроков в памяти сервиса, когда [Redis Sorted Set](top-k-elements.md#-инженерный-кейс) держит его
отсортированным при каждом `ZINCRBY`, — то же самое. Фильтровать миллион строк в приложении
после `SELECT *` — значит тащить по сети всё ради малой доли: `WHERE` в базе работает по
индексу и отдаёт только нужное.

Правило: **работа должна делаться там, где лежат данные и нужная структура**. Глава
[«Postgres: EXPLAIN как pprof»](postgres-plans.md) показывает, как увидеть, делает ли база
то, на что ты рассчитываешь.

## 5. Можно ли сделать её позже?

Раздел без замера — очередь в рамках книги не поднять так, чтобы цифры что-то значили, и
придумывать их я не буду. Но вопрос от этого не менее важен.

Пользователь, нажавший «оформить заказ», ждёт ответа «принято». Письмо-подтверждение,
пересчёт рекомендаций, обновление аналитики и выгрузка в бухгалтерию ему в этот момент не
нужны. Всё, что не нужно для ответа, можно положить в очередь (Kafka, очередь в Redis,
таблица-outbox в Postgres) и сделать отдельным обработчиком. Время ответа перестаёт зависеть
от самого медленного из побочных действий, а обработчики переживают сбой и повторяют работу.

Цена — согласованность: письмо уйдёт не мгновенно, аналитика отстанет на секунды, а
обработчик обязан быть идемпотентным, потому что сообщение может прийти дважды. Поэтому
откладывают только то, для чего задержка допустима, — и это решение про требования, а не
про код.

## 6. Можно ли ответить приблизительно?

«Сколько уникальных посетителей было вчера» — точный ответ требует хранить всех посетителей.
[HyperLogLog](probabilistic-structures.md) даёт ответ с ошибкой меньше процента в
12 килобайтах памяти — в Redis это `PFADD` и `PFCOUNT`. Счётчик «примерно 12 тысяч
просмотров» не обязан быть точным до единицы, а «товар кончился» — обязан.

Вопрос «а точный ответ точно нужен?» чаще всего адресован не коду, а тому, кто ставил задачу.
Иногда он снимает целую подсистему.

## А когда алгоритм всё-таки нужен

Эта глава — не против алгоритмов. Шесть вопросов срезают работу **вокруг** алгоритма, но
остаётся ядро, которое срезать нельзя:

- данные уже в памяти сервиса, и отдать их базе дороже, чем обработать на месте;
- задача не выражается ни индексом, ни `LIMIT`, ни кэшем — граф зависимостей, расписание,
  маршрут, сопоставление строк;
- горячий путь, который выполняется миллионы раз в секунду, — там константа из
  [«Цены на практике»](sliding-window.md) решает всё;
- ты пишешь ту самую «кого-то другого»: базу, брокер, библиотеку, кэш.

Порядок, который из этого следует: **сначала вопросы из этой главы, потом измерение, и только
потом — алгоритм**. Хороший алгоритм, применённый к работе, которую не нужно было делать, —
это быстрое решение не той задачи.

## ⚠️ Типичные ошибки

1. **Оптимизировать сортировку, когда нужен `LIMIT`.** Полная сортировка ради десяти строк —
   в замере в 34 000 раз медленнее индекса.
2. **`OFFSET` для глубоких страниц.** База проходит и выбрасывает все пропущенные строки;
   на миллионной — сотни миллисекунд вместо долей миллисекунды у keyset.
3. **Запрос в цикле.** N+1 в лучшем случае в семь раз медленнее пачки, а в проде ещё и платит
   сетевую задержку за каждый проход.
4. **Сложная структура для неизменяемых данных.** Дерево отрезков там, где хватает префиксных
   сумм, — в замере в 64 раза медленнее на запрос.
5. **Работа в приложении, которую сделает база.** `SELECT *` и фильтр в коде вместо `WHERE`
   по индексу.
6. **Всё синхронно на пути запроса.** Пользователь ждёт письмо, аналитику и выгрузку, хотя
   ему нужен только ответ «принято».

## 💻 Практика: повтори замеры

```bash
make pg-lab                        # база из главы про Postgres
./pglab/n_plus_one.sh 1000 5       # N+1 против пачки
make pg-psql                       # и запросы из разделов 1 и 2 — через EXPLAIN (ANALYZE, BUFFERS)
cd exercises && go test -p 1 -tags solution -run='^$' -bench=StaticRangeSum -count=5 ./segtree/
```

Попробуй `n_plus_one.sh` с 10 и с 10 000 пользователями. У меня вышло так:

| Пользователей | N+1 | пачка | во сколько раз |
|---|---|---|---|
| 10 | 2.2 мс | 1.3 мс | 1.7 — выигрыш меньше миллисекунды |
| 1 000 | 89–95 мс | 13 мс | ~7 |
| 10 000 | 824 мс | 56 мс | ~15 |

Это и есть ответ на вопрос «когда N+1 — проблема»: когда N не маленькое и не ограничено
сверху. На десяти элементах переписывать цикл не обязательно; на списке, который растёт вместе
с данными, — обязательно, и чем раньше, тем дешевле.

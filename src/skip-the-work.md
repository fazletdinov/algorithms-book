# 🧘 Когда алгоритм не нужен: лучшая работа — несделанная

> 🧭 **Зачем эта глава.** Вся книга учит делать работу быстрее: `O(n)` вместо `O(n²)`, куча
> вместо сортировки, окно вместо перебора. Эта глава — противовес. Самые большие выигрыши
> чаще приносит не более быстрый алгоритм, а работа, которую **не сделали**: не отсортировали
> всё ради десяти строк, не пошли в базу тысячу раз, не пересчитали то, что не менялось.
>
> Глава — шесть вопросов, которые стоит задать **до** выбора алгоритма. Числа в первых двух
> разделах — замер на Postgres 16 (два миллиона заказов, медиана из пяти прогонов); лаборатории
> для него в репозитории больше нет, так что это иллюстрация порядка, а не цифры для повтора.
> Замер третьего раздела повторяется тренажёром. Последние три вопроса — рассуждение.

## 1. Нужна ли эта работа вообще?

Нужны 10 самых дорогих заказов из двух миллионов. `ORDER BY amount DESC` сортирует всё
(в замере — 1121 мс). С `LIMIT 10` база сама применяет [Top-K](top-k-elements.md): один проход
и куча на десять строк (`top-N heapsort`, 201 мс) — читать все строки всё равно приходится.
Индекс по сортируемому полю убирает и чтение: B-дерево уже упорядочено, и достаточно взять
десять записей с края (0.033 мс). Ответ один и тот же, разница — в **34 000 раз**.

То же с пагинацией через `OFFSET 1000000 LIMIT 20`: базе негде взять миллионную строку, кроме
как пройти и выбросить все предыдущие (~430 мс). Keyset — «дай 20 строк после `created_at`
последней строки прошлой страницы» — это поиск точки в индексе за `O(log n)` и 20 строк после
неё (0.05 мс). Если значения ключа могут совпадать, keyset делают по паре `(created_at, id)`.

## 2. Можно ли сделать её пачкой?

Сервис показывает заказы тысячи пользователей. Цикл в коде выглядит невинно:

```go
for _, id := range userIDs {
	rows, err := db.Query(ctx, "SELECT id, amount FROM orders WHERE user_id = $1", id) // запрос на каждого
	// ...
}
```

Это **N+1**: один запрос за списком и ещё по одному на каждый его элемент. Пачка — один
запрос `WHERE user_id = ANY($1)` на всех сразу. Выборка у обоих одна и та же; разница — в числе
походов: каждый платит постоянную цену (разобрать запрос, построить план, отдать ответ), а в
проде ещё и сетевую задержку. В замере на Postgres 16, где сети почти не было, тысяча
запросов шла около 90 мс против 13 мс у пачки — в семь раз; на 10 пользователях выигрыш меньше
миллисекунды, на 10 000 — около 15 раз. N+1 становится проблемой, когда N не мало и не
ограничено сверху.

Тот же вопрос работает далеко за пределами SQL: один HTTP-запрос с массивом вместо цикла по ID,
буферизованная запись вместо системного вызова на каждый байт. Это [амортизация](big-o.md) в
прикладном виде: постоянную цену одного похода делят на всю пачку.

## 3. Можно ли сделать её один раз?

[Дерево отрезков](segment-tree.md) отвечает на сумму на отрезке за `O(log n)` и
позволяет обновлять элементы. Но если данные **не меняются** — справочник, итоги за прошлые
дни, снимок — обновлять нечего. Тогда всю работу можно сделать заранее и один раз:
префиксные суммы за `O(n)`, и любая сумма на `[l, r]` — одно вычитание.

```go
prefix := make([]int, len(arr)+1) // prefix[i] — сумма arr[0..i-1]
for i, v := range arr {
	prefix[i+1] = prefix[i] + v
}
sum := prefix[r+1] - prefix[l] // O(1) на запрос
```

| Сумма на отрезке, 100 000 элементов, данные не меняются | нс на запрос |
|---|---|
| префиксные суммы | 1.6 |
| дерево отрезков | 101 |

В 64 раза (бенчмарк — `exercises/segtree/static_bench_test.go`, команда — в «Практике» ниже).
Дерево окупается, только когда между запросами есть обновления. Вопрос, который задают **до**
выбора структуры: меняются ли данные между запросами? Тот же приём — [мемоизация в
ДП](dynamic-programming.md), [LRU-кэш](pattern-combinations.md) перед медленным сервисом,
счётчик, который обновляют при записи, а не пересчитывают при чтении: память в обмен на
повторную работу.

## 4. Может ли её сделать кто-то другой — лучше?

Тот, у кого нужная структура данных уже есть. Сортировать в Go то, что база отдаст уже
упорядоченным по индексу, — повторять работу, которую B-дерево сделало при записи. Фильтровать
миллион строк в приложении после `SELECT *` — тащить всё ради малой доли, когда `WHERE` по
индексу отдал бы только нужное.

Правило: **работа должна делаться там, где лежат данные и нужная структура**.

## 5. Можно ли сделать её позже?

Пользователь, нажавший «оформить заказ», ждёт ответа «принято». Письмо, аналитика и выгрузка
в бухгалтерию ему в этот момент не нужны: их можно положить в очередь и сделать отдельным
обработчиком. Время ответа перестаёт зависеть от самого медленного побочного действия. Цена —
согласованность: письмо уйдёт не мгновенно, а обработчик обязан быть идемпотентным, потому что
сообщение может прийти дважды. Откладывают только то, для чего задержка допустима, — это
решение про требования, а не про код.

## 6. Можно ли ответить приблизительно?

«Сколько уникальных посетителей было вчера» — точный ответ требует хранить всех посетителей.
[HyperLogLog](probabilistic-structures.md) даёт ответ с ошибкой около процента в нескольких
килобайтах. Счётчик «примерно 12 тысяч просмотров» не обязан быть точным до единицы, а «товар
кончился» — обязан. Вопрос «а точный ответ точно нужен?» чаще адресован тому, кто ставил задачу.

## А когда алгоритм всё-таки нужен

Эта глава — не против алгоритмов. Шесть вопросов срезают работу **вокруг** алгоритма, но
остаётся ядро, которое срезать нельзя:

- данные уже в памяти сервиса, и отдать их базе дороже, чем обработать на месте;
- задача не выражается ни индексом, ни `LIMIT`, ни кэшем — граф зависимостей, расписание,
  маршрут, сопоставление строк;
- горячий путь, который выполняется миллионы раз в секунду, — там константа из
  [«Цены на практике»](sliding-window.md) решает всё;
- ты пишешь ту самую «кого-то другого»: базу, брокер, библиотеку, кэш.

Порядок, который из этого следует: **сначала вопросы из этой главы, потом измерение, и только
потом — алгоритм**. Хороший алгоритм, применённый к работе, которую не нужно было делать, —
это быстрое решение не той задачи.

## ⚠️ Типичные ошибки

1. **Сортировать всё, когда нужен `LIMIT`.** Полная сортировка ради десяти строк — в замере
   в 34 000 раз медленнее индекса.
2. **`OFFSET` для глубоких страниц.** База проходит и выбрасывает все пропущенные строки.
3. **Запрос в цикле.** N+1 платит постоянную цену похода — и сетевую задержку — за каждый элемент.
4. **Сложная структура для неизменяемых данных.** Дерево отрезков там, где хватает префиксных
   сумм, — в замере в 64 раза медленнее на запрос.
5. **Всё синхронно на пути запроса.** Пользователь ждёт письмо и аналитику, хотя ему нужен
   только ответ «принято».

> 🌍 **Где это в настоящем коде** (Go 1.24)
>
> - [`bufio.Writer`](https://github.com/golang/go/blob/go1.24.0/src/bufio/bufio.go) — пачка вместо цикла: `Write` копит байты в буфере, и системный вызов уходит один раз на `Flush` или на заполненный буфер.
> - [`sync.Once`](https://github.com/golang/go/blob/go1.24.0/src/sync/once.go) — «сделать один раз»: инициализация выполняется при первом вызове `Do`, остальные получают готовое.
> - [`container/heap`](https://github.com/golang/go/blob/go1.24.0/src/container/heap/heap.go) — куча, на которой строится тот же приём, что у `LIMIT` в базе: держать k лучших вместо сортировки всего.

## ⚡ Шаблон для собеседования

Универсальный каркас **переменного** окна — его и стоит помнить:

```go
left := 0
for right := 0; right < len(s); right++ {
    add(s[right])                  // 1. расширяем окно вправо

    for windowInvalid() {          // 2. пока условие нарушено —
        remove(s[left])            //    сжимаем слева
        left++
    }

    best = max(best, right-left+1) // 3. обновляем ответ
}
```

1. `right` добавляет новый элемент в окно;
2. пока окно «невалидно» — двигаем `left` и убираем элементы;
3. после восстановления условия обновляем ответ (`right - left + 1`).

## 📖 Разбор

<details class="algo-details">
<summary>Теория, два типа окон и сложность</summary>

**Скользящее окно** — техника для операций над подмассивами или подстроками
**фиксированного** или **переменного** размера в линейной структуре (массив, строка).

Ключевая идея — **инкрементальное обновление**: переходя к следующему окну, мы
добавляем один новый элемент и убираем один старый, вместо полного пересчёта. Это
снижает сложность с O(n·k) (наивный пересчёт каждого окна) до **O(n)**.

#### Фиксированное окно

Размер `k` постоянен. Считаем сумму первого окна, затем двигаем границу, добавляя
`arr[i]` и вычитая `arr[i-k]`.

```go
func maxSumSubarray(arr []int, k int) int {
    if k <= 0 || k > len(arr) {
        return 0
    }
    windowSum := 0
    for i := 0; i < k; i++ {
        windowSum += arr[i]
    }
    maxSum := windowSum
    for i := k; i < len(arr); i++ {
        windowSum += arr[i] - arr[i-k] // +новый, −старый за O(1)
        if windowSum > maxSum {
            maxSum = windowSum
        }
    }
    return maxSum
}
```

#### Переменное окно

Размер меняется под условие: расширяем окно правой границей `right`, а при нарушении
условия сжимаем слева `left`. Состояние окна (счётчики, частоты) держим в `map` или
переменной.

```go
// Самая длинная подстрока, где не более k различных символов
func longestKDistinct(s string, k int) int {
    freq := make(map[byte]int)
    left, maxLen := 0, 0
    for right := 0; right < len(s); right++ {
        freq[s[right]]++
        for len(freq) > k { // условие нарушено — сжимаем слева
            freq[s[left]]--
            if freq[s[left]] == 0 {
                delete(freq, s[left])
            }
            left++
        }
        if cur := right - left + 1; cur > maxLen {
            maxLen = cur
        }
    }
    return maxLen
}
```

Порядок шагов для переменного окна: **расширить** (`right++`) → **проверить условие** →
**сжать** при необходимости (`left++`) → **обновить результат**.

#### Сложность

| Тип окна            | Время | Память                          |
|---------------------|-------|----------------------------------|
| Фиксированное       | O(n)  | O(1)                             |
| Переменное          | O(n)  | O(k) или O(σ) (σ — размер алфавита) |

Переменное окно линейно, потому что каждый элемент добавляется и удаляется не более
одного раза (и `left`, и `right` проходят массив всего по разу).

## 🧠 Почему это корректно

Два вопроса, которые отделяют «работает на моих тестах» от «я знаю, что это
правильно»: **почему сжатие слева только при нарушении не пропускает ответ** и
**почему вложенный `while` не делает алгоритм квадратичным**.

### Предусловие применимости — главное

Скользящее окно корректно **тогда и только тогда**, когда оптимальная левая граница
монотонна: при росте `right` нужный `left` **никогда не убывает**. Формально, от
предиката «окно валидно» требуется свойство:

> Если окно `[left, right]` валидно, то любое более узкое `[left', right]` с
> `left' ≥ left` тоже валидно.

То есть валидность при сужении **сохраняется**. Тогда для каждого `right` множество
валидных `left` — это суффикс `[L(right), right]`, и граница `L(right)` не убывает с
ростом `right`.

- **Держится:** «не более `k` различных символов» (убрали символ — различных не
  стало больше); «сумма ≥ target» при **неотрицательных** числах (убрали элемент —
  сумма не выросла).
- **Ломается:** «сумма ≥ target» при наличии **отрицательных** чисел — убрав
  элемент, сумму можно *увеличить*, значит `L(right)` не монотонна. Окно неприменимо,
  нужен префиксный массив + другая техника. Это и есть строгая формулировка пункта
  «окно нельзя пересчитать инкрементально» из карточки «когда НЕ применять».

Прежде чем писать окно — проверь это свойство на задаче. Если оно не держится, окно
даст неверный ответ, а не просто медленный.

### Инвариант цикла

**После обработки очередного `right` отрезок `[left, right]` — самое длинное валидное
окно, заканчивающееся в `right`.** Почему он сохраняется:

1. расширили вправо (`right++`) — возможно, нарушили условие;
2. внутренний `while` двигает `left` вперёд ровно до `L(right)` — первой валидной
   позиции;
3. благодаря монотонности `L` указатель `left` **никогда не нужно возвращать назад**:
   то, что было невалидно при меньшем `right`, тем более невалидно сейчас.

Итоговый ответ — максимум по всем `right` из этих «лучших окон, заканчивающихся в
`right`». Любое валидное окно где-то заканчивается, поэтому, перебрав все правые
концы, мы **не пропускаем ни одного кандидата**.

### Почему линейно, хотя цикл вложенный

Вложенный `while` пугает — выглядит как O(n²). Но `left` **только растёт** и никогда
не сбрасывается: за весь прогон он сделает не более `n` шагов суммарно. `right` —
тоже `n`. Итого ≤ 2n операций с указателями, **амортизированно O(n)**. Стоимость
внутреннего цикла «размазана» по итерациям внешнего — это тот же амортизационный
аргумент, что и у дека в `MaxSlidingWindow` ниже.

## ⚙️ Цена на практике

`O(n)` скрывает константу — а инженер за неё платит тактами и аллокациями.

### `map[byte]int` против `[256]int`

Для счётчика символов в окне напрашивается `map`, но для байтового алфавита почти
всегда лучше массив фиксированного размера:

```go
var freq [256]int   // на стеке, без аллокаций в куче, без хеширования
```

- `map` — это аллокация в куче, хеш на каждом доступе, погоня за указателями и
  нагрузка на GC;
- `[256]int` живёт одним блоком, доступ — одно обращение по индексу, отлично ложится
  в кэш процессора.

Big-O один и тот же — `O(n)`, но на горячем пути разница в разы. `map` оправдан лишь
когда алфавит большой или разреженный (Unicode-руны, произвольные ключи).

### `O(n)` не всегда быстрее `O(n log n)`

Окно за `O(n)` с `map` способно проиграть решению за `O(n log n)` на массиве — из-за
константного фактора и промахов кэша, особенно на небольших `n`. «Асимптотически
лучше» ≠ «быстрее на твоих данных». Меряй (`testing.B`, `pprof`), а не угадывай —
это привычка инженера, а не кодера.

### `MaxSlidingWindow` и дек: почему всё ещё `O(n)`

Наивный максимум окна — `O(n·k)`. Монотонный дек индексов даёт `O(n)`, потому что
**каждый индекс кладётся и вынимается ровно один раз** — снова амортизация, как с
`left` выше. В Go дек удобно держать срезом `[]int` (хранят **индексы**, не значения):
добавляем в конец, снимаем с обоих концов. Резервируй ёмкость заранее —
`make([]int, 0, k)` — чтобы избежать перевыделений при росте.

### Байты против рун

`len(s)` и `s[i]` работают с **байтами**, не символами. Для ASCII-задач это именно
то, что нужно, и это быстро. Для Unicode (`"café"`) итерируйся по `[]rune(s)` или
через `range` — иначе окно «режет» многобайтовый символ пополам. Большинство задач на
LeetCode — ASCII, но на этом регулярно спотыкаются.

## ⚠️ Типичные ошибки

1. **Пересчёт всей суммы окна заново** в цикле — это возвращает O(n·k). Обновляйте
   инкрементально: `windowSum += arr[right] - arr[left]`.
2. **Off-by-one в размере окна** — длина окна это `right - left + 1`, а не `right - left`.
3. **Забыли обновить результат после сжатия** переменного окна — обновляйте `maxLen`
   после того, как условие снова выполнено.
4. **Неверный момент пометки в `map`** — увеличивайте/уменьшайте частоты строго при
   входе элемента в окно и выходе из него, иначе состояние «съезжает».
5. **Не обработаны границы** — пустой массив, `k > len(arr)`, `k = 0`.

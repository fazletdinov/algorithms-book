## 🧭 Откуда берётся окно: выведем его сами

Правило из «Запомни» — `right` расширяет, `left` идёт следом — не нужно зубрить. Оно получается
само, если взять обычный перебор и запретить ему выбрасывать уже посчитанное. Проследим на
задаче.

> **Задача.** Дан массив **положительных** чисел `nums` и число `target`. Найди длину самого
> короткого непрерывного куска с суммой не меньше `target`.
> Пример: `[2, 3, 1, 2, 4, 3]`, `target = 7` → `2` (кусок `[4, 3]`).

В лоб это решают так: берут каждое начало `i` и идут вправо, складывая, пока сумма не дойдёт
до `target`. Дошла — длина-кандидат есть. Переходим к следующему началу и складываем с нуля.

Посмотри на первые две строки перебора:

- начало `i = 0`: `2`, `2+3 = 5`, `+1 = 6`, `+2 = 8` — дошли, длина 4;
- начало `i = 1`: `3`, `3+1 = 4`, `+2 = 6`, `+4 = 10` — дошли, длина 4.

Во второй строке первые три сложения — повтор. Сумму `3+1+2` мы уже держали в руках: это
`8`, из которой ушла двойка, `8 − 2 = 6`. И начинать заново с `[3]` и `[3, 1]` незачем: числа
положительные, раз даже `[3, 1, 2]` не добрал до 7, куски покороче не доберут тем более.

Отсюда приём. При смене начала не выбрасывай сумму, а вычти ушедший слева элемент. Правый
край не возвращай назад — продолжай с того места, где он остановился. Оба края идут только
вперёд, а сумма правится на один элемент за шаг.

**Окно считает, как лимитер запросов «за последние 60 секунд»: пришедшее прибавь справа,
выбывшее вычти слева — и ни один край не ходит назад.**

Это и есть скользящее окно (sliding window). Первую половину вывода — правку суммы на один
элемент — первый виджет ниже показывает на окне постоянной длины. Код этой задачи и трасса по
шагам — в [«📝 Разбор задачи»](#-разбор-задачи).

### Вторая семья: самое длинное при ограничении

Задача выше — из семьи «самое **короткое**, набравшее цель» (дальше — семья B): левый край
двигаем, пока окно ещё годится, и ответ записываем по ходу этого сдвига. Есть зеркальная
семья A — «самое **длинное** при ограничении», например самая длинная подстрока, где не
больше `k` различных букв. Правка та же: впустил справа, выпустил слева. Но левый край двигаем, пока окно **сломано**, а ответ берём
после этого, когда окно снова годится.

На строке `AABACCBA` при `k = 2` (второй виджет ниже) окно растёт до `AABA` — длина 4. На
`right = 4` входит `C`, букв становится три, окно сломано (виджет пишет «окно невалидно»), и
`left` сдвигается впервые — сразу на три шага, до окна `AC`. Дальше окно вырастет лишь до
`ACC`, а `ACCB` и `CCBA` снова ломаются (три вида букв): ответ 4.

В коде обеих семей цикл удобнее вести по правому краю, а не по началу, как в переборе: впустил
элемент — и двигай левый, сколько нужно.

## ⚡ Шаблон для собеседования

Каркасов переменного окна два — по семье. Отличаются они условием внутреннего цикла и местом,
где берут ответ.

```go
// Семья A — самое длинное при ограничении
left := 0
for right := 0; right < len(s); right++ {
    add(s[right])                  // впустили справа

    for windowInvalid() {          // пока окно сломано —
        remove(s[left])            //   выпускаем слева
        left++
    }

    best = max(best, right-left+1) // окно снова годится — ответ после цикла
}
```

```go
// Семья B — самое короткое, набравшее цель
left := 0
for right := 0; right < len(s); right++ {
    add(s[right])                      // впустили справа

    for windowValid() {                // пока цель набрана —
        best = min(best, right-left+1) //   ответ внутри, до сдвига
        remove(s[left])                //   выпускаем слева
        left++
    }
}
```

| Семья | Слова в условии | `left` двигаем | Ответ берём |
|---|---|---|---|
| A. Самое **длинное** при ограничении | «не более `k` различных», «нулей ≤ `k`», «без повторов» | пока окно **сломано** | после цикла: `max(best, right-left+1)` |
| B. Самое **короткое**, набравшее цель | «сумма ≥ `target`», «содержит все буквы `t`» | пока цель **набрана** | внутри цикла, до сдвига: `min(best, right-left+1)` |

В семье B ответ после цикла брать поздно: окно там уже не набирает цель. Длина окна в обеих —
`right - left + 1`: обе границы входят в окно.

## 📖 Разбор

**Скользящее окно** — кусок подряд, который едет по массиву или строке; длина постоянная или
меняется под условие. Главное — **не пересчитывать, а поправлять**: переходя к следующему окну, добавляем
один новый элемент и убираем один старый, а не считаем окно заново. Это снижает сложность с
O(n·k) (пересчёт каждого окна) до **O(n)**.

### Фиксированное окно

Размер `k` постоянен. Считаем сумму первого окна, затем двигаем границу, добавляя
`arr[i]` и вычитая `arr[i-k]`.

```go
func maxSumSubarray(arr []int, k int) int {
    if k <= 0 || k > len(arr) {
        return 0
    }
    windowSum := 0
    for i := 0; i < k; i++ {
        windowSum += arr[i]
    }
    maxSum := windowSum
    for i := k; i < len(arr); i++ {
        windowSum += arr[i] - arr[i-k] // +новый, −старый за O(1)
        if windowSum > maxSum {
            maxSum = windowSum
        }
    }
    return maxSum
}
```

### Переменное окно

Размер меняется под условие. Листинг — семья A из [таблицы в «⚡»](#-шаблон-для-собеседования):
сжимаем, пока окно сломано, ответ берём после. Семья B в коде — в «📝» ниже. Состояние окна
(счётчики, частоты) держим в `map` или переменной.

```go
// Самая длинная подстрока, где не более k различных символов
func longestKDistinct(s string, k int) int {
    freq := make(map[byte]int)
    left, maxLen := 0, 0
    for right := 0; right < len(s); right++ {
        freq[s[right]]++
        for len(freq) > k { // условие нарушено — сжимаем слева
            freq[s[left]]--
            if freq[s[left]] == 0 {
                delete(freq, s[left])
            }
            left++
        }
        if cur := right - left + 1; cur > maxLen {
            maxLen = cur
        }
    }
    return maxLen
}
```

Порядок шагов в семье A: **расширить** (`right++`) → **проверить условие** →
**сжать** при необходимости (`left++`) → **обновить результат**.

Что значит «окно сломано» в задачах практики — меняется только условие внутреннего цикла:

- **без повторов** (`LongestSubstringNoRepeat`) — какая-то буква встретилась в окне дважды;
- **нулей ≤ `k`** (Max Consecutive Ones III, 1004) — нулей в окне больше `k`;
- **заменить не больше `k` букв** (Longest Repeating Character Replacement, 424) — длина окна
  минус частота самой частой буквы в нём больше `k`: столько букв пришлось бы заменить. Частоту
  пересчитывай по массиву `[26]int` на каждой проверке — это 26 сравнений, всё ещё O(n);
- **окно постоянной длины** (Permutation in String, 567; Contains Duplicate II, 219) — сжимать
  нечего: каждый шаг впускает один элемент и выпускает тот, что стоял `k` позиций назад (в 567
  `k = len(p)`, в 219 — `k` из условия), как в `maxSumSubarray`. В окне держишь счётчик букв (567) или множество чисел (219).

Оба типа окна — O(n) по времени; память — O(1) у фиксированного окна с суммой и O(числа разных
значений в окне) у окна со счётчиком `freq` — не больше k + 1 или σ, размера алфавита.

## 🧠 Почему это корректно

<div class="algo-explain" data-key="sliding-window">
  <div class="algo-explain__item">
    <div class="algo-explain__q">Когда скользящее окно вообще применимо? Сформулируй предусловие — не «когда подходит», а что обязано быть верно.</div>
    <div class="algo-explain__ref">Левой границе <b>никогда не нужно возвращаться назад</b>: условие «окно подходит» меняется предсказуемо — в задачах «самое длинное при ограничении» сужение не портит подходящее окно, в задачах «самое короткое, набравшее цель» его не портит расширение (так и говорят: условие — предикат — монотонно). Сумма с отрицательными числами не обещает ни того, ни другого, и окно даёт <b>неверный ответ</b>, а не просто медленный.</div>
  </div>
  <div class="algo-explain__item">
    <div class="algo-explain__q">Что именно верно после обработки каждого <code>right</code>? Назови инвариант цикла.</div>
    <div class="algo-explain__ref">В задачах «самое длинное» отрезок <code>[left, right]</code> — самое длинное подходящее окно, которое кончается в <code>right</code>: внутренний цикл сдвигает <code>left</code> до первого места, где окно снова подходит, а назад его двигать незачем — то, что не подходило при меньшем <code>right</code>, не подойдёт и сейчас. Любое подходящее окно где-то кончается, поэтому максимум по всем <code>right</code> не пропускает ни одного кандидата.</div>
  </div>
  <div class="algo-explain__item">
    <div class="algo-explain__q">Почему это <code>O(n)</code>, хотя внутри цикла есть ещё один цикл?</div>

Два вопроса, которые отделяют «работает на моих тестах» от «я знаю, что это
правильно»: **почему сжатие слева не пропускает ответ** и
**почему вложенный `while` не делает алгоритм квадратичным**.

### Предусловие применимости — главное

Окно работает, если при сдвиге правой границы левой **никогда не нужно возвращаться
назад**. Так бывает, когда условие «окно подходит» меняется предсказуемо: в задачах «самое
длинное окно при ограничении» сужение не портит подходящее окно, а в задачах «самое короткое
окно, набравшее цель» его не портит расширение. Где ломается: сумма при отрицательных
числах — там не гарантировано ни то, ни другое.

Почему из этого следует, что `left` не возвращается. В семье A: если `[left, right]` сломано, то
и более длинное `[left, right+1]` сломано — начинать снова с этого `left` бесполезно. В семье B:
если `[left, right]` набрало цель, то и `[left, right+1]` наберёт, но оно длиннее — короче от
этого `left` уже не найти. Теперь — что бывает, когда ни одно из двух свойств не выполнено.

Возьми `[3, −2, 5]`, `target = 4` и код `minSubArrayLen` из «📝». Окно набирает `3`, потом
`3 − 2 = 1`, потом `1 + 5 = 6` — цель набрана на всех трёх числах, записываем длину 3.
Выпускаем тройку: `6 − 3 = 3`, цель потеряна, сжатие кончилось. Ответ окна — 3, а настоящий
ответ — 1: кусок `[5]`. Окно `[−2, 5]` цель не набирает, хотя более короткое `[5]` за ним —
набирает: отрицательное число сделало короткий кусок тяжелее длинного, и окно прошло мимо.

Если с отрицательными числами спрашивают «сумма **ровно** `k`» (например, сколько таких
кусков) — это решают [префиксные суммы с хеш-таблицей](prefix-sums.md). Для «≥ target» с
отрицательными хеш-таблица не помогает — она ищет только равенство; там нужны префиксные
суммы с [монотонным деком](#maxslidingwindow-и-дек-почему-всё-ещё-on); задача есть в списке [главы о деке](deque-structure.md) (LeetCode 862),
разбора в книге нет.

Прежде чем писать окно — определи семью задачи и проверь «её» свойство. Если ни то, ни
другое не выполнено — окно даст неверный ответ, а не просто медленный.

### Инвариант цикла

**В семье A после обработки очередного `right` отрезок `[left, right]` — самое длинное
подходящее окно, заканчивающееся в `right`.** Почему он сохраняется:

1. расширили вправо (`right++`) — возможно, сломали окно;
2. внутренний `while` двигает `left` вперёд ровно до первого места, где окно снова
   подходит;
3. указатель `left` **никогда не нужно возвращать назад**: то, что не подходило при
   меньшем `right`, при большем не подойдёт тем более.

Итоговый ответ — максимум по всем `right` из этих «лучших окон, заканчивающихся в
`right`». Любое подходящее окно где-то заканчивается, поэтому, перебрав все правые
концы, мы **не пропускаем ни одного кандидата**.

Для семьи B инвариант зеркален: внутренний `while` сжимает окно, *пока цель набрана*,
и по его выходе `[left, right]` уже цель **не набирает**, а самое короткое
набравшее окно, заканчивающееся в `right`, уже записано в ответ на последней
итерации сжатия. Рассуждение о полноте перебора то же самое.

### Почему линейно, хотя цикл вложенный

Вложенный `while` пугает — выглядит как O(n²). Но `left` **только растёт** и никогда
не сбрасывается: за весь прогон он сделает не более `n` шагов суммарно. `right` —
тоже `n`. Итого ≤ 2n операций с указателями, **амортизированно O(n)**. Стоимость
внутреннего цикла «размазана» по итерациям внешнего — это тот же амортизационный
аргумент, что и у дека в `MaxSlidingWindow` ниже. (Что такое амортизированная оценка
строго и почему это не «средний случай» — в главе
[Big-O и амортизированный анализ](big-o.md#3-амортизированный-анализ-рост-среза).)

## ⚙️ Цена на практике

`O(n)` скрывает константу — а инженер за неё платит тактами и аллокациями.

### `map[byte]int` против `[256]int`

Для счётчика символов в окне напрашивается `map`, но для байтового алфавита почти
всегда лучше массив фиксированного размера:

```go
var freq [256]int   // на стеке, без аллокаций в куче, без хеширования
```

- `map` — это аллокация в куче, хеш на каждом доступе, погоня за указателями и
  нагрузка на GC;
- `[256]int` живёт одним блоком, доступ — одно обращение по индексу, отлично ложится
  в кэш процессора.

Big-O один и тот же — `O(n)`, но на горячем пути — в коде, который выполняется чаще всего, — разница в разы. `map` оправдан лишь
когда алфавит большой или разреженный (Unicode-руны, произвольные ключи).

**Замер:** на одной и той же строке в 128 КБ версия на `map` работает **14.7 мс**, на
`[256]int` — **1.8 мс**. Восьмикратная разница при одинаковом Big-O, и больше трети времени
`map`-версии уходит только на хеширование байтов.

### `O(n)` не всегда быстрее `O(n log n)`

Big-O сравнивает рост, а не время: [замер выше](#mapbyteint-против-256int) развёл два
одинаковых `O(n)` в восемь раз. Если у решения за `O(n log n)` на массиве та же константа, что у
окна на `[256]int`, его время — примерно `n · log₂ n` против `8 · n` у окна на `map`: пока
`log₂ n < 8`, то есть `n < 256`, оно быстрее. Меряй (`testing.B`, `pprof`), а не угадывай.

### `MaxSlidingWindow` и дек: почему всё ещё `O(n)`

Максимум каждого окна длины `k` наивно стоит `O(n·k)`; монотонный дек (очередь с двумя
концами) даёт `O(n)` — это новый приём, его разбор свёрнут ниже.

<details class="algo-details">
<summary>⚙️ Второй проход: максимум окна и дек — вернись после главы о монотонном стеке</summary>

**Идея.** Держи в деке индексы тех, кто ещё может стать максимумом окна, — их значения
убывают от головы к хвосту. Новый элемент сзади **выкидывает всех меньших**: они старше и
меньше него, максимумом им уже не стать. Спереди уходит индекс, выехавший за окно. Максимум
окна всегда в голове. Каждый индекс кладётся один раз и снимается не больше одного раза —
снова амортизация, как с `left` выше.

Листай «›» и следи за лентой дека под массивом: на шаге с `6` из дека уходят и `3`, и `5` —
шестёрка новее и больше обеих:

<div class="algo-viz" data-viz="monotonic-deque" data-array="1,3,-1,-3,5,3,6,7" data-k="3"></div>

```go
func maxSlidingWindow(nums []int, k int) []int {
    res := []int{}
    deque := []int{} // индексы, значения убывают
    for i, v := range nums {
        if len(deque) > 0 && deque[0] == i-k {
            deque = deque[1:] // спереди: вышел из окна
        }
        for len(deque) > 0 && nums[deque[len(deque)-1]] < v {
            deque = deque[:len(deque)-1] // сзади: меньшие не нужны
        }
        deque = append(deque, i)
        if i >= k-1 {
            res = append(res, nums[deque[0]]) // максимум — в голове
        }
    }
    return res
}
```

Снятие с головы `deque = deque[1:]` безвозвратно съедает ёмкость среза, и `append` в хвост
со временем всё равно перевыделит массив; на горячем пути держи индекс головы (`head++`).

</details>

### Байты против рун

`len(s)` и `s[i]` работают с **байтами**, не символами. Для ASCII-задач это именно
то, что нужно, и это быстро. Для Unicode (`"café"`) итерируйся по `[]rune(s)` или
через `range` — иначе окно «режет» многобайтовый символ пополам. Большинство задач на
LeetCode — ASCII, но на этом регулярно спотыкаются.

## ⚠️ Типичные ошибки

1. **Пересчёт всей суммы окна заново** в цикле — это возвращает O(n·k). Поправляй
   сумму на один элемент: для фиксированного окна `windowSum += arr[i] - arr[i-k]` (добавили
   новый, вычли ушедший k позиций назад).
2. **Ошибка на единицу (off-by-one) в размере окна** — длина окна это `right - left + 1`, а не `right - left`.
3. **Ответ берут не там** — в семье A его обновляют после цикла сжатия, когда окно снова
   годится; в семье B — внутри цикла, до сдвига `left`: после цикла окно уже не набирает цель.
4. **Неверный момент пометки в `map`** — увеличивай/уменьшай частоты строго при
   входе элемента в окно и выходе из него, иначе `freq` перестанет совпадать с буквами между
   `left` и `right`, и проверка окна начнёт врать.
5. **Не обработаны границы** — пустой массив, `k > len(arr)`, `k = 0`.

> 🌍 **Где это в настоящем коде**
>
> - [`IndexRabinKarp`](https://github.com/golang/go/blob/go1.24.0/src/internal/bytealg/bytealg.go#L66) (Go 1.24) — окно постоянной длины в поиске подстроки: при сдвиге хеш окна обновляется добавлением нового байта и вычитанием ушедшего `s[i-n]`, а не считается заново. На него [переходит `strings.Index`](https://github.com/golang/go/blob/go1.24.0/src/internal/stringslite/strings.go#L98), когда простой поиск слишком часто ошибается.

## 📝 Разбор задачи

Перебор и наблюдение — в [«🧭 Откуда берётся окно»](#-откуда-берётся-окно-выведем-его-сами):
сумму не выбрасывают, а правят на один элемент, и оба края идут только вперёд. Здесь — код и
трасса той же задачи; это семья B из [таблицы в «⚡»](#-шаблон-для-собеседования).

> **Задача.** Дан массив **положительных** целых `nums` и число `target`. Найти длину
> **минимального** непрерывного подмассива, сумма которого `≥ target`. Если такого нет — `0`.
> Пример: `nums = [2,3,1,2,4,3]`, `target = 7` → ответ `2` (подмассив `[4,3]`).

Перебор из «🧭» на полном входе — для каждого нового `i` сумма начинается с нуля, и метрика
«сложений» к концу доходит до 17 на шесть чисел:

<div class="algo-viz" data-viz="min-subarray-naive" data-array="2,3,1,2,4,3" data-target="7"></div>

**Код: переменное окно — O(n).** Числа положительные, поэтому [контрпример с
отрицательным числом](#предусловие-применимости--главное) здесь не грозит.

```go
func minSubArrayLen(target int, nums []int) int {
    left, sum := 0, 0
    best := len(nums) + 1
    for right := 0; right < len(nums); right++ {
        sum += nums[right]            // расширяем окно вправо
        for sum >= target {           // пока валидно — сжимаем слева до упора
            if right-left+1 < best {
                best = right - left + 1
            }
            sum -= nums[left]
            left++
        }
    }
    if best == len(nums)+1 {
        return 0
    }
    return best
}
```

Сравни с наивным виджетом выше на тех же данных: `left` идёт только вперёд и
**ни разу не возвращается назад**, поэтому вместо вложенного перебора получаем один
проход. Рамка вокруг клеток — то же окно `[left..right]`, что и в трассировке ниже. Её ярлык —
`sum` (после вычитания — как она получилась) и сравнение с `target`, зелёный пунктир — лучшее
окно `best`. Метрика
«сложений» здесь заканчивается на 6 против 17 у перебора: каждый элемент прибавляется ровно
один раз (и не больше одного раза вычитается, когда `left` его обгоняет):

<div class="algo-viz" data-viz="min-subarray-window" data-array="2,3,1,2,4,3" data-target="7"></div>

**Трассировка** на `nums = [2,3,1,2,4,3]`, `target = 7`:

| `right` | добавили | `sum` до сжатия | сжатие слева (`left`→) | окно после | `best` |
|---------|----------|-----------------|------------------------|------------|--------|
| 0       | 2        | 2               | —                      | `[2]`      | ∞      |
| 1       | 3        | 5               | —                      | `[2,3]`    | ∞      |
| 2       | 1        | 6               | —                      | `[2,3,1]`  | ∞      |
| 3       | 2        | 8 ≥ 7           | убрали 2 → sum=6, `left=1` | `[3,1,2]` | **4** |
| 4       | 4        | 10 ≥ 7          | убрали 3 → sum=7, ещё убрали 1 → sum=6, `left=3` | `[2,4]` | **3** |
| 5       | 3        | 9 ≥ 7           | убрали 2 → sum=7, ещё убрали 4 → sum=3, `left=5` | `[3]` | **2** |

Ответ — `2`. Обрати внимание: `left` прошёл `0→5` — 5 шагов, `right` — 6, итого 11 ≤ 2n = 12
операций. Тот самый [амортизированный O(n)](#почему-линейно-хотя-цикл-вложенный),
хотя цикл и вложенный.

окно экономит немного. Запусти обе версии на тысячах чисел: перебор от каждого `i` заново

### 💻 А теперь — построй его (и то, что реально в проде)

Распознать мало — инженер доводит до работающего кода. В тренажёре ты строишь **два** лимитера и сравниваешь:
сначала паттерн из этой главы, затем то, что реально крутится в бэкендах. Сигнатуры намеренно чистые (только
ядро, без HTTP), а время подаётся снаружи (`nowMs`) — чтобы поведение было детерминированным и проверяемым.

**Шаг 1. Sliding window log — паттерн главы.** Скользящее окно меток времени по клиенту:

```go
func NewRateLimiter(limit int, windowMs int64) *RateLimiter
// true — запрос пропущен (учтён в окне), false — отклонён (лимит исчерпан)
func (r *RateLimiter) Allow(clientID string, nowMs int64) bool
// через сколько мс освободится слот: 0 — можно сейчас, −1 — никогда (заголовок Retry-After)
func (r *RateLimiter) RetryAfter(clientID string, nowMs int64) int64
```

`Allow` — ровно то самое переменное окно: выкинь метки старше `nowMs − windowMs`, если осталось меньше
`limit` — пропусти (записав `nowMs`), иначе откажи. `RetryAfter` — уже инженерная деталь: боевой API не
просто отвечает «429 Too Many Requests», а говорит клиенту, **когда** повторить (HTTP-заголовок
`Retry-After`); значит, надо посчитать, когда из окна выйдет метка, освобождающая слот.

#### ⚙️ Чем это платит в проде (и что берут вместо)

Sliding window log **точен**, но хранит метку **каждого** запроса: память `O(запросов в окне)` на клиента.
На больших RPS (запросов в секунду) это дорого, поэтому в реальных системах чаще берут:

- **Token bucket** — индустриальный стандарт. Копит «токены» с постоянной скоростью, запрос тратит токен;
  **терпит короткие всплески** и стоит `O(1)` памяти (два числа: запас токенов и время последнего
  пополнения). Именно это — стандартный лимитер Go [`golang.org/x/time/rate`](https://pkg.go.dev/golang.org/x/time/rate)
  (`rate.Limiter` — ведро токенов, изначально полное, пополняется `r` токенами в секунду).
- **Sliding window counter** — приближение: два счётчика, за прошлую и текущую календарную минуту; прошлую берут с той долей, на которую её ещё накрывают последние 60 секунд. Так
  устроен лимитер **Cloudflare**: почти точность лога при `O(1)` памяти. Лучший баланс точность/ресурсы.
- **Fixed window** — просто счётчик на окно; прост, но страдает «граничным всплеском» (до 2× лимита на стыке
  окон).
- **Распределённо** (лимитер на многих инстансах) состояние выносят в **Redis**, а атомарность
  «прочитать-проверить-записать» гарантируют **Lua-скриптом** — иначе гонка (так делают, например,
  [`mennanov/limiters`](https://github.com/mennanov/limiters)). В проде учитывают ещё сбои Redis и рассинхрон
  часов между узлами.

> ⚠️ **Прод-ловушка: память лимитера течёт по клиентам.** Окно чистит *метки*, но если не удалять
> из map **ключ клиента**, у которого меток не осталось, карта растёт с числом *когда-либо
> виденных* клиентов, а не активных. При миллионах уникальных clientID (например, по IP) это
> классическая утечка: сервис живёт неделями и «толстеет». Локально — `delete(hits, id)` при
> опустевшем окне; в Redis эту же роль играет **TTL ключа**. Проверь себя в тренажёре: удаляешь ли ты
> пустые ключи?

**Шаг 2. Token bucket — построй сам.** В том же пакете реализуй боевой вариант — модель `x/time/rate`:

```go
func NewTokenBucket(capacity int, refillPerSec float64) *TokenBucket // изначально полное
func (b *TokenBucket) Allow(nowMs int64) bool // пополни на прошедшее время, потрать токен
```

**Шаг 3. Сделай его потокобезопасным.** В проде лимитер дёргают **несколько горутин
одновременно** (каждый HTTP-запрос — своя горутина), а `TokenBucket.Allow` — это классический
**check-then-act**: прочитал `tokens`, решил, записал. Две горутины без синхронизации читают
одно и то же значение — и обе пропускают запрос по последнему токену (*lost update*), а детектор
гонок кричит про запись наперегонки. Реализуй обёртку:

```go
func NewSafeTokenBucket(capacity int, refillPerSec float64) *SafeTokenBucket
func (b *SafeTokenBucket) Allow(nowMs int64) bool // то же, но безопасно из многих горутин
```

Тест запускает 8 горутин по 50 запросов на ведро ёмкости 100 без пополнения — пройти обязаны
**ровно 100**. Без мьютекса тест ловит и гонку (`-race` — виджет ниже гоняет с ним), и «лишние»
пропуски. Ровно так устроен настоящий `x/time/rate.Limiter` — `sync.Mutex` вокруг всей операции.

**Не спутай с соседом** (вся таблица — в [руководстве по выбору](pattern-selection-guide.md#путаемые-пары-что-обязано-быть-верно)):

- если числа неотрицательны, расширение куска не уменьшает сумму, а нужен один самый короткий или длинный кусок подряд с порогом суммы — Скользящее окно, а не [Префиксные суммы](prefix-sums.md): окно даёт ответ за один проход без лишней памяти, а префиксы хранят n сумм.
- если в массиве есть отрицательные числа, а спрашивают, сколько кусков подряд дают сумму ровно k — [Префиксные суммы](prefix-sums.md), а не Скользящее окно: отрицательное число ломает правило «расширил — сумма выросла», и окно сдвинет левый край мимо ответа.
- если нужен кусок подряд в исходном порядке, а не пара элементов — Скользящее окно, а не [Два указателя](two-pointers.md): встречные указатели ищут пару в отсортированном массиве, а сортировка перемешает куски подряд.

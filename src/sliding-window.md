## ⚡ Шаблон для собеседования

Универсальный каркас **переменного** окна — его и стоит помнить:

```go
left := 0
for right := 0; right < len(s); right++ {
    add(s[right])                  // 1. расширяем окно вправо

    for windowInvalid() {          // 2. пока условие нарушено —
        remove(s[left])            //    сжимаем слева
        left++
    }

    best = max(best, right-left+1) // 3. обновляем ответ
}
```

1. `right` добавляет новый элемент в окно;
2. пока окно «невалидно» — двигаем `left` и убираем элементы;
3. после восстановления условия обновляем ответ (`right - left + 1`).

## 📖 Разбор

<details class="algo-details">
<summary>Теория, два типа окон и сложность</summary>

**Скользящее окно** — техника для операций над подмассивами или подстроками
**фиксированного** или **переменного** размера в линейной структуре (массив, строка).

Ключевая идея — **инкрементальное обновление**: переходя к следующему окну, мы
добавляем один новый элемент и убираем один старый, вместо полного пересчёта. Это
снижает сложность с O(n·k) (наивный пересчёт каждого окна) до **O(n)**.

#### Фиксированное окно

Размер `k` постоянен. Считаем сумму первого окна, затем двигаем границу, добавляя
`arr[i]` и вычитая `arr[i-k]`.

```go
func maxSumSubarray(arr []int, k int) int {
    if k <= 0 || k > len(arr) {
        return 0
    }
    windowSum := 0
    for i := 0; i < k; i++ {
        windowSum += arr[i]
    }
    maxSum := windowSum
    for i := k; i < len(arr); i++ {
        windowSum += arr[i] - arr[i-k] // +новый, −старый за O(1)
        if windowSum > maxSum {
            maxSum = windowSum
        }
    }
    return maxSum
}
```

#### Переменное окно

Размер меняется под условие: расширяем окно правой границей `right`, а при нарушении
условия сжимаем слева `left`. Состояние окна (счётчики, частоты) держим в `map` или
переменной.

```go
// Самая длинная подстрока, где не более k различных символов
func longestKDistinct(s string, k int) int {
    freq := make(map[byte]int)
    left, maxLen := 0, 0
    for right := 0; right < len(s); right++ {
        freq[s[right]]++
        for len(freq) > k { // условие нарушено — сжимаем слева
            freq[s[left]]--
            if freq[s[left]] == 0 {
                delete(freq, s[left])
            }
            left++
        }
        if cur := right - left + 1; cur > maxLen {
            maxLen = cur
        }
    }
    return maxLen
}
```

Порядок шагов для переменного окна: **расширить** (`right++`) → **проверить условие** →
**сжать** при необходимости (`left++`) → **обновить результат**.

#### Сложность

| Тип окна            | Время | Память                          |
|---------------------|-------|----------------------------------|
| Фиксированное       | O(n)  | O(1)                             |
| Переменное          | O(n)  | O(k) или O(σ) (σ — размер алфавита) |

Переменное окно линейно, потому что каждый элемент добавляется и удаляется не более
одного раза (и `left`, и `right` проходят массив всего по разу).

</details>

## 🧠 Почему это корректно

Два вопроса, которые отделяют «работает на моих тестах» от «я знаю, что это
правильно»: **почему сжатие слева только при нарушении не пропускает ответ** и
**почему вложенный `while` не делает алгоритм квадратичным**.

### Предусловие применимости — главное

Скользящее окно корректно **тогда и только тогда**, когда оптимальная левая граница
монотонна: при росте `right` нужный `left` **никогда не убывает**. Эта монотонность
берётся из монотонности самого предиката «окно валидно» — причём задач на окно две
симметричные семьи, и предикат в них монотонен **в разные стороны**.

**Семья 1 — «самое длинное окно при ограничении»** (например, «не более `k`
различных символов»). От предиката требуется:

> Если окно `[left, right]` валидно, то любое более узкое `[left', right]` с
> `left' ≥ left` тоже валидно.

Валидность **сохраняется при сужении**: убрали символ — различных не стало больше.
Тогда для каждого `right` валидные `left` образуют **суффикс** `[L(right), right]`,
внутренний `while` сжимает окно, *пока оно невалидно*, и ответ — максимум длины.

**Семья 2 — «самое короткое окно при пороге»** (например, «сумма ≥ `target`» при
**неотрицательных** числах). Предикат зеркальный:

> Если окно `[left, right]` валидно, то любое более широкое `[left', right]` с
> `left' ≤ left` тоже валидно.

Валидность **сохраняется при расширении**: добавили элемент — сумма не уменьшилась.
А вот сужение её рано или поздно разрушает, поэтому валидные `left` образуют
**префикс** `[0, L(right)]`. Шаблон зеркален: внутренний `while` сжимает окно,
*пока оно валидно*, фиксируя ответ на каждом шаге, и ответ — минимум длины. Именно
так работает `minSubArrayLen` в разборе ниже: `for sum >= target { ...; left++ }`.

В обеих семьях монотонность предиката в свою сторону даёт одно и то же следствие:
граница `L(right)` не убывает с ростом `right`, и `left` никогда не приходится
возвращать назад.

- **Ломается:** «сумма ≥ target» при наличии **отрицательных** чисел — добавление
  элемента может *уменьшить* сумму, а удаление — *увеличить*: предикат не монотонен
  ни в одну сторону, `L(right)` скачет, и окно неприменимо. Нужен префиксный массив +
  другая техника. Это и есть строгая формулировка пункта «окно нельзя пересчитать
  инкрементально» из карточки «когда НЕ применять».

Прежде чем писать окно — определи семью задачи и проверь «её» свойство: сохраняется
ли валидность при сужении (семья 1) или при расширении (семья 2). Если ни то, ни
другое — окно даст неверный ответ, а не просто медленный.

### Инвариант цикла

**После обработки очередного `right` отрезок `[left, right]` — самое длинное валидное
окно, заканчивающееся в `right`.** Почему он сохраняется:

1. расширили вправо (`right++`) — возможно, нарушили условие;
2. внутренний `while` двигает `left` вперёд ровно до `L(right)` — первой валидной
   позиции;
3. благодаря монотонности `L` указатель `left` **никогда не нужно возвращать назад**:
   то, что было невалидно при меньшем `right`, тем более невалидно сейчас.

Итоговый ответ — максимум по всем `right` из этих «лучших окон, заканчивающихся в
`right`». Любое валидное окно где-то заканчивается, поэтому, перебрав все правые
концы, мы **не пропускаем ни одного кандидата**.

Для семьи 2 инвариант зеркален: внутренний `while` сжимает окно, *пока оно валидно*,
и по его выходе `[left, right]` — первое **невалидное** окно, а самое короткое
валидное окно, заканчивающееся в `right`, уже зафиксировано в ответе на последней
итерации сжатия. Рассуждение о полноте перебора то же самое.

### Почему линейно, хотя цикл вложенный

Вложенный `while` пугает — выглядит как O(n²). Но `left` **только растёт** и никогда
не сбрасывается: за весь прогон он сделает не более `n` шагов суммарно. `right` —
тоже `n`. Итого ≤ 2n операций с указателями, **амортизированно O(n)**. Стоимость
внутреннего цикла «размазана» по итерациям внешнего — это тот же амортизационный
аргумент, что и у дека в `MaxSlidingWindow` ниже. (Что такое амортизированная оценка
строго и почему это не «средний случай» — в главе
[Big-O и амортизированный анализ](big-o.md#3-амортизированный-анализ-рост-среза).)

## ⚙️ Цена на практике

`O(n)` скрывает константу — а инженер за неё платит тактами и аллокациями.

### `map[byte]int` против `[256]int`

Для счётчика символов в окне напрашивается `map`, но для байтового алфавита почти
всегда лучше массив фиксированного размера:

```go
var freq [256]int   // на стеке, без аллокаций в куче, без хеширования
```

- `map` — это аллокация в куче, хеш на каждом доступе, погоня за указателями и
  нагрузка на GC;
- `[256]int` живёт одним блоком, доступ — одно обращение по индексу, отлично ложится
  в кэш процессора.

Big-O один и тот же — `O(n)`, но на горячем пути разница в разы. `map` оправдан лишь
когда алфавит большой или разреженный (Unicode-руны, произвольные ключи).

**Не верь на слово — вот замер.** В тренажёре лежит готовый бенчмарк
(`exercises/slidingwindow/mapvsarray_bench_test.go`): обе версии `longestKDistinct`
на одной и той же строке в 128 КБ. Запусти сам:

```bash
cd exercises
go test -bench=KDistinct -benchmem ./slidingwindow/
```

Вот честный вывод с обычной машины (i5-12400, Go 1.24; у тебя цифры будут свои,
но соотношение — похожее):

```text
BenchmarkKDistinct_Map-12       159    14 723 315 ns/op    0 B/op    0 allocs/op
BenchmarkKDistinct_Array-12    1273     1 830 160 ns/op    0 B/op    0 allocs/op
```

Читаем: одна и та же `O(n)`-задача на `map` — **14.7 мс**, на `[256]int` — **1.8 мс**.
**Восьмикратная** разница при одинаковом Big-O — вот сколько стоят хеширование и
погоня за указателями на горячем пути.

Кстати, обрати внимание на `0 B/op` у map-версии: escape-анализ доказал, что
маленький map (здесь не больше 8 ключей) не переживает вызов функции, и разместил
его **на стеке** — кучной аллокации нет вовсе. Восьмикратная цена набежала не из-за
аллокаций, а из-за хеширования на каждом доступе. Урок двойной: компилятор умеет
убирать аллокации (см. [приложение про escape-анализ](appendix-go-memory.md)), но
хеш-функцию за тебя никто не отменит.

Расшифровка — и это самое ценное: **39% всего времени — `aeshashbody`**, то есть

### `O(n)` не всегда быстрее `O(n log n)`

Окно за `O(n)` с `map` способно проиграть решению за `O(n log n)` на массиве — из-за
константного фактора и промахов кэша, особенно на небольших `n` (выше ты видел, что
константа бывает ×8). «Асимптотически лучше» ≠ «быстрее на твоих данных». Меряй
(`testing.B`, `pprof`), а не угадывай — это привычка инженера, а не кодера.

### `MaxSlidingWindow` и дек: почему всё ещё `O(n)`

Наивный максимум окна — `O(n·k)`. Монотонный дек индексов даёт `O(n)`, потому что
**каждый индекс кладётся и вынимается ровно один раз** — снова амортизация, как с
`left` выше. В Go дек удобно держать срезом `[]int` (хранят **индексы**, не значения):
добавляем в конец, снимаем с обоих концов. Нюанс аллокаций: снятие с головы через
`deque = deque[1:]` сдвигает начало среза и **безвозвратно съедает ёмкость** — со
временем `append` в хвост всё равно перевыделит массив, так что `make([]int, 0, k)`
здесь не спасает. Для собеседования срез — норма (код короче), а на горячем пути
держи явный индекс головы (`head++` вместо реслайса) или кольцевой буфер — тогда
хватит одной аллокации на весь прогон.

```go
func maxSlidingWindow(nums []int, k int) []int {
    res := []int{}
    deque := []int{} // индексы, значения убывают
    for i, v := range nums {
        if len(deque) > 0 && deque[0] == i-k {
            deque = deque[1:] // спереди: вышел из окна
        }
        for len(deque) > 0 && nums[deque[len(deque)-1]] < v {
            deque = deque[:len(deque)-1] // сзади: меньшие не нужны
        }
        deque = append(deque, i)
        if i >= k-1 {
            res = append(res, nums[deque[0]]) // максимум — в голове
        }
    }
    return res
}
```

Нажми ▶ и следи за лентой дека под массивом: спереди выбывает индекс, уехавший за
окно, а сзади новый элемент **выкидывает всех меньших** (зачем хранить 3, если пришёл
5 — оно уже никогда не станет максимумом). Максимум окна всегда в голове, ответ
снимается за O(1):

### Байты против рун

`len(s)` и `s[i]` работают с **байтами**, не символами. Для ASCII-задач это именно
то, что нужно, и это быстро. Для Unicode (`"café"`) итерируйся по `[]rune(s)` или
через `range` — иначе окно «режет» многобайтовый символ пополам. Большинство задач на
LeetCode — ASCII, но на этом регулярно спотыкаются.

## ⚠️ Типичные ошибки

1. **Пересчёт всей суммы окна заново** в цикле — это возвращает O(n·k). Обновляйте
   инкрементально: для фиксированного окна `windowSum += arr[i] - arr[i-k]` (добавили
   новый, вычли ушедший k позиций назад).
2. **Off-by-one в размере окна** — длина окна это `right - left + 1`, а не `right - left`.
3. **Забыли обновить результат после сжатия** переменного окна — обновляйте `maxLen`
   после того, как условие снова выполнено.
4. **Неверный момент пометки в `map`** — увеличивайте/уменьшайте частоты строго при
   входе элемента в окно и выходе из него, иначе состояние «съезжает».
5. **Не обработаны границы** — пустой массив, `k > len(arr)`, `k = 0`.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он медленный, и
только потом окно.

> **Задача.** Дан массив **положительных** целых `nums` и число `target`. Найти длину
> **минимального** непрерывного подмассива, сумма которого `≥ target`. Если такого нет — `0`.
> Пример: `nums = [2,3,1,2,4,3]`, `target = 7` → ответ `2` (подмассив `[4,3]`).

**Шаг 1. Наивно: перебрать все подмассивы — O(n²).**

```go
func minSubArrayNaive(target int, nums []int) int {
    best := len(nums) + 1
    for i := 0; i < len(nums); i++ {
        sum := 0
        for j := i; j < len(nums); j++ {
            sum += nums[j]            // сумма [i..j] накапливается
            if sum >= target {
                if j-i+1 < best {
                    best = j - i + 1
                }
                break                 // дальше только длиннее — выходим
            }
        }
    }
    if best == len(nums)+1 {
        return 0
    }
    return best
}
```

Это **работает и проходит тесты**, но делает O(n²) операций: для каждого левого конца
`i` мы заново идём вправо. Соседние левые концы пересчитывают почти один и тот же
суффикс суммы — вот эта повторная работа и есть то, что убирает окно.

Прогоните наивный перебор по шагам и проследите, как для каждого нового `i` сумма
обнуляется и скан стартует заново — `j` снова и снова проходит почти тот же суффикс:

<div class="algo-viz" data-viz="min-subarray-naive" data-array="2,3,1,2,4,3" data-target="7"></div>

**Шаг 2. Ключевое наблюдение.** Числа положительные ⇒ при росте правого конца сумма
**только растёт**, а при сдвиге левого — **только падает**. Значит, выполнено
[предусловие монотонности](#предусловие-применимости--главное): как только окно
стало валидным (`sum ≥ target`), его можно жадно сжимать слева, не боясь пропустить
ответ. Откатывать `left` назад никогда не придётся.

> ⚠️ Будь числа произвольными (с отрицательными), это рассуждение **рушится** —
> сжатие слева может *увеличить* сумму, и окно даст неверный ответ. Тогда нужен
> префиксный массив, см. «когда НЕ применять».

**Шаг 3. Оптимум: переменное окно — O(n).**

```go
func minSubArrayLen(target int, nums []int) int {
    left, sum := 0, 0
    best := len(nums) + 1
    for right := 0; right < len(nums); right++ {
        sum += nums[right]            // расширяем окно вправо
        for sum >= target {           // пока валидно — жадно сжимаем слева
            if right-left+1 < best {
                best = right - left + 1
            }
            sum -= nums[left]
            left++
        }
    }
    if best == len(nums)+1 {
        return 0
    }
    return best
}
```

Сравните с наивным виджетом выше на тех же данных: `left` идёт только вперёд и
**ни разу не возвращается назад**, поэтому вместо вложенного перебора получаем один
проход. Под массивом — то же окно `[left..right]`, что и в трассировке ниже:

**Шаг 4. Трассировка** на `nums = [2,3,1,2,4,3]`, `target = 7`:

| `right` | добавили | `sum` до сжатия | сжатие слева (`left`→) | окно после | `best` |
|---------|----------|-----------------|------------------------|------------|--------|
| 0       | 2        | 2               | —                      | `[2]`      | ∞      |
| 1       | 3        | 5               | —                      | `[2,3]`    | ∞      |
| 2       | 1        | 6               | —                      | `[2,3,1]`  | ∞      |
| 3       | 2        | 8 ≥ 7           | убрали 2 → sum=6, `left=1` | `[3,1,2]` | **4** |
| 4       | 4        | 10 ≥ 7          | убрали 3,1 → sum=6, `left=3` | `[2,4]` | **3** |
| 5       | 3        | 9 ≥ 7           | убрали 2 → sum=7, ещё убрали 4 → sum=3, `left=5` | `[3]` | **2** |

Ответ — `2`. Обрати внимание: `left` прошёл `0→5` суммарно за 5 шагов, `right` — тоже
за 6, итого ≤ 2n операций. Тот самый [амортизированный O(n)](#почему-линейно-хотя-цикл-вложенный),
хотя цикл и вложенный.

```go
// true — запрос пропущен (учтён в окне), false — отклонён (лимит исчерпан)
func (r *RateLimiter) Allow(clientID string, nowMs int64) bool
// через сколько мс освободится слот: 0 — можно сейчас, −1 — никогда (заголовок Retry-After)
func (r *RateLimiter) RetryAfter(clientID string, nowMs int64) int64
```

`Allow` — ровно то самое переменное окно: выкинь метки старше `nowMs − windowMs`, если осталось меньше
`limit` — пропусти (записав `nowMs`), иначе откажи. `RetryAfter` — уже инженерная деталь: боевой API не
просто отвечает «429 Too Many Requests», а говорит клиенту, **когда** повторить (HTTP-заголовок
`Retry-After`); значит, надо посчитать, когда из окна выйдет метка, освобождающая слот.

#### ⚙️ Чем это платит в проде (и что берут вместо)

Sliding window log **точен**, но хранит метку **каждого** запроса: память `O(запросов в окне)` на клиента.
На больших RPS это дорого, поэтому в реальных системах чаще берут:

- **Token bucket** — индустриальный стандарт. Копит «токены» с постоянной скоростью, запрос тратит токен;
  **терпит короткие всплески** и стоит `O(1)` памяти (два числа: запас токенов и время последнего
  пополнения). Именно это — стандартный лимитер Go [`golang.org/x/time/rate`](https://pkg.go.dev/golang.org/x/time/rate)
  (`rate.Limiter` — ведро токенов, изначально полное, пополняется `r` токенами в секунду).
- **Sliding window counter** — приближение (два счётчика соседних фиксированных окон + интерполяция). Так
  устроен лимитер **Cloudflare**: почти точность лога при `O(1)` памяти. Лучший баланс точность/ресурсы.
- **Fixed window** — просто счётчик на окно; прост, но страдает «граничным всплеском» (до 2× лимита на стыке
  окон).
- **Распределённо** (лимитер на многих инстансах) состояние выносят в **Redis**, а атомарность
  «прочитать-проверить-записать» гарантируют **Lua-скриптом** — иначе гонка (так делают, например,
  [`mennanov/limiters`](https://github.com/mennanov/limiters)). В проде учитывают ещё сбои Redis и рассинхрон
  часов между узлами.

> ⚠️ **Прод-ловушка: память лимитера течёт по клиентам.** Окно чистит *метки*, но если не удалять
> из map **ключ клиента**, у которого меток не осталось, карта растёт с числом *когда-либо
> виденных* клиентов, а не активных. При миллионах уникальных clientID (например, по IP) это
> классическая утечка: сервис живёт неделями и «толстеет». Локально — `delete(hits, id)` при
> опустевшем окне; в Redis эту же роль играет **TTL ключа**. Проверь себя в тренажёре: удаляешь ли ты
> пустые ключи?

**Шаг 2. Token bucket — построй сам.** В том же пакете реализуй боевой вариант — модель `x/time/rate`:

```go
func NewTokenBucket(capacity int, refillPerSec float64) *TokenBucket // изначально полное
func (b *TokenBucket) Allow(nowMs int64) bool // пополни на прошедшее время, потрать токен
```

**Шаг 3. Сделай его потокобезопасным.** В проде лимитер дёргают **несколько горутин
одновременно** (каждый HTTP-запрос — своя горутина), а `TokenBucket.Allow` — это классический
**check-then-act**: прочитал `tokens`, решил, записал. Две горутины без синхронизации читают
одно и то же значение — и обе пропускают запрос по последнему токену (*lost update*), а детектор
гонок кричит про запись наперегонки. Реализуй обёртку:

```go
func NewSafeTokenBucket(capacity int, refillPerSec float64) *SafeTokenBucket
func (b *SafeTokenBucket) Allow(nowMs int64) bool // то же, но безопасно из многих горутин
```

Тест запускает 8 горутин по 50 запросов на ведро ёмкости 100 без пополнения — пройти обязаны
**ровно 100**. Без мьютекса тест ловит и гонку (`-race` — виджет ниже гоняет с ним), и «лишние»
пропуски. Ровно так устроен настоящий `x/time/rate.Limiter` — `sync.Mutex` вокруг всей операции.

Подними runner (`cd exercises && go run ./cmd/runner`) и решай все три прямо здесь. Тесты гоняют всплеск,
скольжение окна, изоляцию клиентов, границы, `RetryAfter`, накопление токенов и конкурентный доступ

Мораль инженера: **точный лог хорош, чтобы понять механику; в проде обычно меняют немного точности на `O(1)`
памяти и терпимость к всплескам** (token bucket) — тот же размен «точность ↔ ресурсы», что и у [вероятностных
структур](probabilistic-structures.md). Построив оба, ты чувствуешь этот размен руками, а не на словах.

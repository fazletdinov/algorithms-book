## Зачем сортировать и что здесь главное

В работе ты почти никогда не пишешь сортировку сам — зовёшь `slices.Sort`. Но сортировка —
самый частый **первый шаг** решения. В упорядоченных данных одинаковые значения стоят рядом —
дубликаты и группы находятся за один проход. k-й по величине (его называют порядковой
статистикой) лежит по известному индексу. Пару с нужной суммой находят два указателя — два
индекса, идущие с концов навстречу. Пересекающиеся интервалы оказываются соседями. Заплатил
`O(n log n)` один раз — и задача «перебрать все пары» превращается в «пройти слева направо».

Сами алгоритмы стоит знать по другой причине: внутри них живут два приёма, которые потом
встречаются отдельно от сортировки.

- **Слияние** двух уже отсортированных кусков. Тот же ход — в слиянии интервалов, в слиянии K
  списков, во внешней сортировке файла, который не влез в память.
- **Разбиение** массива вокруг одного элемента. Тот же ход — в поиске k-го элемента без полной
  сортировки и в задаче о флаге из трёх цветов (разложить массив из 0, 1 и 2 по трём зонам).

Порядок главы: сортировка вставками — точка отсчёта за `O(n²)`; слияние и разбиение — два
способа получить `O(n log n)`; подсчёт — как обойтись без сравнений вовсе; быстрый выбор — что
делать, когда нужен один элемент, а не весь порядок. Сводная таблица — в конце, когда будет
что сравнивать.

## 1. Сортировка вставками: точка отсчёта

Простейший способ: держим **отсортированный префикс** слева и по одному «вставляем» в него
следующий элемент, сдвигая бо́льшие вправо.

```go
func insertionSort(a []int) {
    for i := 1; i < len(a); i++ {
        key := a[i]
        j := i - 1
        for j >= 0 && a[j] > key {
            a[j+1] = a[j] // сдвигаем больший элемент вправо
            j--
        }
        a[j+1] = key // вставляем key на освободившееся место
    }
}
```

Сдвигаем только строго бо́льшие (`a[j] > key`), поэтому равные не перепрыгивают друг через
друга — сортировка **устойчива**: равные элементы сохраняют исходный относительный порядок.

На входе виджета ниже, `[5, 2, 4, 1, 3, 6]`, первые три вставки такие. `key = 2`: пятёрка
сдвигается вправо, двойка встаёт на индекс 0 — `[2 5 4 1 3 6]`. `key = 4`: снова один сдвиг —
`[2 4 5 1 3 6]`. `key = 1`: три сдвига, единица проходит весь префикс — `[1 2 4 5 3 6]`.

Сдвигов при вставке ровно столько, сколько в префиксе элементов больше `key`. На массиве,
отсортированном наоборот, это `1 + 2 + … + (n−1)` — отсюда `O(n²)`. На почти отсортированном
сдвигов почти нет — отсюда `O(n)`, и поэтому встроенные сортировки добивают вставками мелкие
куски. Чтобы стать быстрее, надо перестать сравнивать каждый элемент почти со всем префиксом —
это и делают два следующих приёма.

В виджете `key` вынимается в отдельную клетку под массивом. Каждый сдвиг `a[j+1] = a[j]`
переносит «дыру» на шаг влево, поэтому в памяти на миг лежат две одинаковые пятёрки — и одна из
них погашена. Когда слева больше нет элементов больше `key`, он встаёт в дыру:

## 2. Сортировка слиянием: вся работа — на обратном пути

Начнём с задачи полегче: два куска **уже отсортированы**, собрать из них один. Наименьший
элемент результата — одна из двух голов (первых элементов кусков), больше ему негде быть. Значит, сравниваем головы,
выдаём меньшую и повторяем. Каждое сравнение выдаёт один элемент, поэтому на `n` элементов
уходит не больше `n − 1` сравнений: когда один кусок кончился, хвост другого переносится без
сравнений.

Откуда взять отсортированные куски? Разрезать массив пополам и отсортировать каждую половину
тем же способом — рекурсией, пока куски не станут из одного элемента: такой отсортирован сам по
себе. На `[5, 2, 4, 6, 1, 3]`:

```text
вниз — режем пополам:
[5 2 4 6 1 3]
[5 2 4]  [6 1 3]
[5]  [2 4]  [6]  [1 3]
[5]  [2] [4]  [6]  [1] [3]

вверх — сливаем:                 сравнений
[2]+[4] → [2 4], [1]+[3] → [1 3]          по 1
[5]+[2 4] → [2 4 5], [6]+[1 3] → [1 3 6]  по 2
[2 4 5]+[1 3 6] → [1 2 3 4 5 6]            5
```

Делим не глядя на значения — пополам; вся работа делается на обратном пути, при слиянии.
Каждый уровень слияний трогает не больше `n` элементов, уровней — `log₂ n` с округлением вверх
(здесь три), итого `O(n log n)` на **любом** входе, без худшего случая.

```go
func mergeSort(a []int) []int {
    if len(a) <= 1 {
        return a
    }
    mid := len(a) / 2
    left := mergeSort(a[:mid])
    right := mergeSort(a[mid:])
    return merge(left, right)
}

func merge(left, right []int) []int {
    out := make([]int, 0, len(left)+len(right))
    i, j := 0, 0
    for i < len(left) && j < len(right) {
        if left[i] <= right[j] { // ≤, а не < — это и даёт устойчивость
            out = append(out, left[i])
            i++
        } else {
            out = append(out, right[j])
            j++
        }
    }
    out = append(out, left[i:]...)  // хвост одной из половин
    out = append(out, right[j:]...)
    return out
}
```

Устойчивость слиянию даёт одна деталь: при равных головах `merge` берёт из **левой** половины, а левая в исходном массиве
шла раньше.

## 3. Быстрая сортировка: сначала разбиение

Сортировка слиянием делит массив не глядя — пополам — и всю работу делает на обратном пути, при
слиянии. Быстрая сортировка (quicksort) поступает наоборот: всю работу делает **до** рекурсии, а
на обратном пути ей делать уже нечего.

Эта работа называется **разбиением** (partition). Берём один элемент — **опорный** (pivot) — и
переставляем массив так, чтобы всё, что меньше опорного, оказалось слева от него, а остальное —
справа. После этого опорный стоит **там же, где будет стоять в отсортированном массиве**: слева
от него ровно столько элементов, сколько меньше него. Больше его никто не тронет.

Прогоним на `[5, 2, 4, 1, 3]`, опорный — последний, `3`. Держим границу `i`: всё левее `i` —
«меньше опорного». Указатель `j` читает массив слева направо; встретил элемент меньше опорного —
меняет его местами с `a[i]` и сдвигает границу.

```text
j  a[j]  < 3?  массив          i  действие
0   5    нет   [5 2 4 1 | 3]   0  —
1   2    да    [2 5 4 1 | 3]   1  обмен a[0] ↔ a[1]
2   4    нет   [2 5 4 1 | 3]   1  —
3   1    да    [2 1 4 5 | 3]   2  обмен a[1] ↔ a[3]
конец          [2 1 3 5 4]        опорный на границу: a[2] ↔ a[4]
```

Тройка встала на индекс 2 — и это её окончательное место: в `[1 2 3 4 5]` она там же. Слева
`[2 1]`, справа `[5 4]` — оба куска ещё не отсортированы, но перемешиваться между собой им уже
незачем. Осталось сделать то же самое с каждым куском отдельно — это и есть рекурсия.

```go
func quickSort(a []int, lo, hi int) {
    if lo >= hi {
        return
    }
    p := partition(a, lo, hi) // pivot встал на место p
    quickSort(a, lo, p-1)
    quickSort(a, p+1, hi)
}

// Схема Ломуто: pivot = a[hi], i — граница зоны «меньше pivot».
func partition(a []int, lo, hi int) int {
    pivot := a[hi]
    i := lo
    for j := lo; j < hi; j++ {
        if a[j] < pivot {
            a[i], a[j] = a[j], a[i]
            i++
        }
    }
    a[i], a[hi] = a[hi], a[i] // pivot между зонами
    return i
}
```

На любом шаге массив состоит из трёх зон. `a[lo..i)` — меньше опорного; круглая скобка значит,
что правый конец не входит, как `i` в срезе `a[lo:i]`. `a[i..j)` — не меньше опорного,
`a[j..hi)` — ещё не смотрели, а сам опорный ждёт в `a[hi]`. Обе ветки `if` эту картину сохраняют —
проверь по таблице. Это инвариант цикла — утверждение, верное перед каждой итерацией; подробно —
в [главе об инвариантах](invariants.md), она стоит в маршруте после [«Двух указателей»](two-pointers.md). Из него сразу следует ответ:
когда `j` дошёл до конца, непросмотренных не осталось, и опорному место ровно на границе `i`.

**Когда это ломается.** Опорный делит массив на «сколько меньше него» и «сколько больше». Если
он раз за разом оказывается самым большим — а на уже отсортированном входе последний элемент
именно такой, — один кусок пуст, второй короче всего на единицу. Глубина рекурсии — `n` вместо
`log n`, время — `O(n²)`. Лечится двумя строками перед разбиением — взять случайный элемент
(пакет `math/rand/v2`) и поставить его последним:

```go
r := lo + rand.IntN(hi-lo+1)
a[r], a[hi] = a[hi], a[r]
```

Случайный опорный лечит неудачный **порядок**, но не повторы: если все значения равны, ни одно
не меньше опорного, и каждый кусок снова короче всего на единицу — какой элемент ни возьми.

Листинг главы, виджет и эталон тренажёра оставлены с фиксированным `a[hi]`: так разбиение на
одном и том же входе всегда одинаково, и трассу можно сверить руками.

Третий способ получить `O(n log n)` — через кучу: пирамидальная сортировка разобрана в
[главе о куче](heap-structure.md#-пирамидальная-сортировка), когда куча уже будет знакома.

## 4. Сортировка подсчётом: без сравнений

Граница `n log n` (почему — в «🧠» ниже) держится только для алгоритмов, которые узнают о данных
сравнениями. Если значения — целые числа из узкого диапазона, сравнивать не нужно: считаем,
сколько раз встретилось каждое значение, и разворачиваем счётчики в отсортированный массив.
Время `O(n + k)`, где `k` — ширина диапазона.

На входе виджета `[2, 5, 3, 0, 2, 3, 0, 3, 1]`: минимум 0, максимум 5, массив счётчиков
`count = [2 1 2 3 0 1]` — два нуля, одна единица, две двойки, три тройки, ни одной четвёрки,
одна пятёрка. Развернули по порядку индексов — `[0 0 1 2 2 3 3 3 5]`. Ни одного сравнения двух
элементов.

```go
func countingSort(a []int) []int {
    if len(a) == 0 {
        return []int{}
    }
    min, max := a[0], a[0]
    for _, v := range a {
        if v < min { min = v }
        if v > max { max = v }
    }
    count := make([]int, max-min+1)
    for _, v := range a {
        count[v-min]++ // смещение на min — чтобы работать с отрицательными
    }
    out := make([]int, 0, len(a))
    for i, c := range count {
        for ; c > 0; c-- {
            out = append(out, i+min)
        }
    }
    return out
}
```

Виджет — упрощённая версия без смещения на `min`: индекс ячейки и есть значение, поэтому он
берёт числа от 0 до 15, а отрицательные и бо́льшие отбрасывает. Фаза 1 — читаем вход (под
гистограммой прочитанное гаснет), фаза 2 — обходим счётчики по возрастанию и выдаём в `out`:

<div class="algo-viz" data-viz="counting-sort" data-array="2,5,3,0,2,3,0,3,1"></div>

> ⚠️ **Про устойчивость.** Показанная версия «посчитал частоты → выдал значения» устойчива, только
> когда сортируем **сами числа** (равные элементы неразличимы, порядок между ними не важен). Чтобы
> устойчиво сортировать **объекты по целочисленному ключу** (сохраняя исходный порядок равных),
> нужен канонический вариант: из частот строят **префиксные суммы** (нарастающие итоги счётчиков: сколько
> элементов не больше значения — там кончается его участок в ответе), затем
> проходят вход **справа налево**, кладя каждый объект на своё место.
>
> Пример: объекты A, B, C с ключами 2, 1, 2. Нарастающие итоги: ключ 1 кончается на месте 1,
> ключ 2 — на месте 3. Идём справа: C встаёт на место 3 (итог ключа 2 становится 2), B — на
> место 1, A — на место 2. Вышло B, A, C: равные A и C в прежнем порядке. Справа налево — потому
> что каждый участок заполняется с конца: последний из равных встаёт последним.
>
> Именно этот вариант — устойчивая фаза поразрядной сортировки (radix sort: числа сортируют по
> одной цифре за проход). Галочка «устойчива» в таблице относится к нему.

## 5. Быстрый выбор: k-й элемент за O(n)

Если нужен **не весь** отсортированный массив, а лишь k-й по величине, сортировать целиком
незачем. Разбиение уже даёт главное: после него опорный стоит на своём окончательном месте `p`.
Если `p` и есть искомый индекс `target = k − 1` — ответ найден. Если нет, ответ лежит по одну
сторону от опорного, а другую сторону можно выбросить целиком. Быстрый выбор (QuickSelect) —
это быстрая сортировка, которая продолжает только в **одну** сторону.

На входе виджета `[7, 2, 9, 4, 3, 8, 1, 5]`, `k = 4` (значит, `target = 3`) окно `[lo, hi]`
сжимается так:

```text
окно   значения           опорный → место   дальше
[0,7]  [7 2 9 4 3 8 1 5]  5 → 4             4 > 3: hi = 3
[0,3]  [2 4 3 1]          1 → 0             0 < 3: lo = 1
[1,3]  [4 3 2]            2 → 1             1 < 3: lo = 2
[2,3]  [3 4]              4 → 3             = target, ответ 4
```

Каждое разбиение просматривает только окно, а окно каждый раз сжимается до доли `α < 1` от
прежнего. Сумма `n + αn + α²n + …` не больше `n / (1 − α)`: при `α = ½` это `2n` — каждый
следующий просмотр вдвое короче, и все вместе не длиннее двух полных проходов. Отсюда `O(n)` в
среднем. На практике со
случайным опорным это около 2–3,5 n сравнений: ближе к 2 n для минимума, около 3,4 n для медианы.

```go
// k-й наименьший (k от 1). k=1 — минимум, k=len — максимум.
func quickSelect(a []int, k int) int {
    lo, hi, target := 0, len(a)-1, k-1
    for {
        if lo == hi {
            return a[lo]
        }
        p := partition(a, lo, hi)
        switch {
        case p == target:
            return a[p]
        case p < target:
            lo = p + 1 // искомый ранг правее — идём только вправо
        default:
            hi = p - 1
        }
    }
}
```

## 📊 Сравнение алгоритмов

| Алгоритм        | Время (в среднем) | Время (в худшем) | Память   | Устойчива | На месте |
|-----------------|----------------|---------------|----------|-----------|----------|
| Вставками       | O(n²)          | O(n²)         | O(1)     | ✅        | ✅       |
| Слиянием        | O(n log n)     | O(n log n)    | O(n)     | ✅        | ❌       |
| Быстрая         | O(n log n)     | O(n²)         | O(log n) | ❌        | ✅       |
| Пирамидальная ([глава о куче](heap-structure.md#-пирамидальная-сортировка)) | O(n log n) | O(n log n) | O(1) | ❌ | ✅ |
| Подсчётом       | O(n + k)       | O(n + k)      | O(n + k) | ✅        | ❌       |

*Устойчивая* (stable) — равные элементы сохраняют исходный относительный порядок. Это
критично при сортировке по нескольким ключам подряд. *На месте* (in-place) — без
дополнительной памяти сверх O(log n).

## 🧠 Почему это корректно

Три вопроса отделяют «работает на примере» от «я знаю, почему»: **нижняя граница
Ω(n log n)**, **устойчивость слияния** и **почему быстрый выбор линеен**. Корректность
разбиения — это инвариант трёх зон из [раздела 3](#3-быстрая-сортировка-сначала-разбиение).

### Почему сравнениями не быстрее `n log n`

Сортировка, которая умеет только сравнивать, узнаёт о массиве по одному ответу «да/нет» за раз.
До начала возможен любой из `n!` порядков элементов, и алгоритм обязан выяснить, какой именно
ему достался: разным порядкам нужны разные перестановки.

Это игра «угадай число»: один ответ «да/нет» в лучшем случае отсекает половину вариантов. Для
восьми элементов порядков `8! = 40 320`, а делить их пополам до одного приходится около 16 раз —
меньше 16 сравнений в худшем случае не хватит никакому алгоритму. С ростом `n` это число растёт
как `n log n`: быстрее `n log n` сравнениями не отсортировать.

Это нижняя граница **задачи** — `Ω(n log n)`, — а не свойство одного алгоритма (разницу мы
разбирали в [главе про Big-O](big-o.md)). Сортировка подсчётом её не нарушает: она ни разу не
сравнивает два элемента, а кладёт значение прямо в ячейку с его номером. Другой способ узнавать
о данных — другая граница.

### Устойчивость слияния — это `≤`, а не `<`

В `merge` при равенстве голов (`left[i] <= right[j]`) мы берём из **левой** половины.
Левая половина в исходном массиве шла раньше — значит, равные элементы сохраняют
относительный порядок. Замени `≤` на `<` — устойчивость сломается, хотя массив всё ещё
будет отсортирован. Это та деталь, на которой валятся на собеседовании.

### Почему быстрый выбор — O(n) в среднем, а быстрая сортировка — O(n log n)

Быстрая сортировка уходит в рекурсию по **обе** стороны от опорного: T(n) = 2·T(n/2) + O(n) =
O(n log n). Быстрый выбор — только в **одну**: T(n) = T(n/2) + O(n) = O(n) (если опорный делит
ровно пополам, сумма n + n/2 + … → 2n; при случайном опорном доля другая, но сумма всё так же
геометрическая). Оба деградируют до O(n²) при неудачном опорном (например, всегда
максимум на отсортированном входе) — поэтому на практике опорный выбирают **случайно**: тогда
матожидание (среднее по всем случайным выборам) числа сравнений снова `O(n)` у быстрого выбора и `O(n log n)` у быстрой сортировки
при любом порядке входа.

Одно исключение — много равных значений. Разбиение Ломуто кладёт их все по одну сторону, и
случайный опорный не спасает. На массиве из 1000 равных быстрая сортировка делает 499 500
сравнений — ровно `n(n−1)/2`, а быстрый выбор медианы — 374 750, три четверти того же квадрата.
Помогает разбиение на три зоны («меньше / равно / больше»), как в задаче о флаге.

## ⚙️ Цена на практике

### Что вызывает `slices.Sort` в Go

Свою сортировку на работе почти не пишут — вызывают встроенную:

```go
import (
    "cmp"
    "slices"
)

slices.Sort(nums)                                   // по возрастанию, O(n log n)
slices.SortFunc(p, func(a, b Point) int {           // по своему компаратору
    return cmp.Compare(a.X, b.X)                    // <0, 0, >0; НЕ a.X-b.X — вычитание переполняется
})
slices.SortStableFunc(recs, byKey)                  // устойчивая (сохраняет порядок равных)
```

Стандартная `slices.Sort` (и `sort.Slice`) — это **pdqsort** (pattern-defeating quicksort,
`slices.Sort → pdqsortOrdered`). Это гибрид из трёх частей:

1. быстрая сортировка; опорный — медиана трёх, то есть средний **по величине** из элементов на
   ¼, ½ и ¾ куска, а у кусков от 50 элементов каждый из трёх сам берётся как средний из точки и
   двух её соседей — медиана трёх медиан;
2. **вставки** для кусков не длиннее 12 элементов — там квадратичная сортировка с крошечной константой и
   дружбой с кэшем быстрее;
3. **пирамидальная сортировка** про запас, если перекошенных разбиений слишком много, — защита
   от O(n²).

Итог: быстро в среднем и **гарантированные O(n log n)** в худшем случае. `slices.SortFunc` **не устойчива** — для устойчивости есть
`slices.SortStableFunc`. Полный разбор, почему это гибрид трёх сортировок, — в главе
[«Структуры данных в экосистеме Go»](go-stdlib-structures.md#-разбор-почему-slicessort--это-гибрид-трёх-сортировок).

### Устойчивость стоит памяти

`slices.Sort` и быстрая сортировка неустойчивы, зато на месте. За устойчивость платят либо
памятью, либо временем. Слияние из этой главы требует O(n) дополнительного буфера.
`slices.SortStableFunc` буфера не берёт: сортирует вставками куски по 20 элементов и сливает их
на месте поворотами. Сравнений у неё O(n log n), но перестановок — O(n log² n), поэтому она
медленнее неустойчивой. Правило:
если порядок равных не важен — бери неустойчивую (быстрее, без аллокаций); если
сортируешь по второму ключу, сохраняя первый, — нужна устойчивая.

### Аллокации: на месте против копии

`mergeSort` выше возвращает **новый** срез и аллоцирует на каждом слиянии — наглядно, но
на горячем пути — в коде, который выполняется чаще всего, — дорого. Промышленная сортировка слиянием использует **один** буфер на весь вызов
(`make([]int, n)` один раз) и сливает в него. `quickSort` не аллоцирует вовсе.
Когда меряешь (`testing.B`, `pprof`) — аллокации при слиянии часто и есть «скрытая»
константа.

### O(n log n) не всегда быстрее O(n²)

На `n ≤ 12` сортировка вставками обгоняет быструю из-за константы и кэша — именно
поэтому pdqsort переключается на неё. «Асимптотически лучше» ≠ «быстрее на твоих данных».
Меряй, а не угадывай — это привычка инженера, а не кодера.

### Сортировка подсчётом: O(n + k) — палка о двух концах

Для `[]int{1, 1000000}` диапазон k = 10⁶: подсчёт выделит миллион счётчиков ради
двух чисел. Он выигрывает, **только** когда k = O(n) (узкий диапазон: оценки 0..100,
байты, возрасты). Иначе — мусор в памяти и проигрыш быстрой сортировке.

## ⚠️ Типичные ошибки

1. **`<` вместо `≤` в слиянии** — массив отсортируется, но сортировка перестанет быть
   устойчивой. Тихо ломает сортировку по нескольким ключам.
2. **Фиксированный опорный** в быстрой сортировке и быстром выборе — O(n²) на отсортированном
   входе. Выбирай опорный случайно или бери медиану трёх.
3. **Подсчёт с отрицательными** без смещения на `min` — выход за границы массива
   счётчиков (паника).
4. **Быстрый выбор возвращает не то** — путаница 0-/1-индексации `k`. Зафиксируй контракт
   (здесь `k` от 1) и считай `target := k-1`.
5. **Рекурсия в обе части подряд при фиксированном опорном** на отсортированном входе — глубина O(n) и переполнение
   стека. Уходи рекурсией в меньшую часть, а большую обрабатывай циклом: меньшая часть не длиннее
   половины, поэтому глубина не больше log₂ n.

> 🌍 **Где это в настоящем коде**
>
> - [`pdqsortOrdered`](https://github.com/golang/go/blob/go1.24.0/src/slices/zsortordered.go#L63) (Go 1.24) — так работает `slices.Sort`: быстрая сортировка с разбиением по опорному, куски до 12 элементов досортировываются вставками, а после слишком многих неудачных опорных — пирамидальной сортировкой.
> - [`stable`](https://github.com/golang/go/blob/go1.24.0/src/sort/zsortinterface.go#L335) (Go 1.24) — так работает `sort.Stable`: блоки по 20 элементов сортируются вставками, затем соседние блоки сливаются (`symMerge`, слияние без дополнительной памяти).

## 📝 Разбор задачи: k-й наибольший элемент

Это задача [раздела 5 о быстром выборе](#5-быстрый-выбор-k-й-элемент-за-on) в той форме, в какой
её дают на собеседовании: ранг считается с другого конца.

> **Задача** ([LeetCode 215](https://leetcode.com/problems/kth-largest-element-in-an-array/)).
> Дан массив `nums` и число `k`. Вернуть k-й **наибольший** элемент (по значению, не по
> уникальности). Пример: `nums = [3,2,1,5,6,4]`, `k = 2` → `5`.

**Шаг 1. Через полную сортировку — O(n log n).**

```go
func findKthLargest(nums []int, k int) int {
    slices.Sort(nums)
    return nums[len(nums)-k] // k-й с конца
}
```

Работает и проходит. Но мы сортируем **весь** массив ради одного элемента — лишняя работа.

**Шаг 2. Наблюдение.** k-й наибольший — это `(n−k+1)`-й наименьший. Нам не нужен полный
порядок, нужен **один элемент по рангу** — это ровно задача быстрого выбора.

**Шаг 3. Оптимум: быстрый выбор — O(n) в среднем.**

```go
func findKthLargest(nums []int, k int) int {
    return quickSelect(nums, len(nums)-k+1) // (n−k+1)-й наименьший
}
```

На примере: `n = 6`, `k = 2` — ищем 5-й наименьший, `target = 4`.

```text
окно [0,5]  [3 2 1 5 6 4]  опорный 4 → 3   3 < 4: lo = 4
окно [4,5]  [6 5]          опорный 5 → 4   = target, ответ 5
```

Два разбиения, и половина массива `[3 2 1]` после первого ни разу не просматривалась.

**Шаг 4. Что сломается на LeetCode.** Код выше — с фиксированным опорным `a[hi]` (так его
трассу можно сверить руками). В тестах 215 есть отсортированный массив и массив из одинаковых
чисел, и на них разбиение Ломуто режет кусок всего на единицу: на 10⁵ чисел это 1,5–2 секунды —
лимит времени. Нужны обе починки из раздела о быстрой сортировке сразу: **случайный опорный**
(против неудачного порядка) и **три зоны** «меньше / равно / больше» (против повторов — так же,
как во флаге Дейкстры). Все равные опорному встают в середину одним проходом, и если искомый
ранг попал в эту зону, ответ найден.

```go
// k-й наименьший (k от 1): случайный опорный и три зоны.
func quickSelect3(a []int, k int) int {
    lo, hi, target := 0, len(a)-1, k-1
    for {
        pivot := a[lo+rand.IntN(hi-lo+1)]
        // [lo,lt) — меньше pivot, [lt,i) — равны, (gt,hi] — больше
        lt, i, gt := lo, lo, hi
        for i <= gt {
            switch {
            case a[i] < pivot:
                a[lt], a[i] = a[i], a[lt]
                lt++
                i++
            case a[i] > pivot:
                a[i], a[gt] = a[gt], a[i]
                gt-- // пришедший с конца a[i] ещё не проверен — i не двигаем
            default:
                i++
            }
        }
        switch {
        case target < lt:
            hi = lt - 1
        case target > gt:
            lo = gt + 1
        default:
            return pivot // ранг попал в зону равных
        }
    }
}
```

На тех же 10⁵ равных или отсортированных числах — доли миллисекунды, на случайных — около
миллисекунды, как и у Ломуто.

Сортировка делает O(n log n) и упорядочивает всё; быстрый выбор делает O(n) и находит
только нужный ранг. На собеседовании важно проговорить этот переход — он показывает, что
ты выбираешь алгоритм под задачу, а не сортируешь всё подряд по привычке.

> 🧭 **Не пошла задача из основы?** В 912 проверь две вещи: базу рекурсии (срез из нуля или
> одного элемента уже отсортирован) и слияние — пока обе половины не пусты, бери меньшую
> голову (при равенстве — левую, так сортировка остаётся устойчивой), потом допиши хвост той,
> что осталась. В 215 быстрый выбор отличается от быстрой сортировки одной деталью: рекурсия идёт
> **только в ту половину**, где лежит ответ, отсюда `O(n)` в среднем вместо `O(n log n)`; а
> «k-й наибольший» — это `n − k + 1`-й по возрастанию, не перепутай. Из добивки: в 179 всё
> решает **транзитивность компаратора**: сравнивать надо конкатенации (`a+b` против `b+a`),
> а не сами числа — только такое сравнение транзитивно (`a` раньше `b`, `b` раньше `c` ⇒ `a` раньше `c`); 347 — напоминание, что сортировка вообще не всегда нужна: частоты
> ограничены длиной массива и раскладываются по корзинам за `O(n)`.

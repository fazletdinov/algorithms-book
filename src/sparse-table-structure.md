> 🧭 **Зачем отдельная глава.** Sparse table отвечает на «минимум/максимум на `[l, r]`» за честное
> **O(1)** — быстрее дерева отрезков — но ценой: массив должен быть **статичным** (без обновлений),
> а операция — **идемпотентной** (min, max, gcd). Магия в том, что любой отрезок покрывается
> **двумя** перекрывающимися отрезками длины степени двойки, и для идемпотентной операции
> перекрытие не портит ответ. Здесь строим саму таблицу.

## 🧱 Как устроено

Sparse table — это **двумерная таблица** `table[k][i]`: минимум на отрезке длины `2^k`, начиная с
индекса `i`. Строка `k=0` — сам массив (минимумы длины 1), каждая следующая строка удваивает длину
отрезка.

```go
type Sparse struct {
    table [][]int // table[k][i] = min на [i, i+2^k-1]
    log   []int   // предпосчитанные ⌊log2⌋ для O(1) запроса
}
```

```
массив:        5   2   4   7   1   3
k=0 (len 1):   5   2   4   7   1   3
k=1 (len 2):   2   2   4   1   1            ← min пар
k=2 (len 4):   2   1   1                    ← min четвёрок
```

Три факта, которые держат всё:

1. **Каждая строка — удвоение длины.** Зная минимумы отрезков длины `2^(k-1)`, минимум длины `2^k`
   — это минимум двух соседних половин. Так таблица заполняется снизу вверх за O(n log n).
2. **Любой отрезок = два отрезка степени двойки.** Отрезок `[l, r]` длины `len` накрывается двумя
   отрезками длины `2^k` (`k = ⌊log2(len)⌋`): один от `l`, другой заканчивается в `r`. Вместе они
   покрывают `[l, r]` целиком, перекрываясь в середине.
3. **Перекрытие безвредно для идемпотентных операций.** `min(min(A), min(B))` верно, даже если `A`
   и `B` пересекаются — повторный учёт элемента ничего не меняет. Для суммы это сломалось бы.

## 🔨 Построение: `Build`

Строка `k=0` — копия массива. Каждая следующая строка: `table[k][i]` = минимум двух половин длины
`2^(k-1)` из предыдущей строки.

```go
func buildSparse(arr []int) {
    for i := range arr { table[0][i] = arr[i] }       // строка k=0 = массив
    for k := 1; (1 << k) <= len(arr); k++ {
        for i := 0; i+(1<<k) <= len(arr); i++ {
            table[k][i] = min(table[k-1][i],            // левая половина
                              table[k-1][i+(1<<(k-1))]) // правая половина
        }
    }
}
```

> 💡 **Демонстрация построения.** Таблица над `[5,2,4,7,1,3]` заполняется снизу вверх: строка
> `k=0` — массив, строка `k=1` — минимумы пар, строка `k=2` — минимумы четвёрок. Каждая новая
> ячейка — минимум двух подсвеченных половин из строки ниже.

## 🔎 Запрос: `Query` за O(1)

Для `[l, r]` берём `k = ⌊log2(r−l+1)⌋` — наибольшую степень двойки, влезающую в длину. Ответ —
минимум **двух** готовых отрезков длины `2^k`: один от `l`, другой заканчивается в `r`. Они
перекрываются, но для min это не важно.

```go
func query(l, r int) int {           // min на [l, r]
    k := log2(r - l + 1)             // макс. степень, влезающая в длину
    return min(table[k][l],          // отрезок [l, l+2^k-1]
               table[k][r-(1<<k)+1]) // отрезок [r-2^k+1, r] — перекрывает первый
}
```

> 💡 **Демонстрация запроса.** Минимум на `[0, 4]` (длина 5): `k = ⌊log2 5⌋ = 2`, отрезки длины 4
> — `[0, 3]` и `[1, 4]`. Они перекрываются на `[1, 3]`, вместе покрывают `[0, 4]`, и минимум двух
> готовых значений (`2` и `1`) даёт ответ `1` — за два обращения к таблице.

## 🧠 Почему это корректно

### Почему двух отрезков всегда хватает

Для отрезка длины `len` берём `k = ⌊log2(len)⌋`, тогда `2^k > len/2`. Отрезок от `l` длины `2^k`
покрывает левую часть, отрезок, заканчивающийся в `r`, — правую, и поскольку `2^k > len/2`, они
**гарантированно перекрываются** в середине, не оставляя дыр. Значит их объединение — ровно
`[l, r]`.

### Почему перекрытие не вредит (идемпотентность)

Операция **идемпотентна**, если `x ⊕ x = x` (для min/max это так: `min(a, a) = a`). Тогда учёт
элемента дважды (он попал в оба перекрывающихся отрезка) не меняет результат:
`min(min(A), min(B)) = min(A ∪ B)` даже при `A ∩ B ≠ ∅`. Для **суммы** `x + x ≠ x`, поэтому
серединка сложилась бы дважды — sparse table для суммы не годится (там берут префиксные суммы или
дерево).

### Почему запрос — O(1), а построение — O(n log n)

Запрос — это вычисление `k` (по предпосчитанной таблице логарифмов) и **два** обращения к
таблице: константа. Построение заполняет `log n` строк по `n` ячеек, каждая за O(1) → O(n log n)
времени и столько же памяти. Это плата за O(1)-запрос и отсутствие обновлений.

## ⚙️ Цена на практике

### Sparse table против дерева отрезков

- **Sparse table:** запрос O(1), но массив **статичен** (обновления потребовали бы перестроить всю
  таблицу за O(n log n)), и операция должна быть идемпотентной.
- **Дерево отрезков:** запрос O(log n), зато поддерживает **обновления** и любые ассоциативные
  операции (включая сумму, lazy).

Правило: **много запросов min/max по неизменному массиву → sparse table**; есть обновления или
нужна сумма → [дерево отрезков](segment-tree-structure.md) / [Фенвик](fenwick-tree-structure.md).

### Память O(n log n)

Таблица хранит `log n` строк по `n` элементов. Для больших `n` это заметно. Если запросов мало,
дерево отрезков (память O(n)) или даже линейный проход могут оказаться практичнее — взвешивай
предпосчёт против числа запросов.

### Предпосчёт логарифмов

`⌊log2(len)⌋` в запросе должен быть O(1), иначе теряется весь смысл. Его таблицу `log[]` считают
заранее за O(n): `log[1] = 0`, `log[i] = log[i/2] + 1`. Считать логарифм «на лету» в каждом
запросе — частая потеря производительности.

## ⚠️ Типичные ошибки

1. **Применить к сумме** — перекрытие двух отрезков посчитает середину дважды; sparse table только для идемпотентных операций.
2. **Пытаться обновлять** — таблица статична; одно изменение требует перестроить её целиком.
3. **Считать `log2` в запросе каждый раз** — предпосчитывай таблицу логарифмов, иначе запрос не O(1).
4. **Off-by-one во втором отрезке** — он начинается с `r − 2^k + 1`, а не с `r − 2^k`.
5. **Выход за границы** при `i + 2^k > n` — такие ячейки невалидны и не должны участвовать.

Пакет `sparsetable`: `NewSparse` (предобработка O(n log n)) и `Query` (минимум на `[l, r]` за
O(1)). Рандом-тест сверяет твой O(1)-запрос с brute-force `min` на каждом диапазоне. Главный
вопрос — почему перекрытие двух отрезков длины `2^k` не портит ответ (минимум **идемпотентен**), и
почему тот же трюк не сработал бы для суммы.

> 📌 В главе `buildSparse`/`query` — свободные функции над общим состоянием; в тренажёре та же
> логика обёрнута в тип: `NewSparse(arr)` строит таблицу и возвращает `*Sparse`, а `Query` — метод
> на нём. Диапазон `[l, r]` — включительный, индексация с нуля.

## 🧩 Где это нужно

Честно: на LeetCode sparse table напрямую требуется редко — для большинства range-запросов
проходит и [дерево отрезков](segment-tree-structure.md) (с O(log n) на запрос вместо O(1)).
Её ниша — **много запросов идемпотентной свёртки (min/max/gcd) по неизменному массиву**, и
техника **двоичного подъёма** (удвоение по `2^k`), которая из неё растёт.

- На собеседовании это типичный **follow-up**: «массив не меняется, прилетает 10⁶
  запросов range-min — как отвечать быстрее, чем за O(log n)?» → предобработка O(n log n),
  ответ за O(1).
- [Kth Ancestor of a Tree Node](https://leetcode.com/problems/kth-ancestor-of-a-tree-node/) — **двоичный подъём** в чистом виде: та же таблица `up[k][v]` по степеням двойки, что и в sparse table, только над деревом (основа для LCA).
- В спортивном программировании — классический инструмент статического RMQ; саму реализацию собери в тренажёре выше.

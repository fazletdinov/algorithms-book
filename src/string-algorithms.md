## 🎬 Визуализация

> 💡 **Интерактивная демонстрация (KMP).** Образец скользит под текстом: зелёным — совпадение
> символа, красным — несовпадение. При несовпадении образец сдвигается по префикс-функции, а
> указатель текста не откатывается назад. Справа — код с подсветкой строки и переменные (`i`, `j`,
> сдвиг), внизу — шаги. Можно подставить свой текст и образец. (Виджет работает в собранной книге
> `mdbook serve`/`mdbook build`, а не при просмотре `.md` на GitHub.)

## ⚡ Шаблон для собеседования

```go
func kmpSearch(text, pat string) int {
    lps := buildLPS(pat)
    i, j := 0, 0 // i — по тексту, j — по образцу
    for i < len(text) {
        if text[i] == pat[j] {
            i++; j++
            if j == len(pat) {
                return i - j // нашли
            }
        } else if j > 0 {
            j = lps[j-1] // сдвиг образца, i НЕ трогаем
        } else {
            i++
        }
    }
    return -1
}
```

1. предвычисляем `lps` (префикс-функцию);
2. совпало → двигаем оба указателя;
3. несовпало и `j>0` → `j = lps[j-1]` (указатель текста на месте);
4. несовпало и `j=0` → двигаем только `i`.

## 📖 Разбор

<details class="algo-details">
<summary>KMP (префикс-функция), Rabin–Karp и сравнение</summary>

Поиск подстроки: найти первое вхождение образца длины `m` в текст длины `n`. **Наивный**
подход — O(n·m). KMP и Rabin–Karp доводят до **O(n+m)**, по-разному переиспользуя
информацию.

#### KMP: префикс-функция (LPS)

`lps[i]` — длина наибольшего собственного префикса `pattern[0..i]`, совпадающего с его
суффиксом.

```go
func buildLPS(pattern string) []int {
    lps := make([]int, len(pattern))
    length := 0
    for i := 1; i < len(pattern); {
        if pattern[i] == pattern[length] {
            length++
            lps[i] = length
            i++
        } else if length > 0 {
            length = lps[length-1] // откат по уже посчитанным префиксам
        } else {
            lps[i] = 0
            i++
        }
    }
    return lps
}
```

Указатель текста `i` никогда не уменьшается — в этом весь выигрыш.

#### Rabin–Karp: скользящий хеш

Сравниваем не символы, а **хеши**: полиномиальный хеш образца и хеш каждого окна длины
`m`. Хеш окна обновляется за O(1) (rolling hash). Совпали хеши — проверяем строки
посимвольно (защита от коллизий).

```go
func rabinKarp(text, pattern string) int {
    n, m := len(text), len(pattern)
    if m == 0 { return 0 }
    if m > n { return -1 }
    const base, mod = 256, 1_000_000_007
    power := 1
    for i := 0; i < m-1; i++ {
        power = power * base % mod
    }
    var patHash, winHash int
    for i := 0; i < m; i++ {
        patHash = (patHash*base + int(pattern[i])) % mod
        winHash = (winHash*base + int(text[i])) % mod
    }
    for i := 0; i+m <= n; i++ {
        if patHash == winHash && text[i:i+m] == pattern {
            return i
        }
        if i+m < n {
            remove := int(text[i]) * power % mod
            winHash = ((winHash-remove+mod)*base + int(text[i+m])) % mod
        }
    }
    return -1
}
```

#### Сравнение

| Алгоритм     | Время (средн.) | Время (худш.) | Память | Когда выбирать                       |
|--------------|----------------|---------------|--------|--------------------------------------|
| Наивный      | O(n · m)       | O(n · m)      | O(1)   | короткие строки, разовый поиск       |
| KMP          | O(n + m)       | O(n + m)      | O(m)   | гарантированно линейный поиск        |
| Rabin–Karp   | O(n + m)       | O(n · m)      | O(1)   | несколько образцов, сравнение по хешу |

</details>

## 🧠 Почему это корректно

KMP все копируют, но мало кто понимает, **почему** откат по `lps` не пропускает
вхождений и почему всё это линейно.

### Что значит `lps` и почему по нему можно откатываться

Пусть при сравнении произошло несовпадение на `pattern[j]` с `text[i]`. Это значит, что
`pattern[0..j-1]` уже совпал с `text[i-j..i-1]`. У этого совпавшего куска есть
наибольший собственный префикс, равный суффиксу, — его длина и есть `lps[j-1]`. А раз
он суффикс уже совпавшей части, он **автоматически совпадает с текстом** прямо перед `i`.
Поэтому можно продолжить сравнение с `j = lps[j-1]`, **не двигая `i` назад** — этот
префикс перепроверять не нужно.

### Почему не теряем ни одного вхождения

Сдвиг образца ровно на `j − lps[j-1]`. Меньший сдвиг потребовал бы, чтобы *более
длинный* префикс образца совпал с суффиксом уже сопоставленной части. Но `lps[j-1]` —
по определению **самый длинный** такой префикс; ничего длиннее нет. Значит ни один
меньший сдвиг не даёт выравнивания, и пропустить вхождение откатом к `lps[j-1]`
невозможно. ∎

### Почему `O(n + m)` — амортизация

Указатель текста `i` **только не убывает** (никогда не откатывается). Указатель образца
`j` растёт максимум на 1 за шаг `i` и уменьшается только через `lps`. Так как `j ≥ 0`, а
суммарный рост ≤ `n`, суммарное уменьшение тоже ≤ `n` → не более `2n` операций. Построение
`lps` линейно по `m` по тому же аргументу (`length` растёт через `length++`, падает через
откат). Тот же амортизационный довод, что и у скользящего окна.

## ⚙️ Цена на практике

### Гарантированная линейность против «в среднем»

Наивный поиск деградирует до `O(n·m)` на «злом» входе (`text = "aaaa…a"`,
`pattern = "aaa…ab"`). KMP — **линеен в худшем случае**. Rabin–Karp линеен *в среднем*,
но при коллизиях хеша или повторах падает до `O(n·m)` из-за посимвольной доперепроверки.
Нужна гарантия для одного образца — бери KMP.

### Несколько образцов — это уже Aho–Corasick

Rabin–Karp удобен, когда образцов **много** (сравниваем по хешу) или поиск двумерный.
Для множественного поиска как такового обобщение KMP — **Aho–Corasick** (те же
failure-ссылки, но на боре образцов).

### `lps` — переиспользуемый инструмент, не только поиск

Префикс-функция решает целый класс задач: кратчайший палиндром приписыванием, период
строки, «повторяется ли строка из блока» (`n % (n − lps[n-1]) == 0` при `lps[n-1] > 0`).
Навык — узнать, что задаче нужна **failure-функция**, а не просто скопировать поиск.

## ⚠️ Типичные ошибки

1. **В KMP двигают указатель текста назад** — теряется смысл; назад откатывается только `j` через `lps`.
2. **Неверная префикс-функция** — частая ошибка; протестируйте `buildLPS` отдельно (`"aabaab"` → `[0,1,0,1,2,3]`).
3. **Rabin–Karp без проверки строк при совпадении хешей** — коллизии дадут ложные срабатывания.
4. **Переполнение/отрицательный хеш** — берите остаток по модулю и добавляйте `mod` перед `%`.
5. **Пустой образец** — договоритесь о соглашении (здесь возвращаем 0).

## 📝 Разбор задачи

Шаблон выше находит **первое** вхождение. Но на собеседовании чаще просят все — и здесь
прячется ловушка с перекрытием. Пройдём путь от наивного перебора к KMP так, как стоит
рассуждать вслух: сначала рабочий перебор, затем понимание, *почему* он медленный, и
только потом — линейный поиск.

> **Задача.** Дан текст `s` и образец `p`. Вернуть индексы **всех** вхождений `p` в `s`,
> в том числе **перекрывающихся**.
> Пример: `s = "aaaa"`, `p = "aa"` → `[0, 1, 2]` (вхождения `[0,1]`, `[1,2]`, `[2,3]`
> перекрываются).

**Шаг 1. Наивно: для каждой позиции сравнить посимвольно — O(n·m).**

```go
func findAllNaive(text, pat string) []int {
    var res []int
    n, m := len(text), len(pat)
    if m == 0 || m > n {
        return res
    }
    for i := 0; i+m <= n; i++ {
        j := 0
        for j < m && text[i+j] == pat[j] { // сравниваем окно [i..i+m) с образцом
            j++
        }
        if j == m {
            res = append(res, i)
        }
    }
    return res
}
```

Это **работает и проходит тесты**, но на «злом» входе (`text = "aaaa…a"`,
`pat = "aaa…ab"`) каждое окно почти полностью совпадает с образцом и обрывается лишь на
последнем символе — внутренний цикл делает почти `m` шагов на каждой из `n` позиций.
Итого O(n·m). При несовпадении мы **выбрасываем весь прогресс** и начинаем сравнение
заново со сдвига на 1, хотя только что уже прочли эти символы текста.

Прогоните наивный поиск `pat = "aa"` в `text = "aaaa"`: для каждой позиции окно
сравнивается с образцом заново — видно, как одни и те же символы пересравниваются:

<div class="algo-viz" data-viz="string-match-naive" data-text="aaaa" data-pattern="aa"></div>

**Шаг 2. Ключевое наблюдение.** Когда `pat[0..j-1]` совпал, а `pat[j]` — нет, мы уже
знаем содержимое `text[i-j..i-1]`. Сдвигать образец на 1 и перечитывать эти символы
расточительно: достаточно продолжить с `j = lps[j-1]` — длины наибольшего префикса
образца, равного суффиксу совпавшей части. Этот префикс **гарантированно совпадает** с
текстом прямо перед `i`, поэтому [указатель текста `i` никогда не откатывается назад](#что-значит-lps-и-почему-по-нему-можно-откатываться).

Тонкость для **всех** вхождений: найдя совпадение (`j == m`), мы не сбрасываем `j` в `0`,
а делаем тот же откат `j = lps[m-1]`. Так перекрывающийся хвост предыдущего вхождения
переиспользуется как начало следующего — иначе мы бы пропустили `[1,2]` и `[2,3]` в
примере выше.

**Шаг 3. Оптимум: KMP, фиксируем все вхождения — O(n+m).**

```go
func findAllKMP(text, pat string) []int {
    var res []int
    n, m := len(text), len(pat)
    if m == 0 || m > n {
        return res
    }
    lps := buildLPS(pat) // префикс-функция образца — см. раздел «Разбор»
    i, j := 0, 0
    for i < n {
        if text[i] == pat[j] {
            i++
            j++
            if j == m {
                res = append(res, i-j) // нашли вхождение
                j = lps[j-1]           // откат для перекрытий, i НЕ трогаем
            }
        } else if j > 0 {
            j = lps[j-1] // сдвиг образца, i НЕ трогаем
        } else {
            i++
        }
    }
    return res
}
```

Прогоните KMP на `s = "aaaa"`, `p = "aa"`: при несовпадении указатель в образце прыгает
по префикс-функции, а в тексте не откатывается назад:

<div class="algo-viz" data-viz="kmp" data-text="aaaa" data-pattern="aa"></div>

**Шаг 4. Трассировка** на `s = "aaaa"`, `p = "aa"`. Префикс-функция `lps = [0, 1]`:

| `i` | `j` | `text[i]` vs `pat[j]` | действие                       | вхождение |
|-----|-----|-----------------------|--------------------------------|-----------|
| 0   | 0   | `a` = `a`             | `i=1, j=1`                     | —         |
| 1   | 1   | `a` = `a`             | `j==m` → пишем `0`, `j=lps[1]=1` | **0**     |
| 2   | 1   | `a` = `a`             | `j==m` → пишем `1`, `j=lps[1]=1` | **1**     |
| 3   | 1   | `a` = `a`             | `j==m` → пишем `2`, `j=lps[1]=1` | **2**     |

Ответ — `[0, 1, 2]`. Обрати внимание: `i` прошёл `0→4` ни разу не вернувшись назад, а
после каждого вхождения `j` упал в `1` (не в `0`) — именно это сохраняет перекрытие. Тот
самый [амортизированный O(n+m)](#почему-on--m--амортизация). Наивный перебор на этом же
входе дал бы тот же `[0, 1, 2]`, но за O(n·m) сравнений.

## 🧵 Конкурентный поиск (Go)

Поиск подстроки в огромном тексте напрашивается разбить между воркерами. Но тут — классическая
ловушка **границы чанков**: если резать текст на байтовые куски, совпадение, начавшееся в конце
одного куска и кончающееся в начале следующего, **потеряется**.

```
текст:  ...x y | A B... (граница чанков между y и A)
паттерн: "yAB"  ← начинается до границы, кончается после — ни один воркер его не видит целиком
```

Наивный фикс — давать воркеру «хвост» соседнего чанка (нахлёст в `len(pat)-1` байт) — работает, но
легко **задвоить** совпадения на стыке. Проще и безошибочнее — делить не текст, а **диапазон
начальных позиций**:

```go
// воркер отвечает за начала [lo, hi); окно text[i:i+m] всегда целиком в text
for i := lo; i < hi; i++ {
    if text[i:i+m] == pat { c++ }
}
results[w] = c
```

Каждое начало `i` принадлежит ровно одному воркеру, а окно `text[i:i+m]` читается из общего
(неизменяемого) текста — гонок нет, двойного счёта нет, граница не теряется. Чтение общей строки
из многих горутин безопасно: её никто не меняет.

> 💡 Часто «распараллелить» = удачно выбрать, **что** именно делить. Деление по началам, а не по
> байтам текста, убирает всю возню с границами.

```bash
go test -tags solution -race ./parallelsearch/  # общий счётчик не гоняется
```

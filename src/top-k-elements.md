## 🧭 Откуда берётся куча размера k: выведем её сами

Правило «для k наибольших — min-куча» из карточки звучит наоборот, и на нём спотыкаются чаще
всего. Оно перестаёт путать, если вывести его из решения в лоб — на задаче из разбора ниже.

> **Задача.** Дан массив `nums` и число `k`. Верни `k` самых частых значений — то есть `k`
> наибольших по частоте. Возьмём пример из разбора и допишем в конец `4` и `5`:
> `nums = [1,1,1,2,2,3,4,5]`, `k = 2` → `[1, 2]`.

В лоб: посчитать частоты в `map`, отсортировать значения по убыванию частоты, взять первые `k`.

```go
sort.Slice(uniq, func(i, j int) bool {
    return freq[uniq[i]] > freq[uniq[j]] // полный порядок по частоте
})
return uniq[:k]
```

Частоты: `1→3`, `2→2`, `3→1`, `4→1`, `5→1`. Сортировка расставит по местам все пять значений.
Потом `uniq[:k]` возьмёт два, а `3`, `4` и `5` выбросит. Их места мы оплатили — и ни разу на
них не посмотрели. Здесь хвост — три значения из пяти. При `m` уникальных и маленьком `k`
хвост — почти всё.

Что убирает лишнее: вопрос «кто на каком месте» заменить вопросом «пройдёт ли в топ». Для него
весь порядок не нужен. Хватит `k` лучших и частоты самого слабого из них — это **порог**.
Самый слабый — это минимум, поэтому `k` лучших держат в min-куче: её вершина и есть порог.

Пусть значения приходят по порядку `1, 2, 3, 4, 5`. После `1` и `2` порог — частота `2`. У `3`,
`4` и `5` частота `1`: каждое вылетает, едва войдя. Куча не вырастает больше трёх, и каждая
вставка стоит `O(log k)`, а не `O(log m)`.

**Для топа не нужен весь рейтинг — нужен порог: худший из тех, кто сейчас в топе.** Этот
приём — куча размера k (Top K); путь от сортировки до кучи, с трассировкой, — в
[«📝 Разбор задачи»](#-разбор-задачи).

> — min-heap размера k (минимум подсвечен). Когда размер превышает k, выкидываем минимум. Под холстом — строка шага и переменные, ниже — ползунок шагов (или ←/→ на клавиатуре) и код с подсветкой строки. Можно подставить свой массив и `k` и нажать

## ⚡ Шаблон для собеседования

```go
h := &MinHeap{} // куча из k наибольших
for _, num := range nums {
    heap.Push(h, num)
    if h.Len() > k {
        heap.Pop(h) // выкинуть минимум — он не в топе
    }
}
// в h — k наибольших элементов
```

1. кладём каждый элемент в min-heap;
2. как только размер превысил `k` — выкидываем минимум;
3. остаётся ровно `k` наибольших.

## 📖 Разбор

**Top K Elements** — шаблон для поиска K наибольших, наименьших или наиболее частых
элементов коллекции без полной сортировки. Ключевая идея — поддерживать **кучу
размера K** (приоритетную очередь): нам не нужны все элементы в порядке, достаточно
держать инвариант «в куче — K лучших».

<details class="algo-details">
<summary>Код: K наибольших, K частых и сложность</summary>

```go
import "container/heap"

// MinHeap — для K наибольших (минимум на вершине)
type MinHeap []int

func (h MinHeap) Len() int            { return len(h) }
func (h MinHeap) Less(i, j int) bool  { return h[i] < h[j] }
func (h MinHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *MinHeap) Push(x interface{}) { *h = append(*h, x.(int)) }
func (h *MinHeap) Pop() interface{} {
    old := *h
    n := len(old)
    x := old[n-1]
    *h = old[:n-1]
    return x
}

func findKLargest(nums []int, k int) []int {
    if k <= 0 || len(nums) == 0 {
        return nil
    }
    h := &MinHeap{}
    heap.Init(h)
    for _, num := range nums {
        if h.Len() < k {
            heap.Push(h, num)
        } else if num > (*h)[0] { // больше худшего из лучших — заменяем
            heap.Pop(h)
            heap.Push(h, num)
        }
    }
    result := make([]int, h.Len())
    for i := len(result) - 1; i >= 0; i-- {
        result[i] = heap.Pop(h).(int)
    }
    return result
}
```

Для **K наиболее частых** сначала считаем частоты в `map`. Проще всего потом
отсортировать пары по частоте — так сделано ниже, и это `O(m log m)` на `m`
разных значений. Сортировка упорядочивает и те пары, что в ответ не попадут;
в [разборе задачи](#-разбор-задачи) она заменяется тем же приёмом, что выше, —
min-heap размера K, только сравниваем частоты:

```go
func topKFrequent(nums []int, k int) []int {
    freq := make(map[int]int, len(nums))
    for _, num := range nums {
        freq[num]++
    }
    type pair struct{ num, count int }
    pairs := make([]pair, 0, len(freq))
    for num, count := range freq {
        pairs = append(pairs, pair{num, count})
    }
    sort.Slice(pairs, func(i, j int) bool { return pairs[i].count > pairs[j].count })
    result := make([]int, k)
    for i := 0; i < k; i++ {
        result[i] = pairs[i].num
    }
    return result
}
```

#### Сложность

| Задача                | Время       | Память |
|-----------------------|-------------|--------|
| K наибольших/наименьших | O(n log k) | O(k)   |
| K наиболее частых     | O(n + m log m)¹ | O(n)  |

¹ `m` — число **различных** значений: показанный код сортирует все `m` пар «значение—частота»,
отсюда `m log m`. Куча размера `k` вместо полной сортировки пар даёт `O(n + m log k)`, а корзинная
сортировка по частоте — вовсе `O(n)`.

Куча размера K даёт O(n log k) против O(n log n) полной сортировки — заметный выигрыш
при малом k.

## 🧠 Почему это корректно

### Почему min-heap размера K даёт K наибольших

> **Инвариант:** в куче — `K` наибольших из просмотренных. Её вершина (минимум) — это
> **порог**: худший из текущих лучших.

Шаблон кладёт каждый элемент и тут же выкидывает минимум, если куча переполнилась. Вариант
с `if num > (*h)[0]` из свёрнутого кода делает то же самое, но не пускает в кучу того, кто
всё равно вылетит, — экономит вставку и извлечение на каждом слабом элементе. Результат
один: после прохода в куче ровно `K` наибольших. Берём **min-heap** (а не max),
потому что для решения о вытеснении нужен `O(1)`-доступ именно к **худшему** из
оставленных `K` — а это минимум. Тот же приём «обнажить границу», что у
[двух куч](two-heaps.md).

### Почему «K частых» и «K ближайших» — тот же инвариант

Куче безразлично, *что* сравнивать: она держит `K` лучших по **ключу**. Для частых
ключ — счётчик `count`, для ближайших — расстояние (с обратным знаком). Аргумент
корректности дословно тот же: вершина — порог, худший из оставленных; кто слабее порога,
в куче не остаётся. Глубокая суть в том, что **полный порядок не нужен** — нужен
лишь частичный: мы никогда не сравниваем то, что не храним, поэтому относительный
порядок элементов вне топа не важен.

## ⚙️ Цена на практике

### Куча против сортировки и quickselect

`O(n log k)` против `O(n log n)` у полной сортировки — выигрыш тем больше, чем меньше
`k`. И куча работает на **потоке**: в памяти только `k` элементов, данные не обязаны
помещаться целиком. Если же весь массив в памяти и ответ нужен **разово** —
**quickselect** (разбиение вокруг опорного) даёт `O(n)` в среднем. Правило: онлайн/поток
→ куча; один проход по готовому массиву → quickselect.

### `container/heap` боксит интерфейсы

`Push(x any)` и `Pop() any` принимают `interface{}` — каждый `int` **упаковывается** в
интерфейс, а это аллокация в куче (runtime кэширует лишь мелкие значения 0–255).
На горячем пути из миллионов вставок боксинг давит на GC сильнее, чем сами операции с
кучей. Лечится **типизированной кучей** на дженериках (Go 1.18+) или ручной `[]int`-кучей
без интерфейса: Big-O тот же `O(log k)`, а константа в разы меньше.

### «K частых» за `O(n)`: корзины вместо кучи

Частоты лежат в диапазоне `[1, n]` — значит элементы можно разложить по `n+1`
**корзинам-частотам** (bucket sort) и собрать ответ с конца за `O(n)`, вообще без
`log`. Куча и сортировка из примера выше дают `O(n log k)` и `O(n + m log m)` (`m` — число различных значений); корзины
бьют их, когда диапазон ключа ограничен. Классический инженерный размен: **знаешь
границы ключа — считай за линию**.

## ⚠️ Типичные ошибки

1. **Неправильный тип кучи** — для K наибольших нужен min-heap, для K наименьших — max-heap.
2. **Сравнение не с вершиной** — новый элемент сравнивайте именно с корнем кучи `(*h)[0]`.
3. **Куча не ограничена по размеру** — забыв вытолкнуть лишнее, получаете O(n log n) и O(n) памяти.
4. **Пустой массив или `k = 0`** — возвращайте пустой результат до работы с кучей.
5. **`k >= len(nums)`** — тогда возвращаются все элементы, отдельная обработка не нужна, но проверьте границы.
6. **Большое k** (`k > n/2`) — куча перестаёт быть выгодной, рассмотрите QuickSelect или сортировку.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он избыточен, и
только потом куча.

> **Задача.** Дан массив `nums` и число `k`. Вернуть `k` **самых частых** элементов
> (в любом порядке). Гарантируется, что ответ единственный.
> Пример: `nums = [1,1,1,2,2,3]`, `k = 2` → ответ `[1, 2]` (частоты 3 и 2 против 1 у тройки).

**Шаг 1. Наивно: посчитать частоты и полностью отсортировать — O(n log n).**

```go
func topKFreqNaive(nums []int, k int) []int {
    freq := make(map[int]int, len(nums))
    for _, num := range nums {
        freq[num]++
    }
    uniq := make([]int, 0, len(freq))
    for num := range freq {
        uniq = append(uniq, num)
    }
    sort.Slice(uniq, func(i, j int) bool { // полный порядок по убыванию частоты
        return freq[uniq[i]] > freq[uniq[j]]
    })
    return uniq[:k] // берём первые k
}
```

Это **работает и проходит тесты**, но сортирует *все* `m` уникальных значений целиком —
`O(m log m)`, хотя нужны лишь `k` верхних. Мы упорядочиваем и тот «хвост», который сразу
выбросим: лишний `log` на каждом из тех элементов, что в ответ не попадут.

**Шаг 2. Ключевое наблюдение.** Полный порядок не нужен — нужны лишь `k` элементов с
наибольшим счётчиком. Это ровно [инвариант K наибольших](#почему-min-heap-размера-k-даёт-k-наибольших),
только ключ сравнения — не само значение, а его **частота** `count`. Держим **min-heap
размера k** по `count`: его вершина — порог, наименее частый из текущих лучших. Когда куча
полна, новая пара с частотой не ниже порога вытесняет вершину, а более редкая вылетает сама.
После прохода в куче ровно `k` самых частых — и за каждую пару мы платим `log k`, а не `log m`.

**Шаг 3. Оптимум: подсчёт частот + min-heap размера k — O(n log k).**

```go
type entry struct{ num, count int }
type freqHeap []entry

func (h freqHeap) Len() int            { return len(h) }
func (h freqHeap) Less(i, j int) bool  { return h[i].count < h[j].count } // min по count
func (h freqHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *freqHeap) Push(x interface{}) { *h = append(*h, x.(entry)) }
func (h *freqHeap) Pop() interface{} {
    old := *h
    n := len(old)
    x := old[n-1]
    *h = old[:n-1]
    return x
}

func topKFreqHeap(nums []int, k int) []int {
    freq := make(map[int]int, len(nums))
    for _, num := range nums {
        freq[num]++
    }
    h := &freqHeap{}
    heap.Init(h)
    for num, count := range freq {
        heap.Push(h, entry{num, count})
        if h.Len() > k {
            heap.Pop(h) // выкинуть наименее частого — он не в топе
        }
    }
    result := make([]int, h.Len())
    for i := len(result) - 1; i >= 0; i-- {
        result[i] = heap.Pop(h).(entry).num
    }
    return result
}
```

Прогоните min-heap размера `k` на `nums = [1,1,1,2,2,3]`, `k = 2`: куча держит k самых
частых, вытесняя элемент с наименьшей частотой. Здесь вылетает сам новичок `(3, c=1)`; во
второй вкладке (`nums = [1,2,2,3,3,3,4,4,4,4]`) частоты растут, и на полной куче каждая новая
пара вытесняет вершину — порог поднимается 1 → 2 → 3:

**Шаг 4. Трассировка** на `nums = [1,1,1,2,2,3]`, `k = 2`. Частоты: `1→3, 2→2, 3→1`;
пары обрабатываем в порядке `(1,3), (2,2), (3,1)` (порядок обхода `map` в Go не определён и
может меняться от обхода к обходу; ответ от него не зависит, а путь к нему — да). В столбце —
содержимое кучи (как массив `container/heap`, корень слева — это минимум по `count`):

| вставили  | размер | переполнение → выкинули | куча после      | вершина (порог) |
|-----------|--------|-------------------------|-----------------|-----------------|
| `(1, c=3)`| 1      | —                       | `[(1,3)]`       | `(1, c=3)`      |
| `(2, c=2)`| 2      | —                       | `[(2,2),(1,3)]` | `(2, c=2)`      |
| `(3, c=1)`| 3 > 2  | выкинули `(3, c=1)`     | `[(2,2),(1,3)]` | `(2, c=2)`      |

В куче остались `1` и `2` — ответ `[1, 2]`. Тройка с частотой `1` не пробила порог
`c=2` и вылетела сразу же. Куча ни разу не выросла больше `k+1`, поэтому каждая из `m`
вставок стоит `O(log k)`, а не `O(log m)` — отсюда `O(n log k)` против `O(n log n)`
наивной сортировки.

## 🧵 Конкурентный подсчёт частот (Go)

`TopKFrequent` начинается с **подсчёта частот**. На большом потоке этот этап напрашивается на
распараллеливание: бьём вход на чанки, считаем частоты в каждом — и сливаем. Но тут поджидает
самая частая ошибка новичка в Go.

### Чего делать НЕЛЬЗЯ

```go
freq := map[int]int{}
for _, chunk := range chunks {
    go func(c []int) {
        for _, x := range c { freq[x]++ } // ← запись в ОБЩУЮ map из горутин
    }(chunk)
}
```

Go-`map` **не потокобезопасна**: конкурентная запись роняет программу с `fatal error:
concurrent map writes` (это не паника, её даже не поймать `recover`). `-race` тоже укажет на
конфликт.

Прошагай гонку: несколько воркеров делают `freq[7]++` по общей карте. Все читают `0`, все пишут
`1` — инкременты затирают друг друга (вместо `n` получается `1`), а Go-`map` вдобавок падает.

<div class="algo-viz" data-viz="wordcount-race" data-goroutines="3"></div>

### Как правильно: worker pool + fan-in

Каждый воркер копит **свою** карту, а после `WaitGroup` главная горутина сливает их в одну:

```go
partials[w] = local            // воркер пишет в свою ячейку — общей записи нет
// ...wg.Wait()...
for _, p := range partials {   // fan-in: слияние локальных карт
    for k, v := range p { result[k] += v }
}
```

Никаких замков на горячем пути — синхронизация только в момент слияния. Это базовый паттерн
**map-reduce**: разделить → посчитать локально → свести.

Тот же сценарий, но правильно: каждый воркер инкрементит **свою** карту (зелёный), а в конце —
слияние. Все инкременты сохраняются (`freq[7]=n`), красного окна гонки нет.

<div class="algo-viz" data-viz="wordcount-local" data-goroutines="3"></div>

> 💡 Если общая структура всё же нужна по ходу — бери `sync.Mutex`/`sync.RWMutex` или `sync.Map`,
> но почти всегда «локально + слить в конце» быстрее: нет борьбы за замок.

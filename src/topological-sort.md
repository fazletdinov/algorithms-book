## 🧭 Откуда берётся алгоритм Кана: выведем его сами

Задача из «📝 Разбора задачи» ниже: у курсов есть предусловия — «чтобы пройти `a`, сначала
пройди `b`». Нужен любой порядок, в котором можно пройти все курсы.

Человек рассуждает так: **какой курс я могу взять прямо сейчас?** Тот, у которого все
предусловия пройдены. В лоб: каждый раунд пробегаем курсы по номерам и берём первый готовый.

Пять курсов цепочкой, с неудачной нумерацией: каждый требует следующий по номеру. `0?` — это
вопрос «курс `0` уже можно взять?»:

```text
цепочка:  4 ──► 3 ──► 2 ──► 1 ──► 0     (стрелка: «сначала» ──► «потом»)
раунд 1:  0? нет  1? нет  2? нет  3? нет  4? да → берём 4
раунд 2:  0? нет  1? нет  2? нет  3? да → берём 3
раунд 3:  0? нет  1? нет  2? да → берём 2
раунд 4:  0? нет  1? да → берём 1
раунд 5:  0? да → берём 0
```

15 проверок ради 5 курсов, и 10 из них — пустое «нет». Курс `0` спросили пять раз, хотя его
ответ меняется лишь однажды — когда взяли `1`. На такой цепочке из `n` курсов проверок
`n(n+1)/2`: квадрат.

Лекарство: готовность курса может измениться только в один момент — когда пройдено одно из
его предусловий. Значит, не опрашиваем всех по кругу, а заводим каждому курсу счётчик
непройденных предусловий — его **входящую степень** (in-degree). Взяли курс — уменьшаем
счётчик только у тех, кто от него зависит; дошёл до нуля — курс в очередь готовых. На цепочке
это 4 уменьшения счётчика — по одному на предусловие, — и ни одного пустого «нет».

**Входящая степень — это `sync.WaitGroup` у каждого курса: пройденное предусловие делает ему
`Done()`, и курс встаёт в очередь, когда счётчик дошёл до нуля, — никого не опрашивают по кругу.**

Это и есть **алгоритм Кана**. В [«📝 Разбор задачи»](#-разбор-задачи) путь начинается с перебора
ещё грубее — всех перестановок — и доходит до Кана с трассировкой.

## 🎬 Визуализация

> 💡 **Интерактивная демонстрация.** Рядом с вершиной — входящая степень (`in:`). Кан убирает
> вершину со степенью 0 (жёлтая → синяя) и уменьшает степени соседей: текущее ребро жёлтое,
> а снятое становится пунктиром — это и есть «удалить источник вместе с его рёбрами».
> Вершина, у которой сняли последнее входящее ребро, зеленеет: она готова и ждёт в очереди. Под холстом — строка шага и переменные (порядок), ниже — ползунок шагов (или ←/→ на клавиатуре) и код с подсветкой строки.

В примере два источника (`A` и `B`), и очередь почти всё время держит **две** готовые вершины:
порядок, в котором их снимать, — дело выбора, поэтому топологических порядков у графа несколько.

> 🔧 **Где это в Go.** Так компилятор выбирает **порядок инициализации переменных** пакета: строит

## ⚡ Шаблон для собеседования

```go
// Алгоритм Кана (BFS по in-degree)
queue := []int{}
for v := 0; v < n; v++ {
    if inDegree[v] == 0 {
        queue = append(queue, v) // все источники сразу
    }
}
var order []int
for len(queue) > 0 {
    u := queue[0]; queue = queue[1:]
    order = append(order, u)
    for _, w := range adj[u] {
        inDegree[w]--
        if inDegree[w] == 0 {
            queue = append(queue, w)
        }
    }
}
if len(order) != n { /* цикл — порядок невозможен */ }
```

1. считаем in-degree всех вершин;
2. все вершины с in-degree 0 → в очередь;
3. убираем вершину, уменьшаем степени соседей, новые нули → в очередь;
4. `len(order) < n` ⇒ цикл.

## 📖 Разбор

**Topological Sort** находит линейный порядок вершин ориентированного ациклического
графа (**DAG**): если ребро A → B, то A идёт перед B. Сортировка существует тогда и
только тогда, когда граф — DAG (без циклов).

Ключевое наблюдение: в DAG всегда есть вершина с **in-degree = 0** (источник). Обрабатывая
источники и «удаляя» их, открываем новые источники — это **алгоритм Кана**.

<details class="algo-details">
<summary>Алгоритм Кана в коде, DFS-вариант и сложность</summary>

```go
func topologicalSort(numCourses int, prerequisites [][]int) []int {
    graph := make([][]int, numCourses)
    inDegree := make([]int, numCourses)
    for _, prereq := range prerequisites {
        course, prerequisite := prereq[0], prereq[1]
        graph[prerequisite] = append(graph[prerequisite], course)
        inDegree[course]++
    }
    queue := []int{}
    for i := 0; i < numCourses; i++ {
        if inDegree[i] == 0 {
            queue = append(queue, i)
        }
    }
    result := []int{}
    for len(queue) > 0 {
        node := queue[0]
        queue = queue[1:]
        result = append(result, node)
        for _, neighbor := range graph[node] {
            inDegree[neighbor]--
            if inDegree[neighbor] == 0 {
                queue = append(queue, neighbor)
            }
        }
    }
    if len(result) != numCourses {
        return []int{} // цикл — сортировка невозможна
    }
    return result
}
```

**Альтернатива — DFS:** когда вершина полностью обработана, кладём её в стек; развёрнутый
стек даёт топопорядок. Цикл ловится по «серой» (обрабатываемой) вершине.

Для графа A→B, A→C, B→C, B→D, C→D порядок: **[A, B, C, D]**. Граф с циклом
`A→B→C→A` даёт in-degree всех = 1, очередь пуста с начала → `len(result) < V` → цикл.

#### Сложность

| Подход              | Время    | Память   |
|---------------------|----------|----------|
| Алгоритм Кана (BFS) | O(V + E) | O(V + E) |
| DFS                 | O(V + E) | O(V + E) |

</details>

Алгоритм Кана опирается на три факта: в DAG всегда есть источник, удаление источников
сохраняет валидность порядка, а застрявшие вершины — это в точности цикл.

### Почему в DAG всегда есть вершина с in-degree = 0

От противного: пусть у каждой вершины есть входящее ребро. Тогда пойдём «назад» по
входящим рёбрам — на конечном числе вершин мы обязаны вернуться в уже посещённую →
**цикл**, что противоречит ацикличности. Значит источник существует, и Кану всегда есть
с чего начать. После удаления источника подграф остаётся DAG → источник найдётся снова.

### Инвариант Кана

> Когда вершину `v` кладут в результат (её `in-degree` стал `0`), **все** рёбра в `v`
> уже исходят из ранее размещённых вершин.

Значит каждый предшественник `v` уже стоит раньше — порядок уважает все рёбра. По
индукции весь вывод — корректный топопорядок.

### Почему `len(result) < V` ⟺ есть цикл

Вершины, так и не достигшие `in-degree = 0`, — это ровно те, чьи зависимости образуют
**взаимный цикл**: ни одна не освободится, пока не освободится другая. И наоборот: если
граф — DAG, то многократное «снятие источников» опустошает его полностью (по первому
факту источник есть на каждом шаге). Поэтому остаток `> 0` равносилен наличию цикла —
это и есть бесплатный детектор цикла.

### Сложность

Каждая вершина попадает в очередь и выходит из неё один раз, каждое ребро уменьшает
`in-degree` соседа один раз → **`O(V + E)`**.

## ⚙️ Цена на практике

### Кан (BFS) против DFS

Кан даёт **детектор цикла даром** (через `len(result)`) и естественные «слои»
зависимостей (уровни BFS = глубина зависимости). DFS-вариант требует трёхцветной
пометки (белый/серый/чёрный) для отлова цикла и выдаёт обратный постпорядок. Нужны ещё
и обнаружение цикла или слои — бери Кана.

### Лексикографически наименьший порядок — куча вместо очереди

Топопорядок **не единственный**: следующим может пойти любой текущий источник. Если
задача просит *наименьший* порядок (частый follow-up), замени очередь на **min-heap** —
получишь `O((V + E) log V)`. И помни: раз порядков несколько, задача обязана задать
правило разрешения ничьих, иначе «правильных» ответов много (поэтому в тренажёре
топосорт проверяется на *валидность*, а не на точную перестановку).

### Очередь срезом

Как и в [обходах графа](graphs.md): `queue = queue[1:]` не освобождает начало
нижележащего массива — на огромном графе веди индекс головы по фиксированному срезу.

## ⚠️ Типичные ошибки

1. **Путаница in-degree/out-degree** — считайте входящие рёбра, а не исходящие.
2. **Неправильное направление ребра** — `course` зависит от `prerequisite`, поэтому ребро `prerequisite → course`.
3. **Забыта проверка цикла** — если `len(result) != numCourses`, сортировка невозможна.
4. **In-degree обновляется не у тех вершин** — уменьшайте только у прямых соседей текущей.
5. **Несколько источников / компонент** — кладите в очередь сразу все вершины с in-degree 0.
6. **Дубликаты рёбер** безопасны, только пока учтены одинаково и в in-degree, и в списке смежности (тогда лишние +1 и −1 взаимно гасятся). Дедуплицировали одно и забыли другое — вершина никогда не «освободится». Надёжнее отсеять повторы заранее через множество.

> корректный порядок** прохождения всех курсов. Если из-за цикла зависимостей это
> невозможно — верни пустой массив.
> Пример: `numCourses = 4`, `prerequisites = [[1,0],[2,0],[3,1],[3,2]]` → `[0,1,2,3]`
> (0 не зависит ни от кого; 3 — от 1 и 2; оба после 0).

**Шаг 1. Наивно: перебрать все перестановки и проверить — O(n!·E).**

```go
func findOrderNaive(numCourses int, prerequisites [][]int) []int {
    perm := make([]int, numCourses)
    for i := range perm {
        perm[i] = i
    }
    var res []int
    var rec func(k int) bool
    rec = func(k int) bool {
        if k == numCourses {
            pos := make([]int, numCourses)
            for i, c := range perm {
                pos[c] = i
            }
            for _, p := range prerequisites { // [course, prereq]
                if pos[p[1]] >= pos[p[0]] {     // предусловие должно идти раньше
                    return false
                }
            }
            res = append([]int{}, perm...)
            return true
        }
        for i := k; i < numCourses; i++ {
            perm[k], perm[i] = perm[i], perm[k]
            if rec(k + 1) {
                return true
            }
            perm[k], perm[i] = perm[i], perm[k]
        }
        return false
    }
    if rec(0) {
        return res
    }
    return []int{}
}
```

Это **работает и проходит тесты**, но перебирает до `n!` перестановок — уже при `n = 15`
это безнадёжно. Мы угадываем целиком готовый порядок и лишь потом проверяем его, хотя
зависимости можно учитывать **по ходу**, никогда не выбирая курс раньше его предусловий.

**Шаг 2. Ключевое наблюдение.** Курс без невыполненных предусловий — это вершина с
[**входящей степенью 0**](#почему-в-dag-всегда-есть-вершина-с-in-degree--0): его можно
взять прямо сейчас. Взяв его, мы «снимаем» по одному предусловию с каждого зависимого
курса; те, у кого предусловий не осталось, тоже становятся доступны. Перестановки не
нужны — достаточно жадно брать любой доступный курс. А если в какой-то момент
доступных нет, но курсы ещё остались — налицо [взаимный цикл](#почему-lenresult--v--есть-цикл),
и порядок невозможен.

**Шаг 3. Оптимум: алгоритм Кана (BFS по in-degree) — O(V+E).**

```go
func findOrder(numCourses int, prerequisites [][]int) []int {
    graph := make([][]int, numCourses)
    inDegree := make([]int, numCourses)
    for _, p := range prerequisites {
        course, prereq := p[0], p[1]
        graph[prereq] = append(graph[prereq], course) // ребро prereq → course
        inDegree[course]++
    }
    queue := []int{}
    for v := 0; v < numCourses; v++ {
        if inDegree[v] == 0 { // курсы без предусловий — сразу доступны
            queue = append(queue, v)
        }
    }
    order := []int{}
    for len(queue) > 0 {
        u := queue[0]
        queue = queue[1:]
        order = append(order, u)
        for _, w := range graph[u] { // снимаем предусловие у зависимых
            inDegree[w]--
            if inDegree[w] == 0 {
                queue = append(queue, w)
            }
        }
    }
    if len(order) != numCourses {
        return []int{} // остались курсы — цикл, порядок невозможен
    }
    return order
}
```

Прогоните алгоритм Кана на графе курсов: берём вершины с нулевой входящей степенью,
снимаем их рёбра, и так пока не выложим весь порядок:

**Шаг 4. Трассировка** на `numCourses = 4`, `prerequisites = [[1,0],[2,0],[3,1],[3,2]]`
(рёбра `0→1`, `0→2`, `1→3`, `2→3`; стартовые in-degree — `0:0, 1:1, 2:1, 3:2`):

| шаг | взяли `u` | очередь до | обновили in-degree | стало 0 → в очередь | очередь после | `order`       |
|-----|-----------|------------|--------------------|----------------------|---------------|---------------|
| 0   | —         | `[0]`      | старт               | —                    | `[0]`         | `[]`          |
| 1   | 0         | `[0]`      | `1:1→0`, `2:1→0`    | 1, 2                 | `[1,2]`       | `[0]`         |
| 2   | 1         | `[1,2]`    | `3:2→1`             | —                    | `[2]`         | `[0,1]`       |
| 3   | 2         | `[2]`      | `3:1→0`             | 3                    | `[3]`         | `[0,1,2]`     |
| 4   | 3         | `[3]`      | нет соседей         | —                    | `[]`          | `[0,1,2,3]`   |

`len(order) = 4 = numCourses` → возвращаем `[0,1,2,3]`. Каждое предусловие стоит раньше
своего курса (`0` раньше `1` и `2`; `1` и `2` раньше `3`) — порядок валиден. Граф с
циклом, например `[[0,1],[1,2],[2,0]]`, оставит очередь пустой с самого начала
(`in-degree` всех = 1), `len(order) = 0 ≠ 3` → вернётся `[]`. Каждая вершина входит и
выходит из очереди один раз, каждое ребро снимается один раз — **`O(V+E)`**.

> 🧭 **Не пошла задача из основы?** Держись за один факт: Кан — это про **степени входа**.
> Очередь опустела, а вершины остались — значит у них есть неразрешимая зависимость, то есть
> цикл; отдельной проверки на цикл писать не нужно. В 1136 нужны не сами вершины, а **слои**:
> фиксируй размер очереди перед проходом, как в [Tree BFS](tree-bfs.md), — каждый проход и
> есть один семестр. В 310 ощипывают листья **слоями** — все текущие листья разом, — пока не
> останется одна или две вершины. Это не топосорт, а его родственник (тот же Кан, только по
> степеням в неориентированном дереве), а ответ — центры дерева: их **один или два**. Два —
> когда в самом длинном пути нечётное число рёбер; простейший пример — две вершины и одно
> ребро. Код, ждущий ровно одного центра, на нём и ломается.

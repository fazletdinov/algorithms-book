## 🧭 Откуда берётся обход по уровням: выведем его сами

Снимок `levelSize := len(queue)` из карточки — не ритуал. Это ровно то, чего не хватает
обычной очереди, чтобы работать «по уровням». Проследим на задаче из разбора ниже.

> **Задача (Right Side View).** Встань справа от бинарного дерева и выпиши сверху вниз узлы,
> которые видно, — по одному с каждого уровня, самый правый. Здесь ответ — `[1, 3, 4]`.

<div class="algo-fig" data-fig="tree" data-tree="1!(2(_,5),3!(_,4!))" data-caption="5 — правый ребёнок 2, 4 — правый ребёнок 3; синие — видно справа: [1, 3, 4]"></div>

**Первая попытка — идти по правым ссылкам:** `1 → 3 → 4`. Здесь совпало. Но убери узел `4` —
и ответ станет `[1, 3, 5]`: узел `5` висит слева, но правее на его уровне никого нет, и справа
его видно. А проход по правым ссылкам даст `[1, 3]`. Смотреть надо на **весь уровень**.

**Вторая попытка — обычная очередь на срезе, как во «Вспомни» выше:** снимаем узел с
головы, детей кладём в хвост. Узлы выходят в порядке `1, 2, 3, 5, 4` — по уровням, слева
направо. Но где кончается уровень? Когда снимаем `3`, в очереди уже лежит `5` — узел
следующего уровня. Признак «после снятия очередь пуста» срабатывает на `1` и `4`, а `3`
пропускает. Очередь склеила уровни в одну ленту.

**Что чинит.** В начале уровня в очереди лежит ровно он, и никого больше: его дети ещё не
добавлены. Запомни в этот момент `levelSize := len(queue)` и сними ровно столько узлов.
Последний из них (`i == levelSize-1`) — самый правый. Снимки дают `1`, потом `2, 3`, потом
`5, 4` — и в ответ уходят `1`, `3`, `4`.

**Граница между уровнями в очереди уже есть — `levelSize := len(queue)` лишь ставит на ней
засечку, пока в хвост не встали дети.** Этот приём — обход по уровням (level order); путь от
рабочего, но громоздкого DFS со словарём до этого решения, с трассировкой, — в
[«📝 Разбор задачи»](#-разбор-задачи).

## 🎬 Визуализация

> 💡 **Интерактивная демонстрация.** Обход идёт по шаблону ниже: на строке
> `levelSize := len(queue)` очередь содержит ровно текущий уровень (обведён синим). Дети,
> которых кладём в хвост, встают за жёлтую черту в очереди: это уже следующий уровень
> (пунктир на дереве). Сняли `levelSize` узлов — уровень закрыт и уходит в `result`.

## ⚡ Шаблон для собеседования

```go
queue := []*TreeNode{root}
for len(queue) > 0 {
    levelSize := len(queue)       // снимок размера уровня!
    for i := 0; i < levelSize; i++ {
        node := queue[0]
        queue = queue[1:]         // dequeue из начала
        // ... обрабатываем node.Val ...
        if node.Left != nil { queue = append(queue, node.Left) }
        if node.Right != nil { queue = append(queue, node.Right) }
    }
}
```

1. кладём корень в очередь;
2. фиксируем `levelSize` — сколько узлов на текущем уровне;
3. обрабатываем ровно столько, добавляя детей в конец;
4. повторяем, пока очередь не пуста.

## 📖 Разбор

**Tree BFS** (Breadth-First Search) обходит дерево уровень за уровнем: все узлы
уровня `k` обрабатываются прежде, чем алгоритм перейдёт к уровню `k+1`. Узлы хранятся
в **очереди** (FIFO): добавляем в конец, извлекаем из начала — это естественным образом
задаёт порядок «сначала ближние, потом дальние».

<details class="algo-details">
<summary>Полный код обхода по уровням и сложность</summary>

```go
type TreeNode struct {
    Val   int
    Left  *TreeNode
    Right *TreeNode
}

// Обход по уровням: значения узлов, сгруппированные по уровням
func levelOrder(root *TreeNode) [][]int {
    if root == nil {
        return [][]int{}
    }

    queue := []*TreeNode{root}
    result := [][]int{}

    for len(queue) > 0 {
        levelSize := len(queue)               // сколько узлов на текущем уровне
        level := make([]int, 0, levelSize)

        for i := 0; i < levelSize; i++ {
            node := queue[0]
            queue = queue[1:]                 // dequeue из начала
            level = append(level, node.Val)

            if node.Left != nil {             // детей кладём в конец
                queue = append(queue, node.Left)
            }
            if node.Right != nil {
                queue = append(queue, node.Right)
            }
        }

        result = append(result, level)
    }

    return result
}
```

Фиксация `levelSize` до начала внутреннего цикла критична: во время обработки уровня мы
добавляем детей в ту же очередь, и без снимка размера границы уровней «съедут».

#### Сложность

| Метрика | Значение                                        |
|---------|--------------------------------------------------|
| Время   | O(n) — каждый узел добавляется и извлекается один раз |
| Память  | O(w), где w — максимальная ширина дерева (до n/2) |

</details>

## 🧠 Почему это корректно

### Почему уровни не «съезжают»

В момент снимка `levelSize := len(queue)` очередь содержит **ровно узлы текущего
уровня**. Извлекая именно столько, мы опустошаем уровень, а добавленные за это время
дети образуют **следующий** уровень — и попадут в свой снимок на следующей итерации.
Без фиксации размера дети текущего уровня смешались бы с ним, и границы поехали.

### Почему дереву не нужен `visited`

В отличие от [BFS по графу](graphs.md), дереву не нужна пометка посещённого: в дереве
**нет циклов** и у каждого узла ровно один родитель, поэтому повторно в узел не зайти.
Первое достижение узла — на его минимальной глубине, поэтому BFS естественно решает
задачи на минимальную глубину и «вид сбоку».

### Очередь монотонна по глубине

Под обоими фактами выше лежит один инвариант: **очередь всегда содержит узлы не более чем
двух соседних глубин `d` и `d+1`, причём все `d` идут раньше всех `d+1`.** По индукции:
старт — корень (глубина 0); извлекаем узлы по неубывающей глубине, а их детей (глубина
`+1`) кладём в хвост. Значит порядок извлечения **монотонен по глубине**, и первое
извлечение любого узла приходится на его минимальную глубину. Отсюда и «не нужен
`visited`», и корректность `levelSize`-снимка: граница между `d` и `d+1` в очереди
существует физически, мы лишь отрезаем по ней ровно `len(queue)` узлов.

## ⚙️ Цена на практике

### Память `O(w)` против `O(h)` у DFS

BFS держит в очереди целый уровень — до `~n/2` узлов в последнем уровне полного дерева
(`O(w)`, ширина). [DFS](tree-dfs.md) тратит `O(h)` (высота). Поэтому: широкое мелкое
дерево дешевле обходить DFS, а узкие задачи «по уровням / ближайший узел» — это BFS.

### BFS даёт кратчайший путь по рёбрам

Монотонность очереди по глубине — это не только про деревья: на **невзвешенном** графе тот
же FIFO-обход достигает каждой вершины путём из минимального числа рёбер. Поэтому
*Minimum Depth*, *Right Side View* и «ближайший узел с условием» — естественно BFS, а на
графах BFS = кратчайший путь за `O(V+E)` без всякой кучи (см.
[сетки и кратчайшие пути](grids-and-shortest-paths.md)). [DFS](tree-dfs.md) находит
*какой-то* путь, но не кратчайший — выбор обхода диктуется тем, нужна ли тебе именно
**длина/расстояние** ответа.

### Очередь срезом

`queue = queue[1:]` не освобождает начало нижележащего массива (как и в
[графах](graphs.md)) — на огромных деревьях веди индекс головы по фиксированному срезу.

## ⚠️ Типичные ошибки

1. **Не зафиксирован размер уровня** — `levelSize` нужно взять до внутреннего цикла,
   иначе добавленные дети попадут в текущий уровень.
2. **Добавление nil в очередь** — проверяйте `node.Left != nil` и `node.Right != nil`
   перед `append`, иначе при dequeue получите разыменование nil.
3. **Не обработан пустой корень** — при `root == nil` возвращайте `[][]int{}`, не входя в цикл.
4. **Извлечение не из того конца** — BFS требует FIFO (`queue[0]`); чтение с конца
   превратит обход в DFS.
5. **DFS вместо BFS для уровней** — рекурсия с передачей уровня тоже даёт группировку,
   но BFS нагляднее и гарантирует порядок слева направо без лишней логики.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он неуклюж, и
только потом естественное BFS-решение.

> **Задача (Right Side View).** Дан корень бинарного дерева. Вернуть значения узлов,
> **видимых справа**, сверху вниз — то есть по одному с каждого уровня: самый правый.
> Пример: дерево `[1, 2,3, null,5, null,4]` →
>
> ```text
>        1
>       / \
>      2   3
>       \   \
>        5   4
> ```
>
> Ответ — `[1, 3, 4]` (с правого бока видно `1`, `3`, `4`).

**Шаг 1. Наивно: DFS со словарём `уровень → значение` — O(n), но громоздко.**

```go
func rightSideViewDFS(root *TreeNode) []int {
    last := map[int]int{} // последнее значение, увиденное на каждой глубине
    maxDepth := -1

    var dfs func(node *TreeNode, depth int)
    dfs = func(node *TreeNode, depth int) {
        if node == nil {
            return
        }
        last[depth] = node.Val      // правое поддерево перезапишет левое
        if depth > maxDepth {
            maxDepth = depth
        }
        dfs(node.Left, depth+1)
        dfs(node.Right, depth+1)    // правое — после левого, оно и останется
    }
    dfs(root, 0)

    res := make([]int, 0, maxDepth+1)
    for d := 0; d <= maxDepth; d++ {
        res = append(res, last[d])
    }
    return res
}
```

Это **работает и проходит тесты**: обходим левое поддерево раньше правого, поэтому в
`last[depth]` остаётся самый правый узел уровня. Но платим за это лишним: `map` с
аллокацией и хешированием, отдельный учёт `maxDepth`, второй проход для сборки ответа в
правильном порядке. А ведь нужный нам объект — «последний узел уровня» — у BFS и так
лежит на ладони.

**Шаг 2. Ключевое наблюдение.** BFS извлекает узлы строго по уровням и **слева направо**
(см. [«Очередь монотонна по глубине»](#очередь-монотонна-по-глубине)). Значит, внутри
снимка `levelSize` последний извлечённый узел (`i == levelSize-1`) — это в точности
самый правый узел уровня. Никакой словарь, `maxDepth` и второй проход не нужны: правый
узел приходит сам, ровно в момент, когда мы закрываем уровень.

**Шаг 3. Оптимум: BFS по уровням, берём последний узел каждого уровня — O(n).**

```go
func rightSideView(root *TreeNode) []int {
    if root == nil {
        return []int{}
    }
    res := []int{}
    queue := []*TreeNode{root}

    for len(queue) > 0 {
        levelSize := len(queue)               // снимок размера уровня!
        for i := 0; i < levelSize; i++ {
            node := queue[0]
            queue = queue[1:]                 // dequeue из начала
            if i == levelSize-1 {             // последний на уровне = видимый справа
                res = append(res, node.Val)
            }
            if node.Left != nil {
                queue = append(queue, node.Left)
            }
            if node.Right != nil {
                queue = append(queue, node.Right)
            }
        }
    }
    return res
}
```

Один проход, память — `O(w)` под очередь, ответ копится сразу в нужном порядке.

Прогоните обход по уровням: очередь набирает всех детей уровня, и последний снятый с
уровня узел — это и есть видимый справа:

**Шаг 4. Трассировка** на `[1, 2,3, null,5, null,4]` (в скобках помечен узел, попадающий в ответ как последний на уровне):

| Уровень | Очередь в начале | Извлекаем (слева→направо) | Последний (`i==levelSize-1`) | Дети в хвост | `res` |
|---------|------------------|---------------------------|------------------------------|--------------|-------|
| 0       | `[1]`            | `1`                       | **`1`**                      | `2, 3`       | `[1]` |
| 1       | `[2, 3]`         | `2`, `3`                  | **`3`**                      | `5` (от 2), `4` (от 3) | `[1, 3]` |
| 2       | `[5, 4]`         | `5`, `4`                  | **`4`**                      | —            | `[1, 3, 4]` |

Очередь опустела — ответ `[1, 3, 4]`. На каждом уровне в `res` уходит ровно один узел,

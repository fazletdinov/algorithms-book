## 🧭 Откуда берётся подсчёт снизу вверх: выведем его сами

В главе два урока. Первый — три момента записи узла — простой: он целиком в шаблоне и в трёх
порядках обхода под ним. Второй — ответ узла из ответов детей — и есть то, что спрашивают; начнём с
него. Запись «после детей» (post-order) — не просто третий порядок обхода. Это способ **не
считать одно и то же дважды**. Проследим на диаметре дерева.

> **Задача (диаметр дерева).** Найти самый длинный путь между двумя любыми узлами — в рёбрах.
> Путь не обязан проходить через корень. Здесь ответ — `4`.

<div class="algo-fig" data-fig="tree" data-tree="1(2!(4!(6!,_),5!(_,7!)),3)" data-caption="6 — левый ребёнок 4, 7 — правый ребёнок 5; синие — самый длинный путь 6→4→2→5→7, 4 ребра, поворот в 2"></div>

**Как решает человек.** У любого пути есть верхняя точка — узел, где он поворачивает. Самый
длинный путь с поворотом в узле — высота его левого поддерева плюс высота правого: высоту
считаем в узлах, а `l` узлов слева — это ровно `l` рёбер от поворота вниз. Значит, в каждом
узле отдельно посчитать две высоты. Лучший путь — 4 ребра, например с поворотом в узле `2`:
слева высота `2` (`4, 6`), справа `2` (`5, 7`), путь `6→4→2→5→7`.

У `nil` высота 0, у палки из n узлов — n, как в [главе о BST](bst-structure.md). Эту высоту на
LeetCode зовут максимальной глубиной (Maximum Depth) — это одно и то же число.

**Где повтор.** Узел `1` спрашивает высоту поддерева `2` — и `height` обходит `2, 4, 6, 5, 7`,
по дороге узнав высоты `4` и `5`. Потом узел `2` спрашивает их же — и обходит `4, 6, 5, 7`
заново. Потом узел `4` — снова `6`. Узлы `6` и `7` обойдены трижды, а всего `height` делает
12 заходов на 7 узлах. На «палке» (у каждого узла один ребёнок) это уже `O(n²)`: на палке из
шести узлов — 15 заходов.

**Что чинит.** Высоту узел узнаёт, когда дети уже вернули свои: `l` и `r`. В этот момент у него
на руках и путь через себя — `l + r`. Значит, хватит **одного** обхода: наверх отдаём высоту
`1 + max(l, r)`, а `l + r` сравниваем с лучшим ответом, который копим сбоку. 7 заходов вместо 12.

**Узел отдаёт наверх высоту, а диаметр записывает сбоку — один обход вместо обхода на каждый
узел.** Этот приём — подсчёт снизу вверх (post-order DFS) с ответом в общей переменной. Перебор
и один проход кодом, оба на виджетах, и трассировка — в [«📝 Разбор задачи»](#-разбор-задачи).

## 🎬 Визуализация

> 💡 **Интерактивная демонстрация (preorder).** Узлы подсвечиваются в порядке обхода в глубину:
> корень → левое поддерево → правое (синий — текущий, зелёные — посещённые). Бледные листья `nil`
> — пустые потомки: рекурсия заходит и в них, срабатывает `if node == nil { return }`, и такой
> вызов на рисунке подсвечен янтарным пунктиром. Под холстом — строка шага и переменные, ниже — ползунок шагов (или ←/→ на клавиатуре) и код с подсветкой строки. Можно подставить своё дерево
> (уровни, `null` = пусто) и нажать «⟲ Запустить».

## ⚡ Шаблон для собеседования

```go
var dfs func(*TreeNode)
dfs = func(node *TreeNode) {
    if node == nil { // базовый случай — всегда первым
        return
    }
    // preorder:  обработать node.Val ЗДЕСЬ
    dfs(node.Left)
    // inorder:   ... или ЗДЕСЬ
    dfs(node.Right)
    // postorder: ... или ЗДЕСЬ
}
dfs(root)
```

1. база: `node == nil → return`;
2. место `append(node.Val)` задаёт тип обхода;
3. рекурсия в левое и правое поддерево;
4. для очень глубоких деревьев — итеративный обход со стеком.

Для дерева из виджета выше (`1,2,3,4,5,null,6`) три места записи дают три порядка. Виджет
показывает первый:

```text
Pre-order   1 → 2 → 4 → 5 → 3 → 6   (корень → левое → правое)
In-order    4 → 2 → 5 → 1 → 3 → 6   (левое → корень → правое)
Post-order  4 → 5 → 2 → 6 → 3 → 1   (левое → правое → корень)
```

## 📖 Разбор

**Обход в глубину** (Depth-First Search, DFS) идёт вглубь по каждой ветви до конца, прежде чем
вернуться и перейти к следующей. Рекурсивная природа дерева (корень + поддеревья)
естественно ложится на рекурсию; неявный стек вызовов хранит путь от корня. Порядок
обработки корня относительно поддеревьев задаёт три варианта обхода:

- **Pre-order**: корень → левое → правое (копирование дерева, путь от корня);
- **In-order**: левое → корень → правое (для BST даёт **отсортированную** последовательность);
- **Post-order**: левое → правое → корень (высота, сумма, удаление дерева — узлу нужны дети).

In-order ты уже писал в главе о BST — [шесть строк рекурсии](bst-structure.md#-in-order--отсортированный-порядок).
Два других обхода — тот же код, переезжает одна строка `append`: в pre-order она стоит до
обоих рекурсивных вызовов, в post-order — после обоих.

**Вниз — параметром, наверх — возвратом.** Информация в обходе ходит в две стороны. Что
узлу нужно знать от предков (узлов на пути от корня до него) — остаток суммы, допустимые границы, путь от корня, —
передавай вниз параметром: каждый вызов получает свою копию числа. Что родителю нужно от
поддерева — высота, найденный узел, «есть ли там путь», — возвращай наверх. Если вниз
несёшь общий срез-путь, после возврата из узла убери его из пути: соседняя ветвь не должна
видеть чужой узел.

Пример границ — проверка дерева поиска (Validate BST).
Дерево `5(3(_,6),8)` (запись «узел(левый, правый)», `_` — нет ребёнка): у `3` правый ребёнок
`6 > 3`, локально всё верно, но `6` лежит слева от `5` и обязан быть меньше `5`. Границы это
ловят: от `5` влево — `hi = 5`, от `3` вправо — `lo = 3`; `6` вне `(3, 5)`.

**Два ответа в одном числе: −1 как сигнал.** Сбалансированное дерево (Balanced Binary Tree) — в
каждом узле высоты левого и правого поддеревьев отличаются не больше чем на 1. Узлу нужны высоты
детей — значит, считаем снизу вверх, как диаметр. Но родителю надо узнать и второе: нет ли
нарушения где-то ниже. Заводить второе возвращаемое значение не обязательно: высота не бывает
отрицательной, поэтому `−1` свободно и значит «внизу уже нарушено». На дереве `1(2(3(4),_),5)`:
`4` отдаёт 1, `3` — `1 + max(1, 0) = 2`, а у `2` слева 2, справа 0 — разница 2, и `2` отдаёт `−1`.
Корень, получив `−1` слева, сразу отдаёт `−1` дальше — в `5` он даже не спускается. Ответ —
`height(root) >= 0`. Без сигнала пришлось бы в каждом узле заново считать высоты поддеревьев —
тот же повтор работы, что у перебора диаметра в «🧭».

**Пара узлов вместо одного: зеркало.** Симметричное дерево (Symmetric Tree) — левое поддерево
корня зеркально правому. Одним узлом это не проверить: рекурсия идёт по ПАРАМ `(a, b)`. Пара
зеркальна, если значения равны, `a.Left` зеркален `b.Right`, а `a.Right` — `b.Left`: внешние
внуки сравниваются с внешними, внутренние — с внутренними. База — пара, где хотя бы один `nil`:
зеркальна, только если `nil` оба. Частая ошибка — сравнивать `a.Left` с `b.Left`: так
проверяется, что поддеревья одинаковые, а не зеркальные.

**Две рекурсии: обход и сверка целиком.** Поддерево другого дерева (Subtree of Another Tree) —
есть ли в дереве `root` поддерево, совпадающее с `sub` формой и значениями. Поддерево — это узел
вместе со *всеми* потомками, поэтому совпасть должен весь низ, до листьев. Сравнить два дерева
целиком умеет Same Tree из разогрева: та же рекурсия по парам, что у зеркала, только `a.Left`
идёт в пару с `b.Left`. Остаётся обойти `root` и в каждом узле спросить: не отсюда ли
начинается копия `sub`?

```go
func isSubtree(root, sub *TreeNode) bool {
    if root == nil {
        return sub == nil
    }
    return sameTree(root, sub) || // копия начинается здесь?
        isSubtree(root.Left, sub) || isSubtree(root.Right, sub)
}
```

На `root = 3(4(1, 2), 5)` и `sub = 4(1, 2)` сверка в узле `3` падает сразу (`3 ≠ 4`), а в узле
`4` совпадает всё — ответ «да». Добавь узлу `2` ребёнка `0` — и сверка в `4` дойдёт до него и
упадёт: под `4` уже не то же, что в `sub`. Цена: в каждом из n узлов `root` сверка может пройти
до m узлов `sub` — O(n·m). Для собеседования этого хватает; быстрее — записать каждое поддерево
строкой или хешем и сравнивать их, но это уже за пределами главы.

## 🧰 Два приёма поверх обхода — после основы

Основа главы — выше: ответ узла из ответов детей и путь вниз параметром. Дальше две задачи
добивки, где обход — только каркас, а решает дополнительная идея.

### Дерево по двум обходам

Задача Construct Binary Tree from Preorder and Inorder Traversal: даны `preorder` и `inorder`
одного дерева, все значения различны; восстанови дерево. Возьмём `preorder = [3, 9, 20, 15, 7]`
и `inorder = [9, 3, 15, 20, 7]`.

- Pre-order начинается с корня — значит, корень `3`.
- В in-order всё левое поддерево стоит до корня, всё правое — после. `3` стоит на месте 1:
  слева `[9]` — левое поддерево, справа `[15, 20, 7]` — правое.
- Pre-order после корня перечисляет сначала всё левое поддерево, потом всё правое. Следующий в
  нём, `9`, — корень левого; за ним `20` — корень правого. В куске `[15, 20, 7]` значение `20`
  делит его на `15` слева и `7` справа.

Вышло `3(9, 20(15, 7))`. Каждый шаг — то же самое на меньшем куске, то есть рекурсия. Кусок
in-order задаём границами `lo..hi`, а корни берём из pre-order по очереди общим счётчиком `next`:
pre-order как раз в порядке построения — корень, всё левое, всё правое.

Где найти корень в in-order? Проходом по куску — до n шагов на узел, а на дереве-цепочке кусок
сжимается на один узел за раз: `n + (n−1) + … ≈ n²/2` шагов. Значения различны, поэтому место
каждого заранее записываем в `map` «значение → позиция»: один проход по `inorder`, дальше каждый
поиск за O(1), и всё построение — O(n).

```go
func buildTree(preorder, inorder []int) *TreeNode {
    pos := make(map[int]int, len(inorder))
    for i, v := range inorder {
        pos[v] = i // место каждого значения в in-order
    }
    next := 0 // следующий корень в pre-order
    var build func(lo, hi int) *TreeNode
    build = func(lo, hi int) *TreeNode {
        if lo > hi {
            return nil // пустой кусок — пустое поддерево
        }
        node := &TreeNode{Val: preorder[next]}
        next++
        mid := pos[node.Val]
        node.Left = build(lo, mid-1) // левое — первым: так идёт pre-order
        node.Right = build(mid+1, hi)
        return node
    }
    return build(0, len(inorder)-1)
}
```

Порядок двух вызовов важен: pre-order перечисляет левое поддерево раньше правого, и если строить
правое первым, `next` раздаст ему корни левого. Глубина рекурсии — высота дерева: на цепочке из
10⁵ узлов это 10⁵ кадров, стеку Go по силам (раздел [«Стек O(h)»](#стек-oh--риск-на-вырожденном-дереве)).

### Пути с суммой из любого узла: префиксные суммы на пути от корня

Задача Path Sum III: сколько путей с суммой `target`, если путь идёт только вниз, но начинается
и кончается в любом узле. Перебор — из каждого узла пройти вниз, считая сумму, — на цепочке из n
узлов стоит `n + (n−1) + … ≈ n²/2` шагов.

Идея: путь от корня до текущего узла — обычный массив. Путь вниз, кончающийся в текущем узле, —
кусок этого массива, кончающийся в его конце. А «сколько кусков с суммой k кончается здесь» уже
решено в главе о префиксных суммах — [префикс + хеш-таблица](prefix-sums.md#подсчёт-подмассивов-префикс--хеш-таблица):
если накопленная от корня сумма здесь `sum`, кусок имеет сумму `target`, когда выше по пути
встречалась накопленная сумма `sum − target`. В `map` храним, сколько раз встречалась каждая.

Новое по сравнению с массивом одно — **откат**. Уходя из узла обратно вверх, убери его сумму из
`map`: соседняя ветвь не лежит под этим узлом, и его сумма ей не начало пути. Это тот же откат,
что у среза `path` в Path Sum II.

```go
func countPaths(root *TreeNode, target int) int {
    seen := map[int]int{0: 1} // пустой префикс: путь от самого корня
    count := 0
    var dfs func(node *TreeNode, sum int)
    dfs = func(node *TreeNode, sum int) {
        if node == nil {
            return
        }
        sum += node.Val
        count += seen[sum-target] // куски с суммой target, кончающиеся здесь
        seen[sum]++
        dfs(node.Left, sum)
        dfs(node.Right, sum)
        seen[sum]-- // откат: соседней ветви эта сумма не префикс
    }
    dfs(root, 0)
    return count
}
```

Прогон на дереве `1(2, 3)` с `target = 1` (верный ответ — один путь, сам корень `1`):

- узел `1`: `sum = 1`, ищем `1 − 1 = 0` — пустой префикс есть, `count = 1`; записали сумму `1`;
- узел `2`: `sum = 3`, ищем `2` — нет; записали `3`, на возврате стёрли;
- узел `3`: `sum = 4`, ищем `3` — нет, `count` остался `1`.

Без отката на узле `3` нашлась бы сумма `3` от соседа, и `count` стал бы `2` — «путь» `2 → 3`,
которого в дереве нет. Каждый узел — O(1) работы с `map`: всего O(n) по времени и памяти.

## 🧠 Почему это корректно

### Рекурсия — это неявный стек пути

Стек вызовов хранит путь от корня до текущего узла, поэтому его глубина не больше высоты
дерева `h` — отсюда память `O(h)`. Как и [дереву в BFS](tree-bfs.md), DFS **не нужна пометка посещённых узлов** (`visited`): нет циклов, один родитель.

### Порядок обхода выбирают по зависимости данных

Три обхода отличаются лишь моментом записи — но выбор не косметический, а по тому,
**когда результат узла готов**:

- **in-order на BST даёт отсортированную последовательность** — потому что по инварианту
  BST всё левое поддерево `<` узла `<` всего правого; записав левое → узел → правое,
  получаем возрастание;
- **post-order** — когда результат узла зависит от детей (сумма/высота поддерева,
  удаление: сначала освободить детей);
- **pre-order** — когда родителя надо обработать до детей (сериализация, то есть запись дерева в строку; копирование;
  путь от корня).

Подбор обхода под зависимость — и есть инженерная часть, а не «какой попало».

### Почему обход линеен по времени

DFS посещает каждый узел **ровно раз** и проходит каждое ребро дважды — вниз (вызов
`dfs(child)`) и вверх (возврат из него). Узлов `n`, рёбер `n−1` — у каждого узла, кроме корня,
ровно одно ребро к родителю; на узел — `O(1)` работы
(запись значения, два рекурсивных вызова), поэтому суммарно `O(n)`. Это тот же
«посчитай по рёбрам» аргумент, что и у [BFS](tree-bfs.md): обходы дерева линейны, потому
что структура без циклов не даёт зайти в узел повторно.

## ⚙️ Цена на практике

### Стек `O(h)` — риск на вырожденном дереве

Сбалансированное дерево → `O(log n)` стека, но палка → `O(n)`. В Go это прежде всего память:
стек горутины растёт сам, и миллион уровней он выдерживает, а падает только около 10⁷ (ниже —
цифры). Когда глубина может дойти до таких чисел или память стека надо держать под контролем —
итеративный обход с явным стеком `[]*TreeNode`. Для preorder он почти дословно повторяет рекурсию — стек вызовов просто
становится срезом:

```go
stack := []*TreeNode{root}
for len(stack) > 0 {
    node := stack[len(stack)-1]
    stack = stack[:len(stack)-1]                 // pop с вершины
    if node == nil {
        continue                                 // та же база, что и в рекурсии
    }
    // обработать node.Val (preorder)
    stack = append(stack, node.Right, node.Left) // левый сверху — выйдет первым
}
```

Порядок тот же, что у рекурсивного preorder, но глубина ограничена лишь памятью процесса.

In-order итеративно чуть хитрее: узел нельзя записать, пока не пройдено всё его левое
поддерево. Поэтому сначала спускаемся влево до упора, складывая путь в стек, — это ровно те
вызовы, что рекурсия держала бы на стеке в ожидании левого ребёнка. Потом снимаем верхний узел,
записываем его и переходим в его правое поддерево — там всё повторяется:

```go
var stack []*TreeNode
cur := root
for cur != nil || len(stack) > 0 {
    for cur != nil { // спуск влево: путь — в стек
        stack = append(stack, cur)
        cur = cur.Left
    }
    cur = stack[len(stack)-1] // левее никого — пора записать
    stack = stack[:len(stack)-1]
    // обработать cur.Val (inorder)
    cur = cur.Right // дальше — правое поддерево
}
```

На дереве `1(2(4, 5), 3)` стек растёт до `1, 2, 4`, выдаёт `4` и `2`, уходит в `5` и выдаёт её,
затем `1` и `3` — те же `4, 2, 5, 1, 3`, что у рекурсии.

В Go каждый рекурсивный вызов занимает кадр стека — даже хвостовой, стоящий последним в
функции: компилятор не превращает его в цикл. Стек горутины растёт сам, но до предела (порядка
гигабайта). Замер: рекурсивный диаметр на палке из 10⁶ узлов — 0,1 с, из 5·10⁶ — 0,4 с, без
падения; около 10⁷ уровней стек упирается в предел 1 ГБ, и программа падает с `fatal error: stack
overflow` (подробнее — в главе о графах, [«Глубина рекурсии DFS»](graphs.md#глубина-рекурсии-dfs--цена-и-предел)).
Так что на собеседовании рекурсия по дереву — нормальный ответ; явный стек — когда глубина
бывает 10⁷ и больше или когда спрашивают про память. В языках с маленьким стеком (C, Java по
умолчанию) предел наступает на порядки раньше.

### Агрегат: возврат значения против общей переменной

Считая что-то по дереву (сумма, высота, диаметр), есть два стиля: **возвращать** результат
снизу вверх (чистая функция, post-order) или копить в **общей переменной**/замыкании. Для
простых сумм возврат чище и без побочных эффектов; но когда узлу нужны сразу несколько
величин от детей (диаметр — высота левого плюс высота правого, а наверх отдаём только
высоту), удобнее вернуть одно значение, а ответ копить в переменной снаружи. Выбор —
читаемость против необходимости: не тащи через возврат то, что проще накопить сбоку.

> 🔧 **Где это в Go.** DFS-обход дерева зашит в инструменты, которыми ты пользуешься каждый день:
> [`ast.Inspect`/`ast.Walk`](https://pkg.go.dev/go/ast#Inspect) обходят синтаксическое дерево твоего
> кода в порядке обхода в глубину — так устроены многие линтеры и генераторы кода;
> [`filepath.WalkDir`](https://pkg.go.dev/path/filepath#WalkDir) — DFS по дереву каталогов (с
> `SkipDir` в роли отсечения ветви). Написал обход бинарного дерева — понимаешь, как линтер
> ходит по твоему коду.

## ⚠️ Типичные ошибки

1. **Забыт базовый случай** — без проверки `node == nil` рекурсия разыменует nil-указатель.
2. **Неправильный момент записи узла** — место `append` относительно `dfs(node.Left)` и
   `dfs(node.Right)` определяет тип обхода; перепутали — получили не тот порядок.
3. **Забыли, что глубина — это память** — вырожденное в список дерево даёт глубину n: в Go до
   ~10⁶ это лишь мегабайты стека, но к 10⁷ программа падает; при такой глубине — итеративный
   обход со стеком.
4. **Перезаписали ссылку, которая ещё нужна** — менять дерево в обходе можно (Invert Binary
   Tree из разогрева так и делает), но после присваивания `node.Left`/`node.Right` рекурсия
   пойдёт уже по новой ссылке. Прежнего ребёнка, если он ещё понадобится, сначала обойди
   или сохрани в переменную — иначе одно поддерево будет пройдено дважды, а другое ни разу.
5. **Неверная инициализация для путей** — при максимальной сумме пути с отрицательными
   значениями начинай с `math.MinInt`, а не с 0.

> 🌍 **Где это в настоящем коде**
>
> - [`ast.Walk`](https://github.com/golang/go/blob/go1.24.0/src/go/ast/walk.go#L33) (Go 1.24) — обход синтаксического дерева Go-кода в глубину: сначала узел, потом рекурсивно его дети. На нём стоит `ast.Inspect`.
> - [`walkDir`](https://github.com/golang/go/blob/go1.24.0/src/path/filepath/path.go#L309) (Go 1.24) — сердце `filepath.WalkDir`: обработать каталог, затем рекурсивно каждого ребёнка; `SkipDir` отрезает ветку.

## 📝 Разбор задачи

Задача — диаметр дерева из [«🧭»](#-откуда-берётся-подсчёт-снизу-вверх-выведем-его-сами):
перебор и наблюдение — там; здесь код и трасса.

Перебор из «🧭» кодом — для каждого узла отдельно считать высоту поддеревьев, O(n²):

```go
func height(node *TreeNode) int {
    if node == nil {
        return 0
    }
    return 1 + max(height(node.Left), height(node.Right))
}

func diameterNaive(root *TreeNode) int {
    if root == nil {
        return 0
    }
    through := height(root.Left) + height(root.Right) // путь через текущий узел
    left := diameterNaive(root.Left)                  // или целиком в поддереве
    right := diameterNaive(root.Right)
    return max(through, max(left, right))
}
```

Это **работает и проходит тесты**, но медленно. Ниже — перебор из «🧭» на палке из шести
узлов: для каждого узла вызываем отдельный `height()`, который обходит всё поддерево. Под
узлом — сколько раз его уже обошла `height()`; жёлтым — повторный обход. Нижний узел
пересчитают пять раз, всего выйдет 15 визитов на 6 узлах (`n(n−1)/2`), а один проход ниже
обходится ровно шестью:

**Один проход: высота наверх, путь `l + r` — в общий максимум, O(n).** Ответ копим сбоку,
как в разделе [«Агрегат»](#агрегат-возврат-значения-против-общей-переменной).

```go
func diameterOfTree(root *TreeNode) int {
    best := 0
    var height func(*TreeNode) int
    height = func(node *TreeNode) int {
        if node == nil {
            return 0
        }
        l := height(node.Left)
        r := height(node.Right)
        if l+r > best { // путь через node = l + r рёбер
            best = l + r
        }
        return 1 + max(l, r) // наверх отдаём свою высоту
    }
    height(root)
    return best
}
```

Прогони обход в глубину: DFS уходит до листьев и возвращает высоты снизу вверх —
диаметр обновляется попутно в каждом узле как «левая высота + правая высота». Дерево то же,
что в трассировке ниже, `1(2(4(6),5(_,7)),3)` — запись «узел(левый, правый)», `_` — нет ребёнка:

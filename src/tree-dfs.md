## 🎬 Визуализация

> 💡 **Интерактивная демонстрация (preorder).** Узлы подсвечиваются в порядке обхода в глубину:
> корень → левое поддерево → правое (синий — текущий, зелёные — посещённые). Справа — код с
> подсветкой строки и переменные, внизу — кликабельные шаги. Можно подставить своё дерево
> (уровни, `null` = пусто) и нажать «⟲ Запустить». (Виджет работает в собранной книге
> `mdbook serve`/`mdbook build`, а не при просмотре `.md` на GitHub.)

## ⚡ Шаблон для собеседования

```go
var dfs func(*TreeNode)
dfs = func(node *TreeNode) {
    if node == nil { // базовый случай — всегда первым
        return
    }
    // preorder:  обработать node.Val ЗДЕСЬ
    dfs(node.Left)
    // inorder:   ... или ЗДЕСЬ
    dfs(node.Right)
    // postorder: ... или ЗДЕСЬ
}
dfs(root)
```

1. база: `node == nil → return`;
2. место `append(node.Val)` задаёт тип обхода;
3. рекурсия в левое и правое поддерево;
4. для очень глубоких деревьев — итеративный обход со стеком.

## 📖 Разбор

<details class="algo-details">
<summary>Теория, три обхода (pre/in/post-order) и сложность</summary>

**Tree DFS** (Depth-First Search) идёт вглубь по каждой ветви до конца, прежде чем
вернуться и перейти к следующей. Рекурсивная природа дерева (корень + поддеревья)
естественно ложится на рекурсию; неявный стек вызовов хранит путь от корня. Порядок
обработки корня относительно поддеревьев задаёт три варианта обхода:

- **Pre-order**: корень → левое → правое (копирование дерева, префиксные выражения);
- **In-order**: левое → корень → правое (для BST даёт **отсортированную** последовательность);
- **Post-order**: левое → правое → корень (удаление дерева, постфиксные выражения).

Все три обхода отличаются только моментом записи `node.Val` относительно рекурсивных
вызовов.

```go
type TreeNode struct {
    Val   int
    Left  *TreeNode
    Right *TreeNode
}

// Pre-order: корень → левое → правое
func preorderTraversal(root *TreeNode) []int {
    result := []int{}
    var dfs func(*TreeNode)
    dfs = func(node *TreeNode) {
        if node == nil {
            return
        }
        result = append(result, node.Val) // обрабатываем ДО рекурсии
        dfs(node.Left)
        dfs(node.Right)
    }
    dfs(root)
    return result
}

// In-order: левое → корень → правое
func inorderTraversal(root *TreeNode) []int {
    result := []int{}
    var dfs func(*TreeNode)
    dfs = func(node *TreeNode) {
        if node == nil {
            return
        }
        dfs(node.Left)
        result = append(result, node.Val) // обрабатываем МЕЖДУ рекурсиями
        dfs(node.Right)
    }
    dfs(root)
    return result
}

// Post-order: левое → правое → корень
func postorderTraversal(root *TreeNode) []int {
    result := []int{}
    var dfs func(*TreeNode)
    dfs = func(node *TreeNode) {
        if node == nil {
            return
        }
        dfs(node.Left)
        dfs(node.Right)
        result = append(result, node.Val) // обрабатываем ПОСЛЕ рекурсии
    }
    dfs(root)
    return result
}
```

Для дерева выше три обхода дают:

```
Pre-order  (корень→левое→правое):  1 → 2 → 4 → 5 → 3 → 6
In-order   (левое→корень→правое):  4 → 2 → 5 → 1 → 6 → 3
Post-order (левое→правое→корень):  4 → 5 → 2 → 6 → 3 → 1
```

Для очень глубоких деревьев рекурсия рискует переполнить стек — тогда используют
итеративный обход с явным стеком `[]*TreeNode`.

#### Сложность

| Метрика | Значение                                                  |
|---------|------------------------------------------------------------|
| Время   | O(n) — каждый узел посещается один раз                     |
| Память  | O(h), где h — высота дерева (O(log n) сбалансированное, O(n) линейное) |

</details>

## 🧠 Почему это корректно

### Рекурсия — это неявный стек пути

Стек вызовов хранит путь от корня до текущего узла, глубина — `O(h)`. Как и
[дереву в BFS](tree-bfs.md), DFS **не нужен `visited`**: нет циклов, один родитель.

### Порядок обхода выбирают по зависимости данных

Три обхода отличаются лишь моментом записи — но выбор не косметический, а по тому,
**когда результат узла готов**:

- **in-order на BST даёт отсортированную последовательность** — потому что по инварианту
  BST всё левое поддерево `<` узла `<` всего правого; записав левое → узел → правое,
  получаем возрастание;
- **post-order** — когда результат узла зависит от детей (сумма/высота поддерева,
  удаление: сначала освободить детей);
- **pre-order** — когда родителя надо обработать до детей (сериализация, копирование,
  путь от корня).

Подбор обхода под зависимость — и есть инженерная часть, а не «какой попало».

### Почему обход линеен по времени

DFS посещает каждый узел **ровно раз** и проходит каждое ребро дважды — вниз (вызов
`dfs(child)`) и вверх (возврат из него). Узлов `n`, рёбер `n−1`, на узел — `O(1)` работы
(запись значения, два рекурсивных вызова), поэтому суммарно `O(n)`. Это тот же
«посчитай по рёбрам» аргумент, что и у [BFS](tree-bfs.md): обходы дерева линейны, потому
что структура без циклов не даёт зайти в узел повторно.

## ⚙️ Цена на практике

### Стек `O(h)` — риск на вырожденном дереве

Сбалансированное дерево → `O(log n)` стека, но «бамбук» (список) → `O(n)` и **риск
переполнения**. На потенциально вырожденных деревьях — итеративный обход с явным стеком
`[]*TreeNode`. Совсем без доп. памяти (`O(1)`) обходит дерево алгоритм **Морриса**
(временное «прошивание» ссылок) — продвинутый вариант, когда память критична.

### Go не оптимизирует хвостовую рекурсию

Важная Go-специфика: компилятор Go **не делает** tail-call optimization. Даже если
рекурсивный вызов стоит последним, он всё равно занимает кадр стека — переписать DFS
«в хвостовую форму» проблему глубины не решит. Спасает либо явный стек, либо то, что
горутины растят стек динамически (старт ~8 КБ, расширяется до гигабайта), так что предел
выше, чем у фиксированного стека C, но он есть. Когда глубина может быть `O(n)` на
миллионах узлов — переходи на итеративный обход, не надейся на оптимизацию рекурсии.

### Агрегат: возврат значения против общей переменной

Считая что-то по дереву (сумма, высота, диаметр), есть два стиля: **возвращать** результат
снизу вверх (чистая функция, post-order) или копить в **общей переменной**/замыкании. Для
простых сумм возврат чище и без побочных эффектов; но когда узлу нужны сразу несколько
величин от детей (диаметр = max глубина левого + правого, при этом наверх отдаём только
глубину), удобнее вернуть одно значение, а ответ копить в переменной снаружи. Выбор —
читаемость против необходимости: не тащи через возврат то, что проще накопить сбоку.

## ⚠️ Типичные ошибки

1. **Забыт базовый случай** — без проверки `node == nil` рекурсия разыменует nil-указатель.
2. **Неправильный момент записи узла** — место `append` относительно `dfs(node.Left)` и
   `dfs(node.Right)` определяет тип обхода; перепутали — получили не тот порядок.
3. **Переполнение стека на глубоком дереве** — вырожденное в список дерево даёт глубину n;
   используйте итеративный обход со стеком.
4. **Модификация дерева во время обхода** — меняет структуру под рекурсией и ломает её.
5. **Неверная инициализация для путей** — при максимальной сумме пути с отрицательными
   значениями начинайте с `math.MinInt`, а не с 0.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он медленный, и
только потом один проход DFS.

> **Задача.** Дан корень бинарного дерева. Найти его **диаметр** — длину (в рёбрах)
> самого длинного пути между двумя любыми узлами. Путь может и не проходить через корень.
> Пример: дерево `1(2(4(6),5(_,7)),3)` → ответ `4` (путь `6→4→2→5→7`, 4 ребра).

**Шаг 1. Наивно: для каждого узла отдельно считать высоту поддеревьев — O(n²).**

```go
func height(node *TreeNode) int {
    if node == nil {
        return 0
    }
    return 1 + max(height(node.Left), height(node.Right))
}

func diameterNaive(root *TreeNode) int {
    if root == nil {
        return 0
    }
    through := height(root.Left) + height(root.Right) // путь через текущий узел
    left := diameterNaive(root.Left)                  // или целиком в поддереве
    right := diameterNaive(root.Right)
    return max(through, max(left, right))
}
```

Это **работает и проходит тесты**, но `height` вызывается для каждого узла, а сама она
обходит всё поддерево — итого O(n²) на «бамбуке». Узлы у вершины пересчитывают высоту
тех же нижних поддеревьев снова и снова — вот эта повторная работа и есть то, что
убирает один проход.

**Шаг 2. Ключевое наблюдение.** Высота уже считается рекурсивно снизу вверх — это
[post-order](#порядок-обхода-выбирают-по-зависимости-данных): результат узла готов, когда
готовы дети. Значит, в тот самый момент, когда у узла на руках высоты `l` и `r` обоих
поддеревьев, известен и самый длинный путь **через этот узел** — он равен `l + r`. Не нужно
звать отдельную `height`: достаточно по дороге обновлять максимум, а наверх возвращать
свою высоту `1 + max(l, r)`. Это [агрегат через общую переменную](#агрегат-возврат-значения-против-общей-переменной):
возвращаем одно (высоту), а ответ копим сбоку.

**Шаг 3. Оптимум: один DFS, высота + попутный максимум — O(n).**

```go
func diameterOfTree(root *TreeNode) int {
    best := 0
    var height func(*TreeNode) int
    height = func(node *TreeNode) int {
        if node == nil {
            return 0
        }
        l := height(node.Left)
        r := height(node.Right)
        if l+r > best { // путь через node = l + r рёбер
            best = l + r
        }
        return 1 + max(l, r) // наверх отдаём свою высоту
    }
    height(root)
    return best
}
```

**Шаг 4. Трассировка** на дереве `1(2(4(6),5(_,7)),3)` (узлы — в порядке post-order):

| узел | `l` (лев. высота) | `r` (прав. высота) | путь `l+r` | `best` | вернул `1+max(l,r)` |
|------|-------------------|--------------------|------------|--------|---------------------|
| 6    | 0                 | 0                  | 0          | 0      | 1                   |
| 4    | 1                 | 0                  | 1          | **1**  | 2                   |
| 7    | 0                 | 0                  | 0          | 1      | 1                   |
| 5    | 0                 | 1                  | 1          | 1      | 2                   |
| 2    | 2                 | 2                  | 4          | **4**  | 3                   |
| 3    | 0                 | 0                  | 0          | 4      | 1                   |
| 1    | 3                 | 1                  | 4          | 4      | 4                   |

Ответ — `4`. Обрати внимание: каждый узел посетили **ровно раз** и сделали в нём O(1)
работы — отсюда O(n) против O(n²) у наивного варианта. Максимум `best` «защёлкнулся» на
узле `2` (путь `6→4→2→5→7`), хотя сам путь через корень `1` не проходит.

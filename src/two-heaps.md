## 🎬 Визуализация

> 💡 **Интерактивная демонстрация.** Число из потока (жёлтое) попадает в одну из половин, кучи
> балансируются, медиана читается с вершин. Кучи показаны настоящими массивами, как в
> `container/heap`: `[0]` — вершина (синяя), остальное лишь частично упорядочено. Только что
> вставленное число обведено зелёным, перенесённое при балансировке — жёлтым. Под холстом — строка шага и переменные, ниже — ползунок шагов (или ←/→ на клавиатуре) и код с подсветкой строки. Можно подставить свой поток и нажать «⟲ Запустить».

## ⚡ Шаблон для собеседования

```go
func (mf *MedianFinder) AddNum(num int) {
    if mf.lo.Len() == 0 || num <= mf.lo.Top() {
        heap.Push(mf.lo, num) // max-heap: меньшая половина
    } else {
        heap.Push(mf.hi, num) // min-heap: большая половина
    }
    // балансировка: размеры отличаются не более чем на 1
    if mf.lo.Len() > mf.hi.Len()+1 {
        heap.Push(mf.hi, heap.Pop(mf.lo))
    } else if mf.hi.Len() > mf.lo.Len()+1 {
        heap.Push(mf.lo, heap.Pop(mf.hi))
    }
}
// медиана: равные размеры → среднее вершин; иначе вершина большей кучи
```

1. кладём в нужную кучу по сравнению с вершиной max-heap;
2. балансируем размеры переносом вершины;
3. медиана читается с вершин за O(1).

## 📖 Разбор

<details class="algo-details">
<summary>Теория, полная реализация на container/heap и сложность</summary>

Приём **«две кучи»** хранит данные в двух кучах: max-heap для меньшей половины элементов и
min-heap для большей. Медиана разделяет отсортированный набор на две равные части —
держа это разделение, мы получаем медиану из вершин куч за O(1), а вставку — за O(log n),
вместо пересортировки всего набора.

Инвариант после каждой вставки: любой элемент max-heap ≤ любого элемента min-heap;
размеры куч отличаются не более чем на 1.

```go
import "container/heap"

// MaxHeap — меньшая половина (максимум на вершине)
type MaxHeap []int

func (h MaxHeap) Len() int            { return len(h) }
func (h MaxHeap) Less(i, j int) bool  { return h[i] > h[j] } // обратный порядок
func (h MaxHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *MaxHeap) Push(x interface{}) { *h = append(*h, x.(int)) }
func (h *MaxHeap) Pop() interface{} {
    old := *h
    n := len(old)
    x := old[n-1]
    *h = old[:n-1]
    return x
}

// MinHeap — большая половина (минимум на вершине): аналогично, но Less даёт h[i] < h[j]

type MedianFinder struct {
    maxHeap *MaxHeap // все элементы <= медианы
    minHeap *MinHeap // все элементы >= медианы
}

func (mf *MedianFinder) AddNum(num int) {
    if mf.maxHeap.Len() == 0 || num <= (*mf.maxHeap)[0] {
        heap.Push(mf.maxHeap, num)
    } else {
        heap.Push(mf.minHeap, num)
    }
    if mf.maxHeap.Len() > mf.minHeap.Len()+1 {
        heap.Push(mf.minHeap, heap.Pop(mf.maxHeap).(int))
    } else if mf.minHeap.Len() > mf.maxHeap.Len()+1 {
        heap.Push(mf.maxHeap, heap.Pop(mf.minHeap).(int))
    }
}

func (mf *MedianFinder) FindMedian() float64 {
    switch {
    case mf.maxHeap.Len() == mf.minHeap.Len():
        return float64((*mf.maxHeap)[0]+(*mf.minHeap)[0]) / 2.0
    case mf.maxHeap.Len() > mf.minHeap.Len():
        return float64((*mf.maxHeap)[0])
    default:
        return float64((*mf.minHeap)[0])
    }
}
```

**Куча (heap)** — приоритетная очередь: min-heap даёт минимум за O(1), max-heap —
максимум, вставка и удаление — за O(log n). В Go куча реализуется через `container/heap`
поверх среза.

#### Сложность

| Операция     | Время    | Память |
|--------------|----------|--------|
| `AddNum`     | O(log n) | O(n)   |
| `FindMedian` | O(1)     | O(1)   |

</details>

## 🧠 Почему это корректно

Вся корректность держится на **двух инвариантах** и на том, что вставка их сохраняет.

### Инварианты и почему из них следует медиана

1. **Порядок:** любой элемент max-heap ≤ любого элемента min-heap. Значит max-heap —
   это в точности *меньшая половина*, min-heap — *большая*, а граница между ними проходит
   ровно по медиане.
2. **Баланс:** размеры отличаются не более чем на 1.

Из (1) следует, что медиана — на **границе** половин: при нечётном общем числе это
вершина большей кучи, при чётном — среднее вершин обеих. Поэтому `FindMedian` за `O(1)`
смотрит только на вершины — не нужен весь отсортированный набор, нужна лишь **середина**.

### Почему вставка сохраняет инварианты

Шаг 1 — кладём `num` в правильную половину: сравнение с вершиной max-heap решает, в
меньшую или большую половину он попадает → инвариант (1) держится. Шаг 2 — это могло
нарушить баланс (2); чинит **перенос вершины** из переполненной кучи в другую.

Почему перенос не ломает (1)? Переносится **экстремум** — вершина max-heap (наибольший
из меньшей половины) или вершина min-heap (наименьший из большей). Это ровно граничный
элемент: он `≤` всего в min-heap и `≥` всего в max-heap, поэтому, переехав, он
оказывается корректным минимумом/максимумом принимающей кучи. Оба инварианта
восстановлены за одну операцию.

Каждая вставка — одна-две операции с кучей по `O(log n)`.

## ⚙️ Цена на практике

### Почему две кучи, а не отсортированная структура

Отсортированный массив даёт медиану за `O(1)`, но вставку за `O(n)` (сдвиг).
Сбалансированное дерево — `O(log n)` на всё, но тяжелее в реализации. Две кучи дают
`O(log n)` вставку **и** `O(1)` медиану на простых срезах. Фокус: тебе не нужен полный
порядок — нужна только **граница по середине**, а её две кучи и обнажают.

### Скользящая медиана: удаление — вот где сложно

В `SlidingWindowMedian` при сдвиге окна нужно **удалить** выбывший элемент, а куча не
умеет удалять произвольный элемент за `O(log n)` из коробки. Решение — **ленивое
удаление**: пометить выбывший и пропускать, когда он всплывёт на вершину (плюс
балансировать счётчики «эффективных» размеров). Это самая ошибкоопасная часть паттерна —
её и проверяет рандом-тест тренажёра — пакет `exercises/twoheaps`.

**Почему ленивое удаление всё ещё `O(log n)` амортизированно.** Каждый элемент
попадает в кучу один раз и физически выбрасывается один раз — когда сам всплывёт на
вершину. Пометки не добавляют работы сверх этого единственного `Pop`: «протухшую»
вершину снимаем, но это снятие — и есть удаление, оплаченное при входе элемента. За
проход окна получается амортизированно `O(log n)` на шаг — тот же учёт «каждый элемент
входит и выходит ровно раз», что у монотонного дека в
[скользящем окне](sliding-window.md). Опасность не в асимптотике, а в **off-by-one**
счётчиков эффективного размера: именно там, а не в скорости, ломается реализация.

### Паттерн шире медианы

«Поддерживать порог, делящий поток на две части» — это всегда две кучи. В `MaximizeCapital`
(IPO) одна куча хранит проекты, доступные по текущему капиталу, вторая выбирает из них
максимально прибыльный — та же идея «две кучи под две роли».

## ⚠️ Типичные ошибки

1. **Сломанная балансировка** — после каждой вставки разница размеров должна оставаться
   ≤ 1; иначе вершина перестаёт быть медианой.
2. **Перепутаны типы куч** — меньшая половина в max-heap, большая в min-heap; обратный
   выбор нарушает инвариант «maxHeap ≤ minHeap».
3. **Деление на целых** — медиану двух вершин считай через `float64`, иначе потеряешь
   половину (`(2+3)/2 == 2` вместо `2.5`).
4. **Чтение медианы из пустой структуры** — проверяй, что хотя бы одна куча непуста.
5. **Переносится не та вершина** — при балансировке переезжает вершина переполненной кучи,
   а не только что добавленное число. Иначе в меньшую половину может попасть число больше
   чужой вершины, и порядок (1) сломается.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, затем понимание, *почему* он медленный, и
только потом две кучи.

> **Задача.** Числа приходят по одному (поток). Поддерживай структуру с двумя операциями:
> `AddNum(num)` — добавить число; `FindMedian()` — вернуть текущую медиану всех добавленных.
> Медиана — средний элемент отсортированного набора (при чётном размере — среднее двух
> центральных). Пример: добавили `5, 15, 1, 3` → медиана `4.0` (середина `1,3,5,15`).

**Шаг 1. Наивно: хранить срез и сортировать на каждый запрос — O(n log n) на медиану.**

```go
type NaiveMedian struct{ data []int }

func (n *NaiveMedian) AddNum(num int) { n.data = append(n.data, num) }

func (n *NaiveMedian) FindMedian() float64 {
    s := append([]int(nil), n.data...)
    sort.Ints(s)                       // O(n log n) на КАЖДЫЙ запрос
    m := len(s)
    if m%2 == 1 {
        return float64(s[m/2])
    }
    return float64(s[m/2-1]+s[m/2]) / 2.0
}
```

Это **работает и проходит тесты**, но `FindMedian` сортирует весь набор заново на
каждый вызов — `O(n log n)`. Даже если держать срез отсортированным и вставлять
бинарным поиском, вставка стоит `O(n)` из-за сдвига. А ведь после добавления одного
числа порядок почти не меняется — вот эту повторную работу и убирают две кучи.

**Шаг 2. Ключевое наблюдение.** Медиана — это **граница** между меньшей и большей
половиной. Полный порядок нам не нужен — нужна только середина. Если держать меньшую
половину в max-heap, а большую в min-heap так, что любой из max-heap ≤ любого из
min-heap, а размеры отличаются ≤ 1, то медиана всегда лежит на **вершинах** куч. Этот
[инвариант баланса](#инварианты-и-почему-из-них-следует-медиана) при каждой вставке
восстанавливается переносом одной вершины, поэтому полную пересортировку делать не
нужно — она избыточна.

**Шаг 3. Оптимум: две кучи — добавление O(log n), медиана O(1).**

```go
type MedianFinder struct {
    lo *MaxHeap // меньшая половина (макс на вершине)
    hi *MinHeap // большая половина (мин на вершине)
}

func (mf *MedianFinder) AddNum(num int) {
    if mf.lo.Len() == 0 || num <= (*mf.lo)[0] {
        heap.Push(mf.lo, num)          // ≤ вершины max-heap → в меньшую половину
    } else {
        heap.Push(mf.hi, num)          // иначе → в большую
    }
    if mf.lo.Len() > mf.hi.Len()+1 {   // баланс: перенос вершины
        heap.Push(mf.hi, heap.Pop(mf.lo).(int))
    } else if mf.hi.Len() > mf.lo.Len()+1 {
        heap.Push(mf.lo, heap.Pop(mf.hi).(int))
    }
}

func (mf *MedianFinder) FindMedian() float64 {
    switch {
    case mf.lo.Len() == mf.hi.Len():   // чётный размер — среднее двух вершин
        return float64((*mf.lo)[0]+(*mf.hi)[0]) / 2.0
    case mf.lo.Len() > mf.hi.Len():
        return float64((*mf.lo)[0])    // нечётный — вершина большей кучи
    default:
        return float64((*mf.hi)[0])
    }
}
```

`MaxHeap`/`MinHeap` — те же реализации `heap.Interface` поверх среза, что в разделе
«📖 Разбор» (`lo` отдаёт максимум, `hi` — минимум). `heap.Push`/`heap.Pop` стоят
`O(log n)`, чтение вершины `(*mf.lo)[0]` — `O(1)`.

Прогони поток `5,15,1,3,8,7` через две кучи: max-heap держит меньшую половину,
min-heap — большую, медиана читается с их вершин:

| 15       | `[5]`           | `[15]`          | 1 / 1   | **10.0** |
| 1        | `[5, 1]`        | `[15]`          | 2 / 1   | **5.0** |
| 3        | `[3, 1]`        | `[5, 15]`       | 2 / 2   | **4.0** |
| 8        | `[3, 1]`        | `[5, 15, 8]`    | 2 / 3   | **5.0** |
| 7        | `[5, 1, 3]`     | `[7, 15, 8]`    | 3 / 3   | **6.0** |

Обрати внимание на шаг «добавили 3»: `3 ≤ 5` (вершина `lo`) → кладём в `lo`, размеры
становятся `3 / 1`, баланс нарушен → переносим вершину `lo` (это `5`) в `hi`. После
переноса `lo[0]=3`, `hi[0]=5` — граница сместилась ровно на новый граничный элемент,
оба инварианта целы. Каждая вставка — одна-две операции с кучей по `O(log n)`, а
`FindMedian` всегда смотрит лишь на две вершины. (Эта трасса — прогон кода выше,
сверенный с наивной сортировкой: медианы совпали на каждом шаге.)

## 🏗️ Инженерный кейс

> **Ситуация.** Мониторинг задержек сервиса. Идёт поток измерений latency, и надо в любой момент отдавать
> **медиану (p50)** — значение, быстрее которого половина запросов, а медленнее — другая половина.

### 💻 А теперь — построй его (и то, что реально в проде)

В тренажёре ты строишь **два** счётчика перцентилей и сравниваешь. Сигнатуры чистые (только ядро), значения
подаются как `float64` — легко проверять тестами.

**Шаг 1. Две кучи — паттерн главы.** Точная бегущая медиана:

```go
func NewMedianFinder() *MedianFinder
func (m *MedianFinder) Add(x float64)     // положить в нужную половину, сбалансировать
func (m *MedianFinder) Median() float64   // среднее вершин или вершина большей кучи
```

#### ⚙️ Чем это платит в проде (и что берут вместо)

Две кучи дают **точную** медиану, но у них три проблемы для мониторинга: (1) память **O(n)** — хранят
каждое значение; (2) отдают только **медиану**, а не `p99`/`p999`, где живут хвостовые задержки; (3) их
нельзя **сложить** между серверами. Последнее — ключевой senior-урок:

> **Перцентили не аддитивны.** `p99` двух серверов — это **не** среднее их `p99`. Поэтому мониторинг
> хранит задержки как **гистограммы**: их можно складывать между инстансами и окнами времени, а квантиль
> считать уже на объединённой гистограмме. И `p99` из 50 измерений — шум: нужны сотни-тысячи на окно.

Что реально используют:

- **Гистограмма с фиксированными бакетами** — **Prometheus** (`histogram_quantile` линейно интерполирует
  внутри бакета), **HdrHistogram** (латентность, конфигурируемая точность). Память `O(бакетов)` при любом
  потоке, даёт любой квантиль и **складывается** между серверами. Бакеты — логарифмические (1мс, 2, 5, 10…).
- **t-digest** (Ted Dunning; в **Elasticsearch**) — приближённые квантили с упором на точность в хвостах
  (`p99`), тоже мержится.

**Шаг 2. Гистограмма — построй сам.** В том же пакете реализуй боевой вариант (модель Prometheus):

```go
func NewHistogram(upperBounds []float64) *Histogram
func (h *Histogram) Observe(x float64)          // в первый бакет с границей ≥ x
func (h *Histogram) Quantile(q float64) float64 // rank=q·total, интерполяция внутри бакета
func (h *Histogram) Merge(other *Histogram)     // сложить гистограммы (то самое «перцентили не аддитивны»)
```

Подними runner (`cd exercises && go run ./cmd/runner`) и решай прямо здесь. Тесты гоняют медиану (в т.ч.
сверку с сортировкой), квантили гистограммы и слияние двух «серверов»:

Мораль инженера: две кучи — отличный способ **понять**, как держать серединный элемент; но продовый
мониторинг латентности почти всегда стоит на **гистограммах** — за bounded-память, любой квантиль и
**мержимость**. Тот же размен «точность ↔ ресурсы/агрегируемость», что и у [вероятностных
структур](probabilistic-structures.md).

## 🧭 Откуда берутся два указателя: выведем их сами

Правило «мала сумма — левый вправо, велика — правый влево» не нужно зубрить. Оно получается
само, если посмотреть, какие пары перебор проверяет зря, — на массиве виджета ниже.

> **Задача.** Дан отсортированный массив и число `target`. Найди два числа с суммой `target`.
> Пример: `[1, 3, 4, 6, 8, 9, 11, 14]`, `target = 13` → `4 + 9` (индексы 2 и 5).

В лоб — два вложенных цикла: каждое число с каждым правее него.

```go
for i := 0; i < len(arr); i++ {
    for j := i + 1; j < len(arr); j++ {
        if arr[i]+arr[j] == target {
            return i, j
        }
    }
}
```

Восемь чисел — это 28 пар. До `4 + 9` перебор доберётся на 16-й проверке, а если пары нет —
проверит все 28: O(n²).

Посмотри на крайние числа. `1 + 14 = 15` — больше `13`. Но `1` — самое маленькое число, значит
`15` — самая маленькая сумма, в которой вообще участвует `14`. Раз даже она велика, четырнадцать
не войдёт ни в одну пару: вычёркиваем его вместе со всеми семью его парами — одной проверкой.

Теперь крайние `1` и `11`: `1 + 11 = 12` — меньше `13`. Одиннадцать — самое большое из
оставшихся, значит `12` — самая большая сумма с единицей. Единица не дотянула даже с самым
большим — вычёркиваем её со всеми парами. Дальше так же: `3 + 11 = 14` велика — вычёркиваем `11`;
`3 + 9 = 12` мала — вычёркиваем `3`; `4 + 9 = 13` — пара. Пять проверок вместо 28 пар.

Каждая проверка вычёркивает крайнее число слева или справа, поэтому живые числа всегда лежат
подряд между двумя отметками: левая — на самом маленьком живом, правая — на самом большом.
Сумма мала — левая вправо, велика — правая влево.

**Перебор проверяет пары по одной, а два указателя одним сравнением вычёркивают число вместе
со всеми его парами.**

Это встречные два указателя (two pointers): один проход — O(n) времени и O(1) памяти. Виджет
ниже проходит тот же массив по шагам, погасшие ячейки — вычеркнутые числа (на последнем шаге
гаснет всё, кроме найденной пары). Рамка обводит живые числа, её ярлык — сумма крайних и
сравнение с `target`. Ярлык обведён зелёным — сумма мала, следом сдвинется `lo`; голубым —
велика, сдвинется `hi`; залит зелёным — пара найдена. Тот же приём с
внешним циклом — тройки с суммой 0 — в [«📝 Разбор задачи»](#-разбор-задачи).

## ⚡ Шаблон для собеседования

Голый каркас встречных указателей — его и стоит держать в голове:

```go
left, right := 0, len(arr)-1
for left < right {
    sum := arr[left] + arr[right]
    switch {
    case sum == target:
        return left, right // нашли ответ (если нужны все пары — left++ и right--)
    case sum < target:
        left++  // нужна сумма больше
    default:
        right-- // нужна сумма меньше
    }
}
```

1. указатели по краям (`left = 0`, `right = n-1`);
2. считаем величину (сумму / разницу / площадь);
3. сравниваем с целью и двигаем **один** указатель;
4. повторяем, пока `left < right`.

## 📖 Разбор

**Два указателя** (two pointers) — два индекса, которые ходят по массиву или строке и одним
сравнением вычёркивают сразу много кандидатов. Так перебор всех пар за O(n²) превращается в
один проход за **O(n)** при O(1) памяти.

Четыре основных варианта:

- **Встречные указатели** — `left` с начала, `right` с конца, движутся навстречу.
- **Одно направление** — `slow` и `fast` идут с одного края (фильтрация, дедупликация).
- **Три указателя** — разбиение массива на три класса за один проход (Dutch National Flag, ниже).
- **Быстрый и медленный** — движение с разной скоростью (см. [Fast & Slow Pointers](fast-slow-pointers.md)).

#### Встречные указатели

`left` и `right` стоят на краях. Сравниваем сумму с целью: если меньше — двигаем `left`
вправо (нужно больше), если больше — двигаем `right` влево (нужно меньше).

```go
func twoSumSorted(arr []int, target int) (int, int, bool) {
    left, right := 0, len(arr)-1
    for left < right {
        sum := arr[left] + arr[right]
        switch {
        case sum == target:
            return left, right, true
        case sum < target:
            left++ // нужна большая сумма
        default:
            right-- // нужна меньшая сумма
        }
    }
    return 0, 0, false
}
```

Те же встречные указатели проверяют палиндром: сравнивают `s[left]` и `s[right]` и сходятся,
пока символы равны; первое расхождение — не палиндром. В LeetCode 125 указатель сначала
перешагивает всё, что не буква и не цифра, а регистр не различается.

#### Площадь у стенок

Встречные указатели ищут не только пару с суммой. Дан массив высот `h`: две стенки `l` и `r`
держат воду площадью `min(h[l], h[r]) · (r − l)`: высота воды — по низкой стенке, ширина —
расстояние между стенками. Нужна наибольшая (Container With Most Water).
Начни с крайних и пусть левая стенка ниже. Любая другая пара с ней у́же, а выше `h[l]` вода всё
равно не поднимется — площадь только меньше. Левая стенка свой максимум уже показала: запиши
площадь и вычёркивай её, `l++`; ниже правая — зеркально `r--` (при равных — любую). Снова одно
сравнение убирает стенку вместе со всеми её парами. На высотах `1, 8, 6, 2, 5, 4, 8, 3, 7` это
восемь сравнений вместо 36 пар, ответ `49` — стенки `8` и `7`.

#### Одно направление

`slow` — край готовой части, `fast` — разведчик. В удалении дубликатов из отсортированного
массива `nums[0..slow]` — уже отобранные уникальные, и `slow` стоит **на последнем** из них.
Разведчик встретил значение, не равное ему, — сначала `slow++`, потом запись: запись до шага
затёрла бы последний уникальный.

```go
func removeDuplicates(nums []int) int {
    if len(nums) == 0 {
        return 0
    }
    slow := 0
    for fast := 1; fast < len(nums); fast++ {
        if nums[slow] != nums[fast] {
            slow++
            nums[slow] = nums[fast]
        }
    }
    return slow + 1 // длина уникального префикса
}
```

Сдвиг нулей в конец с сохранением порядка остальных — тот же каркас: разведчик `i`, граница
`insertPos`. Здесь `insertPos` стоит **на первой свободной** ячейке после уже собранных
ненулевых, поэтому порядок обратный: сначала запись, потом `insertPos++`.

```go
func moveZeroes(nums []int) {
    insertPos := 0
    for i := 0; i < len(nums); i++ {
        if nums[i] != 0 {
            nums[insertPos], nums[i] = nums[i], nums[insertPos]
            insertPos++
        }
    }
}
```

Разница — в записи: дедупликация **копирует** значение на границу и затирает старое, а сдвиг
нулей **меняет** местами — между `insertPos` и `i` стоят только нули: всё ненулевое разведчик
уже отправил на границу. Ноль с границы уезжает на место разведчика, а пока нулей не
встречалось, `insertPos == i`, и обмен — элемент сам с собой. Во вкладках виджета выше это копия
и обмен.

Третий вариант — три указателя делят массив из трёх видов значений на три зоны за один проход
(Sort Colors, в тренажёре — `DutchFlagSort`); основе он не нужен, поэтому разбор свёрнут.

#### Три указателя: Dutch National Flag

Разложить массив из трёх классов значений (классически `0/1/2` — «голландский флаг»
Дейкстры, он же Sort Colors) за один проход и O(1) памяти. Три границы: `low` — конец
зоны нулей, `high` — начало зоны двоек, `mid` сканирует неразобранное между ними.

```go
func dutchFlagSort(nums []int) {
    low, mid, high := 0, 0, len(nums)-1
    for mid <= high {
        switch nums[mid] {
        case 0:
            nums[low], nums[mid] = nums[mid], nums[low]
            low++
            mid++ // с позиции low мог прийти только 0 или 1 — уже просмотрен
        case 1:
            mid++
        default: // 2
            nums[mid], nums[high] = nums[high], nums[mid]
            high-- // mid НЕ двигаем: элемент с high ещё не классифицирован
        }
    }
}
```

Листай «›» и следи за зонами — они подписаны линейкой под массивом: `0 | 1 | ? | 2`. Залитые
зелёным нули растут слева, двойки в голубой рамке — справа, единицы с голубым оттенком — за
нулями, а `mid` (жёлтая рамка) разгребает неизвестное «?» между ними, от `mid` до `high`. Ключевой момент подсвечен:
после обмена с `high` указатель `mid` **стоит на месте** — приехавший элемент ещё никто
не смотрел:

<div class="algo-viz" data-viz="dutch-flag" data-array="2,0,2,1,1,0"></div>

Инвариант: `nums[0..low)` — нули (круглая скобка: правый конец не входит, как в срезе `nums[0:low]`), `nums[low..mid)` — единицы, всё правее `high` —
двойки; между `mid` и `high` — ещё не просмотренное. Каждый шаг либо двигает `mid`
вперёд, либо сужает `high` — итого O(n). Асимметрия обменов не случайна: с `low`
приезжает уже классифицированный элемент, а с `high` — непросмотренный, поэтому после
обмена с `high` `mid` стоит на месте и проверяет пришедшего.

| Встречные          | O(n)  | O(1)   |
| Одно направление   | O(n)  | O(1)   |
| Три указателя (флаг) | O(n) | O(1)  |

Линейность следует из того, что `left` только растёт, `right` только убывает, а в
варианте «одно направление» каждый указатель проходит массив максимум один раз.

</details>

### Встречные указатели: отбрасывание не теряет ответ

В «🧭» это было на числах, в общем виде так: `arr[left] + arr[right]` — самая **большая**
сумма с `arr[left]` (правее `right` невычеркнутых чисел не осталось) и самая **маленькая** с
`arr[right]` (левее `left` тоже). Поэтому при `sum < target` `arr[left]` не входит ни в одно
решение, а при `sum > target` — `arr[right]`.

Это тот же приём, что и поиск в отсортированной матрице (строки и столбцы возрастают): начав с
правого верхнего угла, одним сравнением отбрасываем целую строку или столбец кандидатов. Угол
самый большой в своей строке и самый маленький в своём столбце. Больше цели — весь его столбец
больше, уходим влево; меньше — вся строка меньше, уходим вниз.

> **Инвариант цикла.** Если решение существует, обе его позиции всегда лежат внутри
> `[left, right]`. Каждый шаг удаляет из диапазона только заведомо непригодный элемент,
> поэтому инвариант сохраняется, а ответ не пропадает.

**Завершаемость:** на каждой итерации либо `left` строго растёт, либо `right` строго
убывает, поэтому за ≤ `n` шагов указатели встретятся (`left < right` перестанет
выполняться). Бесконечного цикла нет, потому что мы никогда не стоим на месте.

### Одно направление: почему достаточно сравнить с последним

В дедупликации инвариант: **`nums[0..slow]` — ровно различные элементы, встреченные к
этому моменту, в исходном порядке.** Когда `nums[fast] != nums[slow]`, текущий элемент
отличается от последнего записанного — значит он новый, пишем его в `slow+1`.

Почему хватает сравнения только с `nums[slow]`, а не со всем префиксом? Потому что
массив **отсортирован**: все дубликаты идут подряд, поэтому «новый» элемент не может
совпасть ни с чем раньше последнего уникального. На неотсортированном массиве это
рассуждение рушится — нужен `map`.

## ⚙️ Цена на практике

`O(n)` у этой техники честный, но есть три места, где инженер платит сверх асимптотики.

### Сортировка — это и есть твоя настоящая сложность

Встречные указатели требуют отсортированного входа. Если сортируешь сам, реальная
сложность задачи — **`O(n log n)`** (сортировка доминирует), а не `O(n)` от прохода.
Не заявляй на собеседовании «O(n)», если на предыдущей строке стоит `sort.Ints`.

### Нужны исходные индексы? Два указателя сломаются

Классическая ловушка LeetCode **Two Sum**: после `sort` исходные индексы потеряны.
Если задача просит вернуть индексы в **исходном** массиве — техника двух указателей
после сортировки даст неверный ответ. Здесь нужен `map[значение]индекс` за `O(n)`
времени и `O(n)` памяти. Развилка по трём вопросам:

- вход уже отсортирован → **два указателя** (`O(1)` памяти);
- не отсортирован и нужны исходные индексы или память не жалко → **хеш-таблица** (`O(n)` памяти);
- не отсортирован, индексы не нужны, а память критична → **сортировка на месте и два указателя**,
  честно `O(n log n)`.

### Мутация на месте и переполнение

Дедупликация и развороты работают **на месте**: никаких аллокаций, ответ —
длина префикса, а вызывающий берёт `nums[:k]`. Это та самая `O(1)` память. Отдельно
держи в голове `arr[left] + arr[right]`: на 64-битных платформах `int` в Go 64-битный, переполнение
маловероятно, но в задачах с большими числами безопаснее сравнивать `target - arr[left]`
с `arr[right]`, чем складывать.

## ⚠️ Типичные ошибки

1. **Применение встречных указателей к неотсортированному массиву** — сначала
   `sort.Ints(arr)`, иначе логика отбрасывания пар неверна.
2. **Неверное условие цикла** — пиши `for left < right`, а не `!=`, чтобы не
   проскочить точку пересечения.
3. **Неправильное направление сдвига** — при `sum < target` двигают `left`, при
   `sum > target` — `right`; перепутать значит пропустить пару: указатель уйдёт от ответа, а не к нему.
4. **Ошибка на единицу (off-by-one) в «одном направлении»** — сначала `slow++`, затем
   `nums[slow] = nums[fast]`, иначе затрёшь нужный элемент.
5. **Забыл обновить результат** в задачах на максимум (площадь, вода) перед сдвигом
   указателей.
6. **Не обработаны границы** — пустой массив или массив из одного элемента.

## 📝 Разбор задачи

Перебор и наблюдение — в [«🧭 Откуда берутся два указателя»](#-откуда-берутся-два-указателя-выведем-их-сами):
одно сравнение вычёркивает крайнее число вместе со всеми его парами. Здесь код и трасса того же
приёма на задаче потруднее: тройка — это пара из «🧭» с внешним циклом по первому числу.

> **Задача (3Sum).** Дан массив `nums`. Найти все **уникальные** тройки `[a, b, c]`
> такие, что `a + b + c = 0`. Порядок троек и элементов внутри не важен.
> Пример: `nums = [-1, 0, 1, 2, -1, -4]` → `[[-1, -1, 2], [-1, 0, 1]]`.

Перебор — тот же, что в «🧭», с третьим вложенным циклом: O(n³), а повторы отсекает множество
уже найденных троек, каждая записана по возрастанию: `−1, 0, 1` (позиции 0, 1, 2) и `0, 1, −1`
(позиции 1, 2, 4) обе станут `[-1, 0, 1]` и совпадут. Виджет показывает, что он проверяет все C(6,3) = 20 троек — столько способов выбрать 3 позиции из 6, — даже когда
ответ давно собран:

<div class="algo-viz" data-viz="three-sum-naive" data-array="-1,0,1,2,-1,-4"></div>

Зафиксируй первое число тройки `nums[i]` — для двух оставшихся нужна пара с суммой `−nums[i]`,
ровно задача из «🧭». Для неё массив сортируют один раз в начале, и сортировка заодно ставит
равные значения рядом — повторы легко перешагнуть, множество найденных троек не нужно.

**Сортировка + два указателя — O(n²).**

```go
func threeSum(nums []int) [][]int {
    sort.Ints(nums)
    var res [][]int
    for i := 0; i < len(nums)-2; i++ {
        if i > 0 && nums[i] == nums[i-1] {
            continue // пропускаем дубль первого элемента
        }
        left, right := i+1, len(nums)-1
        for left < right {
            sum := nums[i] + nums[left] + nums[right]
            switch {
            case sum == 0:
                res = append(res, []int{nums[i], nums[left], nums[right]})
                left++
                right--
                for left < right && nums[left] == nums[left-1] {
                    left++ // перешагиваем дубли слева
                }
                for left < right && nums[right] == nums[right+1] {
                    right-- // перешагиваем дубли справа
                }
            case sum < 0:
                left++ // нужна большая сумма
            default:
                right-- // нужна меньшая сумма
            }
        }
    }
    return res
}
```

Внешний цикл по `i` — O(n), а внутренний проход двумя указателями — O(n), итого O(n²);
сортировка O(n log n) поглощается этим. Память — O(1) сверх результата: множество найденных
троек больше не нужно.

Прогони оптимум на тех же данных: массив сперва сортируется, затем для каждого
фиксированного `i` (подсвечен) пара `left`/`right` сходится навстречу — `left` идёт при
`sum < 0`, `right` при `sum > 0`. Рамка идёт от `i` до `right`, её ярлык — сумма трёх
чисел и её знак, обведённый цветом той плашки, что сдвинется следом. Сравни найденные тройки
с трассировкой ниже. Листинг
виджета — код выше целиком, с двумя циклами перешагивания дублей; на этом входе они ни разу
не срабатывают, а в «Граничных случаях» есть вход «дубли», где левый край перешагивает
повторный `0` сразу после найденной тройки:

**Трассировка** на `nums = [-1, 0, 1, 2, -1, -4]`. После `sort.Ints` →
`[-4, -1, -1, 0, 1, 2]` (индексы `0..5`):

| `i` (`nums[i]`) | `left` | `right` | `sum` | действие | `res` |
|-----------------|--------|---------|-------|----------|-------|
| 0 (`-4`)        | 1…4    | 5       | < 0   | `left++` четырежды, указатели сошлись | — |
| 1 (`-1`)        | 2      | 5       | `−1−1+2 = 0` | запись, `left++` и `right--` | `[-1,-1,2]` |
| 1 (`-1`)        | 3      | 4       | `−1+0+1 = 0` | запись, `left`/`right` разминулись | `[-1,-1,2], [-1,0,1]` |
| 2 (`-1`)        | —      | —       | —     | `nums[2]==nums[1]` → `continue` | — |
| 3 (`0`)         | 4      | 5       | `0+1+2 = 3` > 0 | `right--`, указатели сошлись | — |

Ответ — `[[-1, -1, 2], [-1, 0, 1]]`, совпадает с наивным. Обрати внимание: дубль `-1`
на позиции `i=2` отсекается проверкой `nums[i] == nums[i-1]`, а дубли внутри пары —
перешагиванием после найденной тройки. Без этих двух проверок одна и та же тройка
попала бы в ответ несколько раз.

На шести числах перебор проверяет 20 троек — это быстро. Вот как те же две функции ведут себя

<details class="algo-details">
<summary>Если застрял: квадраты отсортированного массива (<code>SortedSquares</code>)</summary>

Квадраты отсортированного массива с отрицательными числами уже не отсортированы:
`[-2, -1, 0, 2, 3]` даёт `4, 1, 0, 4, 9`. Но самый большой квадрат всегда у одного из краёв —
там числа, самые большие без учёта знака (`|−2| = 2`). Поставь встречные указатели на края, сравни квадраты,
больший запиши в последнюю свободную ячейку ответа и сдвинь его указатель — ответ заполняется
с конца.

</details>

> 🧵 **Конкурентность?** Нет — куда двигать указатели, решает текущее сравнение, и каждый шаг
> зависит от уже пройденного. Это последовательный проход с `O(1)` работы на шаг: параллелить
> нечего, а синхронизация общих указателей съела бы всё. Параллельной тут бывает разве что
> предшествующая **сортировка** (см. [конкурентная сортировка слиянием](k-way-merge.md#-конкурентная-сортировка-слиянием-go)).

**Не спутай с соседом** (вся таблица — в [руководстве по выбору](pattern-selection-guide.md#путаемые-пары-что-обязано-быть-верно)):

- если нужен кусок подряд в исходном порядке, а не пара элементов — [Скользящее окно](sliding-window.md), а не Два указателя: встречные указатели ищут пару в отсортированном массиве, а сортировка перемешает куски подряд.
- если массив уже отсортирован и нужна пара с заданной суммой — Два указателя, а не [Хеш-таблица](hash-table-structure.md): оба решения линейны, но хеш-таблица хранит виденные числа в памяти O(n), а указателям хватает O(1).
- если массив не отсортирован, а сортировать нельзя или потеряются нужные исходные индексы — [Хеш-таблица](hash-table-structure.md), а не Два указателя: сортировка потеряет исходные индексы и сама стоит O(n log n), а таблица «значение → индекс» отвечает за один проход.

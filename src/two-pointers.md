## 🧭 Откуда берутся два указателя: выведем их сами

Правило из карточки — «меньше → `left++`, больше → `right--`» — не нужно зубрить. Оно
получается само, если посмотреть, какие пары перебор проверяет зря. Проследим на задаче из
разбора ниже.

> **Задача (3Sum).** Дан массив `nums`. Найди все разные тройки чисел с суммой 0.
> Пример: `[-1, 0, 1, 2, -1, -4]` → `[-1, -1, 2]` и `[-1, 0, 1]`.

В лоб: три вложенных цикла перебирают все тройки — O(n³). Первый шаг к ускорению очевиден:
зафиксируй первое число тройки `a` — останется найти пару с суммой `−a`. Но если и пару
искать перебором, это всё те же два вложенных цикла.

Посмотри, сколько работы они делают зря. Отсортируем массив: `[-4, -1, -1, 0, 1, 2]`.
Возьмём `a = −4`: нужна пара с суммой `4` среди `[-1, -1, 0, 1, 2]`. Перебор проверит все
10 пар — и ни одна не подойдёт.

А хватило бы одной проверки на каждое число. Пара `(−1, 2)` даёт `1`. Двойка — самое большое
число, значит `1` — самая большая сумма, в которой вообще участвует `−1`. Раз даже она меньше
`4`, пары `(−1, −1)`, `(−1, 0)`, `(−1, 1)` можно не смотреть: эту `−1` вычёркиваем целиком.
Дальше то же со второй `−1`, с `0` (`0 + 2 = 2`) и с `1` (`1 + 2 = 3`) — четыре проверки
вместо десяти.

Зеркально работает и правый край: если самое большое число даже в паре с самым маленьким
даёт сумму больше нужной, вычёркиваем самое большое. Так и получаются два указателя с краёв:
сумма мала — левый вправо, велика — правый влево.

**Перебор проверяет пары по одной, а два указателя одним сравнением вычёркивают число вместе
со всеми его парами.**

Это два указателя (two pointers): внешний цикл по `a` плюс один проход навстречу дают O(n²)
вместо O(n³). Путь от перебора до этого решения, с трассировкой по шагам, — в
[«📝 Разбор задачи»](#-разбор-задачи) ниже.

## ⚡ Шаблон для собеседования

Голый каркас встречных указателей — его и стоит держать в голове:

```go
left, right := 0, len(arr)-1
for left < right {
    sum := arr[left] + arr[right]
    switch {
    case sum == target:
        // нашли ответ
    case sum < target:
        left++  // нужна сумма больше
    default:
        right-- // нужна сумма меньше
    }
}
```

1. указатели по краям (`left = 0`, `right = n-1`);
2. считаем величину (сумму / разницу / площадь);
3. сравниваем с целью и двигаем **один** указатель;
4. повторяем, пока `left < right`.

## 📖 Разбор

**Two Pointers** — техника, в которой по линейной структуре (массив, строка, список)
движутся два индекса, согласованно меняя позиции до выполнения условия. Вместо перебора
всех пар (O(n²)) мы используем отсортированность или монотонность данных, чтобы за один
шаг отбрасывать целые области поиска. Это снижает сложность до **O(n)** при O(1) памяти.

Четыре основных варианта:

- **Встречные указатели** — `left` с начала, `right` с конца, движутся навстречу.
- **Одно направление** — `slow` и `fast` идут с одного края (фильтрация, дедупликация).
- **Три указателя** — разбиение массива на три класса за один проход (Dutch National Flag, ниже).
- **Быстрый и медленный** — движение с разной скоростью (см. [Fast & Slow Pointers](fast-slow-pointers.md)).

<summary>Три варианта с кодом и сложность</summary>

#### Встречные указатели

`left` и `right` стоят на краях. Сравниваем сумму с целью: если меньше — двигаем `left`
вправо (нужно больше), если больше — двигаем `right` влево (нужно меньше).

```go
func twoSumSorted(arr []int, target int) (int, int, bool) {
    left, right := 0, len(arr)-1
    for left < right {
        sum := arr[left] + arr[right]
        switch {
        case sum == target:
            return left, right, true
        case sum < target:
            left++ // нужна большая сумма
        default:
            right-- // нужна меньшая сумма
        }
    }
    return 0, 0, false
}
```

#### Одно направление

`slow` отмечает границу обработанной части, `fast` сканирует массив. Применяется для
удаления дубликатов из отсортированного массива на месте: `arr[0..slow]` всегда
содержит уникальные элементы.

```go
func removeDuplicates(nums []int) int {
    if len(nums) == 0 {
        return 0
    }
    slow := 0
    for fast := 1; fast < len(nums); fast++ {
        if nums[slow] != nums[fast] {
            slow++
            nums[slow] = nums[fast]
        }
    }
    return slow + 1 // длина уникального префикса
}
```

#### Три указателя: Dutch National Flag

Разложить массив из трёх классов значений (классически `0/1/2` — «голландский флаг»
Дейкстры, он же Sort Colors) за один проход и O(1) памяти. Три границы: `low` — конец
зоны нулей, `high` — начало зоны двоек, `mid` сканирует неразобранное между ними.

```go
func dutchFlagSort(nums []int) {
    low, mid, high := 0, 0, len(nums)-1
    for mid <= high {
        switch nums[mid] {
        case 0:
            nums[low], nums[mid] = nums[mid], nums[low]
            low++
            mid++ // с позиции low мог прийти только 0 или 1 — уже просмотрен
        case 1:
            mid++
        default: // 2
            nums[mid], nums[high] = nums[high], nums[mid]
            high-- // mid НЕ двигаем: элемент с high ещё не классифицирован
        }
    }
}
```

Листай «›» и следи за зонами — они подписаны линейкой под массивом: `0 | 1 | ? | 2`. Залитые
зелёным нули растут слева, двойки в голубой рамке — справа, единицы с голубым оттенком — за
нулями, а `mid` (жёлтая рамка) разгребает неизвестное «?» между ними, от `mid` до `high`. Ключевой момент подсвечен:
после обмена с `high` указатель `mid` **стоит на месте** — приехавший элемент ещё никто
не смотрел:

<div class="algo-viz" data-viz="dutch-flag" data-array="2,0,2,1,1,0"></div>

Инвариант: `nums[0..low)` — нули, `nums[low..mid)` — единицы, всё правее `high` —
двойки; между `mid` и `high` — ещё не просмотренное. Каждый шаг либо двигает `mid`
вперёд, либо сужает `high` — итого O(n). Асимметрия обменов не случайна: с `low`
приезжает уже классифицированный элемент, а с `high` — непросмотренный, поэтому после
обмена с `high` `mid` стоит на месте и проверяет пришедшего.

#### Сложность

| Вариант            | Время | Память |
|--------------------|-------|--------|
| Встречные          | O(n)  | O(1)   |
| Одно направление   | O(n)  | O(1)   |
| Три указателя (флаг) | O(n) | O(1)  |

Линейность следует из того, что `left` только растёт, `right` только убывает, а в
варианте «одно направление» каждый указатель проходит массив максимум один раз.

## 🧠 Почему это корректно

Вопрос, который отделяет «работает на примерах» от «я знаю, почему»: **почему,
сдвигая указатель, мы не выбрасываем правильную пару?**

### Встречные указатели: отбрасывание не теряет ответ

Массив отсортирован. На каждом шаге `arr[left] + arr[right]` — это **самая большая**
сумма из всех пар, где левый элемент равен `arr[left]` (потому что `right` указывает
на самый большой из оставшихся). Отсюда два точных утверждения:

- Если `sum < target`, то даже максимальная пара с `arr[left]` не дотягивает до цели.
  Значит `arr[left]` **не входит ни в одно решение** — его можно отбросить навсегда
  (`left++`), ничего не потеряв.
- Если `sum > target`, то `arr[left] + arr[right]` — самая **маленькая** сумма с
  `arr[right]` (левее некуда). Раз и она велика, `arr[right]` не входит ни в одно
  решение → `right--`.

Это тот же приём, что и поиск в отсортированной матрице: одним сравнением отбрасываем
целую строку или столбец кандидатов.

> **Инвариант цикла.** Если решение существует, обе его позиции всегда лежат внутри
> `[left, right]`. Каждый шаг удаляет из диапазона только заведомо непригодный элемент,
> поэтому инвариант сохраняется, а ответ не пропадает.

**Завершаемость:** на каждой итерации либо `left` строго растёт, либо `right` строго
убывает, поэтому за ≤ `n` шагов указатели встретятся (`left < right` перестанет
выполняться). Бесконечного цикла нет, потому что мы никогда не стоим на месте.

### Одно направление: почему достаточно сравнить с последним

В дедупликации инвариант: **`nums[0..slow]` — ровно различные элементы, встреченные к
этому моменту, в исходном порядке.** Когда `nums[fast] != nums[slow]`, текущий элемент
отличается от последнего записанного — значит он новый, пишем его в `slow+1`.

Почему хватает сравнения только с `nums[slow]`, а не со всем префиксом? Потому что
массив **отсортирован**: все дубликаты идут подряд, поэтому «новый» элемент не может
совпасть ни с чем раньше последнего уникального. На неотсортированном массиве это
рассуждение рушится — нужен `map`.

## ⚙️ Цена на практике

`O(n)` у этой техники честный, но есть три места, где инженер платит сверх асимптотики.

### Сортировка — это и есть ваша настоящая сложность

Встречные указатели требуют отсортированного входа. Если вы сортируете сами, реальная
сложность задачи — **`O(n log n)`** (сортировка доминирует), а не `O(n)` от прохода.
Не заявляйте на собеседовании «O(n)», если на предыдущей строке стоит `sort.Ints`.

### Нужны исходные индексы? Два указателя сломаются

Классическая ловушка LeetCode **Two Sum**: после `sort` исходные индексы потеряны.
Если задача просит вернуть индексы в **исходном** массиве — техника двух указателей
после сортировки даст неверный ответ. Здесь нужен `map[значение]индекс` за `O(n)`
времени и `O(n)` памяти. Развилка по трём вопросам:

- вход уже отсортирован или порядок не важен → **два указателя** (`O(1)` памяти);
- нужны исходные индексы / память не жалко → **хеш-таблица** (`O(n)` памяти);
- память критична, можно сортировать на месте → **два указателя** после сортировки.

### Мутация на месте и переполнение

Дедупликация и развороты работают **на месте**: никаких аллокаций, ответ —
длина префикса, а вызывающий берёт `nums[:k]`. Это та самая `O(1)` память. Отдельно
держите в голове `arr[left] + arr[right]`: на 64-битных платформах `int` в Go 64-битный, переполнение
маловероятно, но в задачах с большими числами безопаснее сравнивать `target - arr[left]`
с `arr[right]`, чем складывать.

## ⚠️ Типичные ошибки

1. **Применение встречных указателей к неотсортированному массиву** — сначала
   `sort.Ints(arr)`, иначе логика отбрасывания пар неверна.
2. **Неверное условие цикла** — используйте `for left < right`, а не `!=`, чтобы не
   проскочить точку пересечения.
3. **Неправильное направление сдвига** — при `sum < target` двигают `left`, при
   `sum > target` — `right`; перепутать значит зациклиться или пропустить пару.
4. **Off-by-one в «одном направлении»** — сначала `slow++`, затем
   `nums[slow] = nums[fast]`, иначе затрёте нужный элемент.
5. **Забыли обновить результат** в задачах на максимум (площадь, вода) перед сдвигом
   указателей.
6. **Не обработаны границы** — пустой массив или массив из одного элемента.

## 📝 Разбор задачи

Пройдём путь от наивного решения к оптимальному — так, как стоит рассуждать на
собеседовании: сначала рабочий перебор, потом понимание, *почему* он медленный, и
только затем сведение к двум указателям.

> **Задача (3Sum).** Дан массив `nums`. Найти все **уникальные** тройки `[a, b, c]`
> такие, что `a + b + c = 0`. Порядок троек и элементов внутри не важен.
> Пример: `nums = [-1, 0, 1, 2, -1, -4]` → `[[-1, -1, 2], [-1, 0, 1]]`.

**Шаг 1. Наивно: перебрать все тройки — O(n³).**

```go
func threeSumNaive(nums []int) [][]int {
    n := len(nums)
    seen := make(map[[3]int]bool)
    var res [][]int
    for i := 0; i < n; i++ {
        for j := i + 1; j < n; j++ {
            for k := j + 1; k < n; k++ {
                if nums[i]+nums[j]+nums[k] == 0 {
                    t := []int{nums[i], nums[j], nums[k]}
                    sort.Ints(t)
                    key := [3]int{t[0], t[1], t[2]}
                    if !seen[key] { // дубли разных порядков отсекаем набором
                        seen[key] = true
                        res = append(res, t)
                    }
                }
            }
        }
    }
    return res
}
```

Это **работает и проходит тесты**, но делает O(n³) операций: три вложенных цикла
честно перебирают все сочетания. Вдобавок приходится держать `map` для отсева
дубликатов — лишняя память на то, что отсортированный массив дал бы даром.

Прогоните перебор по шагам: три указателя `i`, `j`, `k` независимо обходят массив, и
каждая тройка с суммой 0 подсвечивается (повторные — отсекает set). Над списком найденных —
сумма текущей тройки, а метрика «проверено» считает, сколько из всех C(6,3) = 20 троек уже
перебрано: перебор проверяет их **все**, даже когда ответ давно собран:

<div class="algo-viz" data-viz="three-sum-naive" data-array="-1,0,1,2,-1,-4"></div>

**Шаг 2. Ключевое наблюдение.** Зафиксируем первый элемент тройки `nums[i]`. Тогда для
оставшихся двух нужна пара с суммой `−nums[i]` — это ровно задача [поиска пары в
отсортированном массиве](#встречные-указатели-отбрасывание-не-теряет-ответ). Отсортировав
вход, мы получаем монотонность: при сумме меньше цели двигаем левый указатель вправо,
при большей — правый влево, не пропуская ни одной пары. Сортировка же даёт и
дедупликацию даром — одинаковые значения идут подряд, и их легко перешагнуть.

**Шаг 3. Оптимум: сортировка + два указателя — O(n²).**

```go
func threeSum(nums []int) [][]int {
    sort.Ints(nums)
    var res [][]int
    for i := 0; i < len(nums)-2; i++ {
        if i > 0 && nums[i] == nums[i-1] {
            continue // пропускаем дубль первого элемента
        }
        left, right := i+1, len(nums)-1
        for left < right {
            sum := nums[i] + nums[left] + nums[right]
            switch {
            case sum == 0:
                res = append(res, []int{nums[i], nums[left], nums[right]})
                left++
                right--
                for left < right && nums[left] == nums[left-1] {
                    left++ // перешагиваем дубли слева
                }
                for left < right && nums[right] == nums[right+1] {
                    right-- // перешагиваем дубли справа
                }
            case sum < 0:
                left++ // нужна большая сумма
            default:
                right-- // нужна меньшая сумма
            }
        }
    }
    return res
}
```

Внешний цикл по `i` — O(n), а внутренний проход двумя указателями — O(n), итого O(n²);
сортировка O(n log n) поглощается этим. Память — O(1) сверх результата (`map` больше
не нужен).

Прогоните оптимум на тех же данных: массив сперва сортируется, затем для каждого
фиксированного `i` (подсвечен) пара `left`/`right` сходится навстречу — `left` идёт при
`sum < 0`, `right` при `sum > 0`. Сравните найденные тройки с трассировкой ниже. Листинг
виджета — код выше целиком, с двумя циклами перешагивания дублей; на этом входе они ни разу
не срабатывают, а в «Граничных случаях» есть вход «дубли», где левый край перешагивает
повторный `0` сразу после найденной тройки:

**Шаг 4. Трассировка** на `nums = [-1, 0, 1, 2, -1, -4]`. После `sort.Ints` →
`[-4, -1, -1, 0, 1, 2]` (индексы `0..5`):

| `i` (`nums[i]`) | `left` | `right` | `sum` | действие | `res` |
|-----------------|--------|---------|-------|----------|-------|
| 0 (`-4`)        | 1…4    | 5       | < 0   | `left++` четырежды, указатели сошлись | — |
| 1 (`-1`)        | 2      | 5       | `−1−1+2 = 0` | запись, `left++` и `right--` | `[-1,-1,2]` |
| 1 (`-1`)        | 3      | 4       | `−1+0+1 = 0` | запись, `left`/`right` разминулись | `[-1,-1,2], [-1,0,1]` |
| 2 (`-1`)        | —      | —       | —     | `nums[2]==nums[1]` → `continue` | — |
| 3 (`0`)         | 4      | 5       | `0+1+2 = 3` > 0 | `right--`, указатели сошлись | — |

Ответ — `[[-1, -1, 2], [-1, 0, 1]]`, совпадает с наивным. Обрати внимание: дубль `-1`
на позиции `i=2` отсекается проверкой `nums[i] == nums[i-1]`, а дубли внутри пары —
перешагиванием после найденной тройки. Без этих двух проверок одна и та же тройка
попала бы в ответ несколько раз.

**Вывод.** **Отсортированные** данные + поиск пары/тройки под условие суммы — сигнал **двух указателей** с
O(1) памятью. Если массив не отсортирован и память не жалко — хеш-множество проще; отсортирован — два
указателя элегантнее и экономнее.

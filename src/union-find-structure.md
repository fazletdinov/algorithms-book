> 🧭 **Зачем отдельная глава.** Union-Find — это **лес деревьев в массиве `parent[]`**: каждое
> множество — дерево, его корень — представитель. Вся механика — две операции (`Find` со сжатием
> пути и `Union` по размеру) плюс две оптимизации, дающие почти константу. Пока не увидел, как путь
> к корню сжимается, а меньшее дерево подвешивается под большее, эти оптимизации — просто слова.
> Здесь строим структуру; применения — компоненты связности и цикл, когда рёбра приходят по
> одному, и [MST Краскала](advanced-graph-algorithms.md). Те же компоненты и цикл обходом, без
> DSU, — в главе [Графы](graphs.md).

## 🧱 Как устроено

Вся структура — это **один массив `parent[]`**: `parent[i]` — родитель элемента `i` в лесу, а у
корня `parent[i] == i`. Массив `size[]` (или `rank[]`) хранит размер дерева для балансировки.

```go
type UnionFind struct {
    parent []int
    size   []int
}

func NewUnionFind(n int) *UnionFind {
    uf := &UnionFind{parent: make([]int, n), size: make([]int, n)}
    for i := range uf.parent {
        uf.parent[i] = i // каждый сам себе корень
        uf.size[i] = 1
    }
    return uf
}
```

<div class="algo-fig" data-fig="tree" data-forest data-tree="0!(1,3,4,5,6); 2!" data-titles="множество {0,1,3,4,5,6}; множество {2} — одиночка" data-array="0,0,2,0,0,0,0" data-array-label="parent" data-link="label" data-caption="parent = [0, 0, 2, 0, 0, 0, 0] после нескольких Union: ребро ведёт от i к parent[i]; синие — корни, у них parent[i] == i. Наведи на элемент или его ячейку"></div>

Три факта, которые держат всё:

1. **Корень представляет множество.** Два элемента в одной группе тогда и только тогда, когда у
   них **один корень**. Поэтому `Find` сводит вопрос «в одной ли группе» к сравнению корней.
2. **Union меняет одну ссылку.** Объединить две группы — это подвесить корень одного дерева под
   корень другого: `parent[корень1] = корень2`. Одна запись — и группы слиты.
3. **Высота дерева — это и есть стоимость.** Find поднимается до корня, поэтому цена = высоте.
   Без балансировки дерево вырождается в цепочку (O(n)); сжатие пути и объединение по размеру
   держат деревья плоскими.

## 🔗 Объединение: `Union` (по размеру)

Объединить группы `x` и `y` — найти их корни и **подвесить меньшее дерево под большее** (по
размеру или рангу). Балансировка не даёт дереву расти в высоту.

```go
func (uf *UnionFind) Union(x, y int) bool {
    rx, ry := uf.Find(x), uf.Find(y)
    if rx == ry {
        return false           // уже в одном множестве
    }
    if uf.size[rx] < uf.size[ry] {
        rx, ry = ry, rx        // меньшее — под большее
    }
    uf.parent[ry] = rx         // подвешиваем
    uf.size[rx] += uf.size[ry]
    return true
}
```

> 💡 **Демонстрация объединения.** 7 одиночных элементов, серия `Union`. На каждом шаге находятся
> корни и меньшее дерево подвешивается под большее — деревья остаются плоскими. Видно, как из
> одиночек собирается одна компонента. Подставь свои элементы и пары.

## 🔎 Поиск: `Find` (сжатие пути)

`Find(x)` поднимается по `parent` до корня. Главная оптимизация — **сжатие пути**: после подъёма
все узлы пути подвешиваются **прямо к корню**, чтобы следующие запросы были мгновенными.

```go
func (uf *UnionFind) Find(x int) int {
    root := x
    for uf.parent[root] != root {  // идём к корню
        root = uf.parent[root]
    }
    for uf.parent[x] != root {     // сжатие пути
        uf.parent[x], x = root, uf.parent[x]
    }
    return root
}
```

> 💡 **Демонстрация поиска со сжатием.** Намеренно вытянутая цепочка `4 → 3 → 2 → 1 → 0`. `Find(4)`
> поднимается до корня `0`, а затем **подвешивает все узлы пути прямо к `0`** — дерево схлопывается
> в плоское. Следующий `Find` любого из них — один шаг.

<div class="algo-viz" data-viz="union-find-find" data-parent="0,0,1,2,3" data-find="4"></div>

«В одной ли группе» — это просто `Find(a) == Find(b)`: сравниваем представителей. Именно так
Union-Find ловит цикл в неориентированном графе (ребро `(a, b)`, у которых уже общий корень) и
строит компоненты связности.

## 🧠 Почему это корректно

<div class="algo-explain" data-key="union-find-structure">
  <div class="algo-explain__item">
    <div class="algo-explain__q">Какой инвариант хранит DSU и почему сжатие пути его не нарушает?</div>
    <div class="algo-explain__ref">Инвариант: все элементы одного множества лежат в одном дереве и имеют один корень. <code>Union</code> его сохраняет (после слияния у всех общий корень), <code>Find</code> им пользуется (равные корни ⟺ одна группа). Сжатие пути меняет <code>parent</code>, но <b>не меняет корень</b> ни одного узла — принадлежность множеству остаётся прежней.</div>
  </div>
  <div class="algo-explain__item">
    <div class="algo-explain__q">Почему объединение по размеру даёт глубину <code>O(log n)</code> даже без сжатия путей?</div>
    <div class="algo-explain__ref">Глубина узла увеличивается на 1, только когда его дерево подвешивают под не меньшее, — а тогда размер дерева, в котором он живёт, минимум <b>удваивается</b>. Удвоений от 1 до <code>n</code> бывает не больше <code>log₂ n</code>, вот и потолок глубины. Вместе со сжатием пути получается амортизированные <code>O(α(n))</code>, с одной оптимизацией из двух — <code>O(log n)</code>, без обеих — <code>O(n)</code>.</div>
  </div>
</div>

### Корень — инвариант множества

Инвариант: все элементы одного множества лежат в одном дереве и имеют один корень. `Union`
сохраняет его (слил два дерева — у всех теперь общий корень), `Find` им пользуется (равные
корни ⟺ одна группа). Сжатие пути меняет `parent`, но **не меняет корень** ни одного узла —
поэтому принадлежность множеству не нарушается.

### Почему сжатие + по размеру дают почти `O(1)`

- **Объединение по размеру/рангу** гарантирует, что при слиянии под корень уходит меньшее дерево,
  поэтому высота растёт логарифмически, а не линейно: `Find` — O(log n) даже без сжатия. Почему
  логарифм: глубина узла увеличивается на 1, только когда его дерево подвешивают под **не меньшее**, —
  а тогда размер дерева, в котором он живёт, минимум **удваивается**. Удвоений от 1 до `n` бывает не
  больше `log₂ n` — вот и потолок глубины.
- **Сжатие пути** дополнительно «расплющивает» деревья при каждом `Find`: пройденные узлы
  оказываются прямо под корнем.

Вместе эти две оптимизации дают амортизированную сложность **O(α(n))**, где α — обратная функция
Аккермана; для любого мыслимого `n` это `≤ 4`, то есть практически константа. Применяешь только
одну из двух — получаешь O(log n); ни одной — O(n).

### Почему DSU умеет только объединять

Структура хранит лишь `parent` к корню — «куда я подвешен». Разъединить элемент назад нельзя:
непонятно, на какие именно подмножества разваливать дерево, и сжатие пути уже потеряло исходную
форму. Задачи на динамическое **разъединение** решают иначе (например, офлайн — обработкой
операций в обратном порядке, превращая удаления в добавления).

## ⚙️ Цена на практике

### Когда брать Union-Find

DSU незаменим, когда нужно **только объединять группы и спрашивать принадлежность**: компоненты
связности, цикл в неориентированном графе, [MST Краскала](advanced-graph-algorithms.md),
эквивалентности (аккаунты, друзья, заливка областей). Это on-line структура: операции приходят
потоком, ответ — сразу.

### Массив вместо указателей

`parent[]` и `size[]` — два целочисленных массива, никаких узлов и указателей: плотная память,
дружелюбно к кэшу, тривиально сериализуется. Это одна из самых дешёвых по константе структур.

### Ранг или размер — почти всё равно

Балансировать можно по **рангу** (оценка высоты) или по **размеру** (число узлов) — обе дают тот
же класс сложности. Размер чуть нагляднее и сразу отвечает на «сколько элементов в группе».
Главное — балансировать хоть как-то и не забыть сжатие пути.

## ⚠️ Типичные ошибки

1. **Забыли сжатие пути или балансировку** — деревья вырождаются в цепочки, Find деградирует до O(n).
2. **Union без Find корней** — `parent[x] = y` вместо `parent[Find(x)] = Find(y)` ломает структуру.
3. **Подвесили большее под меньшее** — теряется балансировка; всегда меньшее под большее.
4. **Попытка разъединить** — обычный DSU этого не умеет; нужен другой подход.
5. **Не инициализировали `parent[i] = i`** — корней нет, Find зациклится или вернёт мусор.

## 🎯 Где это встречается на собеседовании

На собеседовании DSU почти никогда не просят написать «просто так». Его прячут в задачу, где
вопрос один из трёх:

- **«Эта связь лишняя?»** — `Union` вернул `false`: концы уже были в одной группе, и новая связь
  замыкает цикл;
- **«Сколько групп осталось?»** — счётчик `Count`: каждый успешный `Union` уменьшает его на 1;
- **«Эти двое в одной группе?»** — `Find(a) == Find(b)`, но только после того, как склеено всё,
  что надо склеить.

Ниже — по задаче на каждый вопрос. Все три решаются и обходом графа из главы [Графы](graphs.md):
DSU выигрывает там, где связи приходят **по одной** и ответ нужен сразу, — тогда обход пришлось бы
запускать заново на каждую связь.

### Лишняя связь (LeetCode 684)

Сеть из `n` узлов была деревом — связной и без циклов. В неё добавили ещё одну связь. Найди связь,
без которой сеть снова станет деревом; если подходят несколько — ту, что стоит в списке позже.

Прокладываем связи по порядку и спрашиваем у каждой: «её концы уже связаны?». Возьмём
`[[1,2],[2,3],[3,4],[1,4],[1,5]]`:

| Связь | `Find` концов | `Union` | Группы после шага |
|---|---|---|---|
| `[1,2]` | разные | `true` | {1,2} {3} {4} {5} |
| `[2,3]` | разные | `true` | {1,2,3} {4} {5} |
| `[3,4]` | разные | `true` | {1,2,3,4} {5} |
| `[1,4]` | **общий корень** | `false` | — ответ `[1,4]` |

Почему эта связь — самая поздняя из подходящих? Цикл здесь `1–2–3–4–1`, и убрать можно любую его
связь. Но цикл появился ровно в тот момент, когда пришла `[1,4]`: до неё все связи цикла ещё ничего
не замыкали. Значит, `[1,4]` стоит в списке позже остальных связей цикла.

```go
func FindRedundantConnection(edges [][]int) []int {
	uf := NewUnionFind(len(edges) + 1) // узлы 1…n, n = len(edges)
	for _, e := range edges {
		if !uf.Union(e[0], e[1]) { // концы уже в одной группе — цикл
			return e
		}
	}
	return nil
}
```

Обходом то же самое — «перед каждой связью проверь BFS, есть ли уже путь между её концами»: это
O(n) на связь и O(n²) всего. На 10⁵ узлов это больше десяти секунд против миллисекунд у DSU
(замер — в тесте масштаба пакета `dsu`).

### Дерево ли это (LeetCode 261)

Даны `n` вершин и список рёбер. Дерево ли это: всё связано и циклов нет?

Счёт рёбер отвечает на половину вопроса сразу: у дерева на `n` вершинах **ровно `n − 1` ребро**.
Рёбер больше — цикл обязательно есть, меньше — кто-то отрезан. Но ровно `n − 1` ещё не гарантия.
Пример: `n = 4`, рёбра `[[0,1],[1,2],[2,0]]` — их три, как и надо, но третье замыкает треугольник,
а вершина 3 осталась одна.

Поэтому вторая проверка — тот же вопрос, что в 684: «ребро не лишнее?».

```go
func ValidTree(n int, edges [][]int) bool {
	if len(edges) != n-1 {
		return false
	}
	uf := NewUnionFind(n)
	for _, e := range edges {
		if !uf.Union(e[0], e[1]) { // цикл: одно ребро потрачено впустую
			return false
		}
	}
	return true // n−1 успешный Union: групп стало n − (n−1) = 1
}
```

Почему без отдельной проверки связности? `Count` начинается с `n` и падает на 1 при каждом
успешном `Union`. Если все `n − 1` объединений удались, групп осталась ровно одна — всё связано.
На том же треугольнике: 4 → 3 → 2, а третье ребро `Union` отклоняет — ответ `false`.

### Равенства и неравенства (LeetCode 990)

Даны строки вида `"a==b"` и `"a!=b"`. Можно ли дать переменным значения так, чтобы выполнилось всё
сразу? Равенства действуют цепочкой: из `a==b` и `b==c` следует `a = c`.

Равенство склеивает переменные в группу — это `Union`. Неравенство ломает всё, только если его
концы оказались в одной группе. Ловушка — в порядке. Возьмём `["a!=c", "a==b", "b==c"]`:

- если проверять строки по одной, на `a!=c` переменные `a` и `c` ещё в разных группах — вроде бы
  всё хорошо. А через две строки `a`, `b`, `c` склеятся в одну группу, и неравенство нарушится;
- поэтому **два прохода**: сначала все `==` (склеили {a, b, c}), потом все `!=`. На `a!=c`:
  `Find(a) == Find(c)` — противоречие, ответ `false`.

Имена переменных — строки, а DSU работает с номерами `0…k−1`. Мостик — `map` «имя → номер»:
встретили имя впервые — выдали ему следующий номер.
